## 2. The design in one breath

Goober is a bet that agents will write most software, and that the answer to not trusting them is "better boxes, with finer scope" [000 §Introduction]. It is explicitly a research project that should be **useful as a single binary on a developer's machine from day one**, with a bias towards play [005 §Developer Velocity and the Sandbox].

**The manifest.** A box is an ephemeral WASM process with no POSIX inheritance [000 §The Foundational Thinking]. Its manifest is "the executive summary of what a box can do" [150 §Deeper on Manifests]. A manifest is either a **box manifest** or a **config**, which is a manifest with no box [150 §Two kinds of manifest; 012 §A config is a manifest with no box]. Every field now has one definition in one place [150, throughout]. Every manifest lists its domains, and **the domain is the primary key of every conflict** [019 §The domain comes first]. Static content and templates are **embedded directly in manifests**, as plain strings or base64 [070 §Static content].

**Identity and access.** Identity is **per domain**: each primary domain is its own realm [013 §Identity is per domain]. The built-in identity service is openly labeled as high risk, "vibed," behind a sound contract [013 §A warning about the built-in identity service]. Domains are a host registry of primaries and redirects, with optional verification [015 §The domain registry; §Registering a domain].

**Routes and calls.** Overlapping routes resolve by **priority**, and a **share** lets a new box peel off part of a URL's traffic [019 §Priority; §Peeling traffic away]. Configs set header properties in bulk, with per-property priority, and declare rewrites using a deliberately tiny pattern language [012 §Priority is per property; §The pattern language]. Boxes call each other through **internal routes** that carry the caller's authority, never more [039 §Whose call is it?]. Data crosses the host boundary by copying, with a relocating fast path, and the host never trusts a pointer [120 §Getting data out].

**Shipping and operating.**
- Versions are hash-named artifacts [310 §The artifact].
- They are approved by a person, or by **policies** that cover every change [305 §Policies].
- They go live in `go`, `slow`, or `shadow` mode, with automatic rollback on bad health [305 §Deployment modes].
- Operations happen on a reserved panel that never sees user data [300 §Access logs].

**Stability.** Products stay unchanged through **host capabilities** with swappable providers, OpenAPI services that can be **redirected to adapter boxes**, **pins** on every piece of host code a box depends on, and **replay** of every product before each host release [330, throughout].

## 4. What is unique

The good news first, as always, and today it comes in buckets!

### 4.1 Contracts that outlive vendors

The author's own stability notes are the best idea of the day. Boxes code against **host capabilities** like `send-email@1`, while operators swap the provider underneath [330 §Host capabilities: stable contracts, swappable providers]. Any OpenAPI service can later be **redirected to an adapter box** without touching the caller [330 §OpenAPI services: redirect to an adapter box]. "Most companies don't survive for 30 years. Contracts can" [330 §Stability: Controlling the Entire World]. Plenty of platforms offer swappable providers. Very few promise that a product's *code* never changes when a vendor dies, and none I know of make the swap a provable, dependency-only, auto-approvable change [330 §Dependency-only updates; 305 §Policies]. That is genuinely new, and it is the beating heart of goal 2.

### 4.2 Peeling traffic one URL at a time

Priority plus share means a new box can take 5% of one URL from an old box, with no redeploy and no hole [019 §Peeling traffic away]. This is the strangler-fig pattern built into routing itself, with A/B testing *between different boxes* as a side effect. Delightful!

### 4.3 Approval by kind of change

A version is approved automatically only when policies cover *every* change in it, and some kinds of change can never be waived: more reach, more power, less safety, or taking over another route [305 §Policies]. `interior_ok`, where the code changed but the manifest didn't, is the black-box philosophy turned into automation [305 §Policies]. It's an approval system that reads perimeters, not code, exactly as the introduction promised [000 §The Foundational Thinking].

### 4.4 Operations that never see a person

Access logs carry no user ids, IPs, bodies, or headers. Hashes are keyed so short bodies can't be guessed back. The *who* lives only in audits joined by request id [300 §Access logs]. Deployment comparison reports are noisy on purpose [310 §The comparison report]. Agents can then be given operational data freely, which is what makes agentic operators safe.

### 4.5 A pattern language with no regex

`{name}` matches one segment, `{name*}` matches the rest, and there is nothing else: no backtracking and no surprises [012 §The pattern language]. Giving up power for predictability is exactly right for a perimeter people must read.

### 4.6 Still shining

Removing words from the vocabulary, signature-keyed sharing, the predictive checker, signal-only pub/sub, and email addresses as capabilities all remain distinctive [020 §Generated code; 025 §Can a box even behave well?; 040 §Why the last write is all that matters; 038 §What makes this special].

## 6. Limits

Now for the delicious medicine!

### 6.1 The limits

1. **The cost model is still missing.** It's now load-bearing everywhere: health thresholds [305 §Deployment modes], guardrails [310 §Splitting traffic], queue bounds [300 §Instances and queues], and worst cases [025 §Can a box even behave well?] all assume numbers that don't exist.
2. **Per-domain identity vs. a platform people share.** Every primary domain is its own realm [013 §Identity is per domain]. That's perfect for businesses, but the new *personal public infrastructure* use case wants one person to use many small toys. With realms per domain, that's one account per toy, unless toys share a domain, which then shares an origin (§8.1).
3. **Mail routes and reachability disagree.** 038's mail examples have no requirements and no `public` [038 §Converting mail into routes], so the reachability rule refuses them [150 §Reachability]. 015's example requires `user_id` [015 §Email routes], which would refuse every outside sender, who isn't a user at all. Mail needs its own story about what "requirements" means for a sender.
4. **No automatic order between a specific domain and `"*"`.** Specific and `"*"` routes only order by priority [019 §The domain comes first]. Every per-tenant override of a shared page needs a hand-set priority, which will be the most common bump in the system.
5. **Two kinds of shadow.** `deployment.mode: "shadow"` has no network at all [305 §Deployment modes], while 310's shadowing allows calls with no effect through `shadow-calls` [310 §Shadowing]. Both make sense, but with the same word, readers will mix them up.
6. **Email "from day one" in a single binary,** while mail is rented from Stalwart [005 §Developer Velocity and the Sandbox; 099 §Keeping the host small].
7. **Per-tenant quotas** are still missing, and the public use case makes this far more urgent.
8. **`fetch` for user URLs** is still missing. Hearth needs it, and the Trad Wife System needs it for household calendars.
9. **The trusted computing base keeps growing:** markdown, templates, rewrites, relocation, OAuth, image parsing, all in the C++ host [010 §The Manifest; 070; 012; 120; 013; 060].
10. **Migrations** are still undesigned [020 §Data Flow].
11. **Agentic operators can tune but not explain.** The panel's MCP tools return data [300 §For agentic operators], but nothing yet lets an agent *propose* a change and attach its evidence. That's the "agentic optimization" loop from 310 [310 §Agentic optimization], unconnected to approvals [305 §The road ahead].
12. **Leftovers:** the hard-coded signal 42 and `operation` in 030 (§3).

## 7. Proposals

### 7.1 Senders, not users, for mail (limit 3)

Give mail routes their own reachability rule:
- `"public": true` means any sender.
- Requirements are matched against **aligned sender claims**, like `principal/email`, or a signed `token` in the address [038 §What makes this special].

Then fix the examples: 038's support inbox becomes `"public": true`, `ticket_reply` requires its token, and 015's `support@` drops `user_id`. Update the reachability table in 150 to match [150 §Reachability].

### 7.2 A cost model, finally (limit 1)

As proposed yesterday: declare costs in **row reads**, **calls**, and **bytes** per pattern and method. Calibrate them to milliseconds per machine class from the operating panel's own measurements [300 §Box instrumentation]. Then health thresholds, guardrails, and worst cases all speak the same units. The panel already measures everything this needs, so the model can be *learned* rather than guessed.

### 7.3 Federated realms for shared audiences (limit 2)

Keep per-domain realms, and add **one optional trust relationship**: a realm may accept sign-ins from a parent realm through OpenID Connect, so the platform's own domain becomes an identity provider for its toys. Each toy still gets its own `user_id` in its own realm, linked to the parent account, so origins stay isolated and a breach of one toy reaches nothing else, but a person signs in once. This is the same plug-in point the identity warning promises for enterprise single sign-on [013 §A warning about the built-in identity service], used first by the platform itself.

```json
{
	"identity": {
		"trust": ["platform.example"]
	}
}
```

### 7.4 One tie-breaker for domains (limit 4)

Add exactly one rule: **at equal priority, a specific domain beats `"*"`.** It's simple, predictable, and it's how people already expect overrides to work. Equal priority between two specific manifests, or two `"*"` manifests, stays a conflict [019 §Priority].

### 7.5 Rename one shadow (limit 5)

Call 305's health-check mode `"mode": "dark"` or `"canary-dark"`, and keep "shadow" for 310's comparison experiments. Alternatively, make 305's mode simply "shadow with `shadow-calls` empty." Either way, one word should mean one thing.

### 7.6 A development mailer in the binary (limit 6)

The single binary includes a tiny mailer for development that delivers outbound mail into an inbox in the operating panel and accepts inbound mail on a local port. Production swaps in Stalwart and real providers through the same `send-email@1` capability [330 §Host capabilities: stable contracts, swappable providers]. That's capabilities eating their own cooking!

### 7.7 Quotas, now with a public audience (limit 7)

As proposed yesterday, plus a *per-box* daily budget for public toys, so one viral game can't eat the host. The access log and egress audit already count everything this needs [300 §Rollups and cost; 030 §Consequences for the box].

### 7.8 `fetch`, at last (limit 8)

The same as yesterday: https and webcal only, private addresses blocked, caps on size and time, cached by the host, and no effect [035 §Safe calls and effectful calls]. It's now needed by two goals and one use case.

### 7.9 Agents propose, with evidence (limit 11)

Let an agentic operator submit a proposed change to configs, priorities, or shares as a new version. The comparison report or rollups that justify it get attached to the approval, so the approver reads the change and its evidence together [305 §What an approval reads; 310 §Agentic optimization].

## 8. Security evaluation

### 8.1 What changed in the threat picture today

- **Per-domain realms are a big win.** A phished session or a breached realm reaches one tenant [013 §Identity is per domain].
- **The new tension is origin isolation vs. shared accounts** for public toys (limit 2). Toys on paths of one domain share an origin, so one toy's scripts can attack another's pages. Toys on separate domains are isolated, but need federation (§7.3). Subdomains on the Public Suffix List get the best of both [015 §Keeping domains safe].
- **Configs can loosen security headers,** but only above the platform's floors, and loosening is flagged [012 §Priority is per property]. Good.
- **Rewrites can't loop** and can't use regex [012 §Rewrites are routes; §The pattern language]. Good.
- **`interior_ok` ships code with no human** [305 §Policies]. The manifest still bounds the damage, but a malicious interior can still do anything its manifest allows. That's the design's thesis, and it's sound *if* manifests are narrow.
- **The working set** shows drafts only to editors, and keeps drafts out of shared caches through the signature [320 §Who sees it]. Good.
- **Operator power** now flows through the domain registry: re-registering a domain resets ownership [013 §A multi-tenant example]. The tenant-visible audit is still deferred.

### 8.2 By adversary

| adversary | strengths today | gaps | rating |
| --- | --- | --- | --- |
| Malicious box | Narrow vocabulary, untrusted pointers [120 §Getting data out], internal calls never grow authority [039 §Whose call is it?] | `interior_ok` waves code through; the html response and embedded scripts | **Strong** |
| Malicious tenant user | Per-domain realms, grant roles, deny by default [013] | No quotas; email bombing through the system mailer | **Good** |
| External attacker | Optional domain verification plus on-demand TLS gating [015 §Registering a domain] | Verification off plus self-service domain registration is a takeover path; unauthenticated internal hops | **Good**, if verification stays on for shared hosts |
| Operator or infrastructure | Access logs without user data [300 §Access logs], whitelists that expire [310 §The comparison report] | Re-registering domains; telemetry detail | **Adequate** |
| Supply chain | Pins and replay [330] | Unsigned modules; a growing set of parsers in the host | **Needs work** |
| Agent acting for a user | MCP-only tokens, per-domain sessions [050 §Who is calling; 015 §MCP routes] | Agents of owners hold owner power | **Good** |

### 8.3 Under real traffic

- **A viral public toy.** Its domain gets hammered, and its isolates and queue fill. Queues reject with 503 rather than piling up [300 §Instances and queues], but without per-box quotas, one toy can starve the host. **Contain it** with per-box daily budgets and fair-share scheduling.
- **Retry storms from replay.** Recording corpora on every go-live [330 §Proving the host didn't change anything] doubles writes during launches. **Contain it** with sampling.
- **A shadow herd.** `slow` and `shadow` modes double the work of every request for the length of `period-ms` [305 §Deployment modes]. **Contain it** with a host-wide cap on concurrent shadows.
- **Certificate floods.** With verification off, any registered domain that points at the host gets a certificate [015 §Registering a domain]. Let's Encrypt rate limits will bite on mass registrations. **Contain it** by rate-limiting registrations.
- **Working set cache misses.** Editors see uncached pages [320 §Who sees it]. That's fine at editor scale, and a nasty surprise if a product makes "everyone an editor."
- **Tier misconfiguration.** A product sets `interior_ok` and ships a bug at 3am with nobody watching. **Contain it:** `slow` or `shadow` modes roll back automatically on health [305 §Deployment modes], so `interior_ok` should require one of them.

### 8.4 Top ten

1. Fix mail reachability (§7.1). Today it's a contradiction, and contradictions in security rules become holes.
2. Require `slow` or `shadow` whenever `interior_ok` is used.
3. Per-box and per-tenant quotas (§7.7).
4. Keep domain verification on for any host with self-service registration, and refuse to turn it off when more than one tenant exists.
5. Authenticate internal hops (Caddy, Stalwart, internal RPC, NATS) [039 §Speed].
6. Sandbox markdown, templates, and image parsing in WASM.
7. Signed, content-addressed artifacts.
8. `fetch` with private-address blocking (§7.8).
9. A tenant-visible audit of absolute-owner and registry actions [013 §A multi-tenant example].
10. Scrub replay corpora with the same rules as comparison reports, and audit them [330 §Proving the host didn't change anything].

## 9. Operating the system

### 9.1 Humans

- **The operator** installs one binary and gets an HTTP server [005 §Developer Velocity and the Sandbox], puts Caddy in front, and registers domains [015 §Registering a domain]. Their day is the panel: host health, the heat map, and the approval queue [300 §The dashboard; 305 §What an approval reads]. With policies, most versions approve themselves, so the queue holds only reach, power, safety, and takeovers [305 §Policies]. *Their pager:* rollbacks, shadowed routes, dead letters, vault health.
- **A tenant owner** signs in on their own domain and claims their business [013 §A multi-tenant example]. They edit their site through the working set [320 §How an agent publishes] and approve their own content. *What they still can't see:* what the operator did to their tenant.
- **An end user** gets fast pages, mail, and reminders, all on one domain they recognize.

### 9.2 Agents

- **An agent building boxes** writes a manifest against one reference [150], gets mechanical feedback, and ships code changes with no human when `interior_ok` applies [305 §Policies]. It's delightful, and dangerous in exactly the way §8.4 item 2 addresses.
- **An agent publishing content** puts one entry into a working set and looks at the real page [320 §How an agent publishes]. This is Grok's happy path, exactly as the author wanted.
- **An agentic operator** reads rollups, heat, and traces through MCP [300 §For agentic operators], tunes within bounds, and soon, I hope, proposes changes with evidence (§7.9).

- Hearth's per-domain model matches realms exactly [013 §Identity is per domain].
- Redirect proposals map onto rewrites [012 §Rewrites and redirects].
- Versioned pages map onto the working set and bundles [320; 315].

Still missing: `fetch` for calendars, a V8 box, mail forwarding rules, and a development mailer.

### 10.2 Goal 2: maintenance only for external dependencies

This is the big jump today. Capabilities, adapter boxes, pins, provable dependency-only updates, and replay together make goal 2 **checkable rather than hopeful** [330, throughout; 305 §Policies]. What remains:
- the cost model, for health thresholds,
- capability contracts beyond email (text messages, objects),
- a scrubbing design for replay corpora.

I'd call it about **65% designed**.

### 10.3 Personal public infrastructure

- **Publishing a toy:** a person, or their agent, writes a box or just a config with embedded pages [012 §A config is a manifest with no box; 070 §Static content], ships it with `slow` mode [305 §Deployment modes], and points a domain at it. That's genuinely easy!
- **Keeping strangers apart:** per-domain realms and per-domain conflicts isolate toys [013; 019]. ✅
- **Connecting people:** blocked by one-account-per-domain (limit 2, §7.3). Chat works over SSE [040], but real-time games need websockets, which are still a later protocol [030 §Starting small].
- **Discovery:** there's no catalog or directory design at all. A platform box could list toys, but nothing describes how toys opt in.
- **Cost of a popular toy:** quotas are missing (limit 7).
- **Malicious toys:** origin isolation needs subdomains or separate domains (§8.1). Rogue-content checks help with embedded pages [315 §Protecting against rogue content].

**Verdict:** a lovely base for *hosting* toys, and not yet a *network* of people around them. Federation and discovery are the missing halves.

### 10.4 Trad Wife System

- **Gathering a life:** one domain per household is one realm. Each person is a user with roles like `member/{tenant}`, and each person's data is scoped by `user_id` [013; 020 §Where context comes from]. ✅
- **The agent planning:** an agent acts for *one* person [050 §Who is calling]. Planning for the whole household means it reads other people's data through roles the household grants, like a `planner/{tenant}` role. That's possible, but nothing yet describes **consent**: how a household member agrees to what the planner can read and ask of them.
- **Keeping the agent inside its tools:** isolate the planner in its own box, with read access and a narrow write channel for plans and tasks [050 §Isolating agents in their own box]. ✅
- **Plans reaching people:** mail, reminders at each person's local time, and live subscriptions [038; 045 §Data-driven timers; 040]. ✅
- **Learning what got done:** tasks with state machines, Hearth-style, as data. ✅ But the household calendar needs `fetch` (limit 8).
- **Privacy:** per-user keys can be read by the operator [064 §The limits of this design], so for the most intimate data, a household should run its own host, which the single binary makes plausible [005 §Developer Velocity and the Sandbox].

**Verdict:** the structure fits remarkably well, and the missing piece is a **consent model**: who agreed to be planned for, and what the planner may see. I'd suggest a small identity extension where a person grants a role to the planner's box and can see and revoke it, using the same revocable machinery [013 §Granting and revoking roles].
