# 055. The operators' mailbox

Status: built on 2026-11-06 at the human's request. Two decisions wait for the human (§ 7).

The human (2026-11-06): "make sure admin@ has an inbox as well in the operators panel if not
there already. I should be able to respond as admin@ for anything as well, so I need a basic
email client."

There was none. Mail to an address no box route claims was refused at RCPT ("No such recipient
here"), and 041 already promised postmaster@ and abuse@ to the operators without anything
behind it.

## 1. The addresses

The operators' addresses are `admin@`, `postmaster@`, and `abuse@` on:

- every production domain in host.json (`domains` entries without `beta-of`);
- every redirect domain (its primary's tenant);
- the platform domain (`platform-domain`), whose mail is the host's own (no tenant).

Beta domains are not included: beta takes no mail from outside (053 § 4).

Mail to these addresses goes to the operators' mailbox **before** any box's mail route, a
catch-all `*@` included. A box route that names one of them never gets it. `box_guide` says so.

## 2. Receiving

The MTA hook (024) checks the recipient against § 1 before it matches a mail route:

- **RCPT:** accepted, or 452 4.2.2 "Mailbox full; try again later" when the mailbox holds
  `limits.operator-mail-bytes` (§ 5).
- **DATA:** the message is parsed as box mail is (text, HTML, attachments, threading headers)
  and kept, and Stalwart is told to discard it (250). A message past `mail.inbound.max-bytes` is
  refused with 552. Automatic mail (bounces, auto-replies) is kept and marked `automatic`, since
  postmaster@ exists to receive it.
- **The sender:** `sender_verified` is true only when a DKIM signature aligned with From's
  domain passes (024 § 5); otherwise `sender_why` says why not. The panel shows the difference,
  since an unverified From can be anyone.

## 3. Storage

`storage/mail/operators/`, kept the way beta's mailboxes are (053 § 4), through the same code
(`host/src/mailbox.cpp`):

- `<id>.json`: the whole message. The id is 13 digits of milliseconds, `-`, and 8 hex digits.
- `<id>.head`: the row a list reads.
- `<id>.parts/<n>`: each attachment's bytes.

A message holds `direction` (`in` or `out`), `to`, `envelope_from`, `from`, `from_name`,
`to_list`, `cc`, `reply_to`, `subject`, `text`, `html` (each cut at 1 MiB, with `truncated`),
`message_id`, `in_reply_to`, `references`, `date`, `bytes`, `sender_verified`, `sender_why`,
`automatic`, and `attachments` (`index`, `filename`, `content_type`, `bytes`, `inline`). A sent
message also holds `by` (the person), `via` (ses, smtp, or dev), `sent`, and `error`.

## 4. The panel's Mail view

Shown to `host:owner` and `host:operator`, never on beta-ops:

- **Inbox, Sent, All:** newest first, with from, to, subject, a preview, and pills for
  attachments, an unverified sender, automatic mail, and a send that failed.
- **A message:** its headers, whether its sender is verified, its text, its HTML as source
  (never drawn), its attachments as downloads, Delete, and a Reply card.
- **Write and Reply:** From is a list of the operators' addresses within the person's focus,
  with `admin@` first. To is one address. A reply is addressed to the message's Reply-To (or
  From), and it carries `In-Reply-To` and `References` so it threads, and quotes the original.
  Sending asks for a confirmation, goes out at once through the host's mailer
  (`MailQueue::deliver`), and keeps a copy in Sent, sent or not. With the dev mailer or on a
  sandbox nothing leaves the machine (018).

The panel's own calls are `operator_mail {folder, limit}`, `operator_mail_get {id}`,
`operator_mail_attachment {id, index}` (base64, saved by the browser), `write/operator_mail_send
{from, from_name?, to, subject, text, in_reply_to?}`, and `write/operator_mail_delete {id}`.
Sends and deletes are audited (`operators.mail_send`, `operators.mail_delete`).

**Scope (030).** A person focused on some tenants sees the messages to (or sent from) those
tenants' addresses, and sends only as those. The platform domain's addresses are for unfocused
people only.

**No MCP tools.** Agents can't read or send this mail (§ 7).

## 5. Limits

Per 045, the mailbox has a time limit and a byte budget, both in the `limits` check:

- messages are kept **400 days**, as the logs are;
- `limits.operator-mail-bytes`, 1 GiB unless set (at least 16 MiB), past which new mail is
  refused with 452 until a person deletes some. Nothing is dropped for space, since this mail is
  the person's, not derived.

  This adds admin@, which 041 does not list. 041 is "the single list", so admin@ belongs there

## 7. Decisions for the human

1. **Agents and this mail.** Only people read and answer it now. Options: (a) as built; (b) read
   tools (`operator_mail_list`, `operator_mail_get`) for agents not focused on tenants, sending
   still a person's; (c) sending too, held for approval. Recommendation: **(a)** until you want
   an agent triaging abuse@; then (b). An agent that sends as admin@ speaks for you.
2. **More than one recipient, Cc, and attachments on send.** The client sends text to one
   address. Recommendation: leave it basic until you miss one of them.
