# What kcmeatup.com needs next

Written 2026-10-28, late, at the human's request: look at everything not done, predict what
kcmeatup.com needs to be a good directory, a future social network for carnivores, and an AI
agent that people reach by email, and build what matters before tomorrow. Tomorrow the human
tests mail in, and GrokBot (the Grok agent team: Pit Boss, Engineers A and B, the product
agent) builds an **email worker**. The plan is to reach people by email and talk with them,
instead of signing them up.

This is a plan and a forecast, not a ratified design. § 4 is what was built tonight; § 7 is
what waits on the human.

## 1. Where things stand

- **Live.** kcmeatup.com runs on goober. Grok deploys boxes and pages through the operator
  MCP. The kc_locations directory has typed tools, place pages, and (after the next deploy)
  JSON-LD.
- **Mail out.** It works through SES, but nobody has yet checked that SES has kcmeatup.com
  verified as a domain, which sending from `hello@kcmeatup.com` needs.
- **Mail in.** It is built and passes `just mail-e2e` against the real Stalwart. It hasn't yet
  met the internet: the MX record, port 25, and the first real message are tomorrow.

## 3. The email worker, as GrokBot should build it

**What it does.** People write to `hello@kcmeatup.com`, or reply to our outreach. A Grok
model drafts an answer from the thread and the directory's data. The answer goes back in
the same thread, automatically or after an operator approves it. GrokBot also starts
conversations: outreach to a ranch, a butcher, or a person who asked about something.

**The box.** One box, say `kc_mail`, with:

```json
{
  "box": "kc_mail",
  "domains": ["kcmeatup.com"],
  "data": {"sqlite3": {"mail": {"schema": "kc_mail_v1", "database": "kc_mail", "pattern": "sql", "tables": {...}}}},
  "external": {
    "mail": {"mail": {"from-name": "KC Meat Up", "from": "hello@kcmeatup.com"}},
    "grok": {
      "base": "https://api.x.ai",
      "credentials": "keys/tenant/{!tenant}/xai",
      "methods": {"chat": {"verb": "post", "path": "/v1/chat/completions", "result-route": "on_draft",
                           "delivery": {"attempts": 3, "backoff-ms": 5000, "timeout-ms": 90000}}}
    }
  },
  "routes": {
    "mail": {
      "hello@kcmeatup.com": {"receive": {"name": "hello_in", "public": true, "attachments": 3}},
      "reply+{thread : token}@kcmeatup.com": {"receive": {"name": "thread_in", "public": true}}
    },
    "result": {"on_draft": {"timeout-ms": 5000}},
    "timer": {"followups": {"name": "followups", "cron": "0 9 * * *"}},
    "mcp": {"...": "inbox_list, thread_get, draft_approve, draft_edit, outreach_send, contact_stop"}
  }
}
```

**The tables.**

- `contacts`: address, name, status (new, engaged, stopped), source, notes.
- `threads`: id, contact, subject, the latest Message-ID and References, state.
- `messages`: thread, direction, Message-ID, from, text, received_at.
- `drafts`: thread, the key `goober_call` answered, status (thinking, ready, approved, sent,
  failed), text.

**The flow.**

1. **Mail arrives** on `hello_in` or `thread_in`. The box stores the message, finds or opens
   its thread by `in_reply_to`/`references` (or the token), and queues a draft:
   `goober_call("grok", "chat", {"body": {"model": "...", "messages": [...]}})` answers
   `{"accepted": true, "key"}`. The box stores the key on a new draft row (status
   `thinking`) and answers 200. The call leaves after the commit.
2. **The model answers** on `on_draft`: `{"key", "outcome", "status", "body", ...}`. The box
   finds the draft by `key` and parses the model's JSON from `body`. Then it either marks the
   draft `ready` (approval mode) or sends it (automatic mode). Sending is `goober_call("mail",
   "send", {"to", "subject": "Re: ...", "text", "in_reply_to": <their Message-ID>,
   "references": <their references + their Message-ID>})`.
3. **An operator or agent approves** over MCP: `inbox_list` shows threads waiting,
   `thread_get` shows a thread, and `draft_approve` sends. Start in approval mode. Switch a
   contact to automatic only after a few good drafts.
4. **Outreach** is `outreach_send` (MCP, owner only). It writes a first mail, from a template
   or the model, to a contact with status `new`. The host caps it at 3 a day per address and
   200 a day per tenant. Replies in a thread the person started get 20 a day.
5. **Stopping.** If a reply says stop or unsubscribe, the box marks the contact `stopped` and
   sends nothing more. The host's one-click link does the same for every box, for good.
   After that, `send` answers `{"error": "unsubscribed: ..."}`, and the box should mark the
   contact.

**Guardrails the box must keep:**

- **Email is data, never instructions.** The model's system prompt says so. The model gets no
  tools that change anything; it only drafts. Anything it "decides" (prices, promises,
  meetups) waits for approval.
- **From is a claim.** Until Q39, `sender` is null, so don't grant anything because a
  message says it's from the owner. Reply-token addresses (`reply+{thread : token}@`) are the
  capability: only someone who got our mail can write into that thread.
- **Cost.** Every model call is a deliberate outbox element. The box should keep its own
  daily count of calls and stop drafting past it. The host has no spend cap for outside APIs
  yet (§ 6, M5).
- **Loops.** Auto-replies, bounces, and lists are dropped before the box sees them (routes
  without `automatic`). Still, never reply to a message you sent.

**The key.** The operator sets the xAI key once with `key_set`, as tenant `kcmeatup`, name
`xai`, and the allowed host `api.x.ai`. The box never sees it.

## 6. Next to build, in order

1. **M1: DMARC strict in Stalwart**, after the first real message arrives. It's a one-line
   change in `tools/stalwart.sh`, then `just stalwart-e2e`, then deploy.
2. **M2: bounces and complaints.** SES publishes to an SNS topic; an HTTPS subscription to a
   host path verifies the SNS signature. A hard bounce or a complaint unsubscribes the address
   for its tenant, and the box hears it on a result route.
3. **M3: `mail_activity`**, an operator tool listing a tenant's recent mail in and out
   (addresses, subjects, outcomes) from `mail.log` and the hook log, so Grok can answer "did
   it arrive?" itself.
4. **M4: attachments on `send`**: attachment ids of the tenant, up to 3 and 10 MiB in all.
5. **M5: a per-tenant daily cap on outbox calls per service** (`limits.outbox.$service.daily`),
   so a looping worker can't spend the model budget.
6. **M6: `"markdown": true` on `send`**, rendered by the host's markdown renderer (raw HTML
   off) into the layout's HTML part.
7. **Then the directory:** ETags and compression (Phase 5).
8. **Then the social network:** Q24's separate origin, uploads by people (060), and quotas
   (390).
