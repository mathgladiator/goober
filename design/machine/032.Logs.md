# Logs, performance, and auditing agents

A design, built the same day. On 2026-10-29 the human asked for the operations side to grow
up:
- a UI to explore the whole site as a graph of URI flow, "almost like a flame graph";
- a way to audit whether agents are behaving or "going ham";
- templates visible in the operator tooling;
- in-memory measurements, for each URI's p99;
- logs that rotate, are uploaded to the backups when they rotate, and can be searched over the
  last 3 days with a grep-like interface;
- structured logs, so that SOC2 is a reasonable ask of goober as infrastructure.

They chose:
- **Retention:** rotate daily or at 256 MiB, keep 7 days on the machine, and archive each
  rotated file to the backup bucket for 400 days.
- **Integrity:** a hash chain through every line, and sealed archives with a manifest.
- **Personal data:** addresses are logged as keyed hashes, and the search finds them by the
  address.

## 1. The logs

| log | one line per | holds |
| --- | --- | --- |
| `access` | HTTP request, and each mail, timer, and identity call | status, latency, route, box, tenant, and the call's own fields |
| `egress` | outbox delivery and outbound call | service, method, status, latency, bytes |
| `mail` | mail sent | the recipient's hash, subject, status, message id |
| `agents` | box tool call through a site's `/mcp` | client, tool, user id, status |
| `db` | operator SQL (`db_exec`, the CLI) | tenant, database, statement |
| `audit` | security event (§ 4) | actor, action, target, outcome, source address |
| `boxes/$box` | line a box logs | the box's text |

**Every line is one JSON object with a common envelope:**
- `at` is the time, in UTC with milliseconds (RFC 3339);
- `log` is the log's name;
- `seq` is the line's number in that log, never reused, continuing across rotations;
- `host` is the host's name (`public_url`'s host);
- `chain` (§ 3).

Fields that belong to the event keep their names, as before: `request_id`, `tenant`, `actor`,
`status`, and the rest. The envelope comes first, so a reader that doesn't know a log can still
order, attribute, and verify it.

**Addresses are hashes.** Where a line names a person's email address it writes `email_h` (or
`to_h`, `from_h`) and the address's domain (`email_domain`): the first 16 hex digits of an
HMAC-SHA256, under a key derived from the host's reply key, over the address lowercased. A
tenant's own sending address is kept as `from_address`; it's a business's, not a person's.
`mail_activity` takes an `email` to show one address's mail by name. A search given an address computes the same hash
(§ 5). Box logs and operators' SQL are written by others, so the host can't hash what's in
them. That's said in § 8.

## 2. Rotation and archives

**When a log rotates:**
- at the first write after midnight UTC;
- when its file would pass 256 MiB;
- at the hourly tick, if it's from an earlier day, so a quiet log still rotates.

**What rotation does:**
- **The files.** The file becomes `name.1`, and older ones move up, as before (`name.N`), so
  the traffic rollups' tailer keeps reading them. Up to 64 numbered files are kept.
- **The queue.** A hard link of the rotated file goes to `logs/archive/name-$stamp.log`, with
  its manifest (§ 3).

**Uploading.** When backups are on, the backup thread uploads each queued file. It is packed
with `tar -czf`, sealed with the backup key (019 § 2), and put at
`logs/$name/$yyyy/$mm/$dd/$name-$stamp.log.tar.gz.sealed`. Its manifest goes beside it as
`….manifest.json`, which isn't sealed: it holds no log content. Once both are up, the queue's
link is removed.

**Retention:**
- **On the machine,** a numbered file older than 7 days is deleted, if its archive went up (or
  backups are off). A queued file that can't be uploaded is kept, but never past 30 days: it's
  deleted then, with an error recorded.
- **In the bucket,** the backup rotation deletes archives older than 400 days.

`host_health` and the panel show:
- the logs (size, last rotation, oldest local day);
- the archive queue;
- the last upload, and any error;
- a warning when backups are off, since nothing is archived then.

## 3. The chain

Each line is the JSON of its envelope and fields, ending with
`"chain":"<32 hex digits>"`.

**What `chain` is.** The first 32 hex digits of SHA-256 over the previous line's chain, a
newline, and this line written without its `chain` field. A log's first line ever chains from
`"genesis"`. The chain runs on across rotations: a rotated file's first line chains from the
last line of the file before it.

**Writers.** The host writes each log through one writer with a lock. A second process (the
CLI's `db` commands, `token create`) appends under `flock`. It reads the last line again when
the file has grown since it last looked, so the chain stays one chain.

**The manifest** of a rotated file holds:
- the log's name and the file's stamp;
- the first and last `seq`;
- the chain before the first line and after the last;
- the line count;
- the SHA-256 of the file's bytes.

Stored beside the archive, manifests let anyone check that no file is missing between two
others and that no line was changed.

**`log_verify {log, days?}`** walks the local files in order and recomputes every chain. It
answers the lines checked and the first line where the chain breaks. A deleted, inserted, or
edited line breaks it at that point.

What the chain proves: no line was changed, removed, or inserted after it was written, unless
someone also rewrote every later line and every manifest already uploaded. The sealed uploads
are the second half: off the machine, under a key the machine's logs don't hold.

## 4. The audit log

`audit` gathers what an auditor asks for, each line with `actor`, `action`, `target`,
`outcome` (`ok`, `refused`, or `failed`), `ip`, and `request_id`:

| action | when |
| --- | --- |
| `operator.tool` | every operator tool call, over MCP or the panel: the tool, its tenant, path, box, and name arguments, and the outcome |
| `operator.auth_failed` | a bad or expired operator token |
| `panel.scope_set`, `panel.block_lift` | the panel's two writes |
| `identity.sign_in`, `identity.sign_in_failed` | a code accepted or refused, in any realm (the address hashed) |
| `identity.grant`, `identity.revoke` | role changes through tools |
| `config.reload` | SIGHUP, with what changed |
| `host.start`, `host.stop` | the process's life, with the build |
| `token.create`, `token.revoke`, `operator.revoke` | operator tokens and logins, from the CLI |

Reading the logs is itself logged: `log_search` and `log_verify` are operator tools, so each
call is an `operator.tool` line. Operators' own addresses (`oauth:ann@…`) stay as they are in
`actor`: they're the staff identities an audit asks for. Only people's addresses are hashed.

The change log (028) still holds diffs. The audit log points at those changes by `request_id`
and holds no contents.

## 5. The log dive

`log_search {log, pattern?, regex?, fields?, email?, since?, until?, limit?, before?}`:
- **Which logs.** `log` is one log, `all`, or `boxes/$box`.
- **Matching.** `pattern` is a substring, or `regex` an ECMAScript regex, matched against the
  raw line. `fields` is `{name: value}` pairs that must equal the line's own. `email` matches
  any `*_h` field with that address's hash.
- **The window.** It runs from `since` to `until`, which default to the last 24 hours. The dive
  reaches back as far as local files go (7 days, the human asked for 3).
- **The answer.** Newest first, at most `limit` (default 200, at most 1000), each line as
  written. `before` is a cursor (log and `seq`) for the next page.
- **The bound.** It reads at most 2 GiB per call, and says when it stopped early.
- **Scope.** A focused operator (030) only gets lines whose `tenant` is in their scope, and
  lines without a tenant only from `audit` actions they made themselves.

The panel's **Logs** view is the same search, with a log picker, the time range, and the
results; a click filters by that line's `request_id`.

## 6. Performance in memory

The host keeps live statistics as it writes the access log, so reading them waits for no
tailer:
- **Per tenant and path** (the query removed, at most 200 characters):
  - for each of the last 60 minutes: a count, the errors (5xx), the 4xx, a 40-bucket √2 latency
    histogram (as the rollups have), and the maximum;
  - at most 20,000 paths, the least recently seen dropped first;
  - a path a box serves also carries the route's name.
- **Flow.** For each request with a same-site `Referer`, the pair of the referring path and
  this path, per minute. At most 20,000 pairs.

**The tools:**
- **`uri_stats {tenant?, window: 5m | 15m | 1h, prefix?, sort?, limit?}`** answers each path's
  count, error rate, p50, p95, p99, and max.
- **`uri_tree {tenant, window?}`** answers the site as a tree of path segments. It merges the
  live statistics with every listed page (031 § 1), every static file, every box route
  pattern, and the host's own paths. Each node says its kind (page, file, box, host, unknown),
  its count, its errors, and its p99, so a page nobody visits still shows.
- **`uri_flow {tenant, path, window?}`** answers where visitors to the path came from, and where
  they went next.

The rollups (028 § 4) stay the history. The live statistics are lost on restart.

## 7. The panel

| view | shows |
| --- | --- |
| **Sitemap** `#/sitemap` | the tree of § 6 as an icicle (a flame graph laid flat): each segment's width is its traffic (or, by structure, one per leaf), its color its p99, red edges for errors; click to zoom; a node's panel lists its flow in and out and its page, file, or box |
| **Performance** `#/perf` | `uri_stats` as a table, sortable by p99, count, or errors, over 5 minutes, 15 minutes, or an hour |
| **Agents** `#/agents` | `agent_audit` (below): each operator, token, and site agent, with a sparkline of calls, writes, failures, and deletes, and the flags |
| **Content** `#/content` | a tenant's templates, partials, and pages: each one's source, and a page's render checks |
| **Logs** `#/logs` | the log dive (§ 5) |

**`agent_audit {window: 1h | 24h | 7d}`** reads the audit log and the agents log. Per actor it
answers:
- calls, writes, failures, and deletes;
- the distinct paths touched;
- the busiest 5 minutes;
- calls per 10 minutes (or per hour), for a sparkline;
- flags, each with the evidence:
  - **burst:** more than 60 calls in 5 minutes, or more than 30 writes in 10;
  - **failing:** more than a quarter of at least 20 calls fail;
  - **deleting:** more than 10 deletes in an hour;
  - **looping:** the same tool with the same arguments more than 10 times in 10 minutes.

The thresholds are a first guess, kept in one place.

## 8. SOC2

goober is infrastructure, so a customer's SOC2 asks what the host records and keeps. Against
the Trust Services Criteria:

| criterion | what goober does |
| --- | --- |
| CC6.1 logical access | every operator and person action is attributed (`actor`), sign-in successes and failures are in `audit`, operator scope (030) limits reach |
| CC6.2/6.3 access changes | grants, revokes, tokens, and scope changes are `audit` lines |
| CC7.2 monitoring | `audit`, `access`, and `egress` with the live statistics and rollups; the panel; `agent_audit`'s flags |
| CC7.3 evaluating events | the log dive across every log by request id, address, or pattern; three days at hand, 400 in archive |
| CC8.1 change management | the change log (028) with diffs, linked by request id from `audit` |
| A1.2 backups | archives sealed off the machine, kept 400 days, rotation recorded |
| PI1 / integrity | the hash chain, manifests, and `log_verify` |
| C1 / P4 confidentiality and privacy | addresses as keyed hashes, archives sealed, the dive itself audited |

**What isn't goober's to answer:**
- policies, access reviews, and training;
- alerting someone (flags are shown, not paged);
- MFA for operators (codes by mail are one factor);
- clock discipline (the machine's NTP);
- what boxes and operators write in free text (box logs, SQL), which may hold personal data;
- the bucket's own access controls and object lock.

Object lock on the bucket would make the archives immutable even to whoever holds its keys.
It's recommended, and set outside goober.

## 9. Tests

- **logs:** the chain, and verifying it, broken by an edit, a deletion, and an insertion;
  rotation by day and by size; `seq` and chain across rotation; a second writer with `flock`;
  manifests; search by pattern, regex, fields, time, and email hash; the cursor.
- **host:**
  - each log written with the envelope, and addresses hashed;
  - audit lines for tool calls, auth failures, sign-ins, and panel writes;
  - rotation queues an archive, and the backup service uploads it sealed with its manifest
    (against the S3 stand-in), then removes the link;
  - local retention;
  - `log_search` within scope, and `log_verify`.
- **operations:** the live statistics' percentiles, the eviction, flow pairs, and the 60-minute
  window.
- **panel:** the new views load and draw, checked in a browser.
