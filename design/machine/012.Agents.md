# Agents over MCP

> Status: machine-authored and **not ratified**. Recorded on 2026-10-26. It builds the
> box side of `050.AgentsMCP.md`: tools declared in a manifest, served at `/mcp` on every
> domain to callers holding a bearer token from that domain's realm (`009.OAuth.md`), with
> inputs typed by the box's types document (`011.Types.md`). Where it departs from 050, §6
> says so, and the human doc wins until it is updated.

## 1. Declaring a tool

```json
{
	"types": "desk.openapi.json",
	"routes": {
		"mcp": {
			"desk_ask": {
				"tool": {
					"description": "Ask the person to approve something before you do it. ...",
					"input": "json:Ask",
					"requirements": [["owner"]]
				}
			}
		}
	}
}
```

- The key is the tool's name, `[a-z][a-z0-9_]*`. A `name` field may repeat it and must
  match. Tool names share the box's route-name space, and are unique across the host like
  every route name (005 §5).
- `description` is required (at most 2000 bytes), since a model reads it and acts on it.
  It is part of the manifest, so it changes only with a new version.
- `input` is `json:$Type`, or absent for a tool that takes nothing. `response` may be
  `json`, `json:$Type`, or `text`.
- `requirements` are required; `"public": true` is refused, since an agent always acts for
  somebody. Requirements may substitute `{!tenant}` and `{!user_id}` only, for now.
- The box exports `goober_route_$name`, like an HTTP route. `resource` is accepted with a
  warning and does nothing yet.
- Two boxes may not offer the same tool name on overlapping domains.

## 2. The endpoint

`/mcp` on every domain, MCP over streamable HTTP: a JSON-RPC request in a POST, answered
with `application/json`. Methods: `initialize` (protocol versions 2025-06-18, 2025-03-26,
2024-11-05), `ping`, `tools/list`, `tools/call`, and notifications, which get 202.

**Who may call.** Only a bearer access token from this domain's realm: an agent's token, or
a person client's. A cookie isn't enough, so a web page can't drive a person's tools from
their browser. Host identities have no tools here. Without a token the answer is 401 with

```
WWW-Authenticate: Bearer resource_metadata="https://example.com/.well-known/oauth-protected-resource"
```

and `GET /.well-known/oauth-protected-resource` (RFC 9728, also at `.../mcp`) names `/mcp`
as the resource and the realm's issuer as its authorization server. So an MCP client that
follows the MCP authorization spec can discover the realm, register
itself (`/oauth/register`, always an agent), and sign the person in through the
authorization code flow with PKCE, with no setup. Since such clients register
`http://localhost:PORT/callback`, a registered `http://localhost` URI is allowed, matched
exactly (009 §3).

**Discovery is filtered.** `tools/list` returns only the tools whose requirements the person
behind the token passes, each with its description and an `inputSchema` built from the
input type (closed objects, `$ref`s inlined). An agent working for a member never learns
that an owner's tool exists (050 § What the host does for free).

**The list is never stale on the host's side.** `/mcp` builds its list from the active box
versions on every request; nothing is cached. Each tool carries `_meta` with `goober/box` and
`goober/version`, the box version that answers it, and `serverInfo.version` is the host's
version plus a hash of the tool set this caller sees, so it changes when a deploy changes the
list. The host doesn't hold connections open, so it can't send `tools/list_changed`; a client
that keeps its own copy must list again (most do on reconnect, or when the server version
changes). The operator tool `mcp_tools_preview` shows what a domain's `/mcp` lists, and for a
person, what they see and why a tool is hidden. Every `tools/list` answer is an access-log line
with `"mcp": "tools/list"` and `listed`, each tool as `name@version`, so the host's record of
what a client was served sits beside what the client says it saw. A tool declared without an
`input` takes no arguments, and upload warns about it.

**A call.**

1. A tool the caller can't see is an unknown tool, a JSON-RPC error, so an agent can't
   probe what exists: not found, never forbidden.
2. The arguments are checked against the input type. A failure is a tool result with
   `isError: true` and the path that failed, and the box never runs.
3. The box runs through the same path as an HTTP route: its request document has `method`
   `"tool"`, `path` `"mcp:$name"`, and the checked input as `body`; its databases' writes
   commit only if it answers below 500.
4. A 2xx answer becomes the tool result: the body as text, and as `structuredContent`
   when it is a JSON object. A 4xx becomes `isError: true` with the box's `error` message.
   A 5xx, trap, or timeout becomes `isError: true` with only "the tool failed" and the
   request id, since a host failure isn't the model's to reason about.

**Audit.** Every tool call is a line in `logs/agents.log`: the time, request id, tenant,
user, client, whether it was an agent, the tool, the status, and the first 2000 bytes of
the input and the result. The access log also names the tool and client.

## 3. The desk's tools

The desk box (`010.Terminal.md`) offers ten: `desk_ask`, `desk_check`, `desk_recent`,
`desk_set_alarm`, `desk_remove_alarm`, `desk_list_alarms`, `desk_set_dashboard`,
`desk_remove_dashboard`, `desk_set_settings`, and `desk_list_devices`, typed by
`desk.openapi.json`. Its HTTP routes now declare the same types as bodies, so the host
checks those too. An agent connected to a personal goober can ask the person for approval,
read the answer, and set alarms and dashboards on their phone, and has no tool that
decides an approval.

## 4. Trying it

```sh
claude mcp add --transport http mine http://localhost:8080/mcp
```

That should let Claude Code find the realm, register, and open the browser to sign in and
allow it, but **it hasn't been tried with a real MCP client yet**; only the pieces are
tested. `just terminal-e2e` drives the endpoint with a device-flow agent.

## 5. Tests

## 6. Departures and what is missing

| doc | section | v1 says |
| --- | --- | --- |
| 050.AgentsMCP.md | The result vocabulary | 5xx is a tool result marked as an error, not a JSON-RPC protocol error. |
| 050.AgentsMCP.md | What the host does for free | No MCP sessions, streaming, or cancellation; each POST stands alone. No resources or subscriptions. |
| 050.AgentsMCP.md | The audit | The account page lists the newest 20 tool calls made by the person's agents (tool, agent, time, refused or not), read from `logs/agents.log`; inputs and results stay in the log. |
| 050.AgentsMCP.md | Agentic considerations | No per-agent-session quotas of calls or effectful calls yet (PROGRESS.md Phase 3). |
| 050.AgentsMCP.md | Permissions, mirrored | Requirements can't substitute tool input fields yet. |
| 050.AgentsMCP.md | Who is calling | People may call `/mcp` with a person client's token, as 050's table allows, but not with a browser cookie. |
