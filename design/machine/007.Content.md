# Content and Attachments

> Status: machine-authored and **not ratified**. Recorded on 2026-10-26, when the human
> asked for goober to stand up as a CMS: pages as full HTML or markdown, templates,
> listing pages, and images an agent can set over MCP or a person can upload. It extends
> `005.FirstVersion.md` §7–§9, and the code in `host-src/` follows it. It borrows from
> Hearth (https://github.com/adama-platform/hearth), whose content features were read
> from its source on 2026-10-26. Where it departs from a human doc, §11 names the doc and
> section, and the human doc wins until it is updated.

## 1. Why content is its own vector

A box's response is data. A page is not: a browser executes it. HTML carries scripts,
forms, frames, and links to anywhere, so whatever the host serves as HTML is code running
with the tenant's origin and the signed-in person's cookies. That is why content gets its
own vector, with its own rules, rather than being "a file the host happens to serve":

- **Content is the site's source.** Pages, templates, stylesheets, and data files are text
  that people and agents write, read back, and change. They are versioned through the
  host WAL like every other file the host owns, and an agent can edit them in place.
- **Attachments are the site's media.** Images and documents are binary, numbered,
  immutable once stored, and sniffed from their bytes. An attachment is never HTML, so
  an upload can never become a page (070.UI.md § Objects and attachments).
- **The host renders; content never runs.** Markdown and Mustache can't execute
  (070.UI.md § The invariants). The only pages that carry the author's own markup are the
  two HTML kinds of §3, which an operator or an agent writes, never a visitor.

## 2. The content tree

Each tenant has one tree, `storage/content/$tenant/`, written only through the host WAL
(005 §7). The `_host` tree holds host-wide content, as before.

| path | what it is | served |
| --- | --- | --- |
| `*.md` | A markdown page (§3). | Rendered, at its clean URL. |
| `*.html` | An HTML page: a fragment when it has front matter, a whole document when it doesn't (§3). | Rendered or as written. |
| `_templates/$name.html` | A Mustache template (§5). | Never. |
| `_data/$name.json` | A JSON data file for templates (§5). `_data/site.json` is the site's title, navigation, and the like. | Never. |
| any other path | A static file: CSS, JavaScript, fonts, a favicon, a small image. | As written, typed by extension. |

**Private paths.** Any path with a segment that starts with `_` is never served over
HTTP, whatever it holds. Templates, data, and anything else an author wants to keep off
the web live there. The operator API reads and writes them like any other path. The one
exception is the asset directories static site generators write, `_astro/`, `_next/`,
`_nuxt/`, and `_app/`, which are served (2026-10-27), so a built Astro or Next.js site can be
pushed as it is.

## 3. Pages

A page is a `.md` or `.html` file. Its URL is its path without the extension, and an
`index` page is its directory's URL: `blog/hello.md` is `/blog/hello`, and
`blog/index.md` is `/blog`.

| kind | file | what the host does |
| --- | --- | --- |
| markdown | `.md`, front matter optional | Renders the body as markdown (§4), then through the page's template. |
| fragment | `.html` starting with front matter | Wraps the body, as written, in the page's template. |
| document | `.html` without front matter | Serves it exactly as written. No template; this is how an agent sets a whole page. |

This matches Hearth's three kinds (markdown, html, page), mapped onto files.

**Resolving a URL.** For a normalized path `/p` (005 §8), the host serves the first that
exists:

1. the file `p`, if it is a static file or an `.html` page;
2. the page `p.md`, then `p.html`;
3. the page `p/index.md`, then `p/index.html`;
4. a directory listing of `p/` (§6), when the tenant has a `directory` template;
5. otherwise 404.

The root `/` tries `index.md`, `index.html`, then the root's listing. A request for
`/p.md` is redirected (301) to `/p`, so every page has one URL.

**Front matter** is the block at the top of a page between `---` lines (070.UI.md
§ Markdown). Each line is `key: value`. A value starting with `[` or `{` is JSON, so
`requirements: [["owner"]]` works. Keys from the platform are hyphenated. Any other key is
the author's, and is handed to the template as it is.

| key | meaning |
| --- | --- |
| title | The page's title. Defaults to the first `#` heading of a markdown page, then the file name. |
| template | The template that wraps the page (§5). Defaults to `list` for a listing page and `page` otherwise. |
| date | A date for listings and feeds, written `YYYY-MM-DD` or as an RFC 3339 time. |
| summary | The summary shown in listings. Defaults to the first paragraph's text. |
| image | An image for listings and social cards, usually `/attachment/$id.$ext`. |
| tags | A list of tags; a listing can be filtered by one (§6). |
| order | A number for listings sorted by order. |
| draft | When true, the page is neither served nor listed. Operators can still preview it (§9). |
| requirements | Who may read the page, exactly as on a route (006 §4). Without it, the page is public. |
| redirect | A path or URL to send the visitor to instead. |
| redirect-status | 301 (the default), 302, 307, or 308; or 410 to say the page is gone. |
| list, sort, per-page, feed | Make the page a listing (§6). |

**Content negotiation.** A request for a page whose `Accept` prefers `text/markdown` gets
the page's file as written, front matter included, under the same requirements. Everyone
else gets HTML. This is how an agent reads back a page it wrote.

## 4. Markdown

The host renders markdown itself, in the `render` package, rather than through a library.
It covers CommonMark's blocks and inlines and, from GitHub's flavor, tables, task lists,
strikethrough, and bare URLs. Headings get ids from their text, so `#getting-started`
links work.

- Raw HTML in markdown is escaped, always (070.UI.md § Markdown). A page that needs markup
  is an `.html` page instead.
- A link or image whose URL has a scheme other than http, https, mailto, or tel becomes `#`.
  An image may also be a raster `data:image/` URL.

A library (md4c, cmark) can replace the renderer later without changing a page. The
renderer is host code, so 070's rule applies: it is pinned with the host, and a host
upgrade should not change how a deployed page looks.

## 5. Templates

Templates are Mustache (070.UI.md § Templates): variables, sections, inverted sections,
comments, partials, and dotted names. There are no lambdas and no set-delimiter tags.

- **Where they live.** `_templates/$name.html` in the tenant's tree, then in the `_host`
  tree, then the host's built-in `page` and `list` templates. So a tenant with no
  templates at all still gets clean, responsive pages, and an operator can restyle every
  tenant at once from `_host`.
- **Every value is escaped.** `{{x}}` and `{{{x}}}` both escape, except for the names the
  host fills with HTML it rendered itself, looked up at the top of the data, which is only
  `body`. So `{{{body}}}` places the page, and no
  amount of braces lets a page's own fields or a box's JSON inject markup.
- **Layouts.** A template may start with front matter naming a `layout`. Its output then
  becomes the `body` of that layout, so one `base` template can hold the `<head>`, the
  navigation, and the footer, while `page`, `post`, and `list` hold only what differs.
  Layouts chain at most four deep.
- **Partials.** `{{> nav}}` includes `_templates/nav.html`, found the same way.
- **Checked when written.** The operator API refuses a template that doesn't parse.

**What a template sees:**

| name | value |
| --- | --- |
| body | The page's HTML: rendered markdown, or the fragment as written. |
| title, and every front matter key | From the page. |
| page | The front matter again, plus `url`, `path`, and `kind`. |
| site | `_data/site.json`, or `{}`. |
| data | Every `_data/$name.json`, by name. |
| user | The signed-in person (`user_id`, `email`, `roles`, `host`), or null. |
| pages, pagination, tag | For a listing (§6). |
| request | `path`, and `query` as an object. |
| now | `year`, and `date` as `YYYY-MM-DD`. |

## 6. Listings

A page becomes a listing when its front matter says `list: $dir`, where `$dir` is a
directory of the tree (`blog`), or `/` for the root. Hearth declares listings on the
template; goober declares them on the page, so one template can serve many listings.

- **Entries** are the pages directly in `$dir`: `blog/hello.md`, and `blog/trip/index.md`
  as `/blog/trip`. The listing page itself, drafts, private paths, and redirects are left
  out.
- **Each entry** has `url`, `path`, `title`, `date`, `summary`, `image`, `tags`, and every
  other front matter key, so a template can show whatever an author put there.
- **Sorting.** `sort: -date` (the default) sorts newest first, then by title. The keys are
  `date`, `title`, `order`, and `path`, each with `-` for descending.
- **Paging.** `per-page` (default 20, at most 200) splits the entries. `?page=2` picks a
  page, and a page past the end is 404. The template gets `pagination`: `page`, `pages`,
  `total`, `has_prev`, `has_next`, `prev_url`, `next_url`, and `numbers` (each `n`, `url`,
  and `current`).
- **Tags.** `?tag=news` keeps the entries tagged news, and the template gets `tag`.
- **Feeds.** `feed: true` also serves an Atom feed of the newest 20 entries at
  `$url/feed.xml`, with absolute links built from the request's host.

**Directory listings.** A URL that names a directory with no index page is listed only
when the tenant (or `_host`) has a `directory` template. The listing has the same data,
with `title` set from the directory's name. This keeps 070's rule that a hierarchy is
never exposed until someone opts in.

## 7. Attachments

Attachments are the special concept for static media: images and documents that pages
show, which people upload and agents set.

| decision | value |
| --- | --- |
| URL | `/attachment/$id.$ext`, like `https://jeffrey.io/attachment/1.png`. `$ext` must match the stored type, or it is 404. `/attachment/` is a host-owned prefix (041.ReservedRoutes.md). |
| Ids | Per tenant, minted by the tenant's ledger, starting at 1 and never reused. |
| Types | Detected from the bytes, never from the name or the claimed type: PNG, JPEG, GIF, WebP, AVIF, ICO, SVG, and PDF. Anything else is refused. |
| Bytes | `storage/objects/$tenant/attachments/$id`, written through the host WAL. |
| Ledger | The `uploads` table of 060.Files.md, in `storage/sqlite3/$tenant/internal.db`. A row is written as `writing` before the bytes and set to `stored` after them, so no file exists that the ledger doesn't know. |
| Size | 32 MiB with an operator's token (`attachment_put`, or `POST /attachment/upload`); 1 MiB from the attachments page with a browser session. A larger file is refused with the limit (413 over HTTP). *Until 2026-10-28 every way in was held to `limits.body-max-bytes`, 1 MiB for the whole request.* |
| Visibility | `public` (the default), or `members`: anyone signed in to the tenant's realm, or a host operator. |
| Serving | ETag of the SHA-256, `Cache-Control: public, max-age=31536000, immutable` (or `private` for members), `nosniff`. Raster images are inline. SVG and PDF are served as downloads with a `sandbox` CSP, since a browser can run them, but `<img src>` still shows an SVG. |

**Ways in:**

- **A one-time upload URL**: `attachment_upload_url` returns `/attachment/upload?ticket=...`
  on the tenant's domain, good for one PUT (or POST) of up to 32 MiB within 15 minutes, with
  the name, alt, and visibility asked for. An agent whose tool calls can't carry a large base64
  string (they get cut off) uploads from its own code or shell instead. Without code, it sends
  the base64 in pieces with `attachment_upload_part` (`ticket`, `base64`, `done`), each a
  multiple of 4 characters but the last; the last stores the file. The ticket is kept in
  memory by its hash, at most 100 outstanding, with at most 64 MiB of pieces held across them.
- **Cut-off files are refused** on every way in: an image or PDF must run to its format's end
  (PNG's IEND, JPEG's FF D9, GIF's trailer, WebP's RIFF length, PDF's `%%EOF`, an SVG's closing
  tag), and the error says how many bytes arrived.
- **Pages** (`page_put`): a whole `document` may carry front matter, marked `document: true`,
  for `title`, `summary`, `date`, `tags`, `draft`, and `requirements` (not `template` or
  listings); it is still served as written, without the front matter. A path ending in `/`
  writes the directory's index (`/about/` is `about/index.*`), and a write removes every other
  file answering that URL, so two files never compete for one. `page_get` resolves a URL as a
  visit does. Bodies are stored byte for byte. Text derived from HTML (summaries, the meta
  description) leaves out style, script, template, and comments. Without `_data/site.json`'s
  `title`, the built-in templates name the site by its domain.
- **Over MCP**, `attachment_put` takes `base64` bytes (small files: tool calls cut off long
  strings), a `file` already on the tenant's site
  (like `/hero.jpg`; a URL on one of the host's own domains, or loopback, is read the same way
  rather than fetched), or a `url` the host fetches: https
  only, at most 32 MiB, 20 seconds, three redirects. Agents that make or
  find an image usually hold a URL rather than bytes. The fetch uses the system `curl`
  until the host has the fetch capability of 030.TheLargerEnvironment.md, and only
  operators can ask for it.
- **Over HTTP**, `POST /attachment/upload` takes the file as the raw body, or as the
  `file` field of a `multipart/form-data` form, with optional `name`, `alt`, and
  `visibility`. It answers 201 with `{id, url, content_type, size, sha256}`, or a 303 back
  to the manager page for a browser form. The caller is an operator token, a host
  operator's session, or a session holding `owner` in the tenant; a cookie-authenticated
  POST must be same-origin.
- **In a browser**, `GET /attachment/` is the manager for owners and operators: an upload
  form, then every attachment with its thumbnail, its URL and markdown to copy, what uses
  it, and a delete button.

**Unused attachments.** Like Hearth's sweep, the host scans the tenant's text content
(pages, templates, data, CSS, and JS) for `/attachment/$id` and reports, per attachment,
which paths use it. Deleting one that is in use needs `force`. Nothing is deleted
automatically yet; 060's mark and sweep needs object columns in schemas first.

## 8. Box routes with templates

A route may name a `template`, as 070.UI.md § One route, many audiences shows. When the box
answers `application/json` with an object, and the caller prefers `text/html`, the host
renders the object through that template, with `site`, `user`, and `request` added. The
template is the manifest's own `templates.$name` when there is one, then the tenant's
`_templates/$name.html`. Anyone else gets the JSON. The box never knows which.

## 9. The operator API

| tool | does |
| --- | --- |
| site_guide | Explains this document's model to an agent: kinds, front matter, templates, listings, attachments, and the tool to use for each. |
| page_put | Writes a page from `path` (a URL like `/blog/hello`), `format` (markdown, fragment, or document), `body`, and optional `title`, `template`, and `fields`. It builds the front matter, and removes the page's file of another kind, so a URL has one page. |
| page_get | Returns a page's file, kind, front matter, and body. |
| page_list | Lists pages under a directory, with URL, title, date, template, and draft. |
| page_render | Renders a URL exactly as a visitor would get it, as status, headers, and HTML. With `drafts`, it renders a draft, which is how an agent previews. |
| template_put | Writes `_templates/$name.html`, after checking it parses. |
| template_list | Lists the tenant's templates, and which of `page`, `list`, and `directory` fall back to `_host` or the built-ins. |
| attachment_put, attachment_list, attachment_get, attachment_delete | §7. The list can show only unused ones. |
| content_put, content_get, content_list, content_delete | Unchanged, for any path, including `_data/` and static files. |

## 10. Safety of rendered pages

- **Templated pages** (markdown and fragments) carry a CSP: scripts and styles only from
  the site itself (inline styles allowed), images from the site, https, and data URLs,
  forms posting only to the site, and no framing by other sites. `nosniff` and
  `Referrer-Policy: same-origin` too.
- **Documents** carry only `nosniff` and `frame-ancestors 'self'`, since a whole page an
  agent wrote may carry its own inline script. That is a deliberate gap: §11.
- **Every rendered page** has an ETag of its output and `Cache-Control: no-cache`, so a
  browser revalidates and gets 304 when nothing changed. Pages behind requirements are
  `private, no-cache`.
