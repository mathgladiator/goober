# Ids from the host, and jobs that move data

> Status: machine-authored. The decisions in § 10 are the human's, from 2026-10-30. It builds
> `design/human/021.PrimaryKeys.md` and part of `design/human/420.Migration.md`.

On 2026-10-30 a site's engineers reported that goober's ids don't match 021. Realm user ids
were dense and per realm (1, 2, ...). A schema could hold a user reference as a string. Row
keys came from each database file. The human asked for this to be fixed ("the primary key work
is very important"), and for one-time boxes that move data between databases. Their production
databases will be moved into a new, unified database, and that move is what these jobs are for.

## 1. What v1 did

| what | minted by | so |
| --- | --- | --- |
| a realm's user ids | `users.id INTEGER PRIMARY KEY AUTOINCREMENT`, one file per realm | 1, 2, 3 in every realm; user 1 of one realm is not user 1 of another |
| invites, identity events | AUTOINCREMENT in the realm's file | the same |
| uploads | AUTOINCREMENT in each tenant's `internal.db` | the same, per tenant |
| a box table's rows | the table's rowid (`INTEGER PRIMARY KEY`, no AUTOINCREMENT) | dense per database, and SQLite may reuse the top id after a delete |
| a restore | nothing moves any counter | ids written after the last backup can be minted again |

There was no id service. Schemas had six column types (`int32`, `int64`, `double`, `float`,
`boolean`, `string`) and nothing for a reference. 008 § 9 recorded the rowids as a departure.

## 2. The id service

One service mints every new id, as 021 says, on a single machine:

- **Where.** `storage/ids/ids.db`: 021's `id_counter` (one row, `next_id`) and `id_ranges`
  (every range ever vended: start, length, to whom, when). It is an ordinary database under
  storage, so the nightly and the increments carry it with the data it numbers (019).
- **Ranges.** The host takes a range of 10,000 ids. The counter moves forward, durably, in
  the same transaction that records the range, before any id from it is used. A range is used
  up in memory under a mutex. Whatever is left when the host stops is lost, and the gaps are
  fine. Per-thread slices (021's third level) aren't needed on one machine: taking an id is
  one locked increment.
- **The first id.** A fresh service starts at 2^32 (4,294,967,296), and never below the
  highest id already in any database plus a margin of 10,000,000 (§ 6). Every id a SQLite
  rowid or AUTOINCREMENT ever made stays far below 2^32, so an old id and a new one can never
  be the same number. New ids stay below 2^53 for about nine quadrillion more, so even a
  client that reads them as numbers reads them exactly. 021 says ids start at 1; this starts
  higher for that separation (§ 11).
- **`ids_status`** (a read tool): the counter, the current range, and the ranges vended.

## 3. Keys a box never chooses

A new column type, **`id`**: an int64 the host minted. It is the primary key's type, and the
type of every column that refers to a row, a user, or an upload anywhere on the host.

```json
"profiles": {"columns": {
  "id": {"type": "id", "primary-key": true},
  "user_id": {"type": "id"},
  "display_name": {"type": "string", "max-length": 80}
}, "indexes": {"profiles_by_user": {"columns": ["user_id"], "unique": true}}}
```

- **A primary key of type `id`** is created as `INT PRIMARY KEY NOT NULL DEFAULT (goober_id())`.
  `INT`, not `INTEGER`, keeps it an ordinary column rather than SQLite's rowid, so the
  default applies: an insert that leaves the key out gets the next id from the service.
- **A box never names one.** Two host triggers, made with the table, refuse an insert whose
  key the host didn't just mint, and any update that changes the key: "a box never chooses a
  primary key: leave id out, and the host stamps one". Upserts that conflict on another
  unique column, like `user_id`, work as before. Operators' `db_exec` follows the same rule.
- **A reference column of type `id`** is an `INT` column the box writes freely: it holds an
  id minted elsewhere (a user's, another row's). Only primary keys are stamped.
- **New ids come back.** `goober_sql` answers an insert with `ids`, every id stamped by that
  statement, as strings, and `id`, the last of them. `last_insert_id` stays SQLite's rowid,
  as before, for tables keyed the old way.
- **Old tables keep their keys** (the human's choice, § 10). A primary key of type `int64`,
  and the `id` a table gets when it names none, stay SQLite rowids. `schema_put` and uploads
  warn about each (§ 5), and § 7's jobs move their rows into tables keyed by `id`.
- **The SQLite shell** can read these tables, but can't insert into them: `goober_id()` exists
  only inside the host.

## 4. Ids in JSON are strings

Every value read straight from an `id` column crosses JSON as a string, like `"4294967311"`,
in `goober_sql` results, `db_query`, and the panel, as 021 says. A box binds a string, or a
number, and SQLite's column affinity stores it as the integer either way, so `WHERE id = ?`
works with the string it was given. A computed value (`max(id)`) has no column type and
crosses as a number. `{!user_id}` and `user.user_id` were already strings.

## 5. Schema checks

At `schema_put`, `version_upload`, and a source build:

- **Refused:** a primary key that is nullable, or of any type but `id` or `int64`; a default
  on an `id` primary key.
- **Warned** (the schema is stored, and the warning is in the answer):
  - a primary key of type `int64`, or a table naming none: "new rows get this database's
    rowids, not host ids; declare `"id": {"type": "id", "primary-key": true}`";
  - a column whose name is `user_id`, ends in `_user_id`, or ends in `_id`, and whose type is
    `string`, `int32`, or `int64`: "a reference to a user or a row is `{"type": "id"}`; ids
    are never text and never emails".

A warning, not a refusal, because stored schemas are versions and existing tables keep their
shape (420). `box_guide` teaches `id` from the first example.

## 6. Existing ids and restores

- **Kept** (the human's choice). No id that exists is rewritten, so no reference breaks.
- **Jumped past.** The first time a host starts with the service, it reads the highest id in
  every database it keeps: each realm's users, invites, and events; each tenant's uploads; every
  box database's integer keys. The service starts at the larger of 2^32 and that highest id
  plus 10,000,000.
- **After a restore.** `goober-host rehydrate`, and `goober-host ids bump` on a server
  restored any other way, do the same against the restored files: the counter moves past
  their highest id, then 10,000,000 further, so no id that ever left the host, even one
  written after the last backup, is minted again (021).

## 7. Jobs: one-time boxes that move data

420 says a product restructures its data with a box that walks the old tables in batches and
writes the new ones. A job route is that box's entry point.

```json
{"box": "unify_v1", "mission": "Move members and their profiles into the unified database.",
 "data": {"sqlite3": {
   "old_access": {"pattern": "sql", "database": "access", "schema": "access2",
                  "tables": {"users": {"read": true}, "profiles": {"read": true}}},
   "unified":    {"pattern": "sql", "database": "main", "schema": "main1",
                  "tables": {"members": {"read": true, "insert": true}, "moved": {"read": true, "insert": true}}}}},
 "routes": {"job": {"move_members": {"name": "move_members", "timeout-ms": 2000}}}}
```

- **Only an operator starts one** (the human's choice). Deploying a job box runs nothing. A job
  route has no HTTP, MCP, or mail address; the host calls it.
- **Dry run first** (the human's choice). `job_dry_run {box, job, tenant}` runs the whole job
  against copies of the tenant's databases the box names (SQLite's online backup, into
  `storage/tmp/`), then discards them. It reports calls, rows each call said it moved, every
  error, and the box's log. `job_start` is refused unless a dry run of the same box version,
  job, and tenant passed.
- **Batches.** The host calls the route with `{"tenant", "cursor", "dry_run", "call"}`; the
  first cursor is `""`. The box does one batch and answers JSON
  `{"cursor": "...", "done": false, "moved": 250}`. Each call is one request: its SQL commits
  when it returns 200, as a request's does. The host keeps the cursor after each commit, so a
  restart or a `job_stop` resumes at the next batch. `done: true` ends it.
- **Idempotent by design.** A batch may run twice (the host stops between its commit and
  saving the cursor). The recipe in `box_guide`: keep a `moved` table in the target database
  (`old_id`, `new_id`, both `id` or `int64`), check it before inserting, and write it in the
  same statement batch. The same table maps old references to new ids for the next tables.
- **Ids.** Moved rows get fresh host ids, since a box never names a key. References to users
  keep the user's id, which already exists (§ 6). References between moved rows are rewritten
  through `moved`.
- **Bounds.** Each call has the route's `timeout-ms`, fuel, and the strategies' row limits.
  A job pauses after 3 failed calls in a row, with the error. One job runs at a time per
  tenant.
- **Tools.** `job_list` (each job route of each active box, and its runs), `job_dry_run`,
  `job_start`, `job_status {run}`, and `job_stop {run}`. `job_start` and `job_stop` change
  things, so they wait for approval when an agent's approvals are on (035). The panel shows
  runs and their progress.
- **Done is recorded** per box version, job, and tenant. Starting it again needs
  `again: true`.

## 8. References across databases

A row refers to another row, in any database, or to a user, by its `id`. Never by email: an
address changes, and two realms may hold the same one. A box that only has an address (mail in,
before anyone signs in) keeps the address in its own row until the person is known. Resolving
a mail sender to a user id is a separate decision (§ 10, open).

## 9. Build order

1. The service, `ids_status`, the first-start jump, `goober-host ids bump`, rehydrate's jump.
2. Users, invites, and uploads minted by it.
3. The `id` type, the triggers, `goober_sql`'s `ids`, strings in JSON, schema warnings,
   `box_guide`.
4. Jobs (§ 7).

## 10. Decisions

| decision | the human chose |
| --- | --- |
| Existing ids | Kept; the service starts past them |
| A box naming a primary key | Never |
| Existing tables | Keep SQLite's keys; new tables declare `id`; jobs move the rest |
| Table limits | Narrow grants: a database's operations limited to the tables the manifest declares (008 § 4.1) |
| Starting a job | Only an operator |
| Dry run | Required before the real run |
| The route kind | `routes.job` |
| Open | Resolving a mail sender's address to a user id for a box |
