# 048. Heat studies: where a domain's heat is, by endpoint

Status: drafted by Claude on 2026-11-03 at the human's request, built, and made lean the same
day. The human's words: "I want a way to do a study on a domain to discover heat by endpoint."
Then, on the first version: "Clean it up for performance, don't worry about internal, and make
it crisp and clean." It goes with per-domain operational controls (rate limits, concurrency
limits, endpoint overrides), designed in `047.Controls.md`. A study shows where a domain's heat
is and suggests controls an operator can set. It never sets one.

In 300's terms, heat is CPU cost, weight is the size of data, and bandwidth pressure is the
data rate. A study measures all three per endpoint, over a window someone picks, on one domain.

## 1. What a study is

A study is a time-boxed look at one domain's traffic:

- **Time-boxed.** 5 to 1440 minutes; 60 when left out.
- **In memory while it runs.** Every finished request on the domain feeds accumulators keyed
  by endpoint (§ 3).
- **A report when it ends.** The report is written to storage and kept 30 days (§ 6).
- **Look-only.** It changes nothing about how anything is served. It reads what the request
  path already knows, at the place the access log is written.

The limits:

- **One study per domain.** A second start on the same domain is refused, naming the running
  study.
- **Four on the host at once** (`HeatStudies::kMaxRunning`).

## 2. The tools

| tool | kind | scope rule | answers |
| --- | --- | --- | --- |
| `heat_study_start {domain, minutes?, why}` | changing, never waits | `kDomain` | the study's summary row: `id`, `domain`, `tenant`, `state` (`running`), `started_ms`, `ends_ms`, `minutes`, `why`, `by` |
| `heat_study_stop {id}` | changing, never waits | `kStudy` | the summary row, `state` `stopped`, `stopped_by` |
| `heat_study_get {id}` | read | `kStudy` | a running study's progress (with `remaining_ms`), or a finished one's report (§ 4) |
| `heat_study_list {domain?}` | read | `kFiltered` | summary rows, newest first, running ones with `remaining_ms` |

**Approvals.** Starting or stopping a study changes nothing that is served, so neither waits
for approval. `is_read_call` answers true for both, as it does for `db_export`. Neither is a
read tool, so an observer (`host:observer`) and the look-only panel can't start or stop one.
Only `heat_study_get` and `heat_study_list` are read tools.

**Audit.** Every start, stop, and end is an audit-log line:

- `study.start`: the operator, the domain, the id, the minutes, and why. A refused start is
  audited with `refused` and the error.
- `study.stop`: the operator's stop (`ended_by: operator`). The host writes the same line,
  with actor `host`, when a study's time is up (`ended_by: time`) and when the host stops
  (`ended_by: host_stopping`).

**Scope** (030):

- **`heat_study_start` is `kDomain`.** It names a domain, not a tenant: a focused operator
  starts studies on their tenants' domains only.
- **`heat_study_stop` and `heat_study_get` are `kStudy`.** The study's id is looked up before
  the call, and a study of another tenant's domain is refused ("heat study 4 is outside your
  scope", naming no tenant, since ids can be guessed). A post-filter (`kResult`) would let a stop
  run before the refusal, so the check comes first. The rule and the tools read `id` with one
  parser (`mcp::integer_arg`): an integer, a whole double like `4.0`, or a string of digits is the
  same study; any other shape (`4.5`, `true`, an array) is refused before either acts, never read
  two ways (the operator MCP checks integer and boolean arguments first, 030 § 3).
- **`heat_study_list` is `kFiltered`.** Every row names its tenant.

**Departure.** The request named `kTenant` for the start. `kTenant` needs a `tenant` argument
and refuses a call without one. The start takes a domain, so `kDomain` is the rule that fits,
and it reaches the same tenant through the domain.

`heat_study_start` checks that the domain is one the host serves (a configured domain, not a
redirect), that `minutes` is 5 to 1440, and that `why` is given.

## 3. What is counted

### 3.1 Which requests

**The hook.** `Host::access_log` already learns each finished request's tenant, route, box,
status, and duration, and feeds the live statistics (032 § 6) and the pulse (028 § 4.6). Beside
them is one line:

```cpp
if (heat_ && heat_->watching(domain)) heat_observe(req, line, domain, bytes_out);
```

**Bytes out.** `access_log` gains one parameter, `bytes_out`: the body sent, given by the
request path's one `Finish`. It is 0 for a HEAD and for a stream. Bytes in are the request
body's size.

**Left out**, never counted, shown, or suggested for:

- the host's own paths: `/goober/*` (health, ready, PWA, unsubscribe, connect) and CORS
  preflights (every `OPTIONS`; no box route takes one). The human: "don't worry about
  internal". Monitors polling `/goober/ready` no longer dilute a site's numbers;
- tries (`route_try`): no one visited;
- the panel;
- the operator API (`/goober-operations-mcp`);
- the mail hook;
- the host's own calls: timers, outbox results, identity events, and internal calls. These
  are logged with paths that don't start with `/`.

### 3.2 The endpoint

An endpoint is an API and a key, in 047's vocabulary, and studies use only 047's four APIs.

| what was asked | API | endpoint |
| --- | --- | --- |
| a box route | `box:<box name>` | `METHOD /pattern`: the route's declared pattern as 047's `match`, from the same route-table match the dispatcher makes |
| `/mcp` | `mcp` | the tool's name, or `(rpc)` for a call that isn't a tool call (initialize, tools/list) |
| `/identity/*`, `/oauth*`, `/.well-known/*` | `identity` | `METHOD /path`, with `/identity/invite/{rest*}` for invite links |
| a page, an asset | `content` | `METHOD /path`; attachments as `GET /attachment/{file}` |
| nothing answered (404) | `content` | `(not found)` |
| the host refused a content path (400 and up) | `content` | `(refused)` |

**Box routes.** The pattern conversion (`operations::endpoint_match`) uppercases the method,
keeps literals, and writes each parameter as `{name}`, leaving out its type:

```
get  /posts/{id : int64}   ->   GET /posts/{id}
```

A HEAD counts as its GET route. A subscription (036) counts as `GET` on its pattern.

**A refused box route stays its route's.** A 401 for a route that needs a sign-in, a 403, or a
rate limit's 429 before the box ran is still that route's. The endpoint comes from matching
the route table, not from which part of the host answered, so an endpoint's status mix shows
what callers of that route got.

**Capability links are never endpoints.** Invites are folded to `{rest*}`, as the live
statistics fold them. The same goes for paths nothing answers and refusals of content paths,
so a scanner can't fill the table with its guesses.

### 3.3 Per endpoint

| number | how |
| --- | --- |
| requests, and shares | counted; the endpoint's share of the domain's heat, requests, and bytes |
| heat | the time spent serving, summed (µs) |
| bytes | in and out, and the largest body in |
| busiest minute | the endpoint's most requests in one minute of the study, and when |
| distinct clients | exact while the endpoint has seen at most 256 clients at once (`exact: true`); past that, a HyperLogLog of 256 registers, within about 6.5% (`exact: false`) |
| each client's busiest minute | each client's most requests on the endpoint in one minute, as p50, p99, and max over clients (§ 3.4), and the busiest client's share of the endpoint's requests (`top_share`). This is what a per-client rate needs |
| peak concurrent, and per client | the most requests in flight at once on the endpoint, and the most one client had at once (§ 3.5) |
| latency | p50 and p99 (in the 40 latency buckets the host uses everywhere, clamped to the max), and max |
| status mix | 2xx, 3xx, 4xx (not 429), 5xx, and 429 |

**The whole domain** gets totals (requests, heat, bytes, the status mix, latency) and its
requests per minute (a series, its peak, and when). Its distinct clients are the union of the
endpoints' HyperLogLogs, an estimate. Its ten busiest clients by keyed hash (`clients.top`) are
summed from the endpoints' client tables at report time, each with the endpoint it asked most.
No per-request work is done for the domain beyond its totals.

### 3.4 Each client's busiest minute

**What is kept.** Per endpoint, a table of clients: each client's current minute, its count in
that minute, its best minute so far, its requests, and its keyed hash (§ 7), made once when the
client first asks the endpoint.

**Folding.** When the table is full (256 clients) and a new client arrives, clients not seen in
the current minute are folded, at most once a minute. A folded client's best minute goes into a
histogram of finished clients, and it leaves the table.

**The histogram.** 184 buckets: exact below 64, then eight buckets per power of two, so within
12.5%. A percentile answers its bucket's upper edge, never above the largest seen.

**The distribution** is that histogram plus the clients still in the table.

**Overflow.** If every client in a full table was seen this minute, a new client's request is
counted everywhere else, but not attributed to a client (`unattributed_requests`).

**A folded client that comes back** starts over. Its later minutes are counted as one more
client's, so the max stays right and the p99 can only lean low. A folded client is also missing
from `clients.top`, so the top list counts the clients still in the tables.

### 3.5 Concurrency from finished requests

The hook sees a request only when it finishes. From its duration it knows when it started
(`end - us`, on the monotonic clock). Each endpoint keeps a ring of its last 64 finished
requests.

**How it is counted.** A new interval is checked against each one in the ring, both ways:

- Does the earlier one contain the new one's start? Then the new one's count goes up.
- Does the new one contain the earlier one's start? Then the earlier one's count goes up.

A long request that finishes after the short ones inside it is still counted at every start
it covers.

**How exact it is.** The peak is exact while no more than 64 overlap on the endpoint. Past
that, it can only be low. The per-client peak counts the same way, among the same client's
intervals.

**Departure.** The request asked for "peak concurrent in flight". Counting in flight would need
a second hook where a request begins, and the endpoint isn't known there: a box route is
matched later, and an MCP tool's name later still. Counting from finished requests keeps the
hook to one place and is exact to the ring's size. The human kept this (§ 11, decision 1).

### 3.6 The 500 endpoints, and "other"

The first 500 endpoints seen are tracked with every number. Past that:

- A request for an untracked endpoint goes to `other`, which has the same numbers.
- The untracked endpoint is counted as a candidate (up to 5,000 candidates; past them only
  `other` counts).

**Promotion.** Once a minute, a candidate busier than the least busy tracked endpoint takes its
place, for up to 50 swaps a minute. The endpoint it replaces is folded into `other`. A promoted
endpoint's report names `tracked_from_ms` and `before_tracked`, the requests counted in `other`
before it was tracked. So the tracked set approaches the top 500 by requests, and every request
is counted once, in an endpoint or in `other`.

### 3.7 Memory

At most about 22 KiB per tracked endpoint: a count per minute (up to 1,441), 256 clients, a
ring of 64, the histograms, and the HyperLogLog.

Measured (`HeatStudy.ADayOfManyEndpointsStaysSmall`): a day-long study of 600 endpoints, 500
of them tracked, held 10.5 MiB (10.7 before the cleanup). A study is at most about 12 MiB, so
four at once are about 48 MiB. The report and `heat_study_get` give `memory_bytes`.

When a study ends, its counts are freed once the report is written. A small shell (its domain,
its lock, and its summary fields, well under 1 KiB) stays until the host stops, so a request
that found the study just before it ended reads a live object (§ 3.8).

### 3.8 The cost on the request path

**Nothing running anywhere:** `watching` is one relaxed atomic load (measured 1.6 to 2.6 ns,
the loop included).

**A study running:**

- **Finding the study takes no lock.** The running studies sit in four slots, each an atomic
  pointer. `watching` compares the domain with each slot's (4 to 6 ns for a domain no study
  watches). A study's slot is cleared when it ends, under its own lock.
- **One lock per study,** taken once per request on its domain and held for the update (about
  100 ns). No host-wide lock is taken.
- **No strings on the way in.** The hook hands the study views: the API, the box's name, the
  method, and the route's declared pattern (or the path, or the tool). The study keys the
  endpoint by a 64-bit hash of those parts and builds the endpoint's names once, when it first
  sees it. Two endpoints share a hash with odds of about one in 10^12 for 5,500 of them; they
  would be counted as one.
- **The client's keyed hash is made once per endpoint it asks,** not per request. The request
  path hashes the client with `std::hash` to find it; the log key's HMAC (§ 7) runs only when a
  client is new to an endpoint's table.
- **No domain-wide client table or concurrency ring.** The first version's ring of 512 for the
  whole domain was the costliest part of each request (a scan of 512 intervals), and nothing
  a control takes came from it.

Measured on 2026-11-03, release build, one machine (`HeatStudy.RecordCost` in the operations
tests, `HeatStudyHostTest.HookCost` in the host's; both print their numbers):

| | before | after |
| --- | --- | --- |
| a request recorded (40 endpoints, 3,000 clients), one thread | 380 to 580 ns | 100 to 145 ns |
| the same, four threads at once (wall time per request) | 710 to 810 ns | 290 to 650 ns |
| a domain no study watches, one running elsewhere | 6 to 10 ns | 4 to 6 ns |
| the whole hook in the host (keying a box route, the client, recording) | about 1,230 ns | about 290 ns |
| nothing running | one relaxed load | one relaxed load (about 2 ns) |

Four threads on one domain contend for its one lock; the wall time per request is still a
fraction of a microsecond, past any rate the host serves. Sharding the study (per-shard
endpoint tables merged at report time) would remove that contention but not the per-endpoint
ring, and wasn't worth its weight.

## 4. The report

### 4.1 Fields

**Summary:**

- `id`, `domain`, `tenant`, `state`, `ended_by`, `why`, `by`, `stopped_by`;
- `minutes`, `started_ms`, `ends_ms`, `ended_ms`, `elapsed_ms`, `saved_ms`;
- `requests`, `endpoints`, and `hottest` (the hottest endpoint and its heat share).

`state` is `running`, `done`, `stopped`, or `interrupted`. `ended_by` is `time`, `operator`,
`host_stopping`, or `restart`.

**The whole domain:**

- `totals`: `requests`, `heat_us`, `bytes_in`, `bytes_out`, `status`, and `latency_us`;
- `per_minute`: `series`, `peak`, and `peak_at_ms`;
- `clients`: `distinct` (an estimate) and `top`, the ten busiest by keyed hash: `client_h`,
  `requests`, and the `endpoint` and `api` each asked most.

**`endpoints`,** ranked by heat (ties by requests, then by name). Every row has `endpoint`,
`api`, `requests`, `heat_share`, `requests_share`, and `bytes_share`. The hottest 100 also
carry:

- `heat_us`; `bytes`: `in`, `out`, `max_in`;
- `latency_us`: `p50`, `p99`, `max`;
- `per_minute`: `peak`, `peak_at_ms`;
- `clients`: `distinct`, `exact`, `busiest_minute` (`p50`, `p99`, `max`), `top_share`, and
  `unattributed_requests` when there were any;
- `concurrent`: `peak`, `per_client_peak`;
- `status`: `2xx`, `3xx`, `4xx`, `5xx`, `429`;
- `tracked_from_ms` and `before_tracked` for a promoted endpoint;
- `suggest` (§ 4.2).

**The rest:** `tracked` (`endpoints`, `cap`, `other_requests`, `promoted`), `memory_bytes`, and
three `notes`: what heat and a client are, how exact the minutes and concurrency are, and how to
use the suggestions.

**Small.** A report is at most 256 KiB (`kReportMaxBytes`). Past that, the detail of the cooler
endpoints goes first (100, then 50, 20, 0). The day-long test's report is 163 KiB with every
detail in (202 KiB before the cleanup).

### 4.2 Suggestions

Each detailed endpoint's `suggest` is either `{control_set, reasons}` or `{none: why}`.

**`control_set`** holds ready-to-send `control_set` arguments in 047's vocabulary:

```json
{"domain": "www.example.com", "api": "box:shop",
 "endpoint": {"id": "post_cart_id", "match": "POST /cart/{id}"},
 "set": {"rate": {"per-minute": 24, "burst": 12, "by": "client"},
         "concurrent": {"max": 6, "per-client": 2},
         "body-max-bytes": 6144, "timeout-ms": 1000},
 "mode": "observe", "why": "heat study 3: observe first, then enforce"}
```

**`reasons`** gives each number with its inputs, like "per-minute 24 = max(10, 2 x 12, the p99
of each client's busiest minute over 40 clients); burst is half that". Counts are worded for
their number: "1 client", "1 request", "1 byte".

The formulas:

| property | value | when |
| --- | --- | --- |
| `rate` by client | `per-minute` = max(10, 2 × the p99 of each client's busiest minute); `burst` = ceil(per-minute / 2) | by default |
| `rate` by all | `per-minute` = max(10, 2 × the endpoint's busiest minute, every client together); `burst` the same | only when the endpoint's whole rate is the risk: it holds 25% or more of the domain's heat, over 20 or more clients, and no client has 10% of its requests. A per-client rate wouldn't protect it then |
| `concurrent` | `max` = max(2, 2 × the peak in flight); `per-client` = max(1, 2 × one client's peak) | always |
| `body-max-bytes` | max(1024, 2 × the largest body seen, rounded up to a KiB) | when a request had a body |
| `timeout-ms` | max(1000, 2 × the slowest answer, rounded up to 100 ms) | box routes only |
| `mode` | `"observe"` | always |
| `closed` | never suggested | a person decides to close an endpoint |

**No suggestion** (`none`) when:

- the endpoint had fewer than 20 requests ("only 1 request: too few to suggest from; study
  longer, or at a busier time");
- it is a grouped row (`(not found)`, `(refused)`, `(rpc)`, or `other`).

**Always observe.** Every suggestion comes in `mode: "observe"`. The operator sends it, reads
`control_report` while it observes, and enforces once it would have refused only what it
should. The study never sets a control.

**Departure: `by: user`.** It is never suggested. A study keys clients by address and keeps no
user ids (§ 7), so it has no per-user minutes to base a number on.

### 4.3 Agreed with 047

Settled when the two merged on 2026-11-03:

- **The shape.** A suggestion is `control_set`'s arguments as 047 takes them: `domain`, `api`,
  `endpoint: {id, match}`, `set` with the properties, `mode: "observe"`, and `why`. The `id` is
  made from the endpoint (letters and digits kept, the rest `_`, lowercase: `POST /cart/{id}` is
  `post_cart_id`), so a second suggestion for the same endpoint updates the same override.
- **MCP tools.** At first they got none: 047 matched only `"METHOD /path"`, and every MCP call
  is `POST /mcp`. 047 now takes `"TOOL /<name>"`, which matches one tool's calls
  only and names no `api`, so a hot tool's suggestion is `{"endpoint": {"id": "tool_search", "match":
  "TOOL /search"}, ...}` with `rate`, `concurrent`, and `body-max-bytes` (every call has a
  body), and no `timeout-ms`, as for every endpoint that isn't a box route (§ 11, decision 5).
  `(rpc)` (initialize, tools/list) stays a grouped row with none.

## 5. While it runs, and when it ends

**While it runs:**

- `heat_study_get` builds the report from memory, with `state: running` and `remaining_ms`.
- The timer thread's one-second tick ends a study whose time is up. A request that finishes
  at or after `ends_ms` isn't counted.
- The tick writes each running study's report to its file once a minute, and promotes
  endpoints (§ 3.6).

**It ends** in one of three ways:

- **Time up:** `state: done`, `ended_by: time`, `ended_ms` = `ends_ms`.
- **`heat_study_stop`:** `state: stopped`, `ended_by: operator`, `stopped_by`. What was gathered
  is kept. A second stop answers that the study already ended.
- **The host stopping** (`Host::stop`, after every request in flight has finished):
  `state: stopped`, `ended_by: host_stopping`.

**A crash or a kill.** The file is written at the start, then once a minute, so after a crash
or a kill the file holds the last minute's save with `state: running`. The next start finds it,
marks it `state: interrupted`, `ended_by: restart`, and `ended_ms` = its last save, and says so
in the startup notes. A study doesn't resume after a restart; start another. New ids carry on
past the highest id in the directory.

## 6. Storage and limits

Each study is one file, `storage/operations/studies/<id>.json`, beside the panel's other files
in `operations/`. It is the report as JSON.

**Kept** 30 days after the study ends. The hourly housekeeping deletes older ones.

**The budget** is `limits.studies-bytes`, 64 MiB (floor 1 MiB). Past it, the oldest finished
report goes first, at the hourly housekeeping and whenever a study ends. A running study's file
counts toward the budget but is never deleted. A study is derived and expiring, so rule 1 of 045
applies: dropped oldest first, never refused.

**Reported** in the `limits` check of `/goober/ready` and `host_health` as `studies`.

045's table has the row:

| what | where | kept | byte budget | over budget | built |
| --- | --- | --- | --- | --- | --- |
| heat study reports | `operations/studies/` | 30 days after the study ends | `studies-bytes`, 64 MiB; each report at most 256 KiB | the oldest finished report goes | yes |

**Backups.** The nightly holds `storage/operations/studies` with the rest of storage. Reports
are small, and a restore keeps them (§ 11, decision 4).

## 7. Nothing private

A report names no address and no user id:

- **A client is a keyed hash.** The host's log key (`address_hash_for_logs`, 032 § 1) is applied
  to the rate limiter's client key (`rate_key`: the address, or an IPv6 /64). For an IPv4
  client it is the same hash as the audit log's `client_h`, so the log dive finds that client's
  lines without the report holding the address. In memory, a client is found by a plain hash of
  the same key, which never leaves memory.
- **`clients.top` lists hashes and counts only** (§ 11, decision 3).
- **No paths that carry capabilities** (§ 3.2).
- **No user ids.** The access line's `user_id` is never read, and the report never carries one.
- **The operator who started the study is named** (`by`, `stopped_by`). Operators are who
  acted (032 § 4).

The host test `RequestsAreKeyedByEndpointAndGetSuggestions` checks that a report holds neither
the test client's address nor `user_id`.

## 8. The panel: Studies (`#/studies`)

Look-only, from `heat_study_list` and `heat_study_get`. A focused operator sees only their
tenants' studies (the scope's filter and refusal, § 2).

- **The list:** each study with its domain, state (a running one with the time left), start,
  minutes, requests, hottest endpoint and its share, who started it, and why. A row opens it.
- **One study:**
  - **The header:** why, who, and when; for a running study, the time left and "numbers so
    far". It refreshes every 15 seconds while visible.
  - **Totals:** requests, heat, bytes, the busiest minute, clients (≈, an estimate), and p99
    latency.
  - **Requests per minute:** a chart.
  - **Busiest clients:** the ten by keyed hash, their requests, and the endpoint each asked
    most.
  - **Where the heat is:** bars for the top 20 endpoints, by heat (CPU share), requests, or
    bytes, colored hot to cold, and a note of what went to `other`.
  - **Endpoints:** a table of every detailed endpoint: requests, heat share, bytes out, peak per
    minute, clients, each client's busiest minute (p50 · p99 · max), the most at once (and for
    one client), latency p50 and p99, 4xx, 5xx, and 429.
  - **Suggested controls:** each endpoint's `control_set` arguments as JSON, and the reason for
    each number. The panel sends nothing: "send it, read control_report while it observes, and
    enforce once it holds."

The bars are SVG with widths as attributes, so the panel's content security policy (no inline
styles) holds.

## 9. How to use it

The same recipe is in HUMAN.md and the box guide:

1. **Start a study for an hour at a busy time:**

   ```
   heat_study_start {domain: "www.example.com", minutes: 60, why: "Monday's peak"}
   ```

2. **Read it:** the panel's **Studies** view, or `heat_study_get {id}`. Look at what holds the
   heat, and which endpoints one client drives hard (a high client p99 per minute). The busiest
   clients' hashes find their lines, and their user agents, in the log dive.
3. **Send a suggestion as it is:** `control_set` with the `control_set` arguments. They are in
   observe mode.
4. **Check `control_report`:** what the control would have refused, and whom.
5. **Enforce:** the same `control_set` with `mode: "enforce"`, once it would have refused only
   what it should.

## 11. Decisions for the human

Decisions 1 to 4 were made on 2026-11-03 with one answer (decision 5 followed from 047's tool match): "Clean it up for performance, don't
worry about internal, and make it crisp and clean."

1. **Concurrency from finished requests (§ 3.5). Decided: kept.** Exact up to 64 in flight per
   endpoint, with one hook. The domain-wide ring of 512 went with the cleanup (§ 12).
2. **The `host` API (§ 3.2). Decided: "don't worry about internal".** `/goober/*` paths and
   preflights are no longer studied at all: no rows, no suggestions. The global rate limiter
   covers them.
3. **Top clients by hash (§ 7). Decided: kept.** The ten busiest clients' keyed hashes, so an
   operator can find their lines in the log dive. A hash is stable for the host's log key, so a
   client can be followed across studies, as in the audit log.
4. **Reports in backups (§ 6). Decided: kept.** They are small and kept 30 days; leaving them in
   the nightly costs little.
5. **Controls for one MCP tool (§ 4.3). Decided: tools can be matched.** The controls work of
   2026-11-03 added `"TOOL /<name>"` on api `mcp` (with a fixed MCP queue and a strict per-agent
   MCP rate), so a hot tool now gets a suggestion like any other endpoint.

## 12. What the cleanup cut, and why

The first version counted more than an operator uses to find heat and set a control. Cut on
2026-11-03:

| cut | why |
| --- | --- |
| the `host` API: `/goober/*` and preflight rows | "don't worry about internal" (decision 2); a monitor's polls of `/goober/ready` also skewed the domain's numbers |
| client classes (browser, bot, agent, other), per endpoint and in the totals | a reading of the user agent that a bot can fake; it cost a lowercase copy and 21 substring searches per request; no suggestion used it. The log dive by `client_h` shows the real user agents |
| fuel | a second measure of heat, for box routes only; heat is the time serving, and `hot_boxes` shows fuel |
| `ranks` (`by_heat`, `by_requests`, `by_bytes`) | every endpoint row already carries its three shares, and the panel sorts them itself |
| per-endpoint series for the hottest 10, and each endpoint's mean per minute | the panel never drew them; the peak and when are what a rate needs; the mean is requests over the elapsed minutes |
| the domain's client table (4,096 clients): its busiest-minute distribution and exact distinct count | per request, a second table update for the domain; suggestions are per endpoint. Distinct clients are now the union of the endpoints' estimates, and the top clients come from the endpoints' tables |
| the domain's concurrency ring (512) | the costliest part of each request; no control takes a domain-wide concurrency from a study |
| `exact_up_to` on each row, `tracked.candidates`, `candidates_dropped`, `detailed`, two of the five notes | constants and bookkeeping; the notes say the ring's size once |
| `classify_client` and the host's user-agent and bearer reading | went with the classes |

Kept, as the human decided: concurrency from finished requests (decision 1), top clients by
keyed hash (decision 3), and reports in backups (decision 4).
