# 048. Heat studies: where a domain's heat is, by endpoint

Status: drafted by Claude on 2026-11-03 at the human's request, and built. The human's words:
"I want a way to do a study on a domain to discover heat by endpoint." It goes with per-domain
operational controls (rate limits, concurrency limits, endpoint overrides), designed in
`047.Controls.md`. A study shows where a domain's heat is and suggests controls an operator can
set. It never sets one.

In 300's terms, heat is CPU cost, weight is the size of data, and bandwidth pressure is the
data rate. A study measures all three per endpoint, over a window someone picks, on one domain.

## 1. What a study is

A study is a time-boxed look at one domain's traffic:

- **Time-boxed.** 5 to 1440 minutes; 60 when left out.
- **In memory while it runs.** Every finished request on the domain feeds accumulators keyed
  by endpoint (§ 3).
- **A report when it ends.** The report is written to storage and kept 30 days (§ 6).
- **Look-only.** It changes nothing about how anything is served. It reads what the request
  path already knows, at the place the access log is written.

The limits:

- **One study per domain.** A second start on the same domain is refused, naming the running
  study.
- **Four on the host at once** (`HeatStudies::kMaxRunning`).

## 2. The tools

| tool | kind | scope rule | answers |
| --- | --- | --- | --- |
| `heat_study_start {domain, minutes?, why}` | changing, never waits | `kDomain` | the study's summary row: `id`, `domain`, `tenant`, `state` (`running`), `started_ms`, `ends_ms`, `minutes`, `why`, `by` |
| `heat_study_stop {id}` | changing, never waits | `kStudy` | the summary row, `state` `stopped`, `stopped_by` |
| `heat_study_get {id}` | read | `kStudy` | a running study's progress (with `remaining_ms`), or a finished one's report (§ 5) |
| `heat_study_list {domain?}` | read | `kFiltered` | summary rows, newest first, running ones with `remaining_ms` |

**Approvals.** Starting or stopping a study changes nothing that is served, so neither waits
for approval. `is_read_call` answers true for both, as it does for `db_export`. Neither is a
read tool, so an observer (`host:observer`) and the look-only panel can't start or stop one.
Only `heat_study_get` and `heat_study_list` are read tools.

**Audit.** Every start, stop, and end is an audit-log line:

- `study.start`: the operator, the domain, the id, the minutes, and why. A refused start is
  audited with `refused` and the error.
- `study.stop`: the operator's stop (`ended_by: operator`). The host writes the same line,
  with actor `host`, when a study's time is up (`ended_by: time`) and when the host stops
  (`ended_by: host_stopping`).

**Scope** (030):

- **`heat_study_start` is `kDomain`.** It names a domain, not a tenant: a focused operator
  starts studies on their tenants' domains only.
- **`heat_study_stop` and `heat_study_get` are `kStudy`,** a new rule. The study's id is looked
  up before the call, and a study of another tenant's domain is refused ("heat study 4 is of
  other"). A post-filter (`kResult`) would let a stop run before the refusal, so the check
  comes first.
- **`heat_study_list` is `kFiltered`.** Every row names its tenant.

**Departure.** The request named `kTenant` for the start. `kTenant` needs a `tenant` argument
and refuses a call without one. The start takes a domain, so `kDomain` is the rule that fits,
and it reaches the same tenant through the domain.

`heat_study_start` checks:

- that the domain is one the host serves (a configured domain, not a redirect);
- `minutes` within 5 to 1440;
- that `why` is given.

## 3. What is counted, and how a request finds its endpoint

### 3.1 Which requests

**The hook.** `Host::access_log` already learns each finished request's tenant, route, box,
status, and duration, and feeds the live statistics (032 § 6) and the pulse (028 § 4.6). Beside
them is one line:

```cpp
if (heat_ && heat_->watching(domain)) heat_observe(req, line, domain, bytes_out);
```

**The cost when nothing runs.** `watching` is one relaxed atomic load when no study runs
anywhere. When some study runs, it takes a lock and compares the domain with at most four.
Nothing else happens for a domain no study watches. The work of keying (§ 3.2) and hashing the
client happens only for a studied domain.

**Bytes out.** `access_log` gains one parameter, `bytes_out`: the body sent, given by the
request path's one `Finish`. It is 0 for a HEAD and for a stream. Bytes in are the request
body's size.

**Left out:**

- tries (`route_try`): no one visited;
- the panel;
- the operator API (`/goober-operations-mcp`);
- the mail hook;
- the host's own calls: timers, outbox results, identity events, and internal calls. These
  are logged with paths that don't start with `/`.

### 3.2 The endpoint

An endpoint is an API and a key, in 047's vocabulary.

| what was asked | API | endpoint |
| --- | --- | --- |
| a box route | `box:<box name>` | `METHOD /pattern`: the route's declared pattern as 047's `match`, from the same route-table match the dispatcher makes |
| `/mcp` | `mcp` | the tool's name, or `(rpc)` for a call that isn't a tool call (initialize, tools/list) |
| `/identity/*`, `/oauth*`, `/.well-known/*` | `identity` | `METHOD /path`, with `/identity/invite/{rest*}` for invite links |
| a page, an asset | `content` | `METHOD /path`; attachments as `GET /attachment/{file}` |
| nothing answered (404) | `content` | `(not found)` |
| the host refused a content path (400 and up) | `content` | `(refused)` |
| `/goober/*` (health, ready, PWA, unsubscribe, connect) | `host` | `METHOD /goober/<segment>/{rest*}` |
| a CORS preflight | `host` | `(preflight)` |

**Box routes.** The pattern conversion (`operations::endpoint_match`) uppercases the method,
keeps literals, and writes each parameter as `{name}`, leaving out its type:

```
get  /posts/{id : int64}   ->   GET /posts/{id}
```

A HEAD counts as its GET route. A subscription (036) counts as `GET` on its pattern.

**A refused box route stays its route's.** A 401 for a route that needs a sign-in, a 403, or a
rate limit's 429 before the box ran is still that route's. The endpoint comes from matching
the route table, not from which part of the host answered. So an endpoint's status mix shows
what callers of that route got.

**Capability links are never endpoints.** Unsubscribe links, list confirmations, and invites
are folded to `{rest*}`, as the live statistics fold them. The same goes for paths nothing
answers and refusals of content paths, so a scanner can't fill the table with its guesses.

**Not in 047's vocabulary.** The `host` API isn't one of 047's four. Its rows are shown, but
never get a suggestion (§ 4.2).

### 3.3 Per endpoint

| number | how |
| --- | --- |
| requests, and the API | counted |
| requests per minute | a count per minute of the study; the report gives the peak, when it was, and the mean, and a series for the 10 hottest endpoints |
| distinct clients | each client kept by its keyed hash. Exact while the endpoint has seen at most 256 clients at once (`exact: true`). Past that, a HyperLogLog of 256 registers estimates it, within about 6.5% (`exact: false`) |
| each client's busiest minute | each client's most requests in one minute of the study, as p50, p99, and max over clients (§ 3.4). This is what a per-client rate needs |
| peak concurrent, and per client | the most requests in flight at once on the endpoint, and the most one client had at once (§ 3.5) |
| latency | p50, p99 (in the 40 latency buckets the host uses everywhere, clamped to the max), and max |
| heat | the time spent serving, summed (µs), and fuel where a box ran |
| weight | bytes in and out, and the largest body in |
| status mix | 2xx, 3xx, 4xx (not 429), 5xx, and 429 |
| client classes | browser, bot, agent, and other (§ 3.6) |

The whole domain gets the same numbers: one more accumulator, with up to 4,096 clients and a
concurrency ring of 512. The report also lists the ten busiest clients by keyed hash
(`top_clients`): requests, busiest minute, and class.

### 3.4 Each client's busiest minute

**What is kept.** Per endpoint, a table of clients: each client's current minute, its count in
that minute, its best minute so far, and its requests.

**Folding.** When the table is full (256 clients) and a new client arrives, clients not seen in
the current minute are folded, at most once a minute. A folded client's best minute goes into a
histogram of finished clients, and it leaves the table.

**The histogram.** 184 buckets: exact below 64, then eight buckets per power of two, so within
12.5%. A percentile answers its bucket's upper edge, never above the largest seen.

**The distribution** is that histogram plus the clients still in the table.

**Overflow.** If every client in a full table was seen this minute, a new client's request is
counted everywhere else, but not attributed to a client (`unattributed_requests`).

**A folded client that comes back** starts over. Its later minutes are counted as one more
client's, so the max stays right and the p99 can only lean low.

### 3.5 Concurrency from finished requests

The hook sees a request only when it finishes. From its duration it knows when it started
(`end - us`, on the monotonic clock). Each endpoint keeps a ring of its last 64 finished
requests, and the domain keeps a ring of 512.

**How it is counted.** A new interval is checked against each one in the ring, both ways:

- Does the earlier one contain the new one's start? Then the new one's count goes up.
- Does the new one contain the earlier one's start? Then the earlier one's count goes up.

A long request that finishes after the short ones inside it is still counted at every start
it covers.

**How exact it is.** The peak is exact while no more than the ring's size overlap
(`exact_up_to`). Past that, it can only be low. The per-client peak counts the same way,
among the same client's intervals.

**Departure.** The request asked for "peak concurrent in flight". Counting in flight would need
a second hook where a request begins, and the endpoint isn't known there: a box route is
matched later, and an MCP tool's name later still. Counting from finished requests keeps the
hook to one place and is exact to the ring's size.

### 3.6 Client classes

**Departure.** The access log doesn't classify clients, so the study does it from what the
request carries, and keeps only the class:

- **agent:** a bearer token, or `/mcp`;
- **bot:** a user agent naming a bot, a crawler, a spider, or a tool (curl, wget, python,
  Go's client, headless browsers, monitors, and others in `classify_client`);
- **browser:** a user agent starting `Mozilla/`;
- **other:** anything else.

It is a cheap reading, not a verdict. A bot that says it is a browser counts as a browser.

### 3.7 The 500 endpoints, and "other"

The first 500 endpoints seen are tracked with every number. Past that:

- A request for an untracked endpoint goes to `other`, which has the same numbers.
- The untracked endpoint is counted as a candidate (up to 5,000 candidates; past them only
  `other` counts).

**Promotion.** Once a minute, a candidate busier than the least busy tracked endpoint takes its
place, for up to 50 swaps a minute. The endpoint it replaces is folded into `other`. A promoted
endpoint's report names `tracked_from_ms` and `before_tracked`, the requests counted in `other`
before it was tracked. So the tracked set approaches the top 500 by requests, and every request
is counted once, in an endpoint or in `other`.

### 3.8 Memory

At most about 22 KiB per tracked endpoint:

- a count per minute (up to 1,441);
- 256 clients;
- a ring of 64;
- the histograms;
- the HyperLogLog.

Measured (`HeatStudy.ADayOfManyEndpointsStaysSmall`): a day-long study of 600 endpoints, 500
of them tracked, held 10.7 MiB. A study is at most about 12 MiB, so four at once are about
48 MiB. The report and `heat_study_get` give `memory_bytes`.

## 4. The report

### 4.1 Fields

**Summary:**

- `id`, `domain`, `tenant`, `state`, `ended_by`, `why`, `by`, `stopped_by`;
- `minutes`, `started_ms`, `ends_ms`, `ended_ms`, `elapsed_ms`, `saved_ms`;
- `requests`, `endpoints`, and `hottest` (the hottest endpoint and its heat share).

`state` is `running`, `done`, `stopped`, or `interrupted`. `ended_by` is `time`, `operator`,
`host_stopping`, or `restart`.

**The whole domain:**

- `totals`: requests, `heat_us`, fuel, bytes in and out, the status mix, the client classes,
  and latency;
- `per_minute`: the series, its peak, when the peak was, and the mean;
- `clients`: distinct (and whether exact), and the busiest minute as p50, p99, and max;
- `concurrent`: the peak, the per-client peak, and `exact_up_to`;
- `top_clients`.

**`endpoints`,** ranked by heat. The hottest 100 carry every number in § 3.3 and a `suggest`.
The rest carry their endpoint, API, requests, and heat, requests, and bytes shares.

**`ranks`:** `by_heat`, `by_requests`, and `by_bytes`, the top 20 of each with their share.

**The rest:**

- `tracked`: endpoints, the cap, `other_requests`, candidates, `candidates_dropped`,
  `promoted`, and `detailed`;
- `memory_bytes`;
- `notes`: what heat is, what a client is, how exact each number is, and how to use the
  suggestions.

**Small.** A report is at most 256 KiB (`kReportMaxBytes`). Past that, the series go first,
then the detail of the cooler endpoints (100, then 50, 20, 0). The day-long test's report was
202 KiB with everything in.

### 4.2 Suggestions

Each detailed endpoint's `suggest` is either `{control_set, reasons}` or `{none: why}`.

**`control_set`** holds ready-to-send `control_set` arguments in 047's vocabulary:

```json
{"domain": "www.example.com", "api": "box:shop", "match": "POST /cart/{id}",
 "rate": {"per-minute": 24, "burst": 12, "by": "client"},
 "concurrent": {"max": 6, "per-client": 2},
 "body-max-bytes": 6144, "timeout-ms": 1000,
 "mode": "observe", "why": "heat study 3: observe first, then enforce"}
```

**`reasons`** gives each number with its inputs, like "per-minute 24 = max(10, 2 x 12, the p99
of each client's busiest minute over 40 clients); burst is half that".

The formulas:

| property | value | when |
| --- | --- | --- |
| `rate` by client | `per-minute` = max(10, 2 × the p99 of each client's busiest minute); `burst` = ceil(per-minute / 2) | by default |
| `rate` by all | `per-minute` = max(10, 2 × the endpoint's busiest minute, every client together); `burst` the same | only when the endpoint's whole rate is the risk: it holds 25% or more of the domain's heat, over 20 or more clients, and no client has 10% of its requests. A per-client rate wouldn't protect it then |
| `concurrent` | `max` = max(2, 2 × the peak in flight); `per-client` = max(1, 2 × one client's peak) | always |
| `body-max-bytes` | max(1024, 2 × the largest body seen, rounded up to a KiB) | when a request had a body |
| `timeout-ms` | max(1000, 2 × the slowest answer, rounded up to 100 ms) | box routes only |
| `mode` | `"observe"` | always |
| `closed` | never suggested | a person decides to close an endpoint |

**No suggestion** (`none`) when:

- the endpoint had fewer than 20 requests ("too few to suggest from; study longer, or at a
  busier time");
- it is a grouped row (`(not found)`, `(refused)`, `(preflight)`, `(rpc)`, or `other`);
- its API is `host`.

**Always observe.** Every suggestion comes in `mode: "observe"`. The operator sends it, reads
`control_report` while it observes, and enforces once it would have refused only what it
should. The study never sets a control.

**Departure: `by: user`.** It is never suggested. A study keys clients by address and keeps no
user ids (§ 7), so it has no per-user minutes to base a number on.

### 4.3 Open with 047

047 is being written in parallel; these must agree when the two merge:

- **An MCP tool's `match`.** The study writes `"match": "<tool name>"` with `"api": "mcp"`.
  If 047 names a tool another way (such as `"tool"`), the suggestion follows it.
- **`control_set`'s argument names.** The study writes `domain`, `api`, `match`, the
  properties, `mode`, and `why`. If 047's tool takes another shape, `suggest_controls` changes
  in one place.

## 5. While it runs, and when it ends

**While it runs:**

- `heat_study_get` builds the report from memory, with `state: running` and `remaining_ms`.
- The timer thread's one-second tick ends a study whose time is up. A request that finishes
  at or after `ends_ms` isn't counted.
- The tick writes each running study's report to its file once a minute, and promotes
  endpoints (§ 3.7).

**It ends** in one of three ways:

- **Time up:** `state: done`, `ended_by: time`, `ended_ms` = `ends_ms`.
- **`heat_study_stop`:** `state: stopped`, `ended_by: operator`, `stopped_by`. What was gathered
  is kept. A second stop answers that the study already ended.
- **The host stopping** (`Host::stop`, after every request in flight has finished):
  `state: stopped`, `ended_by: host_stopping`.

**A crash or a kill.** The file is written at the start, then once a minute, so after a crash
or a kill the file holds the last minute's save with `state: running`. The next start finds it,
marks it `state: interrupted`, `ended_by: restart`, and `ended_ms` = its last save, and says so
in the startup notes. A study doesn't resume after a restart; start another. New ids carry on
past the highest id in the directory.

## 6. Storage and limits

Each study is one file, `storage/operations/studies/<id>.json`, beside the panel's other files
in `operations/`. It is the report as JSON.

**Kept** 30 days after the study ends. The hourly housekeeping deletes older ones.

**The budget** is `limits.studies-bytes`, 64 MiB (floor 1 MiB). Past it, the oldest finished
report goes first, at the hourly housekeeping and whenever a study ends. A running study's file
counts toward the budget but is never deleted. A study is derived and expiring, so rule 1 of 045
applies: dropped oldest first, never refused.

**Reported** in the `limits` check of `/goober/ready` and `host_health` as `studies`.

045's table gains the row:

| what | where | kept | byte budget | over budget | built |
| --- | --- | --- | --- | --- | --- |
| heat study reports | `operations/studies/` | 30 days after the study ends | `studies-bytes`, 64 MiB; each report at most 256 KiB | the oldest finished report goes | yes |

**Backups.** The nightly holds `storage/operations/studies` with the rest of storage. Reports
are small, and a restore keeps them.

## 7. Nothing private

A report names no address and no user id:

- **A client is a keyed hash.** The host's log key (`address_hash_for_logs`, 032 § 1) is applied
  to the rate limiter's client key (`rate_key`: the address, or an IPv6 /64). For an IPv4
  client it is the same hash as the audit log's `client_h`, so the log dive finds that client's
  lines without the report holding the address.
- **`top_clients` lists hashes and counts only.**
- **No paths that carry capabilities** (§ 3.2).
- **No user ids.** The access line's `user_id` is never read, and the report never carries one.
- **The operator who started the study is named** (`by`, `stopped_by`). Operators are who
  acted (032 § 4).

The host test `RequestsAreKeyedByEndpointAndGetSuggestions` checks that a report holds neither
the test client's address nor `user_id`.

## 8. The panel: Studies (`#/studies`)

Look-only, from `heat_study_list` and `heat_study_get`. A focused operator sees only their
tenants' studies (the scope's filter and refusal, § 2).

- **The list:** each study with its domain, state (a running one with the time left), start,
  minutes, requests, hottest endpoint and its share, who started it, and why. A row opens it.
- **One study:**
  - **The header:** why, who, and when; for a running study, the time left and "numbers so
    far". It refreshes every 15 seconds while visible.
  - **Totals:** requests, heat, bytes, the busiest minute, clients (≈ when estimated), the
    most at once, and p99 latency.
  - **Requests per minute:** a chart.
  - **Each client's busiest minute:** p50, p99, max, and the most one client had at once, with
    the busiest clients by keyed hash and class.
  - **Where the heat is:** bars for the top 20 endpoints, by heat (CPU share), requests, or
    bytes, colored hot to cold, and a note of what went to `other`.
  - **Endpoints:** a table of every detailed endpoint: requests, heat share, p99, peak per
    minute, clients, client p99 per minute, the most at once, bytes out, 4xx, 5xx, 429, and the
    share of bots.
  - **Suggested controls:** each endpoint's `control_set` arguments as JSON, and the reason for
    each number. The panel sends nothing: "send it, read control_report while it observes, and
    enforce once it holds."

The bars are SVG with widths as attributes, so the panel's content security policy (no inline
styles) holds.

## 9. How to use it

The same recipe is in HUMAN.md and the box guide:

1. **Start a study for an hour at a busy time:**

   ```
   heat_study_start {domain: "www.example.com", minutes: 60, why: "Monday's peak"}
   ```

2. **Read it:** the panel's **Studies** view, or `heat_study_get {id}`. Look at what holds the
   heat, which endpoints one client drives hard (a high client p99 per minute), and what a bot
   is behind.
3. **Send a suggestion as it is:** `control_set` with the `control_set` arguments. They are in
   observe mode.
4. **Check `control_report`:** what the control would have refused, and whom.
5. **Enforce:** the same `control_set` with `mode: "enforce"`, once it would have refused only
   what it should.

## 11. Decisions for the human

1. **Concurrency from finished requests (§ 3.5).** It is exact up to 64 in flight per endpoint
   and 512 per domain, with one hook. The alternative is a second hook at the request's start,
   counting in flight, with the endpoint known only at the finish. Recommended: keep this one.
2. **The `host` API (§ 3.2).** `/goober/*` paths and preflights are shown, but get no suggestion,
   because 047's APIs are `box:<name>`, `content`, `mcp`, and `identity`. Should 047 gain
   `host`, or should these paths stay uncontrollable by operators? Recommended: stay as is; the
   global rate limiter covers them.
3. **Top clients by hash (§ 7).** The report lists the ten busiest clients' keyed hashes, so an
   operator can find their lines in the log dive. A hash is stable for the host's log key, so a
   client can be followed across studies. Recommended: keep them, as the audit log does.
4. **Reports in backups (§ 6).** They are small and kept 30 days; leaving them in the nightly
   costs little. Recommended: keep them in.
