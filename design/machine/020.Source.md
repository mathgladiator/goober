# Source Projects over MCP

> Status: machine-authored and **not ratified**. Recorded on 2026-10-27. It builds
> `design/human/521.Source.md` (drafted by Claude at the human's request, for the human to own):
> the `source` package (the store and diffs), and the host's `builder.cpp` and
> `source_tools.cpp`.

## 1. The loop

An agent with an operator token (Grok, Claude) works like this:

1. `source_create {project, template}` creates a project. The template is `empty`, `rust-box`,
   `wat-box`, or `site` (with `tenant`).
2. `source_checkout {project}` returns every file at the head, text inline up to `max_bytes`
   (default 200,000), with each file's SHA-256, and the revision.
3. `source_commit {project, base_rev, message, changes}` makes a new revision. Each change is
   `{path, text}`, `{path, base64}`, or `{path, delete: true}`.
4. `source_build {project, rev?}` builds, or `source_deploy {project, rev?}` builds and deploys.
   Each answers within 25 s, finished or with a `job` to follow with `source_job`.
5. `source_log`, `source_diff {from, to?, paths?}`, and `source_revert {rev}` read and undo.

A person does the same from a terminal: `goober.py source new|pull|push|build|deploy|list`.
A pulled directory remembers its project and revision in `.goober-source.json`. `push` sends
only what differs from that revision, by hash.

## 2. Storage

Everything lives in `storage/source/source.db`, so the S3 increments carry it like any other
database (019).

| table | holds |
| --- | --- |
| `projects` | name, description, head, when, and the deployed revision |
| `revisions` | each revision's message, author (the operator: `config` or `token:NAME`), and time |
| `trees` | every revision's whole file list: path, SHA-256, size |
| `changes` | the paths each revision wrote or deleted |
| `blobs` | file contents by SHA-256, stored once |

**Limits.** 4 MiB a file, 10,000 files, 256 MiB a project, and 500 changes a commit. Project
names are `[a-z][a-z0-9_-]*`. Paths are relative and safe: no `.` or `..`, NUL, backslash, or
line breaks, and a file can't sit where a directory is.

## 3. Concurrency

A commit names its base. When others committed since, the commit lands on top if none of the
paths changed in `(base, head]` are among its paths, and the result says `rebased`. If they
overlap, the commit is refused: `{committed: false, conflicts: [...]}`, with an error telling
the agent to read those files again and commit on top of the head. Nothing is ever merged
inside a file.

## 4. What a project builds

`goober.project.json` at the root says what a project builds:

```json
{ "boxes": ["."], "schemas": ["leads1.schema.json"], "sites": [{ "dir": "site", "tenant": "playground" }] }
```

**A box directory** has `manifest.json`, its types document if the manifest names one, and one
of these:

- `box.wasm`, used as is;
- `box.wat`, which the host compiles at upload;
- `Cargo.toml`, built with `cargo build --release --target wasm32-unknown-unknown --offline`.

**A Rust build runs in a bubblewrap sandbox** (`source.sandbox: "bwrap"`, the default):

| what | how |
| --- | --- |
| Network | None (`--unshare-all`). |
| Environment | Cleared. `HOME=/work`. |
| Readable | `/usr` and its links read-only. From `/etc`, only `alternatives` and `ld.so.*`, so no password files or the host's secrets. The toolchain (cargo's directory and `RUSTUP_HOME`) read-only. The vendored crates at `/vendor`. |
| Writable | Only the revision's files at `/work`, and the project's target cache at `/target` (`storage/source/cache/PROJECT/`). |
| Bounded | `source.build-timeout-ms` (default 300 s), in its own process group, killed whole. |

**Crates** come only from the host's vendored set: `source.vendor`, made by `tools/vendor.sh`
(serde and serde_json by default). That set is the whole of what a box may depend on.

`source.sandbox: "none"` builds without bubblewrap. It is only for a machine you trust.
Without bwrap installed, a sandboxed build refuses and says how to fix it.

**Sites** are every file under their directory, written as the tenant's content.

## 5. Deploy

A deploy runs in this order, and stops at the first failure with the reason in the log:

1. schemas, through `schema_put`'s path: the same content is a no-op;
2. boxes, through `version_upload`'s path, each a new active version, with every upload
   check;
3. site files, through `content_put`'s path.

Then the project's `deployed_rev` is set. Jobs run one at a time on their own thread. The newest
100 are kept in memory and listed by `source_job`.

## 6. On a server

`just deploy you@server --with-rust` (`tools/deploy.sh ... --with-rust`):

1. vendors the crates here;
2. installs bubblewrap and rustup (for the goober user, with the wasm32 target) on the
   server;
3. unpacks the vendored crates to `/srv/goober/vendor`;
4. sets `source.vendor` and `source.cargo` in `host.json`.

Without `--with-rust`, projects of WAT, prebuilt WASM, and sites still build and deploy.

## 7. Tests

**`source/test`:**

- commits, checkouts, log, delete, and no-op commits;
- the rebase and the refusal of overlapping commits;
- revert, with binary files;
- path rules and limits;
- diffs, checked against `diff -u`, including new, deleted, no-newline, and too-large files;
- diffs between revisions.

**`host/test/source_tools_test.cpp`**, through the operator MCP on a running host:

- a WAT box created, checked out, deployed, and serving;
- changed, committed, and redeployed;
- a stale commit refused with its conflict;
- diff, log (with the operator as author), and revert;
- a site deployed as content;
- build and deploy failures that say why;
- a Rust box built with cargo in the sandbox and serving, and a compiler error returned in
  the log;
- the sandbox shows no `/etc/passwd` and no home directories, `HOME=/work`, and a read-only
  `/usr`.
