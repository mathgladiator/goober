# Source Projects over MCP

> Status: machine-authored and **not ratified**. Recorded on 2026-10-27. It builds
> `design/human/521.Source.md` (drafted by Claude at the human's request, for the human to own):
> the `source` package (the store and diffs), and the host's `builder.cpp` and
> `source_tools.cpp`.

## 1. The loop

An agent with an operator token (Grok, Claude) works like this:

1. `source_create {project, template}` creates a project. The template is `empty`, `rust-box`,
   `wat-box`, or `site` (with `tenant`).
2. `source_checkout {project}` returns every file at the head, text inline up to `max_bytes`
   (default 200,000), with each file's SHA-256, and the revision.
3. `source_commit {project, base_rev, message, changes}` makes a new revision. Each change is
   `{path, text}`, `{path, base64}`, or `{path, delete: true}`.
4. `source_build {project, rev?}` builds, or `source_deploy {project, rev?}` builds and deploys.
   Each answers within 25 s, finished or with a `job` to follow with `source_job`.
5. `source_log`, `source_diff {from, to?, paths?}`, and `source_revert {rev}` read and undo.
6. `source_tree {project, rev?}` lists a revision's files without their contents, with its
   message and changed paths; `source_box_history {box}` says which deploys made a box's
   versions (§ 9).

A person does the same from a terminal: `goober.py source new|pull|push|build|deploy|list`.
A pulled directory remembers its project and revision in `.goober-source.json`. `push` sends
only what differs from that revision, by hash.

## 2. Storage

Everything lives in `storage/source/source.db`, so the S3 increments carry it like any other
database (019).

| table | holds |
| --- | --- |
| `projects` | name, description, head, when, and the deployed revision |
| `revisions` | each revision's message, author (the operator: `config` or `token:NAME`), and time |
| `trees` | every revision's whole file list: path, SHA-256, size |
| `changes` | the paths each revision wrote or deleted |
| `blobs` | file contents by SHA-256, stored once |
| `jobs` | every finished build and deploy, with its log and result (§ 9) |
| `deploys`, `deploy_boxes` | every deploy that put something live: revision, job, who, when, and each box version it uploaded (§ 9) |
| `mirrored` | which patches and snapshots are in the backup bucket (§ 10) |

**Limits.** 4 MiB a file, 10,000 files, 256 MiB a project, and 500 changes a commit. Project
names are `[a-z][a-z0-9_-]*`. Paths are relative and safe: no `.` or `..`, NUL, backslash, or
line breaks, and a file can't sit where a directory is.

## 3. Concurrency

A commit names its base. When others committed since, the commit lands on top if none of the
paths changed in `(base, head]` are among its paths, and the result says `rebased`. If they
overlap, the commit is refused: `{committed: false, conflicts: [...]}`, with an error telling
the agent to read those files again and commit on top of the head. Nothing is ever merged
inside a file.

## 4. What a project builds

`goober.project.json` at the root says what a project builds:

```json
{ "boxes": ["."], "schemas": ["leads1.schema.json"], "sites": [{ "dir": "site", "tenant": "playground" }] }
```

**A box directory** has `manifest.json`, its types document if the manifest names one, and one
of these:

- `box.wasm`, used as is;
- `box.wat`, which the host compiles at upload;
- `Cargo.toml`, built with `cargo build --release --target wasm32-unknown-unknown --offline`.

**A Rust build runs in a bubblewrap sandbox** (`source.sandbox: "bwrap"`, the default):

| what | how |
| --- | --- |
| Network | None (`--unshare-all`). |
| Environment | Cleared. `HOME=/work`. |
| Readable | `/usr` and its links read-only. From `/etc`, only `alternatives` and `ld.so.*`, so no password files or the host's secrets. The toolchain (cargo's directory and `RUSTUP_HOME`) read-only. The vendored crates at `/vendor`. |
| Writable | Only the revision's files at `/work`, and the project's target cache at `/target` (`storage/source/cache/PROJECT/`). |
| Bounded | `source.build-timeout-ms` (default 300 s), in its own process group, killed whole. |

**Crates** come only from the host's vendored set: `source.vendor`, made by `tools/vendor.sh`
(serde and serde_json by default). That set is the whole of what a box may depend on.

`source.sandbox: "none"` builds without bubblewrap. It is only for a machine you trust.
Without bwrap installed, a sandboxed build refuses and says how to fix it.

**Sites** are every file under their directory, written as the tenant's content.

## 5. Deploy

First, everything is checked and nothing is stored: each schema (it parses, and its name is
new or holds the same content), then each box exactly as an upload would check it (manifest,
types, data against the active schemas plus the project's new ones, the module, and conflicts
with the active boxes). One failure stops the deploy with every reason in the log, and nothing
is stored: a schema name stays free for the fixed revision. A build runs the same checks, so a
green build deploys. *Until 2026-10-28 schemas were stored before the boxes were checked, so a
box's typo left its schema stored for good.*

Then it stores, in this order, and stops at the first failure with the reason in the log:

1. schemas, through `schema_put`'s path: the same content is a no-op;
2. boxes, through `version_upload`'s path, each a new active version, with every upload
   check;
3. site files, through `content_put`'s path.

Then the project's `deployed_rev` is set. Jobs run one at a time on their own thread. Queued
and running jobs live in memory; each finished one is kept (§ 9).

## 6. On a server

Every `just deploy` (`tools/deploy.sh`), first install or upgrade:

1. installs bubblewrap and a C toolchain (`build-essential`: crates' build scripts and proc
   macros, like serde's derive, link for the server itself), and rustup for the host's user if
   it isn't there, with the wasm32 target (made sure of on every deploy; the toolchain's version
   moves only with `rustup update`);
2. vendors the crates on the server, as the host's user, then copies them into a root-owned
   `/srv/$user/vendor` the builds read but can't change (a failed vendoring keeps the last set);
3. sets `source.vendor` and `source.cargo` in `host.json`;
4. checks it all with `goober-host toolchain`: the rust-box template plus a `#[derive]`, built
   through `build_project`, as the host's user, offline, in the sandbox. Deploy ends with a
   check of everything (the services, the toolchain, mail) and fails if any check does.

`--without-rust` skips it; projects of WAT, prebuilt WASM, and sites still build and deploy.
*Until 2026-10-28 this took `--with-rust` and vendored on the deploying machine.*

## 9. Jobs and deploys, kept

Added 2026-10-30, at the human's request: the panel should understand source management and
show build logs, and a box's history should be understandable from its source.

- **Jobs.** Every build and deploy is written to `jobs` the moment it finishes, before it shows
  as done: kind, revision, state, who, when it was queued, started, and finished, the whole log,
  and its result. Numbers go on from the newest kept job, so a number is never reused after a
  restart. `source_job {job}` reads a running job from memory and a finished one from the
  store; `source_job {project?, limit?}` lists the running ones, then the kept ones, newest
  first, without logs.
- **Deploys.** A deploy that put boxes live is written to `deploys` with each box version it
  uploaded (`deploy_boxes`). A deploy that failed after some boxes went up is kept too, with
  those boxes: they are live, and they came from that revision.
- **Box history.** `source_box_history {box}` lists the deploys that uploaded the box, newest
  first: project, revision, its message, who deployed it, when, the job, and the version.
  `version_list` names each version's `source` (project, revision, job) when a deploy made it.
  A version uploaded with `version_upload` has none.
- **Scope (030).** `source_tree` follows the project's rule, like `source_log`;
  `source_box_history` follows the box's, like `version_list`.

## 10. The mirror in the backup bucket

The human chose, on 2026-10-30: sealed like every other backup object, and both patches and
snapshots.

| object | what |
| --- | --- |
| `source/PROJECT/patches/000042.patch.sealed` | revision 42 as `git format-patch` writes it |
| `source/PROJECT/snapshots/000042.tar.gz.sealed` | every file of revision 42, which was deployed, with `.goober-deploy.json` |

Both are under the bucket's `prefix`, sealed with the backup key (019 § 3), the object's name
bound into the seal.

**A patch** is one mail message, as `git format-patch` makes it:

- `From`: the author, quoted, with an address made from it (`token-grok@goober.invalid`), since
  an operator name like `token:grok` is no address. `Date` is the revision's time, and
  `Subject` is `[PATCH]` and the message's first line. The rest of the message is the body,
  then `Goober-Project:` and `Goober-Revision:` lines.
- A body line that a reader would take for the patch (`---`, `diff -`, `Index: `, `From `) is
  indented by one space.
- Each changed file has a `diff --git` header, `new file mode 100644` or
  `deleted file mode 100644`, and an `index` line with git's blob ids (SHA-1 of
  `blob SIZE\0` and the bytes). Text is a unified diff with 3 lines of context. A file that
  isn't text is a `GIT binary patch`: a `literal` of the new bytes and one of the old, each a
  zlib stream of stored (uncompressed) deflate blocks with its Adler-32, in git's base85 lines.
  So no compression library is needed, and every byte comes through.
- The first revision is a patch from nothing.

`git am` of a project's patches in order gives a repository whose every commit holds exactly
that revision's files, with its author, time, and message. A test replays a history with
binary files, a path with a space, a non-ASCII path, an empty file, deletions, and a revert.

**A snapshot** is a `tar.gz` of a deployed revision's files, plus `.goober-deploy.json`: the
project, revision, message, author, and time, and each deploy of that revision with its job,
who, when, box versions, state, and whole build log. It is written once a deploy's job is
kept. A file named `.goober-deploy.json` in the project itself is replaced by it in the
snapshot.

**The stream.** The backup thread (019 § 4) asks the source store what isn't in the bucket yet,
patches first, oldest first, at most 25 a tick. Each is written, sealed, put, then marked in
`mirrored`. A failure waits 10 s, doubling to an hour, and is the backup's `last_error`.
`backup_run {what: "source"}` runs it now. `backup_status` shows `source`: when it last ran,
what's pending, and when it retries. `source_list` shows each project's `mirror`: patches
through which revision, snapshots, and pending. Rotation never touches `source/`: the history
is kept for good, like the source store itself. A sandbox never mirrors.

Since `source.db` is in every nightly and increment, a restore brings `mirrored` back with it,
so the mirror goes on where the restored store says it was.

## 11. Reading the mirror back

```
goober-host source-mirror DIR [--project P] [--from host.json | --bucket B [--region R]
                              [--endpoint URL] [--prefix P]] [--key-file F]
```

It takes the bucket, the AWS keys, and the backup key exactly as `rehydrate` does (019 § 5);
`just source-mirror DEST [PROJECT]` (`tools/source-mirror.sh`) reads them from
`~/.config/goober/backup.env`.
It writes `DIR/PROJECT/patches/000042.patch` and `DIR/PROJECT/snapshots/000042.tar.gz`,
unsealed, and skips files already there, so a second run fetches only what's new. It ends by
printing how to replay the patches into git (`git init`, then `git am .../patches/*.patch`)
and unpack a snapshot.

## 12. In the panel

The panel's Source view (028 § 3) shows the projects with their head, deployed revision, and
mirror; a project's revisions with the deployed one marked and each revision's builds; a
revision's message, colored diff, and files; any file with line numbers; and a job's whole
build log. A box's page lists **From source**: the deploys behind its versions, each linking
to its revision and its log. It is look-only: building, deploying, and reverting stay with
the MCP tools.

## 13. Staged commits

Added 2026-10-30. A site's engineers work through a client that attaches only a few files per
tool call, so a six-file change became two commits, and the first was a revision that didn't
build. `source_stage {project, base_rev, changes}` adds changes to a **draft**, one per project
and operator (the operator the host checked, so agents signed in as one person share it):

- A later change to a path replaces an earlier one; `{path, delete: true}` stages a deletion.
- The draft is made from `base_rev`, and staging on another base is refused until the draft is
  committed or dropped (`source_stage {project, discard: true}`).
- It holds at most 500 changes and the project's byte limit; paths and sizes are checked as
  staged, and a refused call stages nothing.
- The answer names the draft's `stage` id, its files, and when it expires: an hour after its
  last change.
- Drafts live in `source.db` (`drafts`, `draft_files`), so a restart keeps them.

`source_commit {project, base_rev, message, stage, changes?}` commits the draft whole, with any
changes given there on top, under the usual rebase and conflict rules (§ 3). A commit drops
the draft; a conflict keeps it and answers its id, so nothing staged is lost while the agent
reads the conflicting files; it then discards the draft and stages again on the new head. No
revision ever holds half a change.
