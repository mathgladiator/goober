# 053. A beta site on the production host

Status: decided by the human on 2026-11-04 (§ 9); being built in steps (§ 10).

The human (2026-11-04): "I'm also think about having a beta version of a site. So,
beta.example.com uses the production goober instance for testing, and I want deployment to ask
if it should setup a beta. A key thing about making beta work, is that it allows staging
deployments, so I will also need a beta-ops subdomain as well which is also asked at startup.
Beta will not implement email, and instead it will have a dumb email viewer and client within
the beta-ops. This allows the beta operator to inject emails, see responses, and test
everything in isolation."

## 1. The conflict with 310

`design/human/310.Deployments.md` § Staging says: "A staging environment is just another goober
host, configured with its own domains and its own data." The human now asks for beta on the
**production** host. This proposal follows the new ask; 310's sentence should change with the
human's own edit, or say that staging may be a beta on the same host. Until then the human doc
wins, so this waits for the human (§ 9, decision 1).

310's reasons for staging still hold, and the proposal keeps them: its own data (synthetic,
never a copy with personal data), agents with free rein there, and a batch the human promotes.

## 2. The shape

For a site `example.com` (tenant `acme`), setting up beta adds:

- **`beta.example.com`**: a domain of its own **beta tenant**, `acme_beta`, marked in host.json
  as the beta of `acme`:

  ```json
  "domains": {
    "example.com": {"tenant": "acme"},
    "beta.example.com": {"tenant": "acme_beta", "beta-of": "example.com"}
  }
  ```

  (`beta-of` names the production domain; tenant names are `[a-z][a-z0-9_]*`, so `acme_beta`.)
  A tenant brings its own databases, identity realm (its own accounts and sessions), content,
  attachments, keys, flags, and controls, so beta shares no data with production. Every box that
  serves `example.com` serves `beta.example.com` too (a manifest's domains match its beta's).
- **`beta-ops.example.com`**: the panel and the operator MCP for beta tenants only, the way
  `operations.domain` serves the panel today (028 § 1):

  ```json
  "operations": {"domain": "ops.example.com", "beta-domain": "beta-ops.example.com"}
  ```

## 3. Staging deployments

A box gets a second slot beside its live version: its **beta version**, which answers on beta
domains only. Production keeps its live version.

- `version_upload {..., channel: "beta"}` stores a version and makes it the box's beta version;
  `version_promote {box, version, channel: "beta"}` moves the beta slot to a stored version. With
  no beta version, beta domains get the live one.
- **Shipping:** `beta_ship {box}` promotes the beta version to live, or starts a 052 split from
  it (`beta_ship {box, split: {ladder}}`). In production's approval queue it shows what changed
  from the live version and how long it ran in beta.
- The route tables for beta domains are built from the beta versions, so a beta version may add
  routes, tables, and schema versions: it runs against beta's own databases. Shipping it runs the
  same checks as any promote, and schemas apply to production's databases then.
- Content, partials, templates, and pages are per tenant already, so beta's are beta's own.
  `beta_copy_content {tenant}` copies production's pages to beta to start (never data).

## 4. Mail in beta

Nothing leaves the machine from a beta tenant's mail. Every message a beta tenant would send
(sign-in codes, invites, a box's `mail` service, list mail) is **captured** instead, in
`mail/beta/<tenant>/`, and counted like sent mail. Inbound mail to beta domains isn't accepted on
port 25.

beta-ops has a **Mail** view, a small mail client:

- **Inbox of what was sent:** every captured message, newest first: from, to, subject, when, which
  box or host feature sent it, and the text and HTML (the HTML drawn as text, as the panel draws
  everything, or in a sandboxed frame; § 9, decision 6). A sign-in code shows there, so the beta
  operator can sign in as any test person.
- **Compose:** write a message as any sender to any beta address (from, to, subject, text,
  attachments, and optionally `in-reply-to` one of the captured messages), and inject it. The host
  hands it to the same path as Stalwart's hook (024): the box's `routes.mail` answer, reply
  tokens, verified-sender rules (beta trusts the From it's given; it says so), and the box's
  replies land back in the inbox.
- Tools for agents: `beta_mail_list`, `beta_mail_get`, `beta_mail_send` (inject), so an agent can
  test a mail flow end to end.

## 5. Other effects in beta

Mail is one effect. A beta box's `external` calls, push, phone, and the robot can also reach the
world. Proposed, as 310 does for shadows: a beta tenant's outbox elements and service calls
**fail** unless the service says `"beta": "allow"` in the manifest, which is only allowed for
methods whose effect is `none` (reads, like a weather lookup). Push and phone are captured like
mail.

## 6. Who operates beta

- **beta-ops sign-in:** host operators, as on the panel. A beta operator is an operator focused on
  the beta tenants (030), or a new role `host:beta` that grants every beta tenant and nothing else.
- **Agents:** a token or OAuth grant from beta-ops is focused on beta tenants. As 310 wants, beta
  agents get free rein there: no approvals for beta-channel uploads and promotes, content, data,
  and drops on beta tenants (with no users, nothing to protect). Shipping to production
  (`beta_ship`) is a production call and waits for the owner's approval.
- A beta-focused operator can upload a version of a box that serves production only into its
  beta slot (scope rule `kManifest` learns channels).

## 7. Deployment asks

`goober-host audit` (every deploy, 028) asks, for each site without one:

1. "Set up a beta for example.com at beta.example.com? (yes / not now / never)"
2. With yes: "Serve beta's operations at beta-ops.example.com? (yes / not now / never)"

Yes writes the domains, the beta tenant, and `operations.beta-domain` into host.json, adds both
names to Caddy (on-demand TLS already covers them once DNS points there), and says which DNS
records to add. "never" is kept in `audit.quiet` as the other offers are.

## 8. What it costs

- The registry gains a beta slot per box and builds tables for beta domains: the largest change
  (boxes package).
- The mailer gains a capture mode per tenant; the mail hook gains an inject path.
- A second panel origin, filtered to beta tenants, with a Mail view.
- Config: `beta-of`, `operations.beta-domain`; the audit's two offers.
- Tests for each, and a `just beta-e2e` that signs in on beta through the captured code, deploys a
  beta version, injects a mail, reads the reply, and ships.

## 9. Decisions (the human, 2026-11-04)

1. **Staging on the production host, linked to production.** "Ultimately, I want staging to be
   about the product, so it can run on the same host and I want it explicitly linked to
   production such that box promotions can happen. The promotion should be designed such that it
   can happen within the same host or against another remote host. For now, we start with
   in-host promotion so content and boxes can be staged for review. Eventually, I'll have grok
   engineering work only on beta and then I'll take control of promotion and migration."
   So: beta is linked to its production site by `beta-of`; a promotion is one reviewable bundle
   (§ 11) applied in-host now, and the same bundle can later be sent to another host. 310's
   "a staging environment is just another goober host" now reads as one of two ways; the human
   edits 310 when they choose.
2. **Beta's data:** its own tenant, sharing nothing with production.
3. **Staging deployments:** a beta slot per box (§ 3).
4. **Effects in beta:** service calls and the outbox fail unless a service allows them for reads;
   push and phone are captured like mail (§ 5).
5. **Who runs beta:** a `host:beta` role; beta agents have free rein on beta tenants (§ 6).
   Promotion to production is the owner's.
6. **Captured HTML mail:** shown as text and as its source (recommended; not asked).
7. **One beta per site** (recommended; not asked).

## 10. Build steps

1. Config: `beta-of` on a domain, `operations.beta-domain`; a beta domain matches every
   manifest its production domain matches.
2. The registry's beta slot, beta route tables, `version_upload {channel: "beta"}`,
   `beta_version`, and requests on beta domains answered by beta versions.
3. Mail captured for beta tenants; the injector; `beta_mail_*` tools.
4. Effects that fail in beta unless allowed.
5. beta-ops: the panel and operator MCP on `operations.beta-domain`, `host:beta`, scope.
6. Promotion (§ 11).
7. The deploy audit's two offers.

## 11. Promotion

A promotion carries what beta changed to production as one **change set** (042), so it is
previewed together, applied in order, and rolled back by one call:

- **Boxes:** each box whose beta version differs from its live version becomes a `version` member
  (`{box, version}`: the beta version, stored already). A box new in beta (no live version) is a
  member too.
- **Content:** each page, template, partial, or file that differs between the beta tenant and the
  production tenant becomes part of a `content` member for the production tenant. A file beta
  deleted is listed, not deleted (production keeps it until a person removes it).
- **Not carried:** data (databases stay each tenant's own: no rows go from beta to production),
  accounts, keys, flags (listed, for a person to set), and attachments (a page that links a beta
  attachment is flagged in the preview).

`promotion_preview {tenant}` (a read tool) builds the bundle from the beta tenant of `tenant` and
answers the change set's preview: every member, each box's review against its live version and
what widens, each page's diff, and what isn't carried. `promotion_start {tenant, include?}` makes
the draft change set; applying it is `changeset_apply`, which is the owner's: from an agent it
always waits for the owner's approval, and the panel's Promote view applies it for an owner.
After it applies, the beta slots of the promoted boxes are cleared (beta follows live again).

**To another host, later.** The bundle is self-contained: each version's manifest, module, and
types, and each content file's text, with the source host and tenant. Sent to another host's
operator MCP (`changeset_import`), it becomes a draft change set there, previewed and applied by
that host's owner. Nothing in the in-host path assumes the target is the same host except where
the versions are already stored.
