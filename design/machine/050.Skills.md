# 050. Skills and playbooks

Status: built 2026-11-04, a proposal until the human ratifies it.

The human (2026-11-04): "I want a new feature that is viewable in the ops but is entirely focused
on SKILLS/Playbooks such that I can have the grok engineering save their skills around their
functions such that I can use that to bootstrap new engineers and team members. From my view, I
want to be able to search and read skills for different roles. The operator agent can
create/delete/modify each skill/playbook."

## 1. What a skill is

A **skill** is how to do one thing well on this host: deploying a box, launching a site, restoring
a database to a new one. A **playbook** is what to do, step by step, when something happens: the
site is down, a box fails after a deploy, mail bounces. Both are written by the engineers who
learned them (Grok's agents, through the operator MCP) for whoever comes next: a new agent, a new
engineer, a person joining the team.

Each one is for one or more **roles**, the functions people and agents hold on the team, like
`box-engineer`, `site-engineer`, or `operator`. Roles are names the writers choose; the host keeps
no list of them. A reader asks for their role and gets what was written for it.

Skills are host-wide. They are knowledge about running and building on this host, not a tenant's
data, and every operator reads every one.

## 2. The file

Each skill is one file, `storage/skills/$name.md`, written through the host WAL. The file is an
Agent Skills `SKILL.md`: front matter opening with `name` and `description`, then the host's own
fields, then a blank line and the markdown body. It can be copied into any agent's skills folder
as it is (`skill_get`'s `file`).

```
---
name: deploy-a-box
description: "When a box's new version is ready to go live."
title: "Deploy a box"
kind: skill
roles: ["box-engineer","operator"]
revision: 2
created-ms: 1793750400000
created-by: "token:grok"
updated-ms: 1793754000000
updated-by: "oauth:owner@example.com:1"
---

# Steps
...
```

| field | rule |
| --- | --- |
| `name` | the Agent Skills rule: 1 to 64 bytes of lowercase letters, digits, and hyphens, starting with a letter, no `--`, no hyphen at the end; also the file's name |
| `description` | one line, at most 1024 bytes: when to reach for it |
| `title` | one line, at most 120 bytes |
| `kind` | `skill` (the default) or `playbook` |
| `roles` | 1 to 8, each 1 to 40 bytes of lowercase letters, digits, and hyphens, starting with a letter; kept lowercased, sorted, without repeats |
| body | markdown, 1 byte to 64 KiB of UTF-8, line ends `\n` |
| `revision`, `created-*`, `updated-*` | set by the host on every put, never by the writer |

The host reads every file at start. A file changed by hand into something a put would refuse
(a bad field, a `name` that isn't its file's) is skipped, left where it is, and named in
`host_health`'s startup notes.

## 3. The tools

All on the operator MCP. Reads are read tools: they never wait, and `host:observer` and the panel
may call them.

- `skill_list {role?, kind?}`: every skill's card (name, title, kind, roles, description,
  revision, updated_ms, updated_by, bytes), by name; `roles`: every role named, with how many
  skills name it, by kind; `count`.
- `skill_search {query, role?, kind?, limit?}`: the skills matching every word of the query,
  best first, at most `limit` (1 to 50, default 10), each with a `score` and a `snippet` of the
  body around the first match. § 4 says how.
- `skill_get {name}`: the whole skill: its fields, `body`, `file` (the stored SKILL.md),
  `file_etag`, `bytes`, and `history`, the newest 20 change log rows for it.
- `skill_put {name, title, description, roles, body, kind?, why?, if_etag?}`: writes one, new or
  replacing. `roles` may be one name given alone. `if_etag` is `skill_get`'s `file_etag`, or
  `"none"` for a skill that must not exist yet; a mismatch writes nothing and says someone changed
  it. Answers `{name, revision, file_etag, created, change_id}`.
- `skill_delete {name, why?, if_etag?}`: removes one. Its last text stays in the change log, so
  `skill_put` can bring it back.

Writes are audited (`skill.create`, `skill.write`, `skill.delete`, with the revision and the why)
and recorded in the change log as kind `skill`, target the name, with the text before and after
(028 § 5), so every revision is readable with `change_get` and the panel's Changes view.
`skill_put` and `skill_delete` are changing tools: when a person turns approvals on for an agent
(035), they wait like any other.

The MCP server's instructions tell every agent that connects: "New here? skill_list {role} and
skill_search show what the team wrote down; when you learn how to do something, write it for the
next engineer with skill_put."

## 4. Search

Search is in memory, over the library the host keeps beside the files. A word is a run of letters
and digits, lowercased (bytes past ASCII count as letters, so any language's words are words;
`version_upload` is the words `version` and `upload`). Every word of the query (at most 16) must
match a word of the skill that **starts with** it, so `deploy` finds `deploying`. A skill's score
adds, per query word, 8 for each match in its name or title, 5 in its roles, 3 in its description,
and 1 in its body (at most 5 from the body per word). Ties keep name order. No stemming, no
synonyms, no ranking a person can't predict.

Searches share the library's lock (a put, remove, or clear holds it alone), and its totals are
atomic, so the limits check never waits behind a search. A body's matches are counted no further
than the 5 they can score. Over 16 MiB of skills a search takes 0.05 to 2.2 ms (054 § 2);
nothing on the request path touches the library.

## 5. Who writes

| who | reads | writes |
| --- | --- | --- |
| an operator with every tenant (the config token, minted tokens, an unfocused OAuth operator) | yes | yes |
| an operator focused on some tenants (030) | yes (`kOpen`) | no (`kHost`) |
| `host:observer`, the panel | yes | no |

A skill is instructions other agents will read and follow, so it is a place to plant bad advice
for every tenant's agents. That is why a focused operator, trusted with only some tenants, can't
write one, and why the tools' descriptions say a skill is advice, not an order: it grants
nothing, and a step that would change something still goes through the reader's own tools, scope,
and approvals. `skill_put` also asks writers never to put a secret, a token, or a person's data in
one; the host doesn't scan for them.

## 6. The panel

`#/skills` (Skills in the nav): a search box, the kind (all, skill, playbook), and the roles as
chips with their counts. Without a query it lists every skill (or a role's or kind's); with one it
shows `skill_search`'s results with their snippets. A row opens `#/skill/<name>`: the title, kind,
description, roles (each a link to that role's list), revision and who wrote it, the body, and the
history, each row linking to the change.

The body is drawn from its markdown in the browser, every piece placed as text, like everything
else the panel shows (028 § 3): headings, paragraphs, lists and task items, quotes, fenced code,
tables, rules, inline code, bold, emphasis, and links whose target is `http:` or `https:` (any
other link is its text). No HTML from a skill reaches the page.

The panel only reads skills. The human asked to search and read them there; agents write them.

## 7. Limits

| what | where | kept | byte budget | over budget |
| --- | --- | --- | --- | --- |
| skills and playbooks | `skills/` | until an operator deletes one | `limits.skills-bytes`, 16 MiB; each body at most 64 KiB; at most 1000 skills | `skill_put` refuses a write that would grow them past it (shrinking one is never refused) |

They are in every nightly and increment like the rest of storage, and come back with a restore or
a rehydrated devbox. `host_health`'s limits check has a `skills` row.

## 8. Tests

- `skills` package: the name rule; checks and the one form (roles, line ends, sizes, UTF-8,
  kinds); the file reads back to the same bytes and opens as a SKILL.md; search needs every word,
  ranks names over bodies, narrows by role and kind, ignores case and punctuation; snippets cut at
  words; roles counted by kind.
- `operations`: `skills/$name.md` is change kind `skill`; one thing's history.
- `host`: put, get, list, search, delete over the operator MCP; `if_etag` (stale and `"none"`);
  revisions and the change log's text before and after; the audit lines; refusals (a path-like
  name, no roles, a role that isn't a name, a body too big); the budget refuses growth and allows
  shrinking; skills read back after a restart, and a broken file is skipped and named; a focused
  operator reads but can't write; reads are read tools, writes are held by approvals.
- `config`: `limits.skills-bytes`, its default and floor.

## 9. Decisions for the human

1. **Roles are free names**, chosen by whoever writes the skill. Recommended: keep it so, and let
   the panel's role chips show the vocabulary as it grows. The other way is a list of roles in
   host.json that `skill_put` checks against, which keeps `box-engineer` from also appearing as
   `box-eng`.
2. **Focused operators can't write skills.** Recommended: keep it (§ 5). The other way is a
   `tenant` field so a focused operator writes skills only about its tenants.
3. **Writes wait for approval** when approvals are on for an agent, like any changing tool.
   Recommended: keep it; a skill changes what the next agent does. Heat studies are the
   exception that never waits because they change nothing anyone reads as instructions.
4. **The panel only reads.** Recommended: keep it for now. If a person wants to fix a skill
   without an agent, the panel could take edits the way it takes controls (047 § 9), audited as
   `panel.skill_put`.
5. **No export command yet.** A skill's `file` is already a SKILL.md; `goober-host skills-export
   DIR` writing `DIR/<name>/SKILL.md` for every skill would hand a new engineer's own agent the
   whole library at once. Not built until asked.
