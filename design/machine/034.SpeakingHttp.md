# Speaking HTTP: a small language for any API, sealed secrets, and connections

A design, built in stages from the same day. On 2026-10-29 the human asked that boxes be able
to talk to the world's APIs without the host owning them:
- a box as an MCP proxy to Hevy, with each person's Hevy key stored securely;
- boxes posting to Strava;
- X as a target;
- broad support in the spirit of POSSE (publish on your own site, syndicate elsewhere), with
  GetLate.dev (now Zernio) as the example of a broker.

OpenAPI is the baseline; some APIs are odd. `033.HttpFormats.md` is the research: the formats,
an audit of popular APIs, and the patterns that break "just OpenAPI".

The human chose:
- **Per-user secrets are sealed and stored in the box's database.** The host encrypts each
  secret, bound to its tenant, service, and owner. The box keeps the sealed value and names it
  in a call; only the host ever reads the plaintext, and only while the call goes out.
- **The host runs the OAuth connect flow** as a client acting for the person.
- **Manifests import OpenAPI operations and add small adapters** for what specs can't say.

The principle: **the host owns mechanisms, not APIs.** There is no Strava or X code in the host.
A manifest composes a few named mechanisms per service, and the knowledge about each API lives
in manifests and the specs they pin.

## 1. A service, in full

`external.$service` (015 § 1) keeps every field it had and gains these:

```json
"external": {
  "strava": {
    "base": "https://www.strava.com/api/v3",
    "spec": "strava@3f2a9c1e0b7d",
    "auth": {"kind": "bearer"},
    "credentials": "sealed",
    "connect": {"oauth2": {
      "authorize": "https://www.strava.com/oauth/authorize",
      "token": "https://www.strava.com/oauth/token",
      "client-id": "keys/tenant/{!tenant}/strava_client_id",
      "client-secret": "keys/tenant/{!tenant}/strava_client_secret",
      "client-auth": "body", "scopes": ["activity:write", "read"], "scope-separator": ",",
      "result-route": "strava_connected"}},
    "headers": {"user-agent": "beef-share/1.0"},
    "limits": {"remaining": "x-ratelimit-usage", "retry-after": true},
    "methods": {
      "athlete": {"op": "getLoggedInAthlete"},
      "upload": {"op": "createUpload", "body": "multipart",
                 "poll": {"op": "getUploadById", "path": {"uploadId": "{body.id}"},
                          "done-when": {"at": "body.activity_id", "present": true},
                          "failed-when": {"at": "body.error", "present": true},
                          "every-ms": 2000, "within-ms": 300000},
                 "result-route": "strava_uploaded"}
    }
  }
}
```

| field | meaning |
| --- | --- |
| `spec` | A pinned OpenAPI document in the host's spec store (§ 2): `name@sha12`. |
| `methods.$m.op` | An operation of the spec: its `operationId`, or `"VERB /path"` as the spec spells the path. The verb, path, parameter places, and body type come from the spec; `verb` and `path` are then not given. |
| `auth.kind` | How the secret is applied (§ 3): `header`, `bearer`, `basic`, `query`, or `oauth1`. Without `kind`, `auth` is 015's `{header, prefix}`. |
| `credentials` | As before, a key name (`keys/system/x`, `keys/tenant/{!tenant}/x`), or `"sealed"`: each call carries a sealed secret (§ 4). |
| `connect` | How a person connects their account (§ 5): `{"paste": {...}}` or `{"oauth2": {...}}`. |
| `headers` | Constant headers on every call: an API version (`Linkedin-Version`, `Notion-Version`, `anthropic-version`), a `User-Agent` some APIs require. |
| `methods.$m.body` | `json` (default), `form`, `multipart`, or `raw` (§ 6). Given by the spec's request body when it has only one type. |
| `methods.$m.upload` | A chunked upload of a stored attachment (§ 7). |
| `methods.$m.poll` | An async job polled until done or failed, then reported to the result route (§ 8). |
| `limits`, `methods.$m.error-when` | Rate limits and errors carried on a 200 (§ 9). |
| `"base": "*"` with `methods.$m.any-public` | The box gives the whole URL, any public HTTPS address (§ 10). For discovered endpoints: Webmention, Micropub, a person's Mastodon instance. |

A call is `goober_call(service, method, {path, query, body, credential?, url?})`.
- `credential` is a sealed value, for a `"sealed"` service.
- `url` is for an `any-public` method.

## 2. Specs

**The spec store.** Specs are kept by the host in `storage/specs/$name/$sha256.json`, shared
by every box and tenant. A manifest pins one by name and the first 12 hex digits of its
SHA-256. The host never fetches a spec while a call is made.

**Getting specs in:**
- `spec_put {name, text}` checks and stores one, answering its pin.
- `spec_list` and `spec_get` read them back.
- A source project lists `"specs": ["specs/strava.json"]` in `goober.project.json`; a build
  or deploy stores each (named by the file's stem) before checking its boxes, and its log says
  each pin to write into the manifest.

**The formats.** OpenAPI 2.0 (Swagger), 3.0, 3.1, and 3.2, as JSON. A YAML spec is converted
to JSON before it's put. The host has no YAML parser, and a spec is data an agent can convert.

**At upload, every `op` must resolve:**
- an `operationId`, or `VERB /path` naming a path and verb the spec has;
- each path parameter the operation declares has a place in the call.

**Odd specs.** Hevy's spec has no `operationId`s, so its methods name `"GET /v1/workouts"`. A
spec with mistakes is fixed by putting a corrected copy under the same name; the new pin is a
new hash. OpenAPI Overlays are a later addition.

**What a spec gives a call:**
- the verb and the path template;
- which parameters go in the path, the query, or a header (a header parameter the spec
  declares may come from the box's `query` object, by name);
- the request body's media type.

What a spec says about security is ignored: `auth` and `credentials` decide.

## 3. Applying a secret

| `auth.kind` | sends | for |
| --- | --- | --- |
| `header` | `name: prefix secret` (`{"kind": "header", "name": "api-key"}`) | Hevy (`api-key`), Anthropic (`x-api-key`), Shopify, Discord (`prefix: "Bot "`) |
| `bearer` | `Authorization: Bearer secret` | most APIs, and every OAuth 2 connection |
| `basic` | `Authorization: Basic base64(user:secret)`; `user` fixed (`"api"`), or the secret is `user:password` | Twilio, Mailgun, Stripe, WordPress application passwords |
| `query` | `?name=secret` | YouTube API keys |
| `oauth1` | an OAuth 1.0a HMAC-SHA1 signature over the method, URL, and parameters, with the consumer key and secret from `consumer-key` and `consumer-secret` (key names), and the token and token secret from the sealed secret, or from `token` and `token-secret` keys for the app's own account (X's portal issues one) | X user context, Tumblr |

The secret is whatever the credential holds:
- a key's value;
- a sealed secret's `value`;
- a sealed OAuth 2 connection's access token, refreshed first when needed (§ 5).

A query secret is dropped from the egress log with the rest of the query, as before.

## 4. Sealed secrets

**The vault key.** The host keeps a vault key, `keys/system/vault_key`, 32 random bytes made
on first use. It is backed up with the key store in the sealed nightly. Each tenant has its
own sealing key: HMAC-SHA256 of the vault key over `goober-seal` and the tenant.

**A sealed value** is `gsv1.` and base64url of:
- a 16-byte random salt;
- the ChaCha20 ciphertext of the secret's JSON;
- an HMAC-SHA256 tag over everything before it, and over its context (encrypt-then-MAC, as
  backups seal files, 019 § 2).

**The context** is `tenant`, `service`, and the owner, never stored in the value. A value
moved to another tenant or service fails its check.

**What's inside** is JSON, which the box never sees:
- `{"kind": "key", "value"}` for a pasted key;
- `{"kind": "oauth2", "access_token", "refresh_token", "expires_at", "scope", "id", "gen"}`
  for a connection;
- `{"kind": "oauth1", "token", "token_secret"}`.

**Only the host seals.** Connections (§ 5) are the only way a sealed value is made. A box
can't seal a value it holds, so no plaintext passes through a box at all.

**Using one.** A call names it as `credential`. The host unseals it under the tenant and the
service, applies it (§ 3), and forgets it. In the outbox, the element keeps the sealed value,
not the plaintext; it is unsealed at each delivery attempt. A sealed value that doesn't open
fails the call with `{"error": "the credential doesn't open for this service"}`.

**Losing the vault key** loses every sealed value: people connect again. `goober-host vault key`
prints it, for safekeeping beside the backup key.

**Built so far (2026-10-29):** §§ 1 to 10 as written, with OAuth 1.0a's three-legged flow left
out (tokens come from keys, or a sealed value made another way later). A `paste` connection's
`check` is a method name or an operation.

## 5. Connections

The host serves the connect flow at `/goober/connect/$box/$service`, on the tenant's site, to
a signed-in person. A box links to it, optionally with `?return=/settings` and `&ref=`, an
opaque value of the box's (up to 200 characters).

**Paste** (`{"paste": {"label", "help?", "check?"}}`), for API keys:
- A host-served form asks for the key: a password field, with the label and a help link.
- `check` is a method (like `"GET /v1/user/info"`) the host calls with the key. A 401 or 403
  answers "that key didn't work", and nothing is sealed.
- Otherwise the key is sealed as `{"kind": "key"}`.

**OAuth 2** (`{"oauth2": {...}}`):

| field | meaning |
| --- | --- |
| `authorize`, `token` | the provider's endpoints, https |
| `client-id`, `client-secret` | key names (the tenant's app registration with the provider); the secret is optional for PKCE-only public clients |
| `client-auth` | `body` (client id and secret in the form) or `basic` (HTTP Basic), at the token endpoint |
| `scopes`, `scope-separator` | what is asked for, joined by `" "` (default) or `","` (Strava) |
| `pkce` | true (S256) for providers that take it (X requires it) |
| `extra` | more authorize parameters, like `{"approval_prompt": "auto"}` |

**The dance:**
1. The host redirects to `authorize` with `state` (random, stored with the box, the service,
   the person, the return path, the PKCE verifier, and a 10-minute life) and
   `redirect_uri = https://$domain/goober/connect/callback`.
2. The callback checks `state` once, exchanges the code at `token`, and seals the tokens.

The provider's app registration must list that redirect URI.

**Delivering the sealed value.** The host calls the box's `result-route` (a `routes.result`
route, 015 § 3), as the person, with
`{"service", "kind", "credential", "owner", "ref", "scope", "label"}`, where `owner` is the
person's user id. The box stores `credential` against its row, and the host redirects the
browser to `return`. If the route fails, the person sees an error and nothing is kept.

**Refresh:**
- **When.** An OAuth 2 credential whose `expires_at` is within `refresh.early-ms` (default 5
  minutes) is refreshed before the call, with `grant_type=refresh_token`.
- **One at a time.** A refresh holds a lock on the connection's `id`, so two calls never spend
  one refresh token (Strava, X, and Bluesky rotate them).
- **The host remembers.** The newest tokens are kept, sealed, in
  `storage/connections/state.db` under the connection's `id` and a generation number. A call
  presenting an older generation uses the newer one.
- **The box catches up.** The call's answer carries `"credential"`, the new sealed value, so
  the box can update its row. When it doesn't, the host's copy still serves.
- **Failure.** A refresh answered `invalid_grant` marks the connection dead in the host's
  state. Calls then fail with `{"error": "connection_expired", "connect": "/goober/connect/..."}`,
  so the box can send the person back.

**Disconnecting** is the box's: it deletes its row. A provider's revoke endpoint is a method
like any other.

## 6. Bodies

| `body` | the box's `body` | sent as |
| --- | --- | --- |
| `json` | any JSON | `application/json` (a string body stays `text/plain`, as in 015) |
| `form` | an object; arrays as `"arrays": "brackets"` (`a[]=1&a[]=2`, the default) or `"repeat"` (`a=1&a=2`) | `application/x-www-form-urlencoded`, for Stripe, Mastodon, Micropub, Webmention, and token endpoints |
| `multipart` | an object: a string or number is a field, `{"attachment": "12"}` a file part with the stored file's name and type, `{"json": ...}` a JSON part (Discord's `payload_json`) | `multipart/form-data` |
| `raw` | `{"attachment": "12"}` | the stored bytes with their content type (Bluesky's `uploadBlob`, WordPress media) |

Attachments are the tenant's stored attachments (007 § 7). Their bytes never cross the box's
ABI: the host reads them as the call goes out. A call naming another tenant's attachment is
refused. Bodies are at most 64 MiB.

## 7. Chunked uploads

For APIs that take a file in pieces (X media, Dropbox sessions, LinkedIn video), with its three
steps declared:

```json
"media": {"upload": {
  "attachment": "body.media",
  "init": {"op": "initializeMediaUpload",
           "body": {"media_type": "{content_type}", "total_bytes": "{bytes}", "media_category": "tweet_image"},
           "id": "body.data.id"},
  "append": {"op": "appendMediaUpload", "path": {"id": "{id}"}, "body": "multipart",
             "parts": {"media": "{chunk}", "segment_index": "{index}"}, "chunk-bytes": 4194304},
  "finalize": {"op": "finalizeMediaUpload", "path": {"id": "{id}"}}},
  "poll": {...}, "result-route": "media_ready"}
```

- **The box's call** names the attachment (`{"body": {"media": "12"}}`). The host runs init,
  each append, and finalize as one outbox element, and the result route gets finalize's answer
  (or the poll's, § 8).
- **Templates.** `{content_type}`, `{bytes}`, and `{filename}` come from the attachment;
  `{id}` from init's answer at `id`; `{chunk}` and `{index}` from each append.
- **Failure.** Any step failing fails the element, and the outbox retries it from init.
- **The limit.** Up to 64 MiB per body in this first version; the file is read whole.

## 8. Polling

For APIs whose work finishes later (Strava uploads, X media processing, Instagram and Threads
containers, TikTok):

| field | meaning |
| --- | --- |
| `op`, `path`, `query` | the status call, with `{body.x}` placeholders filled from the first call's answer |
| `done-when`, `failed-when` | `{"at": "body.a.b", "present": true}` or `{"at": ..., "equals": "succeeded"}` |
| `every-ms` | the wait between polls (1000 to 600000) |
| `every-from` | a response field in seconds that overrides it (X's `check_after_secs`) |
| `within-ms` | how long before giving up (up to a day) |

**What a poll needs.** Polling methods must be outbox calls with a `result-route`.

**How it runs:**
- After the first call (or upload) succeeds, the element waits in the outbox as `polling` and
  the dispatcher calls the status operation when it's due. No box sleeps.
- When `done-when` holds, the result route gets `outcome: "done"` with the last answer.
- `failed-when`, or running past `within-ms`, gives `outcome: "dead"` with that answer.

## 9. Limits and errors on 200

**`limits`:**
- **`retry-after`** (true by default) honors `Retry-After` on 429 and 503: the outbox waits
  that long before trying again, not its own backoff.
- **`remaining`** names a header whose `0` means the service's lane waits until `reset`, read
  as seconds or a time.

**`error-when`** (like `{"at": "body.ok", "equals": false}`) makes a 200 a failure for the
outbox and the box, for Slack, Telegram, and GraphQL's `errors`.

## 10. Any public address

A method with `"any-public": true`, on a service whose `base` is `"*"`, takes the whole URL from
the call's `url`. It must be HTTPS. The host's address checks (017 § 2: a public address, no
redirects to private ones) apply, and the egress log records the URL without its query. This
is for discovered endpoints: Webmention (the endpoint is on the target page), Micropub, a
person's Mastodon instance, WordPress. Credentials still come from the manifest or the call,
never from the URL.

## 11. The scenarios

**A Hevy MCP proxy:**
- **The service.** `hevy` with the Hevy spec pinned (methods as `"GET /v1/workouts"`),
  `auth: {"kind": "header", "name": "api-key"}`, and `credentials: "sealed"`, with
  `connect: {"paste": {"label": "Hevy API key", "check": "GET /v1/user"}}`.
- **The box.** It stores each person's sealed key in a `connections` table. Its MCP tools
  (012) call `hevy` with the caller's credential.
- **Reads and writes.** Reads are `effect: none`. Writes are `effect: none` too when the person
  is there and waiting for an answer, or `outbox` with a result route.
- **Paging.** Pages of at most 10 are the box's loop.

**Strava:**
- **The service.** `strava` as in § 1: the spec pinned, an OAuth 2 connection with
  `client-auth: body` and scopes joined by commas, and multipart uploads of a stored GPX or FIT
  attachment.
- **The upload.** It polls `getUploadById` until `activity_id` (or `error`), then the result
  route has the activity.
- **Rotation.** Strava rotates refresh tokens, so the host's single-flight refresh and stored
  generation matter here.

**X:**
- **The service.** `x` with X's spec pinned, an OAuth 2 connection with `pkce: true`,
  `client-auth: basic`, and the scopes `tweet.write media.write users.read offline.access`.
- **Images.** The chunked upload (§ 7), polling `processing_info` for video.
- **Posting.** `createPosts` with the media ids, from the result route.
- **Fallback.** `oauth1` is there for apps on OAuth 1.0a user context.
- **Cost.** X bills per post, more for posts with links (033 § 2a). A POSSE box should know it.

**POSSE.** A `posse` box keeps the canonical post on the site (031's posts) and syndicates it:
- **Webmention** is `any-public`, a form body, and no auth.
- **Micropub** and **Micro.blog** are `any-public` or a base, bearer, and a form body.
- **WordPress** is basic with an application password via paste, and `raw` media.
- **Mastodon** is `any-public` (the person's instance) with an OAuth 2 connection; per-instance
  app registration is a box's job through a method.
- **Bluesky** is app passwords via paste, and `createSession` as a method. Its OAuth (DPoP, PAR,
  per-person servers) is left out.
- **X**, as above.
- **A broker** like Zernio is one more service: bearer with a tenant key, its presigned media
  URL as an `any-public` `raw` PUT, and an `Idempotency-Key`. A broker holds every social token
  itself; going direct keeps them in the box's database, sealed.

## 12. What's left out

- **Pagination as a host primitive.** Boxes page with their own cursors; `033 § 4.2 (7)` has
  the shape.
- **Resumable uploads** (YouTube, Google Drive): a session URL with `Content-Range` PUTs.
- **Presigned POSTs** with form fields (S3-style).
- **GraphQL as a method kind.** It's possible today as a `json` POST.
- **JWT assertions** (GitHub Apps, Google service accounts) and template HMAC signers.
- **OpenAPI Overlays.**
- **Bluesky OAuth.**
- **Inbound webhook verification** (033 § 3, the ninth primitive).

## 13. Tests

- **vault:** sealing round-trips; another tenant's, service's, or owner's context fails; a
  flipped byte fails; the format.
- **specs:** OpenAPI 2.0 and 3.x operations by `operationId` and `VERB /path`, parameter
  places, body types, and refusals.
- **manifest:** the new fields, and refusals.
- **host, against a stand-in service:**
  - each `auth.kind` (`oauth1` against RFC 5849's worked example);
  - a sealed credential in a call and through the outbox;
  - a moved credential refused;
  - form, multipart with an attachment, and raw bodies;
  - paste with a check;
  - the OAuth 2 dance with PKCE, the result route, and the redirect;
  - single-flight refresh with rotation, and the remembered generation;
  - `invalid_grant` to `connection_expired`;
  - a chunked upload;
  - polling to done, failed, and past its deadline;
  - `Retry-After`, `error-when`, and an `any-public` call refused for a private address.
