# 022. Mail templates

Status: built, at the human's request on 2026-10-28: "an email template... nicely formatted
with the sign in code... a welcome back that is a bit leaner... sane defaults that can be
customized, and this applies for all emails." It extends 038.Mail.md and
`design/machine/018.Mail.md`.

## 1. What a template is

A template has a name and three parts, each Mustache:

| part | rendered as | notes |
| --- | --- | --- |
| `subject` | plain text | one line, at most 200 bytes after rendering |
| `text` | plain text | required: every mail has a text part |
| `html` | HTML, every value escaped | `""` makes the HTML from the text: paragraphs at blank lines, `<br>` at newlines |

The `layout` template wraps every mail. Its `text` and `html` must each hold `{{{content}}}`,
where the rendered mail goes (the only value placed unescaped). It also gets `subject`,
`preheader` (the text's first line, shown by clients beside the subject), `site`, and `email`.

Every template gets `site` (the domain the mail is about) and `email` (the recipient).

## 2. The host's own mails

| name | when | values |
| --- | --- | --- |
| `sign-in-new` | the code for an address not yet proved (021): a first sign-in, or an invite taken up | `code`, `expires_minutes` |
| `sign-in-returning` | the code for an address proved before; shorter | `code`, `expires_minutes` |
| `new-grant` | a person let an app or agent act for them | `kind`, `acting`, `client`, `from`, `unchecked` |
| `agent-token` | an operator minted an agent token for a person | `client`, `days` |

The defaults are written for mail clients: tables for layout, inline styles, no images,
scripts, or links. The sign-in code sits in a large monospace box. 013's rules hold: a sign-in
mail names the site, warns never to share the code, and carries no link. An operator can
change the wording; `mail_template_put` reminds them of these rules.

If a template fails to render when sent (it rendered when it was saved), the fallback text
the identity service wrote goes instead: a template can never stop a sign-in code.

## 3. Overrides

Templates live under `storage/mail/templates/$tenant/$name.json`. The template in effect for
a tenant is the first of:

1. the tenant's own copy,
2. `_host`'s copy, which every tenant uses unless it has its own,
3. the default.

A host realm mail (a host operator's sign-in) uses `_host`'s copy, else the default.
Removing a copy falls back to the next one.

## 4. Box mail

Every box mail gets an HTML part: the box's text inside the tenant's layout. A box may also
send a template of its tenant's own, by name:

```json
{"to": "person@example.org", "template": "order-ready", "vars": {"name": "Ann"}, "reply_to": "..."}
```

The template is rendered in the call, so a missing template or bad values fail the call, not
the delivery. `vars` is at most 16 KiB; `site` is the request's domain and `email` is always
`to`, whatever `vars` says. A box can't send the host's own templates (`sign-in-new` and the
rest) or the layout, so no box can send a mail that looks like a sign-in code.

## 5. MIME

A mail with HTML is `multipart/alternative`: the text part first (8bit, or base64 if a line
passes 998 bytes), then the HTML as base64. SES and SMTP send the same message.

## 6. Operator tools

| tool | does |
| --- | --- |
| `mail_template_list` | the templates in effect for a tenant, with whose copy each is |
| `mail_template_get` | a template's parts, its source, its purpose, and its sample values |
| `mail_template_put` | checks (by rendering with the sample values) and saves a copy or a new template |
| `mail_template_remove` | removes a copy |
| `mail_template_preview` | renders with the samples (or given `vars`); with `to`, sends it, subject prefixed `[Test]` |

## 7. Not built

- Images in mail (would be attachments served from the site; links to them are tracking).
- A template editor in the panel; operators and agents use the tools.
