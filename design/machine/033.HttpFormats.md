# Describing HTTP APIs: the formats, and an audit of popular APIs

Research, 2026-10-29. The human asked how HTTP is described cleanly, how widely each way is
supported, and how popular APIs actually behave (Amazon left out: it's a world of its own), so
that boxes can speak to Hevy, Strava, X, and broadly for POSSE (publish on your own site,
syndicate elsewhere) without the host owning every API. `034.SpeakingHttp.md` is the design
built on it.

**Citations.** A URL in a claim was fetched or found by search on 2026-10-29. **[pk]** marks
what comes from prior knowledge and wasn't checked again then: likely, not verified.
**[unverified]** marks claims where sources disagreed or the primary page couldn't be read.

## 0. Headline findings

1. **OpenAPI really is the baseline, and it's better than it looks.** Every large API in the
   audit that ships a machine-readable description ships OpenAPI (or Swagger 2.0, or Google
   Discovery). I downloaded and parsed four: X (3.0.0, 257 operations, all with
   `operationId`), Stripe (3.0.0, 612 operations, all with `operationId`), Discord (3.1.0, 250
   operations, all with `operationId`), and Strava (Swagger 2.0, 31 operations, all with
   `operationId`).
2. **"Import by operationId" isn't enough on its own.** Hevy's spec (OpenAPI 3.0.0,
   `info.version` 0.0.1) is embedded in `https://api.hevyapp.com/docs/swagger-ui-init.js`, has
   **zero** `operationId`s, and declares no `securitySchemes`. The key is a required `api-key`
   header *parameter* on each operation. Import also has to accept `"GET /v1/workouts"`
   (method + path template).
3. **OpenAPI can't say how to sign.** The X spec lists the OAuth 1.0a user context as
   `{"type": "http", "scheme": "OAuth"}`, a scheme name OpenAPI defines no behavior for. Its
   media-upload operations accept either `{"OAuth2UserToken": ["media.write"]}` or
   `{"UserToken": []}` (OAuth 1.0a). Signing, token refresh, rotation, and per-user
   connections all sit outside every description format. The host has to own them as named
   adapters.
4. **The other recurring gaps** are uploads (multipart with a metadata part, chunked
   INIT/APPEND/FINALIZE, resumable `Content-Range` sessions, presigned PUT), async jobs with
   polling (Strava uploads, X media, Instagram/Threads containers, TikTok, Pinterest video),
   pagination conventions, rate-limit headers, and errors returned with HTTP 200 (Slack,
   Telegram).
5. **The IETF drafts are live but not RFCs.** `Idempotency-Key` is
   draft-ietf-httpapi-idempotency-key-header-08, dated 22 Oct 2026. `RateLimit` /
   `RateLimit-Policy` is draft-ietf-httpapi-ratelimit-headers-11, dated 23 May 2026 and
   expiring 24 Nov 2026. Real APIs still mostly use `X-RateLimit-*` variants and their own
   idempotency headers.
6. **GetLate.dev is now Zernio.** The domain redirects (`docs.getlate.dev` returns 301 to
   `docs.zernio.com`), and per https://zernio.com/rebrand the API, keys, and webhooks carried
   over. Its shape is a good POSSE model: one `POST /v1/posts` with `platforms[{platform,
   accountId}]`, media by presigned URL, `Idempotency-Key`, and webhooks.
7. **About eight host primitives** cover nearly the whole audit: spec import, credential
   appliers (with oauth2-refresh and oauth1/hmac/jwt signers), per-user connections, body
   encodings, uploads, polling, pagination, and rate-limit/error interpretation. One more,
   webhook verification, is adjacent. Section 4 maps each primitive to the APIs it unlocks.

| **API Blueprint** | Markdown-based REST description (MSON data structures). | Most of the above. | Effectively dormant (Apiary/Oracle). **[pk]** |

| **Google API Discovery documents** | Google's own JSON: `resources.methods` with `httpMethod`, `path`, `parameters` (location: path/query), `request`/`response` schema refs, `scopes`, **`mediaUpload`** (accepted MIME types, `maxSize`, `protocols.simple` and `protocols.resumable` paths), and `supportsMediaDownload`. | Pagination as convention only (`pageToken`/`nextPageToken`). | All Google APIs. | **gRPC/protobuf + `google.api.http`** | Proto services with HTTP/JSON transcoding annotations (`get: "/v1/{name=shelves/*}"`, `body: "*"`). | Same auth gaps; needs a transcoder. | Google, Envoy, grpc-gateway. Relevant only for gRPC-first services. **[pk]** |
| **Smithy** (AWS origin) | A protocol-agnostic IDL with traits (`@http`, `@paginated` with input/output token paths, `@idempotencyToken`, `@retryable`, waiters for async polling, `@auth` traits incl. SigV4). | n/a | Mainly AWS. **Notable as prior art:** it models pagination, idempotency tokens, and *waiters* (polling with acceptors) as first-class traits, which is exactly goober's gap list. Treat as inspiration only. **[pk]** |
| **TypeSpec 1.0** (GA May 2025) | Microsoft's TS-like API language. `@typespec/http` and `@typespec/openapi3` are stable emitters (https://typespec.io/blog/typespec-1-0-GA-release/ via search). | It authors OpenAPI; it isn't a runtime format. | Azure SDKs; growing. Irrelevant at runtime: goober consumes the emitted OpenAPI. |
| **HAR 1.2** | Recorded request/response pairs (headers, cookies, bodies, timings). | Any abstraction. | Universal in browsers. Useful only as test fixtures or to reverse-engineer an undocumented API. **[pk]** |
| **Postman collections v2.1** | Requests in folders, variables, auth helpers (incl. **OAuth 1.0 signing, AWS SigV4, Hawk, Digest, NTLM**), pre-request scripts in JS. | Signing beyond the built-ins needs scripts (JS). | Huge informal adoption. LinkedIn, Discord, and others publish official collections (the LinkedIn page fetched above links one). **Its auth-helper list is a good inventory of the schemes people actually need.** |
| **.http / REST Client files** (VS Code REST Client, JetBrains HTTP Client) | Plain request text with `{{variables}}`, `###` separators, and simple response-handler scripts (JetBrains). | Everything structural. | Popular for hand testing. A good *readability* target for goober's vocabulary. **[pk]** |
| **Hurl** | Plain-text requests plus `[Captures]` (JSONPath/XPath/header/regex) plus `[Asserts]`, chained in files; `[Options] retry`. | Signing; loops. | Growing in CI. **Captures + asserts + retry is the minimal "workflow" grammar**, close to what goober needs for poll loops. **[pk]** |
| **MCP tool descriptions** | `name`, `title`, `description`, `inputSchema` (JSON Schema 2020-12 by default), optional `outputSchema`, `annotations` (untrusted unless from a trusted server), and `x-mcp-header`. The spec at https://modelcontextprotocol.io/specification/latest/server/tools is currently versioned 2026-07-28. | No HTTP at all: tools are opaque functions. Guidance for state is "return an explicit handle." | Universal among agent clients. Relevant to goober because the Hevy MCP-proxy scenario turns OpenAPI operations into MCP tools: goober already mirrors box routes into MCP tools (machine doc 012). |

**Takeaway.** Import OpenAPI (2.0, 3.0, 3.1, 3.2) and Google Discovery as *catalogs of
operations*. Apply Overlays to patch them. Borrow Arazzo/Hurl's step shape (capture, assert,
retry-after) and Smithy's trait ideas (paginated, idempotencyToken, waiters) for the gaps,
expressed as a handful of host-owned primitives rather than a workflow engine.

## 2. API audit (AWS excluded)

Legend. **Spec**: official machine-readable description. **Auth**: how calls authenticate.
**Body**: request encodings that matter. **Page**: pagination. **RL**: rate-limit signaling.
**Idem**: idempotency support. **Async**: job/poll patterns. **Hooks**: inbound webhooks and
how they're verified.

## 3. Patterns that break "just OpenAPI"

| Pattern | Where it shows up | Why OpenAPI alone falls short | What the host must own |
| --- | --- | --- | --- |
| **Request signing: OAuth 1.0a** | X (user context, incl. media), Tumblr, legacy Garmin, Flickr **[pk]** | The X spec can only label it `http`/`OAuth`. The signature base string (method, normalized URL, sorted percent-encoded params incl. form body), nonce, timestamp, and HMAC-SHA1 with consumer+token secrets are behavior, not shape. | One `oauth1` signer: about 150 lines over OpenSSL, which the host already links. Four secrets per connection. |
| **HMAC request signing (exchange-style)** | Coinbase legacy keys (`CB-ACCESS-KEY`/`-SIGN`/`-TIMESTAMP`, HMAC-SHA256 hex of `timestamp+method+path+body`), Kraken (`API-Sign`) **[pk]**, Facebook `appsecret_proof` **[pk]** | Every vendor has its own canonical string. | A *template* HMAC signer: `{algorithm, key, message: "{timestamp}{verb}{path}{body}", encoding: hex|base64, put: header/X}`. | **JWT assertions** | GitHub Apps (RS256 → installation token), Google service accounts (RFC 7523), Microsoft certificate credentials, Coinbase CDP (ES256 JWT per request) | Not in any format. | A `jwt` minter: claims template + `alg` (RS256/ES256/EdDSA) + private key from the key store, used either directly as a Bearer or exchanged at a token endpoint (cached until `exp`). |
| **Per-user OAuth2 tokens with refresh and rotation** | Strava (6 h, rotating refresh), X (2 h, `offline.access`), atproto (single-use refresh), Dropbox, Spotify, Reddit (1 h), LinkedIn (60 d/365 d, non-rotating), Threads/IG (60 d, refreshed by a *different* grant), Google | OpenAPI `oauth2` gives URLs and scopes only. The box never sees a token. |
| **Dynamic per-user endpoints** | Mastodon (instance), atproto (PDS + auth server), Micropub (discovered), WordPress (self-hosted), Webmention (target-discovered), Shopify (per shop) | `servers` is static. | A connection may carry its own `base`. ## 4. What follows for goober

### 4.1 Principles

- **The host owns *mechanisms*, not *APIs*.** No Strava or X code in the host. The host knows
  about eight named mechanisms; a manifest composes them per service. Vendor knowledge lives
  in manifests (and shareable "service descriptions" that boxes import), never in C++.
- **OpenAPI is the catalog, the manifest is the policy.** A spec supplies verbs, paths,
  parameter locations, and schemas. The manifest adds what specs can't: credentials,
  connections, effect/outbox, `require`, pagination, polling, upload mode, and limits.
- **Pin and vendor specs.** The host never fetches a spec at call time. A spec is uploaded
  with the box (or referenced by `sha256`), optionally patched by an Overlay, and checked at
  upload: every imported operation exists, and every `{param}` has a source.
- **Bytes never cross the ABI.** Uploads name host attachments (007's `/attachment/$id`).
- **The box never sees a secret.** That includes per-user keys. The Hevy scenario as worded
  ("API key per user stored securely in the box's database") **conflicts with goober's
  existing rule** (015: `credentials` is a key name, "never a value"). The recommendation is a
  host-held per-user connection. That's a decision for the human (see 4.5).

### 4.3 The four scenarios in this vocabulary

**(1) Hevy MCP proxy.** One service, a `paste` connection per user, `header` auth
`api-key`, the spec imported from the vendored, embedded document with an Overlay that adds
`operationId`s (or `VERB /path` references), and `paginate: page` with `max: 10`. The box
exposes MCP tools (goober 012) that call `goober_call("hevy", "listWorkouts", …)`; reads are
`effect: none`, writes (`POST /v1/workouts`) are `effect: outbox` or `immediate`. Add host
jitter for scheduled syncs, since Hevy asks clients not to call at xx:00. The primitives used
are 1, 2, 3, and 7.

**(2) Strava.** An `oauth2` connection (`client-auth: body`, `refresh.rotates: true`,
`early-ms` ≈ 1 h given the "same token if >1 h left" rule), an `upload` multipart body
(`file` = attachment, `data_type`, `external_id` as the idempotency placement), then `poll`
`GET /uploads/{id}` until `activity_id`, delivered to a result route. `limits.pair` reads the
15-minute and daily headers. The primitives used are 1, 3, 4, 6, and 8.

**(3) X.** Prefer the `oauth2` connection with PKCE and the `tweet.write media.write
offline.access` scopes. `oauth1` is the fallback the spec also accepts. Then a chunked
`upload` (initialize/append/finalize), a `poll` on `processing_info`, and finally `POST
/2/tweets` with `media.media_ids`. Budget against pay-per-use pricing (posts with URLs cost
about 13× more per the 2026 changelog; a POSSE box that always links back to the original
should know this). The primitives used are 1, 2/3, 5, 6, and 8.

**(4) POSSE.** There are two paths, and the host supports both without new mechanisms:
- **Use a broker (Zernio):** one service, `bearer` with a tenant key, `presigned` media, and
  `Idempotency-Key`. Connecting accounts is Zernio's `GET /v1/connect/{platform}` redirect,
  which a box route can bounce the user through. That's fastest and covers 16 posting
  targets, but a third party holds every social token, and pricing/terms are theirs.
- **Go direct (emulate Zernio inside goober):** a `posse` box with one adapter per network,
  each a manifest service. Cheapest to support, in order: **Webmention** (form, no auth,
  discovered endpoint), **Micropub/Micro.blog** (bearer + form), **WordPress** (basic app
  password + raw media), **Mastodon** (per-instance OAuth, form + `Idempotency-Key`, media
  202 poll), **Bluesky** (app password; raw `uploadBlob`; facets computed by the box),
  **Threads/Instagram** (container → poll → publish, media by *public URL*, so goober's
  attachment routes must be publicly fetchable), **LinkedIn** (version header,
  initializeUpload), **X** (above). Avoid Medium (closed), Fitbit (shutting down), and Garmin
  (gated). TikTok needs an app audit before public posts.

  Copy Zernio's request shape for the box's own API: `{content, mediaItems[{url,type}],
  platforms[{platform, accountId, customContent?}], scheduledFor, timezone}`, answered with a
  per-platform status and fed by webhooks or polls.

### 4.4 Coverage of the eight primitives

| Primitive | APIs in the audit that need it (excluding trivially-bearer ones) |
| --- | --- |
| 1 spec import | X, Stripe, Discord, GitHub, Twilio, SendGrid, OpenAI, Pinterest, Spotify, MS Graph, Strava, Hevy (≈12 with official specs) |
| 2 appliers beyond bearer | Hevy, Discord, Shopify, Anthropic, Twilio, Mailgun, Stripe, WordPress, Telegram, YouTube; signing: X, Tumblr; JWT: GitHub Apps, Google SA, MS Graph |
| 3 connections / OAuth2 | Strava, X, Reddit, Spotify, Dropbox, LinkedIn, Pinterest, Google, MS Graph, TikTok, Threads, Instagram, Facebook, Mastodon, Notion (public), Shopify, Slack, Hevy (paste), Bluesky (paste), WordPress (paste) |
| 4 body encodings | form: Stripe, Twilio, Mastodon, Micropub, Reddit, Slack, Webmention; multipart: Strava, Discord, Mailgun, Tumblr, Mastodon; raw: Bluesky, WordPress; header-json: Dropbox; graphql: Buffer, Shopify |
| 5 uploads | X, YouTube, Drive, MS Graph, Dropbox, LinkedIn, TikTok, Instagram, Slack, Zernio, Shopify, Pinterest |
| 6 poll | Strava, X, Instagram, Threads, TikTok, Pinterest, Mastodon, Shopify bulk, OpenAI/Anthropic batches |
| 7 paginate | every list API |
| 8 limits/errors | all 429 users; specifically Strava, X, GitHub, Mastodon, Discord, Reddit, Slack/Telegram (errors on 200), GraphQL APIs |

Primitives 1 to 4 plus 7 and 8 are enough for the Hevy proxy and most read/write APIs. 5 and
6 are what social posting with media actually needs (Strava, X, IG/Threads, TikTok,
YouTube). `oauth1`, `hmac`, and `jwt` are small, self-contained signers. atproto OAuth
(DPoP, PAR, per-user authorization servers) is the one thing in the audit that doesn't fit
the pattern cheaply, and I'd leave it out of a first version.

### 4.5 What the human decided

On 2026-10-29 the human chose, from these:
- **Per-user secrets are sealed and kept in the box's database.** The host encrypts each one
  under a vault key, bound to its tenant, service, and owner. The box stores the sealed value
  and names it in a call, and never sees the plaintext. (The alternative was a host key store
  per user.)
- **The host serves the OAuth connect flow** (`/connect/$service` and its callback) as an
  OAuth client for the person, and hands the box the sealed tokens.
- **Manifests import OpenAPI operations and add small adapters** for what specs can't say.

The rest (pinned specs only, which signers first, polling as a host primitive, egress to
returned hosts) follows the recommendations above, and `034` says how.
