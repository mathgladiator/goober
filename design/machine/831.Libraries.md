# Host libraries

On 2026-10-29 the human asked for three things:
- Boxes should handle calendar invites easily: send and create them, handle accepts and
  declines, and handle proposals. Parsing and producing ICS should be a prime host function.
- Time should be a first-class citizen, with a standard library of sorts.
- Manifests should be able to import closed host functions that do heavy lifting. This
  document is the design for that.

The human chose:
- a `libraries` manifest section with one new ABI import;
- time zone rules from the server's tzdata, with each answer naming its version;
- a goober-written ICS library, heavily tested;
- design, then build.

This is built: `time@1` and `ics@1`.

## 1. What a library is

A library is a **closed host function set**: code in the host, behind a versioned contract,
that a box calls the way it calls a pure function.

- **Closed.** A box can't add, replace, or extend one. The host ships them, as it ships the
  mailer. A library is part of the host, not of any box.
- **Pure.** A library function reads only its input, plus the request's clock and the host's
  tzdata. It writes nothing, calls nothing outside the host, and has no effect to commit or
  roll back. Calling it twice with the same input gives the same answer.
- **Versioned like 330's capabilities.** `time@1` is a contract the host keeps:
  - Within a major version, functions and optional fields may be added. Nothing may change
    meaning or disappear.
  - A break is `time@2`, served beside `time@1` for as long as any box names it.
- **Heavy lifting.** Libraries exist for work that is large, subtle, and the same for
  everyone: time zones and recurrence, calendar formats. Later candidates include phone
  numbers, address parsing, money and currencies, units, and text search. A box would
  otherwise compile such work into every module, each copy with its own bugs.

## 2. The manifest

```json
{
  "libraries": {
    "time": "time@1",
    "ics": "ics@1"
  }
}
```

- **The key** is the name the box calls it by, a chosen name under the naming rule.
- **The value** is a library and its major version.
- **Upload checks.** A name the host doesn't have, or a version it doesn't serve, refuses the
  upload, saying which libraries and versions it has.
- **Approvals (305).** Adding or changing a library is a manifest change of kind
  `libraries_changed`, like any other.

## 3. The boundary

One new import, beside `goober_call` (120's copy boundary, the same shape):

```c
// Calls a declared library's function with a JSON argument. Returns the result's length, to
// read with goober_result_read, or -1 when a pointer is out of bounds.
int32_t goober_lib(const char* lib, int32_t lib_len, const char* fn, int32_t fn_len,
                   const char* json, int32_t json_len);
```

**Results** are JSON.
- A failure is `{"error": "...", "code": "..."}`, and never traps the box.
- `code` is one of:
  - `unknown_library`, for a name the manifest doesn't declare;
  - `unknown_function`;
  - `bad_input`;
  - `too_large`;
  - `limit`, when expansion stops at its cap.

**Limits** keep a library call from becoming a way around the box's own budgets.
- An argument is at most 1 MiB, and a result at most 16 MiB (the boundary's `kMaxResponseBytes`).
- A request makes at most 10,000 library calls.
- A recurrence expands to at most 10,000 instances.
- The host's time in libraries counts in the request's `us`, so heat and the rollups see it
  (028).

**Determinism (300 § traces, 330 § replay).**
- `time.now` is the request's clock, the same `goober_now_ms` the box sees, so a replayed
  request sees the same now.
- Zone answers depend on tzdata. Every answer that used it names `tzdata`, the version string
  of the server's IANA database (`2025b`), so a replay on a newer server can tell when a
  difference is a rule change.

**Bindings.**
- Rust: `goober::lib(name, function, json) -> Value`, in the shared `goober.rs`.
- C: the import above.
- Contracts: a generated binding can be typed from each library's contract, which
  `library_get` returns.

**Operators and agents** read the contracts with two read tools (028 § 7):
- `library_list`, every library and version;
- `library_get`, one library's functions, with the input and output of each, and examples.

## 4. `time@1`

Instants are int64 unix milliseconds (`ms`) and RFC 3339 strings. Wall-clock time is
`{"date": "2026-11-05", "time": "18:00:00"}` or the string `"2026-11-05T18:00:00"`, always
with a zone named in IANA form (`America/Chicago`).

| function | takes | gives |
| --- | --- | --- |
| `now` | `{zone?}` | `{ms, utc, local?, zone?, offset?}`: the request's clock |
| `parse` | `{text, zone?}` | `{ms, utc}`: RFC 3339 with a zone or offset; a date or a local time with `zone` |
| `format` | `{ms, zone}` | `{utc, local, date, time, offset, abbreviation, dst, weekday, iso_week, day_of_year}` |
| `to_utc` | `{local, zone}` | `{ms, utc, offset, adjusted?}`: in a gap (spring forward), the time after it, and `adjusted: "gap"`; in an overlap (fall back), the earlier, and `adjusted: "overlap"` |
| `add` | `{ms, zone, years?, months?, weeks?, days?, hours?, minutes?, seconds?}` | `{ms, utc, local}`: calendar units in the zone (a day across a DST change is 23 or 25 hours), then exact units; a month past its end clamps (Jan 31 + 1 month is Feb 28 or 29) |
| `diff` | `{from, to, zone?}` | `{ms, seconds, days?}`: exact, and calendar days in the zone |
| `start_of` | `{ms, zone, unit: day, week, month, year, week_starts?}` | `{ms, utc, local}` |
| `zone` | `{zone, ms?}` | `{zone, offset, abbreviation, dst, next_change?}`, or `bad_input` for an unknown zone |
| `zones` | `{prefix?}` | `{zones: [...]}`, the IANA names |
| `recur` | `{rrule, start: {local, zone} or ms, from?, to?, limit?, exdates?, rdates?}` | `{instances: [{ms, utc, local}], truncated}`: RFC 5545 recurrence |

Every answer that used a zone also has `tzdata`.

**Recurrence** (`recur`, and `ics@1`'s `expand`) is RFC 5545 § 3.3.10 and § 3.8.5:
- **Rule parts.** `FREQ` (SECONDLY to YEARLY), `INTERVAL`, `COUNT`, `UNTIL`, `BYSECOND`,
  `BYMINUTE`, `BYHOUR`, `BYDAY` (with ordinals for MONTHLY and YEARLY: `1FR`, `-1SU`),
  `BYMONTHDAY` (negative from the end), `BYYEARDAY`, `BYWEEKNO`, `BYMONTH`, `BYSETPOS`, and
  `WKST`.
- **Zones.** Instances are computed in the start's wall-clock zone, so a 9:00 meeting stays at
  9:00 across DST.
- **Exceptions.** EXDATEs are removed and RDATEs added.

## 5. `ics@1`

A calendar is parsed into **events as JSON**, and built back from them. Boxes never handle
folding, escaping, TZIDs, VTIMEZONEs, or iTIP methods themselves.

```json
{"uid": "meetup-7@example.com", "sequence": 0, "status": "CONFIRMED",
 "summary": "Brisket night", "description": "...", "location": "Q39", "url": "https://...",
 "start": {"ms": 1793923200000, "utc": "2026-11-06T00:00:00Z", "local": "2026-11-05T18:00:00",
           "zone": "America/Chicago"},
 "end": {"ms": ..., ...}, "all_day": false,
 "rrule": "FREQ=WEEKLY;BYDAY=TH", "exdates": [...], "recurrence_id": null,
 "organizer": {"email": "thesis@example.com", "name": "The Example Club"},
 "attendees": [{"email": "ada@example.org", "name": "Ada", "partstat": "ACCEPTED",
                "role": "REQ-PARTICIPANT", "rsvp": true}],
 "comment": null, "alarms": [{"trigger": "-PT30M", "action": "DISPLAY"}], "other": {"X-...": "..."}}
```

All-day events have `start` and `end` as `{"date": "2026-11-07"}`.

| function | takes | gives |
| --- | --- | --- |
| `parse` | `{ics}` | `{method, prodid, events: [event], todos: [...], warnings: [...]}` |
| `build` | `{method?, events: [event], prodid?}` | `{ics}`: a whole VCALENDAR, VTIMEZONEs left to the receiver's IANA names, UTC where no zone is given |
| `invite` | `{event, organizer, attendees, method?: REQUEST or CANCEL}` | `{ics, event}`: iTIP (RFC 5546) for those attendees, `RSVP=TRUE`, `NEEDS-ACTION` |
| `respond` | `{ics, attendee, partstat: ACCEPTED, DECLINED, or TENTATIVE, comment?, propose?: {start, end}}` | `{ics}`: the REPLY, or with `propose`, a COUNTER to send back to the organizer |
| `interpret` | `{ics, me?}` | what a mail means, in one word: `{kind, uid, sequence, attendee, partstat, proposed?, comment, event}` (below) |
| `counter_decline` | `{counter_ics, organizer, comment?}` | `{ics}`: DECLINECOUNTER |
| `counter_accept` | `{event, counter_ics}` | `{ics, event}`: the event moved to the proposed times, `sequence` raised, as a REQUEST to send to everyone |
| `expand` | `{ics or event, from, to, limit?}` | `{instances: [{ms, utc, local, recurrence_id}], truncated}` |

**`interpret`**'s `kind` is one of:

| kind | when |
| --- | --- |
| `invite` | METHOD:REQUEST with sequence 0: a new event (`for_me` and `my_partstat` say whether `me` is invited) |
| `update` | REQUEST with a higher sequence: the organizer changed it; compare with your copy's sequence |
| `accepted`, `declined`, `tentative` | REPLY, from `attendee` |
| `delegated` | REPLY with PARTSTAT=DELEGATED |
| `reply` | another REPLY, like NEEDS-ACTION |
| `proposal` | COUNTER: `proposed` is `{start, end}`, the times the attendee asked for, and `comment` their reason |
| `counter_declined` | DECLINECOUNTER, to an attendee whose proposal the organizer turned down |
| `cancelled` | CANCEL |
| `refresh` | REFRESH: the attendee asks for the current version |
| `published` | PUBLISH: an announcement, no reply expected |
| `added` | ADD: instances added to a recurring event |
| `other` | no METHOD it knows, or no event |

**Parsing** is lenient in what it reads and strict in what it keeps.
- **Reading.** It takes folded lines, LF or CRLF, any case, `TZID`s that are IANA names,
  Windows names (`Central Standard Time`, mapped by CLDR's table for the common zones), or
  defined by the file's own `VTIMEZONE`.
  - A `VTIMEZONE` is evaluated from its STANDARD and DAYLIGHT rules, and its definition is
    used before any name, as RFC 5545 says.
  - An unknown TZID is read as UTC with a warning.
  - Floating times are read in the calendar's `X-WR-TIMEZONE`, or UTC with a warning.
- **Keeping.** The input is at most 1 MiB, a component holds at most 10,000 properties,
  nesting is at most 8 deep, and anything over is a warning, not a crash.

**Building** writes what every client accepts: CRLF, lines folded at 75 octets on UTF-8
boundaries, TEXT escaped, parameters quoted when they must be, UTC times or `TZID`s with
IANA names, `DTSTAMP` from the request's clock, `PRODID:-//goober//ics@1//EN`.

### Proposals

A proposal, an attendee asking for another time, is iTIP's COUNTER. Outlook sends it from
"Propose new time", and Gmail, Apple, and goober's own `respond` with `propose` send it too.
A box handles one in three steps:
1. The mail route gets the message; `ics.interpret` says `kind: "proposal"`, with `proposed`
   and `comment`.
2. The box decides: its own rule, or its agent, or the people (the community's digest can
   ask, 783).
3. It sends either `ics.counter_accept`'s REQUEST (moved, sequence raised) to every
   attendee, or `ics.counter_decline`'s DECLINECOUNTER to the one who proposed.

A box finding a time for a group, before any invite exists, proposes slots in its own words
(a digest's options) and invites once enough people pick one. `time@1` does the arithmetic:
`add`, `start_of`, and `recur` for "every Thursday at 7 in Chicago", in the group's zone.

## 6. Mail and calendars

The mail service uses `ics@1` itself, so boxes get calendars without touching ICS.

- **`send` takes `"ics"`** besides 783's `"invite"`. The value is the text of any calendar
  built with `ics@1` (an invite, a REPLY, a COUNTER, a DECLINECOUNTER, or a CANCEL). It goes
  as a `text/calendar` alternative with its METHOD, and as `invite.ics`.
- **`"invite"`** keeps its shape and is now built by `ics@1`'s `invite`.
- **Received mail's `calendar`** is `ics@1`'s `interpret` of the message's `text/calendar`
  part, with `me` set to the mail route's address: `{kind, uid, sequence, attendee, partstat,
  proposed?, comment, event}`. It also carries `ics`, the part's text (up to 256 KiB), which
  `counter_accept`, `counter_decline`, and `respond` take.

## 7. Built, and tested

- **Packages:**
  - `calendar`: the iCalendar model, parser, serializer, recurrence, VTIMEZONE evaluation,
    zones, and iTIP.
  - `libraries`: the registry, `time@1`, `ics@1`, and the JSON contracts.
- **Box plumbing:**
  - `runtime_wasm` has the `goober_lib` import;
  - `manifest` has `libraries`;
  - the host checks libraries at upload, routes calls, keeps the per-request limit, logs
    `libraries` and `tzdata` on the access line, and adds `library_list` and `library_get`;
  - the mail service uses `ics@1`.
- **Tests:**
  - RFC 5545's own recurrence examples (§ 3.8.5.3): 18 of them, DAILY through YEARLY, with
    BYDAY ordinals, BYMONTHDAY, BYYEARDAY, BYWEEKNO, BYSETPOS, UNTIL, and WKST;
  - DST at both edges in America/Chicago and Europe/London;
  - VTIMEZONE evaluation against IANA;
  - a Windows TZID;
  - Gmail-, Outlook-, and Apple-shaped REQUEST, REPLY, and COUNTER messages;
  - round trips (parse, build, parse);
  - fuzzing in the `fuzz` package;
  - a WAT box calling both libraries through `goober_lib`;
  - the Rust binding, built into a box.

## 8. Left out

- **Writing VTIMEZONEs.** Builders write IANA TZIDs, which every major client reads. A
  receiver that needs VTIMEZONE blocks can be served later by a `vtimezone: true` option.
- **VTODO and VJOURNAL.** They are parsed and passed through, without helpers.
- **Free/busy (VFREEBUSY).** Parsed, but not computed.
- **Locale formatting** ("Thursday, November 5 at 6 PM"). Boxes write their own words; `format`
  gives the parts. A `locale@1` library is the candidate.
