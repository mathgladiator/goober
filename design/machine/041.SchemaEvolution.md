# Schema evolution: the next version of a schema

> Status: machine-authored on 2026-10-31, at the human's request ("Let's do schema changes
> next", 040 § 5, decision 5). It builds `design/human/420.Migration.md` on v1's direct SQL
> (`008.Databases.md`). Where v1 can't do what 420 says, § 9 names it and the human doc wins;
> § 10 lists the choices 420 doesn't settle, each built the most conservative way, for the
> human to confirm or change.

## 1. What 420 asks for, and what v1 had

420 asks that a table change shape without any deployed box noticing. A schema version is
compared with the one before it, and each change is classified. Expansions, contractions,
index changes, and type changes the host can emulate are applied at once, in place. Anything
else is refused, unless an upgrade box forces it. A person is warned about every consequence
first.

Before this, v1 only expanded (008 § 3). A schema such as `guestbook2` could add tables,
columns, and indexes to a table that `guestbook1` made. A column a schema left out was left
alone, because schemas are partial. Every other change was refused. Nothing said that
`guestbook2` *followed* `guestbook1`, so a column that was left out could never mean "drop it".

## 2. `follows`: the next version

A schema names the version it replaces:

```json
{"schema": "guestbook2", "follows": "guestbook1", "tables": {...}}
```

- The followed schema must be stored, and not retired. Only one stored schema may follow any
  one schema, so each schema's versions form a line: core13, then core14, then core15.
- **The tables of `to` replace the tables of `from`.** A table, column, or index that `from`
  declares and `to` leaves out is dropped. A schema without `follows` keeps v1's partial,
  expand-only meaning.
- `from` is always the version just before `to` (420's "one step at a time"). A box pinned
  further back reaches `to` through each step in turn.

## 3. The kinds of change

`schema_check` and `schema_put` compare each table of `to` with the same table in `from`, and
answer the step: each change, its kind, and a sentence about it.

| kind | the changes | applied |
| --- | --- | --- |
| `expansion` | a new table; a new column that is nullable or has a default | at once |
| `contraction` | a dropped column; a dropped table | once a person approves the schema (§ 6), then at once |
| `indexing` | a new non-unique index; a new index of any kind on a new table; a dropped index; a non-unique index whose columns change | at once |
| `emulated` | int32 to int64; float to double; a column that comes to allow null; a `max-length` removed or raised | at once, with a warning |
| `forced` | a new column existing rows can't fill (not nullable, with no default); any other type change (narrowing, unrelated types); a column that stops allowing null; a `max-length` added or lowered; a default changed; a new unique index on an existing table | only through an upgrade box (§ 7), once a person approves the schema |
| `refused` | a primary key added, dropped, renamed, or retyped; a table's key moved to another column | never, not even forced |

**Renames.** A rename looks to the host like a drop and an add. When a table drops one column
and adds another of the same type, the step says that if this is a rename, the drop loses the
data. The fix is a new column plus a job (038 § 7), or an upgrade box.

**Consequences.** Every step lists 420's warnings that apply to it, in 420's words:

- data will be dropped;
- writes will be discarded;
- reads will be invented;
- values will be invented;
- values may not fit;
- rows will be rewritten.

`schema_check` also answers what the step would do to each database already holding `from`
(§ 8): how many rows hold data a contraction would drop, and whether a forced table has rows
waiting for an upgrade.

## 4. How a step is applied to a database

Each table has one physical shape: the newest applied version's shape, plus what older boxes
still need (§ 5). A step is applied in one transaction on each database, when the first
request that binds `to` opens that database. If `from` isn't applied there yet, it is applied
first (recursively, down the line), so every database goes through the same steps in order.

1. Expansions: `CREATE TABLE`, `ALTER TABLE ADD COLUMN`, as before.
2. Emulated changes: the table is rebuilt with the changed columns' new definitions. The
   rebuild creates a new table, copies every row, drops the old table, renames the new one,
   and recreates the indexes and the host's triggers.
3. Contractions: the dropped columns and tables become tombstones (§ 5).
4. Indexing: dropped indexes are dropped, and new ones are created.
5. The host's records are updated: `goober_columns`, `goober_indexes`, and the new
   `goober_dropped` (every dropped table and column, with the schema that dropped it, so a
   dropped name is never reused). `to` is recorded in `goober_schemas`.

Before a step that drops data, rebuilds a table, or rewrites rows, the host takes a snapshot of
the database (008 § 11) if `from` was already applied there. If the snapshot fails, nothing
changes. A database created fresh skips the snapshot, since its tables are empty.

A column or table that another applied schema, outside this line, also declares can't be
dropped or changed: that step is refused for that database, naming the schema.

## 5. Tombstones: what older boxes see

v1 boxes write SQL, so an older box's statements still name a dropped column. If the column
were removed, those statements would no longer prepare, and the box would notice. So a
contraction keeps the name and drops the data:

- **A dropped column** is set, in every row, to the value an older box would read. That value
  is the column's default in `from`, or null if the column was nullable, or else zero, `''`,
  or false. Two host triggers, one after an insert and one after an update of that column,
  set it back to that value. Writes to the column are dropped, and reads return the default,
  as 420 says. If the column had no default, the table is rebuilt so the column has one, so
  that inserts from newer boxes, which don't name the column, still work.
- **A dropped table** is emptied. A host trigger deletes every row inserted after that, so it
  reads as empty, and writes to it are dropped.
- Newer boxes can't name either one: their schema doesn't declare it, and their grants are
  checked against their schema.
- A tombstoned table goes for good when a person drops it in the panel, once nothing binds
  it (008 § 11). That drop also frees the name. A tombstoned column stays until physical
  removal is built (§ 10).

## 6. A person approves what drops or rewrites data

The human decided on 2026-10-30 that drops are a person's act in the panel (008 § 11). A
contraction drops data, and a forced step rewrites it. So a schema whose step contracts or
forces anything is stored by `schema_put` as **held**:

- It isn't applied anywhere, and a version that names it is refused at upload, until a
  `host:owner` focused on every tenant approves it in the panel's Database view. They read the
  step's sentences, type the schema's name, and say why.
- The approval is kept beside the schema as `$name.approved`. It is a line in the audit log
  (`panel.schema_approve`) and a row in the change log.
- Expansions, indexing, and emulated changes need no approval, as before.

## 7. Upgrade boxes

A forced step is carried out by an upgrade box, as in 420:

```json
{"box": "core14_upgrade", "mission": "Split users.name for core14.",
 "routes": {"upgrade": {"users": {"from": "core13", "to": "core14",
   "rows": {"name": "upgrade_users_row"}, "timeout-ms": 20}}}}
```

- **Pure.** An upgrade box has only `routes.upgrade`. It has no data strategies, external
  services, flags, or other routes. It may import host libraries, which are pure. It runs
  with `now_ms` 0 and a fixed random seed, so the same row always gives the same answer.
  `from` and `to` may be written with `.schema`, as 420 writes them.
- **Rows.** The handler gets one row in the `from` shape as its JSON body, and answers it in
  the `to` shape with a 200. Ids travel as strings. The primary key must come back unchanged.
- **Writes and reads are refused** (§ 10, decision 4). v1 boxes write direct SQL, so there are
  no named writes to upgrade, and an older box's reads can't be translated. Instead, 420's
  "old readers are covered, or gone" is met by "gone": an upgrade runs only once no box,
  active or disabled, whose current version is pinned to `from` or older, names the table.
- **Covers the step.** Every forced table of `to` has a route, and every route names a table
  of the step. All the box's routes name the same `from` and `to`.
- **`upgrade_dry_run {box}`** copies every database holding `from` and runs the
  whole step there. It answers each database's rows rewritten, and the rows that failed, with
  their keys and the reason. Nothing real changes.
- **`upgrade_start {box}`** (a changing tool) is refused until a dry run of the same box
  version passed and a person approved `to`. For each database holding `from`, the host takes
  a snapshot, then runs the step in one transaction while that database's writes wait. It
  builds each forced table in its new shape, runs every row through the handler, checks each
  result against the new shape's constraints, and swaps the new table in. If any row fails,
  that database rolls back and stays at `from`, and the answer names the row and why.
- **A database that missed the upgrade.** One created later, whose forced tables are still
  empty, applies the step on open with no rows to rewrite. One that has rows, such as one
  restored from a snapshot, refuses boxes pinned to `to` ("waits for its upgrade") until an
  operator runs `upgrade_start` again. This is 420's "new boxes wait for their data".
- A forced table loses its dropped columns physically, since no older box remains. Their
  names go into `goober_dropped` all the same.

## 8. The tools

| tool | kind | does |
| --- | --- | --- |
| `schema_check {schema}` | read | as before, plus `follows`'s step, its consequences, `held`, and `databases`: each database holding `from`, with rows that hold data to be dropped and forced tables' rows |
| `schema_put {schema}` | changing; stores, goes live where it only expands | as before, plus the step; a held schema says a person must approve it in the panel |
| `db_describe` | read | plus `dropped`: the tombstoned tables and columns, and the schema that dropped each |
| `db_unbound` | read | plus `held_schemas`: stored schemas waiting for a person's approval, with their steps |
| `upgrade_dry_run {box}` | changing, though it changes no data (it runs box code, on copies), like `job_dry_run` | § 7 |
| `upgrade_start {box}` | changing; goes live | § 7 |

Both upgrade tools touch every tenant's databases, so an operator focused on some tenants (030)
can't call them. The box guide's "Changing a schema" tells engineers all of this.
| panel `POST /api/write/drop {kind: "schema_approve"}` | a person's | approves a held schema (§ 6) |

## 9. Where v1 departs from 420

| 420 says | v1 |
| --- | --- |
| Emulated type changes are converted on the way in and out; a read that can't be converted fails, and null reads as the older version's default | Boxes read rows as SQL gives them. An older box sees a widened value as it is, and a null as null. The step's warnings say so. |
| An index a deployed `by_index` strategy names can't be dropped | `by_index` doesn't run in v1, so no box names an index. |
| A contraction removes the column or table | It becomes a tombstone (§ 5): the data goes, and the name stays for older boxes' SQL. |
| `writes` and `reads` handlers keep old boxes running through a forced change | Refused. A forced upgrade waits until no box pinned to `from` or older names the table (§ 7). |
| Each database upgrades holding its writer lease, offline databases before their next request | `upgrade_start` upgrades every database on the host, each in one transaction. A database with rows that missed it waits for another `upgrade_start`. |
| Every schema change is approved by a human | Only contractions and forced steps wait for a person (§ 6). Expansions, indexing, and emulated changes are applied as soon as a box binds them, as before (approvals per agent, 035, still hold `schema_put` when they're on). |

## 10. Decisions for the human

| # | decision | built |
| --- | --- | --- |
| 1 | How a schema names its previous version | An explicit `"follows": "core13"`. Without it, a schema keeps v1's partial, expand-only meaning, so no stored schema changes what it means. |
| 2 | Whether a contraction physically removes a column | No: it becomes a tombstone, held at the old default by host triggers (§ 5), so older boxes' SQL keeps working. Removing columns physically, once no box names them, would be a person's act in the panel. That isn't built. |
| 3 | Who lets a contraction or a forced step happen | A `host:owner` in the panel, after reading the step (§ 6), extending 2026-10-30's "drops are a person's act". |
| 4 | Upgrade boxes' `writes` and `reads` | Refused until boxes have named writes (`by_id`, `by_index`). Until then an upgrade waits for older boxes to be gone, so the table is unserved between disabling the old box and `upgrade_start`. |
| 5 | A changed default, and a new unique index on an existing table | Forced, not emulated: a new default would change what older boxes' inserts store, and a unique rule may not hold on existing data. |
| 6 | How an upgrade runs | Like a job (038 § 7): an operator runs a dry run on copies, then the real run, with a snapshot of every database first. |
