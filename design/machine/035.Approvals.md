# Approvals per connected agent

A design, built the same day. On 2026-10-30 the human said approvals would only slow them down
for now, but asked for "the ability to turn approvals on and off per connected agent in the
operator panel". This is that switch, and the queue it fills. It is the first piece of
305.Approvals.md's intent (a human approves what an agent wants to change), cut down to one
question: may this agent act alone right now?

## 1. The switch

- **Per connected agent.** An agent is how an operator call arrives:
  - `oauth:$email:$client`: an agent signed in through the operator OAuth issuer (023) as
    a person, one per client (Grok, Claude);
  - `token:$name`: a minted operator token;
  - `config`: the config's `operations-token`.
- **Off by default.** With no switch, every agent acts as before.
- **Kept** in `storage/operations/approvals.db` (`switches`), not in the host config: a person
  flips it in the panel without a deploy or a reload.
- **Who flips it:** a `host:owner` for any agent; a `host:operator` for the agents signed in as
  themselves. Observers can't. Each change asks for confirmation and is an `approvals_set`
  action in the change log and a `panel.approvals_set` line in the audit log.
- **Which agents are listed:** every agent that has called the operator MCP endpoint (recorded
  at most once a minute in `agents`), every operator token, and the config's token.

## 2. What waits

With the switch on, a `tools/call` from that agent:
1. is checked exactly as before: read-only roles, operator scope (030), and the tool's schema.
   A refusal is still a refusal, never a request;
2. if the tool is a read tool (the panel's list), runs as before; looking never waits;
3. otherwise isn't run. It's stored as a request (`requests`: the agent, the tool, its
   arguments up to 1 MiB, the request id), and the agent gets a successful result:

```json
{"pending_approval": 42, "tool": "content_put", "note": "...a person approves or denies this call in the panel..."}
```

`approval_status {id?}` (a read tool, never held) answers one of the agent's own requests, or
its latest 20, and whether approvals are on for it. A request not decided in 24 hours becomes
`expired`.

The hold is a hook in the MCP server's policy (`Policy.hold`), after the checks and before the
call, so batched calls are held one by one too.

## 3. Deciding

The panel's **Operators** view has an **Approvals** card: the agents with their switches, the
waiting requests with their arguments, and the last 30 decisions.

- **Who decides:** a `host:owner` any request; a `host:operator` their own agents' requests.
- **Deny** marks the request `denied`. Nothing runs.
- **Approve** claims the request (`running`, so two people clicking at once can't run it twice),
  then runs the tool **as the agent**: under the agent's scope and roles as they are at that
  moment, with the agent as the actor for every change. The result is stored with the request
  (up to 64 KiB) and shown in the panel; the agent reads it with `approval_status`.
- **The record:** `approval.approved` or `approval.denied` in the audit log; the call itself as
  an `operator.tool` line with `via: "approval"` and `approved_by`; and a change-log action by
  the agent naming the approver. The held call's own `operator.tool` line has outcome `held`.

## 3a. Hardening (2026-10-30, from the operator review)

- **Secrets aren't shown or kept.** A held call's arguments are shown with secrets replaced
  (`key_set`'s `value`, and any `password`, `secret`, `client_secret`, or `token`), to the person
  and the agent alike; once decided or expired, only that copy is kept.
- **What's approved is what runs.** A `source_deploy` or `source_build` held without `rev` is
  pinned to the head when it's held. The panel never cuts arguments silently: past 20,000
  characters it says how many more there are.
- **Revoked agents don't run.** Approving a request whose agent can no longer sign in (its token
  revoked, the config's token removed, its person no longer an operator) denies it instead.
- **No request is left running.** A request running when the host stopped becomes
  `interrupted` at the next start; a call that throws is recorded as failed.
- **Bounds.** At most 50 pending requests per agent.
- **Who sees what.** A person who isn't an owner sees and decides only their own agents'
  requests and switches; a switch an owner turned on stays until an owner turns it off.

## 4. What it isn't

- **Not 305's version registry or policies.** No diffs, no go/slow/shadow modes, no standing
  rules ("let this agent deploy pages but not boxes"). The switch is all or nothing per agent.
- **Not an approval of an agent's claim about a human.** Only a person signed in to the panel
  decides; an agent can't approve its own requests, or anyone's, through any tool.
- **Not for the panel's own writes**, which are already a person's.
- **No notification.** A waiting request is seen in the panel; nothing is mailed or pushed.

## 5. Tests

- **mcp:** a hold answers in the tool's place and isn't filtered.
- **host** (operator_scope_test): off by default; only an owner switches a token; read tools run
  while on; a write is held and changes nothing; a scope refusal stays a refusal; the agent
  sees its request; a helper can't decide a token's request; an approve runs it once as the
  agent, and a second approve is a 404; a deny never runs; the audit log names held, approved,
  denied, and the approver; off again, calls run at once.
