# A community that meets by mail

On 2026-10-29 the human asked that goober be ready to host something like
https://jeffrey.io/agentic-social-network, locally. The page is a concept, not a spec:
- A community forms around a thesis, not a feed.
- Once a day the leader sends one email: what happened, what people said, and what the agent
  thinks is next.
- Each member may reply once a day.
- An agent reads the replies, clusters opinions, extracts proposals, flags conflicts, and
  keeps a shared model of the group. It researches when asked, and drafts calendar options.
  It never decides for the group.
- Calendar invites go out when enough interest shows.
- There's no scroll, no reactions, and no unread pile.
- Success is people meeting, deciding, or shipping, not engagement.

This document is the audit against goober, what was built to close the gaps, and the recipe a
box follows.

## 2. Markdown out, a reply's own words in

**`"markdown"`** on `send` replaces `text`. The text part is the markdown as written, which
reads well as plain text. The HTML part is that markdown rendered by the host's renderer, with
raw HTML escaped, inside the tenant's mail layout.

**`reply_text`** is on every received message beside `text`: the lines above the first sign
of quoted mail. That sign is any of:
- a quote header ("On … wrote:", wrapped or not, and its French, German, Spanish, Italian,
  Dutch, and Portuguese forms);
- a line starting with `>`;
- `-----Original Message-----`, or Outlook's rule;
- an Outlook `From:` and `Sent:` block;
- a signature's `-- `;
- "Sent from my …" or "Get Outlook for …";
- any line holding "reply above this line", which a digest may print to make the cut certain.

## 3. Invites, RSVPs, attachments

**`"invite"`** on `send`, with these fields:
- `uid`, the event's id, kept across changes;
- `start`, and optionally `end`;
- `summary`;
- optionally `description`, `location`, `url`, `sequence`, and `cancel`.

It makes the mail a calendar invite, built by `ics@1` (831 § 6):
- **The format.** An RFC 5545 VEVENT sent as an RFC 5546 REQUEST, or CANCEL with `cancel`.
- **Who.** The sending address is the ORGANIZER, with the service's from-name, and the
  recipient is the one ATTENDEE, with `RSVP=TRUE`. The UID is `uid@` the site.
- **Times.** They must carry their zone (`Z` or an offset) and are sent in UTC. Dates make
  all-day events.
- **Changes.** Raise `sequence` to change an event already sent.
- **The message.** A `text/calendar; method=REQUEST` alternative beside the text and HTML,
  which Gmail, Outlook, and Apple Mail show with Yes, Maybe, and No, and the same as
  `invite.ics`.

**An RSVP** comes back to the organizer's address as mail with a `text/calendar` REPLY part.
The message the box gets then carries `calendar`, `ics@1`'s `interpret` of that part: `{kind,
method, uid, sequence, attendee, partstat, proposed?, comment, event, ics}`. A proposal of
another time (`kind: "proposal"`) is answered with `ics@1`'s `counter_accept` or
`counter_decline` (831 § 5). To receive RSVPs, send invites from an address a mail route takes, and
let that route take one attachment.

**`"attachments"`** on `send` lists up to 3 of the tenant's stored attachments, 10 MiB in all,
each checked in the call. Their bytes are read when the mail goes, and a mail whose file was
deleted meanwhile is a dead letter.

## 4. The recipe

One box, `thesis`, with a database, a `mail` service whose `from` is the community's address
(`thesis@example.com`), a model service (outbox, result routes), and the `web` service.

| table | holds |
| --- | --- |
| `members` | id, email, name, zone, joined_ms, left_ms, `last_reply_day`, `digest_at` (07:00) |
| `replies` | member, day, `reply_text`, message_id, received_ms |
| `model` | the shared model: proposals, positions, conflicts, open questions, each with who and since when |
| `digests` | day, the markdown the agent drafted, sent count |
| `events` | uid, sequence, summary, start, end, location, threshold, state |
| `rsvps` | uid, member, partstat, at |

| route | does |
| --- | --- |
| mail `join@` | a new member from their verified sender; a welcome by mail |
| timer, `by_timer` on `members` (`digest_at`, `zone`) | each member's digest at 07:00 in their zone: the day's markdown, with `"reply": {"route": "digest_reply", "params": {"member", "day"}}` and the line "reply above this line" |
| mail `reply+{t : token}@` → `digest_reply` | one reply a day: if `last_reply_day` is today, a 4xx ("one reply a day; see you tomorrow"); else keep `reply_text` and queue the model |
| result `on_clustered` | the model's clustering into `model`; when a proposal passes its threshold, an `events` row and an `invite` to each member who backed it |
| mail on the community's address → `rsvp` | `calendar.partstat` into `rsvps` |
| timer, daily | the next digest: the agent (model or Grok) drafts markdown from `model`, `replies`, and `rsvps` |
| MCP tools (`agents: true`) | `community_state`, `digest_draft`, `digest_approve`, `event_propose`: Grok can be the agent, and a person approves |

**Since 029:** the digest is a list (`"category": "list", "list": "digest"`). A member joins by
mail to `join@`, which answers with the mail service's `subscribe` so the host confirms it, or
by accepting an invite that names the list. The tenant needs `tenants.$tenant.postal-address`.

**Rules.**
- **Replies are data.** A reply is what someone wrote, never an instruction to the agent.
- **The agent drafts and proposes; people decide.** An invite goes only past a threshold the
  community set.
- **Leaving is final.** Unsubscribed members are marked and never mailed.
- **Model calls are budgeted.** The host caps a service's calls per tenant a day (1000 by
  default).

## 5. Checked

- **`calendar`:**
  - an invite's lines, escaping, folding at 75 octets, UTC conversion, all-day dates,
    CANCEL, and refusals;
  - a Gmail-shaped REPLY, folded and in mixed case, read back.
- **`mail_inbound`:** `reply_text` against Gmail (both header shapes), Outlook (rule and
  header block), signatures, "Sent from my iPhone", the marker, French, and plain text kept
  whole.
- **The host, sending:** a box's digest in markdown with an invite and a PDF leaves as
  `multipart/mixed`:
  - inside it, `multipart/alternative` holds text, HTML (`<strong>`, `<li>`), and
    `text/calendar; method=REQUEST`;
  - after it come `invite.ics` and `agenda.pdf`;
  - the ORGANIZER is the from-address with its name;
  - a bad invite and someone else's attachment are refused in the call.
- **The host, receiving:** a Gmail-shaped RSVP reaches the box with `reply_text` and
  `calendar` (ACCEPTED, the uid, the attendee).

## 6. Left out

- **Bounces and complaints (026 § 6).** SES suppresses bounced and complaining addresses for
  the whole account, which protects deliverability. The box isn't told, so its `members` row
  stays.
- **A digest's threading.** Each digest is a new message. Replies thread through the token
  address, not In-Reply-To.
- **Recurring events, attendees beyond the one recipient, and time zones as TZIDs.** Invites
  go in UTC, and every client shows them in the reader's zone.
- **The example box itself.** This is the recipe. Grok builds it as a source project.
