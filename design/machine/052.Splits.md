# 052. A/B splits and the traffic controller

Status: built 2026-11-04, a proposal until the human ratifies it. It is the first piece of
`design/human/310.Deployments.md` § Splitting traffic and § The traffic controller.

The human (2026-11-04), after the cleanup work: "It's fine that a live box can be dropped, but
I'd like the ability to train so let's get a/b traffic flow started."

## 1. What it does

A **split** sends a share of a live box's real requests to a **candidate** version, with real
effects, beside the live version. A person stays on one version for the whole split. The
**traffic controller** moves the share up a ladder while guardrails hold, rolls back on its own
when they don't, and promotes the candidate at 100%. An operator can also hold a share by hand,
change it, or end the split at any time.

## 2. Who lands where

Each request gets a bucket from 0 to 9999: the first 60 bits of SHA-256 of `salt | box | key`,
mod 10000. The candidate answers when the bucket is below the share (in basis points). The key:

| caller | key (310) |
| --- | --- |
| a signed-in person, on an HTTP route | `u:<domain>:<user id>` |
| anyone else, on an HTTP route | `a:<address>`, the address as the rate limiter counts it (an IPv6 /64 is one) |
| a person or agent calling a box's MCP tool on `/mcp` | `u:<domain>:<user id>` |

The salt is drawn when a split starts and kept for its life, so each new split assigns people
afresh, and a restart keeps everyone where they were. Raising the share only adds people to the
candidate: whoever was on it stays.

What splits, in this first version: HTTP routes and box MCP tools.
What stays on the live version: subscriptions (`routes.sse`), timers, mail routes, internal
calls from other boxes, jobs, identity events, outbox results, and upgrades. 310 asks for timers by a hash of their key and for
internal calls to follow the request that caused them; both are left for later (§ 9).

A try (`route_try`) runs the version it names, never a split's arm.

## 3. Which versions can split

Both versions run against the same data at once, and the router keeps the live version's tables,
so this version is strict. A split is refused, naming each difference, unless both versions:

- answer the same routes: every HTTP route, MCP tool, timer, internal, identity, mail, result,
  job, and upgrade route, with the same verb, pattern, and name (and mail address);
- bind the same data: every strategy with the same name, pattern, schema, database, and tenant;
- serve the same domains.

So a candidate changes behavior, not shape. A new route, a new table, or a new schema version
goes live the usual way (and 310's checker for "compatible" schemas and types can loosen this
later). The candidate must be stored (`version_upload {activate: false}`), not archived, and pass
the same manifest checks as a promote.

## 4. The controller

`boxes/<box>/split` holds the split through the host WAL: the candidate version, the share, the
salt, the mode, the ladder, the step's start, `step_minutes`, `min_requests`, the guardrails,
who started it and why, and its history (every share, when, by whom, why). The registry loads it
at start and resumes the split.

Every second, on the timer thread, for each split:

1. **Guardrails**, in every mode, judged once each arm has served 20 requests in the current
   step:
   - the candidate's 5xx rate is past the live version's by more than `error_rate_delta`
     (default 0.02, two points);
   - or its p99 is past `p99_ratio` (default 1.5) times the live version's, and by more than
     20 ms.

   Either one rolls the split back at once, saying which and by how much.
2. **The ladder**, in mode `ladder`: once `step_minutes` (default 30) have passed in the step and
   the candidate served `min_requests` (default 200) in it, the share moves to the next step. The
   default ladder is 1%, 5%, 25%, 50%, 100%. Reaching 100% promotes the candidate: it becomes the
   live version, and the split ends.

Each arm is counted twice: in the current step (reset at each step and each change) and since
the start: requests, 5xx, and latency in power-of-two buckets, from which p50 and p99 are read
(each at most twice the truth). The counts live in memory, so a restart starts them again; the
split itself continues.

A split ends when it is promoted or rolled back (by the controller or an operator), and also
when the box gets a new live version any other way (`version_promote`, an upload that
activates), is disabled, or is dropped. Its record is kept as `boxes/<box>/split-last`
(`split_report`'s `last`): with the totals when the controller or `split_stop` ends it; with
outcome `ended` and no totals when a new live version or a disable ends it (054). A drop leaves
none.

The candidate is kept from archiving while it serves (045 § 3.1).

## 5. The tools

All on the operator MCP, scope rule `kBox` (`split_list` is `kFiltered`). Starting, changing, and
ending are changing tools: audited (`split.start`, `split.set`, `split.step`, `split.promote`,
`split.rollback`), in the change log as operator actions (the operator's calls, one row each; the
controller's steps are the host's, audited only), and held when approvals are on.

- `split_start {box, version, why, share? | ladder?, step_minutes?, min_requests?, guardrails?}`:
  `share` (percent) holds a fixed share (mode `manual`); otherwise the ladder (percents, rising,
  ending at 100). Guardrails are `{error_rate_delta: 0 to 1, p99_ratio: 1 to 100}`.
- `split_set {box, share?, mode?: "ladder", why?}`: `share` holds that share and pauses the
  ladder (0 sends everyone back while the split stays); `mode: "ladder"` resumes it from the next
  step above the share.
- `split_stop {box, outcome: "rollback" | "promote", why?}`.
- `split_report {box}` (read): the state, both versions, the share, the mode, when the next step
  can come, the split's record (guardrails, ladder, history), and both arms side by side for the
  step and since the start; `last`, the previous split.
- `split_list {}` (read): every running split, both arms since the start.

The access log marks each request of a split box with `split: "live"` or `"candidate"`.

## 6. The panel

A box's page (`#/box/<name>`) shows a **Split** card while one runs: the share, the ladder and
when the next step can come, the guardrails, both arms side by side (requests, 5xx, p50, p99)
for the step and since the start, and the history. Once it ends, a **Last split** card says how
it ended, when, by whom, and why, with the totals. Look-only: the tools change splits.

## 7. Tests

- `boxes`: a split serves the candidate under its share and the live version above it; it is
  resumed after a restart with the same salt; the candidate is kept from archiving; promoting
  ends it; versions that move a route, the live version itself, and a box that isn't there are
  refused; disabling ends it.
- `host` (`splits_test`): at 50%, about half of 200 addresses get the candidate and each address
  always gets the same version; both arms are counted; a share of 0 sends everyone back; a
  rollback keeps the live version and records `last`; the ladder steps after its minutes and
  promotes at 100%; a candidate answering 500s is rolled back by the guardrail on its own;
  refusals (moved route, the live version, a share past 100, a falling ladder, stopping no split);
  scope rules, read tools.

## 8. How this sits with 310

- **Followed:** a stable hash so a person stays on one version (user id within a domain, else the
  address); a ladder like 1%, 5%, 25%, 50%, 100%; guardrails on errors and p99 relative to the
  live version that stop the ramp and move traffic back on their own; instant rollback because
  the live version keeps running; both versions side by side in the panel; manifests say nothing
  about traffic.
- **Not yet:** shadowing and the comparison report; cost per request as a guardrail; timers by
  key and internal calls following the trace; splits between two different boxes after an
  approved conflict (310's traffic controller holds those too).
- **Stricter for now:** 310 refuses splits across incompatible schemas or types. This refuses any
  difference in routes or data bindings, so the router and the data stay one shape.
- **Approval:** 310 says nothing serves traffic without approval. Here starting a split is a
  changing tool, held only when approvals are on for the agent, as uploads are today (305's
  policies aren't built).

## 9. Decisions for the human

1. **What splits now.** HTTP routes and box MCP tools only. Recommended: add subscriptions,
   timers (by key), and internal calls (following the caller's arm) next, once a real split asks
   for them.
2. **Strict compatibility** (§ 3). Recommended: keep it until 310's checker for compatible
   schemas and types exists.
3. **Default guardrails and ladder:** 2 points of 5xx, 1.5 times p99 (and 20 ms), 30 minutes and
   200 candidate requests a step. Recommended: keep; each split can set its own.
4. **Counts in memory.** A restart starts a split's counts again (the split continues).
   Recommended: keep; the five-minute traffic rows already persist per box.
5. **"train".** Read as the ability to try a new version on part of the traffic before it takes
   it all, and to drain the old one by promoting. If it meant something else (shadowing, or
   training an agent on the comparisons), say so.
