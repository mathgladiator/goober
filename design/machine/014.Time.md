# Time

> Status: machine-authored and **not ratified**. Recorded on 2026-10-26. It builds the timer
> half of `045.Time.md`: host-level timers on `every-ms` or `cron`, and data-driven timers
> over `by_timer` sources, firing per row on a cron in each row's zone or once at a row's
> `at-field`. The code is the `timers` package (cron in a zone) and `host/src/scheduler.cpp`.
> Where it departs from 045, §6 says so, and the human doc wins until it is updated.

## 1. Declaring timers

```json
{
	"data": {
		"sqlite3": {
			"devices_t": {
				"schema": "terminal1", "database": "terminal", "pattern": "by_timer",
				"table": "devices", "timezone-field": "timezone"
			},
			"reminders_t": {
				"schema": "jobs1", "database": "jobs", "pattern": "by_timer",
				"table": "reminders", "active-field": "on"
			}
		}
	},
	"routes": {
		"timer": {
			"sweep": { "name": "sweep", "every-ms": 60000 },
			"nightly": { "name": "nightly", "cron": "0 3 * * *" },
			"morning-briefing": { "name": "desk_morning", "source": "devices_t", "cron": "0 6 * * *" },
			"remind": { "name": "remind", "source": "reminders_t", "at-field": "remind_at", "timeout-ms": 500 }
		}
	}
}
```

| field | meaning |
| --- | --- |
| `name` | The route name; the box exports `goober_route_$name`. Unique across the host like every route name. |
| `every-ms` | 1,000 ms to 31 days. Host-level only. |
| `cron` | Five fields (§2). In the host's zone, or with a `source`, in each row's `timezone-field`. |
| `at-field` | A column of the source holding an instant: Unix ms, or RFC 3339 in UTC. Needs a source whose strategy has an `active-field`. |
| `source` | A `by_timer` strategy of the same box. |
| `timeout-ms` | Overrides the box's timeout for fires, 1 to 10,000. |
| `missed` | `once` (the default for cron) or `skip` (the default for every-ms). |

Exactly one of `every-ms`, `cron`, or `at-field`. `requirements` and `public` are refused,
since only the host calls a timer. `target` and `tenant-field` are accepted with a warning.

A `by_timer` strategy names `table`, and optionally `timezone-field` and `active-field`.
Its schema must be stored and must have those columns, and the at-field of any timer that
reads it. The box can't run SQL through it; only the scheduler reads it. Its schema is
applied to the database like a `sql` strategy's.

## 2. Cron

`minute hour day-of-month month day-of-week` with `*`, numbers, ranges `a-b`, lists `a,b`,
and steps `*/n` or `a-b/n`; day of week is 0 to 7, with 0 and 7 both Sunday. With both day
fields restricted, either one matching is enough, as in classic cron. Names (MON) aren't
accepted.

Times are wall-clock times in the zone, from the system's time zone database (C++20
`std::chrono`). As 045 asks, a local time that doesn't exist (spring forward) fires at the
next time that does, and one that happens twice (fall back) fires only the first time. A
row whose `timezone-field` doesn't name a real zone never fires.

## 3. The scheduler

A host thread ticks once a second. Each tick, for every active box, every timer, and every
tenant the box serves (§6):

- **every-ms**: due `every-ms` after it last fired; first due one period after the host
  starts.
- **cron**: due at the next match, computed once and kept until it fires. With `missed:
  once`, if the last completed fire is older than the schedule's latest match, that match
  fires once as soon as the host starts.
- **data-driven**: the source's rows are read again every 10 seconds (`SELECT *`, filtered
  by `active-field = 1`, at most 10,000 rows per source per tenant). A cron source fires
  each row in its own zone, keyed by the row's primary key. An `at-field` source fires every
  row whose instant has passed.

A fire is a request with no user: the request document has `method` `"timer"`, `path`
`"timer:$name"`, the row as JSON in `body` (or an empty body), and the tenant and one of its
domains. It runs through the same box call as an HTTP route, with its database writes in
one transaction, committed if it answers below 500, **or if it doesn't answer at all**, since
nobody is waiting for a response. Returning nonzero, trapping, or timing out rolls back.

- **No pile-ups.** A fire still running blocks the next one for the same timer, tenant, and
  row.
- **One-shot rows disable themselves.** When an at-field fire succeeds, the host runs
  `UPDATE table SET active-field = 0 WHERE pk = ? AND at-field IS ?` in the fire's own
  transaction, so a row moved while the fire ran stays on. A failed one-shot fire is tried
  again after a minute.
- **Progress is kept.** The last due time of each completed cron fire is stored in
  `storage/sqlite3/$tenant/timers.db`, so `missed: once` works across restarts. Nothing
  else is stored: the plan is rebuilt from the manifests, the config, and the rows.
- **Logged.** Every fire is an access-log line with `timer`, `tenant`, `due`, and `row`.

Tests drive `Host::timer_tick(now)` with an injected clock (045 § The rules of time), so a
day of schedules, with a restart, runs in a fraction of a second.

**Operator tools:** `timers_list` shows what is planned and when; `timer_run` fires a timer
now for one tenant, once per active row, which is how to try a 6am timer at noon.

## 4. The terminal's morning briefing

The desk box (`010.Terminal.md`) reads `devices` as a `by_timer` source in each device's
registered zone, and at 6am there puts a high-priority notification on the person's devices
when approvals are waiting ("3 approvals are waiting for you."), or removes it when none are.
This is 999 § Alarms's "a data-driven cron timer at 6am in each person's timezone", acting
about the person through data, never as them. `just terminal-e2e` fires it with `timer_run`
and finds it in the snapshot.

## 5. Tests

`timers/test/cron_test.cpp` covers parsing, 6am in two zones, both DST transitions, day
fields, steps, never-matching schedules, and instants. `manifest/test` covers timer and
`by_timer` parsing and refusals. `host/test/timers_test.cpp` covers periodic, per-row cron
across zones (and a row with no real zone), one-shot rows turning off once, catching up after
a restart, and the operator tools.

These tests never wait on the wall clock: they call `Host::timer_tick(now_ms)` with a
simulated clock, so a day of schedules runs in milliseconds. A fire's box sees the tick's time
as its `now_ms` (`CallOptions.now_ms`), and a failed one-shot row's backoff counts from the
tick, so nothing in a fire reads the real clock behind the test's back.

## 7. Trying a timer

`route_try {timer, at_ms?, row?}` fires a stored version's timer route once, dark versions
too, as the scheduler would, on copies of the tenant's databases (the same copies every write
try uses). `at_ms` is the fire's now, the present by default. A plain timer fires with no row.
A `by_timer` source fires the row named by `row` (its key, as `timers_due` names it), or else
the row due first from `at_ms`: the earliest at-field, or the next cron time in each row's
zone; a row that would never fire (no time, no real zone) is said so and not fired. A fired
at-field row is turned off in the copies, as a real fire turns it off. The answer has `due`
(and `due_note` when it isn't due yet at `at_ms`), `ok`, and the try's usual changes, grant
use, logs, and would-be deliveries.

## 8. The real clock, daily

The blocking suite simulates time; whether the real driver keeps real time is checked apart.
`goober-temporal` (`host-src/packages/host/temporal/`) starts a whole host, lets its timer
thread run for some minutes on the wall clock with an every-5-seconds timer, a minute cron, and
one-shot rows spread over the run, then reads every fire from the access log and checks it
against when it was due: on time (at most 2 seconds late, never early), none missed, none
twice, and the wall clock agreeing with the monotonic clock within a second over the run (a
clock step or a paused machine shows there). It writes `temporal-<start>.jsonl`, one line per
fire (`timer`, `row`, `expected`, `actual`, `drift_ms`, `verdict`) and a summary line, and
exits 1 on any failure. It isn't a ctest test. `just temporal [minutes]` runs it into
`temporal-logs/` (ignored by git); `host-src/tools/temporal-daily.sh install` installs a
systemd user timer that runs five minutes of it once a day, keeps every summary in
`temporal-logs/summary.jsonl`, and deletes runs older than 90 days.
