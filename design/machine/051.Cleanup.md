# 051. Cleanup: drops an agent asks for and a person approves

Status: built 2026-11-04, a proposal until the human ratifies it.

The human (2026-11-04): "For removing existing boxes, I want to see approvals in the
operational panel such that I can clean the machine up. I want to be able to approval database
drops, box drops. I'm not sure about the status of these, but I think it will be important since
I'm doing a migration and have no users, and I like things to be tidy."

## 1. Where things stood

- **Databases, tables, snapshots, and schemas** could be dropped (or retired) only by a
  `host:owner` in the panel's Database view, typing the name; refused while a box binds it; a
  snapshot first (008 § 11). The human had decided that drops are a person's act, never a
  tool's, so no MCP tool dropped anything and an agent could only point at what could go
  (`db_unbound`).
- **Boxes** could only be disabled (`box_disable`). Nothing removed one: its directory, every
  version, and its flags stayed, and its stored versions aged out only by the 400-day rule
  (045 § 3.1). A database a disabled box bound counted as bound, so it couldn't be dropped
  either. A migration left the machine full of boxes no one would run again.
- **Approvals** (035) held an agent's changing calls only when a person had turned approvals
  on for it, and any `host:owner` or `host:operator` could approve.

## 2. What changes

1. An agent can **ask** for a drop: `box_drop` and `db_drop`. The request always waits for a
   person, whatever the agent's approvals switch says. The decision stays a person's act, as
   the human decided on 2026-10-30; what's new is that an agent can put the request in front of
   them.
2. A box can be **dropped for good** (§ 3), by an approved request or by a person in the panel.
3. The panel gets a **Cleanup** view (§ 5): the requests waiting, every box and database with
   what dropping it would take and what blocks it, and what was dropped.

## 3. Dropping a box

A box drop:

- takes the box out of service at once, if it is live (as `box_disable` would);
- removes its disabled record;
- deletes every stored version's files, leaving each version's tombstone in
  `boxes/<box>/deleted/<version>.json` (module SHA-256 and size, who stored it, when it was
  live), marked `"dropped": true`, so `version_get` still says what it was;
- removes its flags for every tenant (`flags/<tenant>/<box>.json`);
- writes `boxes/<box>/dropped`: who, why, who approved it, what state it was in and at which
  version, when, and the versions deleted;
- is one WAL bundle for the registry's files, then one for the flags; it is in the audit log
  (`drop.box`) and the change log (action `box_drop`).

It leaves alone:

- **Its databases.** Data outlives code. A database only this box bound becomes unbound, and
  the drop's answer names it (`databases_unbound`), ready for its own `db_drop`.
- Its logs (they rotate out), its change log rows and tombstones (the record), its job runs.
- **Controls on its API** (`box:<name>`): they match nothing once it is gone. The check names
  the domains that have them (`controls_on_domains`), for `control_remove`.

It is refused while another box, live or disabled, calls it (`external` naming it with
`box`): that box would break. Drop the caller first, or deploy a version of it that no longer
calls.

The name stays usable. Uploading a box of that name again removes the `dropped` record and
starts afresh; the old tombstones stay beside the new versions.

There is no undrop. The nightly backups (14 days) and the local nightly copies hold the box as
it was; the source project, if the box came from one, can build it again.

## 4. The tools

- `box_drop {box, why?, dry_run?}` (scope rule `kBox`).
- `db_drop {tenant, database, table?, why?, dry_run?}` (scope rule `kTenant`): a whole
  database, or one table of it.
- `cleanup_report {}` (a read tool, `kHost`): every box not dropped, each with its check; every
  tenant's databases, each with its check; snapshots per tenant (how many, bytes); the boxes
  dropped (when, by, approved_by, why).

With `dry_run: true`, a drop tool is a read call: it changes nothing, never waits, and answers
the check:

- a box: `state` (`live`, `disabled`, `stored`, `dropped`, `none`), `version`, `versions`,
  `bytes`, `mission`, `domains`, `routes`, `databases` (each with `after`: unbound, or still
  bound by the other boxes named), `callers`, `controls_on_domains`, `takes`, and `blocked`
  (the reasons it can't go now);
- a database or table: `exists`, `bytes`, `tables` (with rows), `rows`, `bound_by`, `takes`,
  and `blocked` (each box and strategy binding it).

Without `dry_run`, the call always waits for a person, except in development mode (`--local`,
`just run`), where it runs at once and its records say `approved_by: "development mode
(--local)"` (the human, 2026-11-04):

- The hold (035's `Policy.hold`) is installed for every operator now. It holds a drop tool's
  call whatever the switch says, and anything else only when the switch is on.
- The agent gets `{pending_approval, tool, note}`; the note points at the Cleanup view.
  `approval_status {id}` gives the outcome. An undecided request expires in a day, and an agent
  may have 50 waiting (035).
- Only a `host:owner` approves a drop, and must type the name of what goes (`confirm_name`: the
  box, the database, or `database.table`), as a drop made in the panel requires. Anyone who may
  decide (`host:owner`, `host:operator` for their own agents) may deny one.
- Approving runs the call as the agent, under its scope and roles as they are then (035 § 3).
  The checks run again: what was unblocked when asked may be blocked when approved, and then
  the request ends `done` with the tool's error and nothing dropped.
- The tool itself refuses to drop unless the call is running under a person's approval on its
  thread (`approved_by_now`), so no other path that calls tools directly (change sets) can drop.
- A database drop takes its snapshot first and says where it is, as the panel's drop always
  has (008 § 11). The audit lines (`drop.box`, `drop.database`, `drop.table`) and change log
  rows carry `approved_by`.

The panel's own drop (`POST /api/write/drop`, `host:owner` only, typing the name) takes `kind:
"box"` as well, for a person focused on every tenant. Both paths run the same code.

## 5. The panel's Cleanup view (`#/cleanup`)

- **Waiting for you:** each drop request: what (box, database, or table, with its tenant), its
  state, which agent asked and when, its why, what it would take (checked when the page loads:
  versions and bytes, each database and what becomes of it, controls left), and what blocks
  it. **Approve…** (an owner, when nothing blocks it) asks for the name to be typed. **Deny** is
  for anyone who may decide. Other held calls are counted, with a link to Operators.
- **Boxes:** every box not dropped: state, versions, size, its databases, and what blocks
  dropping it; **Drop…** for an owner when nothing does (type the name, then a why).
- **Databases:** every tenant's: size, rows, who binds it; **Drop…** for an owner when no box
  binds it. Unbound tables, schemas, and snapshots stay in the Database view; the snapshots kept
  per tenant are summed here.
- **Dropped boxes:** when, by, approved by, why.

The Operators view's approvals list links a drop to the Cleanup view instead of approving it
there. The view refreshes every 15 seconds, so a request appears without reloading.

A tidy migration, then: the agent asks `box_drop` for each old box (a dry run first shows what
it takes), you approve them in Cleanup, and the databases they leave unbound show up for their
own `db_drop`.

## 6. Tests

- `boxes`: a dropped box leaves only tombstones marked dropped and its record; the other boxes
  still serve; a restart doesn't bring it back; dropping twice or a box that never was is
  refused; uploading the name again makes it a box again; a disabled box drops.
- `host` (`cleanup_test`): an agent's `box_drop` waits with approvals off; the panel's
  approvals list shows the check; an operator and an observer can't approve; the owner must type
  the name; once approved the box is out of service, 404s, its database is unbound, and the
  audit and the report say who approved it; a database drop that a box still binds is refused
  when approved and drops nothing; after the box goes, an approved database drop snapshots
  first; a box another box calls is refused until the caller goes; only an owner drops in the
  panel; a denied drop changes nothing; dry runs are read calls; every tool has a scope rule.
- `host` (`panel_test`): no tool drops a table or retires a schema; `db_drop` only asks.

## 7. How this sits with the other docs

- 008 § 11 said no MCP tool drops anything. A tool still drops nothing by itself: `db_drop` and
  `box_drop` ask, and a person decides. 008 is updated to say so.
- 035 said a held call waits only when a person turned approvals on. Drops are the exception:
  they always wait, and only an owner approves them. 035 is updated to say so.
- No human doc covers dropping boxes. 305 and 310 (versions and deployments) and 045 § 3.1
  cover versions aging out; a drop is the person's shortcut for a box no one will run again.

## 8. Decisions (the human, 2026-11-04)

1. **Only a `host:owner` approves a drop.** "Yes, only the owner can drop."
2. **Drops always wait, even for the config's token and minted tokens, except in development
   mode.** "Drops should also always wait for me except in development mode." Built: under
   `--local` a drop runs at once.
3. **A live box can be dropped in one step.** "It's fine that a live box can be dropped." Trying a
   new version on part of the traffic first is 052's A/B split.
4. **A box drop keeps its databases.** "Databases should be independent from database," read as
   independent from boxes.
5. **No undrop; backups are the way back.** "Back up is fine as well."
