# Reads, caching, and performance reports

On 2026-10-30 the human wrote: "ideally, GET should not write to a database as this also
enables caching as well. As part of the manifest, a cache policy would make sense as well since
we have pubsub support, so I want the ability to refine and tune products for ultra performance
with correct and consistent behavior being the default. That is, the engineering team can tune
specific portions well, and this also suggests MCP reports about performance should be
assembled as well."

This document has three parts. § 2 (GETs change nothing) is built. § 3 to § 5 (versions, the
`cache` field, conditional requests) are built since 2026-10-31, with the decisions in § 9;
§ 6 (subscriptions) and § 7 (performance reports) are not yet.

## 2. GETs change nothing (built)

A box route answering `get` or `head` runs read-only, exactly like a subscription's evaluation
(036 § 5):

- **Statements.** A statement that writes is refused before it runs; the box gets the error
  `a read changes nothing (a GET, a HEAD, or a subscription): this statement writes`.
- **Reads begin deferred.** No statement of a read-only request takes the write lock, so reads
  run beside a writer instead of queueing behind it (SQLite's WAL gives each reader a snapshot).
  Before this, a GET through a strategy that may write took the lock with its first statement.
- **Calls out.** Only reads: web reads, a person's mail preferences, and service methods whose
  effect is `none`. Anything that would be an outbox element is refused.
- **What it doesn't cover.** Other methods, and the host's own routes. Those change nothing on a
  GET (an invite's link shows a page, 029) except where a protocol requires it: a provider's
  OAuth redirect to `/goober/connect/callback` (034) is a GET that stores the connection, and it
  is single-use, bound to the state the host issued. The host's bookkeeping (the access log, live
  statistics) isn't tenant data.

The upload can't see this: SQL is text, and which statement runs depends on the request. The
refusal is at run time, and § 7's report counts refused writes per route so an operator sees a
box that tries.

**Links in mail.** A mailed link is a GET, and mail scanners open links nobody clicked. A link
that confirms, unsubscribes, or accepts shows a page whose button POSTs (the host's invites
already work this way, 029). The leads example box was the one box that confirmed on the GET;
it now shows a button.

## 3. Versions (built)

Caching needs to know when data changed. The host keeps a **version** per tenant database: a
number in memory, seeded at start with the time in microseconds (as the bus's sequence is, 036
§ 3, so it never goes backwards across restarts), and moved on every commit the host makes to
that database: a box's request, a timer, the host's own writes there, an operator's `db_exec`, a
schema applied. A rehydrate or restore restarts the host, which reseeds.

A write the host doesn't make (someone running `sqlite3` on the file) is caught by
`PRAGMA data_version` on a connection the host keeps open on each database a cached route reads
(at most 512 files; the least recently asked closes first). An entry records both numbers, and
either one moving makes it stale.

*As built:* the version is kept per database file in `db::Databases` (`version`, `bump`,
`data_version`). It moves when a request's connection commits with changes, when an operator's
`db_exec` changes rows, when a schema is applied, and when a table or the database is dropped.

A read-only request records, for each database it reads, the version **before** its first
statement begins the snapshot. A commit that lands between the two makes the recorded version
older than the snapshot, which only invalidates sooner; it never keeps a stale answer.

## 4. The `cache` field (built)

**The default stays as today: every GET runs the box.** The host adds an ETag from the answer's
bytes and answers a matching If-None-Match with a 304, which saves the bytes but not the work.

The reason it isn't more is that an answer can depend on more than data. The host can account
for most of that: the box version, content files and partials (each edit moves a version the
host keeps), and web reads (the host sees the call, and won't cache it). It can't account for
the clock: every call's input carries `now_ms`, so the host can't tell whether a box looked.
A page that says "5 minutes ago" changes with no write at all. Caching is therefore a promise
only the box's engineer can make: *this answer is a function of what the signature names, and
of the data*. The engineer makes it per route:

```json
"/menu": {"get": {"name": "menu", "public": true, "response": "json",
  "cache": {"by": "data", "fresh-ms": 60000, "check-percent": 1}}}
```

| field | values | meaning |
| --- | --- | --- |
| `by` | `"data"` (default) or `"wake"` | When an entry goes stale. `data`: when any database the evaluation read moves its version (§ 3). Correct whatever the box reads, and coarse: any write to the database invalidates it. `wake`: when a topic in `wake` moves (036), and only then. Narrow, and correct only if every write that changes the answer publishes one of those topics. |
| `wake` | 1 to 8 topic templates, as in 036 § 2 | Required with `by: "wake"`, refused otherwise. `{!user_id}` needs a route that isn't public. |
| `fresh-ms` | 1000 to 86400000, default 60000 | The longest an entry is used, whatever happens. It bounds how long a dependence on the clock can show. |
| `browser-ms` | 0 to 31536000000, default 0 | What browsers and proxies may keep. 0 sends `no-cache` with the ETag: they always ask, and § 5 answers cheaply. More is explicit staleness: `max-age` (`public` for a public route, `private` otherwise). |
| `check-percent` | 0 to 100, default 1 | The share of hits that also run the box and compare the bytes (§ 4.3). |

### 4.1 What an entry is keyed by

The signature, as 150 defines it and 036 § 5 uses for subscriptions: tenant, domain, box
version, route, path parameters, the query, the request headers the route declares, and who
asks (user id, roles, a person or which agent client, whether a host identity), or no one for a
public route. Seeing the working set is part of it (320). A cached route, like a subscription,
is shown only the request headers it declares: every header shown is part of the key, and each
browser's own would give it an entry of its own.

A public route has one entry for everyone; a route with requirements has one per person.

*As built:* the signature is the box's input with the request id left out. A cached route's box
sees exactly what is keyed:
- a GET and a HEAD share one entry (`method` is `get` for both);
- only the request headers the route declares (none, when it declares none);
- no `client_key`;
- for a public route, no user (`user` is null), whoever asks. The template and partials still
  render for the person asking, on every request, since the host renders them from the entry.

The box version is in the key, so a new version, a promotion, or a disabled box never serves
an old entry. Drafts (the working set, 320) aren't built, so they aren't in the key yet.

### 4.2 What is stored, and what isn't

- Stored: the box's `200` or `204` answer (before templates and partials, which render per
  request), with its headers, the versions (or topic sequences) it read, and the flags it read
  (039; a flag set since makes the entry stale), up to 1 MiB.
- Not stored: any other status, an answer that sets a cookie (a box can't, but the host checks),
  and an answer whose evaluation made any call through `goober_call` (a web read, another box,
  a service), since the host can't version what those read.
- Memory: a host budget (`cache.bytes` in host.json, default 256 MiB), at most a quarter of it
  per tenant, least recently used first out, by bytes.

### 4.3 Checking the promise

The promise in § 4 can be wrong: a box that uses the clock or randomness, or a `wake` list
that misses a table. So a share of hits (`check-percent`) also run the box, off the request's
path, and compare its bytes with the entry's. A mismatch replaces the entry, is counted per
route, and is written to the box's log with the route and a hash of the signature. § 7's
report names the route. A wrong declaration shows up as a number an operator sees, not as a
quiet bug.

### 4.4 Where it's declared

On the route in the box manifest, by the engineers who know what the answer depends on. A
config may override a route's `cache` (012's per-property priority), which is how an operator
A/B tests a lifetime, as 012 describes.

### 4.5 Refused at upload

`cache` on anything but a `get` route (`subscribe` routes have their own group answers, § 6);
`wake` without `by: "wake"`, or `by: "wake"` without `wake`; a field out of range; `{!user_id}`
on a public route.

## 5. Conditional requests (built)

For a route that declares `cache`, an If-None-Match that matches a live entry gets a 304
without waking the box: 037's promise, kept for the routes whose engineers made § 4's promise.

*As built:* the ETag is a hash of the bytes sent, after the template and partials render from
the entry, for cached routes as for the rest. The proposal's ETag from the signature and versions
would miss a template or partial edited since, and the person's own rendering; the bytes don't.
What the 304 saves is the box: rendering from the entry is cheap. The host sets Cache-Control
for a cached route (§ 4's `browser-ms`): `public` only for a public route asked by no one,
`private` otherwise; `no-cache` at 0, else `max-age`. Every answer's access-log line carries
`"cache"`: `hit`, `miss`, `stale`, or `304`.

## 6. Subscriptions (not built)

A subscription group (036 § 5) is already a shared answer for one signature, kept fresh by
wakes. A plain GET on a subscribe route whose group has a current answer can be served from
it. Left for later: a subscribe route's GET runs the box as before, and `cache` on a subscribe
route is refused at upload.

## 7. Performance reports over MCP (built)

Operators and their agents tune what they can measure. `uri_stats` (032 § 6) gives per-path
counts and latency percentiles; the reports add where the time goes and what to do about it.

### 7.1 What the host records

Built 2026-10-31. The numbers live in memory (`PerfStats`, `packages/host/src/perf.cpp`), so
they start over when the host restarts and cover an hour at most; the access log keeps each
call's split for longer.

- **Per call**, in the access log (a `perf` object: `queue_us`, `box_us`, `sql_us`, `lock_us`,
  `statement_us`, `commit_us`, `out_us`, `render_us`, `bytes_out`, `statements`,
  `refused_writes`, `cache`) and summed per tenant, box, and route by the minute for an hour:
  - waiting for a box thread;
  - running the box (minus the host calls it made);
  - SQL, split into waiting for the write lock (`BEGIN IMMEDIATE`), running statements, and
    committing;
  - calls out;
  - rendering (templates and partials);
  - bytes out;
  - the cache's answer: hit, miss, stale, 304, or a check (a field the cache fills, § 4–5,
    and `PerfStats::record_cache`, which also takes a check's mismatch);
  - writes refused under § 2.

  Queue time and rendering are known only for HTTP routes; a timer, tool, job, or mail call
  records the rest. A job's dry run records nothing. "Running the box" is the engine's time
  less the time inside `goober_sql` and calls out. SQL time is measured in the database layer:
  `BEGIN IMMEDIATE`'s wait is the lock wait, stepping is the statement time, and `COMMIT` is the
  commit time.
- **Per statement**, kept in memory for the last hour (six ten-minute slots), at most 2,000
  statements a host (the one run longest ago makes room): keyed by tenant, box, strategy, and
  the statement's text with whitespace folded, with the routes that ran it, and
  - count, total and maximum time, and rows returned;
  - SQLite's own counters: VM steps, full-scan steps, sorts, and automatic indexes
    (`sqlite3_stmt_status`), which show a missing index plainly.

### 7.2 The tools

All are read tools, so they never wait for approval (035) and follow operator scope (030).

- **`perf_report {tenant?, box?, window}`**:
  - **Per route:** count, p50/p95/p99, the average split from § 7.1, the cache's hit rate, 304s
    and check mismatches, refused writes, and its three costliest statements.
  - **Findings,** each with its evidence:
    - `cacheable`: a GET read 30 times or more in the window, with no cache declared, whose
      databases changed at most once per 20 reads: declare `cache`.
    - `missing_index`: a statement run 5 times or more with 100 full-scan steps a run or more,
      or any automatic index: the table and the columns its WHERE and ORDER BY name, as the
      index to add in a new schema version (a cheap reading of the text, not a parser).
    - `lock_wait`: a route averaging 5 ms or more waiting on the write lock, a fifth of its
      time or more.
    - `cache_mismatch`: a cache whose checks mismatch: the answer depends on more than its
      declaration says.
    - `get_writes`: a GET, a HEAD, or a subscription that tried to write.
    - `subscription_churn`: a subscription evaluated 20 times or more whose answer changed in a
      tenth of them or fewer: its wake topics move far more often than its answer.
- **`perf_statements {tenant, box?, sort, limit}`**: the statement table, sorted by total time,
  count, full-scan steps, or maximum time.

Both are read tools, on the panel's list. A focused operator names a tenant (030 `kTenant`).
- **`cache_status {tenant}`**: the tenant's entries and bytes, and per route the hit rate,
  mismatches, and evictions.
- **`cache_clear {tenant, route?}`**: a changing tool, so it waits for approval when that is
  on.

    - A GET read often whose databases rarely changed: declare `cache`.
    - A statement with many full-scan steps per row: the index it wants.
    - A route spending much of its time waiting on the write lock.
    - A cache whose checks mismatch: the answer depends on more than its declaration says.
    - A GET that tries to write.
    - Subscriptions evaluated far more often than their answers change.
- **`perf_statements {tenant, box?, sort}`**: the statement table, sorted by total time, count,
  or full-scan steps.
- **`cache_status {tenant}`** (built): the tenant's entries and bytes against its budget, and
  per cached route its declaration and, since the host started, hits, misses, stale entries,
  304s, entries stored, checks, mismatches, and evictions.
- **`cache_clear {tenant, route?}`** (built): a changing tool, so it waits for approval when
  that is on.

The panel's Performance view (028, 032 § 7) shows the findings, where each route's time goes,
and the statement table under its per-URI table.

## 9. Decisions

On 2026-10-31 the human asked for "the best caching decisions that elevate consistency and
product correctness". Taken in that light:

1. **Opt-in per route.** No route is cached unless it declares `cache`: correct by default,
   and every promise is one an engineer wrote down and review sees.
2. **The clock stays in the input** (no ABI change). Box SQL may no longer read the clock
   (`date('now')` is refused, the same day), so `now_ms` in the input is the only clock a box
   has, and `fresh-ms` bounds how long an answer that used it can show.
3. **`check-percent` defaults to 1**: a wrong promise becomes a number in `cache_status`.
4. **`browser-ms` is allowed, default 0** (`no-cache` with an ETag, so browsers always ask and a
   304 is cheap). It is the only staleness the host can't take back; § 7's `perf_report` lists the
   routes that use it.
