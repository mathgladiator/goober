# 047. Controls: rate, concurrency, and other limits per domain, API, and endpoint

Status: drafted by Claude on 2026-11-03 at the human's request, and built. The human's words: "I
want rate limiting, concurrent limits, and other operational controls per API per domain with the
ability to have endpoint override. Each override becomes something that can be monitored as well
to determine effectiveness."

On 2026-11-03 the human decided three of the questions put to them and added a fifth level, the
box's own limits per route (§ 13): "(4) I just want rate limit reached." "(5) don't need it
yet." "(7) operators can override at any time since a control may be bum." "Also, manifests can
set an override per operation as well so each box has fuel/limits that are enforced by the
host." This document says what was built from those words (§ 12 maps them to its questions).

This document follows 390.Quotas.md where the two meet. Controls belong to operators, not to
products, though a box may declare limits of its own that operators can always beat (§ 13). They have defaults with overrides that name only what differs. A refusal is clear and
counted. 390's quotas are what a tenant may consume over time (users, rows, bytes). Controls are
how fast and how much at once a domain's endpoints are reached. They are close to 390's "requests
per day" in "What comes later", but they are per minute and in flight, not per day (§ 12).

## 1. The shape

A control is a set of properties at one level. Five levels exist. For each property, the most
specific level that names it wins (012's per-property priority):

| level | where it is set | id it is monitored under |
| --- | --- | --- |
| host defaults | host.json `controls.defaults` (optional) | `defaults`, on every domain |
| a domain's defaults | `control_set {domain}` | `defaults` |
| an API on the domain | `control_set {domain, api}` | the API's name, like `box:shop` |
| a box route's own limits | the route's `limits` in the box's manifest (§ 13) | `box:<box>/<route name>`, like `box:shop/add_to_cart` |
| an endpoint override | `control_set {domain, endpoint: {id, match}}` | the override's `id` |

So host defaults < domain < API < the box route's `limits` < an operator's endpoint override. An
operator can always beat a box's limit with an override, from the tools or the panel (§ 9).

An **API** is one of these:

| API | what it covers |
| --- | --- |
| `box:<box name>` | the box's routes on the domain: HTTP routes, subscriptions, and CORS preflights for them |
| `content` | pages, templates, attachments, static files, `/goober/pwa/`, the keep-fragment script, and paths nothing answers |
| `mcp` | `/mcp` |
| `identity` | sign-in and the account (`/identity/`), OAuth (`/oauth`, `/.well-known/`), and the links a person follows from mail or to connect a service (`/goober/connect/`, `/goober/list/`, `/goober/unsubscribe/`, `/goober/mail/`) |

`identity` also takes the links in a person's mail. That way every path a tenant's domain serves
belongs to exactly one API. They are the person's own account pages, as sign-in is.

The host-wide per-client limit (`limits.requests-per-minute`) and the sensitive buckets (sign-in,
token, register, device, authorize, upload, mcp; 013's review) stay as the outer shield. They are
checked first and are unchanged. A control only acts inside them. The panel's origin, the operator
MCP endpoint, `/goober/health`, `/goober/ready`, `/goober/deploy`, redirect domains, and Stalwart's
mail hook are never controlled, because they belong to no tenant's domain.

## 2. Host defaults

```json
"controls": {
  "defaults": {"rate": {"per-minute": 600}, "concurrent": {"per-client": 8}, "mode": "enforce"}
}
```

`controls.defaults` takes the properties of § 3 and an optional `mode`, which is `enforce` by
default. It is checked when host.json loads, with the same errors the tools give. It applies under
every domain's own defaults and changes on a reload (SIGHUP). Domains' own controls are never in
host.json: tools set them (§ 4), as 039's flags are set.

## 3. Properties

The keys are platform keys, so they are hyphenated. A control names only the properties it
changes. Each property is replaced whole: a `rate` at an endpoint is that endpoint's whole rate,
not a merge of its fields with the domain's. Any property may be `"off"`, which lifts it at that
level and below.

| property | value | refused with |
| --- | --- | --- |
| `rate` | `{"per-minute": 0.1 to 1000000, "burst": 1 to 1000000, "by": "client" \| "user" \| "all"}`. `burst` defaults to a quarter minute's worth, at least 1. `by` defaults to `client`. | 429 and `Retry-After` (the seconds until a token is there) |
| `concurrent` | `{"max": 1 to 100000, "per-client": 1 to 100000}`, one or both; `per-client` at most `max` | 503 and `Retry-After: 1` |
| `body-max-bytes` | 1 to the host's `limits.body-max-bytes` | 413 |
| `timeout-ms` | 1 to the host's `limits.timeout-ms.max` | not refused: a box call it bounds fails as any timed-out call does |
| `fuel` | 1 to the host's `limits.fuel` max: the wasm fuel one box call may burn | not refused: a call that runs out traps (`out_of_fuel`, a 500), as any call out of fuel does |
| `closed` | `true`, or `{"status": 503 \| 410 \| 451, "retry-after-s": 0 to 86400, "message": one line of at most 300 bytes}`; `status` defaults to 503 | its status, with `Retry-After` when given; answered without waking anything |

- **`by`.** `client` is the client's address as the host-wide limit keys it (`rate_key`: an IPv4
  address, or an IPv6 /64). `user` is the signed-in account, or the bearer token's subject, and
  the client when nobody is signed in. `all` is one bucket shared by everyone the control's scope
  covers.
- **Scope.** A `rate` or `concurrent` counts within the scope of the level that supplied it. On
  an endpoint override, that is the endpoint. On an API's control, it is every request of that API
  on the domain. On the defaults, it is every controlled request on the domain.
- **Only lower.** `body-max-bytes` and `timeout-ms` can't pass the host's limits. The host reads a
  body up to its own limit, then a control refuses one larger than the control's. A box call's
  timeout is the lower of the control's and the box's own. `timeout-ms` bounds the box calls a
  request wakes: a box's HTTP route, or a box tool on `/mcp`. A request that wakes no box ignores
  it.
- **closed** answers before any box, page, or identity screen runs, through the host's error
  page. The `message` shows on the page (the template gets `{{message}}`) and in the JSON answer
  as `"message"`.
- **fuel** replaces the call's fuel, which is otherwise the box's `behavior.fuel` resolved within
  the host's `limits.fuel`. Unlike `timeout-ms`, it isn't the lower of the two: the most specific
  level wins, so an operator's override can give a box's route more fuel than its own `limits`
  allow, up to the host's max, and `"off"` gives the box its own fuel back. It reaches the call as
  `goober-control-fuel`, as `timeout-ms` does. An observed `fuel` is shown in `effective` and
  counts nothing, since a call's fuel is known only when it ends.

**Mode.** Every control has a `mode`: `enforce` or `observe`. An observed control refuses
nothing. It counts what it would have refused, on its own buckets, so watching changes no answer.
For each property:

- the **enforced** value comes from the most specific level in `enforce` mode that names it;
- the **observed** value comes from the most specific level in `observe` mode that names it, when
  that level is more specific than the enforced one.

So an override started in observe leaves the enforced levels below it working while it is
watched. An observed `timeout-ms` counts the calls that took longer than it.

Refusals are host errors. They get the site's error page, or JSON for an API caller (a bearer
token, or `Accept: application/json`), the same as every other host error. Checks run in this
order: closed, then the body, then the rate, then concurrency. Concurrency comes last because it
holds a slot.

**What a refused client reads.** The human, 2026-11-03: "I just want rate limit reached." A
client is never told which control refused it. A `rate` or `concurrent` refusal says only "rate
limit reached": the error page shows the status and those words (the template gets them as
`{{message}}`), and the JSON is `{"error": "rate limit reached", "status", "request_id"}`. No
control id, level, API, or bucket is in the body or a header; the access log keeps them (§ 10).
`rate` answers 429 with `Retry-After`, and `concurrent` 503 with `Retry-After: 1` (300 says 503
when busy). `body-max-bytes` answers 413 as before, and `closed` keeps the operator's message.
The host's older limits say the same words: the host-wide per-client limit and its sensitive
buckets, the anonymous-write budget, the open-subscription caps (429 each), and the operator
endpoint's bad-token budget.

## 4. Endpoint overrides

An override has three parts:

- an `id` the operator chooses: letters, digits, and `_`, not starting with a digit, at most 64,
  and not `defaults`, `content`, `mcp`, or `identity`;
- a `match` of `"METHOD /path"`;
- an optional `api`, which makes it match only that API's requests.

**Match.** `METHOD` is uppercase letters, or `*` for any. `GET` matches HEAD too, as routes do.
The path has one space before it and starts with `/`. Its segments are literal, `{name}` (exactly
one segment), or `{name*}` (the rest, possibly empty; last only). 012's patterns are the same.
Paths are compared after the host normalizes them: percent-decoded, with no trailing slash. So
`/docs/{rest*}` matches `/docs`, `/docs/a`, and `/docs/a/b`. The query is never matched.

**Tools.** `"TOOL /name"` matches a box tool call on `/mcp` (the tool `name`; `{rest*}` matches
every tool). A tool call meets only its tool's own `limits` (§ 13) and `TOOL` overrides: the
`/mcp` request that carries it has already met the domain's defaults, the `mcp` API's control,
and any `/mcp` override. A `TOOL` override never matches an HTTP request, and a `*` override
never matches a tool call. It takes no `api`.

**Specificity.** When several overrides match a request, the most specific wins: more literal
segments, then fewer wildcards, then a named method over `*`, then the order they were listed in.
Only the winner applies and is counted. Overrides are compiled and sorted once, when they change,
so a request takes the first that matches.

A domain has at most 100 overrides and 50 API controls.

## 5. Setting them

All four tools are scoped by the domain's tenant (030): `control_set`, `control_remove`, and
`control_report` take rule `kDomain`, which resolves the domain to its tenant; `control_list` is
`kFiltered`. Approvals (035) hold `control_set` and `control_remove` for an agent. A person makes
the same changes in the panel without waiting (§ 9).

- **`control_set {domain, api?, endpoint?: {id, match}, set?: {...}, mode?, why}`.** This is a
  changing tool. With neither `api` nor `endpoint`, it sets the domain's defaults. With `api` and
  no `endpoint`, it sets that API's control. With `endpoint`, it sets an override, and `api` then
  narrows the override to that API.
  - `set` merges into the control. A key replaces its property. `null` removes the property from
    this control.
  - `mode` is required for a new control, and the tool's description says to start in observe.
  - `match` is required for a new override.
  - `why` is one line of at most 300 bytes, and it is required.
  - Checking is strict. An unknown key, a wrong type, a value out of range, a match that doesn't
    parse, a redirect domain, or an unknown domain is refused with an error naming the key, and
    nothing is stored.
  - It answers `id`, `level`, `mode`, `set`, `before`, and `effective`. `effective` gives each
    property's enforced and observed value and where it comes from.
  - It adds notes, never refusals, in two cases: an API names a box not live on the domain yet,
    and a new control is enforced without being observed first.
- **`control_remove {domain, id, why?}`.** This is a changing tool. `id` is `defaults`, an API's
  name, or an override's id. The control's rows stay until they age out (§ 6), and its history is
  kept under `removed`, the newest 50. A box route's own limits (`box:<box>/<route>`) are refused
  here, with the way to beat them: an override that matches the route.
- **`control_list {domain?}`.** This is a read tool. For each domain it gives `host_defaults` and
  then each control: the domain's defaults, each API's, each box route's own limits, then each
  override. Each control has `id`, `level` (`host`, `domain`, `api`, `box`, `endpoint`), `api`,
  `match`, `mode`, `set`, `effective`, `in_flight` (now), `changes`, and `last_change`. An override
  that names no API shows its effective values without an API's level, because which API's control
  applies depends on the request. A box route's control also has `from: "manifest"`, `box`,
  `version`, `what` (like `POST /cart` or `TOOL /search`), and `limits` as the manifest wrote them;
  a route no client calls (a timer, say) adds a `note` that its fuel is enforced at each call and
  nothing is counted.
- **Kept.** Each domain's controls are one file, `storage/controls/$tenant/$domain.json`, written
  through the host WAL as 039's flags are. They are durable, carried in the nightly and the
  increments (019), and outside anything a box can write. Each change is a `control` row in the
  change log with the file before and after, and an audit line (`control.set`, `control.remove`;
  `panel.control_set`, `panel.control_remove` when a person made it in the panel) with the before,
  the after, and the why. Each control keeps its newest 20 changes (`at_ms`, `by`,
  `why`, `before`, `after`) for its report.
- **Live.** A change compiles the domain's whole file, puts it in the gate, and the next request
  sees it, with no restart. A file that doesn't compile is refused whole. A stored file that
  doesn't compile at start (edited by hand) is a startup note, and that domain runs with host
  defaults only.

## 6. Monitoring every control

Each domain's defaults, each API's control, each box route's own limits (`box:<box>/<route name>`,
on each domain the route answers), and each override is its own monitored id. The gate
counts in memory, in five-minute buckets per (domain, id). It hands each bucket to the traffic
rollups when the bucket ends, and the host's stop flushes the open ones. Rows are kept 7 days in
`operations/traffic.db` within `limits.traffic-bytes`, like every other rollup (045 § 3). Each row
holds:

| field | meaning |
| --- | --- |
| `matched` | requests the control met (each level in a request's chain counts it) |
| `allowed` | of those, not refused |
| `rate`, `concurrent`, `body`, `closed` | refused, by reason, counted on the control that supplied the refusing value |
| `would` | requests an observed property of this control would have refused (once per request) |
| `clients`, `would_clients` | distinct clients refused, or would-refuse: a 256-bit linear-counting sketch, so rows union and windows add up (approximate, saturating at 1000) |
| `top_client`, `top_n` (and `would_top`, `would_top_n`) | the busiest single client's refusals, named by the host's keyed address hash (032), never an address |
| `peak` | the most of the control's requests in flight at once |
| `hist`, `n5` | latency of the allowed (the traffic histogram's √2 buckets), and how many answered 5xx |

In-flight slots are held by a ticket that travels with the request's finish. Calling it counts
the latency and status and gives the slots back. A finish path that never calls it (a handler that
threw) gives them back when the ticket is dropped. So every path out of a request, errors
included, releases what it held.

## 7. Reports

`control_report {domain, id?, window: 1h | 12h | 7d}` is a read tool. It gives one report per
control, and removed ones while their rows last. Each report has these parts:

- **Series.** A point per step (5 minutes, 10 minutes, or an hour) with matched, allowed, refused
  and each reason, would, peak, p50 and p99 of the allowed, and 5xx.
- **Totals.** These add `refused_ratio`, `would_ratio`, `clients_refused`, `top_client_share`
  (the busiest client's share of refusals, grouped across buckets), `would_clients`, and
  `ratio_5xx`.
- **History** (newest first) and `last_change`.
- **Effect.** This compares equal spans before and after the last change. A span runs from the
  change to now, at most 3.5 days, because 7 days of rows must hold both. For each side it gives
  requests, refused, would, p99, and the 5xx share. A control created by its last change has
  nothing counted under it before, and the effect says so.
- **Verdicts.** These are plain lines, most telling first:

| verdict | when |
| --- | --- |
| "never matched in 12h: check the match, or nothing called it" | nothing matched |
| "closed: answered N requests without waking anything" | it closed something |
| "refusals come mostly from one client (X% of N): shielding" | at least 10 refused and one client holds half or more |
| "refuses many clients (M, X% of requests): may be too tight" | refused 10 or more distinct clients, or 3 or more and a fifth of what matched, and no single client holds half |
| "refused N of M (X%) from K clients: too few to judge yet" | it refused some, and neither line above applies |
| "matched N but never refused (loose or not needed)" | enforced, matched, refused nothing |
| "observe: would have refused X% (N of M) from K clients" | observed, and it would have refused some |
| "observe: would have refused nothing (M requests): loose, or safe to enforce" | observed, and it would have refused none |
| "X% of the allowed answered 5xx: what is behind it is struggling" | at least 20 allowed and 5% or more 5xx |
| "removed: its rows stay until they age out" | the control is gone |

## 8. /goober/ready

`health.controls` holds three ratios over all requests in the last five minutes:
`refused_ratio`, `would_refuse_ratio`, and `matched_ratio`. The endpoint is public, so it gives
ratios only and names no tenant or domain. The Prometheus text carries
`goober_control_refused_ratio` and `goober_control_would_refuse_ratio`.

Verdicts don't warn here. The human, 2026-11-03, on alerts: "don't need it yet." (§ 12, 4.)

## 9. The panel

The Controls view (`#/controls`) has a domain picker. For each control it shows the mode, the
last change, and the effective values with where each comes from. It then shows the report's
totals and verdicts, a chart of allowed and refused by reason, a would-refuse chart for observed
controls, latency, and the effect. The change log's kind filter has `control`.

**A person changes any control here, at any time.** The human, 2026-11-03: "operators can override
at any time since a control may be bum." A person with `host:owner` or `host:operator` (not
`host:observer`, who gets 403) may set, change, switch to observe or enforce, or remove any
control of a domain in their scope (030). It is a person's act, like the panel's drops (028 § 2):
- per control, a mode toggle (Switch to observe, or Enforce), Edit (the properties as JSON, the
  match, the mode), and Remove, each with a why that is required;
- "Add a control", an override by default (id, `match`, an optional `api`, mode, properties),
  or an API's control or the domain's defaults;
- on a box route's own limits, "Override…", which opens the form with the route's match and its
  limits filled in, since those come from the manifest and are beaten, never edited.

The page posts `POST /api/write/control_set` and `/api/write/control_remove` with the tools'
arguments. The host runs the same change the tools make, as `panel:<email>`, so it is in the
control's history, the change log (by the person), and the audit log as `panel.control_set` or
`panel.control_remove` (a refusal too). It never waits for approvals: approvals hold an agent's
calls, and this is a person.

## 10. On the request path

The hook is one call in `Host::handle`, after the host-wide shield and the tenant's path are
known, and before anything is queued. The logic is in the `controls` package (`spec`: parsing,
the matcher, the merge; `gate`: buckets, in-flight counts, rows; `report`: series and verdicts)
and in `host/src/controls.cpp`.

- A domain with no controls and no host defaults costs one map lookup, and one look at the box
  limits compiled for the live set (two shared pointers copied under short locks; a set with no
  route limits, or none on this domain, stops there).
- Box routes' own limits are compiled once per live set (an upload, a promotion, a disable), keyed
  by the route, never per request. When some live box on the domain declares them, the request's
  route is matched once to find its limits.
- A request on a controlled domain walks its domain's sorted overrides, then does a few map
  operations under one lock. It reads no disk.
- The request's API is worked out only when an API control, or an override naming an API, exists.
- `by: user` needs the account. Sessions and tokens are in SQLite, and network threads only route
  (host QUALITY.md), so the account is looked up on a worker and kept a minute per credential
  hash. Until it is known, the request counts as its client's. A made-up credential is never an
  account, so it can't open a fresh bucket.
- An enforced `timeout-ms` travels to the box call as an internal request header
  (`goober-control-timeout-ms`), and an enforced `fuel` as `goober-control-fuel` (`0` when lifted).
  Incoming `goober-control-*` headers are stripped, and boxes never see `goober-` headers.
- A box tool call on `/mcp` has its own check in `mcp_routes.cpp`, after the input is checked and
  before the box wakes, with the tool's limits and `TOOL` overrides (§ 4). Refused, the tool
  answers an error result with "rate limit reached" (or "the input is larger than this tool
  takes"), and the agents log records the status.

The access log's line for every controlled request has `"control": {"id", "outcome": "allowed"
| "refused", "reason"?, "would"?: ["id:reason"], "api"?}`. `id` is the most specific control the
request met, or the refusing one. A refusal is `error_by: "host"` and counted as `(refused)` in
the live statistics, as other host refusals are.

## 11. Departures from the request, and why

- **Observed levels are checked beside the enforced ones, never in their place.** If an observed
  override replaced the enforced default below it, watching would loosen protection. So the most
  specific enforced value still applies, and the observed one is counted on its own buckets.
- **`identity` also takes the mail and connection links** (`/goober/connect/`, `/goober/list/`,
  `/goober/unsubscribe/`, `/goober/mail/`), so every path on a domain is in one of the four APIs.
- **Properties replace whole.** A `rate` is not merged field by field across levels, because a
  burst tuned for one per-minute is wrong for another.
- **`"off"`** lifts a property at a level, which the request didn't name. Without it, an endpoint
  couldn't escape a domain-wide `closed` or rate (an open health check while the shop is closed,
  say).
- **A control with no properties is allowed.** It changes nothing and is still monitored, which
  is a way to watch an endpoint before deciding anything.
- **`control_remove` takes an optional `why`,** for the audit line and the history.
- **The scope rule is `kDomain`** for set, remove, and report. It is the existing rule that
  resolves a domain to its tenant, which is what was asked. `control_list` is `kFiltered`, so a
  focused operator sees only their tenants' domains.
- **The effect can't see before a control existed.** Requests are counted under a control's id
  only once it exists, so a new override's "before" is empty. Compare with its API's or the
  domain's report for the time before. (048's heat study is the tool for looking first.)
- **The busiest client is approximate across buckets.** Each bucket keeps its own busiest client,
  of at most 1024 tracked. A window groups those, which is right whenever one client dominates,
  and that is the case the verdict is for.

From the decisions of 2026-11-03 (§ 13):

- **Operators override at any time, not within manifest bounds.** 300 (Instances and queues) says
  "The manifest declares the defaults and the bounds, and an operator can tune within those
  bounds from the panel without a deployment", and "Changing a bound itself ... goes through the
  approval queue." The human now says operators override at any time: an endpoint override beats a
  box's limits, past them either way, with no approval for a person in the panel. 046 § 11 lists
  it too.
- **150 lacks `limits`.** 150.DeepManifest.md's route fields don't list `limits`; it is a field
  150 lacks, as 300's `queue` was before it. design/human/ isn't edited here.
- **`fuel` became a control property**, so that an operator's override can beat a box's fuel as it
  beats the rest. It replaces the call's fuel rather than only lowering it (§ 3).
- **A tool's own limits act inside `/mcp`'s.** A tool call has already met the domain's levels
  on the `/mcp` request, so its `limits` add to them rather than replace them; for a tool, a box's
  looser rate doesn't loosen the `mcp` API's. Only a `TOOL` override beats the tool's limits.
- **A box's limits may be looser than the domain's or an API's.** That is the order the human gave
  (API < the route's `limits`), so a box can lift its own route above an operator's API control;
  only an override is sure to win. § 12, 5 asks whether that should stay.
- **No `"off"` and no `closed` or `timeout-ms` in a manifest.** A box declares limits; lifting one
  or closing a route is an operator's. A route keeps its own `timeout-ms` where it was.
- **`limits.body-max-bytes` beside 037's `max-body-bytes`.** An HTTP route may give both. 037's is
  the route's contract and no control lifts it; `limits.body-max-bytes` is a control an override
  can beat. § 12, 6 asks whether one should go.
- **Per tenant per route, counted per domain.** A box route's budget and its rows are kept per
  (domain, route), as every control's are. A tenant answers on one domain and its redirects (which
  are never controlled), so that is per tenant; a tenant with two primary domains would have two
  budgets.
- **Rate and concurrency only where a client calls.** Timers, internal routes, mail, results,
  identity routes, jobs, and upgrades take only `fuel`: the host or another box calls them, at a
  pace the host sets or the calling route's limits already bound.

## 12. Decisions for the human

Decided on 2026-11-03 (the human numbered them in conversation; mapped here):

- **3. Who sees the refusing control's id?** "(4) I just want rate limit reached." Nobody: a
  refused client reads "rate limit reached" (§ 3), the older limits too.
- **4. Alerts.** "(5) don't need it yet." No warnings in `/goober/ready` for verdicts (§ 8).
- **Operators override.** "(7) operators can override at any time since a control may be bum."
  The panel's editing (§ 9), and an override beating a box's own limits (§ 13).

Still open:

1. **Requests per day (390's "later").** Controls are per minute and in flight. A per-day budget
   per domain would be one more property (`daily`), counted in the same rows. Should it be added
   now, or wait for 390's quota work?
2. **Should host defaults be monitored per domain?** Today the host's defaults count as each
   domain's `defaults`. A separate `host` id would show the host's own rule apart from the
   domain's, at the cost of another row per domain.
5. **May a box's limits be looser than the operator's API control?** The order given puts the
   route's `limits` above the API, so a box can loosen what an operator set for its API until an
   override says otherwise. I recommend keeping it (the box knows its routes) and showing it: a
   box limit looser than its API's could be a note in `control_list`. Not built.
6. **Keep both body limits?** 037's `max-body-bytes` (the route's contract) and
   `limits.body-max-bytes` (a control an operator can beat). I recommend keeping both and saying
   so in the box guide, which it does.

## 13. A box route's own limits

The human, 2026-11-03: "Also, manifests can set an override per operation as well so each box has
fuel/limits that are enforced by the host." A route in a box manifest may declare `limits`, in
this document's vocabulary:

```json
"/cart": {"post": {"name": "add_to_cart", "public": true,
  "limits": {"fuel": 5000000, "rate": {"per-minute": 30, "by": "user"},
             "concurrent": {"max": 4, "per-client": 1}, "body-max-bytes": 4096}}}
```

| key | takes | where |
| --- | --- | --- |
| `fuel` | a whole number, 1 to the host's `limits.fuel` max | every route: http, sse, mcp tools, internal, timers, identity, mail, results, jobs, upgrades |
| `rate` | § 3's `rate` | http routes, mcp tools, sse subscriptions |
| `concurrent` | § 3's `concurrent` | http routes, mcp tools, sse subscriptions |
| `body-max-bytes` | 1 to the host's `limits.body-max-bytes` | http routes other than get and delete, mcp tools (the input's bytes) |

- **Checked strictly at upload.** The manifest package checks the shape: an object, only the keys
  the route's kind takes, no `"off"`, `fuel` a whole number of at least 1, `timeout-ms` refused
  with a pointer to the route's own. The host's manifest check, which runs on every upload, store,
  promotion, and `version_upload` dry run, checks the values with § 3's parser against the host's
  own limits, so the ranges are one code's. Errors name the route: `route add_to_cart
  limits.rate.per-minute must be 0.1 to 1000000`.
- **Compiled at version load.** When the live set changes, each gated route's limits become a
  control at level `box`, always `enforce`, keyed by the route. A route whose limits no longer fit
  the host (its `limits.fuel` was lowered since) runs without them, and `control_list` says why.
- **Enforced per tenant per route** by the gate (§ 6, § 10), in the merge of § 1. `fuel` on a route
  no client calls is the call's fuel directly.
- **Shown.** `version_get` gathers them as `limits: [{route, what, id, limits, note?}]`.
  `version_diff` lists each property's change: a limit added or lowered narrows, removed or raised
  widens, and a change of shape (a rate's `by`) is neutral; a new route's limits are listed too.
  `control_list` shows each with the manifest's value and that it came from the box, and
  `control_report` monitors each under `box:<box>/<route name>`.
- **Beaten by an operator.** An endpoint override that matches the route (`"POST /cart"`, or
  `"TOOL /search"` for a tool) wins, property by property, at once, from the tools or the panel.
