# Backups to S3, and Rehydrating a Devbox

> Status: machine-authored and **not ratified**. Recorded on 2026-10-27. It builds
> `design/human/663.Backups.md` (drafted by Claude at the human's request, for the human to own).
> The code is the `backup` package (sealing, page deltas, names) and the host's `backups.cpp`
> (the service) and `rehydrate.cpp`. The local `goober-host backup DIR` copy (PROGRESS.md
> Phase 3) stays, and shares the copying code.

Since 2026-10-29 the backup thread also uploads rotated logs, sealed, under `logs/`, kept 400
days (032 § 2).

## 1. Config

```json
"backup": {
	"s3": { "bucket": "my-goober-backups", "region": "us-east-1", "prefix": "example.com/", "endpoint": "" },
	"nightly-at": "03:30",
	"keep-days": 14,
	"databases-every-ms": 900000
}
```

- Backups are on when `backup.s3.bucket` is set. `region` defaults to `aws.region`.
- `endpoint` is for S3-compatible services: R2, B2, MinIO, or a stand-in on 127.0.0.1.
- `nightly-at` is UTC.
- The AWS keys are the key store's (018 §2). The IAM user needs `s3:GetObject`, `PutObject`,
  `DeleteObject`, and `ListBucket` on the bucket. A devbox only needs to read.

## 2. The bucket

| object | what |
| --- | --- |
| `nightly/2026-10-27T03-30-00Z.tar.gz.sealed` | the whole storage (attachments aside) and `host.json`, at that second |
| `increments/NIGHT/AT/MANIFEST.json.sealed` | a restore point: how to rebuild every database and file at AT |
| `increments/NIGHT/AT/N.pages.sealed` | one database's pages that differ from NIGHT's copy |
| `increments/NIGHT/AT/files.tar.gz.sealed` | the other files that changed since NIGHT |
| `assets/TENANT/ID.EXT.sealed` | one attachment |
| `source/PROJECT/patches/NNNNNN.patch.sealed`, `source/PROJECT/snapshots/NNNNNN.tar.gz.sealed` | source projects' history: every revision as a patch, every deployed revision whole (020 § 10); never rotated |

Every object is under `prefix`, and every one is sealed (§3).

## 3. Sealing

A sealed file has four parts:

1. `GOOBERS1`;
2. a 16-byte random salt;
3. the ChaCha20 ciphertext (RFC 8439, nonce 0, counter 0);
4. an HMAC-SHA-256 tag over everything before it.

The file's encryption and MAC keys are HMACs of the backup key with the salt, so no two files
share a key stream. Unsealing checks the tag over the whole file before it decrypts a byte, and
writes the result only if the tag holds.

The backup key is 32 random bytes in `keys/system/backup_key`, made on first use.
`goober-host backup key` prints it, and `--confirm` records that a copy is kept elsewhere. Until
then, `backup_status` and the startup notes say so. Losing the key loses the backups.

Why not S3 server-side encryption alone? It protects the disks, not the data from anyone holding
the bucket's credentials or a misconfigured policy. With sealing, a leaked bucket leaks nothing.

## 4. The three streams

A backup thread ticks every 5 seconds (`backup_tick`). A sandbox host never ticks.

| stream | when | how |
| --- | --- | --- |
| assets | the ledgers are rescanned every 30 s, or at once after an upload | Each `stored` attachment is queued once in `storage/backup/state.db`, sealed, and put. A failure backs off from 10 s, doubling, up to an hour. An attachment deleted here becomes `gone` and leaves the bucket after keep-days. |
| nightly | the first tick at or after `nightly-at` each day, or at once when there is no night yet; retried 15 min after a failure | A consistent copy of storage (SQLite's online backup for each database), without attachments, logs, mail, tmp, or the backup state, plus `host.json`, packed with `tar -czf`, sealed, and put. Then the night's page map of every database and hash of every file is recorded. Then rotation runs. |
| increment | every `databases-every-ms` after the last nightly or increment | Described below. |

**Reading storage** (2026-10-30, after a site's nightly failed with "cannot read
.../storage: Permission denied"). The nightly, the increments, and the local backup walk
storage the same way: subtrees a backup never holds (`tmp/`, `logs/`, `mail/`, `backup/`,
`source/cache/`, and attachments for the archive) aren't entered, so nothing in them can stop
a backup, whoever made it. A directory or file a backup must hold and can't read fails the run
with its path, owner, and mode, like `cannot read .../storage/content/x (owner root, mode
0700)`. An increment never takes an unreadable file for a removed one. Storage is the host's
user's, all of it: every deploy gives back, with `find -execdir chown -h` (on the name, from
inside the directory, so a planted symlink can't aim root elsewhere), whatever another user
made there, and prints it; the audit's `storage` check (028 § 8) names what the host can't use.

**An increment:**

1. For each database that changed since the last increment (its size and mtime, then the
   SHA-256 of a fresh snapshot), the pages that differ from the night's copy are written,
   sealed, and put.
2. Other files that differ from the night's go up as one sealed `tar.gz`. That archive is reused
   while the set of changes stays the same.
3. The manifest goes last, listing every database with its SHA-256 and delta, the files
   archive, and what was removed. A restore point exists only once everything it names is in
   the bucket.
4. When nothing changed, nothing is uploaded.

**Increments are differential.** Each one is measured against the night, not against the
increment before it. So a restore needs the night and one increment, and a lost increment costs
only its own moment.

**Rotation** lists `nightly/` and `increments/` and deletes every night older than keep-days by
the stamp in its name, with its increments. The newest night always stays. A failed nightly
deletes nothing.

## 5. Rehydrate

```
goober-host rehydrate DIR [--at MOMENT] [--from host.json | --bucket B [--region R] [--endpoint URL] [--prefix P]]
                          [--key-file F] [--keep-keys] [--port N]
```

The AWS keys come from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and optionally
`AWS_SESSION_TOKEN`. The backup key comes from `GOOBER_BACKUP_KEY` or `--key-file`.
`just rehydrate DEST [AT]` (`tools/rehydrate.sh`) reads all of these from
`~/.config/goober/backup.env`.

MOMENT is UTC: `2026-10-26` (the day's end), `2026-10-26T18:00`, or `2026-10-26T18:00:00Z`.
Rehydrate restores the latest point at or before it.

DIR must be empty or missing. Rehydrate:

1. downloads, unseals, and unpacks the night;
2. applies the increment: each database with a delta is rebuilt (the night's copy, the delta's
   pages, cut to its length) and must match the manifest's SHA-256; databases the manifest
   doesn't name are removed; the changed files are unpacked; removed files are removed;
3. downloads every attachment the restored ledgers say is `stored`. Missing ones are reported,
   not fatal;
4. runs `PRAGMA quick_check` on every database;
5. drops `storage/keys/` unless `--keep-keys`;
6. writes the devbox's `host.json`: the archived config with storage `./storage`, listen
   127.0.0.1:PORT, `"sandbox": true` (018 §4), no `backup`, no `public-url`, the dev mailer, and
   cookies that aren't Secure;
7. writes `REHYDRATED.json`, saying what was restored from where.

Run the devbox with `goober-host --config DIR/host.json --local`, or `just run DIR`.

## 6. Operators

- MCP:
  - `backup_status` (with `points`, the bucket's restore points);
  - `backup_run` (`nightly`, `increment`, or `assets`).
- CLI:
  - `goober-host backup key [--confirm]`;
  - `goober-host backup list`;
  - `goober-host key set NAME` and `key list`.

`backup_status.healthy` is false when the last nightly is more than 26 hours old or the last
attempt failed. That is the red line of 663 § What the operator sees.

## 7. Tests

**`backup/test`:**

- sealing round-trips;
- the wrong key, a flipped byte, and a short file are refused without writing anything;
- deltas hold only changed pages, rebuild exactly through growth, shrinking, a new database,
  and a changed page size, and refuse the wrong base;
- stamps, moments, and restore points.

**`host/test/s3_backup_test.cpp`**, against the stand-in S3:

- the first tick uploads the asset and the night, and everything in the bucket is sealed;
- an increment carries a small delta and the changed files;
- a quiet tick uploads nothing;
- rehydrating the latest point and the night's gives the right rows, pages, and attachment;
- the devbox is a sandbox that refuses to back up;
- the wrong key fails;
- rotation keeps 14 days and the newest night;
- a deleted attachment leaves the bucket after keep-days;
- a failed nightly is recorded, waits, and then succeeds.

**`tools/backup_e2e.py` (`just backup-e2e`)** runs the real binary against `tools/fake_s3.py`.
That stand-in checks SigV4 with its own Python implementation. The script covers:

- the AWS keys set from the CLI;
- an agent refused when it tries to set them;
- a nightly, an asset, and an increment;
- the key warning, before and after it is confirmed;
- the CLI's restore list;
- a rehydrated devbox serving the latest page and attachment, and a rehydrate of the night's
  older page;
- the wrong key.

## 9. The daily upload budget

The human, 2026-11-01: "Ultimately, I don't want too much uploaded." The host counts every
object it puts in the bucket and holds back what can wait once a day's budget is spent.

**Counting.**
- Each object put is counted on its UTC day under its stream, the key's first segment:
  `nightly`, `increments`, `logs`, `assets`, or `source`. Sealed bytes are counted, which are
  what S3 stores.
- Counts live in `storage/backup/state.db` (`upload_days`), 90 days.
- Each rotation lists `nightly/`, `increments/`, and `logs/` already; what each held then is
  kept (`bucket_held`). Assets and the source mirror aren't listed, since listing them grows
  with every file.

**The budget.** `limits.upload-bytes-per-day`, 1 GiB unless set; 0 turns it off. Once the day's
uploads reach it:

| stream | past the budget |
| --- | --- |
| nightly | goes. Rotation, keep-days, and every restore point rest on it. |
| attachments | go. Nothing else carries them off the machine. |
| log archives | wait for the next UTC day, except one queued a week or more, which goes anyway. The queue keeps a file 30 days before dropping it (032 § 2), so a budget too small for a nightly can't lose logs. |
| increments | wait. The next increment, or the next nightly, carries every change, so nothing is lost; the restore points in between are. |
| source mirror | waits. Revisions stay in the source store until they go. |

The host says so once a day on standard error. `/goober/ready`'s `limits` check warns from 80%
of the budget (an `uploads` entry), and `backup_status` answers `uploads`:
- `today_bytes`, `today` by stream, `budget_bytes`, `today_share`, and `deferring`;
- `days`: 30 days by stream;
- `bucket`: what rotation saw;
- `note`, when the last nightly alone is past the budget.

An operator's `backup_run` isn't held to the budget: a person asked for it.

**What the budget doesn't do.** It spreads uploads over days; it doesn't make them smaller. A
nightly is the whole of storage (attachments aside) every night, so on a site with more data
than the budget, the nightly alone spends it, and only the rule above keeps logs moving. Making
less go up means:
- fewer logs (§ 10 of 032, the velocity view);
- a shorter `keep-days` (what the bucket holds, not what goes up);
- a longer `databases-every-ms` (fewer increments).

**Free reductions taken.**
- The panel's live statistics (`operations/traffic.db` and `operations/failures.db`) are no
  longer in nightlies or increments. They are five-minute rows kept a week; `traffic.db` alone
  may be 64 MiB (045). A restore starts them empty; the traffic tailer recounts what logs are
  on the machine.

**Checked, and already lean.**
- Attachments go up once each.
- An increment uploads only changed pages, and changed files only when their fingerprint moves.
- An unchanged increment uploads nothing.
- Logs and nightlies are gzip-compressed tar (`tar -czf`); JSON lines compress about tenfold.
  `gzip -9` or zstd would gain a little more for more CPU; zstd would change the archive format,
  so it waits for the human.
