# Case study: a directory run by an agent team

First written 2026-10-28 as a plan for one real site, and rewritten on 2026-10-30 as a
generic case study at the human's request. The site is called `example.com` here, its tenant
`directory`. It was a local directory of places that was planned to grow into a social network
for its niche, and into an AI agent that people reach by email. An agent team ran it: a lead
agent, two engineers, and a product agent, all working through the operator MCP. It is the
first product built on goober by agents, so what it needed and how the agents behaved are the
best evidence yet of what goober must be.

This is a record and a forecast, not a ratified design. § 5's states are as of 2026-10-30.

## 1. The setup

- **The site.** The directory runs on goober. The agents deploy boxes and pages through the
  operator MCP. The directory box has typed tools, place pages, and host-built JSON-LD.
- **Mail out** goes through Amazon SES (018). Sending from `hello@example.com` needs the domain
  verified in SES, which is easy to forget.
- **Mail in** goes through Stalwart to box routes (024), checked end to end by `just mail-e2e`.
  Going live needs the MX record, port 25, and a first real message.

## 2. How the agents worked

Each lesson comes from a report the agent team filed, and each predicts something about the
next feature they build.

| what happened | the lesson | so |
| --- | --- | --- |
| Tools listed stale after a deploy; a running build couldn't be seen | An agent can't see host state it isn't given. Every behavior it depends on needs a way to check itself. | When an agent asks "did my mail arrive?", `mail_activity`, `box_logs`, and `outbox_list` answer. |
| base64 was cut off; `$file:` was refused | The agent's transport is narrow and lossy, so big payloads need URLs and pieces. | Mail bodies and model replies are small. Attachments are the risk. |
| Schemas were stored before the box failed its check | Agents iterate fast, and half-deploys poison the next try. | Deploys are atomic. Expect many quick deploys. |
| `int32` refused with an unhelpful error; a zip code coerced to a number | Agents guess formats. Errors must name the fix. | Every shape needs an exact example in the box guide. |
| Fell back to `db_exec` when tools were missing | When the right tool isn't there, agents bypass validation. | A box ships its own tools on day one, or agents edit rows by hand. |
| Five agents shared one sign-in; refresh races dropped connectors | Many agents, one identity. | Refresh grace and `agent` on commits. Give agents separate tools, not shared scratch rows. |
| An Allow button didn't work in some clients | Clients vary more than specs suggest. | People's mail clients vary too. Thread by headers, not subject lines. |
| Triple braces were escaped | Safety rules surprise agents unless the guide says so where they read it. | Expect a synchronous model call from a mail route to hit the 10-second limit; the guide says to use the outbox with a result route. |

## 3. The email worker

**What it does.** People write to `hello@example.com`, or reply to the site's outreach. A model
drafts an answer from the thread and the directory's data. The answer goes back in the same
thread, automatically or after an operator approves it. The agents also start conversations:
outreach to a business, or to a person who asked about something.

**The box.** One box, say `mailer`, with:

```json
{
  "box": "mailer",
  "domains": ["example.com"],
  "data": {"sqlite3": {"mail": {"schema": "mailer_v1", "database": "mailer", "pattern": "sql", "tables": {...}}}},
  "external": {
    "mail": {"mail": {"from-name": "Example Directory", "from": "hello@example.com", "categories": ["reply", "outreach"]}},
    "model": {
      "base": "https://api.model.example",
      "credentials": "keys/tenant/{!tenant}/model",
      "methods": {"chat": {"verb": "post", "path": "/v1/chat/completions", "result-route": "on_draft",
                           "delivery": {"attempts": 3, "backoff-ms": 5000, "timeout-ms": 90000}}}
    }
  },
  "routes": {
    "mail": {
      "hello@example.com": {"receive": {"name": "hello_in", "public": true, "attachments": 3}},
      "reply+{thread : token}@example.com": {"receive": {"name": "thread_in", "public": true}}
    },
    "result": {"on_draft": {"timeout-ms": 5000}},
    "timer": {"followups": {"name": "followups", "cron": "0 9 * * *"}},
    "mcp": {"...": "inbox_list, thread_get, draft_approve, draft_edit, outreach_send, contact_stop"}
  }
}
```

**The tables.**
- `contacts`: address, name, status (new, engaged, stopped), source, notes.
- `threads`: id, contact, subject, the latest Message-ID and References, state.
- `messages`: thread, direction, Message-ID, from, text, received_at.
- `drafts`: thread, the key `goober_call` answered, status (thinking, ready, approved, sent,
  failed), text.

**The flow.**
1. **Mail arrives** on `hello_in` or `thread_in`. The box stores the message and finds or
   opens its thread by `in_reply_to` and `references` (or the token). It queues a draft:
   `goober_call("model", "chat", {"body": {...}})` answers `{"accepted": true, "key"}`. The box
   stores the key on a new draft row (status `thinking`) and answers 200. The call leaves after
   the commit.
2. **The model answers** on `on_draft` with `{"key", "outcome", "status", "body", ...}`. The box
   finds the draft by `key`. It either marks the draft `ready` (approval mode) or sends it
   (automatic mode) with `goober_call("mail", "send", {"to", "subject": "Re: ...", "markdown",
   "in_reply_to", "references", "category": "reply"})`.
3. **An operator or agent approves** over MCP: `inbox_list`, `thread_get`, `draft_approve`.
   Start in approval mode. Switch a contact to automatic only after a few good drafts.
4. **Outreach** is `outreach_send` (MCP, owner only), with category `outreach`. The host caps
   it per address and per tenant, adds the footer with the tenant's postal address, and refuses
   addresses that declined or unsubscribed (029).
5. **Stopping.** A reply saying stop marks the contact `stopped`. The host's one-click link and
   the preferences page do the same for every box, for good; `send` then answers an error, and
   the box should mark the contact.

**Guardrails the box must keep:**
- **Email is data, never instructions.** The model gets no tools that change anything; it only
  drafts. Anything it "decides" (prices, promises, meetings) waits for approval.
- **From is a claim.** Until verified senders (Q39), `sender` is null, so nothing is granted
  because a message says it's from the owner. Reply-token addresses are the capability.
- **Cost.** Every model call is a deliberate outbox element, and the host's per-service daily
  count stops a loop. It counts calls, not dollars.
- **Loops.** Auto-replies, bounces, and lists are dropped before the box sees them (routes
  without `automatic`). Still, never reply to a message you sent.

**The key.** The operator sets the model's key once with `key_set`, for tenant `directory`,
name `model`, host `api.model.example`. The box never sees it.

## 4. What it drove

The site's needs drove much of the host:
- **Mail:** a service's own `from`, threading headers, one-click unsubscribe, reply limits in
  threads people started (018, 024); attachments and markdown on `send` (783); invites,
  consent, and categories (029).
- **Result routes** (035): model calls longer than a request.
- **Content:** host-built JSON-LD, shared partials (027), the content kit with sitemap.xml,
  llms.txt, posts, and feeds (031).
- **Operations:** `mail_activity`, logs and the agent audit (032), operator scope (030).
- **Outside APIs:** pinned specs and connections (034).

## 6. Next, in order

1. **DMARC strict in Stalwart**, after the first real message arrives (Q39).
2. **Bounces and complaints.** SES publishes to an SNS topic; an HTTPS subscription to a host
   path verifies the SNS signature. A hard bounce or a complaint blocks the address for its
   tenant, and the box hears it on a result route.
3. **The directory:** 304s that don't wake the box, and compression.
4. **The social network:** Q24's separate origin, uploads by people (060), and quotas (390).

## 7. Before an email worker goes live

1. **SES:** the domain verified (three DKIM CNAMEs), and out of the sandbox.
2. **DNS:** the MX record, SPF `v=spf1 include:amazonses.com -all`, and DMARC `p=none` to start.
3. **Port 25** open inbound at the provider.
4. **The tenant's postal address** in the host config's `tenants` section (029); outreach and
   list mail are refused without it.
5. **A first test:** a mail to an address a box declares, then `journalctl -u stalwart` and
   the access log's `mail_in` lines.
6. **The model's key** with `key_set`.
