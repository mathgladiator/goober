# Local Identity, Setup, and Operator Tokens

> Status: machine-authored and **not ratified**. Recorded on 2026-10-22, when the human
> asked for identity that works locally, an interactive setup for a dev box or
> production, `just run`, and `just mcp`. It extends `005.FirstVersion.md`, and the code
> in `host-src/` follows it. Where it departs from a human doc, the doc and section are
> named in §8, and the human doc wins until it is updated. OAuth (clients, codes, tokens, the device flow) was
> added after it, in `009.OAuth.md`.

## 1. What v1 identity is

The built-in identity service of `013.Identity.md`, cut to the part a person can play
with: sign in on a domain, get a session, and have the host gate box routes by grant
roles. It lives in the `identity` package, with its HTTP endpoints in the `host` package.

| decision | value |
| --- | --- |
| Realm | One per **tenant**: `storage/identity/$tenant.db`. Host identities live in `storage/identity/_host.db`. |
| Sign-in | Passwordless only: a six-digit code mailed to the address. Codes last 10 minutes, are single use, lock after 5 wrong tries, and at most 5 are mailed per address per 10 minutes. |
| Sign-up | Anyone may sign up in a tenant realm by signing in. Only addresses in `identity.operators` can sign in to `_host`. Both look the same to the caller. |
| Session | An opaque 256-bit token in a cookie. Only its `sha256:` hash is stored, in the 013 `tokens` table with kind `session`. |
| Cookie | `__Host-goober-session` with `Secure; HttpOnly; SameSite=Lax; Path=/` when `identity.cookie-secure` is true (the default). `goober-session`, without `Secure`, when it is false and in local mode. The value is `t.$token` for a tenant session and `h.$token` for a host session. |
| Mail | The dev mailer (005 §11, Q45): a MIME file under `storage/mail/outbox/` and a line in `logs/mail.log`. In local mode, the code is also printed in the host's terminal. |
| Schema | The 013 schema minus passwords, passkeys, authorization codes, and device codes. `users.id` is `AUTOINCREMENT`, so a user_id is never reused. Every change of identity or role is audited in the same transaction. |

## 2. The endpoints

All under `/identity/`, which no box can declare (`041.ReservedRoutes.md`).

| endpoint | does |
| --- | --- |
| GET /identity/sign-in?return=/path | The sign-in page: an email field. It says nothing of host operators. |
| GET /identity/sign-in/as-host?return=/path | The host operator sign-in page, on any domain. Nothing links to it, so a tenant's customers never see a way in to the host. It is unlisted, not secret: an operator still needs a listed address and its code. |
| POST /identity/email/start | Mails a code, when the address may sign in, and shows the code page either way. |
| POST /identity/email/verify | Checks the code, opens a session, sets the cookie, and redirects (303) to `return`. |
| POST /identity/sign-out | Ends the session, clears the cookie, and redirects to `return` or `/`. |
| GET /identity/account | Who you are, your roles, and a sign-out button. Redirects to sign-in when signed out. |
| GET /identity/me | JSON: `signed_in`, `user_id`, `email`, `realm`, `host`, `roles`, `domain`; 401 when signed out. |

The pages follow the screen requirements of 013 that apply without OAuth: they are served
only by the host, with `X-Frame-Options: DENY`, a CSP of `frame-ancestors 'none'` and
`form-action 'self'`, and `Cache-Control: no-store`. A POST whose `Origin` names another
host is refused with 403. `return` must be a path on the same site. A tenant may restyle
the pages with a static file `sign-in.css` in its content, which the page links when it
exists (Q47).

**A deep link keeps its fragment** (2026-10-30, from a site's engineers). A signed-out visit to
`/docs/guide#install` is redirected to `/identity/sign-in?return=%2Fdocs%2Fguide`; the browser
keeps `#install` on the sign-in page (RFC 9110 § 10.2.2) but never sends it, and a form's POST
drops it. So the sign-in page carries one small inline script, allowed by its SHA-256 in the
page's CSP (`script-src 'sha256-…'`, nothing else), that appends `location.hash` to the form's
`return` field when that field has none. `return` then carries `/docs/guide#install` through
the code page to the final 303. `return` may hold a fragment of at most 256 of RFC 3986's
fragment characters; any other fragment is dropped and the path kept. Without JavaScript the
person lands at the page's top, as before.

That covers the gate's 303, where the browser carries the fragment to the sign-in page. It
doesn't cover a fragment that stays on the page the flow starts from: a "Sign in" link on
`/docs/guide#install`, or a box's own consent or gate page (`/consent?return=/docs/guide`) whose
form posts back. So the host also serves `/goober/keep-fragment.js` (2026-10-31), loaded by the
built-in partial `<!--#include keep-fragment-->`, which the built-in base template has. On load
and on every hash change it appends the page's `#fragment` to each `<input name="return"
data-fragment>` and to the `return=` of each same-site link to `/identity/sign-in` or marked
`data-keep-fragment` (the current page when the link has none). Templated pages allow it under
their own `script-src 'self'`. A box's redirect may carry the fragment back, under the same
256-character rule (`box_status_refusal`). A layout of a site's own needs the partial in its
`<head>`; without JavaScript, the person lands at the page's top. Invites and OAuth consent
return to host pages or registered redirect URIs, which have no fragment to keep.

## 3. Who gets which roles

- **Host operators** are `identity.operators` in the host config, an email and its host
  roles, exactly as 013 § Bootstrapping the host shows. A host session's roles are read
  from the config on every request, so removing an address from the config takes its
  host roles away at once. No route and no tool can grant a host role.
- **The first owner** of a tenant is `domains.$domain.owner`, as `015.Domains.md` has
  registering a domain name its first owner. When that address signs in, it is granted
  `owner` **if no user in the realm holds `owner`**. This covers the first sign-in, a
  config edited after the person signed up, and repairing a realm left without an owner,
  which 013 says only a host owner can do. The host owner does it by editing the config.
- **Everyone else** gets roles from an operator, through the MCP tools in §5, or from a box
  route that declares `grantable` or `revocable` (§ 3.1).

### 3.1 Roles a box grants and revokes

Built on 2026-10-31, when the human decided pages should gate on roles a box sets (a person
who signed a consent, say), as 013 § Granting and revoking roles designs it: the manifest, not
the box, says which strings a route may hand out or take away, and to whom.

```json
"/consent": {
  "post":   {"name": "consent", "requirements": [],
             "grantable": {"options": ["consented"], "to": "{!user_id}"}},
  "delete": {"name": "withdraw", "requirements": [],
             "revocable": {"options": ["consented"], "to": "{!user_id}", "allow-self-revoke": true}}
}
```

- **Where.** Only on an HTTP `post`, `put`, `patch`, or `delete` route with requirements. A
  public route has no caller to check, and a GET changes nothing. MCP tools keep `grantable`
  and `revocable` as accepted-but-not-built (an agent's call isn't a person's act); jobs,
  timers, internal, identity, and mail routes have no caller and take neither.
- **Options** are tenant roles, `role` or `role/scope`, never `host:` ones. They may use
  `{!tenant}`, `{!user_id}`, the target's own parameter, and a route parameter only when every
  requirements clause checks it (a clause naming it, like `admin/project_{p}`, or a realm-wide
  role like `owner`), so a caller can only hand out scope they were checked against (013 §
  Scoping roles by substitution).
- **`to`** is `{!user_id}` (the caller) or `{param}`, a route parameter holding a user id of
  the realm. With `{param}` on a route any signed-in user may call, the upload warns.
- **Self-revoke.** A revocation whose target is the caller is refused unless the route says
  `"allow-self-revoke": true`, which the upload warns about (013).
- **Roles that open this box.** When a route can grant a role that one of the box's own routes or
  tools requires (parameters compared as wildcards), the upload warns: whoever the granting route
  lets in can open what that role gates, pages included. Delegation is quiet: when every clause of
  the granting route already asks for that role, or for `owner`, the caller hands out nothing they
  don't hold (decided 2026-10-31, 043 § For the human).
- **The call.** `goober_role_grant(role_ptr, role_len) -> i32` and `goober_role_revoke`: 0 when
  the host took it, else the length of why not in the result buffer (`goober_result_read`), or
  -1 for a bad pointer. Rust: `goober::role_grant("consented") -> Result<(), String>`. Refused:
  a role no option yields after substitution, a target that isn't a user of the realm, a host
  identity's call, an agent's call (a role change is a person's own act), and a seventeenth
  change in one call (at most 16; 043 R4). A route offering `owner` is a warning at upload.
- **When it lands.** A role change is taken during the call and applied after it commits, as
  the outbox is (Q16): a call that answers 5xx, traps, or fails its commit changes no roles, and
  a dry run (`route_try`, `job_dry_run`) changes none and says so in its answer.
- **Audited** in the realm's own audit (`by: "box:$box/$route"`, shown by `realm_get` and the
  panel's realm view) and in the host's audit log (`role.grant`, `role.revoke`, with the box,
  route, request id, and target). The change log records files, so it doesn't: neither does an
  operator's `role_grant`.
- **Reviewed.** `version_upload` lists each new or wider option, target, or self-revoke as a
  widening, and a narrower set as narrowing.
- **Pages** name these roles in their requirements as any other, and roles are read fresh on
  every request, so the next page view after the grant opens. A cached box route's entry is
  keyed by the caller's roles too, so a role change never serves an answer made for the old ones.
- **Removing an option** from the manifest removes the box's power, not anyone's role: the
  strings stay with the people who hold them, as roles from any other source do, until a route
  or an operator (`role_revoke`) takes them away.

## 4. Requirements on routes

Every HTTP route in a v1 manifest now says who may call it, as 013 requires: either
`"public": true`, or `"requirements"`. A route with neither, or with both, is refused at
upload. The examples were updated to match.

- `requirements` is a disjunction of conjunctions: a list of lists of roles, or a flat list
  of roles, which is one clause.
- `[]` is one empty clause: any signed-in user of the realm.
- A role in a requirement is `host:$name`, or `$role` or `$role/$scope`, each part
  `[A-Za-z0-9_]`. Any part may hold `{param}` (a path parameter of the same route),
  `{!tenant}`, or `{!user_id}`. The checker refuses anything else.
- A substituted value holding `/` or `:` fails the request with 400 before any matching
  (013 § Grant roles).
- A host identity satisfies only clauses whose roles are all host roles. A tenant identity
  satisfies only clauses that name no host role. So `[]` is never satisfied by a host
  identity, and a host identity can't use a tenant role even if one somehow appeared in
  its list.

When a route needs a signed-in caller and there is none, a GET or HEAD that accepts
`text/html` is redirected (303) to `/identity/sign-in?return=...`, and anything else gets
401. A signed-in caller who satisfies no clause gets 403.

The request document gains `user`: `null` when signed out, or `{"user_id": "7", "email":
"...", "roles": [...], "host": false}`. It is filled on public routes too. The cookie and
authorization headers still never reach a box.

## 5. Operator access

- **Tokens.** `goober-host token create --name NAME` mints a token, `gop_` and 64 hex
  digits, and prints it once. It is stored as `storage/operations/tokens/$sha256.json`
  holding its name, creation time, and roles (`host:owner`, the only role in v1). Files are
  written atomically, so tokens can be minted while the host runs, and the host reads the
  file per request, so a revoked token stops working at once. `token list` and
  `token revoke NAME_OR_ID` manage them.
- `operations.token` in the config is now optional. A dev box keeps one there for
  `tools/goober.py`; production setup leaves it out.
- The access log names the operator for each MCP call: `config`, or `token:$name`.
- **New tools:** `realm_get`, `role_grant`, `role_revoke`, and `sessions_revoke` (the
  last two from `410.API.md`; `role_grant` and `role_revoke` are new, under the dev policy).
  `role_grant` creates the user when the address is new, so a role can wait for a first
  sign-in. No tool reads the mail outbox, since a code is between a person and the
  identity service.

## 6. Local mode

`goober-host --local` is for playing on one machine with any config, including a
production one:

- it listens on 127.0.0.1 and ignores `public-url`;
- session cookies are plain (not `Secure`), since a plain-HTTP host can't rely on
  browsers accepting a `Secure` cookie everywhere;
- sign-in codes are printed in the terminal;
- `$domain.localhost` reaches `$domain`, since browsers send every `*.localhost` name to
  this machine, so `http://bobsplumbing.com.localhost:8080/` plays Bob's domain locally;
- `localhost` and `127.0.0.1`, when not configured, reach the platform domain, or else the
  first domain.

## 7. Setup and the justfile

`just` recipes at the repo root drive everything, with `demo/` as the default directory:

| recipe | does |
| --- | --- |
| just run | Builds, writes `demo/host.json` with dev defaults if it is missing, and runs the host with `--local`. |
| just setup | Builds, then walks through the decisions below and writes `demo/host.json` (or any directory given). |
| just mcp | Mints an operator token named `claude-code` and prints the `claude mcp add` command. |
| just serve | Runs the host as configured, without local mode. |
| just tokens, just revoke | Lists or revokes operator tokens. |
| just examples | Deploys the example boxes and site to the running host. |
| just test, just check, just reload | The suite, a config check, and SIGHUP. |

`host-src/tools/setup.sh` asks, in order: dev box or production; your email (a host
operator with `host:owner`, and the first owner); the listen address and port; the
domains, tenants, and first owners; other operators and session length; threads and
pinning; box limits; and how operators get in. It shows the config, writes it only when
confirmed (mode 0600), and checks it with `goober-host check`. Production also gets
`deploy/goober-host.service` (systemd), `deploy/goober-backup.service` and `.timer` (a local
copy of storage each night in `backups/`, kept 14 days), and `deploy/Caddyfile`, since TLS
belongs to the proxy (`099.TheSystem.md`). Production sets `listen.behind-proxy`, and with it
setup asks only for a loopback address (127.0.0.0/8 or `::1`): the host believes the proxy's
`X-Forwarded-For`, so nothing else may reach its port (043, decided 2026-10-31). A dev box can seed the examples by starting the host briefly.
`--defaults` answers everything with the dev defaults, which is what `just run` uses.

## 8. What this departs from

| human doc | section | v1 says |
| --- | --- | --- |
| 013.Identity.md | Identity is per domain | A realm is a tenant. Redirect domains exist (005 § 6), but a tenant may still have two domains of its own, which then share a realm, though their cookies stay per domain. |
| 013.Identity.md | Sessions, schema, and the login API | No OAuth 2.1, device flow, client registration, passwords, or passkeys yet. The sign-in endpoints set a first-party cookie for the browser that is signing in, rather than completing an authorization flow for a client. |
| 013.Identity.md | Bootstrapping the host | Host roles are read from the config on every request rather than granted once at first sign-in. A host operator signs in on any domain, at `/identity/sign-in/as-host`, rather than on the platform domain and diving in (Q49's handshake is not built). |
| 013.Identity.md | Granting and revoking roles | Built for HTTP routes (§ 3.1); MCP tools can't grant or revoke, and agents' calls are refused. The ABI is one host call per direction with the role as a string, not a generated function per route. |
| 410.API.md | Identity | `role_grant` and `role_revoke` are new tools. Operator tokens act as host:owner rather than as host identities. |
| 005.FirstVersion.md | §9 | Operators may use minted tokens; `operations.token` is optional. |
