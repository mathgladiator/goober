# Mail: SES, and Mail That Boxes Send

> Status: machine-authored and **not ratified**. Recorded on 2026-10-27, at the human's request
> ("integrate SES as well, so we can make emails work properly"). It extends the v1 mailer
> (006 §3) with Amazon SES and gives boxes a host-owned `mail` service through the outbox (015).
> 038.Mail.md's mail routes, verified senders per domain, and reply-token capabilities are still
> to come; §6 says where this departs.

## 1. The host's mailer

One mailer sends everything: sign-in codes, grant notices, and boxes' mail.

| `identity.mailer` | sends through | needs |
| --- | --- | --- |
| `dev` (default) | nothing: each mail is a MIME file in `storage/mail/outbox/` | |
| `smtp` | an SMTP server, TLS required (006) | `identity.smtp {url, from, username, password-file}` |
| `ses` | Amazon SES's v2 API (`SendEmail`, raw MIME) | `identity.ses {from}`, the AWS keys |

```json
"aws": { "region": "us-east-1" },
"identity": { "mailer": "ses", "ses": { "from": "no-reply@example.com", "configuration-set": "goober" } }
```

`identity.ses` also takes `region` (default `aws.region`) and `endpoint` (an https address, or
`http://127.0.0.1:port` for a stand-in in tests). The From address must be a verified SES
identity. A configuration set is optional and is how SES publishes bounces and complaints.

## 2. AWS keys

The AWS keys live in the key store, never in the config:

- `keys/system/aws_access_key_id`
- `keys/system/aws_secret_access_key`
- optionally `keys/system/aws_session_token`

They are set on the server: `printf %s "$KEY" | goober-host key set aws_access_key_id` (the value
comes on stdin, never on a command line), or by `setup.sh`. The IAM user needs
`ses:SendRawEmail`, plus the bucket permissions in 019.

These keys, and `backup_key`, are the host's own:

- `key_set` and `key_delete` refuse them over MCP. Whoever sets the AWS keys chooses where mail
  and backups go, and the backup key decides who can read the backups.
- No manifest may name them as a service's credentials.

Requests are signed with Signature Version 4 by the `aws` package. Its signer is tested against
AWS's published examples and against curl's own `--aws-sigv4`. The signature and any session
token go to curl in a 0600 config file, never on its command line.

## 3. Boxes send mail

A box declares a `mail` service. Its one method is `send`:

```json
"external": { "mail": { "mail": { "from-name": "Beef Share" }, "methods": { "send": { "budget": { "calls": 1 } } } } }
```

```
goober_call("mail", "send", {"to", "subject", "text", "reply_to"?}) -> {"accepted": true, "key"} or {"error"}
```

- **Checked in the call:**
  - `to` and `reply_to` are each one plain address;
  - the subject is one line of 1 to 200 characters;
  - the text is 1 to 64 KiB of UTF-8.
- **Sent after commit:** the mail becomes an outbox element (verb `MAIL`) in the request's
  transaction. It leaves only if the request commits, and is retried six times over a day.
  A refusal is a dead letter.
- **From the host, or the tenant:** the From address is the mailer's, with the box's
  `from-name` as its display name, unless the service names its own `from`, such as
  `"mail": {"from-name": "Beef Share", "from": "hello@example.com"}`. That address must be on
  a domain the host config gives the box's tenant, checked at each call; SES must have that
  domain verified, or the mail is a dead letter. A box sending from its own address should
  declare a mail route for it, so replies come back (024). Added 2026-10-28 for outreach.
- **In a thread:** `in_reply_to` (one Message-ID) and `references` (up to 20) become the
  `In-Reply-To` and `References` headers, so a reply lands in the person's conversation.
  `references` defaults to `in_reply_to`. A Message-ID may come with or without `<>`.
- **Since 2026-10-29, 029 governs who a box may mail:** categories with their rules, lists
  with double opt-in, blocks instead of the unsubscribe list, and the host's footer with a postal
  address. This section is the history.
- **Unsubscribe, always:** every box mail carries `List-Unsubscribe` with a one-click link
  (RFC 8058, `List-Unsubscribe-Post`) and the layout's footer shows it. The link is
  `/goober/unsubscribe/$tenant/$hash/$mac` on the mail's site, a MAC under the host's reply
  key over a hash of the address, so the address never appears in it. A GET asks (mail
  scanners open links), and a POST unsubscribes. The tenant's list is
  `storage/mail/unsubscribed.db`, by hash only. A send to an unsubscribed address fails in the
  call, and one already queued is a dead letter at delivery. The operator tool
  `mail_unsubscribed` checks, adds, or removes one address. Sign-in codes are host mail, and
  never stopped by it. Gmail and Yahoo require one-click unsubscribe from bulk senders, and
  CAN-SPAM requires an opt-out in commercial mail. CAN-SPAM's postal address is the
  template's to carry.
- **Within limits:** at most `mail.daily-max` mails a day per tenant (default 200), and
  `mail.per-address-daily` to one address (default 3). An answer in a thread the person
  started gets `mail.reply-per-address-daily` instead (default 20): its `in_reply_to` must be a
  Message-ID that address sent the tenant in the last 30 days, which mail in notes, as hashes
  of the address and the ID, in `storage/mail/inbound.db`'s `received` table. A made-up
  In-Reply-To stays under the outreach limit.
  - The count lives in `storage/mail/sent.db`, keyed by a hash of the address, so the ledger
    holds no addresses.
  - An address past its limit is refused for good (a dead letter).
  - A tenant past its limit waits, as a 429.
- **Out of the logs:** the egress log records `mail:` without the address. `logs/mail.log` has
  the address, as it always has for sign-in mail.

`leads` uses this for its confirmation links.

## 4. The sandbox

`"sandbox": true` (set by rehydrate, 019 §5) makes a host that touches nothing outside:

- every mail goes to the dev mailer;
- `immediate` and `none` external calls fail with "this host is a sandbox";
- the outbox delivers nothing, so elements wait in plain view (`outbox_dead_letters` shows only
  dead ones, `pending` elements stay pending);
- no backup runs.

Web fetches still work. They are read-only and polite.

## 5. Tests

- `aws/test`: the signer against AWS's examples and curl, S3 and SES against a stand-in that
  checks every signature (`fake_aws.h`).
- `host/test/mail_test.cpp`:
  - a box's mail leaves through the stand-in SES only after commit, with the from-name,
    reply-to, and logs right;
  - the per-address limit dead-letters a second mail;
  - SES 5xx is retried after backoff;
  - bad mail is refused in the call;
  - a sandbox sends nothing;
  - sign-in mail goes through SES, and missing AWS keys say so.

## 6. Departures and what is missing

| doc | section | v1 says |
| --- | --- | --- |
| 038 | Mail routes, reply tokens | Not built: no inbound mail. |
| 038 | Verified senders | One From address per host. Boxes choose a display name. |
| 038 | Special providers | SES and SMTP only. Bounces and complaints are SES's (its account suppression list, a configuration set). goober doesn't read them yet. |
| 030 | External services | `mail` is a new kind of service, beside `base`, `box`, and `web`. |
| 390 | Quotas | Mail per tenant per day is a host-config limit, not yet a quota per domain. |

## Delivery is at least once (2026-10-30)

The outbox sends, then records the send. A crash, or a failed write, between the two sends the
mail again on the next tick. Services that take an idempotency key drop the second; SES has
none, so a recipient can, rarely, get a mail twice. The daily limits count a send before it
goes and give the count back if it fails.

## 7. Checking a domain's mail from the tools (2026-10-30)

A site's engineers had to read their mail DNS through public DNS-over-HTTPS, and a test mail they
sent didn't show in `mail_activity`. Now:

- **`mail_domain_check {domain}`** (a read tool; the host's tenant domains only, scoped by domain).
  It looks up, live, through the host's resolver (`res_nquery`; `dns.cpp` parses the answers):
  - **MX:** each record, its addresses, and whether it is this host (every address is one the
    platform domain has). With mail in set up (024), no MX or one elsewhere is a warning with the
    record to add. Port 25 is tried only on an MX address that is this host's own, never anyone
    else's, with a 3 s limit, and the answer notes that a provider's firewall can still block it
    from outside.
  - **SPF:** the `v=spf1` record. None suggests one (with `include:amazonses.com` when the mailer
    is SES); two is a warning (RFC 7208 § 3.2); SES missing from it is a suggestion.
  - **DMARC:** the `v=DMARC1` record at `_dmarc`; none suggests `p=none` with a report address.
  - **SES**, when it sends: SES v2 `GetEmailIdentity` with the host's AWS keys: whether the
    domain is an identity, verified for sending, and its Easy DKIM status and three tokens, with
    the CNAME records they need. Without keys, or another mailer, it says it skipped.
  - **The postal address**, when the tenant has none (no tool sets it: the human chose deploy
    only; the deploy's settings step asks, or host.json).
  Each finding has a level and, where there is one, the plain fix.
- **Test sends are mail activity.** `mail_template_send_test` logs its mail as the tenant's, marked
  `test`, so `mail_activity` shows it with `test: true`. The dev mailer's lines now carry the same
  fields as SES's and SMTP's (`tenant`, `status`, `via`), so a devbox's mail shows too. The call
  itself was already an operator action in the access log.
