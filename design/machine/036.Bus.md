# The bus: publish on commit, subscribe over SSE

A design for 040.TheBus.md, built the same day (and tested end to end). On 2026-10-30 the human asked for "pub sub and
SSE support so products can refresh and update in real-time". 040 already says what the bus
is; this says how v1 builds it on one machine, and what it decides that 040 leaves open.

## 1. What 040 settles, and v1 keeps

- **The bus carries signals, never data.** A signal is a topic and a sequence number.
- **Publishing comes from the data.** A strategy declares `publish`, and the topic moves only
  when a request's writes through that strategy commit.
- **Subscribing is a route.** `routes.sse` declares a `subscribe` route with `wake`,
  `coalesce-ms`, and `refresh-ms`. The host evaluates it like a GET, read-only, and sends the
  answer as an SSE event whose id is the sequence number.
- **Coalescing and sharing.** At most one evaluation per coalescing window, shared by every
  subscriber with the same signature; an answer identical to the last one isn't sent.
- **In-process** on a single machine.

## 2. The manifest

```json
"data": {"sqlite3": {"orders": {"schema": "shop1", "database": "shop", "pattern": "sql",
  "tables": {"orders": {"insert": true, "update": ["status"]}},
  "publish": "orders"}}},
"routes": {"sse": {"/orders/live": {"subscribe": {
  "name": "live_orders", "requirements": [["shop/staff"]], "response": "json",
  "wake": ["orders"], "coalesce-ms": 250, "refresh-ms": 30000}}}}
```

- **`publish`** on a strategy: one topic template.
- **`routes.sse.$path.subscribe`**: `name`, `public` or `requirements` (exactly as an HTTP
  route), `response`, `query`, `request-headers`, `template`, `includes`, and:
  - `wake`: 1 to 8 topic templates;
  - `coalesce-ms`: 50 to 60000, default 250;
  - `refresh-ms`: 1000 to 3600000, default 30000.
- **Topic templates** are 1 to 8 segments joined by `/`. Each segment is `[A-Za-z0-9_-]{1,64}`
  or one of `{!tenant}`, `{!user_id}`, `{!domain}`. Route parameters aren't allowed: a write
  can't fill them, so nothing could ever publish what a subscriber waits for. A `wake` with
  `{!user_id}` needs a route that isn't public.
- **Topics are per tenant.** The host keys every topic by the request's tenant, so `orders` in
  one tenant is not `orders` in another, whatever the template says. A strategy pinned to a
  fixed tenant's database (020) publishes in the tenant of the request that wrote.

## 3. Sequences

One counter for the host, seeded at start with the time in microseconds, so a sequence never
goes backwards across restarts. Each publish sets the topic to the next value. A subscription's
event id is the highest sequence among its wake topics when the evaluation began, so a publish
during an evaluation causes another.

A reconnecting client sends `Last-Event-ID`. If it equals the group's last id and the answer is
cached, nothing is sent until the next change; otherwise the current answer is sent at once.

## 4. Serving a subscription

- **The request.** A GET with `Accept: text/event-stream` on a subscribe route's path. The host
  checks access exactly as for an HTTP route (requirements, sign-in, agent tokens), then
  answers `200` with `content-type: text/event-stream`, `cache-control: no-store`, and
  `x-accel-buffering: no`, holding the connection open.
- **A plain GET** on the same path (no event stream asked for) evaluates once and answers like
  an HTTP GET, so a page can load the first state with `fetch` and then subscribe.
- **Events.** `id: <seq>`, `event: update`, and the answer's body as `data:` lines. A status
  that isn't 2xx sends `event: error` with `{"status"}`; a 401 or 403 also ends the stream.
- **Keepalive.** A comment line (`: ping`) every 15 seconds.
- **Lifetime.** A stream ends after 15 minutes. The browser's EventSource reconnects by itself,
  with `Last-Event-ID`, and the request is checked again, so a revoked session or a removed role
  stops receiving within 15 minutes.
- **Slow readers.** A stream more than 256 KiB behind is closed.

## 5. Evaluation

- **The signature** is the tenant, the box and route, the path parameters, the query the
  route sees, and the person (user id and roles), or no one. Subscribers with the same
  signature share one group, one evaluation, and one cached answer.
- **Read-only.** An evaluation runs with the database session refusing any statement that
  writes, and `goober_call` refusing anything but safe calls (effect `none`, web reads, mail
  preferences). The box sees `"method": "subscribe"`.
- **When.** A wake sets the group due at `max(now, last evaluation + coalesce-ms)`. A group
  not evaluated for `refresh-ms` is evaluated anyway. Evaluations run on the box pool.
- **What's sent.** If the answer's bytes equal the last ones sent, nothing; otherwise every
  subscriber in the group gets it.
- **Redeploys.** Each evaluation finds the route again from the request's path; if the box no
  longer serves it, the streams end.

## 6. Limits

| limit | value |
| --- | --- |
| streams on the host | 4000 |
| streams per tenant | 1000 |
| streams per client address | 32 |
| groups evaluated at once | the box pool's size |

Past a limit, the request gets `429` with `retry-after`.

## 7. Operators

`bus_status {tenant}` lists the tenant's topics with their sequences and last publish times,
and its groups: route, subscribers, evaluations, last evaluation, and last answer's size.

## 8. Left out

- **A cluster.** 040 recommends core NATS; v1 is one machine.
- **Publishing from operator SQL** (`db_exec`): it doesn't go through a strategy.
- **Topics from route parameters**, and qualified topics across tenants.
- **WebSockets.** SSE is enough for signals one way; writes stay HTTP requests.

## 9. Tests

- **bus:** monotonic sequences, wake callbacks, unwatch.
- **server_http:** a stream's headers, chunks in order, close by either side, slow-reader close.
- **manifest:** `publish`, `routes.sse` fields and refusals.
- **host:** a write that commits publishes and a rolled-back one doesn't; a subscriber gets
  the first answer, an update after a write, nothing for an identical answer, and the refresh;
  two subscribers share one evaluation; writes and effectful calls refused in an evaluation;
  access checked; Last-Event-ID; tenant isolation; limits.
