## 1. What is built

| piece | where |
| --- | --- |
| Clients that act as the person or as an agent | `identity` (`src/oauth.cpp`), the `clients` table |
| Authorization codes with PKCE, S256 only | `GET`/`POST /oauth/authorize` |
| Access and refresh tokens, rotation, reuse detection | `POST /oauth/token` |
| Revocation | `POST /oauth/revoke` |
| Metadata (RFC 8414) | `GET /.well-known/oauth-authorization-server` |
| Dynamic registration (RFC 7591), agents only | `POST /oauth/register` |
| The device flow (RFC 8628), agents only | `POST /oauth/device`, `/oauth/device/verify` |
| Bearer tokens on box routes and `/identity/me` | the host's caller resolution |
| `"agents": true` on HTTP routes (050) | `manifest`, checked before the box runs |
| Signed-in apps and agents on the account page, with revoke | `/identity/account`, `POST /identity/grants/revoke` |
| Operator tools | `client_list`, `client_put`, `client_remove` |

Each tenant realm is its own issuer. The issuer is the request's origin: `https://` plus
the `Host` header, or `http://` in local mode or when `identity.cookie-secure` is false.
The `Host` header has already been resolved to a configured domain before any of this
runs.

## 2. Clients: person or agent (999 decision 1)

The `clients` table gains `acts_as` (`person` or `agent`) and `source` (`config`,
`operator`, `dynamic`, or `host`). Every token copies `is_agent` from its client.

- **A person client** acts as the person, the way their browser does. Its tokens satisfy
  every route the person's roles satisfy. Only the host config (`identity.clients`, in
  every tenant realm) or an operator (`client_put`, in one realm) can register one, and
  it needs at least one redirect URI. **It can't use the device flow**, so a typed code
  never mints person tokens: a person client's tokens only ever go to its registered
  redirect.
- **An agent client** acts for the person. Its tokens reach only routes that say
  `"agents": true` (§5). Dynamically registered clients are always agents, are shown as
  unverified on the consent screens, and may have no redirect URIs, in which case only
  the device flow works for them.

The config entry for the terminal:

```json
{
	"identity": {
		"clients": {
			"dumb-terminal": {
				"name": "dumb terminal",
				"redirect-uris": ["com.mathgladiator.dumb:/oauth/callback", "http://127.0.0.1/callback"],
				"acts-as": "person"
			}
		}
	}
}
```

A config client is written into a realm the first time that realm sees it, and rewritten
when the config changes. Removing a client (`client_remove`) deletes its codes and tokens.

## 3. Redirect URIs

A registered redirect URI is https, a loopback `http://127.0.0.1/...` or
`http://[::1]/...`, an exact `http://localhost:PORT/...`, or a private-use scheme, like
`com.mathgladiator.dumb:/oauth/callback` (RFC 8252 §7.1). RFC 8252 wants that scheme
reverse-DNS, but Cursor registers `cursor://`, so one word is taken too; the schemes a
browser handles itself (`http`, `https`, `javascript`, `data`, `file`, `blob`, `about`, and
the like) never are. No fragments, no spaces, at most
512 bytes, at most 10 per client.

A requested redirect URI must equal a registered one, byte for byte, with one exception
(999 decision 2): when both are loopback URIs on the same host literal with the same path
and query, the port may differ, since a desktop app listens on an ephemeral port
(RFC 8252 §7.3). `localhost` is not loopback here, and nothing else is relaxed.

A bad client or redirect is shown as an error page and never redirected to. Every other
error goes back to the client's redirect with `error` and `state` (RFC 6749 §4.1.2.1).

## 4. The flows

**Authorization code.** `GET /oauth/authorize` needs `response_type=code`, a known
`client_id`, an allowed `redirect_uri`, and `code_challenge` with
`code_challenge_method=S256` (a 43-character base64url challenge). `state` is optional
and returned unchanged; `scope` is accepted and ignored (999 § Signing in), since grant
roles do that job.

1. With no tenant session cookie (a host session doesn't count), the browser is sent to
   `/identity/sign-in?return=...` and comes back.
2. The consent screen names the domain, the person, and the client. It says whether the
   client acts as the person or as an agent, shows where the client comes from (the
   https redirect's host, "the app that opens `com.example.app:` links", or "an app on
   this computer" for loopback), marks dynamic clients unverified, and lists the
   person's roles, as 013 § Sign-in screen requirements asks.
3. Allow posts to `/oauth/authorize`. The POST must carry an `Origin` of this host, or
   `Sec-Fetch-Site: same-origin`; a POST with neither is refused, so a forged form can't
   hand out a code. The screen's CSP adds the redirect's origin or scheme to
   `form-action`, because browsers check `form-action` on the redirect too.
4. The browser is sent to `redirect_uri?code=...&state=...&iss=...`. `iss` is the
   issuer (RFC 9207), so a client talking to several servers can't be mixed up. An https
   redirect is a 303. An app's (a private-use scheme or a loopback port) is a page that
   opens it with `Refresh: 0;url=...` and an "Open <app>" button: Chrome can drop an app
   launch at the end of a post's redirect without a word, which left Cursor's Allow button
   doing nothing (2026-10-28). Denying goes back the same way, with `error=access_denied`.

A code lasts 60 seconds and works once. Using it a second time revokes the tokens the
first use bought, since only a thief replays a code.

**Tokens.** `POST /oauth/token`, form-encoded, public clients only (no secret):

| grant_type | needs |
| --- | --- |
| authorization_code | client_id, code, redirect_uri (the same one), code_verifier |
| refresh_token | client_id, refresh_token |
| urn:ietf:params:oauth:grant-type:device_code | client_id, device_code |

The answer is `{access_token, token_type: "Bearer", expires_in, refresh_token}` with
`Cache-Control: no-store`. Errors are RFC 6749 JSON: `invalid_client` is 401, the rest 400.

| token | form | lifetime |
| --- | --- | --- |
| access | `goa_` + 64 hex digits | 1 hour |
| refresh | `gor_` + 64 hex digits | `identity.session-days` from issue |

Both are stored only as `sha256:` hashes. One sign-in's tokens share a **grant**
(`tokens.family`). A refresh rotates the refresh token and records `rotated_to` and
`rotated_at`. The grant's earlier access tokens run to their hour rather than end at the
refresh: ending them cut off a second session sharing the grant, which then refreshed with
the spent token and lost the grant (Grok's connectors, 2026-10-28). A rotated refresh token
presented again within 60 seconds of its rotation (`kRefreshReuseGraceMs`) is a client
racing itself, two sessions or a retry after a lost reply: it gets a new pair in the same
grant, and the audit says `refresh_raced`. Later, it revokes the whole grant, since two
parties hold it, and the client signs in again, which 999 § Signing in already expects
("any 4xx from the token endpoint during a refresh means the session is over"). A thief
who replays a stolen refresh token within that minute gets tokens until the next replay
after it; the minute is the price of not logging out agents that refresh in parallel.

**Revocation.** `POST /oauth/revoke` with `token` and `client_id` revokes that token's
whole grant, and answers 200 whatever the token was (RFC 7009). A client can't revoke
another client's token. Disabling a user, `sessions_revoke`, and removing the grant on the
account page all end it at the next request.

**Device flow.** For agents without a browser (013 § How an agent logs in):

1. `POST /oauth/device` with an agent's `client_id` returns `device_code`, `user_code`
   (like `WDJB-MJHT`, from 20 consonants), `verification_uri`, `expires_in` (600), and
   `interval` (5). There is no `verification_uri_complete`: the person types the code on
   a page they reached themselves. A client may have 10 device sign-ins pending.
2. The person opens `/oauth/device/verify`, signs in, types the code (case and dash
   don't matter), sees the agent named, marked unverified when dynamic, and allows or
   refuses. Both POSTs need the same-origin check of step 3 above.
3. The agent polls the token endpoint. Answers: `authorization_pending`, `slow_down`
   (faster than the interval), `access_denied`, `expired_token`, then tokens once.

## 5. Bearer tokens and agents

A request with `Authorization: Bearer ...` is resolved only through that token: a bad or
expired one is nobody, and never falls back to the cookie. A good one becomes the same
caller a cookie session would be, plus whether it is an agent and which client holds it.

- **Box routes.** Requirements are checked as for a cookie session. Then, if the caller is
  an agent and the route doesn't say `"agents": true`, the host answers 403 before the box
  runs (050 § Who is calling). The request document's `user` gains `agent`, and
  `client_id` when it is an agent (`{!client_id}`).
- **Pages.** An agent reads content as nobody, since a page isn't a route it opted into.
- **401s.** A caller with a bearer token, or one that doesn't accept `text/html`, gets 401
  rather than a sign-in redirect, with `WWW-Authenticate: Bearer`, plus
  `error="invalid_token"` when a token was sent (RFC 6750 §3).
- **JSON errors.** A host error answered to a caller with a bearer token, or one that
  asks for `application/json` over HTML, is `{"error", "status", "request_id"}` in place
  of the HTML error page.
- **Cross-site checks.** A box route's state-changing request is still refused when its
  `Origin` names another site; a native app sends none.

## 6. The account page

`/identity/account` lists every live grant (a refresh token neither revoked nor rotated):
the client's name, whether it acts as the person or as an agent, and unverified when
dynamic, each with a Remove button that posts to `/identity/grants/revoke`. That is 013's
"every new session is visible, with a way to revoke it", without the new-session email,
which waits for a real mailer.

## 7. Tests

`identity/test/oauth_test.cpp` drives the service: redirects, codes, PKCE (the RFC 7636
vector), rotation and reuse, revocation, the device flow, and client checks.
`host/test/oauth_routes_test.cpp` drives the endpoints: the terminal's whole sign-in, consent
and forged consents, bearer calls, 401s, refresh reuse, loopback ports, revocation, broken
requests, and an agent through registration, the device flow, and the agents rule.
