# The operator panel

A design, built the same day. On 2026-10-29 the human asked for the operator UI: a change
log, all the boxes, a graphical view of traffic and data flow, and a database explorer.
They chose:

- an ops subdomain;
- look-only;
- all four kinds of change (operator actions, box deploys, content and partial writes,
  schema changes);
- a browser side with no build step.

This builds the first part of `design/human/300.OperatingPanel.md`. Sitemap, Performance,
Agents, Content, and Logs views were added on 2026-10-29 (032 § 7). Approvals (305), tuning
(`tune_instances`, `tune_queue`), counters, traces, and cost are left for later (§ 10).

## 1. Where it is served

| config | the panel is at |
| --- | --- |
| `operations.domain: "ops.example.com"` | `https://ops.example.com/` on the mainline port |
| `operations.listen: "127.0.0.1:9443"` | a second listener; every request on it is the panel's |
| neither, in local mode | `http://ops.localhost:$port/` |
| neither, otherwise | nowhere: the panel is off |

- **`operations.domain` is never a tenant's domain.** The config check refuses a value that
  is also a key of `domains`, so the panel never shares an origin with a site (300 § The
  reserved surface). Its cookies, scripts, and CSP are its own.
- **On the panel's origin, only the panel answers.** It serves `/` and its assets,
  `/api/$tool`, the host-realm sign-in under `/identity/`, and `/goober/health`. Every other
  path is a 404. No box route, page, `/mcp`, or `/oauth/` is served there.
  `/goober-operations-mcp` keeps working on every domain, as before.
- **The private listener** (`operations.listen`) is the blast-radius mode from 300. It is
  reached with an SSH tunnel: `ssh -L 9443:127.0.0.1:9443 server`, then
  `http://localhost:9443/`. Browsers accept a Secure cookie on `http://localhost`, so sign-in
  works through the tunnel.

## 2. Who can see it

- **Sign-in.** People sign in with an emailed code as a host identity, at
  `/identity/sign-in/as-host` on the panel's origin. Only an address in
  `identity.operators` gets a code. On this origin the site sign-in (`/identity/sign-in`)
  redirects to the host one, so no tenant-realm account can be made here.
- **Roles (300).** `host:owner`, `host:operator`, and `host:observer` may open the panel. An
  address holding any other host role is refused with 403.
- **Look-only.** The panel calls only the read tools in § 7, for every role. Changes still go
  through `/goober-operations-mcp`, where Grok works. Since 2026-10-29 there are two
  exceptions, both things only a person may do: setting an operator's scope (030) and lifting
  a mail block (029 § 6).
- **`host:observer` on MCP.** An operator whose roles include neither `host:owner` nor
  `host:operator` may call only the read tools, over MCP as well. Other tools are left out of
  `tools/list` and refused by `tools/call`. Until now, any host role could call every tool.
  `config`-token and `goober-host token create` tokens stay `host:owner`.
- **Requests.**
  - The page is static. It calls `POST /api/$tool` with a JSON body, so the tool's arguments
    never appear in a URL.
  - The host requires `content-type: application/json` and a same-origin `Origin` header.
    That, together with the `SameSite=Lax` host cookie, stops a cross-site form from calling
    a tool.
  - Responses carry `cache-control: no-store`.
- **Content Security Policy.** `default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none';
  form-action 'self'`.
  - No inline script and no third party.
  - Values from tenants (paths, names, row data) are placed with `textContent`, never as
    HTML.

## 3. The browser side

Three files, `index.html`, `panel.css`, and `panel.js`, kept in `host-src/packages/panel/assets/`
and compiled into the binary.
- **No build step:** plain ES2020, hash routing, and SVG drawn by hand.
- **ETags:** each asset is served with one; `index.html` is `no-cache`.

| view | shows |
| --- | --- |
| **Overview** `#/` | host health (build, uptime, requests, startup notes, backups, mail); traffic for the last 12 hours; the boxes as a heat map, hot to cold by CPU time; the newest changes |
| **Traffic** `#/traffic` | requests over a window (1h, 12h, 7d, 30d), stacked by status class, with p50 and p99 latency; a table of routes (requests, errors, p50, p99, fuel, SQL calls, outbox calls); filters by tenant and box |
| **Data flow** `#/flow` | the whole host as a graph, left to right: tenants (with their domains), then boxes, pages, and host routes, then databases, services, and other boxes; each edge's width is its traffic over the window |
| **Boxes** `#/boxes`, `#/box/$name` | every box: active version, domains, routes, traffic. One box: its graph (§ 6), routes with their numbers, its versions, its manifest, and its newest log lines |
| **Changes** `#/changes` | the change log (§ 5), newest first, filtered by kind and tenant. Opening one shows its diff: lines for text, keys for a manifest |
| **Database** `#/db` | tenant, then database, then table: columns and schema, row count, rows 50 at a time, and a box for one read-only SQL statement |

Views refresh every 15 seconds while visible. The panel follows the system's light or dark
setting.

## 4. Traffic: rollups from the access log

Rollups are a view derived from the access log. The access log stays the record (300 §
Access logs).

- **The tailer.** Every 5 seconds, and before any traffic read, the host reads the lines
  appended to `logs/access.log` and `logs/egress.log` since its cursor. A cursor is the
  file's inode and byte offset, kept in `storage/operations/traffic.db`.
  - **Rotation.** When `access.log` rotates (to `access.log.1`), the tailer finishes the old
    file from its offset, then starts the new one at 0.
  - **Crashes and first start.** After a crash nothing is lost, since the lines are still
    there. The first start reads all the logs on disk, so a host's history comes into the
    panel at once.
- **A line's key.** Each line is counted under `(minute, tenant, box, route)`:
  - **tenant:** the line's `tenant`, or the tenant of its domain, or `""`.
  - **box and route:** the line's `box` and `route`, when a box answered.
  - **Otherwise the box is `""`, and the route says what the host did:**
    - `operations`: an operator MCP call;
    - `page`: a page or static file;
    - `identity`;
    - `oauth` (including `/.well-known/`);
    - `attachment`;
    - `mcp`: a site's `/mcp`;
    - `mail_in`;
    - `unsubscribe`;
    - `health`;
    - `panel`;
    - `unknown`: no configured domain.
  - **Never keyed:** paths, users, and addresses. The access log keeps none of them, and the
    rollups don't either (300).
- **Each row** holds the count, then the 3xx, 4xx, and 5xx counts. It then holds the sums of
  `us`, `fuel`, `sql`, and `outbox`, and the largest `us`. Last comes a latency histogram:
  40 buckets, each √2 wider than the one before: the first holds up to 32 µs, and the last
  everything past about 16 s.
  - p50 and p99 are read from the histogram (to within one bucket), so rows can be summed
    over any window.
- **Edges.** The tailer keeps edge counts, under `(minute, tenant, from_box, to_kind,
  to_name)`:
  - `internal`, from a line's `internal: "a -> b"`;
  - `service`, from each egress line: count, errors, `us`, and bytes out and in.
- **Retention.** Minute rows are kept 48 hours, and are summed into hour rows kept 400 days
  (300 § Rollups and cost).
- **Windows.**

  | window | points | from |
  | --- | --- | --- |
  | 1h | 60 of 1 minute | minutes |
  | 12h | 72 of 10 minutes | minutes |
  | 7d | 168 of 1 hour | hours |
  | 30d | 120 of 6 hours | hours |

## 5. The change log

Every durable change to the host's files goes through the host WAL. There are four writers:

- content (`content/$tree/...`), which covers pages, templates, partials, data files, and
  site CSS;
- box versions (`boxes/$box/...`);
- schemas (`schemas/$name.schema.json`);
- attachments (`objects/$tenant/attachments/$id`).

The WAL takes an observer, called once a bundle's commit record is durable and before it is
applied. At that moment the old files are still on disk. The host's observer writes one row
per change to `storage/operations/changes.db`:

| field | holds |
| --- | --- |
| `id`, `at_ms` | its order and time |
| `kind` | `deploy`, `upload` (a version stored but not activated), `content`, `partial`, `template`, `schema`, `attachment`, or `other` |
| `action` | `create`, `write`, `delete`, or `activate` |
| `tenant`, `target` | the tenant (or `_host`), and the path, box, or schema name |
| `actor` | who: the operator as the access log names them (`config`, `token:$name`, `oauth:$email:$client`), or `host` for the host's own writes and a site's uploads |
| `request_id` | the operator call that caused it, which links it to the action (below) |
| `bytes_before`, `bytes_after`, `hash_before`, `hash_after` | sizes and SHA-256s |
| `before`, `after` | the text, for content and schemas of at most 64 KiB, so a diff can be shown; texts older than 90 days are dropped, the rest of the row is kept |
| `detail` | for a deploy: `version` and `previous` |

Further rules:

- **One bundle, one row per meaning.** A box upload's bundle (manifest, module, types, and
  `active`) becomes one `deploy` row, or one `upload` row when nothing was activated.
- **Partial versions.** `partial_put`'s kept copies (`_partials/_versions/`) are written
  without rows of their own, since the partial's own row already has its before and after.
- **Operator actions.** Every operator `tools/call` is also written as one row of `actions`:
  - `at_ms`, `operator`, `tool`, and `request_id`;
  - the same `arg_*` fields the access log keeps (`tenant`, `path`, `box`, `project`,
    `name`);
  - whether it failed.

  The panel shows actions next to the changes they caused. It has a filter for the actions
  that changed something.
- **What isn't here.**
  - Tenant database rows. A box's writes to its own tables are traffic, not changes.
  - `db_exec`, which has its own log (`logs/db.log`), shown as an action.
  - Keys, which are recorded only by name, as an action; their values are never logged.
  - Config edits, which happen outside the host.

## 6. Data flow

`box_graph {window, box?}` answers nodes and edges for the window.

- **Without `box`:** the host's graph. Its columns are:
  - tenants, each with its domains;
  - tenants' pages (route `page`), host routes (identity, OAuth, attachments, `/mcp`), and
    boxes;
  - each box's databases (its `data` strategies, by database name), its services (from
    `external`), and the boxes it calls (`internal`).

  A tenant's edges to boxes and pages come from the rollups (requests, errors, CPU time).
  Box-to-database edges carry the box's SQL calls. Box-to-service and box-to-box edges come
  from the edge rollups.
- **With `box`:** one box, as 300 describes:
  - its routes on the left, by protocol (http, mcp, timer, mail, internal, identity, event),
    with requests, errors, p99, and fuel each;
  - the box in the middle;
  - its databases, services, outbox, and callees on the right.

  The graph comes from the active manifest, so a route with no traffic still shows, at zero.
- **Heat and weight.** Heat is CPU time (`us`) and is drawn as color. Traffic is drawn as an
  edge's width. Bytes are drawn as width only on service edges, the one place the host
  measures them today.

## 7. The tools

The panel is a client of the operator API (410). Everything it shows, an agent can read too.

**New tools:**

| tool | answers |
| --- | --- |
| `traffic` `{window, tenant?, box?}` | the series (§ 4) and the routes table |
| `hot_boxes` `{window}` | boxes by CPU time, with requests and errors (410) |
| `box_graph` `{window, box?}` | § 6 (410) |
| `changes` `{kind?, tenant?, before_id?, limit?}` | change rows without their texts, newest first |
| `change_get` `{id}` | one row with `before` and `after`, or for a deploy both manifests |
| `operator_actions` `{changed_only?, before_id?, limit?}` | actions, each with the ids of its changes |

**Read tools.** These are what the panel and `host:observer` may call:

- **Overview and traffic:** `host_health`, `traffic`, `hot_boxes`, `box_graph`,
  `access_log`.
- **Changes:** `changes`, `change_get`, `operator_actions`.
- **Boxes:** `box_list`, `box_logs`, `version_list`, `version_get`, `route_check`,
  `mcp_tools_preview`, `timers_list`, `outbox_dead_letters`.
- **Databases:** `db_list`, `db_describe`, `db_query`, `schema_list`, `schema_get`.
- **Domains and identity:** `domain_list`, `realm_get`, `client_list`.
- **Content:** `content_list`, `content_get`, `page_list`, `page_get`, `page_render`,
  `template_list`, `partial_list`, `partial_get`, `attachment_list`, `attachment_get`.
- **Mail:** `mail_activity`, `mail_unsubscribed`, `mail_template_list`,
  `mail_template_get`, `mail_template_preview`.
- **Source:** `source_list`, `source_read`, `source_log`, `source_diff`, `source_job`.
- **Other:** `backup_status`, `key_list`, `crawl_list`, `crawl_pages`, `crawl_records`,
  `box_guide`, `site_guide`, `rust_binding`.

`db_query` is already read-only: the database opens the statement for reading and refuses
writes.

## 8. Config

```json
{
  "operations": {
    "token": "…",
    "domain": "ops.example.com",
    "listen": "127.0.0.1:9443"
  }
}
```

Both new fields are optional. `domain` must be a DNS name and must not be in `domains`.
`listen` is `address:port`; port 0 takes any free port (for tests).

For a site at example.com, the domain needs three things, outside the host:
- an `A` record for `ops.example.com`;
- the name added to the site line of `/etc/caddy/Caddyfile`, so Caddy gets its certificate;
- `operations.domain` in `host.json`.

Setup doesn't ask for a panel domain; every deploy's operations audit offers one.

### The operations audit

A deploy checks more than whether the host is up: it checks how the host is run, and says
what to do about it. On 2026-10-30 the human made it a rule: the deploy is the sanity check
for operating, too. `goober-host audit [--config host.json] [--caddyfile PATH] [--json]`
prints one line per check; it advises and never fails a deploy.

| id | what it finds |
| --- | --- |
| `panel` | No `operations.domain`: suggests `ops.` on the platform domain (or the first public domain), with the DNS records it needs, and other domains' `ops.` names as alternatives. One panel serves every tenant. Set: checks its name resolves to the platform domain's addresses. |
| `caddy` | A domain in `domains`, or the panel's, missing from the Caddyfile's site lines: Caddy gets no certificate for it. |
| `mailer` | `identity.mailer` is `dev`: nobody receives sign-in codes. |
| `backup` | No `backup.s3`: backups stay on the machine. |
| `operators` | No `identity.operators`: nobody can sign in to the panel. |

DNS is "ready" when every address of the panel's name is one of the platform domain's.

```json
{"audit": {"quiet": ["panel"]}}
```

`audit.quiet` names checks not to suggest again; each is still listed, as quiet, so a choice
made once stays visible. Ids are lowercase letters and hyphens; an id no check has is itself
a finding.

The deploy (`server-bootstrap.sh`) runs the audit after its checks. When `panel` is suggested
and its DNS is ready, it asks: yes sets `operations.domain`, adds the name to the Caddyfile's
first site line, checks both (`goober-host check`, `caddy validate`), restarts the host,
reloads Caddy, and waits for `https://ops…/` to answer; if either is refused, both files are
put back (`host.json.before-panel`, `Caddyfile.before-panel`). "never" adds `panel` to
`audit.quiet`. Without a terminal, it only prints.

## 9. Tests

- **Rollups.**
  - Lines are keyed and summed.
  - The histogram's p50 and p99 are right.
  - A rotation is followed.
  - A restart resumes at the cursor without counting twice.
  - Minutes become hours.
- **Changes.**
  - The classifier is right for each WAL path.
  - An upload bundle gives one deploy row.
  - Before and after texts are kept, and large ones aren't.
  - The actor and request id come from the operator call.
- **Panel routes.**
  - Signed out, the panel sends you to sign in.
  - A tenant domain never serves the panel.
  - The ops domain serves nothing else.
  - A non-read tool is refused.
  - A missing JSON content type, or a cross-origin post, is refused.
  - Assets are served with the CSP.
- **Roles.** `host:observer` over MCP lists and calls only read tools.
- **Config.** `operations.domain` is refused when it's a tenant domain.
- **Audit.** Caddyfile site lines; the panel suggested with its DNS missing, ready, or
  elsewhere; a set panel checked for DNS and Caddy; quiet checks noted, bad ids refused or
  reported; mail, backups, and operators.
