# The operator panel

A design, built the same day. On 2026-10-29 the human asked for the operator UI: a change
log, all the boxes, a graphical view of traffic and data flow, and a database explorer.
They chose:

- an ops subdomain;
- look-only;
- all four kinds of change (operator actions, box deploys, content and partial writes,
  schema changes);
- a browser side with no build step.

This builds the first part of `design/human/300.OperatingPanel.md`. Sitemap, Performance,
Agents, Content, and Logs views were added on 2026-10-29 (032 § 7). Approvals (305), tuning
(`tune_instances`, `tune_queue`), counters, traces, and cost are left for later (§ 10).

## 1. Where it is served

| config | the panel is at |
| --- | --- |
| `operations.domain: "ops.example.com"` | `https://ops.example.com/` on the mainline port |
| `operations.listen: "127.0.0.1:9443"` | a second listener; every request on it is the panel's |
| neither, in local mode | `http://ops.localhost:$port/` |
| neither, otherwise | nowhere: the panel is off |

- **`operations.domain` is never a tenant's domain.** The config check refuses a value that
  is also a key of `domains`, so the panel never shares an origin with a site (300 § The
  reserved surface). Its cookies, scripts, and CSP are its own.
- **On the panel's origin, only the panel answers.** It serves `/` and its assets,
  `/api/$tool`, the host-realm sign-in under `/identity/`, and the host's own `/goober/health`,
  `/goober/ready`, and `/goober/deploy` (JSON nobody but the host writes). Every other
  path is a 404. No box route, page, `/mcp`, or `/oauth/` is served there.
  `/goober-operations-mcp` keeps working on every domain, as before.
- **The private listener** (`operations.listen`) is the blast-radius mode from 300. It is
  reached with an SSH tunnel: `ssh -L 9443:127.0.0.1:9443 server`, then
  `http://localhost:9443/`. Browsers accept a Secure cookie on `http://localhost`, so sign-in
  works through the tunnel.

## 2. Who can see it

- **Sign-in.** People sign in with an emailed code as a host identity, at
  `/identity/sign-in/as-host` on the panel's origin. Only an address in
  `identity.operators` gets a code. On this origin the site sign-in (`/identity/sign-in`)
  redirects to the host one, so no tenant-realm account can be made here.
- **Roles (300).** `host:owner`, `host:operator`, and `host:observer` may open the panel. An
  address holding any other host role is refused with 403.
- **Look-only.** The panel calls only the read tools in § 7, for every role. Changes still go
  through `/goober-operations-mcp`, where Grok works. Since 2026-10-29 there are two
  exceptions, both things only a person may do: setting an operator's scope (030) and lifting
  a mail block (029 § 6). Later came drops (§ 8, Database drops) and, on 2026-11-03, per-domain
  controls (§ 4.9): a person with `host:owner` or `host:operator` sets, changes, observes, or
  removes any control at any time, audited as `panel.control_set` or `panel.control_remove`, in
  the change log, never waiting for approvals; `host:observer` gets 403.
- **`host:observer` on MCP.** An operator whose roles include neither `host:owner` nor
  `host:operator` may call only the read tools, over MCP as well. Other tools are left out of
  `tools/list` and refused by `tools/call`. Until now, any host role could call every tool.
  `config`-token and `goober-host token create` tokens stay `host:owner`.
- **Requests.**
  - The page is static. It calls `POST /api/$tool` with a JSON body, so the tool's arguments
    never appear in a URL.
  - The host requires `content-type: application/json` and a same-origin `Origin` header.
    That, together with the `SameSite=Lax` host cookie, stops a cross-site form from calling
    a tool.
  - Responses carry `cache-control: no-store`.
- **Content Security Policy.** `default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none';
  form-action 'self'`.
  - No inline script and no third party.
  - Values from tenants (paths, names, row data) are placed with `textContent`, never as
    HTML.

## 3. The browser side

Three files, `index.html`, `panel.css`, and `panel.js`, kept in `host-src/packages/panel/assets/`
and compiled into the binary.
- **No build step:** plain ES2020, hash routing, and SVG drawn by hand.
- **ETags:** each asset is served with one; `index.html` is `no-cache`.

| view | shows |
| --- | --- |
| **Overview** `#/` | host health (build, uptime, requests, startup notes, backups, mail); the boxes as a heat map, hot to cold by CPU time; the key graphs over the window (§ 4.5); the newest changes |
| **Services** `#/services`, `#/services?service=$name` | what went out to services (§ 4.4): every service with its calls, failures, retries, dead letters, and latency; one service's methods per box, failure statuses, and latest failures; the outbox's queue, the mail limits, mail in, and backups |
| **Traffic** `#/traffic` | requests over a window (1h, 12h, 7d), stacked by status class, with p50 and p99 latency; a table of routes (requests, errors, p50, p99, fuel, SQL calls, outbox calls); filters by tenant and box |
| **Data flow** `#/flow` | the whole host as a graph, left to right: tenants (with their domains), then boxes, pages, and host routes, then databases, services, and other boxes, then each database's tables with the operations granted on them; each edge's width is its traffic over the window |
| **Boxes** `#/boxes`, `#/box/$name` | every box: active version, domains, routes, traffic. One box: its graph (§ 6), **Grants**: each table its strategies grant against what this version's statements used, with what to narrow (`grant_usage`, 008 § 4.1), routes with their numbers, its versions (with the source revision each came from), its manifest, its newest log lines, and **From source**: the deploys behind its versions (020 § 9) |
| **Source** `#/source`, `#/project/$name`, `#/job/$id` | source projects (head, deployed revision, how far the backup bucket's mirror has come) and the newest builds and deploys; a project's revisions, the deployed one marked, with their builds; a revision's message, colored diff, and files; a file with line numbers; a job's whole build log (020 § 12) |
| **Performance** `#/perf` | each URI's live numbers (`uri_stats`, 032 § 7); then what to fix, with its evidence, where each route's time goes per call (queue, box, lock wait, SQL, commit, calls out, render, cache hits, refused writes), and the last hour's statements with SQLite's counters (`perf_report`, `perf_statements`, 037 § 7) |
| **Changes** `#/changes` | the change log (§ 5), newest first, filtered by kind and tenant. Opening one shows its diff: lines for text, keys for a manifest |
| **Database** `#/db` | tenant, then database, then table: columns and schema, row count, rows 50 at a time, and a box for one read-only SQL statement |
| **Studies** `#/studies`, `#/studies?id=$id` | heat studies (048): the list; a running study's progress; a finished one's heat by endpoint (bars by CPU share, requests, or bytes), the busiest clients by keyed hash, the endpoints table (each client's busiest minute, concurrency, latency, statuses), and the suggested controls in observe mode with their reasons (§ 4.8) |

Views refresh every 15 seconds while visible. The panel follows the system's light or dark
setting.

## 4. Traffic: rollups from the access log

Rollups are a view derived from the access log. The access log stays the record (300 §
Access logs).

- **The tailer.** Every 5 seconds, and before any traffic read, the host reads the lines
  appended to `logs/access.log` and `logs/egress.log` since its cursor. A cursor is the
  file's inode and byte offset, kept in `storage/operations/traffic.db`.
  - **Rotation.** When `access.log` rotates (to `access.log.1`), the tailer finishes the old
    file from its offset, then starts the new one at 0.
  - **Crashes and first start.** After a crash nothing is lost, since the lines are still
    there. The first start reads all the logs on disk, so a host's history comes into the
    panel at once.
- **A line's key.** Each line is counted under `(five minutes, tenant, box, route)`:
  - **tenant:** the line's `tenant`, or the tenant of its domain, or `""`.
  - **box and route:** the line's `box` and `route`, when a box answered.
  - **Otherwise the box is `""`, and the route says what the host did:**
    - `operations`: an operator MCP call;
    - `page`: a page or static file;
    - `identity`;
    - `oauth` (including `/.well-known/`);
    - `attachment`;
    - `mcp`: a site's `/mcp`;
    - `mail_in`;
    - `unsubscribe`;
    - `health`;
    - `panel`;
    - `unknown`: no configured domain.
  - **Never keyed:** paths, users, and addresses. The access log keeps none of them, and the
    rollups don't either (300).
- **Each row** holds the count, then the 3xx, 4xx, and 5xx counts. It then holds the sums of
  `us`, `fuel`, `sql`, and `outbox`, and the largest `us`. Last comes a latency histogram:
  40 buckets, each √2 wider than the one before: the first holds up to 32 µs, and the last
  everything past about 16 s.
  - p50 and p99 are read from the histogram (to within one bucket), so rows can be summed
    over any window.
- **Edges.** The tailer keeps edge counts, under `(five minutes, tenant, from_box, to_kind,
  to_name)`:
  - `internal`, from a line's `internal: "a -> b"`;
  - `service`, from each egress line: count, errors, `us`, and bytes out and in.
- **Retention.** One resolution: five-minute rows, kept seven days, and no longer (the human,
  2026-10-31: "I don't really want long term metrics, just five minute approximations is
  good. I don't want traffic storage bloating the disk."). This departs from 300 § Rollups and
  cost, which asks for hourly rollups kept 400 days. `traffic.db` also has a byte budget,
  `limits.traffic-bytes` (64 MiB; 045.Limits.md): past it, the oldest hours go first. Freed pages
  go back to the disk (incremental vacuum), and the write-ahead log is cut back after each
  checkpoint. Until 2026-10-31 there were minute rows (48 hours) and hour rows (400 days); a host
  opening such a file drops them, counts the logs still on disk again, carries the gauges over
  at five minutes, and vacuums. A week of one busy site (50 routes each answering every
  minute, 5 services each called every minute) is about 12 MiB.
- **Windows.**

  | window | points |
  | --- | --- |
  | 1h | 12 of 5 minutes |
  | 12h | 72 of 10 minutes |
  | 7d | 168 of 1 hour |

The human asked on 2026-10-31 for errors to stay out of the sitemap's flame graph, for a page of
error rates from the outside, and for a separate view of how boxes fail. § 4.1 to § 4.3 are
that.

### 4.1 Errors in the access log, and the icicle

- **Who made an error.** Every access line of a 4xx or 5xx says `error_by`:
  - `host`: no box ran (no such path, a gate, a refused input, a limit);
  - `box`: a box answered it (its own 404, say);
  - `box_failed`: a box ran and failed (a trap, a timeout, a bad answer, a 5xx it may not send).
- **Whether a link led there.** A line with a Referer says `ref`: `same` (this site) or
  `other`. Which page or site is never kept here.
- **The icicle** (`uri_tree`, the Sitemap view) is the site's own traffic. Live statistics
  count an error the host answered before any box ran under one name, `(refused)`, as
  `(not found)` already counted paths nothing answers. The tree leaves out both, and
  box-to-box calls (`internal:...`). A box route's own errors stay on its node and show in its
  color: a box's 404 for a missing place is that route's traffic. `uri_stats` still lists both
  names.

### 4.2 Errors from outside (the Errors view, `error_report`)

- **What counts.** Every access line with a status of 400 or more, except box-to-box calls
  (the calling box's business, § 4.3) and route_try's lines.
- **Rows** go beside the traffic rows, in the same transaction as the tailer's cursor, under
  `(five minutes, tenant, status, place, box, route, error_by, ref)`, with the same
  retention and windows.
- **A place** is the box route when a box ran. Otherwise it is one of these:
  - a page's path, only when the line names a file that exists (a gated page, say);
  - a host area (`identity`, `oauth`, `mcp`, `operations`, `attachment`, `unsubscribe`, ...);
  - `(not found)` for every path nothing answers, so a scan can't push out the rest;
  - `(other)`.

  So the rollups hold page paths of the site's own content, never a path a visitor made up.
- **The view.**
  - The share of requests that failed, then 4xx, 5xx, and each maker's count.
  - A series stacked by maker against all requests.
  - A table by status, and one by referral. An error behind a link on this site is a broken
    link.
  - The places, most first, each split by referral, with a link to its access-log lines.
- **Custom pages** for these are 007 § 13.

### 4.3 How boxes fail (the Box failures view, `box_failures`)

- **The record.** Every box call (requests, MCP tools, timers, mail, jobs, identity events,
  results, subscriptions, internal calls) counts once under its route and kind. route_try,
  job dry runs, and cache hits don't count. Each way it went wrong counts under a class, in a
  group (a try's or dry run's failure is kept apart, below):

  | group | classes | counted |
  | --- | --- | --- |
  | call | trap, timeout, out_of_fuel, failed, no_response, bad_response, bad_status, render_failed, outbox_failed, host_write_failed, commit_failed, host_error, job_failed (a job batch the host couldn't take: no cursor, a cursor that didn't move) | once per failed call: the failure rate |
  | sql | sql_error, no_clock, refused_write | per statement, even when the call went on to succeed |
  | outbox | delivery_retry, delivery_dead | per delivery attempt that failed, on the box that queued it |
  | internal | internal_failed | on the caller, when a call to another box failed (the callee's own failure is on the callee) |
  | answer | mail_rejected, mail_deferred | a mail route's choice, not a fault |

- **Where it lives.** `storage/operations/failures.db`, written by the traffic loop every 5
  seconds from what calls left in memory. A call never waits on it. A crash loses at most
  those seconds, as live statistics do. Five-minute counts are kept seven days, and the
  newest 200 messages per box for seven days (045.Limits.md). A message is the host's own text (a trap's, a SQL
  error's, a delivery's) or a box's error, at most 300 bytes, as box logs keep them (032 § 8).
- **The view.**
  - The calls, the share that failed, and the counts per group.
  - A series stacked by group.
  - Routes by most failures, with their classes.
  - The latest messages, each linking to the box's log by request id.
  - Tries and dry runs that failed, in their own card (2026-10-31).
- **Tries and dry runs, apart.** A failure of a `route_try` or a `job_dry_run` is kept in its
  own table (the newest 100 per box, seven days) and answered under `tries`, each with `trial`
  (`route_try` or `job_dry_run`), so a failed dry run says why. Tries count in no rate and
  never push real messages out.
- **A box's 5xx, separated.** The Errors view's `box_failed` is what visitors saw of these.
  Box failures says which class.

The human asked on 2026-10-31 for key graphs of the service, for a way into the metrics of
external services (the special ones, like mail, and then any service), and for the data flow to
show the services used and the flow from boxes to them. § 4.4, § 4.5, and § 6 are that.

### 4.4 External services (the Services view, `service_report`)

- **What counts.** Every call out the egress log records, and every mail the mailer sent:
  - a box's calls through `goober_call` and its outbox's deliveries (`outbox_id` set), mail
    and invites included;
  - the host's own: web push sends (service `push`), the robot's fetches (`web`, from an
    operator's crawl or a box), and OAuth token refreshes (the service's name, method
    `oauth2.token`);
  - the mail log (`logs/mail.log`): every mail the mailer handled, as service `mailer`, method
    the mailer (`ses`, `smtp`, or `dev`). A box's mail has its tenant and is from `boxes`; the
    host's own (sign-in codes, invites, operator test mail) has its realm and is from `host`.
    The mailer's line now says how long it took (`us`) and, for the host's own mail, its realm.
- **A failure** is no answer (status 0, called `neterr`), an error, or a status of 400 or more.
  A sent mail counts as status 250.
- **Rows.** The same tailer that reads the access log reads the egress and mail logs too (one
  cursor each, the same rotation rules), and counts each line under `(five minutes, tenant,
  box, service, method)`: calls, failed, `n4`, `n5`, `neterr`, outbox deliveries, `us`, bytes out
  and in, and the latency histogram. Failures are also counted by `(five minutes, tenant,
  service, status)`. Retention and windows are § 4's.
- **The latest failures.** Each failed line is kept with its time, tenant, box, service,
  method, status, error (at most 300 bytes), URL without its query (at most 200), and
  `request_id` or `outbox_id`: the newest 100 per service, for seven days. Addresses in errors are
  already hashed by the log writer (032 § 1).
- **Retries and dead letters** are the outbox group of box failures (§ 4.3), per service: a
  delivery that failed and will be tried again, or that gave up.
- **The queue.** Each outbox tick (every 2 seconds) counts the elements waiting per tenant and
  service as it reads them, and hands the counts to the rollups in memory. Each five minutes'
  largest is written by the traffic loop (gauge rows, seven days); the latest
  sample is kept in memory. A sandbox's outbox isn't sampled.
- **The tool.** `service_report {window, tenant?, service?, latest?}`, a read tool (the panel
  and observers may call it; a focused operator names a tenant). It answers § 4's window
  fields, `totals`, a series (calls, failed, outbox deliveries, p50, p99), `services` (each with
  `kind`: `external`, `mail`, `web`, `push`, or `mailer`; its boxes and tenants; `retries` and
  `dead`; services the active boxes declare show at zero), `methods`, `statuses`, `latest`, and:
  - `outbox`: the queue's series and each tenant's and service's count now;
  - `mail`: the mailer, `daily-max`, `per-address-daily`, and each tenant's mail in the last 24
    hours from the sent ledger;
  - `mail_in`: the inbound hook's calls and refusals;
  - `backups`, without `tenant`: `backup_status`'s summary (on, healthy, last nightly and
    increment, last error).
- **Not reported:** bounces and complaints. SES tells the configuration set's destination, not
  the host; the panel says so rather than showing zero.
- **The view.** The totals; calls stacked answered and failed, and latency; a table of services
  (click one for its page); methods per box; failures by status; the queue with what waits now;
  the latest failures with a link to their egress-log lines; and the mail and backups cards.

### 4.5 Key graphs (the Overview)

The Overview's key graphs, over the window picked, each linking to its view: requests by status
class; the error rate (4xx and 5xx against all requests); p50 and p99 latency; box failures by
group; calls out to services, answered and failed, with their latency; the outbox's deliveries
and its queue; and mail sent and failed. A row of numbers sums them. A focused operator sees
their first tenant's.

### 4.6 Health for an outside monitor (`/goober/ready`)

The panel is inside the host; when the host is sick, someone outside has to notice. So
`/goober/ready`, which deploys and bots already read, also answers `health`: numbers an outside
monitor polls and graphs over time. They come from memory (a five-minute pulse of one-minute
buckets, filled as requests, box calls, mail, and calls out are logged), a few gauges the host
keeps current (the outbox as its last tick found it, the worker queue, open connections), and a
few cheap reads (free disk, the backup state's three times, the log archive's queue). No log
file is read, and the whole is computed at most once a second.

```
"health": {
  "window_s": 300, "uptime_s": 86400,
  "requests": {"ratio_4xx": 0.02, "ratio_5xx": 0, "p50_ms": 0.5, "p99_ms": 12.3, "max_ms": 40.1},
  "boxes": {"failure_ratio": 0}, "mail": {"failure_ratio": 0}, "services": {"failure_ratio": 0.01},
  "outbox": {"depth": 3, "oldest_age_s": 12, "dead": 0},
  "workers": {"queued": 0, "open_connections": 4},
  "disk": {"free_bytes": 52000000000, "free_ratio": 0.61},
  "backups": {"enabled": true, "nightly_age_s": 30000, "increment_age_s": 600, "logs_age_s": 3000},
  "logs": {"archive_queued": 0, "write_errors": 0}
}
```

- **Ratios, latencies, ages, and gauges; never volumes.** `/goober/ready` answers on every
  domain without signing in, and request, mail, or call counts would tell anyone a site's
  traffic. A ratio is 0 when nothing happened in the window. The monitor's own polls of
  `/goober/ready` aren't counted. This is reversible: counts could be added behind the
  operations token if the human wants them (for the human, 2026-10-31).
- **What each means.** `requests`: answers to visitors and clients (tries left out). `boxes`:
  box calls that failed as calls (a trap, a timeout, a bad answer; 4.3's group "call"), against
  all box calls. `mail`: sends the mailer reported failed against all sends (test sends left
  out). `services`: calls out (the egress log) answered 4xx or 5xx or not at all. `outbox`:
  elements waiting, the oldest one's age (null with none), and dead letters kept. Ages are
  null for something that never happened; `backups` has only `enabled` when backups are off.
- **Prometheus.** `/goober/ready?format=prometheus`, or a scraper's `Accept: text/plain;
  version=0.0.4`, answers the same numbers as text exposition: `goober_ready`, `goober_*`
  for each number above (seconds and milliseconds in their names), `goober_check_ok{check}`
  for each check, and `goober_loop_age_seconds{loop}`. It always answers 200, since a scraper
  takes a 503 as the target being down; `goober_ready 0` says not ready. Unknown values (null)
  are left out, not written as 0.
- **Lost on restart.** The pulse is in memory, like live statistics; `uptime_s` says when
  that happened. The panel's rollups (§ 4) are where history lives.
- **Logs (2026-11-01).** `logs` also carries `growth`, each host log's last 24 hours over its
  usual day, with `boxes` for the largest box log, and `projected_budget_ratio`, the logs
  directory in 7 days at today's rate over `limits.logs-bytes` (032 § 10). Ratios only, as
  above; computed at most once a minute, by the traffic loop, never by the request.
  Prometheus: `goober_log_growth_ratio{log}` and `goober_logs_projected_budget_ratio`.
- **The limits check (2026-11-03).** `checks.limits` (045) is public too, so there each budget
  is only `{share, warn?}` (`share` is used over the limit, to three places) and its `near`
  warnings are ratios ("exports at 85% of limits.exports-bytes", "a tenant's snapshots at
  100% of limits.snapshot-files"): no bytes, no file or copy counts, no tenant, no box, and
  no local-copies or disk rows (the disk has its own check). host_health carries the whole
  report: bytes, counts, the fullest tenant, and the local copies. The public report is
  measured at most every 30 seconds (it walks exports, snapshots, logs, and tmp); the storage
  probe and the disk check stay live on every call. The traffic store's size in it is what the
  last traffic pass measured, so a poll never waits behind that pass.

### 4.7 Logs and uploads (`#/volume`)

The human asked, on 2026-11-01, for a dashboard when log volume grows, and not too much
uploaded. The view is host-wide; a focused operator gets a note instead. It reads two read
tools, `log_velocity` (032 § 10) and `backup_status` (019 § 9).

- **Warnings first:** each log that grew three times its usual day, and the projection past
  `limits.logs-bytes`, in the words /goober/ready uses (with the box's name, for operators).
- **Totals:**
  - bytes written in the last 24 hours;
  - what's on the machine;
  - what waits in the archive queue;
  - the projection in 7 days, and its share of the budget.
- **Log volume:** a stacked chart of bytes per step over the window, for the four biggest logs
  and the rest as one.
- **By log:** the last 24 hours (bytes and lines), today, the usual day, growth (red when it
  grew), and days known. A row opens that log alone.
- **Who writes the most:** the tenant, box, and route behind the most bytes over the window,
  with their share of their log.
- **Uploads:**
  - **Totals:** today's bytes, the budget, its share, and whether logs and increments are
    waiting.
  - **Uploads per day:** a stacked chart over 30 days, by stream.
  - **In the bucket:** what rotation last saw under `nightly/`, `increments/`, and `logs/`.
  - When backups are off, it says so.

### 4.8 Heat studies (`#/studies`)

The human asked, on 2026-11-03, for "a way to do a study on a domain to discover heat by
endpoint". A study counts one domain's requests by endpoint for 5 minutes to a day and keeps a
report 30 days (`design/machine/048.HeatStudy.md`). The view reads two read tools,
`heat_study_list` and `heat_study_get`, and never starts or stops a study: an operator or an
agent does that with `heat_study_start` and `heat_study_stop`, which observers and the panel
can't call. What it shows is 048 § 8. Since the cleanup of 2026-11-03 a study leaves out the host's own
paths (`/goober/*`, preflights), so the view never shows them, and the report it reads is
smaller: no client classes, fuel, or rank lists (048 § 12).

### 4.9 Controls (`#/controls`)

Built on 2026-11-03 with per-domain controls (047). The view has a domain picker. For each of
the domain's controls it shows the mode, the last change (when, who, and why), and the effective
values with where each one comes from. It then shows `control_report`'s totals and verdicts, a
chart of allowed and refused by reason, a would-refuse chart for observed controls, latency, and
the effect of the last change. Removed controls show while their rows last. It reads
`control_list` and `control_report`, both read tools. The change log's kind filter has `control`
(and `flag`). A box route's own limits (047 § 13) show as their own controls, from the manifest.

Since 2026-11-03 the view also edits, for a person with `host:owner` or `host:operator` (the
human: "operators can override at any time since a control may be bum"): per control a mode
toggle, Edit, and Remove, "Add a control" (an override by default: id, match, api, mode, and the
properties as JSON), and "Override…" on a box route's limits. Each needs a why. The page posts
`/api/write/control_set` and `/api/write/control_remove`, which run what `control_set` and
`control_remove` run, as the person, never held for approval (047 § 9). Agents keep using the
tools, where approvals apply.

### 4.10 Skills and playbooks (`#/skills`)

## 5. The change log

Every durable change to the host's files goes through the host WAL. There are four writers:

- content (`content/$tree/...`), which covers pages, templates, partials, data files, and
  site CSS;
- box versions (`boxes/$box/...`);
- schemas (`schemas/$name.schema.json`);
- attachments (`objects/$tenant/attachments/$id`).

The WAL takes an observer, called once a bundle's commit record is durable and before it is
applied. At that moment the old files are still on disk. The host's observer writes one row
per change to `storage/operations/changes.db`:

| field | holds |
| --- | --- |
| `id`, `at_ms` | its order and time |
| `kind` | `deploy`, `upload` (a version stored but not activated), `content`, `partial`, `template`, `schema`, `attachment`, or `other` |
| `action` | `create`, `write`, `delete`, or `activate` |
| `tenant`, `target` | the tenant (or `_host`), and the path, box, or schema name |
| `actor` | who: the operator as the access log names them (`config`, `token:$name`, `oauth:$email:$client`), or `host` for the host's own writes and a site's uploads |
| `request_id` | the operator call that caused it, which links it to the action (below) |
| `bytes_before`, `bytes_after`, `hash_before`, `hash_after` | sizes and SHA-256s |
| `before`, `after` | the text, for content and schemas of at most 64 KiB, so a diff can be shown; texts older than 90 days are dropped, the rest of the row is kept |
| `detail` | for a deploy: `version` and `previous` |

Further rules:

- **One bundle, one row per meaning.** A box upload's bundle (manifest, module, types, and
  `active`) becomes one `deploy` row, or one `upload` row when nothing was activated.
- **Partial versions.** `partial_put`'s kept copies (`_partials/_versions/`) are written
  without rows of their own, since the partial's own row already has its before and after.
- **The call says what it made.** A `tools/call` that wrote answers with `change_ids` (and
  `change_id` when it made one): the rows with its request id added since the call began.
  Added 2026-10-30, so a reviewer can pin a change without looking it up.
- **Operator actions.** Every operator `tools/call` is also written as one row of `actions`:
  - `at_ms`, `operator`, `tool`, and `request_id`;
  - the same `arg_*` fields the access log keeps (`tenant`, `path`, `box`, `project`,
    `name`);
  - whether it failed.

  The panel shows actions next to the changes they caused. It has a filter for the actions
  that changed something.
- **What isn't here.**
  - Tenant database rows. A box's writes to its own tables are traffic, not changes.
  - `db_exec`, which has its own log (`logs/db.log`), shown as an action.
  - Keys, which are recorded only by name, as an action; their values are never logged.
  - Config edits, which happen outside the host.

## 6. Data flow

`box_graph {window, box?}` answers nodes and edges for the window.

- **Without `box`:** the host's graph. Its columns are:
  - tenants, each with its domains;
  - tenants' pages (route `page`), host routes (identity, OAuth, attachments, `/mcp`), and
    boxes;
  - each box's databases (its `data` strategies, by database name), its services (from
    `external`), and the boxes it calls (`internal`).

  A tenant's edges to boxes and pages come from the rollups (requests, errors, CPU time).
  Box-to-database edges carry the box's SQL calls. Box-to-service and box-to-box edges come
  from the edge rollups.
- **With `box`:** one box, as 300 describes:
  - its routes on the left, by protocol (http, mcp, timer, mail, internal, identity, event),
    with requests, errors, p99, and fuel each;
  - the box in the middle;
  - its databases, services, outbox, and callees on the right.

  The graph comes from the active manifest, so a route with no traffic still shows, at zero.
- **Tables** (added 2026-10-30, 008 § 4.1), in both graphs: one column right of the
  databases, a node for each table a `sql` strategy grants (`table:$database.$table`). Its
  edge from the database carries `ops` (the operations granted, `riud`), `grants` (each box's
  strategy, operations, read and update columns, the operations it used, and how many calls
  touched the table since the host started), and `unused` when no box has touched it. The
  panel prints the operations beside the table, draws unused grants dashed, and lists every
  box's grant in the edge's tooltip. A box's grant reaches nothing else, so the graph is the
  box's whole reach in its databases.
- **Services** (added 2026-10-31, § 4.4), in both graphs:
  - each service node carries its calls, failures, and p99 over the window, and opens its page
    in Services;
  - a box's services come from its manifest first, so a mail or web service says so even
    before it is called;
  - the host's own calls out (push, the robot, token refreshes) are edges from the tenant's
    host routes, or from "the host" when no tenant is named;
  - the mailer is a node right of the services: an edge from each mail service carries the
    mail it handed on, and one from each tenant's host routes the host's own mail (sign-in
    codes, invites), with failures.
- **Heat and weight.** Heat is CPU time (`us`) and is drawn as color. Traffic is drawn as an
  edge's width. Bytes are drawn as width only on service edges, the one place the host
  measures them today.

## 8. Config

```json
{
  "operations": {
    "token": "…",
    "domain": "ops.example.com",
    "listen": "127.0.0.1:9443"
  }
}
```

Both new fields are optional. `domain` must be a DNS name and must not be in `domains`.
`listen` is `address:port`; port 0 takes any free port (for tests).

For a site at example.com, the domain needs three things, outside the host:
- an `A` record for `ops.example.com`;
- the name added to the site line of `/etc/caddy/Caddyfile`, so Caddy gets its certificate;
- `operations.domain` in `host.json`.

Setup doesn't ask for a panel domain; every deploy's operations audit offers one.

### The operations audit

A deploy checks more than whether the host is up: it checks how the host is run, and says
what to do about it. On 2026-10-30 the human made it a rule: the deploy is the sanity check
for operating, too. `goober-host audit [--config host.json] [--caddyfile PATH] [--json]`
prints one line per check; it advises and never fails a deploy.

| id | what it finds |
| --- | --- |
| `panel` | No `operations.domain`: suggests `ops.` on the platform domain (or the first public domain), with the DNS records it needs, and other domains' `ops.` names as alternatives. One panel serves every tenant. Set: checks its name resolves to the platform domain's addresses. |
| `caddy` | A domain in `domains` (a redirect too), or the panel's, missing from the Caddyfile's site lines: Caddy gets no certificate for it. |
| `mailer` | `identity.mailer` is `dev`: nobody receives sign-in codes. |
| `backup` | No `backup.s3`: backups stay on the machine. |
| `operators` | No `identity.operators`: nobody can sign in to the panel. |
| `postal` | A tenant a public domain serves has no `tenants.$t.postal-address`: its invites, lists, and boxes' mail to people are refused (029 § 8). |
| `storage` | Paths in storage not owned by the storage directory's owner (the host's user), or that it can't read and write: up to 10 named, with the count and the `chown` that fixes them. Every deploy gives them back first (019 § 4). |
| `redirect` | One finding per name. A tenant's public domain without `www.` in front, whose `www.` name isn't in `domains`: suggests redirecting `www.` to it (005 § 6), with its DNS state and the records it needs. Only for a name of two labels, like `example.com`, unless its `www.` already resolves. Set: warns when the redirect's name doesn't resolve here. |

`mailer` and `backup` also warn when SES or S3 is set but the host has no AWS keys
(`keys/system/aws_access_key_id`, `aws_secret_access_key`); the audit checks only that the
files exist, and never reads a key.

DNS is "ready" when every address of the panel's name is one of the platform domain's.

```json
{"audit": {"quiet": ["panel"]}}
```

`audit.quiet` names checks not to suggest again; each is still listed, as quiet, so a choice
made once stays visible. Ids are lowercase letters and hyphens; an id no check has is itself
a finding. A check about one name is quieted for that name alone by `id:name`, like
`redirect:www.example.com`.

The deploy (`server-bootstrap.sh`) runs the audit after its checks. When `panel` is suggested
and its DNS is ready, it asks: yes sets `operations.domain`, adds the name to the Caddyfile's
first site line, checks both (`goober-host check`, `caddy validate`), restarts the host,
reloads Caddy, and waits for `https://ops…/` to answer; if either is refused, both files are
put back (`host.json.before-panel`, `Caddyfile.before-panel`). "never" adds `panel` to
`audit.quiet`. Without a terminal, it only prints.

Each suggested `redirect` is offered the same way, after the panel: "Redirect
https://www.example.com/ to https://example.com/ now? [y]es, [n]ot now, ne[v]er". Yes adds
`"www.example.com": {"redirect-to": "example.com"}` to `domains` and the name to the site line
that serves `example.com`, so Caddy gets its certificate and proxies it to the host, which
answers the redirect. The same checks and the same putting back (`*.before-redirect`), and it
waits for `https://www.example.com/` to answer `301` to `https://example.com/`. "never" adds
`redirect:www.example.com` to `audit.quiet`. Until its DNS points here, the deploy says to add
the record, and asks only whether never to suggest it.

### Database drops (2026-10-30)

The Database view ends with a card of what no box binds (`db_unbound`) and the tenant's
snapshots (`db_snapshots`). For `host:owner`, each unbound database or table has Drop, each
schema no box names has Retire, and each snapshot has Delete. The page asks the person to

### A new tenant

On 2026-10-30 the human asked to launch a new tenant's domain during a deploy:
`deploy.sh SERVER --add-tenant [DOMAIN]`. On an existing install, before mail in (so Stalwart
relays for the new domain in the same run), the deploy asks, from a terminal:

| question | rule |
| --- | --- |
| the domain | a public DNS name not already in `domains` (a tenant's or a redirect) or the panel's |
| the tenant | `[a-z][a-z0-9_]*`, suggested from the domain's first label; an existing tenant only after a yes, since one name per tenant is 015's rule and a redirect is usually what's wanted |
| the first owner | an email, or none |
| the postal address | one line, or none (the settings step asks later) |
| terms and privacy | paths on the site, or none |
| `www.` | redirect it to the domain (default yes), when `www.` isn't taken |

It shows the DNS records the names need (A or AAAA to this server, and MX to the platform
domain when mail in is on) and whether each resolves here yet, and asks to go ahead. Then
`tools/tenant_edit.py` (tested in CTest as `tools.tenant_edit`):

1. adds `domains.$domain` (tenant and owner), `domains.www.$domain` as a redirect, and the
   tenant's missing settings to host.json, as the host's user; a tenant that exists keeps every
   setting it has;
2. `goober-host check`;
3. adds a site block for the names to the Caddyfile, as root: a copy of the body of the block
   that proxies to goober (`health_uri /goober/health`), so the new site has its own
   certificate and the same proxy and error handling;
4. `caddy validate`, then restarts the host (ready within a minute) and reloads Caddy;
5. waits up to a minute for `https://$domain/goober/health` through Caddy; a certificate that
   isn't there yet (DNS not pointed) is a note, not a failure.

Any refusal puts host.json and the Caddyfile back (`*.before-tenant`) and fails the deploy.
Without a terminal, the domain and `--tenant-name` are required (with `--tenant-owner`,
`--tenant-postal`, `--tenant-www` for the rest), and `deploy.sh` refuses before building
without them. On a first install the flag is skipped: setup asks for the domains.

### Missing settings

On 2026-10-30 the human asked that the deploy ask for anything missing, starting with the
postal address. A finding about a missing setting carries `asks` in `--json`, one per value:

| kind | what the deploy does with the answer |
| --- | --- |
| `text` | Sets it at `path` in host.json, and each of `also` beside it (the SES from address sets `identity.mailer: "ses"`). |
| `operator` | Adds the address to `identity.operators` as `host:owner`. |
| `key` | `goober-host key set NAME`, the value on stdin; asked without echo, once per deploy. |

Each ask has a `prompt` and a `pattern` the answer must match whole; three tries, then it is
skipped. The checks that ask: `postal` (per tenant), `mailer` (the from address and the AWS
keys), `backup` (the bucket and the AWS keys), `operators` (an address).

After the panel, the deploy's `── settings` step asks, per finding: yes, not now, or never
(quiet, as above). Enter skips a value. The answers are applied together, as the host's user:
host.json is copied to `host.json.before-settings`, edited, checked with `goober-host check`,
and the host restarted and waited on for a minute; if any of that fails, host.json is put back
and the deploy fails. Keys are set after. It ends by listing what is still missing.

Root talks to the terminal, and the audit's JSON is the host user's output, so prompts are
stripped of control characters and paths and key names are checked before they're used.

## 9. Tests

- **Rollups.**
  - Lines are keyed and summed.
  - The histogram's p50 and p99 are right.
  - A rotation is followed.
  - A restart resumes at the cursor without counting twice.
  - Buckets are kept seven days and no longer; the old minute and hour tables are replaced;
    over its budget, the oldest hours go.
  - Services are counted from the egress and mail logs once, across a restart, with methods,
    statuses, and the newest 100 failures per service.
  - Gauges keep each five minutes' largest and the latest sample; a key gone from a sample reads 0.
  - An outbox tick samples its queue.
- **Services in the panel.** `service_report` names each service's kind (a box's mail, a box's
  external service, push, the mailer), the outbox's deliveries, and the latest failure's
  request id, and leaves backups out for one tenant; `box_graph` draws the services with
  their numbers, the host's push from its routes, and the mailer behind a box's mail service.
- **Changes.**
  - The classifier is right for each WAL path.
  - An upload bundle gives one deploy row.
  - Before and after texts are kept, and large ones aren't.
  - The actor and request id come from the operator call.
- **Panel routes.**
  - Signed out, the panel sends you to sign in.
  - A tenant domain never serves the panel.
  - The ops domain serves nothing else.
  - A non-read tool is refused.
  - A missing JSON content type, or a cross-origin post, is refused.
  - Assets are served with the CSP.
- **Roles.** `host:observer` over MCP lists and calls only read tools.
- **Config.** `operations.domain` is refused when it's a tenant domain.
- **Audit.** Caddyfile site lines; the panel suggested with its DNS missing, ready, or
  elsewhere; a set panel checked for DNS and Caddy; quiet checks noted, bad ids refused or
  reported; mail, backups, and operators.
