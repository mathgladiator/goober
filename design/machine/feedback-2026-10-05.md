## 2. The design in one breath

Goober is a research bet that agents will write most software and can't be trusted with the old keys. So it gives them "better boxes, with finer scope," and makes "the wrong action impossible rather than merely frowned upon" [000 §Introduction]. The bet is explicitly about confidence without reading code, and containment over correctness, with growth a non-goal [005 §Goals; §Non-Goals].

**The box.** A box is an ephemeral WASM process with no POSIX inheritance [000 §The Foundational Thinking]. It is described by a JSON manifest, "the primary artifact that humans read" [010 §The Manifest], which deploys atomically with the module through a human approval queue [010 §Start with Hello World].

**The manifest and the box's interface.** Routes are keyed by protocol, then path or name, then verb. Today's protocols are `http`, `sse`, `mail`, `mcp`, and `timer`, and the verbs include `upload` and `asset` [010 §Start with Hello World; 040 §The manifest; 038 §Converting mail into routes; 050 §Tools are routes; 045 §Host-level timers; 060 §Uploading through a route; 060 §Asset data routes]. The C interface the box sees is generated using the WASM reactor pattern [010 §Start with Hello World]. Platform keys are hyphenated, and names people choose use underscores [010 §Start with Hello World].

**Identity and access.** A user is anyone with a secure context from an OAuth flow [015 §Identity and Access]. Access is gated by flat, hierarchy-free **grant role** strings, with `/` reserved for namespaces, requirements written in disjunctive normal form, deny by default, and `"public": true` as the only opt-out [015 §Grant roles]. Routes can grant and revoke roles, but only from options that substitute from the secure context or the target user [015 §Granting and revoking roles; §Scoping roles by substitution].

**Behaviour and data.**
- `boundary` sets the shape of networking, `lifecycle` sets whether an isolate outlives a request, and a per-isolate budget bounds it [010 §Start with Hello World].
- Data is reached through strategies whose scope comes from server-held context, and the generated functions take no id at all [020 §Generated code; §Where context comes from].
- Writes, grants, uploads, and network side effects all ride one atomic write set and outbox [025 §Batched writes and no torn writes; 035 §The Outbox; 015 §Granting and revoking roles; 060 §Taking ownership].

**Time, files, keys, and UI.**
- Time arrives as host timers and data-driven schedules [045 §Host-level timers; §Data-driven timers].
- Files arrive through a preprocessing upload pipeline with a ledger and system-level garbage collection [060 §The upload ledger; §Mark and sweep].
- Keys live under a single vault-held root key with envelope encryption [064 §Envelope encryption].
- UI is served by content negotiation, logic-less templates, and a private backing tree [070 §One route, many audiences; §Templates; §One backing tree].

**Agents and the edge.** Agents use MCP routes that mirror HTTP and can't call HTTP routes unless those opt in [050 §Who is calling]. Around all of it, the edge is rented so that the host stays small [099 §Keeping the host small].

## 4. What is unique

Good news first, because the good news is *very* good.

### 4.1 Removing words, now in every layer

Yesterday this was the crown jewel. Today it has been applied *everywhere*, which is the mark of a real principle rather than a clever trick:

- **Files:** box-side functions are scoped to a folder the context resolves, so a box can't name someone else's file [060 §Asset data routes].
- **Keys:** a credential name can only substitute from the secure context [064 §Per-user keys].
- **Grants:** option strings can never come from what the caller typed [015 §Scoping roles by substitution].
- **Agents:** an agent can't even *see* a tool its person couldn't call [050 §What the host does for free].
- **Schedules:** a schedule can't compute anything, because it only names fields [045 §Data-driven timers].

Each one is the same move, "we don't frown upon the wrong action, we remove the words for it" [030 §Bringing in a service], and each one is enforced by the host rather than by hoping.

### 4.2 Flat roles with no hierarchy

Making grant roles dumb strings, with no inheritance, so that "who can make someone an admin?" is answered by searching manifests [015 §Granting and revoking roles], is an audit property most role systems give up on day one. Pairing that with `/` namespaces that can't be forged by substitution [015 §Grant roles] gives multi-tenancy without a policy language. Lovely!

### 4.3 System-level garbage collection with a forcing function

The upload ledger has a rule that *every* upload is settled at commit as attached, an asset, or orphaned [060 §Taking ownership]. Add the explicit stance that drafts are a product decision while collection is a system one [060 §Taking ownership], and you get the rarest of things: an upload system where stranded bytes are impossible by construction. Bytes also outlive backup retention [060 §Mark and sweep], which most systems forget until the first restore.

### 4.4 Agents as a narrower interface, not a different user

"Agents are simply users acting on behalf of a user" [050 §MCP]. They inherit exactly their person's requirements [050 §Permissions, mirrored], but they can reach only the deliberately small `mcp` surface [050 §Who is calling]. Dangerous actions are gated by which write channels exist in the agent's box [050 §Isolating agents in their own box]. That is a cleaner answer to agent safety than confirmation dialogs, and I say that having proposed confirmation dialogs yesterday!

### 4.5 Time without a little language

Schedules name fields (`at-field`, `zone-field`), and all date math lives in the box that writes the row [045 §Data-driven timers]. That keeps the manifest declarative and auditable, and it dodges the "restrictions turning into a programming language" trap the author feared [030 §Starting small].

### 4.6 Everything from yesterday, still

All of these remain as distinctive as ever:
- signature-keyed isolate sharing [010 §Start with Hello World; 020 §Where context comes from],
- the predictive checker [025 §Can a box even behave well?],
- signal-only pub/sub [040 §Why the last write is all that matters],
- capability email addresses [038 §What makes this special].

## 6. Limits

### 6.1 The goal change, and why it is wonderful news

Goal 2 now says a product may be maintained **for its external dependencies only**, and never changes capabilities or UI. That reshapes the limits:

- **Schema evolution drops in priority.** A new column is a capability change, which is out of scope, so compatibility views (yesterday's 5.7) matter far less.
- **Dependency pinning rises to the top.** Every OpenAPI document [030 §Bringing in a service], special provider [038 §Sending mail], and type document [036 §Changing a type] is now *the* maintenance surface. Its versioning must be first-class.
- **UI must be frozen with the product.** Templates already deploy with the box [070 §Templates]. But the host's **default layout and stylesheet** [070 §Helpers] and its rendering of markdown [070 §Markdown] would change a product's look if the host changed them. Under goal 2, that's a violation.

### 6.2 The limits

1. **The approval queue and deploy flow are undesigned.** It's the governance backbone [010 §Start with Hello World] and the bottleneck at scale, yet there is no document for how a change is submitted, diffed, risk-tiered, approved, rolled out, or rolled back.
2. **The copy boundary is unspecified.** How structs, strings, and handles cross between host and guest memory, who allocates, and how long pointers stay valid are all implied by examples but never stated [010 §Start with Hello World; 020 §Generated code]. A one-shot build would have to invent this.
3. **The checker's cost model is unspecified.** "Worst-case reads multiplied by the per-row cost" [025 §Can a box even behave well?] needs real numbers and units, or the checker can't refuse anything with confidence.
4. **Dependency pinning isn't versioned.** Special providers publish an OpenAPI spec [038 §Sending mail], but the spec has no version, so an adapter change silently changes every product that uses it. That breaks goal 2.
5. **Host-owned rendering isn't pinned.** The default layout, markdown renderer, and helper script [070 §Helpers; §Markdown] are host code that can change a product's UI. That breaks goal 2.
6. **The query vocabulary is thin.** `by_id` and `by_index` [020 §SQL and solo]. Hearth's features mostly fit, but trade products need date ranges, search, and totals.
7. **There are no per-tenant quotas.** Budgets are per request, per isolate [010 §Start with Hello World], and per agent session [050 §Agentic considerations], but nothing caps a tenant's daily calls, storage [060 §The upload ledger], or emails.
8. **User-supplied URLs.** Hearth fetches people's ICS calendar links, which no capability covers yet. That's still an SSRF hole waiting for a design.
9. **Sequencer granularity.** "One sequencer per scope" [025 §Cache coherency and sequencers] still risks making ordinary multi-strategy routes non-atomic [025 §How atomic is atomic?].
10. **Observability and telemetry scoping** remain deferred [010 §Start with Hello World]. Monitoring is a data path that can leak around the boundary.
11. **The trusted computing base:** the host is C++ and now parses OAuth, WebAuthn, images, archives, markdown, and templates [010 §The Manifest; 015; 060; 070]. The trusted base grew today, *a lot*.
12. **The migration design is missing**, yet it's referenced [020 §Data Flow; 025 §First, structured data that can version and live migrate].

### 6.3 Cross-document inconsistencies

- **Two ways to place a file.** 070 places objects with a strategy `key` like `"{tenant}/jobs/{job_id}/"` [070 §Objects and attachments], while 060 places uploads with a route `folder` [060 §Uploading through a route]. Two mechanisms do one job; pick one.
- **Deny by default vs. timers.** 015 says every route without requirements is refused [015 §Grant roles], but 045 says timer routes carry none [045 §Host-level timers]. 015 needs the stated exception.
- **The verb list.** 037 lists HTTP verbs [037 §Everything a request can carry], while `upload` and `asset` are manifest verbs defined elsewhere [060 §Reasoning as a preprocessing step; §Asset data routes].
- **Leftovers from yesterday:**
  - `bool` vs `boolean` [037 §Everything a request can carry; 036 §A strict subset],
  - `mail_user` vs `mailer_send_message` and service-level `operation` [030 §Bringing in a service],
  - the hard-coded `signal == 42` [010 §Start with Hello World],
  - the undefined `token` type [038 §Converting mail into routes],
  - the incomplete `response` list in 010's schema table [010 §Start with Hello World].
- **The secure context's contents are spread out.** 050 adds an agent `client_id` [050 §Who is calling], which 015 doesn't list [015 §Identity and Access]. Somewhere, one table should list everything the secure context can hold.

## 7. Proposals

### 7.1 Write the ABI document (for limit 2)

Add `012.TheBoundary.md`. It would cover:
- a linear-memory layout for every generated type,
- who allocates (I'd suggest a **host-written, guest-owned arena per request**, reset when the request ends),
- string encoding (UTF-8 with explicit lengths, as the examples already imply [010 §Start with Hello World]),
- how long a pointer stays valid (for the duration of the call, as 050 already says for events [050 §Tools are routes] and 010 for events [010 §Start with Hello World]),
- integer widths (already fixed width [010 §Start with Hello World]).

This is the single biggest boost to one-shot readiness (§12).

### 7.2 Write the deploy and approval document (for limits 1 and 4)

Add `080.Deploy.md`, where an artifact is the manifest, the module, the templates, the types, the schemas, and the pinned dependency specs, all addressed by one hash. The flow:

1. **Submit:** an agent pushes an artifact.
2. **Check:** the checker produces the reports [025 §Where torn writes are possible; 036 §Changing a type].
3. **Tier:** green, amber, or red (yesterday's 5.12).
4. **Approve:** a human approves amber and red.
5. **Roll out:** shadow traffic, then a canary, then everyone [000 §The Foundational Thinking].
6. **Roll back:** a single command.

Dependency-only updates (goal 2's one allowed kind of change) get their own fast lane. The checker *proves* that nothing but pinned dependency specs changed, so the product's capabilities and UI are byte-for-byte identical.

### 7.3 Version every dependency, including the host's own (for limits 4 and 5)

- **Special providers publish versioned specs.** A manifest pins `"provider": "amazon-ses@1"`, and the host keeps `@1` working forever as an adapter on top of whatever SES becomes [038 §Sending mail].
- **Host rendering is pinned like a dependency.** The manifest names its `"layout": "default@3"`, `"markdown": "commonmark@1"`, and `"helpers": "client@2"`, so a host upgrade never changes a deployed product's pixels [070 §Helpers].

Both make goal 2's promise checkable rather than hopeful.

### 7.4 A cost model with units (for limit 3)

Give each access pattern a declared cost in **row reads**, each external call a cost in **calls**, and each byte a cost in **bytes**, with host-measured calibration that converts them to milliseconds per machine class. The checker then reports a worst case in milliseconds against `timeout-ms` [010 §Start with Hello World], and refuses routes that can't fit.

### 7.5 Tenant quotas (for limit 7)

Add a `quotas` block at the product level:

```json
{
	"quotas": {
		"per-tenant": {
			"requests-per-day": 100000,
			"external-calls-per-day": 5000,
			"emails-per-day": 500,
			"storage-bytes": 5368709120
		}
	}
}
```

The ledger already knows storage [060 §The upload ledger], and the egress audit already counts calls [030 §Consequences for the box], so enforcement is mostly bookkeeping.

### 7.6 A `fetch` capability (for limit 8)

The same as yesterday's 5.11, now with a home. An `external` entry with `"kind": "fetch"`:
- reads its URL from a data field (the `-field` style from 045 [045 §Data-driven timers]),
- allows only https or webcal,
- blocks private addresses after resolution,
- caps size and time,
- caches on the host,
- has `effect: "none"` [035 §Safe calls and effectful calls].

### 7.7 Sandbox the parsers (for limit 11)

Run image, archive, markdown, and template processing **in WASM themselves**, as host-owned boxes with fuel and memory limits. The host stays C++, but the riskiest parsing moves into the same jail the design already trusts [000 §The Foundational Thinking]. That turns limit 11 from "rewrite the host" into "eat our own cooking". Delicious!

### 7.8 Reconcile the inconsistencies (for 6.3)

- **File placement:** keep the store-level `key` in 070 as the *only* placement, and let 060's route `folder` be a sub-folder appended to it.
- **Timers:** add "timer routes are host-only and exempt" to 015's deny-by-default rule.
- **Verbs:** add one sentence in 037 listing manifest verbs: `upload`, `asset`, `subscribe`, `tool`, `resource`, and `fire`.
- **The secure context:** add a table of everything it can hold to 015: `user_id`, `client_id`, `tenant`, `timer/*`, and so on.

### 7.9 Two access patterns before SQL (for limit 6)

Add `by_range` (an index plus a limit) and `aggregate` (a schema-declared view refreshed on commit). Together they cover "this week's jobs" and "this month's revenue", which is most of what a trade business asks of its data, while keeping the checker's worst case computable [025 §Can a box even behave well?].

## 8. Security evaluation

### 8.1 By adversary

**A malicious or buggy box.**
- *Strengths, which grew today:*
  - no sockets [030 §The Network],
  - no ids [020 §Generated code],
  - no recipients [030 §Bringing in a service],
  - no paths, only handles [060 §Uploading through a route],
  - no keys [064 §The invariants],
  - no cookies [070 §Keeping browsers safe],
  - no raw HTML from markdown [070 §Markdown],
  - an atomic write set covering data, grants, uploads, and side effects [025; 015 §Granting and revoking roles; 060 §Taking ownership; 035].
- *Gaps:*
  - The `html` response type [070 §One route, many audiences] lets a box ship its own scripts. CSP limits the damage [070 §Keeping browsers safe], but a box can still phish within its own origin.
  - Covert channels between isolates on a shared host.
- *Rating:* **strong**.

**A malicious tenant user.**
- *Strengths:*
  - flat roles [015 §Grant roles],
  - substitution limits on options [015 §Scoping roles by substitution],
  - default deny [015 §Grant roles],
  - no self-revoke without a flag [015 §Granting and revoking roles],
  - folders that can't escape [060 §Uploading through a route],
  - preprocessing of hostile files [060 §Reasoning as a preprocessing step],
  - listing off by default [070 §One backing tree].
- *Gaps:*
  - no per-tenant quotas (limit 7),
  - no client idempotency keys on retried POSTs (open since yesterday's §6.2),
  - **email bombing:** `/identity/email/start` can be pointed at a victim's address. Rate limits are per address and per client [015 §Sign-in screen requirements], but the system mailer's reputation is shared by every tenant [038 §Sending mail].
- *Rating:* **good**.

**An external attacker.**
- *Strengths:*
  - passkeys first,
  - client origins shown, with unverified clients marked,
  - typed device codes,
  - no account enumeration [015 §Sign-in screen requirements],
  - SMTP-time verdicts [038 §What makes this special].
- *Gaps:*
  - Internal hops (Caddy to host, Stalwart to host) are still unauthenticated on paper.
  - SSRF via user URLs (limit 8).
  - The open `/oauth/register` endpoint is spammable [015 §The implicit API].
- *Rating:* **good, with three fixes needed**.

**An operator or compromised infrastructure.**
- *Strengths:*
  - the vault holds only the root key [064 §Envelope encryption],
  - AEAD binds each ciphertext to scope and owner,
  - secret access is logged by name [064 §Envelope encryption],
  - key backups are kept apart from data [064 §Decent practices],
  - a warning on absolute-owner power [015 §A multi-tenant example],
  - write-only backup credentials [064 §Decent practices].
- *Gaps:*
  - The operator can read every per-user key, which is stated honestly [064 §The limits of this design].
  - Telemetry is still unscoped.
  - The tenant-facing audit of absolute-owner actions is deferred [015 §A multi-tenant example].
- *Rating:* **adequate, and honestly documented**, which I adore.

**Supply chain.** Artifacts are atomic [010 §Start with Hello World], but modules aren't signed, and dependency specs aren't hashed into identity (§7.2). Today also brought a much bigger set of bought parsers (images, archives, OAuth, WebAuthn) that must be pinned and audited.
- *Rating:* **needs work**.

**An agent acting for a user.**
- *Strengths:*
  - the `mcp`-only surface [050 §Who is calling],
  - identical requirements [050 §Permissions, mirrored],
  - filtered discovery and per-session quotas [050 §What the host does for free; §Agentic considerations],
  - reviewed descriptions [050 §Tools are routes],
  - isolation by box [050 §Isolating agents in their own box].
- *Gaps:* an agent holding a person's `owner/{tenant}` role can do anything that person can do through `mcp` tools. Tool narrowness is a *product* responsibility the checker can't enforce.
- *Rating:* **good**, with product discipline required.

### 8.2 Under real traffic

What actually happens on the first busy Monday, joyfully catalogued:

- **Credential stuffing and email bombing on day one.** These are mitigated by rate limits [015 §Sign-in screen requirements], but the shared system mailer's sender reputation is the real casualty. **Containment:** give identity mail its own dedicated sending domain and per-destination daily caps.
- **Noisy neighbours.** One tenant's import job pegs a CPU. Per-request timeouts help [010 §Start with Hello World], but without tenant quotas (limit 7), fairness is luck. **Containment:** a fair-share scheduler per tenant in the host.
- **Retry storms at third parties.** When a vendor is down, every outbox element retries [035 §Delivery], and recovery becomes a thundering herd. **Containment:** a circuit breaker per external service, with jittered backoff shared across all boxes [030 §Consequences for the box].
- **The 6am cliff.** Thousands of digests fire at once in one timezone. This is spread by design [045 §The rules of time], but the outbox and the mailer then queue a burst. **Containment:** let the mailer's rate limit drive backpressure into timer spreading.
- **SSE connection counts.** Every open dashboard holds a connection [040 §The manifest]. A deploy that restarts the host drops them all, and they all reconnect at once [040 §Why the last write is all that matters]. **Containment:** jittered reconnects in the helper script [070 §Helpers], and coalescing absorbs the evaluations [040 §The quadratic problem].
- **Disk full.** Uploads, ledgers, and SQLite files share one disk. **Containment:** storage quotas, and refusing uploads before the data disks fill.
- **Vault outage during a restart.** The host can't start [064 §The limits of this design]. **Containment:** don't restart during vault incidents. Planned restarts check vault health first.
- **Image parser zero-days.** Hostile uploads are a classic remote code execution path. **Containment:** §7.7, with parsers in WASM.
- **Restores.** A restore brings back a database that references orphaned uploads. **Containment:** already handled, since bytes outlive retention [060 §Mark and sweep]. Splendid!

### 8.3 Top ten security tasks

1. Authenticate internal hops (Caddy, Stalwart, NATS) with mutual TLS or loopback-only listeners.
2. Per-tenant quotas, including emails per day (§7.5).
3. A dedicated sending domain for identity mail, plus per-destination caps.
4. Sandbox the hostile-input parsers in WASM (§7.7).
5. Signed, content-addressed artifacts, with dependency specs hashed in (§7.2).
6. Rate limits and operator approval options for `/oauth/register`.
7. Client idempotency keys folded into outbox keys.
8. A `fetch` capability with private-address blocking (§7.6).
9. Telemetry inheriting the data boundary.
10. A tenant-visible audit of absolute-owner grants [015 §A multi-tenant example].

## 9. Operating the system

### 9.1 Humans

- **The operator** runs Caddy, Stalwart, the host, Litestream, and a vault on one machine [099 §One machine, then many]. Their day is the approval queue: reading manifests, torn-write reports, and type-change classifications rather than code [025 §Where torn writes are possible; 036 §Changing a type].
  - *They get paged for:* vault health, disk, the mail queue, the dead-letter queue [035 §Delivery], and sweeper anomalies.
  - *What delights them:* a bad box shows up as errors on one project, not as a breach [000 §The Foundational Thinking].
  - *What frustrates them:* no deploy tooling exists yet (limit 1), and with a thousand products, the queue *is* their job.
- **A tenant owner (Bob the plumber)** signs in with a passkey [015 §Sign-in screen requirements], manages his team with roles like `member/bobs_plumbing` [015 §A multi-tenant example], enters his SES credentials once on a host screen [064 §Per-user keys], and never sees a manifest. Bob's experience is excellent, *if* the products are good. Bob can't see what the operator did to his tenant yet [015 §A multi-tenant example].
- **An end user** sees fast pages rendered from templates [070 §One route, many audiences], uploads photos that quietly lose their GPS data [060 §Reasoning as a preprocessing step], and gets reminders at the right local time [045 §Data-driven timers].

### 9.2 Agents

- **An agent building boxes** writes C, Rust, or anything that compiles to WASM, plus a manifest, then submits them. It gets crisp, mechanical feedback from the checker [015 §Granting and revoking roles; 025 §Can a box even behave well?].
  - *What delights it:* it never writes HTTP, JSON, MIME, SQL connections, or auth code [037; 038; 020].
  - *What frustrates it:* there's no specified copy boundary (limit 2), no local dev loop described, and a hard-coded `signal == 42` in the examples that will mislead it.
- **An agent acting for a person** connects through the device flow [015 §How an agent logs in], sees only the tools its person may use [050 §What the host does for free], and runs out of quota before it runs up a bill [050 §Agentic considerations].
  - *What frustrates it:* typed errors are good [050 §The result vocabulary], but nothing tells it *why* a tool is missing, which is the point. Products must write tool descriptions with care [050 §Tools are routes].

### 10.2 Goal 2: maintenance only for external dependencies

For a product to change only when a dependency changes:

- **Product capabilities are frozen by the artifact** [010 §Start with Hello World]. ✅
- **UI is frozen with the templates** [070 §Templates]. ⚠️ Host rendering isn't pinned (§7.3).
- **Dependencies are pinned.** ⚠️ OpenAPI documents are pinned [030 §Bringing in a service], but provider specs aren't versioned (§7.3).
- **Dependency-only updates are provably dependency-only.** ❌ This needs the deploy design (§7.2).
- **The host can change underneath without breaking products.** ⚠️ There's no ABI versioning document yet (§7.1).

**Verdict:** the design's *philosophy* fits goal 2 beautifully. Boxes own only logic [025 §What the box never thinks about]. The *mechanisms* that prove it, versioning and the deploy fast lane, are the next documents to write.

## 12. One-shot readiness

**How complete the spec is for a decent one-shot build of the Hearth-capable MVP: about 40 per cent**, up from about 25 per cent yesterday.

**What a one-shot build would get right:**
- the manifest shapes and examples [010; 015; 020; 037; 045; 050; 060; 070],
- the generated function names and patterns,
- the identity schema and endpoints [015 §Sessions, schema, and the login API],
- the upload ledger and states [060 §The upload ledger],
- the key schema [064 §Envelope encryption],
- the bus semantics [040],
- the timer rules [045 §The rules of time],
- the HTTP behaviours [037].

**Where it would have to guess:**
- **The copy boundary** (limit 2): the most consequential guess.
- **One complete manifest schema.** Fields are spread across eighteen documents, with no single JSON Schema.
- **The checker's algorithms and cost units** (limit 3).
- **The host's configuration format.** Only the identity snippet exists [015 §Bootstrapping the first owner].
- **The deploy and approval flow** (limit 1).
- **The migration and `.schema` format.** The column annotation is a comment [060 §Taking ownership].
- **Error codes and the host's own HTTP error shapes.**
- **Language and library choices** beyond "C++" and "WASM" [010 §The Manifest].
- **A test strategy.** The legacy `PHILOSOPHY.md` hints at one, but it isn't ratified.

**What would raise the number most:**
1. `012.TheBoundary.md`, the memory and ABI spec (+15 per cent).
2. One consolidated `manifest.schema.json` generated from the docs (+10 per cent).
3. `080.Deploy.md`, the artifact, approval, and rollout design (+10 per cent).
4. An end-to-end walkthrough: one Hearth feature, from manifest to C to request to commit (+10 per cent).

With those four, a one-shot build of the skeleton plus data plus HTTP plus identity becomes genuinely plausible.
