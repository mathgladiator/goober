# 021. Identity events: proving addresses, first verifications, and sign-ins

Status: built, at the human's request on 2026-10-28. It extends 013.Identity.md and
`design/machine/006.LocalIdentity.md`. The human chose identity routes over waiting for sources
(023), and a 30-day life for accounts never proved.

## 1. Who is an account

An account exists in a realm only once its address has been proved, with one exception.

- **Typing an address creates nothing.** `POST /identity/email/start` stores a hashed one-time
  code and mails it. The account is created when the code comes back
  (`/identity/email/verify`). A robot typing addresses leaves only a code row, which is deleted
  a day after it expires (`Identity::prune`).
- **A new account holds no roles.** It can call routes whose requirements are `[]` (any
  signed-in user of the realm), and nothing else, until a grant or the config's first owner
  gives it a role.
- **The exception is an invite.** A grant to an address with no account (`grant` tool,
  `goober-host` CLI) creates the account at once, unproved, so the role is waiting at first
  sign-in.

`users.verified_at` records when the address was first proved: set by the first
successful code, NULL for an invite not yet taken up. Realms made before the column existed
count an account as proved if it ever signed in or holds a token.

Since 2026-10-29, an invite that mails someone is 029's: a record in the realm, accepted only
with a sign-in code. A grant to a new address still makes the waiting account described here,
and mails nothing. 029 adds the events `invite-accepted` and `invite-declined`.

**Invites expire.** An account still unproved 30 days after it was made
(`kUnverifiedTtlMs`) is deleted with its roles, and the audit records `user_expired`. The host
prunes every realm in the config, and `_host`, once an hour.

## 2. Events

Every successful email-code sign-in appends to the realm's `events` table, in the same
transaction as the session:

| kind | when |
| --- | --- |
| `first-verified` | the address was proved for the first time: a new account, or an invite taken up |
| `signed-in` | every sign-in, the first included |

A first sign-in appends both, `first-verified` first. Each event holds its id (never reused),
the user's id and email, and the time. Events are kept 7 days (`kEventTtlMs`).

## 3. Identity routes

A box hears events through routes only the host calls:

```json
"routes": {"identity": {
  "first-verified": {"name": "welcome", "timeout-ms": 2000},
  "signed-in": {"name": "on_sign_in"}}}
```

- At most one route per event per box. `timeout-ms` is 1 to 10000; the box's behavior applies
  otherwise. No `public` or `requirements`: nobody else can call them.
- The host calls the route for each event in the realm of every tenant the box serves (its
  domains in the config), as the person who signed in: `user` is them, with their roles, as on
  their own request. The body is JSON:
  `{"event", "event_id", "user_id", "email", "at"}`. `event_id` (`$tenant:$id`) is the same on
  every retry, so a box that must act once can record it.
- The route commits like any request: its writes, outbox elements (mail), and internal calls.

## 4. Delivery

- **After commit, never in the way.** Sign-in only appends the event. The timer thread reads
  events each second and calls the routes on the box pool, so a slow or broken box never
  delays a sign-in.
- **A cursor per route, per tenant**, in `storage/sqlite3/$tenant/timers.db`
  (`goober_identity_cursors`). It survives restarts. A route new to a tenant starts at the
  realm's newest event: it hears what happens from then on, not history.
- **In order, at least once.** Events go one at a time; the cursor moves only past an event
  whose call succeeded (a status below 500, or no response) or was given up. A failed call is
  retried after 2, 4, 8 s... up to 10 minutes, and nothing after it is delivered meanwhile.
  After 8 failures the event is given up, logged to stderr and the access log
  (`"gave_up": true`), and the route moves on.
- **Gone people are skipped.** An event for an account since deleted or disabled moves the
  cursor without a call, except the `deleted` event itself, which is called as nobody (§ 6).
- Each call is an access-log line with method `identity`, the route, the event id, and the user.

## 6. Deleting an account

Added 2026-10-30. A site's engineers needed to erase a person's mail within 30 days of their
account's deletion, and goober had no deletion. The human chose: the account is erased with a
tombstone that keeps the id, and boxes hear a `deleted` event they must act on within 30 days,
with the panel showing which haven't.

**Who deletes.** The person, on `/identity/account` ("Delete my account", a POST with the word
`DELETE` typed, same-origin like every account form; then the cookie is cleared and a plain page
says what happened). Or an operator, with `user_delete {tenant, email | user_id, why}`: tenant-
scoped (030), a changing tool that waits for approval when an agent's approvals are on (035),
and an `audit` log line `user.delete` naming `user:$tenant/$id` and the reason, never the address.
The host realm's operators come from the config and can't be deleted this way.

**What happens, in one transaction in the realm:**

| what | becomes |
| --- | --- |
| sessions, access and refresh tokens (every agent's grant) | revoked |
| unused authorization codes; pending device codes | consumed; denied |
| roles, and roles they granted | removed; `granted_by` cleared |
| pending sign-in codes for the address | deleted |
| the account | `email` = `deleted:$id` (never an address: no `@`), `deleted_at`, `disabled_at`; the row stays, so the id is never reused |
| the address in their events, their audit rows, and invites to or from them | erased (`''` or `deleted:$id`); an open invite to them is revoked |
| terms they accepted | kept: no address, and the record of consent |
| a `deleted` event and a `deletions` row | appended; the row is kept for good, the event 7 days like the others |

**Kept on purpose:** the address's mail blocks and unsubscribes in `consent.db` (029). They are
keyed by a hash, and they protect the person: someone who asked for no mail still gets none
after deleting their account.

**The same address later** signs up as a new person with a new id and no roles. Nothing links
the two.

**The `deleted` event** is delivered like the others (§ 4), to boxes declaring
`"routes": {"identity": {"deleted": {"name": ...}}}`, called as nobody, with the body
`{"event": "deleted", "event_id", "user_id", "at"}` and no address. The box must erase or
anonymize every row about that user id within 30 days.

**Acknowledgements.** A call the box answered under 500 (or without answering) is its
acknowledgement; one given up after 8 tries is `failing`. Both are kept per tenant in
`goober_deletion_acks`. The read tool `deletions {tenant}` lists each deletion with every box
that serves the tenant or holds its data:

| state | means |
| --- | --- |
| `acknowledged` | its route answered |
| `pending` | not delivered yet |
| `failing` | given up after 8 tries |
| `missed` | its route was added after the deletion (a new route hears only what comes after it, § 4): erase by hand |
| `no_route` | it holds the tenant's data and declares no `deleted` route |

A deletion with any box not acknowledged after 30 days is `overdue`. The panel's Operators view
lists the deletions not yet acknowledged everywhere.

## 7. Not built

- Events for passkeys and passwords (they don't exist yet), and for sign-out or grants.
- Replaying history to a new route, or resetting a cursor (an operator tool, when wanted).
- Identity as a 023 source with event routes. When sources exist, this table is the natural
  first host-owned source, and identity routes become event routes over it.
