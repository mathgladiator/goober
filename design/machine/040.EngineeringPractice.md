## 1. What the engineers ran into

Four engineers and a data engineer, working through agents (Grok), sent feedback all day on
2026-10-30. Read together, their friction fell into a few kinds:

| kind | what happened | examples |
| --- | --- | --- |
| Not knowing what a call does | Whether a call goes live, stores dark, or stores nothing; which etag is which; whether it waits for approval | "version_upload goes live at once", file etag vs body etag, page_render vs box_render |
| No way to see before it's live | Gated pages, dark versions, and content deploys checked only once live | "the 303 behavior is unverified until live", no content_deploy dry run |
| Half changes | A client attaching four files per call made broken intermediate revisions and non-atomic deploys | source commits, content deploys |
| Concurrent edits | Several agents editing one shared thing; last writer wins | templates, partials, an input file edited while under review |
| Not knowing what's new | Production ran builds behind main; agents keep the tool list from when they connected | asking for tools that existed |
| Ids and types | Dense per-realm ids, string user references, numbers vs strings | 021's gap, `{"id": 3}` vs `"3"` |
| Data with no undo | A migration, a drop, a bulk load | "partial loads must be repaired by hand" |

## 2. The practices, per kind of change

Every change an engineer or agent makes should be: **described** (the tool says what it
does), **previewable** (a dry run that stores nothing), **reviewable** (a diff, with what
widens), **triable** (exercised for real without reaching people or data), **atomic** (one
change, however many calls it took to describe), **safe against teammates** (if_etag), and
**undoable** (a version to go back to, or a snapshot), then **watched** after it lands.

| change | preview | review | try | atomic | if_etag | undo | watched |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Box version | `version_upload {dry_run}` (+ unstored `schemas`) | `review`/`widens`, `version_diff` | `route_try` (HTTP routes, tools, mail) | stored dark, then `version_promote` | — | `version_promote` the old one, `box_disable` | `version_health`, `perf_report` |
| Source | `source_build` | `source_diff` | — | `source_stage` | base_rev conflicts | `source_revert` | build logs kept |
| Pages and files | `page_render`, `page_lint {body}`, `content_deploy {dry_run}` | `changes` with diffs | `page_render {as: "signed_out"}` | `content_stage`, `content_deploy` | every write (`if_etag`) | kept versions (partials), the change log | `content_deploy` verify with `expect_status` |
| Templates, partials | `page_render` / `box_render` with unsaved ones | `changes` | the same | in a `content_deploy` | yes | partials keep ten versions | — |
| Schemas | `schema_check` | warnings | — | — | names never reused | — (expand only) | — |
| Data moves | `job_dry_run` on copies | the dry run's report | the dry run | batches with a kept cursor | — | a snapshot before every real run | `job_status` |
| Databases | `db_unbound` | — | — | — | — | `db_snapshot`, `db_restore_to_new`; drops only by a person, snapshot first | — |
| Flags | — | `flag_list`, the change log | — | one value | — | set it back | flags read are in the access log |
| Mail routes | `mail_route_check` | in `review` | `route_try {mail}` | move with dark + promote | — | box_disable / box_enable | `mail_activity` |

## 3. Built overnight (2026-10-31)

- **`route_try`.** Any stored version's HTTP route, dark ones included, called through the
  real request path (gate, declared inputs, template by Accept, partials, ETag, Vary), as a
  visitor or as an account looked up and never signed in. GETs are read-only on live data;
  writes run on copies, thrown away, and report the rows they changed and what they would
  have queued. Marked in the access log; kept out of statistics. Observers may try GETs only.
- **Reviews and widenings.** Every `version_upload` answers `review` and `widens`: each change
  that adds reach (a grant, a write, a route made public, a new mail address, service, From
  address, domain, browser caching, a flag value) in sentences. A person approving a held
  upload sees them. `version_diff` compares any two stored versions.
- **`version_health`.** After a promote, each route's failures and latency against the version
  it replaced, with the rollback named. It never rolls back by itself.
- **A snapshot before every real job run** of each database the box may write; a run whose
  snapshot can't be taken doesn't start.
- **`if_etag` on every content write**: partials and static files joined pages and templates.
- **Content deploys**: dry runs that render and lint signed out, staging across calls,
  expected statuses and locations for gated pages, character-counted titles.
- **Sign-in keeps a deep link's `#fragment`.**
- **`whats_new`**: `host-src/CHANGES.md`, built in, says what each build lets agents do.
- **Integer arguments accept strings of digits**, so "ids are strings" never refuses a call.

## 4. Where engineers will still get hurt

1. **Several kinds of change that belong together.** A feature is often a schema, a box
   version, templates, and a flag. Each has its own preview and undo; since 2026-10-31 a change
   set (042) reviews, applies, and rolls them back together.
2. **Schemas only grow.** 420's contractions, renames, and upgrade boxes aren't built, so a
   wrong column lives forever or needs a job and a new table.
3. **Timers can't be tried** against a dark version. HTTP routes, MCP tools, and mail routes
   can (route_try, on copies for anything that may write), since later the same night.
4. **Health is bounded by the local logs**: version_health reads every access-log file still
   on the machine (7 days) by the window, within a budget it reports; older windows would need
   the sealed archives in the bucket.
5. **Mail authenticated only by SPF** gets no `from_user_id`.
6. **Production lags main.** Most of the day's "it doesn't work" was a build hours behind.
   `whats_new` helps agents notice; it doesn't close the gap.
7. **A version that widens reach still goes live alone** when the agent's approvals are off.
   The widening is said, but nobody has to read it.

## 5. Decisions for the human

| # | decision | recommended |
| --- | --- | --- |
| 1 | A version whose review widens reach (a new grant, a public route, a new From address) waits for a person even when the agent's approvals are off | **Yes.** Narrowing and neutral changes stay fast; only more reach needs a person. |
| 2 | Change sets: one reviewed, approved, and rolled-back unit across schema, box versions, content, and flags | **Decided 2026-10-31: build it** ("For the one change, rolled back, it should be execute"). Built the same day: 042.ChangeSets.md. |
| 3 | Automatic rollback on a `version_health` regression | **No.** Keep findings for a person or agent; an automatic rollback can fight a fix in progress. |
| 4 | Agents promote only versions they tried | **A warning, not a refusal**: `version_promote` answers when no `route_try` or dry run touched that version. |
| 5 | Schema evolution (420): contractions and upgrade boxes | **Next large piece of work**, after change sets. |
| 6 | Deploy cadence | **Deploy after each merged batch** the human reviews, so production is never a day behind. |
