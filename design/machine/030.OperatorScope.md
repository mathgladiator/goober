# Operator scope: focusing an operator on some tenants

A design, built the same day. On 2026-10-29 the human asked, for when the host has several
tenants, that each operator can be focused on one tenant, some, or all. It's a per-operator
setting, changed in the operator UI, so agents acting as an operator (Grok) can be held hard
to one site for safety.

## 1. The setting

- **What it holds.** An operator's scope is `all`, or a list of tenants. Every operator starts
  at `all`, so nothing changes until someone narrows one.
- **Who it applies to:**
  - **a person in `identity.operators`**, by address. It covers everything they do: the panel,
    and every agent signed in as them through the operator issuer (023);
  - **an operator token** (`goober-host token create`), by its name;
  - **the config's `operations-token`**, as `config`.
- **Where it's kept.** `storage/operations/scopes.json`: one entry per operator, with
  `tenants`, `set_by`, and `at`. It's written atomically, and read again on every call, so a
  change applies at once.

## 2. Who changes it

- **Only in the panel.** There is no MCP tool that changes a scope, so no agent can widen its
  own, or anyone's. This follows 410's rule for approvals: a human in the UI.
- **`host:owner`** sets any operator's scope, including widening it back to `all`.
- **`host:operator`** may only narrow their own: pick a subset of what they have. A scope
  never widens below the owner.
- **`host:observer`** can't change it.
- **Requests.** The panel posts `/api/write/scope` with JSON and a same-origin `Origin`, like
  its reads (028 § 2), and adds a `confirm` field the page fills from the dialog.
- **The record.** Every change goes to the change log as an operator action
  (`operator_scope_set`), with the operator, the old scope, the new scope, and who set it.
- **The CLI.** `goober-host token create --tenants shop` mints a token that starts
  focused. That's for a human at a shell; the panel can widen it later.

The panel shows the scope on every page: "Focused on shop" in the header, or nothing for
`all`. Its **Operators** view lists every operator and token with their scope, and is where
the owner edits them.

## 3. What a focused operator may do

The scope is enforced in the host, on every tool call, from the panel and from
`/goober-operations-mcp` alike. Every tool has a rule. A tool without one is refused for a
focused operator (deny by default), and a test fails when a registered tool has no rule.

| rule | tools | allowed when |
| --- | --- | --- |
| **tenant** | content, pages, partials, templates, attachments, PWA and push, mail templates, invites, realm and roles, clients, agent tokens, outbox retries, `db_*`, `timer_run`, `traffic`, `changes`, `key_set` and `key_delete` | `tenant` is given and in scope. When `tenant` is optional and left out (meaning every tenant, or the system's keys), the call is refused |
| **box** | `box_graph`, `box_logs`, `version_get`, `version_list`, `version_promote` | every tenant the box serves is in scope. A box on `"*"` serves every tenant, so it's out of reach |
| **manifest** | `version_upload` | the uploaded manifest's domains all belong to tenants in scope |
| **domain** | `mcp_tools_preview`, `route_check` | the domain's tenant is in scope |
| **schema** | `schema_put` | no box serving an out-of-scope tenant binds the schema |
| **project** | `source_*` | every box and site the project's `goober.project.json` names is in scope, checked on the head revision. `source_deploy` checks again at deploy, and `source_create` needs its `tenant` in scope |
| **ticket, change, job** | `attachment_upload_part`, `change_get`, `source_job` | the tenant, box, or project behind the id is in scope |
| **filtered** | `domain_list`, `box_list`, `source_list`, `timers_list`, `outbox_dead_letters` | always; rows outside the scope are left out |
| **open** | `box_guide`, `site_guide`, `rust_binding`, `library_list`, `library_get`, `schema_list`, `schema_get`, `web_fetch`, `operator_scope` | always; they read nothing of any tenant |
| **host** | `host_health`, `hot_boxes`, `access_log`, `operator_actions`, `key_list`, `backup_*`, `crawl_*`, `web_optout` | never; they read or change the whole host |

- **`tools/list`.** A focused operator sees only the tools some call could pass, so the host
  tools aren't listed.
- **A refusal** is a tool error naming the scope and how it changes: "operator
  oauth:ann@example.com is focused on shop; widen it in the panel's Operators view".
- **`operator_scope`** (read) tells any caller its own scope, so an agent can learn where it
  stands.
- **The panel**, for a focused person:
  - leaves out what it can't show: the host's health, heat, and access log;
  - shows traffic, changes, data flow, and the database explorer for the tenants in scope;
  - limits its tenant pickers to the scope.

## 4. What it doesn't do

- **It doesn't lower roles.** A focused `host:owner` is still an owner inside the scope. A
  `host:observer` still only reads.
- **It isn't a tenant role.** Tenant realms are untouched. The scope says which tenants an
  operator acts on, not what anyone may do on a site.
- **Agents on a site's `/mcp`** are tenant-realm users (012) and were never operators. The
  scope doesn't apply to them.

## 5. Tests

- **Every registered tool has a rule** (the deny-by-default check).
- **Tenant tools:** one in scope passes, one out of scope is refused, and a left-out optional
  tenant is refused.
- **Boxes:** a box on `"*"` is refused, and one on a scoped domain passes. The same for
  `version_upload` by its manifest.
- **Filtered lists** drop other tenants' rows. `tools/list` hides the host tools.
- **The panel:**
  - the owner widens and narrows anyone;
  - an operator only narrows their own;
  - an observer is refused;
  - a cross-origin post is refused;
  - the change log records each change.
- **OAuth:** an agent signed in as a focused person is focused.
