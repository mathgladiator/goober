# Databases

> Status: machine-authored and **not ratified**. Recorded on 2026-10-26, when the human
> asked to "get databases" and for an administrative tool to poke the databases each
> tenant has. It builds the first data pattern of `020.DataFlow.md` and
> `028.Query.md`, using decisions already recorded in `005.FirstVersion.md` §11. The code
> in `host-src/` follows it. Where it departs from a human doc, §9 names the doc and
> section, and the human doc wins until it is updated.

## 1. What v1 builds

One pattern: **direct SQL** (028.Query.md § Direct SQL access), because it is the one
that needs no generated code, so a box written by hand in WAT, C, or Rust can use a
database today. The access patterns (`by_id`, `by_index`), iterators (`query`), and timers
(`by_timer`) are accepted in a manifest with a warning and do nothing yet.

| piece | v1 |
| --- | --- |
| Schemas | JSON `.schema` artifacts (Q14), stored once by name, immutable. §2 |
| Databases | One SQLite file per tenant per database, created on first use: `storage/sqlite3/$tenant/databases/$database.db`. §3 |
| Manifest | `data.sqlite3.$strategy` with `pattern: "sql"`, naming the tables, columns, and operations the box may use. §4 |
| Boundary | Two imports, `goober_sql` and `goober_result_read`. §5 |
| Transactions | One per database per request, committed when the box answers below 500. §6 |
| Operators | MCP tools and a CLI to list, describe, query, and change any tenant's databases. §7 |

## 2. Schemas

A schema is a partial set of a database's tables, pinned at one version
(020.DataFlow.md). Its name carries the version, like `guestbook1`.

```json
{
	"schema": "guestbook1",
	"tables": {
		"entries": {
			"columns": {
				"id": { "type": "int64", "primary-key": true },
				"name": { "type": "string", "max-length": 80 },
				"message": { "type": "string", "max-length": 2000 },
				"created_ms": { "type": "int64" },
				"approved": { "type": "boolean", "default": false },
				"rating": { "type": "int32", "nullable": true }
			},
			"indexes": {
				"entries_by_created": { "columns": ["created_ms"] }
			}
		}
	}
}
```

- **Types** are the 036.Json.md shorthands that make sense for a column: `int32`, `int64`,
  `double`, `float`, `boolean`, and `string`. Tables are `STRICT`, so SQLite itself refuses
  a value of the wrong type. A boolean is an integer checked to be 0 or 1, and
  `max-length` becomes a `CHECK` on the string's length.
- **Columns** are `NOT NULL` unless `nullable` is true. `default` is a literal.
- **The primary key** is one `int64` column marked `primary-key`, which becomes SQLite's
  rowid. A table that names none gets `id`. Ids come from SQLite, not from the host
  ranges of 021.PrimaryKeys.md (§9).
- **Names** of tables, columns, and indexes match `[a-z][a-z0-9_]*`, and can't start with
  `goober_` or `sqlite_`, which belong to the host and to SQLite.
- **Stored once.** `schema_put` stores `storage/schemas/$name.schema.json`. Storing the
  same name again with different content is refused, since a schema is a version. A
  manifest that names a schema the host doesn't have is refused at upload.

## 3. Applying a schema: expand only

A database starts empty, and every schema a box brings is applied to it the first time a
request for that tenant touches it. Applying only ever adds (420.Migration.md § Change
kinds, Q43):

| change | applied |
| --- | --- |
| A new table | Created, with its indexes. |
| A new column | Added. It must be nullable or have a default, since rows already exist. |
| A new index | Created. |
| A column the schema leaves out | Left alone: schemas are partial. |
| A column whose type, nullability, or length changes | Refused. |
| An index whose columns or uniqueness change | Refused. |

The host records what each schema added in two host tables inside the database,
`goober_schemas` and `goober_columns`, so it compares against what it declared rather
than against SQLite's own description. An upload whose schema would be refused by any
tenant's existing copy of the database is refused at upload, naming the tenant, so a
deploy never fails halfway through the tenants.

## 4. The manifest

```json
{
	"data": {
		"sqlite3": {
			"guestbook": {
				"schema": "guestbook1",
				"database": "guestbook",
				"pattern": "sql",
				"tables": {
					"entries": { "read": true, "insert": true, "update": ["approved"], "delete": true }
				},
				"row-limit": 500,
				"step-budget": 1000000
			}
		}
	}
}
```

- `database` is a name, and may hold `{!tenant}`. Every database already lives inside its
  tenant's directory, which is what makes the connection unable to see past the scope
  (020.DataFlow.md § SQL and solo).
- `tables.$table` lists what the box may do: `read` and `update` are `true` or a list of
  columns, and `insert` and `delete` are booleans. Every table and column must be in the
  schema. Anything not listed is refused.
- `row-limit` (default 1000) and `step-budget` (default 1,000,000 SQLite VM steps) cap one
  statement; a statement that goes past either fails with an error the box sees.

## 5. The boundary

| import | signature | does |
| --- | --- | --- |
| goober_sql | (strategy_ptr i32, strategy_len i32, sql_ptr i32, sql_len i32, params_ptr i32, params_len i32) -> i32 | Runs one statement through a strategy and returns the length of its result, or -1 for a bad pointer. |
| goober_result_read | (ptr i32, len i32) -> i32 | Copies the last result into box memory and returns the bytes copied. |

`params` is JSON: an array for `?` placeholders, or an object for `:name` ones, holding
null, booleans, numbers, and strings. The result is JSON too:

```json
{ "columns": ["id", "name"], "rows": [[1, "Ada"]], "changes": 0, "last_insert_id": 1 }
```

or `{"error": "..."}`. Integers are JSON numbers when they fit in 53 bits, and strings
otherwise; blobs are `{"base64": "..."}`.

Before a statement runs, the host prepares it with SQLite and checks it with SQLite's
authorizer, as 028 § Direct SQL access plans:

- one statement only;
- every table and column it reads, inserts, updates, or deletes is granted by the strategy;
- no `ATTACH`, `PRAGMA`, transaction statement, or schema change;
- only functions on the host's list of pure ones: aggregates, string, math, date, and the
  JSON functions, so a box can build its response with `json_group_array`. `random()`,
  `randomblob()`, and `load_extension()` are refused; randomness comes from the host.

## 6. Transactions

A request opens each database it touches once and begins a transaction on its first
statement: `BEGIN IMMEDIATE` when that statement writes, `BEGIN` otherwise. When the box
returns, the host commits if the box answered with a status below 500, and rolls back if
it answered 5xx, trapped, timed out, or ran out of fuel. A failed commit turns the
response into a 500. So one request's writes land together or not at all, and a box that
crashes halfway leaves nothing behind.

This is SQLite's own transaction, not the host WAL bundle of 005 §7, which keeps file
changes crash-proof. A database's durability is SQLite's WAL mode with `synchronous=FULL`.

## 7. Operating the databases

**MCP tools**, all acting as host:owner under the dev policy:

| tool | does |
| --- | --- |
| schema_put, schema_get, schema_list | Store a schema, read one, list them. |
| db_list | Every tenant's databases: the boxes and strategies that use each one, its file size, and its tables with row counts. |
| db_describe | One database: its tables, columns, indexes, and the schemas applied to it. |
| db_query | Runs one read-only statement (anything SQLite says is read-only) and returns up to `limit` rows (default 100, at most 1000). |
| db_exec | Runs one `INSERT`, `UPDATE`, or `DELETE`, and returns the rows changed. Schema changes and host tables are refused. Every call is logged to `logs/db.log` with the operator, the tenant, the database, and the statement. |

**The command line** works with the host running or stopped, since SQLite allows readers
beside a writer:

```
goober-host db list --config demo/host.json
goober-host db describe playground guestbook --config demo/host.json
goober-host db query playground guestbook "SELECT * FROM entries" --config demo/host.json
```

and `just db`, `just db-describe`, and `just sql` wrap them.

## 8. Cross-site forms

Since boxes can now write, a POST, PUT, PATCH, or DELETE to a box route whose `Origin`
names another site is refused with 403 before the box runs, as 070.UI.md § Keeping
browsers safe asks of the host.

## 9. What this departs from

| human doc | section | v1 says |
| --- | --- | --- |
| 028.Query.md | Direct SQL access | Writes run in a SQLite transaction per request, not in the host's write set and bundle. |
| 028.Query.md | Direct SQL access | `insert` is granted per table, not per column, since SQLite's authorizer reports inserts by table. |
| 020.DataFlow.md | data.$provider.$strategy | Only `pattern: "sql"` runs; the others are accepted with a warning. |
| 021.PrimaryKeys.md | Host-minted ids | Primary keys are SQLite rowids, and integers cross JSON as numbers up to 53 bits. |
| 005.FirstVersion.md | §7 storage tree | A database is `databases/$database.db`, with no version in the name, since schemas only expand. |
| 420.Migration.md | Change kinds | Only expansions; contraction and upgrade boxes come later. |
