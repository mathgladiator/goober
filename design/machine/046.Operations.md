# 046. Operations: running goober as its one operator

Status: drafted by Claude on 2026-11-03 at the human's request: "Since I've done a bunch with
operations, make sure the design documents reflect all the operational insights." It gathers
what 2026-10-28 to 2026-11-02 taught about running the host in one place. It points to the
documents that hold the detail rather than repeating it. Where it and the code disagree, the
code (`host-src/`) wins and this document is wrong. HUMAN.md is the one-page check; this is
the account behind it.

## 1. The stack around the host

The host is one process that speaks plain HTTP and SQLite. Everything else is rented
(099), and a deploy installs and checks all of it (§ 2).

| piece | what it does | how it meets the host |
| --- | --- | --- |
| Caddy | TLS, certificates, HTTP/2, the public ports 80 and 443 | Proxies each site line to the host on loopback. Holds a request up to 15 s while the host restarts, then answers a JSON 503 with `Retry-After` (HUMAN.md § 5). A domain gets a certificate only when it is on a site line of `/etc/caddy/Caddyfile`; the audit's `caddy` check names any that aren't (028 § 8). |
| `goober-host` (systemd `goober-host.service`) | the host itself, as the `goober` user, from `/srv/goober/host` | `listen.behind-proxy` is on, so `listen.address` must be loopback (127.0.0.0/8 or `::1`): the host believes the proxy's `X-Forwarded-For`, and a config with any other address is refused (043, decided 2026-10-31). `systemctl reload` is `SIGHUP`, which rereads host.json. |
| `goober-backup.timer` | a local copy of storage every night at 03:15, into `backups/<date>/`; the newest 3 dated copies kept with S3 backups on, 14 with them off | Runs `goober-host backup DIR`, which removes the older dated copies itself (A12). It is separate from the S3 nightly and runs whether or not S3 is set (045 § 6). |
| Stalwart (`stalwart`, `goober-stalwart-tls.timer`) | mail in on port 25 | Hands each message to the host's MTA hook over loopback; the box's answer is the SMTP answer (024). A deploy leaves it running unless something it is made from changed. The timer copies Caddy's certificate renewals to it. |
| Amazon SES | mail out: sign-in codes, invites, and boxes' mail through the outbox | The SES API, with AWS keys in the key store (018). Bounces and complaints go to SES's configuration set, not to the host. |
| The S3 bucket | backups off the machine: attachments, sealed nightlies, increments, log archives, the source mirror | Every object is sealed under the backup key before it leaves (019). The same AWS keys. |
| The kernel | | Every deploy turns multipath TCP off, in the kernel and in Caddy (HUMAN.md § 3). Kernel updates are the operator's. |
| bubblewrap and the Rust toolchain | sandboxed source builds (020) | Installed and checked by every deploy unless `--without-rust`. |

The panel is served on its own origin, `operations.domain` (a site line in the Caddyfile like
any other), or on `operations.listen`, reached through an SSH tunnel (028 § 1).

## 2. What a deploy does

`just deploy you@server` builds the `server` preset on the deploying machine, copies the
binary, and runs `tools/server-bootstrap.sh` there (host-src/README.md, HUMAN.md § 5). On the
2026-10-30 rule that the deploy is the sanity check for operating too, it is also the audit:

1. **The gate.** The new binary checks the config (`goober-host check`) before anything
   restarts. A config it refuses stops the deploy with the old host still running.
2. **Ready, or rolled back.** The host restarts and must answer `/goober/ready` with `ok`
   within a minute. If it doesn't, the deploy prints the host's last 60 log lines, puts the
   previous build back (`/usr/local/bin/goober-host.prev`), and fails. The `disk` check can
   block a deploy by design: under 256 MiB free, readiness fails (044 § 3.7).
3. **The outside check.** The server checks itself through its public name, as people and
   agents reach it, against the pages listed for the domain in
   `~/.config/goober/readiness.d/` on the deploying machine (`tools/readiness.py`). The result
   is published at `/goober/deploy` and summed up in `/goober/ready` as `deploy`.
4. **The operations audit** (`goober-host audit`, 028 § 8): the panel, Caddy's site lines, the
   mailer, backups, operators, postal addresses, `www.` redirects, and storage ownership. It
   advises and never fails a deploy; it offers the panel and redirects (yes, not now, never),
   and the `── settings` step asks for what's missing (postal address, mail from address,
   bucket, AWS keys, an operator). `audit.quiet` silences a check for good, visibly.
5. **Everything this host needs**: the services and timers, a C toolchain, cargo with the
   wasm32 target, a real sandboxed Rust build, Stalwart on port 25, and the mail hook. The last
   line must be `✓ every check passed`.

Every step that edits host.json or the Caddyfile copies it first (`*.before-panel`,
`*.before-redirect`, `*.before-settings`, `*.before-tenant`) and puts it back if the host or
Caddy refuses the result. `--add-tenant` launches one more site the same way (028 § 8).

Deploys are fast and frequent while approvals are off (040 § 5, decision 6). The deploy asks for
the human's sudo password, so the human runs it.

## 3. What to watch, and where

### 3.1 From outside

`/goober/ready` is public on every domain. Its `checks` say what is wrong (storage, disk,
limits, identity, boxes, stores, loops, mcp, queue, deploy; HUMAN.md § 1), and it answers 503
when one fails. Its `health` is the last five minutes in ratios, latencies, ages, and gauges,
never volumes (028 § 4.6). `?format=prometheus` gives the same as Prometheus text, always 200.
An uptime checker or a Prometheus pointed at it is today the only thing that can tell anyone
the host is down (§ 9, decision A1). HUMAN.md § 1 names the series to graph and the alert.

## 4. What is kept, and for how long

Everything the host grows on its disk has a time limit and a byte budget, set under
host.json's `limits`; over budget, the derived is dropped oldest first, new work is refused
naming the limit, and what a person must decide on is never deleted (045 § 1). 045 § 3 is the
authoritative table with budgets and floors; this one adds what lives in memory and in the
bucket, so the whole of what goober keeps is in one place.

**On the machine**

| what | kept | budget (045) |
| --- | --- | --- |
| logs (`logs/`) | rotated daily or at 256 MiB; numbered files 7 days; the archive queue 7 days with backups off, 30 with them on (032 § 2) | `logs-bytes` 4 GiB, reported and projected, not enforced |
| traffic, errors, services, gauges, log volume (`operations/traffic.db`) | five-minute buckets 7 days; the newest 100 failures per service 7 days; a total per log per day 90 days | `traffic-bytes` 64 MiB, oldest hours dropped |
| box failures (`operations/failures.db`) | five-minute counts 7 days; the newest 200 messages and 100 failed tries per box, 7 days | bounded by those counts |
| the change log (`operations/changes.db`) | rows for good; before and after texts 90 days | texts at most 64 KiB |
| change sets | applied, failed, rolled back: 90 days after their last change; drafts and discarded: 30 (042 § 9) | 48 MiB each |
| box versions | archived 30 days after going inactive, deleted 400 days after, leaving a tombstone; never the live one, a disabled box's, the newest 3 that were live, or a kept change set's (045 § 3.1) | time only |
| snapshots | until a person deletes them in the panel | `snapshot-bytes` 2 GiB and `snapshot-files` 100 per tenant; new ones refused past them |
| exports | 7 days | `exports-bytes` 1 GiB |
| tries and dry runs | the call | `try-bytes` 512 MiB, and `free-bytes` 1 GiB left on the disk |
| `tmp/` | `tmp-hours` 24, swept hourly and at start | reported |
| delivered outbox rows | 7 days; dead letters until a person retries or discards them (015) | `outbox-daily-per-service` |
| mail: the send ledger, received attachments | 2 days; `mail.inbound.attachment-days` 30 | time only |
| the robot's cache (`web/`) | 30 days, at most 20,000 pages (017) | count and time |
| never-verified accounts; identity events | deleted 30 days after they were made; events 7 days (021) | time only |
| deletions | the row for good, as a tombstone id (021 § 6) | none |
| source projects and build logs | for good (020 § 9) | 256 MiB per project; the build cache has none (045 § 6) |
| job runs and tries rows (`operations/jobs.db`) | for good, small (044 § 3.5) | none |
| upload counts (`backup/state.db`) | 90 days | none |
| local nightly copies (`backups/<date>/`, beside storage) | the newest 3 with S3 backups on, 14 with them off | **none**; named as `local-copies` in `limits` (045 § 6) |

**In memory, lost on restart**

| what | kept |
| --- | --- |
| live per-URI statistics and flows | the last 60 minutes; at most 10,000 paths and 20,000 flows (032 § 6) |
| `/goober/ready`'s pulse | the last five minutes (028 § 4.6) |
| per-statement performance | the last hour, at most 2,000 statements (037 § 7) |

**In the bucket**

| what | kept |
| --- | --- |
| nightlies, with their increments | `keep-days`, 14, by the stamp in the name; the newest always stays; a failed nightly deletes nothing (019 § 4) |
| attachments | for good while the site has them; `keep-days` after they're deleted here |
| log archives | 400 days (032 § 2) |
| the source mirror | for good (020 § 11) |

Uploads to the bucket are held to `limits.upload-bytes-per-day` (1 GiB; § 5).

## 5. Backups and uploads

The detail is 019; the operator's part is short:

- **The backup key.** Print it (`goober-host backup key`), keep it off the machine, then
  `--confirm`. Without it nothing in the bucket can be read. The vault key (sealed secrets
  boxes keep, 034) is the same kind of thing: copy it beside the backup key.
- **Storage is the host user's, all of it.** A `goober-host` command run with `sudo` but
  without `-u goober` leaves files the host can't read, and the next nightly fails naming the
  path. Every deploy gives them back; the audit's `storage` check names them (HUMAN.md § 4).
- **What a nightly holds.** Storage without attachments (they go once, on their own), logs,
  mail, `tmp/`, exports, the backup state, the source build cache, or the panel's live
  statistics (`traffic.db`, `failures.db`, recounted from the logs after a restore), plus
  host.json (019 § 4, § 9).
- **The daily upload budget.** Once a day's uploads pass `limits.upload-bytes-per-day`, log
  archives (unless queued a week), increments, and the source mirror wait for the next UTC
  day; the nightly and attachments always go, and nothing is dropped (019 § 9). It spreads
  uploads; it doesn't shrink them. Less goes up with fewer logs, a longer
  `databases-every-ms`, or a smaller site.
- **A backup is real once restored.** `just rehydrate ~/copy [moment]` builds any moment as a
  sandboxed devbox; `just backup-e2e` checks the format. Nothing restores on a schedule (§ 9,
  decision A4).

## 6. Logs and their growth

The detail is 032. Every log line is JSON with an envelope and a hash chain; addresses are
keyed hashes. Logs rotate daily or at 256 MiB, stay 7 days on the machine, and go to the
bucket sealed for 400 days. The access log keeps each path, which can hold user data (§ 10).

Since 2026-11-01 the host counts what it writes, by log, tenant, box, and route (032 § 10). A
log **grew** when its last 24 hours are at least 3 times its usual day (the median of the 7
known days before) and at least 1 MiB. The **projection** is the logs directory in 7 days at
today's rate against `limits.logs-bytes`. Both warn in `/goober/ready`'s `limits` check and
show as ratios in `health.logs`; `log_velocity` and the Logs and uploads view name who writes
the most.

## 7. When something goes wrong

Each entry: the sign, then what answers it. HUMAN.md has the exact commands.

| trouble | the sign | what to do |
| --- | --- | --- |
| **The disk is filling** | `/goober/ready`'s `disk` low (under 10% or 2 GiB) or failing (under 256 MiB); `limits` `near` | `du -sh storage/* backups`. The host drops old traffic rows and refuses new tries and exports itself. Delete old snapshots in the panel's Database view; `export delete`; raise a limit only if the disk has room. The local nightly copies in `backups/` are often the biggest and have no budget; `limits`' `local-copies` says how much they hold, and with S3 backups on only 3 are kept (045 § 6). |
| **A log is growing fast** | `limits` `near`: "access wrote 40 MiB in the last 24 hours, 6 times its usual"; `health.logs.growth` | `log_velocity` or the Logs and uploads view; its "who writes the most" names the box and route; `log_search` for the lines. A box logging too much gets a version that logs less; a burst of visitors passes; a scanner is blocked at Caddy. |
| **Uploads past the daily budget** | `limits` warns from 80% (`uploads`); `backup_status.uploads.deferring` | Nothing is lost: logs and increments wait a day. If the nightly alone is past the budget (`backup_status`'s `note`), raise `limits.upload-bytes-per-day` or upload less (§ 5). |
| **Outbox dead letters** | `health.outbox.dead`; `service_report`'s `dead`; the Box failures view's outbox group | `outbox_dead_letters` shows each with every attempt; fix the cause (a key, the service), then `outbox_retry` or `outbox_discard`. A queue that only grows shows as `health.outbox.oldest_age_s`. |
| **Mail failing** | `health.mail.failure_ratio`; the Services view's `mailer`; `host_health.mail` | `mail_activity` for the tenant; `mail_domain_check` for MX, SPF, DMARC, and SES's DKIM; `logs/mail.log`. Common causes: SES still in its sandbox, a domain not verified, AWS keys missing (the audit's `mailer` check), a tenant without a postal address (refused by rule, 029 § 8), `mail.daily-max` reached. Mail in: `host_health.smtp_listener`, `journalctl -u stalwart`, port 25 at the provider. |
| **A box failing** | `health.boxes.failure_ratio`; the Errors view's `box_failed`; the Box failures view | `box_failures` names the class (trap, timeout, out of fuel, SQL error, ...) and the latest messages; `box_logs` by request id. Then roll back (`version_promote` the version before; `version_health` names it), flip a declared kill switch (`flag_set`, 039), or `box_disable`. |
| **A key missing** | calls failing in the box's hands; deliveries retried, then dead (015 § 3); the audit's `mailer` and `backup` checks for AWS keys | `key_list` shows what is set (never the value); `key_set` sets it, bound to its hosts; AWS and backup keys only on the machine (`goober-host key set NAME`, value on stdin). Dead letters then go through `outbox_retry`. |
| **A bad host deploy** | the deploy fails readiness | It rolls itself back. By hand: copy `goober-host.prev` over the binary and restart (HUMAN.md § 5). |
| **A bad box version or change** | `version_health` regressions; errors after a promote | `version_promote` the one before (the newest 3 that were live are always there; an archived one needs `version_restore` first, 045 § 3.1). A change set rolls back whole with `changeset_rollback` (042). Content: the change log has the before text; partials keep ten versions. Data: `db_snapshot` before, `db_restore_to_new` after. No automatic rollback (040 § 5, decision 3). |
| **An agent misbehaving** | `agent_audit`'s flags; many `FAILED` tool lines; `operator_actions` | Gentlest first: approvals on for that agent in the panel (035), so its changing calls wait for a person; focus it on one tenant (030); revoke its token (`goober-host token revoke NAME`) or every grant your address holds (`goober-host operator revoke`); `systemctl stop goober-host` last (HUMAN.md § 6). One token per agent, so the logs say which. |
| **The host is down** | an empty 503 from Caddy; the outside monitor | `journalctl -u goober-host -n 60`; `goober-host check`; deploy again (HUMAN.md § 5). |

## 8. What the reviews taught

From 040 (engineers working through agents, 2026-10-30 and 31), 043 (code and security), and
044 (performance and operations), and the four rounds of 013:

- **Every change is described, previewable, reviewable, triable, atomic, safe against
  teammates, undoable, and watched** (040 § 2). The friction was never a missing feature
  alone; it was not knowing what a call does, or seeing a change only once it was live.
- **Production lags main.** Most of a day's "it doesn't work" was a build hours behind. Deploy
  after each merged batch; `whats_new` tells agents what the running build can do; an agent
  keeps the tool list it fetched, so reconnect after a deploy (040 § 4, HUMAN.md § 6).
- **One token per agent.** A shared token makes every log line say `config` (HUMAN.md § 6).
- **A check must be held to the act it guards.** `if_etag` checked and then written with
  nothing between let two agents clobber each other (043 R1).
- **Write as the host's user only where only the host's user can reach.** A file opened by
  name in a shared directory can be a planted link (043 R2): `O_EXCL | O_NOFOLLOW`, and work
  inside storage.
- **Believe a forwarded address only from the proxy.** Hence loopback-only behind a proxy, and
  IP literals only (043 R3, decision 1).
- **Bound what a box can make the host do per call** (043 R4: 16 role changes), and **fail
  closed** when a template breaks (043 R5).
- **Measure before tuning.** Two network threads serve about 19,000 pages a second, far past
  the experiments; the slow thing was reading a day's log from its start to find its end
  (044 § 1, § 2.1).
- **A crash leaves what a call would have cleaned.** Copies of private rows outlived a killed
  try until startup swept them (044 § 2.2). Anything a call makes in `tmp/` is swept at start
  and hourly.
- **A full disk fails every write at once,** so free space is a readiness check (044 § 2.3).
- **Everything grown on disk needs a time limit and a byte budget,** in one table (045). Long
  history was the wrong default: the human wanted five-minute approximations for a week.
- **Run the commands the docs give.** HUMAN.md's export fetch didn't work as written until it
  was run (044 § 2.5, § 2.7).
- **A signal nobody is shown is no signal.** Every view here waits for someone to look (044 §
  4.1); `/goober/ready`'s `health` exists so something outside can look all the time.
- **Storage belongs to one user.** A `sudo` without `-u goober` broke a site's nightly (019 §
  4); deploys now give storage back and the audit names what they couldn't.
- **The deploy is the operations check.** Asking for missing settings during a deploy, where
  the human is already at a terminal, is what got postal addresses and redirects set (028 § 8).
