# 045. Limits: what the host grows on its own disk

Status: drafted by Claude on 2026-10-31 at the human's request, and built. The human's words: "What
is Try? We should have a general rule about size limits. ... I don't really want long term
metrics, just five minute approximations is good. I don't want traffic storage bloating the
disk." Restore drills are postponed until a product is done.

## 1. The rule

Everything the host grows on its own disk has two limits: how long it is kept, and a byte budget.
Both are listed in one table (§ 3), with defaults sized for a small server (a VPS with a disk of
20 to 80 GB). Every byte budget can be changed in host.json's `limits` object (§ 4). Over a budget, the host
does one of three things, depending on what the thing is:

1. **Derived or expiring things are dropped, oldest first.** This covers anything the host can
   count again from the logs, or that was going to expire anyway: the panel's rollups, temporary
   files, and exports past their week.
2. **New work that would pass a budget is refused.** This covers tries, dry runs, exports, and
   snapshots. The error names the limit's key and says how to raise it, for example
   `limits.try-bytes`.
3. **What a person must decide on is never deleted.** Snapshots are the case: past their limit
   the host refuses new ones and warns, and a person deletes old ones in the panel.

Each budget's use is reported in the `limits` check of `/goober/ready` and in `host_health`'s
`ready.checks.limits`. A budget at 80% or more is marked `warn` and named in `near`. The check
never fails: the host drops or refuses on its own. Only a nearly full disk fails readiness, and
that is the `disk` check (under 256 MiB free; 044 § 2.3).

`/goober/ready` is public, so its `limits` check names no tenant. `host_health`, an operator
tool, does.

Above every budget there is one more rule: new work that writes more must leave
`limits.free-bytes` (1 GiB) free on the disk holding storage. This applies to tries, dry runs,
exports, and snapshots.

## 2. What a try is

A try runs a stored version of a box once, through the real request path. The version is often
a dark one, uploaded with `activate: false` and not live yet. A try can be:

- `route_try` on an HTTP write, an MCP tool, a mail route, a timer, or an internal route;
- `job_dry_run`;
- `upgrade_dry_run`;
- a change set's preview of its members' tries.

Every try that may write runs on **copies** of the tenant's databases, so nothing live changes
and nothing reaches anyone. The copies are thrown away when the call returns. A GET or HEAD try
reads live data read-only and copies nothing.

The copies cost disk while the try runs. Every database the box writes is copied whole.
Together the copies may hold `limits.try-bytes` (512 MiB), and they must leave
`limits.free-bytes` free. Past either limit the try is refused, with an error that names the
limit. Two tries running at once are each held to the limit. Their sum is reported as
`limits.tries`.

The box guide's "Try before live" and the `route_try` tool description say the same.

## 4. Setting a limit

host.json:

```json
{
  "limits": {
    "try-bytes": 1073741824,
    "exports-bytes": 2147483648,
    "traffic-bytes": 134217728,
    "snapshot-bytes": 4294967296,
    "snapshot-files": 200,
    "logs-bytes": 8589934592,
    "free-bytes": 2147483648,
    "tmp-hours": 12
  }
}
```

Each value is in bytes (or files, or hours), with a floor below which the host wouldn't work:

| key | floor |
| --- | --- |
| `traffic-bytes` | 4 MiB |
| `logs-bytes` | 64 MiB |
| `tmp-hours` | 1 hour |
| `free-bytes` | 0 |
| the rest | 1 MiB, or 1 file |

A config past a floor, or with a value of the wrong type, is refused when loaded, naming the
key. A reload (`SIGHUP`) takes new values: the traffic budget on its next pass, and the rest on
their next use.

These keys share `limits` with the per-call limits already there (`body-max-bytes`,
`timeout-ms`, `fuel`, `memory-max-bytes`, `requests-per-minute`,
`outbox-daily-per-service`), so a person looks in one place.

## 5. The traffic store's change

Until 2026-10-31, `traffic.db` and `failures.db` kept minute rows for 48 hours and hour rows for
400 days. There is now one resolution, five-minute buckets, kept seven days. The windows are
1h (12 points of 5 minutes), 12h (72 of 10 minutes), and 7d (168 of 1 hour); 30d is gone
from the tools and the panel.

Opening an old file does this:

- **`traffic.db`:**
  1. drops the old tables and the tailer's cursors, so the logs still on disk (7 days) are
     counted again into five-minute buckets;
  2. carries the gauges, which no log holds, over at five minutes;
  3. checkpoints and vacuums the file, and turns on incremental vacuum.
- **`failures.db`:** carries its minute rows over as five-minute counts and drops the hour rows,
  since no log holds them.

After each pruning pass, freed pages go back to the disk, and the write-ahead log is
checkpointed and cut back to 1 MiB.

Measured (`TrafficTest.DISABLED_SizeOfAWeek`): a week of one busy site, 50 routes each
answering every minute and 5 services each called every minute, is 51 MiB of access log. It is
counted in about 4 seconds into 100,800 route rows and 10,080 service rows: an 11.6 MiB
`traffic.db`, with an empty write-ahead log.

The old scheme kept 2,880 minute rows and 9,600 hour rows per route at steady state, against
2,016 rows per route now: about 6 times the rows, so about 70 MiB for the same site after 400
days. The demo host's `traffic.db-wal` had sat at 4 MiB; it is now cut back after every pass.

## 6. Departures and open items

- **The panel's history.** 300 § Rollups and cost asks for hourly rollups kept 400 days. The
  human chose five-minute approximations for a week instead (028 § 4).
- **Logs over budget are only reported.** Rotated logs already leave after 7 days. Deleting a
  numbered file early wouldn't free its bytes while its archive link waits for upload, so
  enforcing `logs-bytes` waits for a decision on what may go first.
- **The source build cache has no budget yet.**
- **Copy-on-write tries** (`FICLONE`) would make tries nearly free on filesystems that have it.
  The cap comes first; copy-on-write waits until a database nears it (044 § 4.2).
