# 045. Limits: what the host grows on its own disk

Status: drafted by Claude on 2026-10-31 at the human's request, and built. The human's words: "What
is Try? We should have a general rule about size limits. ... I don't really want long term
metrics, just five minute approximations is good. I don't want traffic storage bloating the
disk." Restore drills are postponed until a product is done.

## 1. The rule

Everything the host grows on its own disk has two limits: how long it is kept, and a byte budget.
Both are listed in one table (§ 3), with defaults sized for a small server (a VPS with a disk of
20 to 80 GB). Every byte budget can be changed in host.json's `limits` object (§ 4). Over a budget, the host
does one of three things, depending on what the thing is:

1. **Derived or expiring things are dropped, oldest first.** This covers anything the host can
   count again from the logs, or that was going to expire anyway: the panel's rollups, temporary
   files, and exports past their week.
2. **New work that would pass a budget is refused.** This covers tries, dry runs, exports, and
   snapshots. The error names the limit's key and says how to raise it, for example
   `limits.try-bytes`.
3. **What a person must decide on is never deleted.** Snapshots are the case: past their limit
   the host refuses new ones and warns, and a person deletes old ones in the panel.

Each budget's use is reported in the `limits` check of `/goober/ready` and in `host_health`'s
`ready.checks.limits`. A budget at 80% or more is marked `warn` and named in `near`. The check
never fails: the host drops or refuses on its own. Only a nearly full disk fails readiness, and
that is the `disk` check (under 256 MiB free; 044 § 2.3).

`/goober/ready` is public, so its `limits` check says only each budget's `share` (used over
the limit) and `warn`, and its `near` warnings are ratios: no bytes, no file or copy counts, no
tenant, no box, and no `local-copies` or `disk` rows (2026-11-03; before, it carried bytes and
counts that told anyone how much a site holds and writes). `host_health`, an operator tool,
carries the whole report. The public report is measured at most every 30 seconds; the storage
probe and the `disk` check are live on every call. The logs directory is measured counting
each file once (the archive queue's files are hard links to rotated ones, 032 § 10).

Above every budget there is one more rule: new work that writes more must leave
`limits.free-bytes` (1 GiB) free on the disk holding storage. This applies to tries, dry runs,
exports, and snapshots.

## 2. What a try is

A try runs a stored version of a box once, through the real request path. The version is often
a dark one, uploaded with `activate: false` and not live yet. A try can be:

- `route_try` on an HTTP write, an MCP tool, a mail route, a timer, or an internal route;
- `job_dry_run`;
- `upgrade_dry_run`;
- a change set's preview of its members' tries.

Every try that may write runs on **copies** of the tenant's databases, so nothing live changes
and nothing reaches anyone. The copies are thrown away when the call returns. A GET or HEAD try
reads live data read-only and copies nothing.

The copies cost disk while the try runs. Every database the box writes is copied whole.
Together the copies may hold `limits.try-bytes` (512 MiB), and they must leave
`limits.free-bytes` free. Past either limit the try is refused, with an error that names the
limit. Two tries running at once are each held to the limit. Their sum is reported as
`limits.tries`.

The box guide's "Try before live" and the `route_try` tool description say the same.

The table is the disk. In memory, MCP calls waiting their turn grow with what callers send
(047 § 14.8). They are fixed at 1024 calls and 128 MiB of request bodies in

the real bound is about twice that.

### 3.1 Box versions

The human, 2026-11-01: "box versions archive for liability, they get deleted if inactive after
400 days."

**Inactive.** A version is inactive from the moment it stops being live: another version is
promoted over it, or its box is disabled. A version stored dark and never promoted is inactive
from when it was stored. Each version keeps a life record beside its files
(`boxes/<box>/versions/<version>/life.json`, written through the host WAL with the change that
caused it): `stored_ms`, `stored_by` (the operator), `live` (each period, `from_ms` and
`until_ms`), `inactive_since_ms`, and `archived_ms`. A version stored before records were kept
has no record; the first pruning gives it one with its inactive time starting then, whatever its
age (`first_seen`), so nothing written before this rule is archived or deleted early.

**Kept from both.** The host never archives or deletes:

- the live version;
- a disabled box's version (`box_enable` serves it again), however long the box is off;
- the newest `limits.version-keep` (3) versions that were live before, by when they were last
  live, so `version_promote` always has a rollback target (a version with no record counts, the
  newest stored first);
- a version a kept change set names (as a member, or as what it replaced), for as long as the
  change set is kept (042 § 9: 90 days applied, 30 days drafts).

**Archived** after `limits.version-archive-days` (30) inactive. Its files stay where they are, so
`version_get`, `version_diff`, and `version_list` read it for the record: its manifest,
`module_sha256`, who stored it, and when it was live. Nothing runs it: `route_try`,
`job_dry_run`, `version_promote`, `box_enable`, and change sets refuse it, naming
`version_restore {box, version, why}`, which a person (or an agent, when approvals are off)
calls to bring it back to stored with its inactive time started again. Uploading the same bytes
again restores it too. The host has no compression library, so archiving saves no disk; it marks
what is on its way out and keeps it out of use.

**Deleted** after `limits.version-delete-days` (400) inactive: the manifest, module, types
document, and life record go, and `boxes/<box>/deleted/<version>.json` stays, a tombstone of a few
hundred bytes with `box`, `version`, `module_sha256`, `module_bytes`, `stored_ms`, `stored_by`,
`live`, `inactive_since_ms`, `archived_ms`, `deleted_ms`, and the source deploy that built it
(020) when there was one. `version_list` lists it as deleted and `version_get` answers the
tombstone. A deleted version can't be restored; uploading the bytes again stores it anew.

**Records.** Every archive, restore, and delete is an audit-log line (`version.archive`,
`version.restore`, `version.delete`). None is a change-log row: a life record or a tombstone is
not an upload, and the change log's classifier skips them.

**When.** The hourly housekeeping. `version_list` answers each version's `state` (`live`,
`stored`, `archived`, `deleted`), `inactive_since`, `archives_at`, `deletes_at`, or `kept` with
why; the panel's box page shows the same.

**Cost.** Which versions kept change sets name is read in one pass over the change sets
(each parsed once) for every box at once: once per pruning and once per `version_list` or
other per-box read. Before 2026-11-03 the pruning read every change set once per box, so its
cost, held under the registry's lock, grew as boxes × change sets. Now it is one parse per
change set plus the boxes' life records; change sets are bounded by their own pruning (042
§ 9), so this is small, but it is still done under the registry's lock each hour.

**Copies elsewhere.** The nightly backup holds `storage/boxes` as it was that night, kept 14
days (019), so a deleted version leaves the bucket within 14 days by the bucket's own rotation;
the host deletes nothing from the bucket for this rule. The source mirror (020) keeps source
patches and deployed snapshots, not modules, and is untouched.

`limits.version-archive-days` (1 to 3650), `limits.version-delete-days` (90 to 36500, more than the
archive days), and `limits.version-keep` (1 to 100) change them.

## 4. Setting a limit

host.json:

```json
{
  "limits": {
    "try-bytes": 1073741824,
    "exports-bytes": 2147483648,
    "traffic-bytes": 134217728,
    "snapshot-bytes": 4294967296,
    "snapshot-files": 200,
    "logs-bytes": 8589934592,
    "free-bytes": 2147483648,
    "tmp-hours": 12,
    "version-archive-days": 30,
    "version-delete-days": 400,
    "version-keep": 3,
    "upload-bytes-per-day": 2147483648,
    "studies-bytes": 134217728,
    "skills-bytes": 16777216,
    "beta-mail-bytes": 67108864,
    "operator-mail-bytes": 1073741824
  }
}
```

Each value is in bytes (or files, or hours), with a floor below which the host wouldn't work:

| key | floor |
| --- | --- |
| `traffic-bytes` | 4 MiB |
| `logs-bytes` | 64 MiB |
| `tmp-hours` | 1 hour |
| `free-bytes` | 0 |
| `version-archive-days` | 1 day |
| `version-delete-days` | 90 days, and more than `version-archive-days` |
| `version-keep` | 1 version |
| `upload-bytes-per-day` | 0, which turns the budget off |
| `operator-mail-bytes` | 16 MiB |
| the rest (`studies-bytes`, `skills-bytes`, `beta-mail-bytes` among them) | 1 MiB, or 1 file |

A config past a floor, or with a value of the wrong type, is refused when loaded, naming the
key. A reload (`SIGHUP`) takes new values: the traffic budget on its next pass, and the rest on
their next use.

These keys share `limits` with the per-call limits already there (`body-max-bytes`,
`timeout-ms`, `fuel`, `memory-max-bytes`, `requests-per-minute`,
`outbox-daily-per-service`), so a person looks in one place.

## 5. The traffic store's change

Until 2026-10-31, `traffic.db` and `failures.db` kept minute rows for 48 hours and hour rows for
400 days. There is now one resolution, five-minute buckets, kept seven days. The windows are
1h (12 points of 5 minutes), 12h (72 of 10 minutes), and 7d (168 of 1 hour); 30d is gone
from the tools and the panel.

Opening an old file does this:

- **`traffic.db`:**
  1. drops the old tables and the tailer's cursors, so the logs still on disk (7 days) are
     counted again into five-minute buckets;
  2. carries the gauges, which no log holds, over at five minutes;
  3. checkpoints and vacuums the file, and turns on incremental vacuum.
- **`failures.db`:** carries its minute rows over as five-minute counts and drops the hour rows,
  since no log holds them.

After each pruning pass, freed pages go back to the disk, and the write-ahead log is
checkpointed and cut back to 1 MiB.

Measured (`TrafficTest.DISABLED_SizeOfAWeek`): a week of one busy site, 50 routes each
answering every minute and 5 services each called every minute, is 51 MiB of access log. It is
counted in about 4 seconds into 100,800 route rows and 10,080 service rows: an 11.6 MiB
`traffic.db`, with an empty write-ahead log.

The old scheme kept 2,880 minute rows and 9,600 hour rows per route at steady state, against
2,016 rows per route now: about 6 times the rows, so about 70 MiB for the same site after 400
days. The demo host's `traffic.db-wal` had sat at 4 MiB; it is now cut back after every pass.

## 6. Departures and open items

- **The panel's history.** 300 § Rollups and cost asks for hourly rollups kept 400 days. The
  human chose five-minute approximations for a week instead (028 § 4).
- **Logs over budget are only reported.** Rotated logs already leave after 7 days. Deleting a
  numbered file early wouldn't free its bytes while its archive link waits for upload, so
  enforcing `logs-bytes` waits for a decision on what may go first. Since 2026-11-01 the host
  warns before it gets there: a log growing three times its usual day, or a 7-day projection
  past the budget (032 § 10).
- **The upload budget defers; it doesn't shrink.** It holds log archives and increments for a
  day, never the nightly or attachments, and never drops anything (019 § 9). Uploading less
  means fewer logs, a shorter `keep-days`, or fewer increments.
- **The source build cache has no budget yet.**
- **The local nightly copies are kept by count, not by bytes** (found 2026-11-03, decided and
  built the same day, 046 A12). The `goober-backup` timer that setup installs runs
  `goober-host backup` into `backups/<date>/` every night at 03:15, copying storage (logs,
  temporary files, and caches aside). Given a directory named YYYY-MM-DD, `goober-host backup`
  then removes the dated copies beside it past the newest 3 when `backup.s3` is set (the
  bucket holds the history), or 14 when it isn't. A dated copy is a directory named
  YYYY-MM-DD holding a `BACKUP.json`, so one a backup made; nothing else beside it is touched
  or counted, a dated directory without `BACKUP.json` included (2026-11-03: before, any dated
  directory beside it could go, someone's own `2026-08-01/` too), and the directory may be
  given with a trailing slash. A copy a failed run left (no `BACKUP.json`) therefore stays
  until a person removes it. The human: "I like that policy and keep it simple." They have no
  byte budget, since the host doesn't own them, but `host_health`'s `limits` check names them
  as `local-copies`: how many, their bytes (each copy's `BACKUP.json` count, or measured for a
  copy a failed run left), and how many are kept (the public `/goober/ready` leaves them out). The `disk` check sees the space they take
  when they share storage's filesystem (the default).
- **Copy-on-write tries** (`FICLONE`) would make tries nearly free on filesystems that have it.
  The cap comes first; copy-on-write waits until a database nears it (044 § 4.2).
