# Change sets: one change, previewed, applied, and rolled back together

> Status: machine-authored on 2026-10-31 and built the same day, at the human's decision on
> 040 § 5 item 2: "For the one change, rolled back, it should be execute." Code:
> `host-src/packages/host/src/changesets.cpp`; tests: `host-src/packages/host/test/changeset_test.cpp`.

## 1. The problem

A feature is rarely one kind of change. Order notes are a schema (a `notes` table), a box version
that reads and writes it, a page that explains it, and a flag that turns it on. Each kind already
has its own preview and undo (040 § 2), but they were four separate acts: four reviews, four
moments of going live, and four separate undos when it goes wrong. The rollback in particular had
to be worked out by hand under pressure, in the right order.

A change set makes them one change: built up over several calls, previewed together, reviewed
together (one list of everything that widens), applied by one call in a fixed order, and rolled
back by one call.

## 2. Members

A change set is a draft holding members. Adding a member with the same key replaces it.

| kind | given as | key | done by |
| --- | --- | --- | --- |
| schema | `schema_put`'s schema | `schema:$name` | `schema_put` |
| version | `{box, version}` of a stored version (dark or old), with optional `tries`; or `{manifest, wat \| wasm_base64, types?}`, stored dark when applied | `version:$box` | `version_upload {activate: false}` for an upload, then `version_promote` |
| content | `{tenant, pages?, files?}` as `content_deploy` takes them, merged by path; or `{tenant, from_stage: true}` to copy the operator's `content_stage` draft in | `content:$tenant` | `content_deploy` (verified signed out) |
| flag | `{tenant, box, flag, value}` | `flag:$tenant/$box/$flag` | `flag_set` |

Each member runs through the operator tool that does it alone, so a change set checks nothing
less than those tools do. A version given as an upload exists because a box version is checked
against stored schemas when it is stored: a version that needs the set's own schema can't be
stored dark before the set applies, so the set stores it right after its schemas.

**The seam for more kinds.** Schemas are expand-only today (008), so a schema member is a
`schema_put` and nothing else. When 420's evolution lands (contractions, renames, upgrade boxes),
each becomes a new member kind with its own preview, apply, and undo entries in the same three
places (`changeset_preview`, the apply loop, `changeset_undo`), and its own row in § 5. Nothing
else changes.

Limits: 20 schemas, 20 versions, 10 tenants' content (100 pages and 200 files each), 50 flags,
and 48 MiB.

## 3. Preview and review

`changeset_preview` runs each member's own dry run and stores nothing:

- a schema: `schema_check` (its tables, warnings, whether it is already stored);
- a version: for an upload, `version_upload {dry_run: true}` with the set's unstored schemas
  passed as `schemas`; for a stored version, its review against the box's live version (or the
  version a disabled box had), as `version_diff` gives it; and each of its `tries` through
  `route_try` against that version (a 5xx is a problem; a look-only caller tries GETs only);
- content: `content_deploy {dry_run: true}`, every URL rendered signed out from the would-be files;
- a flag: whether the box as it will be (the set's version of it, else the live one) declares the
  flag, serves the tenant, and allows the value, and what the flag is now.

It answers `ok`, each member's result, `problems`, and `widens`: every widening across the set's
versions as sentences prefixed by the box, for one review.

## 4. Apply

`changeset_apply {id}` is a changing tool: it waits for approval when the agent's approvals are on
(035), and the person approving sees the preview (without tries) and what widens. The draft's
`version` is pinned when the call is made, before any hold, so a member added while the apply
waits is refused rather than slipping in.

In order:

1. The preview runs again. Any problem: nothing is applied, and the answer is the preview.
2. Every existing database the set's versions may write (for each tenant they serve) gets a
   `db_snapshot`. If one can't be taken, nothing is applied.
3. Members apply in kind order: **schemas, then versions, then content, then flags**. Flags come
   last because a flag's value is checked against the version that declares it, and content after
   versions because pages may link to a box's new routes.
4. Before each member, what it replaces is kept: whether the schema was stored; the box's live
   version (or that it was disabled, with the version and why, or that it had none); every site
   file the content will write or remove, byte for byte (or that it was absent); the flag's value.
   After it, what it made: the live version, each file's `file_etag`, the flag's value.
5. If a member fails, the members already applied are undone in reverse (§ 5), and the set is
   `failed`. A content member that failed after writing (a verify problem) is undone too.

Each member's call is recorded in the change log's actions with the change set's id, the WAL
writes they make are change-log rows like any other, and the answer carries their `change_ids`.
The apply is audited (`changeset.apply`).

## 5. Rollback

`changeset_rollback {id}` undoes an applied set in one call, in reverse order. Per member:

| kind | rollback |
| --- | --- |
| flag | `flag_set` back to the value it had, with the reason "rolled back with change set $id" |
| content | every file put back byte for byte, or removed if the set created it; unchanged files untouched |
| version | `version_promote` the version the box had; a box that was disabled is promoted to its old version and disabled again with its old reason; a box that wasn't live before is disabled |
| schema | **nothing.** Schemas only grow: the schema stays stored, and any table or column a version added to a database stays there, unused by the restored version |

Data a version wrote while it was live isn't touched by a rollback. The snapshots apply took are
named in the answer; `db_restore_to_new {snapshot}` brings a database back as it was before.

**Drift.** Before undoing anything, rollback checks that each member is still as the set left it:
the box still on the set's version, each file still at the `file_etag` the set wrote, each flag
still at the set's value. Anything changed since (a teammate's later edit) refuses the rollback
and names each change; `force: true` rolls back over them, and they are lost. A member that can't
be undone leaves the set `applied`, with the error, so it can be fixed and rolled back again.

## 6. Tools

| tool | kind | what |
| --- | --- | --- |
| `changeset_create {title, why?}` | draft | starts a draft; answers its id (a string) |
| `changeset_add {id, schemas?, versions?, content?, flags?, remove?}` | draft | adds or replaces members; `remove` drops by key, or one content path as `content:$tenant:$path` |
| `changeset_show {id}` | read | the set, members without bodies, steps with before and after |
| `changeset_list {state?}` | read | newest first |
| `changeset_preview {id}` | read | § 3 |
| `changeset_apply {id, version?}` | changing | § 4 |
| `changeset_rollback {id, force?}` | changing | § 5 |
| `changeset_discard {id}` | draft | marks a draft discarded |

Draft calls store only the draft, which nothing reads until an apply, so they never wait for
approval (as `content_stage`). Observers may show, list, and preview.

**Scope (030).** Each member is checked against the operator's scope as the tool that does it
alone would be (`schema_put`, `version_upload` or `version_promote`, `content_deploy`, `flag_set`,
`route_try` for tries), when added, previewed, applied, and rolled back. A focused operator sees
only their own change sets.

**States:** `draft`, `applied`, `failed` (an apply that stopped and was undone), `rolled_back`,
`discarded`. Only a draft applies; only an applied set rolls back; each happens once.

## 7. Storage

One JSON file per change set in `storage/operations/changesets/$id.json`, written durably; ids come
from the id service (038). The applied record keeps the bytes content replaced, so a set that
replaced large files is as large as they were. Backups carry the directory with the rest of
storage.
