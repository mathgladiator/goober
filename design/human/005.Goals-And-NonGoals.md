# Goals and Non-Goals

## Moving Fast with AI

This isn't a project to rethink the entire world. It is, however, a project that lets me experiment with AI using a new runtime. Every vibe project that I have built becomes a slog of decisions, which then requires constant QA of both the current decisions and the past decisions. At a certain point, the project that started with enthusiasm is a slog, and the productivity gains came at an unpredictable cost with an uncertain future. It is never really clear if the project is good enough to stand behind.

The primary goal is to experiment with whether this can be overcome, producing confidence in an operable system that behaves well with a tolerable risk surface.

## Letting Agents go ham

We want to fully embrace AI going ham, such that a chat bot like Grok could build and ship runtime code to the system. Grok can compile Rust to WASM, so this raises the question of whether we even need source control anymore if I can get the contents into a box. Having had a prior project manage static content along with some dynamic content, this becomes a natural extension of that endeavor, with better boundaries.

If the artifact is the truth, then the artifact has to carry what source control used to carry. A deployed box is a WASM module and a manifest, versioned together and approved together, so the system itself keeps the history of every shape a box has had, who approved it, and when. Source control becomes optional for the box, but it never becomes optional for the platform: the host, the checker, and these documents are the part a human must be able to read, diff, and trust.

## Limited Audience and Research as the Goal

We treat this as a research project, so that we can generate content about building with AI. Maybe this project can grow, but that growth is a non-goal.

## Goals

- **Confidence without reading the code.** A person should be able to approve a box by reading its manifest, not its source, and feel the shape of what it can do and what it can break. We are asking humans to read the pipe, not the product.
- **Risk that is known before it is taken.** The worst a route can do, where torn writes are possible, what a box can reach, and what it costs should all be answerable from the manifest before anything is deployed.
- **Agents can ship.** An agent should be able to build a box and submit it, with the human approval queue as the only gate between a good idea and a running product.
- **Containment over correctness.** The interior of a box can be slop, as long as the slop stays inside the box. Bad code should show up as errors and latency for one project, never as a breach.
- **Boxes that don't rot.** A box owns only its business logic, so once approved, it should keep working while the host, the edge, and the outside world change around it.
- **One machine first.** Everything must run on a single machine as a real deployment, and growing to many machines must not change a single manifest.
- **A concrete proving ground.** Rebuilding Hearth on this runtime, as a set of ordinary boxes rather than a special-purpose server, is the first real test of whether the ideas hold. Beyond that, a catalog of small tools for blue-collar businesses is the stretch test: can many products run for years without being touched? Proving that they could is a goal; selling them is not.

## Non-Goals

- **Growth.** Users, adoption, and revenue are not what this project optimizes for, and the design should never be bent towards them.
- **Rethinking everything.** Boundaries that earned their keep, like HTTP, SQLite, SMTP, TLS, and OpenAPI, are kept as good shapes, and the commodity edge is rented rather than rebuilt.
- **Running existing software.** There is no POSIX inheritance and no attempt to host arbitrary programs, legacy frameworks, or containers someone already has.
- **A general-purpose cloud.** This is not a competitor to the big edge and serverless platforms, and feature parity with them is not interesting.
- **Making agent code good.** Improving what is inside a box is left to the agents and their tools. The platform only promises that whatever is inside stays inside.
- **Every feature of every database.** Data starts with a small set of well-known access patterns, and full SQL is an escape hatch with a cost, not a starting point.
- **Long-lived, living processes.** Boxes are ephemeral and optimized, not immortal. The dream of code that changes while memory stays was explored in Adama, and it is deliberately left behind.
- **Hiding the operator's power.** Whoever runs the system can do anything the system can do. We will make that power visible and auditable, but we won't pretend it away.

## How we will know

The experiment works if three things turn out to be true:

1. A box written by an agent can be approved by a person in minutes, from its manifest alone, and the person is comfortable standing behind it.
2. A box left alone for months still runs, while the host underneath it has changed many times.
3. When a box is bad, the damage is exactly what the manifest said the worst case could be, and nothing more.

If any of these fails, we will have learned something worth writing about, which is also a success for a research project.
