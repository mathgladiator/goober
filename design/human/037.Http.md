# More HTTP details

Query parameters, post bodies, put bodies, delete, and more. The manifest design promised that we would get to the full range of HTTP, and this is where we do it. The rule is the same as everywhere else: the host does the protocol, and the box gets strongly typed values. A box should never parse a URL, never read a header it didn't ask for, and never see a byte of JSON it has to validate itself.

## Everything a request can carry

Every piece of a request that the box can see is declared on the route, along with its type. Anything not declared is invisible to the box, and anything that fails its type is rejected by the host with a 400 before the box even wakes up.

```json
{
	"types": "orders.openapi.json",
	"routes": {
		"http": {
			"/orders/{order_id : int64}": {
				"get": {
					"name": "get_order",
					"query": {
						"include_items": { "type": "bool", "default": false }
					},
					"response": "json:Order"
				},
				"put": {
					"name": "update_order",
					"body": "json:OrderUpdate",
					"max-body-bytes": 65536,
					"response": "json:Order"
				},
				"delete": {
					"name": "delete_order",
					"response": "empty"
				}
			}
		}
	}
}
```

| part | how it is declared | what the box sees |
| --- | --- | --- |
| Path parameters | In the path, like {order_id : int64} | A typed argument. |
| Query parameters | A query block with types and defaults | Typed fields, with defaults filled in by the host. |
| Headers | An allowlist on the route | Only the headers it named, already decoded. |
| Bodies | A body type: json with a named type, text, or binary | A generated structure, or a buffer with a known length. |
| Body size | max-body-bytes, with a sane default | Nothing; oversized bodies never reach the box. |
| Cookies and tokens | Not on the route at all | Context values, verified by the host, as described in the data design. |

Named types like Order and OrderUpdate are not invented here. They come from the box's types document, which borrows the schema section of an OpenAPI document, as described in [036.Json.md](036.Json.md). The response is declared the same way, and the box fills in a generated structure rather than writing JSON by hand. The host serializes it, which means a box can't produce a malformed response or leak a field the schema doesn't name.

```C
#include <stdbool.h>
#include <stdint.h>

struct order_update {
	int32_t quantity;
	bool gift_wrap;
};

struct order {
	int64_t id;
	int32_t quantity;
	bool gift_wrap;
};

int64_t update_order_get_order_id();
const struct order_update* update_order_get_body();
void update_order_respond_json(const struct order* order);
void update_order_respond_error_simple_4xx(int32_t status);
```

## The status vocabulary

A route doesn't get to pick any number it likes. The verb and the response type decide which success the box can send: a json response sends 200, a create sends 201, and an empty response sends 204. Errors from the box are 4xx only and clamped, as described in the manifest design, while 5xx belongs to the host, because only the host knows when the system is the one at fault. Redirects are declared on the route with their targets rather than built by the box, since an open redirect is a classic way to turn a trusted domain into a phishing tool.

## What the host does for free

Because the manifest describes the route completely, the host can take on the boring parts of HTTP that every web framework makes each product reinvent:

- **Validation.** Types, schemas, sizes, and content types are checked before the box wakes up, so a bad request costs the host a parse and costs the box nothing.
- **CORS.** Allowed origins live in the manifest, and the host answers preflight requests itself.
- **Conditional requests.** A GET whose data comes from strategies has a natural ETag: the signature plus the sequence numbers of everything it read. The host can answer If-None-Match with a 304 without waking the box, since the sequencer already knows nothing changed.
- **Compression and range requests.** These are properties of bytes, not of products, so they belong to the host.
- **HEAD and OPTIONS.** Derived from the route, never written by hand.

## Other protocols speak HTTP too

HTTP is the tactical start, and it is also the shape other protocols get converted into before they reach the box. Subscriptions arrive over SSE, as described in the bus design, and mail arrives as HTTP from Stalwart, as described in [038.Mail.md](038.Mail.md). The box doesn't care which wire a request came in on; it only sees the route.

## The invariants

- **The box only sees what the route declares.** Undeclared headers, parameters, and fields don't exist inside the box.
- **Invalid requests never wake the box.** The host rejects them with a 4xx and records why.
- **The box never writes protocol bytes.** It fills in structures, and the host serializes them.
- **The status vocabulary is fixed by the manifest.** Success codes come from the route, 4xx from the box is clamped, and 5xx is reserved for the host.
