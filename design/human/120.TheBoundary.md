# The Boundary

For starting out, we are going to leverage the best practices that WASM supports. The reason we do this is that we will accept the overhead of copying data into and out of the box as a baseline measure. However, with C support, we have the option of a dance between the box and the host, where the host tells the box, "Hey, you have data arriving for an event, the size is $len, and the pickup id is $id," such that the box can do a linear copy of the data from the host into its linear WASM memory very quickly, and then do a linear pass to remap pointers into WASM space. This means messages are going to be immutable payloads. This will have a lot of finicky optimizations across platforms, so we start with the fallback, which is also what we keep for when the WASM memory and host memory don't align, or there are sizing issues.

This document pins down exactly how data crosses between the host and a box, since every other design assumes it without saying it. The boundary is versioned, starting at goober-abi@1, and every box pins the version it was built against, as described in the stability design, so the host can grow new boundaries without breaking old boxes.

## Ground rules

- **Linear memory belongs to the box.** The host never keeps pointers into it, and never assumes anything it finds there is valid.
- **Layouts are the wasm32 C ABI.** Little-endian, pointers and size_t are 32 bits, int64_t is 64 bits, and every structure is aligned the way a C compiler targeting wasm32 aligns it. The generator emits these layouts, and the host is built from the same description, so both sides agree on every offset.
- **Strings and buffers are a pointer plus a length.** Strings are UTF-8, and nothing depends on a terminating zero, though the host writes one after every string it delivers as a courtesy to C.
- **Payloads are immutable.** Data delivered into a box is const as far as the generated code is concerned, and data the box hands back is copied out by the host before the call returns, so neither side can change a message the other is reading.

## The fallback: copy field by field

The first implementation, and the one that always works, is the simplest. Generated code asks the host for each piece of a payload in turn, and copies it into memory the box owns.

1. The host tells the box what arrived, by signal or event, as the manifest design describes.
2. The generated getter, like update_order_get_body, asks the host for the size of each variable-length field, allocates space for it in a per-request arena, and asks the host to copy the field in.
3. The getter assembles the structure in the arena and hands the box a const pointer to it.

This costs one host call per variable-length field, which is fine for small payloads and painfully honest for large ones, which is exactly what makes it a good baseline: every byte copied is visible, and the operating panel reports bytes copied and time spent copying per route, so we know what the faster path is worth before we build it.

## The dance: pick up a whole payload in one copy

The faster path is the one from the opening paragraph. The host prepares the whole payload ahead of time, already laid out in the wasm32 C ABI, as one contiguous block, and the box picks it up in a single copy.

```C
#include <stdint.h>

// Asked by generated code, never by hand.
// Returns the size of the payload waiting under pickup_id.
uint32_t goober_payload_size(uint32_t pickup_id);

// Copies the payload into dest, which must have room for its size;
// returns 0 on success.
int32_t goober_payload_pickup(uint32_t pickup_id, void* dest);
```

1. **Announce.** The host tells the box that a payload of size $len is waiting under pickup id $id.
2. **Allocate.** The generated code allocates $len bytes in the per-request arena, aligned to 8.
3. **Copy.** The box calls goober_payload_pickup, and the host copies the block into the arena with one linear copy.
4. **Relocate.** The block was built as if it started at address zero, so every pointer inside it is really an offset. The block ends with a relocation table listing where those pointers are, and the generated code walks it once, adding the arena's address to each one.

```
+--------------------+  offset 0
| header             |  magic, version, root offset, relocation table offset, count
+--------------------+
| root structure     |  struct order_update, with pointers stored as offsets
+--------------------+
| strings and arrays |  every variable-length field, each aligned
+--------------------+
| relocation table   |  the byte offsets of every pointer field to fix up
+--------------------+
```

After relocation, the box has an ordinary C structure with ordinary pointers, all inside its own memory, built from one copy and one linear pass. Nothing about the box's code changes between the fallback and the dance; only the generated getter does, so the host and generator can switch a route between the two without the box ever knowing.

## Getting data out

When the box responds, the generated function passes the host a pointer to the response structure in the box's own memory. The host walks it using the layout it shares with the generator, and copies each piece out into host memory, checking every pointer and length as it goes:

- **Every pointer must land inside linear memory,** and every pointer plus its length must too. A pointer that points outside, or a length that runs off the end, fails the response with a 500, and the box gets no second chance in that request.
- **Lengths are capped** by the route's declared limits, so a box can't hand back a 2 GB string because it forgot to set a length.
- **The host copies before it returns,** so whatever the box does to that memory afterwards changes nothing the host is holding.

The same rules cover everything else a box passes to the host: write sets, outbox elements, grants, file writes, and counters. The host treats every number a box gives it as untrusted input, because it is.

## Memory and lifetimes

- **A per-request arena.** Generated code owns a small bump allocator that is reset when the request ends, so payloads never fragment the box's own heap and never need to be freed by hand. Shared boxes reset it between requests, and async boxes reset each event's portion when goober_on_event returns.
- **Payloads live as long as their request.** A pointer from a getter is valid until the request responds. For async boxes, an event's payload is valid only during the goober_on_event call that delivered it, which is why the MCP and manifest designs tell async boxes to keep a context_id rather than a pointer.
- **Large data never crosses as a payload.** Anything that could be big, like an upload, arrives as a handle through the file-like API from the file design, and is read in pieces the box chooses. A route's declared size limits guarantee every payload fits comfortably in the box's memory.

## When the dance doesn't fit

We start with the fallback, and keep it, because the fast path depends on things that won't always hold:

| situation | what happens |
| --- | --- |
| A payload is larger than the box's free memory or the route's limit | The host refuses the request before the box wakes up, so this never reaches the boundary. |
| A box uses 64-bit memory | The layouts differ, so the generator emits the fallback until a 64-bit layout is defined. |
| A language can't use C layouts directly | Its generated bindings use the fallback, or, later, the Component Model's canonical encoding. |
| A payload is tiny | The fallback is used anyway, since one host call costs less than the bookkeeping of a pickup. |

## The boundary across migrations

The boundary has to stay still while the tables behind it move. A box's row structures are stamped out from the schema version its manifest pins, so the boundary between host and guest is defined by that version, not by whatever shape the table has today. When a table changes, as described in the migration design, the boundary doesn't change at all; the host does the adapting on its own side of it.

- **Reads are projected to the box's version.** The host builds the row the box expects from the table's current shape before copying it across: columns the box doesn't know are left out, dropped columns are filled from the defaults the box's version declares, and emulated type changes are converted back. The box receives exactly the layout it was generated against, field for field.
- **Writes are adapted from the box's version.** An insert, update, or upsert arrives as a whole row in the box's layout, and a patch or patch-except arrives with exactly the columns its write names. The host writes the columns the table still has, discards the ones it dropped, and leaves the ones the box doesn't know alone, or fills them from their defaults on insert.
- **There is only one shape.** Every allowed schema change is applied in place, so the host never keeps two copies of a table in step, and the projection is all the adapting there is.

So a box built today against core13 copies the same bytes across the same boundary in ten years, even if the table underneath is core20 by then, because the API refuses every schema change the host can't project. That is the stability design's promise applied to data: the host changes, the tables change, and the boundary doesn't.

## The invariants

- **The host never trusts a pointer from a box.** Every pointer and length is bounds-checked against linear memory and the route's limits.
- **Every crossing is a copy.** Neither side ever holds a reference into the other's memory after a call returns.
- **Payloads are immutable.** Delivered data is const, and returned data is copied out before the call returns.
- **The generator and the host share one layout.** The wasm32 C ABI, generated from the same description, is the contract.
- **The fallback always works.** The fast path is an optimization the box can't see, never a requirement.
- **Migrations never move the boundary.** Rows cross in the box's pinned schema version, and the host adapts on its own side.
