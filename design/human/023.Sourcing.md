# Data Sourcing

Since migrations can be complicated, and we want to bias towards a long-term view, we create special instances of databases with special tables that we bias towards history. These are sources. A source is a table that is immutable by design: rows are only ever added, never changed, and never removed, and its shape can only expand. Each row is an event, something that happened, and since what happened doesn't stop having happened, a source only grows. This is event sourcing, held to a rule strict enough that a source never needs a migration.

Ordinary tables are the current state, and they are the right truth for most products. A plumber's job list doesn't need its history replayed. Some data is different: the jobs a crew booked, moved, and finished over ten years; the payments a business took; the things that happened in a household. That data is worth more as a history than as a current state, because the questions people ask of it change over time, and a question nobody thought to ask five years ago can still be answered if the events are still there. A source keeps the events, and boxes build whatever current state they need from them, as many times as they need to.

## A source database holds only sources

A source lives in a source database, which is a database that holds sources and nothing else. Ordinary tables live in ordinary databases. Keeping them apart lets the host treat a source database differently everywhere it matters: it is never compacted, never rewritten in place, backed up as an append-only file, placed and counted on its own, and it never runs any of the changes in the migration design except pure expansion.

A .schema marks a table as a source, and a schema that declares a source declares only sources, so a source database is the union of source schemas just like an ordinary database is the union of ordinary ones. Like any other database, its name is a template, so each tenant can have its own source database, like jobs_log_{!tenant}.

Every source database has one sequence. Each event committed to any source in that database takes the next number, in commit order, so the events across every source in one database have a single order, and that order is the order in which they happened. There is no order across databases, since each database commits on its own, as described in the data shape design.

## An event can only grow

A source's shape changes like any table's, through a new schema version, but the only change the host accepts is pure expansion:

| change | allowed | what other versions see |
| --- | --- | --- |
| A new source | Yes | Nothing, until a box pins a version that has it. |
| A new column with a default, or allowing null | Yes | Older writers' events fill it from its default. Older readers never see it. |
| A dropped column or a dropped source | Refused | Not applicable. An event can't forget a field it was written with. |
| A rename, a type change of any kind, or a new constraint | Refused | Not applicable. The event already happened, in its shape. |
| A new index or a dropped index | Refused | Not applicable. Boxes don't query sources; see below. |

Because the only change is expansion, every event ever written can be read by every version of every box, forever, with nothing to emulate. An older event read by a newer box has each newer column filled from its default. A newer event read by an older box has the columns it doesn't know left out. The projection is total in both directions, so a source never has a migration, never needs an upgrade, and never loses data. That is the whole bet of this document: give up the right to change what happened, and in exchange, never migrate it.

The cost is the same warning as everywhere else: a default is an invented value. An older box's event read by a newer box carries the default for every column the older box didn't know, and the checker says so when a new column is added.

## Writing to a source

A box adds events through a strategy whose pattern is append, and every write on it has the kind append. There is no other kind on a source: insert, update, upsert, patch, and patch-except are refused, since each of them would change or replace something that already happened.

```json
{
	"data": {
		"sqlite3": {
			"job_log": {
				"schema": "jobs_log2.schema",
				"database": "jobs_log_{!tenant}",
				"pattern": "append",
				"writes": {
					"job_booked": { "kind": "append", "source": "job_booked" },
					"job_moved": { "kind": "append", "source": "job_moved" },
					"job_done": { "kind": "append", "source": "job_done" }
				}
			}
		}
	}
}
```

Each append write names the source it adds to, and generates one function that takes the whole event as a structure stamped from the pinned schema version. The box can't pass a sequence number, a time, or who it was, because the host stamps all of them. Every event carries an envelope the host writes alongside the box's columns:

| envelope field | meaning |
| --- | --- |
| seq | The event's place in the source database's sequence. |
| at | The commit time. |
| request_id | The request that wrote it, so traces join it to everything else. |
| box and version | The box, and the version of it, that wrote it. |
| schema | The schema version the event was written in. |
| writer | The reserved identifiers of the request that wrote it, like !user_id, recorded as data. |

An append is part of the request's write set, like any other write, so an event exists if and only if the request's bundle commits. A strategy with the append pattern can also publish to a topic, exactly as in the bus design, so a screen can wake up when something happens.

## Handling events

A box builds current state from a source with a route under the event protocol. An event route is a handler: the host gives it one event at a time, in sequence order, and it does whatever an ordinary route can do with it, which usually means writing an ordinary table.

Like the timer design, an event route has two halves. The data source says what the handler can see: a strategy whose pattern is by_cursor, which the box can't call from its code at all, since it exists only for the handler. The route says how it runs: which strategy to read, which sources in it to handle, and where to start.

```json
{
	"data": {
		"sqlite3": {
			"job_log_for_handlers": {
				"schema": "jobs_log2.schema",
				"database": "jobs_log_{!tenant}",
				"pattern": "by_cursor"
			},
			"jobs_by_day": {
				"schema": "jobs5.schema",
				"database": "tenant_{!tenant}",
				"table": "jobs_by_day",
				"pattern": "by_index",
				"index": "day",
				"index-is": "{day}",
				"limit": 200,
				"read": true,
				"writes": {
					"put_job": { "kind": "upsert" }
				}
			}
		}
	},
	"routes": {
		"event": {
			"build-jobs-by-day": {
				"name": "build_jobs_by_day",
				"source": "job_log_for_handlers",
				"events": ["job_booked", "job_moved", "job_done"],
				"from": "first",
				"timeout-ms": 200
			}
		}
	}
}
```

The handler receives each event as a typed structure stamped from the schema version its own manifest pins, along with the envelope, so there is nothing to map and nothing to forget. Event routes aren't reachable from outside the host, so like timers they carry no requirements and no "public"; the host is the only caller.

### Context

A handler has no user. The writer's reserved identifiers are in the envelope, as data the handler can read, but they aren't the handler's context, so a handler can never satisfy a requirement on behalf of the person who wrote the event, and it can't act as them. When the source database is named from {!tenant}, the host runs the handler once per tenant in the domain registry, with !tenant set, exactly as it partitions a data-driven timer, so a handler reading tenant 9's events can only write tenant 9's tables.

### The cursor

The host keeps one cursor for every event route, for every source database it reads. The cursor is the sequence number of the last event the handler finished, and it belongs to the route, not to a version of the box, so deploying a new version of the box picks up where the old version stopped.

- **One at a time.** The host gives the handler the next event after its cursor, waits for it to respond, commits its write set, and then advances the cursor, in that order. A handler never sees two events at once, and never sees them out of order.
- **The cursor moves with the bundle.** Advancing the cursor is part of the handler's bundle. When the bundle touches only one database, the host keeps the cursor in that database and advances it in the same transaction, so each event's effect happens exactly once. When it touches more, the cursor advances once the bundle commits, and every part of the bundle carries an idempotency key made from the route, the source database, and the seq, so a retry after a crash behaves like once, as described in the outbox design.
- **A failure stops the line.** If the handler traps, times out, or fails, its write set is thrown away, the cursor stays put, and the host retries the same event with backoff. Since order matters, the handler doesn't move on to the next event until this one succeeds, so one bad event stalls one handler for one source database, and the operating panel says which event, which handler, and why. The fix is a new version of the box, which picks up at the same cursor.
- **Where a new route starts.** from says where a new route's cursor begins: first, the first event ever written, or next, the next event committed after the route is deployed. The default is first.

### A new route is a new view of all of history

That last rule is the point of the whole design. A new event route with "from": "first" starts at the beginning of history and works its way forward, one event at a time, until it catches up with the present, and then it keeps up. So any table a handler builds can be built again, in a new shape, by a new route, from the same events, while the old route keeps the old table current.

This is how a source turns a data migration into a deployment. When a product needs a table in a new shape, it adds the new table, which is a pure expansion, and a new event route that fills it from the first event. The old route and the old table keep working the whole time. When the new route has caught up, the readers move to the new table, and the old route and the old table are retired, all through ordinary approvals. There is no dual-write code and no backfill job, since replaying the source is the backfill. The migration design leans on this for the hard cases.

Catching up isn't free. A route starting at the first event of ten years of history has ten years to read, and the host paces it, within the box's budgets, so a catch-up can't starve the routes serving people. The operating panel shows every handler's lag, as the number of events and the time between its cursor and the newest event, so a person can see when a new view is ready.

### What a handler can't do

- **A handler can't append to a source it reads,** directly or through a chain of other handlers, since that is a loop that never ends. The checker refuses the direct case and every chain it can see, as in the no-cycles rule of the internal messaging design.
- **Boxes don't query sources.** There is no by_id, by_index, or query on a source, and no index to make one fast. A source is read one event at a time, by handlers, in order. Anything a person wants to look up is a table a handler builds.

## The invariants

- **A source is append-only.** Events are added, and never changed or removed.
- **A source only expands.** The only schema change a source accepts is a new source or a new column with a default or allowing null.
- **Every version reads every event.** Older events gain defaults and newer events lose unknown columns, so a source never migrates.
- **A source database holds only sources.** It has one sequence, in commit order, and no order exists across databases.
- **An event exists if and only if its bundle commits.** Appends ride in the write set like any other write.
- **Handlers see one event at a time, in order.** A failure stalls the handler at that event rather than skipping it.
- **The cursor belongs to the route.** A new version keeps it, and a new route starts its own, from the first event by default.
- **A handler has no user.** The writer is in the envelope as data, never in the context.
