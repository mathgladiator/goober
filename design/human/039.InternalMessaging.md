# Internal Messaging

We are going to borrow HTTP idioms and introduce an "internal" route, which behaves exactly like HTTP. The key difference is that an internal route is never reachable from outside the system. In the initial case of a single machine, the host will talk directly to the box right after the caller's handler, skipping the network overhead entirely. In the case of a cluster, this will use an internal network RPC that is optimized for high throughput, such that latency is minimized. This is primarily for request/response message passing.

This is how boxes talk to boxes when they need an answer right now. The network design already described one box calling another as an external service, and the outbox already described one box telling another something after a commit. Internal routes are the first-class, fast version of the former, and they leave the latter exactly as it is.

## Declaring an internal route

An internal route lives under routes with internal as its protocol, and it looks like any HTTP route: a path, a verb, a typed body and response from the types document, and the same status vocabulary. What it adds is a list of callers, which names the boxes allowed to call it.

```json
{
	"types": "billing.openapi.json",
	"routes": {
		"internal": {
			"/invoices": {
				"post": {
					"name": "create_invoice",
					"body": "json:InvoiceRequest",
					"response": "json:Invoice",
					"callers": ["jobs", "subscriptions"],
					"requirements": [["owner/{!tenant}"], ["admin/{!tenant}"]]
				}
			},
			"/invoices/{invoice_id : int64}": {
				"get": {
					"name": "get_invoice",
					"response": "json:Invoice",
					"callers": ["jobs"]
				}
			}
		}
	}
}
```

The callers list is the internal route's version of deny by default: an internal route with no callers is refused by the checker, since nothing could ever call it, and "public" means nothing here, since nothing outside can reach it anyway. Requirements are optional on top of callers, and when present, they are checked against the person the call is ultimately made for, as described below.

### Binding to a tenant

An internal route can bind to a tenant through a path argument, like /sweeps/{tenant_slug}/overdue, and use it to choose a database, like tenant_{tenant_slug}. Only internal routes may do this, as described in the data flow design: routes the outside world can reach must take the tenant from {!tenant}, so a caller can never type their way into someone else's data. Inside the cluster, the callers list is the gate, and the human approving the box is responsible for checking that every caller passes the right tenant, which is why the checker flags every internal route that names a database from a path argument.

## Calling an internal route

A box that calls another box declares it, just like it declares an external service, except that it names a box instead of a base URL and an OpenAPI document. The host already knows the other box's manifest, so it generates the calling code from the callee's own types.

```json
{
	"external": {
		"billing": {
			"box": "billing",
			"methods": {
				"create_invoice": {
					"budget": {
						"calls": 2
					}
				}
			}
		}
	}
}
```

```C
#include <stdint.h>

// Generated in the jobs box from the billing box's create_invoice route.
// Returns the status of the call; on success, the invoice is filled in.
int32_t billing_create_invoice(const struct invoice_request* request, struct invoice* out);
```

The caller never learns where the billing box runs. On a single machine, the host hands the request straight to a billing isolate in the same process, and in a cluster, it sends it over the internal RPC to whichever host serves billing for that tenant. The call looks identical in both cases, which is the whole point.

Both sides must agree: the caller declares that it calls create_invoice, and create_invoice names the caller in its callers list. Either one alone is refused by the checker, so a box can't quietly start depending on another box, and a box can't quietly start being depended on.

## Wrapping an external service

Internal routes are also how an external service gets wrapped when it changes underneath us, as the stability design describes: a box that called a vendor directly can be pointed at an adapter box instead, which proxies the old contract onto whatever replaced it. Checking that this actually works end to end, here is how each piece fits.

The calling box only changes its manifest, by adding box next to the pinned OpenAPI document. Its module, its generated code, and its calls stay exactly the same.

```json
{
	"external": {
		"forecasts": {
			"openapi": "weather.v2.openapi.json",
			"box": "weather-adapter",
			"methods": {
				"getForecast": {}
			}
		}
	}
}
```

The adapter box implements the old service's design as internal routes, one for each operation it stands in for, at the same path and verb the pinned OpenAPI document gives that operation, and it names the boxes it serves in callers. It reaches the new vendor through its own external service, with its own keys.

```json
{
	"box": "weather-adapter",
	"mission": "Serve the retired weather.v2 contract on top of the new weather provider.",
	"domains": ["*"],
	"types": "weather.v2.openapi.json",
	"routes": {
		"internal": {
			"/forecast/{postal_code : string}": {
				"get": {
					"name": "getForecast",
					"response": "json:Forecast",
					"callers": ["jobs"]
				}
			}
		}
	},
	"external": {
		"new_weather": {
			"openapi": "new-weather.v1.openapi.json",
			"base": "https://api.new-weather.example",
			"credentials": "keys/system/new-weather",
			"methods": {
				"getOutlook": {
					"budget": { "calls": 1 }
				}
			}
		}
	}
}
```

What the host and checker guarantee when a service is redirected:

| concern | how it works |
| --- | --- |
| Matching the contract | The adapter's types document is the pinned OpenAPI document itself, and the checker confirms that every method the caller uses has an internal route at the same path and verb, with the same request and response types. A missing or mismatched operation refuses the redirect before it ships. |
| Both sides agree | The caller lists the box, and the adapter lists the caller in callers, so a redirect can't happen by one side alone, exactly as for any internal call. |
| Credentials | The caller's credentials for the old vendor are never passed along, since keys never enter a box. The adapter uses its own keys for the new vendor, and the caller's credentials field is ignored while the redirect is in place. |
| Restrictions | The caller's require blocks still apply before the call leaves the caller, so a field pinned to {!email} is filled in by the host and arrives at the adapter already pinned, and the adapter can't widen it. |
| Effects | A call whose effect was "outbox" becomes an outbox element addressed to the adapter, so it still happens after the caller's bundle commits, at least once, with the same idempotency key. A call with no effect stays a synchronous internal call. |
| Authority | The internal call carries the caller's reserved identifiers, like {!tenant} and {!user_id}, so the adapter acts for the same person in the same tenant, and never with more. |
| Budgets and audit | The caller's budget for the old service still counts each call, the adapter's own budgets cap what it does with the new vendor, and both hops land in the audit. |
| Approval | For the caller, adding box is a dependencies change, which the approvals design lets policies ship. For the adapter, adding a caller is an ordinary change to its own version. |

The result is a proxy that the caller can't tell apart from the vendor it was written against. The adapter is an ordinary box, reviewed once, and every box that used the old service can share it by listing it the same way.

## Whose call is it?

An internal call is made on behalf of whoever the caller's request was made for. The host carries the caller's secure context across: the domain, the tenant, and the user_id, if there is one. Two more values describe the call itself.

| context value | meaning |
| --- | --- |
| !caller_box | The name of the box that made the call. |
| !caller_route | The name of the route in that box that made the call. |

Because the user_id travels with the call, the callee's requirements are checked against the actual person, so a box can't use another box to do something its person isn't allowed to do. A member of Bob's Plumbing who triggers a job that calls create_invoice is still a member, and create_invoice, which requires an owner or admin, refuses them. The callee is never a deputy that can be confused into lending its authority.

A call from a timer has no user, so it carries only what the timer provides. An internal route that is meant to be called from timers simply has no requirements, and relies on its callers list alone.

## Calls and commits

Each box has its own write set and commits its own bundle, so an internal call is not part of the caller's bundle. When the caller makes a synchronous call to a route that can write, the callee commits its writes before the caller has committed its own, and if the caller then fails, the callee's writes stay. This is the same as an "immediate" call in the outbox design: the change can happen even when the request that asked for it fails, and the checker reports it.

When the caller doesn't need the answer right away, the outbox is the better tool. An outbox element addressed to another box is a request to that box that only happens after the caller commits, so it rides the caller's bundle and happens at least once, at the cost of the caller not seeing the result inside its own request.

| need | use | if the caller later fails |
| --- | --- | --- |
| Read something from another box now | A synchronous internal call | Nothing changed, if the callee's box has no writable strategies. |
| Ask another box to change something, and use the answer now | A synchronous internal call | The callee's change stays, and the checker reports it. |
| Tell another box to change something after this request commits | An outbox element addressed to the box | Nothing happens, since the caller's bundle never commits. |

## Idempotent internal routes

Idempotency can be a feature of an internal service rather than a burden on every box that calls it. An internal route marked "idempotent": true asks the host to remember the idempotency key of every call it completes: the outbox's key for outbox elements, and the fire's key for timers, made from the timer, the row key, and the scheduled time. When the same key arrives again, the host returns the first result without running the box again. The keys are kept per tenant, in the tenant's own directory, for long enough to cover any retry the host might make.

This is what lets the system offer global at-least-once delivery for outbox elements and timers across a whole cluster: delivery is retried until it succeeds, from any host, and an idempotent route turns "at least once" into "once" at the receiving end, without the receiving box writing a line of deduplication code. Timers use this directly, since a timer can deliver each fire to another box's internal route, as described in the time design, and that route lists the timer's box in its callers like any other caller.

## Time, budgets, and loops

- **Deadlines travel.** The callee's timeout is the smaller of its own timeout-ms and whatever remains of the caller's, so a chain of calls can never outlive the request that started it.
- **Budgets apply on both sides.** The caller's budget caps how many calls it makes, and the callee's budget caps how much each call can do.
- **Cycles are refused.** Since every call is declared in both manifests, the checker can draw the whole call graph across boxes, and it refuses a deployment that would create a cycle. The host also caps how deep a chain of calls can go, as a second line of defense.
- **The checker adds up the worst case.** A route's worst case includes the worst case of every internal route it calls, so "can this box behave well?" still has an answer when the work is spread across boxes.

## Speed

On a single machine, an internal call never touches the network or a serializer. Both boxes are generated from the same types document, so the host copies the request structure from the caller's memory into the callee's, runs the callee, and copies the response back. The cost is two copies and one isolate.

In a cluster, the internal RPC runs over long-lived, mutually authenticated connections between hosts, with a compact binary encoding derived from the same types, and requests multiplexed over each connection. Since the bus already keeps hosts in touch, the host knows which machine serves a box for a tenant, and a call goes straight there without a lookup on the hot path.

## What the host does for free

- **Routing.** The host resolves a box name to a running isolate, here or on another machine.
- **Context propagation.** The domain, tenant, user_id, and caller identity are carried across every call.
- **Validation.** Requests and responses are checked against their types on the way in and out.
- **Audit.** Every internal call is written down with its caller, its callee, the person it was made for, and its result.
- **Compatibility.** When the callee's types change, the checker already knows every box that calls it, as described in the JSON design, and names each one before the change ships.

## The invariants

- **Internal routes are never reachable from outside.** Only boxes named in callers can reach them.
- **Both sides declare the call.** A caller lists the route, and the route lists the caller.
- **Authority never grows across a call.** The callee checks the caller's person, not the caller's box.
- **An internal call is not part of the caller's bundle.** Synchronous calls to writable boxes can change things even when the caller fails, and the outbox is the way to tie a change to the caller's commit.
- **Deadlines only shrink.** No call outlives the request that started it.
- **There are no cycles.** The checker refuses them, and the host caps call depth.
