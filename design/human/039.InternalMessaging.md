# Internal Messaging

We are going to borrow HTTP idioms and introduce an "internal" route, which behaves exactly like HTTP. The key difference is that an internal route is never reachable from outside the system. In the initial case of a single machine, the host will talk directly to the box right after the caller's handler, skipping the network overhead entirely. In the case of a cluster, this will use an internal network RPC that is optimized for high throughput, such that latency is minimized. This is primarily for request/response message passing.

This is how boxes talk to boxes when they need an answer right now. The network design already described one box calling another as an external service, and the outbox already described one box telling another something after a commit. Internal routes are the first-class, fast version of the former, and they leave the latter exactly as it is.

## Declaring an internal route

An internal route lives under routes with internal as its protocol, and it looks like any HTTP route: a path, a verb, a typed body and response from the types document, and the same status vocabulary. What it adds is a list of callers, which names the boxes allowed to call it.

```json
{
	"types": "billing.openapi.json",
	"routes": {
		"internal": {
			"/invoices": {
				"post": {
					"name": "create_invoice",
					"body": "json:InvoiceRequest",
					"response": "json:Invoice",
					"callers": ["jobs", "subscriptions"],
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"]]
				}
			},
			"/invoices/{invoice_id : int64}": {
				"get": {
					"name": "get_invoice",
					"response": "json:Invoice",
					"callers": ["jobs"]
				}
			}
		}
	}
}
```

The callers list is the internal route's version of deny by default: an internal route with no callers is refused by the checker, since nothing could ever call it, and "public" means nothing here, since nothing outside can reach it anyway. Requirements are optional on top of callers, and when present, they are checked against the person the call is ultimately made for, as described below.

## Calling an internal route

A box that calls another box declares it, just like it declares an external service, except that it names a box instead of a base URL and an OpenAPI document. The host already knows the other box's manifest, so it generates the calling code from the callee's own types.

```json
{
	"external": {
		"billing": {
			"box": "billing",
			"methods": {
				"create_invoice": {
					"budget": {
						"calls": 2
					}
				}
			}
		}
	}
}
```

```C
#include <stdint.h>

// Generated in the jobs box from the billing box's create_invoice route.
// Returns the status of the call; on success, the invoice is filled in.
int32_t billing_create_invoice(const struct invoice_request* request, struct invoice* out);
```

The caller never learns where the billing box runs. On a single machine, the host hands the request straight to a billing isolate in the same process, and in a cluster, it sends it over the internal RPC to whichever host serves billing for that tenant. The call looks identical in both cases, which is the whole point.

Both sides must agree: the caller declares that it calls create_invoice, and create_invoice names the caller in its callers list. Either one alone is refused by the checker, so a box can't quietly start depending on another box, and a box can't quietly start being depended on.

## Whose call is it?

An internal call is made on behalf of whoever the caller's request was made for. The host carries the caller's secure context across: the domain, the tenant, and the user_id, if there is one. Two more values describe the call itself.

| context value | meaning |
| --- | --- |
| caller/box | The name of the box that made the call. |
| caller/route | The name of the route in that box that made the call. |

Because the user_id travels with the call, the callee's requirements are checked against the actual person, so a box can't use another box to do something its person isn't allowed to do. A member of Bob's Plumbing who triggers a job that calls create_invoice is still a member, and create_invoice, which requires an owner or admin, refuses them. The callee is never a deputy that can be confused into lending its authority.

A call from a timer has no user, so it carries only what the timer provides. An internal route that is meant to be called from timers simply has no requirements, and relies on its callers list alone.

## Calls and commits

Each box has its own write set, so an internal call is not part of the caller's transaction. When the caller makes a synchronous call to a route that can write, the callee commits its writes before the caller has committed its own, and if the caller then fails, the callee's writes stay. This is exactly the "network call that must happen immediately" from the shape of data, so the checker treats it the same way: a route that makes a synchronous internal call to a box that has any writable strategies is not atomic, and must say "atomic": false.

When the caller doesn't need the answer right away, the outbox is the better tool. An outbox element addressed to another box is a request to that box that only happens after the caller commits, which keeps the caller atomic, at the cost of the caller not seeing the result inside its own request.

| need | use | atomic for the caller |
| --- | --- | --- |
| Read something from another box now | A synchronous internal call | Yes, if the callee's box has no writable strategies |
| Ask another box to change something, and use the answer now | A synchronous internal call | No; the checker requires "atomic": false |
| Tell another box to change something after this request commits | An outbox element addressed to the box | Yes |

## Time, budgets, and loops

- **Deadlines travel.** The callee's timeout is the smaller of its own timeout-ms and whatever remains of the caller's, so a chain of calls can never outlive the request that started it.
- **Budgets apply on both sides.** The caller's budget caps how many calls it makes, and the callee's budget caps how much each call can do.
- **Cycles are refused.** Since every call is declared in both manifests, the checker can draw the whole call graph across boxes, and it refuses a deployment that would create a cycle. The host also caps how deep a chain of calls can go, as a second line of defense.
- **The checker adds up the worst case.** A route's worst case includes the worst case of every internal route it calls, so "can this box behave well?" still has an answer when the work is spread across boxes.

## Speed

On a single machine, an internal call never touches the network or a serializer. Both boxes are generated from the same types document, so the host copies the request structure from the caller's memory into the callee's, runs the callee, and copies the response back. The cost is two copies and one isolate.

In a cluster, the internal RPC runs over long-lived, mutually authenticated connections between hosts, with a compact binary encoding derived from the same types, and requests multiplexed over each connection. Since the bus already keeps hosts in touch, the host knows which machine serves a box for a tenant, and a call goes straight there without a lookup on the hot path.

## What the host does for free

- **Routing.** The host resolves a box name to a running isolate, here or on another machine.
- **Context propagation.** The domain, tenant, user_id, and caller identity are carried across every call.
- **Validation.** Requests and responses are checked against their types on the way in and out.
- **Audit.** Every internal call is written down with its caller, its callee, the person it was made for, and its result.
- **Compatibility.** When the callee's types change, the checker already knows every box that calls it, as described in the JSON design, and names each one before the change ships.

## The invariants

- **Internal routes are never reachable from outside.** Only boxes named in callers can reach them.
- **Both sides declare the call.** A caller lists the route, and the route lists the caller.
- **Authority never grows across a call.** The callee checks the caller's person, not the caller's box.
- **An internal call is not part of the caller's commit.** Synchronous calls to writable boxes make a route non-atomic, and the outbox is the atomic alternative.
- **Deadlines only shrink.** No call outlives the request that started it.
- **There are no cycles.** The checker refuses them, and the host caps call depth.
