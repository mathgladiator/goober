# Domains

As part of routing and the context, we will consider domains as a first-class citizen, such that you can register a domain with the system, and that domain (along with subdomains, which can redirect) can then provide a tenant id. As part of static content, static content will also be domain specific.

This impacts HTTP, email, and MCP routes.

## The domain registry

The host keeps a registry of every domain it serves, in the platform's own database, next to identity rather than inside any box. A domain is either the primary domain for a tenant, or a redirect that sends everything to that primary domain. There are no aliases: a tenant is served under exactly one name, and every other name it owns redirects there, so links, cookies, passkeys, and mail all agree on one domain.

```sql
CREATE TABLE domains (
	domain TEXT PRIMARY KEY,              -- lowercase, punycode for international names
	tenant TEXT NOT NULL,                 -- the tenant this domain provides
	kind TEXT NOT NULL,                   -- 'primary' or 'redirect'
	redirect_to TEXT,                     -- for redirects, the domain to send people to
	verification_hash TEXT,               -- the DNS TXT proof the registrant publishes, for hard verification
	verified_at INTEGER,                  -- under hard verification, nothing is served until this is set
	mail_enabled INTEGER NOT NULL DEFAULT 0,
	first_owner_email TEXT,                -- for primary domains, who becomes owner/$tenant on first sign-in
	created_by INTEGER NOT NULL,          -- the user_id that registered it
	created_at INTEGER NOT NULL
);
```

| kind | example | behavior |
| --- | --- | --- |
| primary | bobsplumbing.com | Serves the tenant, and is the name the tenant is known by in links and mail. |
| redirect | www.bobsplumbing.com | Answers every request with a permanent redirect to the domain in redirect_to, keeping the path. |

A tenant has exactly one primary domain and any number of redirects, like www.bobsplumbing.com or bobs.goober.example, but a domain belongs to exactly one tenant, which is what makes the domain a safe source for the tenant id.

## The domain in the secure context

When a request arrives, the host looks up the domain it was addressed to before anything else happens. An unknown domain, or one that hasn't passed hard verification on a host that requires it, gets nothing at all: no route, no box, and no hint about what exists. A known domain sets two reserved identifiers, as described in the reserved identifiers design.

| reserved identifier | meaning |
| --- | --- |
| !domain | The primary domain the request arrived on, like bobsplumbing.com. |
| !tenant | The tenant that domain provides, like bobs_plumbing. |

The tenant is a reserved name that always comes from the domain. A manifest never declares it and can't set it; it simply writes {!tenant} wherever a scope needs the tenant, like "database": "tenant_{!tenant}". Because the tenant comes from the registry, and the registry only changes through registration, nothing a caller types can choose the tenant, which is what lets every strategy, key, and role scope by {!tenant} safely.

## Registering a domain

Registering a domain is a host feature with its own implicit API, like the identity service's. Boxes never see it.

1. **Ask.** A host operator holding "host:owner", or the tenant's own "owner" signed in on the tenant's primary domain, asks to register a domain for that tenant. A new primary domain also names the email address of its first owner, who is granted "owner" in the fresh, empty identity realm on first sign-in, as described in the identity design.
2. **Prove, when required.** If the host requires hard verification, it answers with a verification value, and the registrant publishes it as a DNS TXT record on the domain. The host checks DNS and sets verified_at.
3. **Serve.** From then on, as soon as the domain's DNS points at the host, it starts accepting traffic. If mail is enabled, the host also produces the MX record the registrant needs to publish for receiving, while the records for sending, like SPF and DKIM, come from whichever email provider sends for the tenant, since sending is a pure function of the provider, as described in the mail design.

## Soft and hard verification

There are two levels of verification, and the first one is never off.

| level | what it checks | when |
| --- | --- | --- |
| Soft | The domain is in the host's registry. | Always. Caddy's on-demand TLS asks the host, at the reserved route /internal/routes/tls/ask, before it ever requests a certificate, and the host only says yes for registered domains, so nobody can make the system fetch certificates, or serve anything, for a domain it was never told about. |
| Hard | The registrant controls the domain, proven by a DNS TXT record. | When the host requires it, on top of soft verification. |

Hard verification is optional, and it is a host-level setting rather than something a manifest or a tenant decides:

```json
{
	"domains": {
		"verification": "hard"
	}
}
```

| setting | a domain serves traffic once | suits |
| --- | --- | --- |
| "soft" | It is registered, and its DNS points at the host. | A single person running their own infrastructure, where the only person registering domains is the person who owns them. This is the simple, pleasant default. |
| "hard" | It is registered, its TXT record is verified, and its DNS points at the host. | A host with many tenants, since it stops one tenant from registering a domain that someone else controls but that happens to point at the host. |

Even with only soft verification, a stray domain pointed at the host by mistake, or by someone hoping to borrow a certificate, gets nothing: Caddy asks, the registry says no, and no certificate is ever requested.

Removing a domain is the reverse, and it is just as deliberate: the registry row is deleted, and the certificate is no longer renewed. Under hard verification, the same domain can only come back by being verified again, which is what prevents a takeover, where a domain someone forgot about still points at the system and a stranger registers it for their own tenant. Under soft verification, that protection rests entirely on who is allowed to register domains, so a host with more than one tenant should require hard verification.

## HTTP routes

HTTP routes don't change shape at all. The same manifest serves every domain of every tenant, and the domain only shows up through the secure context. Since every tenant has exactly one primary domain, !domain is always the name a tenant is known by, and a route can use it in links without worrying about which name a person typed.

Redirect domains never reach a route. The host answers them itself, so www.bobsplumbing.com or bobs.goober.example sending people to bobsplumbing.com costs a lookup, not a box.

## Static content

Static content is domain specific through the manifest it lives in. Every manifest, and every config, lists the domains it applies to, either specific domains or "*" for all of them, and its embedded static content is served on exactly those domains, as described in the UI design.

```json
{
	"config": "bobs-site",
	"domains": ["bobsplumbing.com"],
	"static": {
		"/": {
			"content-type": "text/markdown",
			"content": "# Bob's Plumbing",
			"public": true
		}
	}
}
```

So Bob's site lives in a manifest for bobsplumbing.com, Anne's lives in one for anneslandscaping.com, and anything every tenant shares lives in one for "*". Isolating content and apps by domain, while still allowing some common domains, is also what makes the domain the primary key of every conflict, as described in the conflicts design.

## Email routes

Mail addresses are domain specific, since the part after the @ is a domain. A mail route can name a local part without a domain, and it then matches that local part on every mail-enabled domain the registry knows, with the tenant resolved from the recipient's domain.

```json
{
	"routes": {
		"mail": {
			"support@": {
				"receive": {
					"name": "support_inbox",
					"public": true
				}
			}
		}
	}
}
```

Mail to support@bobsplumbing.com reaches support_inbox with tenant bobs_plumbing, and mail to support@anneslandscaping.com reaches the same route with tenant annes_landscaping. A catch-all address, "*@", receives mail for every address on the tenant's domains that no other mail route claims, with the recipient in the reserved identifier {!to}, as described in the mail design. Outbound mail is sent from the tenant's own domain through the tenant's email provider, which signs it, so each business keeps its own sending identity and reputation, as the mail design's per-tenant mailers intend.

## MCP routes

An agent connects to a specific domain, like bobsplumbing.com/mcp, and that domain decides the tenant for everything the agent does. Identity is per domain: each primary domain is its own identity realm, with its own accounts, as described in the identity design. The consent screen names the domain the agent is connecting to, and a token issued on bobsplumbing.com is only accepted in Bob's realm. An agent working for Alice at Bob's Plumbing can't take its token to Anne's Landscaping, since Alice's account at Anne's is a different account entirely.

## Keeping domains safe

- **Soft verification is always on.** Caddy asks the registry before requesting any certificate, so an unregistered domain never gets one, and is treated exactly like a domain the system has never heard of.
- **Hard verification for shared hosts.** With hard verification, a domain proves control through DNS, and a removed domain has to prove itself again before it is served, which closes the door on takeovers of forgotten domains. A host with more than one tenant should require it.
- **Cookies stay on their domain.** The identity service sets cookies for the exact domain only, never for a parent, so one tenant's subdomain can't read or set another tenant's cookies. A platform domain that gives tenants subdomains, like bobs.goober.example, belongs on the Public Suffix List, so browsers treat each tenant's subdomain as its own site.
- **Look-alikes are shown as they are.** International domains are stored in punycode and shown that way in every security screen, so a look-alike domain can't pass for the real one on a consent page.

## The invariants

- **A domain belongs to exactly one tenant.** The tenant in the secure context is whatever the registry says the domain provides.
- **Nothing is served on an unregistered domain.** No route, no box, no certificate, and no hint, and the same goes for a domain that hasn't passed hard verification on a host that requires it.
- **One name per tenant.** Every tenant has exactly one primary domain, and every other domain it owns redirects there.
- **Callers can't choose their tenant.** The tenant comes from the registry, never from anything the request carries.
- **Redirects never wake a box.** The host answers redirect domains itself.
- **Identity is per domain.** Each primary domain is its own realm, and a token is only accepted in the realm that issued it.
