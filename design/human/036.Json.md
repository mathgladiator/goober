# JSON and the Types of a Box

Every box that speaks JSON needs somewhere to say what its JSON looks like, and we are not going to invent a schema language to do it. OpenAPI already has one, it is built on JSON Schema, and agents have read more Swagger than any human ever should. So we borrow it. A box's types live in an OpenAPI document under components.schemas, the manifest points at that document, and routes refer to types by name.

## Where a type is defined

The manifest names a types document, and every json body or response refers to a schema in it by name.

```json
{
	"types": "orders.openapi.json",
	"routes": {
		"http": {
			"/orders/{order_id : int64}": {
				"put": {
					"name": "update_order",
					"body": "json:OrderUpdate",
					"response": "json:Order"
				}
			}
		}
	}
}
```

The types document is an ordinary OpenAPI document, except that we only read its components.schemas section. The paths section is ignored, since routes belong to the manifest.

```json
{
	"openapi": "3.1.0",
	"info": { "title": "orders", "version": "7" },
	"paths": {},
	"components": {
		"schemas": {
			"Order": {
				"type": "object",
				"required": [ "id", "quantity", "gift_wrap" ],
				"additionalProperties": false,
				"properties": {
					"id": { "type": "integer", "format": "int64" },
					"quantity": { "type": "integer", "format": "int32", "minimum": 1, "maximum": 100 },
					"gift_wrap": { "type": "boolean" }
				}
			},
			"OrderUpdate": {
				"type": "object",
				"required": [ "quantity" ],
				"additionalProperties": false,
				"properties": {
					"quantity": { "type": "integer", "format": "int32", "minimum": 1, "maximum": 100 },
					"gift_wrap": { "type": "boolean", "default": false }
				}
			}
		}
	}
}
```

From this one document, the tools stamp out three things: the C structures the box fills in and reads, the validator the host runs before the box wakes up, and the serializer the host uses on the way out. The schema is the single source of truth for all three, so they can't drift apart.

## Why borrow OpenAPI

- **The vocabulary already exists.** Objects, arrays, enums, ranges, lengths, and formats are all there, with a decade of tooling behind them.
- **It is the same language as the network design.** External services are described by OpenAPI documents, so a box consumes types and publishes types in one vocabulary.
- **Boxes become services for free.** Since the manifest has the routes and the types document has the schemas, the tools can join them into a complete OpenAPI document for any box. That document is what another box uses to call it, what a human uses to read it, and what any off-the-shelf Swagger tool can render, mock, or test against.
- **Agents are fluent in it.** The less we invent, the fewer tokens get spent rediscovering what we meant.

## A strict subset

JSON Schema can express almost anything, which is exactly the problem. We accept a strict subset, chosen so that every type maps cleanly onto a C structure and every rule can be checked by the host without surprises.

| JSON Schema | what the box sees in C | notes |
| --- | --- | --- |
| integer, format int32 or int64 | int32_t or int64_t | The format is required, since integer alone has no width. |
| number, format float or double | float or double | The format is required, for the same reason. |
| boolean | bool | |
| string | const char* and size_t | maxLength is encouraged, and the host enforces it. |
| string with enum | an enum | The generator stamps out named constants. |
| object | a struct | additionalProperties must be false, so unknown fields are rejected. |
| array | a pointer and a count | maxItems is required, so every array has a ceiling. |
| $ref to another schema | a nested struct | References stay inside the same document. |
| a field not in required | the value plus a has_ field | Absent and zero are different things, and the box can tell. A field with a default skips the has_ field, since the host fills it in. |

Things we refuse for now: oneOf, anyOf, allOf, patternProperties, open objects, and recursive types. Each of these has a real use, and each of them can make a validator or a generated structure much harder to reason about. They can earn their way in later, one at a time.

## One type vocabulary

Every type anywhere in a manifest is an OpenAPI type, so there is exactly one vocabulary to learn. A named type, like json:Order, refers to a schema in the types document. Anywhere a manifest declares a single value, like a context variable, a query parameter, or a header, it writes a small OpenAPI schema inline:

```json
{
	"context": {
		"user_id": {
			"type": "integer",
			"format": "int64",
			"source": "principal/agent"
		}
	}
}
```

Path parameters and mail addresses can't hold an object, so they use a shorthand inside the braces, like {order_id : int64}. A shorthand is always the OpenAPI format name when the type has a format, or the OpenAPI type name when it doesn't, so it maps back to exactly one schema:

| shorthand | OpenAPI schema | C |
| --- | --- | --- |
| int32 | type integer, format int32 | int32_t |
| int64 | type integer, format int64 | int64_t |
| float | type number, format float | float |
| double | type number, format double | double |
| boolean | type boolean | bool |
| string | type string | const char* and size_t |
| token | type string, format token | const char* and size_t, verified by the host |

The token format is the one format of our own. It marks a string that the host signed, like the reply addresses in the mail design, and the host verifies the signature before the value ever reaches a box, so a box only ever sees tokens that are genuine. Anything that isn't in this table, like "bool", "int", or "integer" without a format, is refused by the checker, since a type without a width is a guess.

The .schema files for databases are the one place with their own types, since they describe SQLite columns rather than values on the wire, and the types-are-not-tables rule below keeps the two apart.

## Changing a type

A types document is coupled to the manifest the same way a .schema file is coupled to data, so a change to a type is a change to the box's shape, and it goes through the human approval queue. The checker compares the new document against the deployed one and says what kind of change it is:

| change | effect on callers |
| --- | --- |
| Adding an optional field to a request | Safe; old callers simply don't send it. |
| Adding a field to a response | Safe for tolerant readers, and the checker lists callers that are not. |
| Making an optional field required | Breaking; old callers will be rejected. |
| Removing or renaming a field | Breaking. |
| Narrowing a range, length, or enum | Breaking for callers who used the old values. |
| Widening a range, length, or enum | Safe for requests, breaking for strict readers of responses. |

A breaking change is not forbidden, but it is never a surprise. Because box-to-box calls are declared in manifests, the checker knows exactly which boxes call the route whose type is changing, and it can name them.

## Types are not tables

The types document describes what goes over the wire, while a .schema file describes what goes into a database, and the two are deliberately separate. A table has columns that should never leave the building, and a response often joins or reshapes what a table holds. The tools can stamp out a starting type from a table to save typing, but once it exists, the type is its own thing with its own versioning.

## The invariants

- **Every json body and response names a type in the types document.** There is no anonymous JSON.
- **The types document is the single source of truth.** Structures, validators, and serializers are all generated from it.
- **Objects are closed and arrays are bounded.** Unknown fields are rejected, and every array has a maxItems.
- **Type changes are classified before they ship.** The checker says whether a change is safe or breaking, and which boxes it breaks.
