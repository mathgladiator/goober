# Cluster, Routing, and Services

Beyond the worker model, we can have a notion of shared state within a box. Fundamentally, this means we need to think about what that means in a cluster environment, and this raises the question of how to scale up while leveraging SQLite.

Once we transition a box from a worker to a service, we are required to solve registration, such that other machines in a cluster can find it. This is exactly the same problem as scaling up usage around SQLite, where a single machine becomes the owner of a specific service (like a per-tenant service) or a single database (like a per-tenant database).

Load balancing can leverage stickiness to maximize which boxes handle which requests, minimizing traffic between machines.

The primary failure is machine loss. For the SQLite case, a Litestream pattern, where the WAL is continuously backed up, provides durability. Services, by the process model, will represent data loss. This limits the fullness of the service model, and in a way, a service becomes a stateful cache or app server that must exercise rehydration.

Regardless, the key model to solve is the registration of a single machine's ownership of a resource, the routing of requests to that machine, and then failure detection along with recovery. Each data provider will need its own failure detector and re-instantiation, while we own services, such that they have a time to expire, and we leverage a heartbeat along with a common fleet service for registration that ensures only one machine can really run a service at a time. We keep it really simple to start, so we bias towards a heartbeat for each service, and if the heartbeat fails, then the machine can no longer accept traffic for it.

The lease design is simple: a host registers itself to own a box for X milliseconds, and then checks in every X/2 milliseconds. These boxes must be conditioned for failure, so they talk to databases that provide the real guarantees. If a host's check-in fails for X milliseconds, OR it gets a negative acknowledgment, like being told it lost the lease, then it stops serving traffic. The primary failure mode is a slow clock on two hosts: the host running the service refusing to die, and a slow host sending that host traffic, and thus not learning of new routing. This is a real problem, so we measure as best we can, alarm on clock skew between machines, and isolate machines that are behind at the load balancer level.

## Workers and services

| | worker | service |
| --- | --- | --- |
| Where it runs | Any host, as many isolates as needed | Exactly one host at a time, per owned key |
| State | Nothing assumed beyond the request | Kept in memory between requests, as a cache |
| On machine loss | Nothing lost; another host takes the next request | Memory lost; the next owner rehydrates from durable data |
| Needs registration | No | Yes, through the fleet service |

A service is declared in the manifest's behavior, along with the key that decides ownership. One service instance exists per resolved key, so a per-tenant service has one instance per tenant, each owned by exactly one host.

```json
{
	"behavior": {
		"mode": "service",
		"owned-by": "{!tenant}",
		"lease-ms": 10000
	}
}
```

The box rehydrates in goober_on_start, reading whatever it needs from its data strategies, since anything it kept only in memory is gone the moment its host is. A service that can't rebuild itself from durable data isn't a service; it's a data loss waiting for a machine to fail.

## One registry for everything that is owned

Services and databases have the same shape of problem, so they share one registry. Every owned resource has a key, an owner, and a lease:

| resource | key | owner does |
| --- | --- | --- |
| A service instance | /service/$box/$owned_key | Runs the box in service mode for that key. |
| A timer partition | /timers/$box/$tenant | Plans and fires that box's timers for that tenant. |
| A database file | /database/$provider/$database | Is the single writer for that file, as the shape of data design requires. |

The fleet service that holds the registry is the one piece of the cluster that must agree with itself, so it is not something we build from scratch. It is a small, strongly consistent store run by a consensus protocol, like etcd, or SQLite under Raft as in rqlite, and the host talks to it only to acquire, renew, release, and look up leases. On a single machine, the registry is in-process and every lease is trivially local, so the same code runs on a laptop and a cluster.

## Leases, with fencing

Every lease the fleet service grants carries an epoch: a number that goes up every time the resource changes hands. The epoch is what makes the clock problem survivable.

1. **Acquire.** A host asks for a resource, and the fleet service grants it for lease-ms, along with the next epoch.
2. **Renew.** The host renews every lease-ms / 2. Each renewal returns the same epoch, or a refusal.
3. **Stop early.** The host measures its lease on its own monotonic clock, never wall time, and stops serving a little before the lease runs out, at lease-ms minus a safety margin for clock drift. A refusal stops it immediately.
4. **Wait to take over.** When a lease lapses, the fleet service doesn't hand it to anyone else until lease-ms plus the same margin has passed, so the old owner has stopped by its own clock before the new one starts.
5. **Fence every write.** Every write an owner makes carries its epoch, and the data provider refuses any write with an older epoch than the newest it has seen. A host whose clock lied, or that paused for a long garbage collection, may wake up believing it still owns something, but its writes bounce, so it can't corrupt anything.

Steps 3 and 4 make overlap unlikely, and step 5 makes it harmless. Timing is never trusted on its own; the epoch is the real guarantee, and it lives in the database, where the author's notes say the real guarantees belong.

## Routing

Each host keeps a cached copy of the registry's routing table: which host owns which service key and which database. When a request arrives, the host resolves its owned key from the secure context, like the tenant from the domain registry, and then:

- **If it owns the key,** it runs the request.
- **If another host owns it,** it forwards the request there over the internal RPC from the internal messaging design, as the system design's stickiness rule describes.
- **If nobody owns it,** it asks the fleet service for the lease, and becomes the owner.

The load balancer's stickiness makes forwarding rare, since requests for a tenant keep landing where the tenant lives, but correctness never depends on it.

A stale routing table is the second half of the clock problem: a host that hasn't heard the news keeps forwarding to the old owner. So the old owner answers with a refusal that names the current epoch, instead of serving the request, and the forwarding host refreshes its table and tries again. Stale routes cost one extra hop, never a wrong answer. Hosts whose clocks drift past the alarm threshold are pulled out of the load balancer, as the author's notes require, until they are fixed.

## Timers in a cluster

Timers are owned work too, and they follow the same registry. The unit of timer work is a partition: one box's timers for one tenant, or, for sources that aren't scoped by tenant, one box's timers as a whole. Each partition has exactly one owning host at a time, through a lease with an epoch like any other resource, so a timer never runs on two hosts for the same row.

Partitions are placed by consistent hashing of the box and the tenant onto the hosts in the cluster. That naturally spreads the load: a thousand tenants with a nightly sweep become a thousand partitions scattered across the hosts, not a thousand fires stampeding one machine at midnight. When a host joins or leaves, only the partitions that hash differently move, and the new owner rebuilds its plan for each one from the sources, since the plan is ephemeral state, as described in the time design.

Timers want to hold their databases close. A tenant's timers read that tenant's by_timer sources and usually write to that tenant's database, so the best place to run them is the host that already owns that database. The registry places a tenant's database and its timer partitions with the same consistent hash, so they land on the same host by construction, and timer reads and writes stay local. When they don't line up, during a handoff or after a rebalance, the timer's host doesn't reach across the network into someone else's database: it goes through the proxy service, forwarding the work over the internal RPC to the database's owner, exactly as requests are forwarded in the routing section above. Correctness never depends on the two being together; speed does.

Failover keeps the at-least-once promise. If a host dies mid-fire, its leases lapse, another host takes over the partition with a new epoch, rebuilds the plan from the sources and the durable progress, and fires whatever hadn't completed. Fires that did complete are recognized by their idempotency keys, and fires delivered to idempotent internal routes are deduplicated by the host, so the work happens once even when the fire happens twice.

## Failure and recovery

| failure | detected by | recovery |
| --- | --- | --- |
| A host dies | Its leases stop renewing | After lease-ms plus the margin, another host acquires each lease with a new epoch. Databases are restored from Litestream and services rehydrate. |
| A host is partitioned from the fleet service | Its renewals fail | It stops serving at its own deadline, and its leases move as if it had died. |
| A host pauses or its clock is slow | Clock skew alarms, refused writes | Fenced writes bounce, its stale routes refresh, and the load balancer isolates it. |
| The fleet service is unavailable | Renewals fail everywhere | Hosts keep serving until their own deadlines, then stop, so an outage of the fleet service bounds itself rather than splitting the cluster's brain. |
| A database provider fails | Its own failure detector | Each data provider owns its own detection and re-instantiation, as the author's notes say. |

Durability on machine loss is as good as Litestream's lag behind the WAL, which is small but not zero. A write acknowledged a moment before a machine dies can be lost if its WAL frames hadn't streamed yet, so the honest promise is "durable within the replication window," and boxes that can't accept that window need a provider that replicates synchronously before acknowledging.

## Moving things on purpose

Not every handoff is a failure. To rebalance, drain a host, or deploy a new host version, the owner hands a resource off gracefully: it stops taking new requests for the key, finishes those in flight, flushes the database's WAL to the backup, and releases the lease. The new owner acquires it with the next epoch and starts immediately, without waiting out a timeout, since nothing lapsed.

## The invariants

- **One owner per resource at a time.** Services and databases are owned through the same registry.
- **Every lease has an epoch, and every write carries it.** Stale owners are fenced at the database, whatever their clocks believe.
- **Owners stop before their leases end.** They measure on their own monotonic clocks, with a margin, and new owners wait the margin out.
- **Routing is a cache, and refusals correct it.** A stale route costs a hop, never a wrong answer.
- **Services are caches.** Anything that matters lives in data, and a new owner rehydrates from it.
- **Timers are partitioned by box and tenant.** Consistent hashing spreads them, places them beside their databases, and falls back to the proxy service when they aren't.
- **Durability is within the replication window.** Machine loss can lose only what hadn't streamed yet, and the design says so.
