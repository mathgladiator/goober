# Configs

Moving static content into the manifest and paying closer attention to HTTP headers raises a question about common HTTP properties. A content security policy, a caching rule, or a redirect usually applies to many routes at once, and often to every route on a domain. Repeating it in every manifest would be tedious and easy to get wrong, so we need a way to set properties in bulk: a global config, with domain-specific overrides.

## A config is a manifest with no box

A config is just a manifest with no box. It uses the same format, the same domains field, the same priorities, and the same deployment lifecycle as any other manifest, but since there is no WASM module behind it, it can only declare things the host can do by itself.

| a config can declare | a config can't declare |
| --- | --- |
| Domains it applies to | Routes that need a box to answer, like http, mcp, mail, or internal routes |
| Static content and templates | Data strategies |
| Header properties | External services |
| Rewrites and redirects | Timers, counters, or behavior |

The lack of a box is what prevents the second column, and it is also what makes a config cheap, safe, and easy to review. Drawing that line precisely requires a later document that defines exactly what a manifest is, field by field, and which fields need a box. Until then, the rule of thumb is that anything the host can serve or decide without running code belongs in a config, and anything that needs code belongs in a box's manifest.

## Domains: global and specific

Every manifest, config or not, says which domains it applies to, as described in the domains design.

```json
{
	"config": "platform-defaults",
	"domains": ["*"],
	"headers": {
		"Content-Security-Policy": { "value": "default-src 'self'", "priority": 0 },
		"Strict-Transport-Security": { "value": "max-age=63072000; includeSubDomains", "priority": 0 },
		"Referrer-Policy": { "value": "strict-origin-when-cross-origin", "priority": 0 }
	}
}
```

```json
{
	"config": "bobs-overrides",
	"domains": ["bobsplumbing.com"],
	"headers": {
		"Content-Security-Policy": { "value": "default-src 'self'; img-src 'self' https://maps.example.com", "priority": 10 }
	}
}
```

The first config applies to every domain on the host, and the second applies only to Bob's. Since configs are deployed like anything else, an operator can keep one global config for platform-wide defaults, and tenants or products can add domain-specific configs on top.

## Priority is per property

Every property, from every config and every manifest that applies to a request, carries a priority, and for each property, the one with the highest priority wins. On bobsplumbing.com, Bob's Content-Security-Policy, at priority 10, beats the platform's at priority 0, while Strict-Transport-Security and Referrer-Policy still come from the platform's config, since Bob didn't set them. Priorities are decided property by property, never config by config, so overriding one header never silently drops the others.

| rule | meaning |
| --- | --- |
| The maximum wins | For each property, the value with the highest priority applies. |
| Ties are refused | Two different values for the same property at the same priority, on an overlapping domain, are rejected by the checker, exactly like overlapping routes in the conflicts design. |
| Routes can join in | A box's manifest can set properties on its own routes, with priorities, and they compete under the same rules. |
| Loosening is flagged | When a higher priority makes a security header weaker, like adding an origin to a content security policy or turning off framing protection, the checker reports it to the approver. |

The host also keeps a few floors that no priority can lower. Identity screens always forbid framing, and cookies always belong to identity, as the UI design requires, so a config can tune a product's security headers but never take away the platform's.

## Testing configs

Since a config is a manifest, it is deployed exactly like one: uploaded, checked, approved, split, and made live, as described in the deployments design. Shadowing doesn't apply, since a config has no side effects, but splitting does, so a config can be A/B tested like a box. Trying a stricter content security policy on 5% of visitors and watching the error rate, or a longer cache lifetime and watching latency, measures the real impact of a setting before everyone gets it.

## Rewrites and redirects

A config, or a box's manifest, can also declare rewrite rules from one URL pattern to another. The key value of a redirect is the ability to go from document to document, so that moving a page never breaks a link, and the same idea applies to APIs, where an internal redirect lets an old API path keep working under a new one.

```json
{
	"config": "bobs-site-moves",
	"domains": ["bobsplumbing.com"],
	"rewrites": [
		{ "from": "/old-uri/{slug}", "to": "/new-uri/{slug}", "kind": "redirect" },
		{ "from": "/docs/{rest*}", "to": "/help/{rest*}", "kind": "redirect" },
		{ "from": "/api/v1/jobs/{job_id}", "to": "/api/v2/jobs/{job_id}", "kind": "internal" }
	]
}
```

| kind | what happens |
| --- | --- |
| redirect | The host answers with a permanent redirect to the new URL, so browsers and search engines move with the document. GET and HEAD get a 301, and every other method gets a 308, so a POST stays a POST. |
| internal | The host quietly routes the request to the new path on the same domain, and the caller never knows. The new route's requirements, priority, and box apply exactly as if the caller had asked for it directly. |

### The pattern language

The patterns are deliberately small, so that matching is simple, fast, clean, and free of the usual regular expression perils. We are willing to give up fullness for clear correctness.

- **A path is split into segments at every "/".** Matching compares segment by segment, left to right, with no backtracking, so it takes time proportional to the number of segments and nothing else.
- **A literal segment matches exactly that text.** /old-uri only matches old-uri, case and all.
- **{name} matches exactly one whole, non-empty segment.** /old-uri/{slug} matches /old-uri/plumbing, but not /old-uri/plumbing/thing, and not /old-uri/.
- **{name*} matches everything after the "/", across any number of segments.** It may only appear as the last segment, so /docs/{rest*} matches /docs/a, /docs/a/b/c, and /docs/ itself, with rest capturing whatever came after.
- **There is nothing else.** No partial segments like /page-{n}, no character classes, no optional parts, and no regular expressions.
- **The to side can only use names the from side captured,** and a {name*} capture may only appear as the last segment of the to side, since it may contain "/".
- **The query string is carried over unchanged.**

### Rewrites are routes

A rewrite occupies the URLs its from pattern matches, so it is a route for the purposes of the conflicts design: it has a priority, it conflicts with any overlapping route on the same domain at the same priority, and taking a URL away from a box by rewriting it is reported like any other shadowing. The checker also follows every rewrite to where it leads, and refuses any set of rewrites that could loop, or that would chain more than a few redirects deep, so a person is never bounced around forever.

## The invariants

- **A config is a manifest with no box.** It is deployed, checked, approved, split, and audited like any other manifest.
- **Properties are decided one at a time.** For each property, the highest priority wins, and a tie is refused.
- **The platform's floors can't be lowered.** Some protections apply to every domain, whatever any config says.
- **Patterns never backtrack.** {name} is one segment, {name*} is the rest, and nothing else exists.
- **Rewrites are routes.** They follow the same domain, priority, and conflict rules as everything else, and they can't loop.
