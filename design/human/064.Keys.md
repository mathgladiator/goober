# Keys

So, the host will maintain system-level keys that are stored in an isolated database, protected by encryption with a rotating encryption key that is stored in a secure vault. By abstracting the keys in this way, we also enable per-user keys, which is nice.

The posture here is simple: secure enclave storage is very expensive, so we use it sparingly, and we protect system-level resources well enough with decent practices. The vault holds one thing, the root key, and it is touched when the host starts and when keys rotate, never on a request. Everything else is ordinary encryption done well, in a database that no box can reach.

## What the host keeps

| key | scope | used for |
| --- | --- | --- |
| DKIM signing keys | system or tenant | Signing outbound mail, as in the mail design. |
| Reply token signing keys | system | Minting and verifying reply+{ticket : token} addresses. |
| OAuth and session secrets | system | The identity service's signing and hashing needs. |
| External service credentials | system or tenant | Names like keys/system/mailer or keys/tenant/{tenant}/ses that the network design attaches on the way out. |
| Backup encryption keys | tenant | Encrypting each tenant's backups with its own key. |
| Per-user keys | user | A person's own API keys for services that work per person, like a fitness tracker or their own calendar. |

None of these ever enter a box. A manifest names a key, the host resolves it at the moment of use, and the value lives only in the host's memory for as long as the call takes.

## Envelope encryption

The keys live in their own SQLite database, in their own directory, readable only by the host's user, the same way the identity database is kept apart. Inside it, every secret is encrypted with a data key, and the data key is itself stored wrapped by the root key in the vault.

```sql
-- The data keys, each stored wrapped by the root key in the vault.
CREATE TABLE data_keys (
	version INTEGER PRIMARY KEY,
	wrapped_key BLOB NOT NULL,            -- only the vault can unwrap this
	root_key_id TEXT NOT NULL,            -- which root key wrapped it
	created_at INTEGER NOT NULL,
	retired_at INTEGER                    -- no new secrets after this, still readable
);

-- Every secret, encrypted with a data key.
CREATE TABLE secrets (
	name TEXT NOT NULL,                   -- like 'mailer' or 'hevy'
	scope TEXT NOT NULL,                  -- 'system', 'tenant', or 'user'
	owner TEXT NOT NULL,                  -- '' for system, the tenant, or the user_id
	data_key_version INTEGER NOT NULL REFERENCES data_keys(version),
	nonce BLOB NOT NULL,
	ciphertext BLOB NOT NULL,             -- AEAD, with name, scope, and owner as associated data
	created_at INTEGER NOT NULL,
	updated_at INTEGER NOT NULL,
	PRIMARY KEY (scope, owner, name)
);

-- Every use of a secret, by name and never by value.
CREATE TABLE key_access (
	id INTEGER PRIMARY KEY,
	at INTEGER NOT NULL,
	scope TEXT NOT NULL,
	owner TEXT NOT NULL,
	name TEXT NOT NULL,
	purpose TEXT NOT NULL                 -- like 'external:mail_out.sendEmail' or 'dkim:sign'
);
```

When the host starts, it asks the vault to unwrap the current data keys, once, and keeps them in memory. From then on, reading a secret is a local decryption, which costs microseconds and no money. The name, scope, and owner are bound into each ciphertext as associated data, so a secret copied into another person's row won't decrypt, even by someone with write access to the database file.

Rotation happens at two levels, run by host-level timers from the time design:

- **Rotating the root key** means asking the vault to rewrap each data key under a new root key. It is a handful of vault calls, no matter how many secrets exist.
- **Rotating a data key** means creating a new version, encrypting new secrets with it, and re-encrypting old secrets in the background. The old version is retired, then removed once nothing uses it.

## Naming keys

Every key is named by its scope, then its owner, then its name, so a manifest always says whose key it means:

| scope | name | example |
| --- | --- | --- |
| system | keys/system/$name | keys/system/mailer, the platform's own mailer that the identity service uses for sign-in codes |
| tenant | keys/tenant/$tenant/$name | keys/tenant/{tenant}/ses, a business's own AWS account for sending its mail |
| user | keys/user/$user_id/$name | keys/user/{user_id}/hevy, a person's own API key for a fitness tracker |

These line up exactly with the scope, owner, and name columns of the secrets table, and "/" is reserved in them the same way it is in grant roles, so a substituted tenant or user_id can never reach into another owner's keys.

## Per-user keys

Per-user keys come almost for free from this design: they are just secrets with a scope of user and an owner of a user_id. A manifest declares the kinds of key a product needs, and an external service names one in its credentials, filled from the secure context. Per-tenant keys work exactly the same way, with a scope of tenant, entered by the tenant's owner rather than by each person.

```json
{
	"keys": {
		"hevy": {
			"scope": "user",
			"label": "Your Hevy API key"
		},
		"ses": {
			"scope": "tenant",
			"label": "Your Amazon SES credentials"
		}
	},
	"external": {
		"workouts": {
			"openapi": "hevy.v1.openapi.json",
			"base": "https://api.hevyapp.com",
			"credentials": "keys/user/{user_id}/hevy",
			"methods": {
				"getWorkouts": {}
			}
		}
	}
}
```

Like grant options in the identity design, a credential name may only substitute from the secure context, so a box can only ever use the key of the person it is acting for, and "/" can't be substituted into a name to reach someone else's. A person enters or replaces their key through a screen the host provides, using the label from the manifest, so the key goes straight from the person to the key database without ever passing through a box.

## The limits of this design

Per-user keys are applicable to a specific, useful job: holding a person's credentials for other services so that the platform can act for them, and letting them remove those credentials cleanly. However, it is worth being exact about what they are not, since "per-user keys" can sound like more than this design provides.

| limit | what it means | when it matters |
| --- | --- | --- |
| The operator can read them. | Per-user keys are protected by the system's data key, not by anything only the person holds. Someone with the host and the vault can decrypt every one. | When people expect that even the operator can't see their secrets. That needs keys held by the person, which this design doesn't offer. |
| A running host holds everything. | The unwrapped data keys sit in the host's memory, so a compromised running host exposes every secret, per-user ones included. | This is the price of not calling the vault on every request. It is why the host stays small and boxes never see a key. |
| Per-user keys aren't in the vault. | Giving every person their own vault key would cost a vault call per use and a vault object per person, which is exactly the expense we are avoiding. | When a single secret is valuable enough to justify the vault, like a signing key for releases. Those get their own vault key, sparingly. |
| Deleting a key only shreds what it encrypted. | Removing a per-user or per-tenant key makes what it encrypted unreadable, including old backups, but only data that was actually encrypted with it. | Tenant backups should be encrypted with the tenant's key, so that deleting a tenant really does erase it from history. Plain database files are not covered. |
| No vault, no start. | The host can't unwrap its data keys without the vault, so it can't start while the vault is down. | A running host doesn't notice a vault outage until it restarts or rotates. Restarts should be planned with that in mind. |
| Keys don't make boxes trustworthy. | A key used for a person's request can be misused by that request's box within the scope of that person's own access to the outside service. | The network design's require blocks, budgets, and audit still matter, since the key is only as safe as what may be done with it. |

## Decent practices

Protecting system-level resources well enough doesn't need an enclave for everything. It needs a short list of habits that are never skipped:

- **Secrets are names in manifests, never values.** A manifest that contains a value is refused by the checker.
- **Secrets never reach a box, a log, or telemetry.** Access is recorded by name and purpose in key_access, and values are scrubbed from every error the host reports.
- **The key database is backed up apart from the data.** Its backups are encrypted and stored separately from tenant backups, so one stolen bucket is never both the lock and the key.
- **Cloud credentials are as narrow as the job.** The credentials a host uses to stream backups can write but not read or delete, and restoring is a separate, privileged path.
- **Secrets are short-lived in memory.** Decrypted values are cleared after use, rather than cached alongside everything else.
- **Rotation is routine.** Keys rotate on a schedule, so that rotating in an emergency is a process we've already practiced rather than one we're inventing.

## The invariants

- **The vault holds only the root key.** It is used when the host starts and when keys rotate, never on a request.
- **No key ever enters a box.** Boxes name keys, and the host uses them.
- **A credential name can only substitute from the secure context.** A box can't reach anyone else's key.
- **Every ciphertext is bound to its name, scope, and owner.** A secret moved to another row won't decrypt.
- **Every use is recorded, and no value is.** The audit says who used what, and never what it was.
