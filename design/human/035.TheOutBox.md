# The Outbox

A write to a database can be thrown away, but an email can't be unsent. That one fact is the whole reason this document exists. The data design gives every request a write set that commits all at once or not at all, and the network design lets a box call services through the host. Put them together naively, and a box sends a "welcome!" email, traps on the next line, and the user gets welcomed into an account that does not exist.

The answer is old and boring, which is exactly why we like it: the outbox. A side effect on the network is captured as an element within a queue, and that element lives in the write set alongside the data. If the write set commits, the side effect is committed to happen. If the write set is thrown away, the side effect never existed.

## Safe calls and effectful calls

Not every call changes the world. Reading a forecast is safe to do immediately, and doing it twice is harmless. Sending an email, charging a card, or creating a ticket changes the world, and those are the calls that belong in the outbox. The OpenAPI document gives us a reasonable default from the verb: GET and HEAD are safe, while POST, PUT, PATCH, and DELETE are effectful. The manifest can override this per method, since some APIs are honest about their verbs and some are not.

```json
{
	"external": {
		"mailer": {
			"openapi": "mailer.v3.openapi.json",
			"base": "https://mail.example.com",
			"credentials": "keys/system/mailer",
			"methods": {
				"sendMessage": {
					"require": {
						"body.to": "{user_email}"
					},
					"effect": "outbox",
					"idempotency": "header/Idempotency-Key",
					"delivery": {
						"attempts": 8,
						"backoff-ms": 1000,
						"within-ms": 600000
					},
					"budget": {
						"calls": 3
					}
				}
			}
		}
	}
}
```

The effect field is one of three values. "none" is a safe call that goes out immediately. "outbox" is an effectful call that waits for the commit, and it is the default for effectful verbs. "immediate" is an effectful call that goes out right now anyway, which is sometimes necessary and always makes the route non-atomic, as described in the shape of data.

## What the box sees

For an outbox call, the generated function returns as soon as the host has captured the element in the write set. The box gets back true for accepted, and the same caveat as data applies: accepted is not delivered. The interesting consequence is that the box can't use the response of an outbox call to build its own response, since the call hasn't happened yet. That is a real constraint, and it is the honest one. If a box truly needs the response before it can answer, then the call is "immediate," the route is not atomic, and the checker says so.

```C
#include <stdbool.h>
#include <stddef.h>

struct mailer_send_message_request {
	const char* subject;
	size_t subject_len;
	const char* text;
	size_t text_len;
	// no "to": the host fills it from {user_email}
};

// Captures the message in the outbox; returns true if accepted.
bool mailer_send_message(const struct mailer_send_message_request* request);
```

When a box does care about what happened, the manifest can name a route to receive the result. Once the host delivers the element, or gives up on it, the result comes back to the box as a brand new request on that route, with its own context, its own timeout, and its own write set. The box doesn't wait on the world; the world calls the box back.

## Delivery

After the commit, a dispatcher run by the host drains the outbox. Delivery is at-least-once, because networks fail in the middle of things and the only alternative to at-least-once is at-most-once, which is a polite name for losing messages. To make at-least-once safe, every element carries an idempotency key that the host derives from the request and the element's position in the write set, and the host sends it in the place the manifest names. A service that honors the key turns our at-least-once into exactly-once on its side.

Elements to the same scope go out in sequence order, the same order the sequencer gave the writes, so "create the ticket" never arrives after "close the ticket." Retries back off, and an element that can't be delivered within its deadline lands in a dead letter queue that shows up in monitoring with the full story of every attempt. The box never sees a retry, a backoff, or a timeout from the service; it only sees the result route, if it asked for one.

## Boxes talking to boxes, again

An outbox element whose service is another box is just a request to that box that has been committed to happen. This turns the outbox into the explicit queue between boxes, with the same idempotency, ordering, budgets, and audit as any other call. A box that needs to tell another box something, without waiting for it, writes to the outbox and moves on.

## The invariants

- **An element is enqueued if and only if its write set commits.** There is no side effect without the data, and no data without the side effect.
- **Delivery is at-least-once, with a stable idempotency key.** Retries never invent a new identity for the same element.
- **Elements within a scope are delivered in sequence order.** The outbox never reorders what the sequencer ordered.
- **Every element ends in exactly one place.** It is either delivered or dead lettered, and both are recorded.
- **"immediate" is the only way around the outbox, and it is visible.** The checker marks every route that uses it as able to tear, and a human can see the list.

## Starting small

Tactically, we start with the outbox living inside the same database as the write set, as a table the host owns, since that makes "enqueued if and only if committed" a property of a single SQLite transaction rather than a distributed systems problem. A box with data in a tenant database gets its outbox in that same file, and it packs up and moves with the tenant. There is an open question as to how far a single host should go in owning the dispatcher before it becomes its own service with its own manifest, but that is a happy problem for a later date.
