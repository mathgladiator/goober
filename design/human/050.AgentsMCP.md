# MCP

Much like HTTP, we also enable MCP (over HTTP) at a protocol level. We do this so we can have explicit control over what the agents can do, whilst respecting the same permission boundaries the host enforces on users. Agents are simply users acting on behalf of a user, running code just for them, so that we can minimize accidents and focus on agentic value-add rather than worrying about new routes or surprises. For example, we can trust humans to delete their stuff, but maybe we only trust agents to mark a thing for removal that a human has to approve.

The rule of thumb is that MCP mirrors HTTP. Everything the HTTP design gives a route, a tool gets as well: declared inputs, typed outputs, requirements, a fixed vocabulary of results, and a host that does the protocol so the box never does. The differences are all about the fact that the caller is a model, and a model is fast, tireless, literal, and occasionally talked into things by the text it reads.

## Tools are routes

An MCP tool is declared under routes, just like an HTTP route, with mcp as the protocol, the tool name in place of the path, and tool as the verb. Resources, which are read-only, use resource as the verb and mirror a GET.

```json
{
	"types": "jobs.openapi.json",
	"context": {
		"tenant": {
			"type": "string",
			"source": "domain/tenant"
		}
	},
	"routes": {
		"mcp": {
			"list_jobs": {
				"tool": {
					"name": "list_jobs",
					"description": "Lists the open jobs for this business, newest first.",
					"input": "json:JobQuery",
					"response": "json:JobList",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]]
				}
			},
			"mark_job_for_removal": {
				"tool": {
					"name": "mark_job_for_removal",
					"description": "Marks a job for removal. A person must approve before anything is deleted.",
					"input": "json:JobRef",
					"response": "json:Job",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"]]
				}
			},
			"jobs://{job_id : int64}": {
				"resource": {
					"name": "job",
					"description": "A single job, with its customer and schedule.",
					"response": "json:Job",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]]
				}
			}
		}
	}
}
```

| HTTP | MCP | notes |
| --- | --- | --- |
| A path, like /jobs | A tool name, like list_jobs | Names are unique within the box, as route names already are. |
| A verb, like post | tool, or resource for reads | A resource is the MCP twin of a GET, with the same caching. |
| Path and query parameters | The tool's input, as a named type | Inputs come from the types document, so there is no anonymous JSON. |
| A body | The tool's input | Same max size rules, and invalid input never wakes the box. |
| A response type | The tool's response, as a named type | The host serializes it into the tool result. |
| Headers, cookies, tokens | Not on the tool at all | The agent's identity arrives in the secure context, as described in the identity design. |

The description is new, and it matters more than it looks. It is text that a model will read and act on, so it is part of the box's shape: it lives in the manifest, it goes through the human approval queue like any other change, and the host serves it verbatim. A box can't rewrite its own tool descriptions at runtime, since in a world where words are viruses, a description is an instruction.

## Who is calling

An agent is a user acting on behalf of a user. When an agent signs in through the identity design's OAuth flow, its token is marked as acting for an agent, and the secure context carries two things: the user_id of the person who connected it, and the agent's client_id, as principal/client_id. The user_id is what every requirement and every substitution sees, so an agent can never do more than the person it acts for. The client_id is what tells the host that this is an agent and not the person in a browser. An agent also connects to a specific domain, which decides its tenant and its identity realm, and its token is only accepted in that realm, as described in the domains and identity designs.

That distinction gives us one more rule, and it is the core of explicit control: **an agent's token can only call mcp routes.** HTTP routes refuse agent tokens by default, even when the person behind the agent would pass the route's requirements. An HTTP route can opt in with "agents": true, but most shouldn't, since the whole point of the mcp section is to be the deliberate, reviewed list of what agents can do. A person in a browser can call both, since humans can use any interface we give them.

| caller | HTTP routes | MCP routes |
| --- | --- | --- |
| A person, signed in | Yes, subject to requirements | Yes, subject to requirements |
| An agent acting for that person | Only routes with "agents": true | Yes, subject to the same requirements |
| Nobody signed in | Only routes with "public": true | Never; MCP always requires a user |

MCP routes can't be public. An agent always acts for somebody, and an anonymous agent is just a scraper with a better vocabulary.

## Permissions, mirrored

Everything in the identity design applies to tools without change. Requirements are in disjunctive normal form, a tool with no requirements is refused by the checker, substitution in requirements may use the secure context, the tool's input, or the resource path, and grant roles mean exactly the same strings. An agent passes a requirement if and only if the person it acts for would pass it.

A tool may declare grantable or revocable blocks, with the same options and substitution rules as HTTP. Since handing out power is the last thing we want a model to do on a whim, the checker flags every tool that can grant or revoke a role for the human approving the manifest, and whether agents should have such a tool at all is a product decision.

## Isolating agents in their own box

At core, the goal is that the agent has isolated code, and anything dangerous, like a delete, is gated by access through the workflow rather than by trusting the agent to behave. The cleanest way to get there is often a separate box. A product can give its agents their own box, with its own manifest, its own tools, and different write channels: for example, data strategies that can read jobs and write removal requests, but have no write path to the jobs table at all. The human-facing box keeps the routes that actually delete.

Nothing new is needed for this. It is the same perimeter the rest of the design already draws: an agent box that has no strategy capable of deleting a job can't delete a job, however it is asked, and how a removal request becomes a deletion is the product's own workflow. Which tools exist, and which box they live in, are product decisions, and the manifest makes each of those decisions visible to the human approving it.

## The result vocabulary

Just as an HTTP route doesn't get to pick any status it likes, a tool doesn't get to pick any result it likes. The generated functions mirror HTTP exactly.

```C
#include <stdint.h>

struct job_ref {
	int64_t job_id;
};

const struct job_ref* mark_job_for_removal_get_input();
void mark_job_for_removal_respond_json(const struct job* job);
void mark_job_for_removal_respond_error_simple_4xx(int32_t status);
```

| HTTP | MCP |
| --- | --- |
| 200 with a typed body | A tool result with typed content |
| 4xx from the box, clamped | A tool result marked as an error, with the clamped status and a message the model can act on |
| 404 for a scope miss, never 403 | "Not found", never "forbidden", so an agent can't probe what exists |
| 5xx from the host | A protocol error from the host |

A tool error is something the model reads and reacts to, such as "that job is already closed," so 4xx results carry a short message. A host failure is not the model's business to reason about, so it gets a plain protocol error, and the details stay in the host's accounting.

## What the host does for free

Because the manifest describes every tool completely, the host takes on all of MCP itself, the same way it takes on HTTP:

- **The transport.** MCP over HTTP lives at a single endpoint the host owns, with sessions, streaming, and the OAuth handshake from the identity design.
- **Discovery, filtered by permission.** When an agent lists tools and resources, the host only returns the ones the person behind it can call. An agent working for a member never even learns that delete_job exists, which removes both a temptation and a leak.
- **Validation.** Inputs are checked against their types before the box wakes up, and a malformed call costs the box nothing.
- **Cancellation.** When an agent cancels a call, the host stops the request and throws away its write set, so a cancelled call never half-happens.
- **Subscriptions.** Resource subscriptions are the bus. A resource's wake-up signals and coalescing come straight from the bus design, so an agent watching a job hears that it changed and reads it again, rather than receiving a stream of data.
- **Caching.** Resources get the same ETags as GETs, built from the signature and sequence numbers.
- **The audit.** Every tool call is written down: the agent, the person, the input, and the result. The person can read their agents' history on their account page, and so can whoever audits the box.

## Agentic considerations

Agents are not just fast humans, and a few concerns are specific to them.

- **Agents loop.** A model can call the same tool hundreds of times in a minute without noticing. Per-request budgets still apply, and on top of them, every agent session has its own quota of calls and of effectful calls, so a confused agent runs out of fuel rather than running up a bill.
- **Agents read untrusted text.** A tool result might contain a customer's email, a job note, or a web page, and any of those can contain instructions aimed at the model. The host can't fix the model, but it can keep the blast radius small: tool descriptions are fixed and reviewed, results are typed rather than free-form, and every effect still has to pass requirements and budgets. An injected instruction can at worst make an agent do what its tools allow, which is why the agent's tools, and the box they live in, should be as narrow as the job.
- **Agents are revocable instantly.** Disabling an agent on the account page ends its session at the next request, with no change to any box.
- **Agents get the smallest useful surface.** The mcp section of a manifest is deliberately smaller than the HTTP section. A tool that does not exist can't be misused, which is the same reason a box gets no sockets.

## The invariants

- **Agents can only call mcp routes, unless an HTTP route opts in.** The mcp section is the reviewed list of what agents can do.
- **An agent never passes a requirement its person would fail.** Requirements see the person's user_id, and nothing else.
- **MCP routes are never public.** Every agent acts for a user.
- **Agents get isolated code.** Dangerous actions are gated by which tools and write channels exist, not by trusting the agent.
- **Tool descriptions are part of the box's shape.** They change only through the approval queue, and the host serves them verbatim.
- **An agent only discovers what it may call.** Tool and resource lists are filtered by the person's grant roles.
