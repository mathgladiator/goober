# Backups: Off the Machine, Every Night, and In Between

> Drafted by Claude on 2026-10-27 at the human's request, for the human to edit and own.
> What the host builds of it is recorded in `design/machine/019.Backups.md`.

A goober host is one machine with everything on its disk: tenant databases, identity realms,
uploaded attachments, static content, box versions, keys. If that disk dies, everything dies with it,
unless a copy lives somewhere else. So the host backs itself up to S3 (or anything that speaks
S3), on its own, without an operator remembering to.

There are three streams, each matching how its data changes:

| what | how often | how it goes |
| --- | --- | --- |
| immutable assets (attachments) | as they arrive | each one queued and uploaded once |
| databases | every few minutes | only what changed since the night before |
| everything | nightly | one sealed `tar.gz` of the whole storage |

## Immutable assets are queued

An attachment never changes after it is stored; that is the point of `/attachment/$id.$ext`.
So it only ever needs to go up once. When an upload finishes, the asset is queued, and a
background worker uploads it to `assets/$tenant/$id.$ext` in the bucket. A failure stays in the
queue and is retried with backoff; nothing about the upload waits on S3. The queue is
rebuilt from the attachment ledger, so a crash never loses an asset that needs uploading.

Because assets go up individually, the nightly archive leaves them out. That keeps the
nightly small even when a site holds gigabytes of pictures.

When an attachment is deleted, its copy in the bucket stays for the retention window (below),
so restoring an older night still finds every picture that night referenced.

## Nightly, with a rotating fourteen-day window

Once a night, at a configured hour, the host takes a consistent copy of its storage (SQLite's
online backup for each database, so nothing stops), packs it into one `tar.gz` with the host's
config, seals it, and uploads it as `nightly/2026-10-27T03-30-00Z.tar.gz.sealed`.

The timestamp is in the name, so the window is simple: after a successful upload, the host lists
`nightly/` and deletes every archive whose name is older than fourteen days (configurable). There
are always fourteen nights to choose from, and a failed night never deletes anything.

## Incremental database backups

A night is a long time to lose. Between nightlies, every few minutes (fifteen by default), the
host looks at each database that changed, takes a consistent copy, and compares it page by page
with the copy in last night's archive. Only the pages that differ go up, sealed, under that night's
`increments/`, with a small manifest that says, for every database, how to rebuild it at that moment
and the hash the rebuilt file must have.

Each increment is against the night, not against the increment before it. Restoring to any
moment needs only the night and one increment per database. A lost increment costs that one
moment, not every moment after it. Increments age out with their night.

## Sealed before they leave

A backup holds everything: every person's email address, every row, every key. So nothing goes
to the bucket readable. Every file is sealed with a backup key (ChaCha20 with HMAC-SHA-256,
encrypt-then-MAC) before upload, and checked before it is used on the way back.

The backup key is 32 random bytes made once per host. The host keeps it, and **the operator must
keep a copy somewhere else**. A backup is useless without its key, and the host that held the key is
exactly what a backup is for losing. The host prints the key on request and nags until a copy is
confirmed.

The bucket's own credentials are AWS keys in the host's key store, never in the config. The
IAM user needs only put, get, list, and delete on the bucket.

## Rehydrating on a devbox

A backup is only real once it has been restored, so restoring has to be easy enough to do for
fun. On any machine with the host binary:

```
just rehydrate ~/goober-copy                  # the latest moment
just rehydrate ~/goober-copy 2026-10-26T18:00 # the last moment at or before then
just run ~/goober-copy/host.json
```

It downloads the right night, applies the right increment, fetches the assets, checks every hash,
and writes a devbox config next to it. A rehydrated host is a **sandbox**:

- it listens on localhost only, with the local domain aliases;
- **no mail leaves** (the dev mailer writes it to disk);
- **no outbound calls or outbox deliveries leave**: they wait, visibly, in the outbox;
- **no backups run**, so a devbox never writes into production's bucket;
- the production key store is left out, unless asked for.

That makes the devbox a place to test a new box version against real data, reproduce a bug, or
just prove the backups work, without a single person getting an email they shouldn't.

## What the operator sees

The operating panel (and the operator MCP) shows the last nightly and when, the last increment,
the asset queue's depth and oldest item, the last error, and the restore points in the bucket.
An operator can also start a nightly or an increment now. A backup that hasn't succeeded in
more than a day is a red line.

## Not in scope, yet

- Point-in-time recovery to the second (a write-ahead log shipped continuously). Increments
  every few minutes are the trade.
- Backing up to two places at once.
- Restoring one tenant, or one database, into a live host. Rehydrate a devbox and copy what's
  needed.
- Rotating the backup key. A new key starts a new chain; old archives need the old key.
