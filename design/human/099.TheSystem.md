# The System Around

At core, the system is going to start as a simple HTTP server, and we are going to leverage existing services for managing its role. For example, we will use Caddy for HTTPS, HTTP/2, and the Let's Encrypt dance. We will let the load balancer do its job, and this then also gives us stickiness for users. Similarly, we will use Stalwart for converting SMTP into HTTP, providing mail delivery.

The rule of thumb is to own the box and rent the edge. The host is the part we write, because the host is where every invariant lives. Everything else is a commodity protocol that somebody has already spent a decade getting right, and we are going to be happy to let them.

## Keeping the host small

A host that terminates TLS, speaks SMTP, and runs its own consensus has a hundred reasons to be wrong. A host that speaks plain HTTP in, plain HTTP out, and SQLite to disk has very few, and every line of it can be reviewed by a person who knows what they are looking at. We are asking humans to read the pipe, so the pipe had better be short.

| job | who does it | what the host does instead |
| --- | --- | --- |
| TLS, certificates, HTTP/2 | Caddy | Speaks plain HTTP behind it, and answers Caddy's on-demand TLS check from the domain registry, so certificates are only requested for registered domains, and only verified ones when the host requires verification. |
| Load balancing and stickiness | Caddy, or the cloud's load balancer | Nothing; it just serves what arrives. |
| Mail in and out | Stalwart | Receives mail as HTTP requests and sends mail as HTTP calls from the outbox. |
| Backups of data | Litestream to object storage | Writes to SQLite and trusts the WAL to stream away. |
| Signals between machines | NATS | Publishes and subscribes to tiny signals. |
| Keeping processes alive | systemd, or the orchestrator of the day | Exits cleanly and lets something else restart it. |

These services are trusted infrastructure configured by humans, and the boxes are untrusted code contained by the host. A box never talks to any of them directly.

## Stickiness is for speed, not correctness

If requests for a tenant keep landing on the same host, their isolates stay warm and their SQLite file is already on local disk, so the system gets faster for free. However, nothing may depend on it. When a request lands on the wrong host, the host forwards it to the owner of the file, and the single-writer lease keeps that honest. A load balancer that forgets everything during a deploy should cost us latency, never data.

## One machine, then many

All of this runs on one machine first, with the bus in-process and backups in a bucket somewhere, and for a lot of products, that is the only deployment they will ever need. Adding capacity means adding hosts behind the load balancer and switching the bus to NATS. The manifest doesn't change, the boxes don't change, and the host stays the same small program.

Tactically, we start with Caddy and a single host, which is enough to serve hello world over HTTPS. Litestream comes next, because data without a backup is a hobby. Stalwart comes when the first box sends an email, and NATS comes when the second machine shows up.
