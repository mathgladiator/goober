# Migration

Tables change. A product grows a column, drops a field it regrets, or needs an index it didn't know it needed, and every deployed box that reads or writes that table was built against the old shape. Migration is how a table changes shape without any of those boxes noticing, without surprising anyone about data, and with a human warned, in plain words, about every consequence before it happens.

The goal here is simplicity. The host only performs changes it can emulate perfectly for every box still running against an older shape, and it performs them right away. Everything else is refused at the API, and the developer does it the honest way: with a new table and a box that moves the data, or with a new schema version and an upgrade box that forces the change.

Be warned that this is complex. Schema migration is one of the hardest jobs in operating any product, and nothing in this document makes it easy; it only makes it honest. Two things keep the pressure down. First, by default, a schema can always be expanded, by adding tables or new fields with defaults, and since most products only ever grow, most changes never touch the hard parts. Second, data with a long life can live in sources, which never migrate at all, as described in the sourcing design.

## A schema is a partial set of tables

A .schema file doesn't describe a whole database. It describes some of its tables: a partial set, covering only what one product or one box needs. A database is the union of every schema applied to it, so a jobs product and a billing product can each own their own tables in the same tenant database, and each one changes on its own schedule. This applies everywhere a schema is named: a data strategy names the schema that holds its table, the checker validates queries against the tables a schema declares, and the operating panel shows which schemas make up each database.

A .schema file is never edited. A change to any table in it is a new schema version, like core14 after core13, and both exist side by side. Every manifest pins exactly one version of each schema it uses, so a box built against core13 keeps seeing core13 for as long as it is deployed, whatever the tables have become underneath. Each table has exactly one physical shape in each database at any moment, the shape from the newest version of its schema, and the host projects that shape to whatever version each box pinned.

## The kinds of change

The host compares each table in the new version against the same table in the previous version, and classifies the change. The kind decides everything else.

| kind | examples | executed | what older boxes see |
| --- | --- | --- | --- |
| Pure expansion | A new table; a new column with a default or allowing null | Immediately | Nothing. A new column is invisible to them; their inserts fill it from its default, and their updates and patches leave it alone. |
| Pure contraction | A dropped column; a dropped table | Immediately | Writes to a dropped column are dropped at each write. Reads of it return the default declared for it in their version, or null, zero, or empty if none was declared. A dropped table reads as empty, and writes to it are dropped. |
| Pure indexing | A new index; a dropped index | Immediately | Nothing, except that an index a deployed box's by_index strategy still names can't be dropped until no such box remains. |
| Mixed | Any combination of the three above | Immediately, as the expansions, then the contractions, then the indexing | The combination of the above, column by column. |
| Emulated type change | A type change the host can translate both ways | Immediately, with a warning | Values are converted on the way in and out, and a read that can't be converted fails. |
| Anything else | Renames, narrowing types, new constraints that existing data may break | Refused at the API, unless forced by an upgrade box | Not applicable when refused. The developer adds a new table instead, or forces the upgrade, as described below. |

Since every allowed change is applied immediately, there is no expand phase, no backfill, and no second copy of a table kept in step. The host applies a change to each database in place, using what SQLite does natively (adding and dropping columns, creating and dropping tables and indexes), and records the new version in the database. A database that is offline, or not yet opened, gets every pending change, in order, before it serves its next request.

## Type changes the host can emulate

Most type changes are hard, and they are refused. A few are easy, because the host can convert a value in both directions without losing anything an older box could see, and these are called out by the checker every time:

| change | how the host emulates it | the warning |
| --- | --- | --- |
| Widening an integer, like int32 to int64 | Older boxes read the narrower type and write it as is. | An older box reading a value that no longer fits in its type fails that read, so a widened column must be watched until no older box remains. |
| Widening a float, float to double | The same, with rounding on the way out. | Older boxes see rounded values. |
| Allowing null in a column that didn't | Older boxes read null as the default declared for the column in their version. | Older boxes can't tell a null from that default. |
| Loosening a constraint, like dropping a check or a unique rule | Nothing needs converting. | Older boxes may now read data their version's rules would have refused. |

## What is refused

The API refuses any schema change the host can't emulate perfectly for older boxes, with a message that says why and what to do instead:

- **Renaming a column or a table.** To the host, a rename is a contraction and an expansion, and the contraction would drop the data. Add the new column, or the new table, and move the data with a box.
- **Narrowing a type, or changing it to an unrelated one,** like text to integer. Older boxes would write values the new type can't hold.
- **Adding a constraint existing data might break,** like a unique rule, a check, or a column that no longer allows null. The host can't know in advance that every tenant's data already obeys it.
- **Changing a table's primary key.** Every by_id and by_index strategy depends on it.

These limits are deliberate. Every allowed change is one the host can apply in place, at once, and keep perfectly invisible to older boxes, so a migration never needs a plan, a pipe, or a schedule. Every refusal except the last can be overridden by forcing the upgrade with a box, which moves the hard part into code a person can read and test. Changing a primary key is refused even then.

## Forcing an upgrade with a box

By default, a schema can always be expanded: a new table, or a new column with a default or allowing null, is accepted at any time with no ceremony. That relaxes most of the pressure, and it means people can version within a schema freely, core13, then core14, then core15, as long as each step only expands.

When a step needs more, like a rename, a split, or a narrowed type, the developer can force it. They write the new schema version, and deploy it together with an upgrade box: a box whose WebAssembly says how every existing row, and every existing data write from a box still pinned to the old version, becomes the new shape. The host can't emulate the change on its own, so the upgrade box teaches it how.

```json
{
	"box": "core14_upgrade",
	"mission": "Split users.name into first_name and last_name for core14.",
	"routes": {
		"upgrade": {
			"users": {
				"from": "core13.schema",
				"to": "core14.schema",
				"rows": { "name": "upgrade_users_row" },
				"writes": {
					"profile.user_by_id.rename": { "name": "upgrade_rename" },
					"profile.user_by_id.save_profile": { "name": "upgrade_save_profile" }
				},
				"reads": { "name": "downgrade_users_row" },
				"timeout-ms": 20
			}
		}
	}
}
```

An upgrade route is keyed by the table it upgrades, and it carries three kinds of handler:

| handler | takes | returns | when the host runs it |
| --- | --- | --- | --- |
| rows | One row in the from shape | The row in the to shape | Once for every existing row, in every database, during the upgrade. |
| writes | The values of one named write, in the shape of the box that made it, and the current row in the to shape, if there is one | The row in the to shape | On every such write from a box still pinned to from, after the upgrade. |
| reads | One row in the to shape | The row in the from shape | On every read by a box still pinned to from, after the upgrade. |

Each key under writes names one existing data write as box, strategy, and write, so an upgrade is precise about which writes it upgrades, the same way the checker is precise about which writes a contraction drops.

The rules:

- **An upgrade box is a pure function.** It declares no data strategies, no external services, no outbox, and no keys, and it gets no clock and no randomness, so the same input always gives the same output and the host can run it again on any retry. The checker refuses an upgrade box that asks for anything else.
- **Every old write is covered.** The checker refuses the upgrade unless every named write, in every deployed box version pinned to from, that touches the table has a writes handler. Old boxes keep running, unaware, and their writes are upgraded on the way in.
- **Old readers are covered, or gone.** If any deployed box reads the table at from, the reads handler is required. Without one, the upgrade waits until no such box remains.
- **One step at a time.** from is the version immediately before to. A box pinned further back reaches from through the ordinary projections above, then through the upgrade box.
- **Each database upgrades whole.** Holding a database's writer lease, the host builds the table in its new shape, runs every row through rows, checks each result against the new shape's constraints, and swaps the new table in, in one transaction, while that database's writes wait. If any row fails, the whole upgrade of that database rolls back, the database stays at from, and the operating panel says which row and why. A database that is offline, or not yet opened, upgrades before it serves its next request, like any other pending change.
- **New boxes wait for their data.** A box pinned to to can't serve a database until that database has upgraded.
- **The upgrade box retires last.** It stays deployed until no deployed box is pinned to from, and then it retires with that version.
- **Sources are never upgraded.** A source only expands, as described in the sourcing design, so an upgrade route that names a source is refused.

Forcing an upgrade rewrites data in place, so it is approved like any other box and warned about in plain words before it runs, as listed below. The host can also run the rows handler against a copy of each database first, and report every row that fails, before anything is changed.

## Data migrations are a product's job

When a product really needs to restructure its data, like splitting a name into first and last, or changing a column's type, it does what a careful engineer would do anyway, using only the moves above:

1. **Add a new table** in the new shape, which is a pure expansion.
2. **Deploy a box version that writes both,** keeping the old table and the new one in step on every write.
3. **Backfill with a box,** using a timer or an internal route that walks the old table in batches and writes the new one, idempotently, so it can be retried.
4. **Move the readers** to the new table, through the usual approvals and traffic plans.
5. **Drop the old table,** which is a pure contraction, once no deployed box reads it.

Every step is an ordinary deployment or an ordinary schema change, so it is reviewed, approved, and visible like any other. The meaning of the data lives in a box, where it can be read and tested, and never inside the host.

When the old table is built from a source by an event route, steps 2 and 3 collapse into one: a new event route fills the new table from the first event, while the old route keeps the old table current, as described in the sourcing design. That is the cheapest data migration there is, and it is a good reason to keep long-lived data in sources.

## Writes across versions

Every write in the data flow design has a name and one of five kinds, and the kinds are what make immediate changes safe:

| kind | what it carries | across a change |
| --- | --- | --- |
| insert | A whole row in the box's version | Columns its version doesn't know are filled from their defaults; columns its version has that were dropped are discarded. |
| update | A whole row in the box's version | Columns its version doesn't know keep their current values; dropped columns are discarded. |
| upsert | A whole row in the box's version | An insert if the row doesn't exist, and an update if it does. |
| patch | Exactly the columns it lists | Only those columns are written; any that were dropped are discarded. |
| patch-except | Every column of the box's version except the ones it lists | Mapped like a patch of those columns, so columns its version doesn't know are never touched. |

No kind of write can blank out a column its box has never heard of. Since the checker reads each deployed manifest's writes, it can say exactly which named writes touch a column that a contraction drops, rather than which boxes merely use the table.

## Warnings before anything happens

Every schema change is approved by a human, and the checker spells out its consequences first, in plain words:

| consequence | when the checker warns |
| --- | --- |
| Data will be dropped | A contraction removes a column or table that still holds data, on every database, at once. |
| Writes will be discarded | Named writes in deployed boxes still write a column or table being dropped, and the checker lists them. |
| Reads will be invented | Older boxes reading a dropped column will see its default instead of the value they used to see. |
| Values will be invented | A new column will hold its default for every existing row. |
| Values may not fit | An emulated type change could produce values that older boxes can't read. |
| An index is still in use | A dropped index is named by a deployed by_index strategy, so the change is held until that box is retired. |
| Rows will be rewritten | An upgrade box rewrites every row of a table, on every database. |
| Writes will be rewritten | Named writes in deployed boxes pinned to the old version will pass through code in the upgrade box, and the checker lists them. |
| Reads will be translated | Older boxes will read rows that an upgrade box converted back into their shape. |

## Future: tapping into existing data flow

Writing both tables by hand, in the box, is the simplest way to keep them in step during a data migration, but it means deploying a new version of the box that owns the old table. Data kept in sources already avoids this, since any new event route can rebuild a table from history, as described in the sourcing design. For ordinary tables, a future addition could let a migration box subscribe to the committed writes of an existing table, delivered to an internal route at least once and in order per row, so it can keep a new table in step without touching the old box at all. That is close to treating every table as a source, which is explored further in the machine design on event sources.

## The invariants

- **A schema is a partial set of tables.** A database is the union of the schemas applied to it.
- **Schema versions are immutable.** Changing a table always means a new version.
- **Every allowed change is immediate.** Expansions, contractions, indexing, and emulated type changes are applied in place, with no backfill and no second copy.
- **Every box sees its own version.** Reads and writes are projected at the boundary, so no box notices a change.
- **A schema can always expand.** New tables, and new columns with defaults or allowing null, are accepted by default.
- **What the host can't emulate is refused, unless forced.** Renames, narrowing, and new constraints are done with new tables and boxes, or forced with an upgrade box that covers every row, every old write, and every old reader.
- **An upgrade box is a pure function.** No data, no network, no clock, and no randomness, so the host can run it again at will.
- **Changing a primary key is always refused.**
- **Sources never migrate.** They only expand.
- **A schema version is deleted last.** Only when no deployed manifest pins it.
