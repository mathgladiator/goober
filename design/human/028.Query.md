# Queries

We like simple access patterns like by_id, paginated indices, and append mode. These provide simple, highly common patterns, like an ORM provides. However, they are inefficient, since they force every box to reinvent joins and other such things.

We have to fight a contention between safety and capabilities, and capabilities historically always win. As such, we introduce two concepts.

## Three levels of reach

| level | what the box gets | who checks it | when it's checked | cost is known |
| --- | --- | --- | --- | --- |
| Access patterns | by_id, by_index, and append, generated functions with no SQL at all | The checker | Before deployment | Exactly |
| Manifest query iterators | A fixed, parameterized query written in the manifest | A human, helped by the checker | Before deployment | Bounded by the plan the checker inspects |
| Direct SQL | Any query, built at runtime | The host, for every query | At runtime | Bounded by budgets, not known ahead |

Each level up gives the box more power and asks more of someone. Products should start at the bottom and only climb when they have to, and the manifest makes the climb visible, since each level is a different kind of strategy.

## Manifest query iterators

Here, we put parameterized SQL directly into the manifest to provide paginated query results, so the box can read based on typed parameters. This forces the human to audit the safety and understand the query put into the manifest, but it maximizes performance and capabilities. This burden may defeat many of the points of the design, but we want it available as an escape hatch.

```json
{
	"data": {
		"sqlite3": {
			"open_jobs_with_customers": {
				"schema": "jobs4.schema",
				"database": "tenant_{!tenant}",
				"pattern": "query",
				"sql": "SELECT j.id, j.title, j.starts_at, c.name AS customer FROM jobs j JOIN customers c ON c.id = j.customer_id WHERE j.status = :status AND j.assigned_to = :me ORDER BY j.starts_at, j.id",
				"params": {
					"status": { "type": "string", "enum": ["open", "scheduled"] },
					"me": "{!user_id}"
				},
				"result": "json:JobWithCustomer",
				"limit": 50
			}
		}
	}
}
```

The rules that keep an iterator honest:

- **Read only.** An iterator is a single SELECT. Writes still go through access patterns, so they stay in the write set and commit with the request's bundle.
- **Bound, never built.** Parameters are bound by the host, never pasted into the text. A parameter is either typed, so the box supplies it and the host checks it, or a reserved identifier like {!user_id}, so the host supplies it and the box can't.
- **Scoped by the database.** The database is still resolved from reserved identifiers, like tenant_{!tenant}, so no query, however clever, can reach another tenant's file.
- **Paginated by the host.** The host enforces the limit and pages with a cursor built from the query's ORDER BY, so results are stable and a page never costs more than the limit.
- **Checked against the schema.** The checker prepares the query against the pinned .schema at approval time, so a misspelled column or a type that doesn't match the result is refused before it ships. It also reads SQLite's query plan, and reports any full table scan, so the approver sees the cost along with the text.
- **Always reviewed.** A new or changed query is a data change that widens reach, so no approval policy can wave it through, as described in the approvals design.

The generated code is an iterator, which is what the name promises:

```C
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

struct job_with_customer;

// Opens the query with the box's typed parameters; the reserved ones are filled by the host.
int64_t open_jobs_with_customers_open(const char* status, size_t status_len);

// Fills the next row; returns false at the end of the page or the results.
bool open_jobs_with_customers_next(int64_t cursor, struct job_with_customer* out);

// Closes the iterator early; it is closed automatically when the request ends.
void open_jobs_with_customers_close(int64_t cursor);
```

## Direct SQL access

Here is where we take the biggest leap and build a SQL language parser, such that we can enable every box with dynamic queries. This requires us to pre-parse and interpret the scope of every SQL statement a box sends. The entire point is to ensure that each query is well formed and scoped to what the manifest allows.

The manifest declares what a box's dynamic SQL may touch, table by table:

```json
{
	"data": {
		"sqlite3": {
			"reporting": {
				"schema": "jobs4.schema",
				"database": "tenant_{!tenant}",
				"pattern": "sql",
				"tables": {
					"jobs": { "read": ["id", "title", "status", "starts_at", "customer_id", "total_cents"] },
					"customers": { "read": ["id", "name", "postal_code"] }
				},
				"row-limit": 1000,
				"step-budget": 1000000
			}
		}
	}
}
```

For every statement the box sends, the host parses it, and refuses it before it ever runs unless:

- every table and column it reads or writes is listed, with the operation it uses,
- it is a single statement, with no ATTACH, PRAGMA, or anything that changes the connection,
- every function it calls is on the host's allowlist of pure functions,
- and it stays inside the database the strategy resolved, which is already scoped by reserved identifiers.

What passes runs inside the request's own transaction, so writes, when a table allows them, land in the write set like any other write and commit with the request's bundle, rather than taking the transaction away from the host the way box-managed SQL would. A step budget and a row limit cap what one query can cost, so a runaway join is stopped by the host, counted, and reported, instead of stalling the box's isolate.

Tactically, we don't need to write a parser on day one. SQLite already parses every statement when it prepares it, and its authorizer reports every table, column, and operation the statement touches before it runs, so the host can enforce the manifest's rules using SQLite's own parser, with no chance of disagreeing with it about what a statement means. A parser of our own comes later, when we want richer analysis, like rewriting queries to add row filters, or estimating cost before a query is ever prepared.

Direct SQL keeps the rule from the data design: a box that sends dynamic SQL is solo, since its reads can't be summarized into a signature ahead of time, and every query is inspected as it runs.

## Choosing a level

- **Start with access patterns.** Most reads are by id or by index, and most writes are a row at a time.
- **Reach for an iterator when you need a join or a report** that you can write down once. The cost is a human reading one query.
- **Reach for direct SQL only when queries truly can't be known ahead,** like a reporting screen where people build their own filters. The cost is solo isolates, runtime checks, and budgets that might say no.

## The invariants

- **Every query stays inside its database.** Databases are resolved from reserved identifiers, and nothing can attach another.
- **Parameters are bound, never pasted.** Typed parameters come from the box, and reserved ones from the host.
- **Iterators are reviewed by a person.** No policy can approve a new or changed query.
- **Direct SQL only touches what the manifest lists.** Tables, columns, operations, and functions are all checked before a statement runs.
- **Writes stay in the write set.** Whatever level a write comes from, it commits with the request's bundle, or not at all if the request fails.
- **Every query has a ceiling.** Limits, row caps, and step budgets bound what any one query can cost.
