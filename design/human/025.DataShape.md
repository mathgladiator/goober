# Shape of Data

All data has to have some invariants, since we want this system to exist on either a single machine or a flexible cluster where you can just add capacity. As such, we have a shape of data to consider.

The trick of this whole document is that the box doesn't get a vote. The box asks for "the user," gets a row, maybe writes a row, and goes back to sleep. Everything that makes data hard in production (migrations, replication, caching, ordering, durability) is something the box should never have to think about, because the manifest already told the host everything it needs to know. A manifest declares every strategy a box can touch, the scope of each one, and whether it reads or writes. That means the platform knows, precisely and ahead of time, who depends on what. Most operational pain comes from not knowing that, and from humans guessing.

## First, structured data that can version and live migrate

Structured data must be versionable and provide live migration capabilities. The shape that makes this work is expand and contract: every change happens in two steps, so two versions of the schema can coexist while code is rolling over. You add the new column, backfill it, move the readers and writers, and only then drop the old one.

| option | why we would use it |
| --- | --- |
| SQLite | The tactical start. It is a file, it is everywhere, and agents have read more SQLite than any human ever will. Schema changes are cheap because each database is small. |
| PostgreSQL | When a single database must be big and shared. Transactional DDL and logical replication give us a path to migrate without stopping the world. |
| MySQL with gh-ost or pt-online-schema-change | Proven at scale for online schema changes on huge tables, using a shadow table that catches up and then swaps. |
| CockroachDB and other distributed SQL | Online schema changes built in, following the F1 lineage, for when one region is not enough. |
| FoundationDB with the Record Layer | Ordered keys with strict transactions underneath, schema evolution on top, and a reputation for testing that we should be jealous of. |

The invariants that make the magic happen:

- **A manifest pins exactly one schema version.** Every box declares the version it was built against, so the host can count the readers and writers of each version at any moment.
- **Contract only happens when nobody is left.** The host can drop an old column when no deployed manifest references the old version, which turns "is it safe to migrate?" from a guess into a query.
- **Migrations are expand-only until proven otherwise.** A migration that removes or changes something in place is refused until the expand half has fully landed.

## Second, data that embeds in a machine, packs up, and goes away

We need a data structure that can be embedded in a local machine, packed up, and moved away. SQLite + Litestream is one option, and the idea is that the unit of data is a file you can carry: a tenant is a database, and a database is a file.

| option | why we would use it |
| --- | --- |
| SQLite + Litestream | Streams the WAL to object storage continuously, so a database can be restored anywhere at a point in time. This is the backbone of a database per tenant. |
| LiteFS | Replicates SQLite across machines with a single primary held by a lease, for when reads need to be close to users in many places. |
| rqlite or dqlite | SQLite under Raft, for a small amount of data that must survive losing a machine without an external store. |
| DuckDB with Parquet on object storage | Embedded columnar analytics, for when a box needs to answer questions across a lot of rows without a warehouse. |
| RocksDB or LMDB | Embedded key/value stores for when the data is keys and values and a SQL engine would just get in the way. |

The invariants that make the magic happen:

- **One writer per file.** A database has exactly one place it can be written at a time, held by a lease that the host owns. There are no split brains, because there is no second brain.
- **The file is the unit of placement.** Moving a tenant means moving a file, adding capacity means spreading files, and deleting a tenant means deleting a file, which makes privacy requests boring in the best way.
- **The blast radius is one file.** A corrupt or runaway database hurts one tenant, not the fleet.
- **Every file can be rebuilt from object storage.** A machine is a cache of files, and losing one is an inconvenience rather than an incident.

## Third, unstructured data that many code versions can operate on

The data is unstructured, and the design can handle various code versions operating on the state at the same time. This is the world of documents, logs, and blobs, where a deploy is never instantaneous and old code and new code will both touch the same state.

| option | why we would use it |
| --- | --- |
| Versioned JSON documents | The simplest thing that works. Each document carries a version in an envelope, and old code ignores what it doesn't understand. |
| Event logs (Kafka, Redpanda, NATS JetStream) | State becomes a fold over an append-only log, so a new version of the code can replay history and arrive at its own view. |
| CRDTs (Automerge, Yjs) | Merges without coordination, for collaborative state where many writers act at once and conflicts must resolve themselves. |
| Object storage with content-addressed blobs | Immutable by name, so a blob can be cached forever and never torn by a concurrent writer. |
| A differential document, in the spirit of Adama | A JSON document changed only by deltas, which gives us history, replication, and subscriptions from the same stream. |

The invariants that make the magic happen:

- **Readers tolerate unknown fields, and writers preserve them.** Old code that reads a new document must not crash, and old code that writes a new document must not drop the fields it didn't understand.
- **Every write is idempotent.** Events and deltas carry identity, so a retry is a no-op rather than a double charge.
- **What has been written is never rewritten.** Logs append, blobs are immutable, and documents change by delta, so a reader never sees half of a change.

## Cache coherency and sequencers

Since the manifest declares every strategy and its scope, the host knows exactly which cached values a write can invalidate. A write through user_by_id with a user_id of 7 touches user_by_id(7) and nothing else, so invalidation is precise rather than a prayer and a short TTL. The box never caches data itself, since the host can do it better with knowledge the box doesn't have.

Cross region replication is where this pays off. Each strategy can name a sequencer, which is the single authority that orders writes for a scope, along with the read consistency the box needs.

```json
{
	"data": {
		"sqlite3": {
			"user_by_id": {
				"schema": "core13.schema",
				"database": "some_database",
				"table": "users",
				"pattern": "by_id",
				"id_is": "{user_id}",
				"read": true,
				"write": true,
				"consistency": {
					"sequencer": "scope",
					"reads": "read-your-writes",
					"staleness-ms": 500
				}
			}
		}
	}
}
```

The sequencer assigns every write a monotonic number within its scope, and replicas apply writes strictly in that order, so every region converges on the same history. When a request writes, the host hands back the sequence number, and it rides along in the hidden context of the caller's session. A later read in any region waits until its replica has caught up to that number, or it gets forwarded to the sequencer. That gives us read-your-writes everywhere, bounded staleness for everybody else, and none of it shows up in the box.

The invariants:

- **One sequencer per scope.** Ordering is total within a scope and does not exist between scopes, which is what lets scopes spread across machines and regions.
- **Invalidation is keyed by resolved scope.** A write invalidates exactly the cache entries of its scope, which is the same key we already use for isolate sharing.
- **Sequence numbers are the consistency token.** A session carries the highest sequence it has seen, and no read may go backwards in time.

## Batched writes and no torn writes

A box never writes to the database directly. Every write during a request lands in a write set held by the host, and reads during the same request see that write set layered on top of the data. When the box responds, the host commits the whole write set atomically and in sequence order, and only then does the response leave. If the box traps, times out, or blows its budget, the write set is thrown away, and nothing happened.

This gives every request all-or-nothing semantics without the box ever saying the word "transaction." It also gives the host an opportunity to batch: write sets from many requests to the same database go into a queue and commit together as one transaction and one fsync, which is exactly how SQLite likes to be fed. The cost is a small amount of latency at the end of a request, and the reward is throughput and the end of torn writes.

The invariants:

- **A request's writes are atomic when the route is atomic.** Either the whole write set commits or none of it does.
- **A response never acknowledges uncommitted data.** The host holds the response until the write set is durable.
- **Writes apply in sequence order.** Batching never reorders writes within a scope.
- **A write function returning true means accepted, not committed.** Commitment happens once, at the end, for the whole request.
- **Side effects on the network ride in the write set.** Calls that change the world are captured as elements of an outbox queue and only leave after the commit, which is the subject of the outbox design.

### How atomic is atomic?

We want to be able to say the writes are atomic, and for the simple patterns we can say it with a straight face. However, how atomic the writes can be depends on the complexity of how things are queried and where they land. A write set against one database file is one transaction, and that is a promise SQLite can keep. A write set that spans two tenant databases, or a database and a service across the network, is a promise that would need a distributed transaction, and we are not going to pretend we have one of those lying around.

So atomicity is a field on the route, true by default, which the checker requires to be turned off when the task is too complex to keep the promise.

```json
{
	"routes": {
		"http": {
			"/import": {
				"post": {
					"name": "bulk_import",
					"response": "json",
					"atomic": false
				}
			}
		}
	}
}
```

With atomic set to false, the host commits writes as they arrive in batches, in sequence order, and a failure part of the way through leaves the earlier batches in place. That is a legitimate choice for a bulk import that can be resumed, but it has to be a choice a human can see, rather than an accident nobody noticed.

The things that make a route too complex to be atomic:

| condition | why it breaks atomicity |
| --- | --- |
| Writes that span more than one database | Each file commits on its own, and there is no transaction across files. |
| Writes that span more than one sequencer | Each sequencer orders its own scope, and nothing orders across them. |
| A write set larger than the host's batch limit | The host refuses to hold an unbounded write set in memory, so it must commit in pieces. |
| SQL in the box that manages its own transactions | The box has taken the transaction away from the host. |
| A network call that must happen immediately | The world has already changed before the commit, and the commit can still fail. |

### Where torn writes are possible

At core, the manifest checker can say where torn writes are possible, because every one of those conditions is visible in the manifest. The checker produces a report per route: whether the route is atomic, and if it is not, which condition makes it so and which strategies and services are involved. A route marked atomic that hits one of the conditions is refused with an explanation for the agent. A route marked as not atomic gets listed, so a human reviewing the box can see exactly which routes can leave the data half done and decide whether that is acceptable. A torn write is still possible in this system, but it is never a surprise.

## Can a box even behave well?

Since the manifest describes everything a route can touch, the checker can compute a worst case for a request before anything is deployed. A by_id read is one row. A by_index read is at most its limit. External calls are capped by their budgets. Writes are capped by the write set. Put those together with the timeout and the sequencer placement, and the checker can say whether a route can possibly meet its promises.

Some examples of what the checker can refuse or flag, with an explanation for the agent:

- A route whose worst-case reads multiplied by the per-row cost can't fit inside timeout-ms.
- A write whose sequencer lives in another region while the route's timeout is shorter than a round trip.
- A "shared" lifecycle alongside SQL in the box, which must be solo.
- A by_index strategy whose index doesn't exist in the schema.
- A route that writes through a strategy with no sequencer while the box is deployed to more than one region.
- A route marked atomic whose writes span more than one database or sequencer.

This is the difference between hoping a box behaves and knowing whether it can. The box may still be bad on the inside, but the manifest tells us the shape of the worst it can do.

## What the box never thinks about

Migrations, replication, placement, caching, invalidation, ordering, batching, atomicity, durability, and retries all live in the host, driven by the manifest. The box thinks about converting a request into a response. That is a short list for a reason: every item that moves from the box into the host is an item that is written once, reviewed by a human once, and then works for every box, forever. That is how we get high quality operations and reliability out of boxes that we don't trust to have either.
