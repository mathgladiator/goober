# The Approval Queue

At core, every logical box (/box/$box_name) has a series of versions (/box/$box_name/$version), and for each box we store:

* which version is primary,
* which version is a shadow, and
* which version is being A/B tested against it, such that the primary is A and the secondary is B.

A version that has never received traffic can be deleted as a bad push, since it has no liability.

A single box approval is ultimately a diff on the manifest that shows what is changing, and it starts with a full human review. Obviously, this will not scale. Each box can opt into policies about what matters, so each manifest has a policy section with simple identifiers for the kinds of change that don't need a human for approval.

```json
{
	"policy": ["new_routes_ok"]
}
```

Here, new_routes_ok means a box change will not be flagged if the only thing introduced is a new route. This helps balance what the system can automatically ship, and an important rule is that no policy change can be automated: the system will see a new version of a box with a changed policy, and it will put it through an approval gate for human review. The manifest also has a deployment-validation property:

```json
{
	"deployment": {
		"mode": "go"
	}
}
```

| mode | meaning |
| --- | --- |
| go | Just deploy the thing once it is approved. |
| slow | Launch with an A/B test over a period of time defined by "period-ms", where the only thing tested is box health. |
| shadow | Launch as a full shadow over a period of time defined by "period-ms", where the only thing tested is box health, all side effects are thrown away, and there is no network access. |

The first tactical goal is to sort out how to safely deploy the system, and from there, the richness of validation will come from a rule engine that AI can adjust as needed, for humans to approve. The host has a lot of potential to automate the quality of a system, through shadow traffic and side-effect testing, or even A/B testing with user metrics, and this will evolve over time. For now, we focus on simplicity.

## The registry of boxes and versions

| path | holds |
| --- | --- |
| /box/$box_name | The logical box: its primary, shadow, and secondary versions, and its history. |
| /box/$box_name/$version | One immutable version, named by the hash of its contents, with its manifest, its approval record, and its traffic history. |
| /config/$config_name | The same, for configs, which are manifests with no box. |
| /config/$config_name/$version | One immutable version of a config. |

A box has at most one primary, one shadow, and one secondary at a time. Every other version is either waiting for approval, retired, or never used. A version that has never received traffic, including shadow traffic, can be deleted outright, since nothing it did could have mattered. A version that has received traffic is kept, because it is part of the record of what the system did and may need to be brought back.

## What an approval reads

An approval is a diff of the manifest against the current primary, written as changes a person can read, not as lines of JSON. The checker groups every change into a kind, and the kinds are what policies refer to:

| kind of change | example |
| --- | --- |
| interior | The WASM module changed, and the manifest didn't. |
| new route | A route that didn't exist before. |
| removed route | A route that existed before and is gone. |
| route change | A route's types, requirements, priority, share, or behavior changed. |
| static content | A static entry or template changed. |
| data | A strategy was added, removed, or widened, or a strategy gained write. |
| network | An external service, method, credential, or effect was added or changed. |
| identity | A grantable or revocable option changed. |
| domains | The manifest applies to different domains. |
| headers | A header property changed, tightened or loosened. |
| dependencies | A pin moved, a capability's provider or credentials changed, or an OpenAPI service was redirected to an adapter box, as described in the stability design. |
| policy | The policy list changed. |

Each change also carries the checker's reports from the rest of the design: worst cases, torn writes, type compatibility and the boxes it affects, shadowed routes, loosened security headers, and the rogue content checks for static content. The approver reads the change, the reports, and nothing else, which is the whole point of asking humans to review the perimeter rather than the code.

## Policies

A policy is an identifier in the manifest that says a kind of change doesn't need a human. When every change in a new version is covered by the manifest's policies, the version is approved automatically and recorded as approved by policy. When even one change isn't covered, the whole version waits for a person.

| policy | lets this through without a human |
| --- | --- |
| interior_ok | The WASM module changed, and nothing in the manifest did. |
| new_routes_ok | Only new routes were added, and none of them takes a URL from another route. |
| static_ok | Only static content and templates changed, and the rogue content checks are clean. |
| headers_tighten_ok | Header properties only became stricter. |
| dependencies_ok | Only pinned dependencies moved, as described in the stability design. |

Some kinds of change can never be covered by a policy, because they change what a box is allowed to do rather than how it does it:

- **Policy changes.** A change to the policy list itself always needs a human, as described above.
- **More reach.** A new data strategy, a strategy that gains write, a new external service or credential, a new domain, or a new caller of an internal route.
- **More power.** A new grantable or revocable option, a route that becomes public, or an MCP tool that can grant roles.
- **Less safety.** An "immediate" effect, a route that becomes non-atomic, or a loosened security header.
- **Taking over.** A new priority or share that takes URLs from another route.

## Deployment modes

Once a version is approved, by a person or by policy, its deployment mode decides how it goes live:

```json
{
	"deployment": {
		"mode": "slow",
		"period-ms": 86400000
	}
}
```

| mode | what the host does |
| --- | --- |
| go | Makes the version primary immediately, and keeps the previous primary running until the new one has drained in. |
| slow | Makes the version the secondary, ramps its share up over period-ms, and promotes it to primary at the end, as long as it stays healthy. |
| shadow | Makes the version the shadow for period-ms, with all side effects thrown away and no network access, then promotes it to primary if it stayed healthy. |

Box health is the same everywhere: the version's error rate, its p99 latency, its traps and blown budgets, and its cost per request, each compared with the primary over the same requests. A version that falls past the host's thresholds at any point is rolled back automatically, and the rollback is recorded alongside the approval, so the next person who looks sees both.

Deployment modes are about health only. Deeper experiments, like comparing the behavior of two versions with a report or splitting traffic to measure user metrics, are described in the deployments design, and remain available on top of these modes.

## The road ahead

Policies and modes are deliberately simple identifiers, since the first goal is to deploy safely. Over time, the checks behind them become a rule engine, with richer validation drawn from shadow traffic, side-effect testing, and user metrics, and an agent can propose changes to those rules, which a human approves like any other change to the system's shape.

## The invariants

- **Every version is approved.** By a person, or by policies that cover every change in it, and the record says which.
- **No policy change is ever automated.** Changing what doesn't need a human always needs a human.
- **Reach, power, and safety can't be waved through.** Those kinds of change always go to a person.
- **Unused versions can be deleted, and used versions are kept.** Liability starts with the first request.
- **Unhealthy versions roll back on their own.** Every mode watches health and retreats without waiting for a person.
