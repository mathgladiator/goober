# Stability: Controlling the Entire World

Ideally, every API provider would be stable, or be a business that could stand the test of time. We bias towards OpenAPI, since that gives us the tooling to talk to many services, but those services can change and break a contract. Or, worse, the service can simply disappear, for a myriad of reasons. A long-term goal is to provide stable boundaries, such that we can maintain a binary for decades, so we do two things.

First, super-critical services have a well-defined, long-term API provided by the host, such that the API can be entirely configured by the manifest. For example, we leverage AWS for email, but the contract isn't "Amazon send email"; it is "send email." This allows the manifest to configure the provider along with its keys, and this can all be done by operators. We expect these contracts to be long-lived enough to minimize host deployments, but we can add new providers easily, and eliminate vendors that go bust as well.

Second, for services that are OpenAPI, every service route in a manifest can be redirected from an OpenAPI service to an internal service via a manifest change, without a box change. This allows a new box to be stood up that implements the dead service's design and adapts it to a new service. Ideally, we want to avoid this and update the box, but if you look at a timeline measured in decades, most companies don't survive for 30 years. Contracts can. In the worst case, the existing box can return a sane error code that drives a metric for support engineering to dive into.

## Why this matters

One of the goals is a system where a product, once approved, never changes its capabilities or its user interface, and only needs maintenance when something outside it changes. A box already owns only its business logic, so most of what rots in ordinary software lives in the host or out in the world instead. Stability is about the two halves of that: making sure the host can't change a product underneath it, and making sure the world changing doesn't force the product's code to change either.

## Host capabilities: stable contracts, swappable providers

A host capability is a contract the host defines and promises to keep for a very long time, like send-email@1. A box codes against the contract, and the manifest names which provider fulfills it, along with the keys the provider needs.

```json
{
	"external": {
		"mail_out": {
			"capability": "send-email@1",
			"provider": "amazon-ses",
			"credentials": "keys/tenant/{tenant}/ses",
			"methods": {
				"send": {
					"require": {
						"body.from": "receipts@example.com"
					},
					"effect": "outbox"
				}
			}
		}
	}
}
```

The capability decides the box's generated code, so it never changes for the life of the contract. The provider and the credentials decide where the work actually goes, so an operator can move a tenant from Amazon SES to another mail provider, or to the platform's own Stalwart, by changing only those two fields. The box's module doesn't change, its generated code doesn't change, and its behavior doesn't change, which is exactly the kind of change the approvals design lets through with dependencies_ok.

Capabilities are reserved for services so common and so critical that nearly every product needs them, and whose shape is well understood: sending email, sending a text message, storing an object. Each capability is a small, versioned contract written as an OpenAPI document by the host, and each provider is host code that adapts one vendor to it. Adding a provider is a host change; retiring a vendor that went bust is removing one.

## Payments, and where risk should live

Payments are an opportunity, but they are also where stability and risk are hardest to balance, since payment systems seem to come and go, and payment information is the most dangerous data a product can touch. A key goal is to encourage trusted partners to insert money services, rather than for the platform to become one. That isn't needed now, and it isn't excluded forever.

The philosophy is about where risk goes. Ideally, payments are a hook on the client side: the person's browser talks directly to a trusted payment partner, the partner handles the card, and the box only ever sees a token that stands for the payment. The platform never holds payment information beyond tokens, so a breach of a box, a host, or a backup can't leak a card number, and the partner carries the regulatory weight it is built to carry.

From there, a payment can be a capability, if it becomes so common and well understood that a long-term contract makes sense, or simply an OpenAPI service, called from the outbox with an idempotency key so that a charge is made once. Either way, the same rules apply: the box sees tokens, not cards, and when a payment partner disappears, the contract or the adapter box absorbs the change, so the products that took payments keep their shape.

## OpenAPI services: redirect to an adapter box

Most services aren't capabilities. They are specific vendors, described by their own OpenAPI documents, which the box pins as part of its version. When one of them breaks its contract or disappears, the manifest can redirect it to an internal service instead, without changing the box:

```json
{
	"external": {
		"forecasts": {
			"openapi": "weather.v2.openapi.json",
			"box": "weather-adapter"
		}
	}
}
```

The box keeps calling forecasts exactly as before, through the same generated code, with the same pinned OpenAPI document. The host sends the calls to the weather-adapter box instead of the vendor, as internal calls, as described in the internal messaging design. The adapter box implements the dead service's design, and adapts it to whatever replaced it. It is an ordinary box, with its own manifest, approval, and budgets, so the adaptation is code a person can review once and every box that used the old service can share.

Updating the box to the new service directly is still the better path when someone is around to do it. Redirection is for the timeline measured in decades, when the service is gone and nobody remembers how the box worked, but the contract it was written against is still perfectly good.

When neither is possible, the box still behaves: its calls to the dead service fail, its routes return a sane error code, and the failure shows up in the operating panel as a metric for support engineering to dive into, rather than as a mystery.

## Everything else outside the box is pinned

A box's behavior also depends on host code that isn't a service at all: the boundary it was built against, the code generator that produced its bindings, the renderers that turn its responses into pages, and the script the host serves to browsers. Every one of those is pinned by version in the manifest, so the host can never change them out from under it.

```json
{
	"pins": {
		"abi": "goober-abi@1",
		"generator": "c@1",
		"markdown": "commonmark@1",
		"templates": "mustache@1",
		"layout": "default@3",
		"helpers": "client@2"
	}
}
```

| pin | what it fixes |
| --- | --- |
| abi | The boundary from the boundary design: layouts, host functions, and their meanings. |
| generator | The code generator for the box's language, from the languages design. |
| markdown | The markdown renderer, so the same markdown always becomes the same HTML. |
| templates | The template engine, so the same template and values always produce the same page. |
| layout | The default layout and stylesheet that a box with no design of its own falls back to. |
| helpers | The client script the host serves for calling routes and following subscriptions. |

Host capabilities are pinned the same way, by the version in their name, like send-email@1, and OpenAPI documents are pinned by being part of the version, since they are named by the version's hash.

A pin names a version that never changes. The host may fix a bug in commonmark@1 only if the fix doesn't change any output a deployed box could see; anything else is commonmark@2, and only boxes that pin commonmark@2 get it. Boxes that leave out a pin get the newest version at the time they are deployed, and the checker writes that version into the deployed manifest, so a deployed box always has every pin filled in, whether its author thought about it or not.

## The host keeps every pinned version alive

A pin is only a promise if the host keeps it. The host carries every version of every pinned piece, and every capability contract, that any deployed manifest still uses, and it can't drop a version while one remains. Retiring an old version of the markdown renderer, or an old capability contract, happens the same way as retiring an old box: once nothing deployed uses it, and not before.

## Dependency-only updates

Some outside changes do need a new version of the box's manifest, but never of its code: switching a capability's provider, redirecting an OpenAPI service to an adapter box, or moving a pin. This is the one kind of maintenance the goal allows, so the system makes it cheap and provably safe.

A dependency-only update is a new version that differs from the current one only in pins, capability providers and their credentials, and where external services point. The checker proves it: the WASM module has the same hash, every other field of the manifest is identical, and every static entry and template is byte for byte the same. When that proof holds, the change is of the dependencies kind from the approvals design, and a box whose policy includes dependencies_ok ships it without a human. If anything else changed, even a single character in a template, it isn't a dependency-only update, and it goes through approval like any other change.

## Proving the host didn't change anything

Pins say what the host promises; replay checks that it kept the promise. When a version goes live, the host records a small corpus of representative requests and their responses for each route, with personal data removed in the same way the deployments design's reports remove it. Before any new release of the host goes out, it replays every deployed box's corpus against the new host, using each box's own pins, and compares the results. A difference means the new host changed a product, and the release stops until the difference is understood. A thousand products become the host's test suite, which is how the host can change every week while the products never do.

## What stability doesn't cover

- **Configs.** Header properties, rewrites, and other settings in configs belong to whoever runs the domain, as described in the configs design. Changing them is operations, not a change to a product.
- **The browser.** A pinned page is the same HTML forever, but browsers change. Pinning guarantees that the product didn't change, not that the world didn't.
- **Data.** A box's data changes, of course; stability is about what the box can do, not what it holds.
- **Security.** When a pinned version has a real security flaw, the host fixes it in place, even if output changes, and the fix is recorded and announced. Being safe comes before being identical.

## The invariants

- **Boxes code against contracts, not vendors.** Capabilities are host contracts with swappable providers, and OpenAPI services can be redirected to adapter boxes.
- **Swapping a provider or redirecting a service never changes a box's code.** Both are manifest changes that the checker can prove are dependency-only.
- **Every deployed box has every pin filled in.** Leaving a pin out means "the newest one at deploy time," written down at deploy time.
- **A pinned version never changes what a box can see.** Anything that would is a new version.
- **The host keeps every version that anything still pins.** Old versions and contracts retire only when nothing uses them.
- **Every host release is replayed against every product first.** A difference stops the release.
- **When the world breaks, the box fails sanely.** Calls to a dead service become clear errors and metrics, never mysteries.
- **Security fixes are the only exception.** They change pinned versions in place, and they are always recorded.
