# Handling Mail is fun

A route can also be email to the system. We will use a service like Stalwart to convert SMTP to HTTP, so describing a mail route looks almost exactly like describing an HTTP route. Mail is one of the oldest protocols still standing, it is a swamp of edge cases, and we want no part of the swamp inside a box.

## Converting mail into routes

Stalwart handles everything about SMTP that is cursed: TLS, queueing, MIME parsing, and checking SPF, DKIM, and DMARC. Stalwart's MTA hooks let it ask an HTTP endpoint what to do with a message while the SMTP conversation is still open, and that endpoint is the host. The host matches the recipient address against the manifest, turns the message into a typed request, and wakes the box.

```json
{
	"routes": {
		"mail": {
			"support@example.com": {
				"receive": {
					"name": "support_inbox",
					"max-bytes": 10485760,
					"attachments": 5
				}
			},
			"reply+{ticket : token}@example.com": {
				"receive": {
					"name": "ticket_reply",
					"max-bytes": 1048576,
					"attachments": 0
				}
			}
		}
	}
}
```

The pattern is routes.mail.$address.receive, mirroring protocol, then path, then verb. An address can also leave off its domain, like support@, to match that local part on every mail-enabled domain in the registry, with the tenant resolved from the recipient's domain, as described in the domains design. The address plays the role of the path, and parts of it can be parameters, just like an HTTP path. The box gets a generated structure with what it needs, and nothing it didn't ask for.

```C
#include <stddef.h>
#include <stdint.h>

struct mail_message {
	const char* from;
	size_t from_len;
	const char* subject;
	size_t subject_len;
	const char* text;
	size_t text_len;
	int32_t attachment_count; // attachments live in object storage, by handle
};

const struct mail_message* support_inbox_get_message();
void support_inbox_accept();
void support_inbox_reject();
void support_inbox_defer();
```

## What makes this special

**The box decides during the SMTP conversation.** Because the hook happens before Stalwart says yes, the box's answer becomes the SMTP answer. Accept becomes a 250, reject becomes a 550, and defer becomes a 451 that tells the sender to try again later. A box that doesn't want a message refuses it at the door, rather than accepting it and then sending a bounce to an address that was probably forged.

**The sender is a verified claim, not a string.** Stalwart has already checked DKIM, SPF, and DMARC alignment by the time the host sees the message, so a sender that passes becomes a principal in the context, exactly like a verified token on an HTTP request. A sender that fails is just an unverified string, and a strategy scoped by sender can't resolve from it. Anyone can type any From line, but only an aligned sender gets a scope.

**An email address can be a capability.** The reply+{ticket : token} address above is the interesting one. When a box sends mail about ticket 42, the host mints a reply address with a signed token that names ticket 42 and the recipient. When a reply comes back, the host verifies the signature, and the token's claims become context. Nobody can guess their way into another ticket, because the address itself is the permission, and a forged token never wakes the box.

**Mail loops die at the host.** Auto-replies, out-of-office messages, and bounces are marked by the Auto-Submitted header and friends, and the host drops them for any route that hasn't opted in. Two boxes that auto-reply to each other is a classic way to burn a budget overnight, and the host simply doesn't let the conversation start.

**Attachments never enter the box by default.** They land in object storage, scanned and counted, and the box gets handles and sizes. A box that truly needs the bytes asks for them by handle, within limits, which keeps a 10 MB PDF from becoming a 10 MB copy into every isolate that glances at the message.

## Sending mail

Outbound mail is an external service like any other, and since sending is effectful, it rides the outbox. The box fills in a structure with a subject, text, and maybe a reply token, and the host builds the MIME, signs it with DKIM, and hands it to Stalwart after the write set commits. Nobody writes MIME in a box, and nobody gets a receipt for an order that doesn't exist.

Not every service works with OpenAPI, so as part of sending mail, there will be special providers that the platform supplies tactically. Sending email is one of the host's capabilities from the stability design: the contract isn't "Amazon send email," it is send-email@1, defined by the host, and Amazon SES is one provider for it. SES wants every request signed with AWS Signature Version 4 and comes with its own SDK conventions, which an OpenAPI document can't fully describe, so the platform adapts SES internally to the send-email contract. From the box's side, sending mail looks exactly like any other external service, with the same require blocks, budgets, outbox, and audit.

```json
{
	"external": {
		"mail_out": {
			"capability": "send-email@1",
			"provider": "amazon-ses",
			"credentials": "keys/tenant/{tenant}/ses",
			"methods": {
				"send": {
					"require": {
						"body.from": "receipts@example.com"
					},
					"effect": "outbox"
				}
			}
		}
	}
}
```

The capability field replaces the openapi field, and it names a contract the host keeps for a very long time, while the provider field names the adapter built into the host that fulfills it. An operator can switch a tenant from SES to another provider by changing the provider and its credentials, without changing the box, as described in the stability design. The platform will do this only for trusted vendors, since an adapter is host code that holds credentials and speaks to the outside world, and every line of it is part of what a human has to trust. We will expand this over time to include things like Thrift, gRPC, or other RPC transports. For now, we bias towards OpenAPI, plus special add-ons for trusted vendors.

Credentials for mail come in two scopes. The platform has a full system mailer of its own, named keys/system/mailer, which the identity service uses for sign-in codes and account notices, so that signing in never depends on any one business's setup. However, it is also reasonable for each tenant to have its own credentials in a mailer, since a business may have its own AWS account with SES already set up, its own sending domain, and its own reputation to protect. That is what keys/tenant/{tenant}/ses above means: the tenant comes from the secure context, so Bob's receipts go out through Bob's AWS account, and Anne's go out through Anne's, without either box ever seeing a credential.

## The invariants

- **The box never speaks SMTP or MIME.** Stalwart and the host own the protocol, and the box sees structures.
- **Only aligned senders become principals.** Unverified senders can't resolve a scope.
- **Reply addresses are signed capabilities.** A forged or tampered token never reaches the box.
- **The box's answer is the SMTP answer.** Rejections happen at the door, so we never generate backscatter.
- **Automatic mail is dropped unless a route opts in.** Loops end before they begin.
- **Outbound mail only leaves after a commit.** It rides the outbox like every other side effect.
- **Special providers are host code for trusted vendors only.** They present an OpenAPI spec to the manifest, so a box can't tell an adapter from a plain service.
