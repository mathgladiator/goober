# Source: Keeping the Code in the Machine

> Drafted by Claude on 2026-10-27 at the human's request, for the human to edit and own.
> What the host builds of it is recorded in `design/machine/020.Source.md`.

An agent like Grok can write a box, but it has no laptop. It can't clone a repository, run a
compiler, or keep files between conversations. Today, whatever it writes lives in the chat, and
the only thing that reaches the host is the finished artifact. The source is lost the moment the
conversation ends, and the next conversation starts from nothing.

So goober keeps the source itself. The host holds a tiny source control system, reachable over
the same operator MCP an agent already uses to deploy, and the loop becomes:

1. **check out** a project,
2. **change** some files,
3. **build** it on the host,
4. **deploy** it,

and the source stays in the machine, next to what it built. The next conversation, or a different
agent, checks out the same project and picks up where the last one stopped.

This is deliberately not git. Git is built for many people on many machines merging long-lived
branches. This is built for one owner and their agents on one machine, and for a model that
should spend its attention on the code, not on version control.

## Projects and revisions

A project is a name, like `ranches` or `beef-share-site`, and a straight line of revisions: 1, 2,
3, and so on. Each revision is a full snapshot of every file, with a message, who made it (which
operator token, so which agent), and when. There are no branches. Revisions are never rewritten
or deleted. Going back is a new revision that restores an old one.

Files are text or binary, stored once by content hash, so a revision that changes one file
costs one file.

## Changing files without stepping on each other

A commit says which revision it started from and lists its changes: write this file, delete that
one. If nobody else has committed since, it simply becomes the next revision.

If someone has, and none of the files they touched are files this commit touches, the host
applies the commit on top anyway; that is the common case of two agents working on different parts.
If they overlap, the commit is refused and lists the files that conflict. The agent reads them
again and retries. Nothing is ever merged inside a file.

## What a project builds

A file at the project's root, `goober.project.json`, says what the project is:

```json
{
  "boxes": ["."],
  "schemas": ["ranches1.schema.json"],
  "sites": [{ "dir": "site", "tenant": "playground" }]
}
```

- **boxes**: directories, each with a `manifest.json` and either Rust (`Cargo.toml`), WebAssembly
  text (`box.wat`), or a prebuilt `box.wasm`.
- **schemas**: database schemas to store before the boxes that use them.
- **sites**: directories pushed as a tenant's static content.

Because this lives in the project, the instructions for deploying travel with the code.

## Building on the host

The host builds, because the agent can't. A build runs in a sandbox: no network, nothing visible
but the project's files and the toolchain, its own temporary directory, and a time limit. Rust
crates come from a vendored set the host provides, so a build can't pull new code from the
internet. The agent gets the outcome and the end of the log, compiler errors included, and fixes
the code the same way a person would.

A build is tied to a revision. Building the same revision twice gives back the first result.

## Deploying

Deploying a revision builds it if needed, stores its schemas, uploads each box as a new version,
and pushes each site's files. The host remembers which revision is live, so "what's running?" always
has an answer, and rolling back is deploying an older revision.

## The tools

| tool | does |
| --- | --- |
| `source_list` | the projects, each with its head revision and what is deployed |
| `source_create` | a new project, empty or from a template (a Rust box, a site) |
| `source_checkout` | every file at a revision: small text files with their contents, the rest listed |
| `source_read` | chosen files' contents |
| `source_commit` | a set of changes on top of a revision |
| `source_log` | the revisions, newest first, with the files each changed |
| `source_diff` | what changed between two revisions, as a unified diff |
| `source_revert` | a new revision with an old revision's files |
| `source_build` | builds a revision in the sandbox |
| `source_deploy` | builds and deploys a revision |
| `source_job` | how a build or deploy is going, and its log |

A person can do the same from a terminal (`goober.py source ...`), so a project started by an agent
can be pulled down, edited in a real editor, and pushed back.

## Where it lives

Source lives in the host's storage, so it is in the nightly backup and the increments like
everything else (663). Nothing is published anywhere unless the operator exports it.

## Not in scope, yet

- Branches, merges inside a file, and pull requests.
- Building anything but Rust, WAT, and prebuilt WebAssembly, and Rust crates beyond the vendored set.
- Mirroring to GitHub. `goober.py source pull` writing a revision to a directory is the bridge for now.
