# The User Interface and Helpers

The system design is predicated on an API designed around HTTP, currently, such that the natural targets are web browsers, mobile devices, and desktop apps. This is all normal infrastructure table stakes, but we also want a sense of self-hosting the user interface, since we will already provide a way for the platform to offer OAuth-based identity. As such, any box can simply emit HTML and JavaScript, and we then want to supercharge that with content negotiation, so we also support markdown and templates. We want to consider supporting the following:

* Markdown as a first-class citizen, such that a box can simply emit markdown.
* Templates that wrap content and leverage front matter, such that markdown can convert to HTML in a reasonable way.
* Static content as a special, hyper-optimized box.
* Static proxies to S3 for attachments, like images, and other object storage.

In terms of the design, we add static resources that are embedded directly in the manifest, as a plain string or a base64-encoded string, since AI works well at exactly that level. This way, we leverage the manifest's security system to protect secure content and documents at full privacy fidelity, and we also enable ways of attaching objects to a box. Not only that, but enabling templates is how we can style the OAuth login. This places additional technical requirements on the host, such as:

* Markdown to HTML.
* Mustache templates, for JSON or front matter plus content, to HTML.
* An object storage system (start with disk, plan around S3 limits).

## One route, many audiences

The most useful trick here is content negotiation. A route that responds with a typed JSON value can also name a template, and the host decides what to send based on what the caller accepts. A browser asking for text/html gets the JSON rendered through the template, while an app, another box, or an agent asking for application/json gets the JSON itself. The box writes one route, fills in one structure, and never knows which one it was.

```json
{
	"types": "jobs.openapi.json",
	"templates": {
		"job": "<article><h1>Job {{id}}</h1><p>{{quantity}} items</p></article>"
	},
	"routes": {
		"http": {
			"/jobs/{job_id : int64}": {
				"get": {
					"name": "get_job",
					"response": "json:Job",
					"template": "job",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]]
				}
			},
			"/about": {
				"get": {
					"name": "about",
					"response": "markdown",
					"public": true
				}
			}
		}
	}
}
```

| response | what the box emits | what a browser gets | what an API caller gets |
| --- | --- | --- | --- |
| json with a template | A typed structure | HTML from the template | The JSON |
| markdown | Markdown with optional front matter | HTML from the template the front matter names, or the default layout | The markdown |
| html | HTML and JavaScript, as written | The HTML | The HTML |
| text | Plain text | Plain text | Plain text |

Raw html is allowed, since sometimes a box really does need to hand-build a page, but it is the least preferred option. JSON with a template keeps the box out of the business of writing markup, which is the same reason the box doesn't write JSON or MIME by hand.

## Markdown

Markdown is how a box says "here is a page" without caring what a page looks like. The host renders it with CommonMark, and front matter at the top selects the template and fills in things like the title.

```markdown
---
title: About Bob's Plumbing
template: page
---

# We fix things

Family owned since 1987, serving the whole valley.
```

Raw HTML inside markdown is turned off by default, since markdown often carries text that came from a person, like a job note or a customer's message, and that text must never become a script. A box that truly needs HTML uses the html response instead, which is visible in the manifest.

## Templates

Templates are Mustache, because Mustache is logic-less: a template can loop over a list and fill in values, but it can't compute, call anything, or reach anything the box didn't hand it. That keeps templates in the same category as types, which is to say auditable artifacts rather than code. Templates are embedded in the manifest by name, as plain strings, they deploy atomically with the box, and changing one goes through the approval queue like any other change to the box's shape.

Every value is HTML-escaped by default. The only unescaped slot is the rendered body of markdown, which the host has already rendered safely, so a template can't be talked into injecting a raw string a person typed. Templates can nest, so a page template wraps content, and a layout template wraps every page.

## Static content

Static content is a special, hyper-optimized case: there is no WASM at all, just content the host serves directly. Static content is embedded directly in the manifest, as a plain string for text or a base64-encoded string for binary files, because AI works well at exactly that level: an agent can write a page, a stylesheet, or a small image straight into the manifest it is already editing, with no separate files to keep in sync.

```json
{
	"domains": ["bobsplumbing.com"],
	"templates": {
		"page": "<!doctype html><html><head><title>{{title}}</title><link rel=\"stylesheet\" href=\"/site.css\"></head><body>{{{body}}}</body></html>"
	},
	"static": {
		"/": {
			"content-type": "text/markdown",
			"content": "---\ntitle: Bob's Plumbing\ntemplate: page\n---\n\n# We fix things\n\nFamily owned since 1987.",
			"public": true
		},
		"/site.css": {
			"content-type": "text/css",
			"content": "body { font-family: system-ui; max-width: 40rem; margin: auto; }",
			"public": true
		},
		"/logo.png": {
			"content-type": "image/png",
			"content-base64": "iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR42mNk+M9QDwADhgGAWjR9awAAAABJRU5ErkJggg==",
			"public": true
		},
		"/handbook": {
			"content-type": "text/markdown",
			"content": "# Employee handbook\n\nStart every job by checking the water is off.",
			"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]]
		}
	}
}
```

Every static entry is a route at exactly one path, with its own requirements, its own priority, and its own headers, so the conflicts and configs designs apply to it like any other route. The host content-addresses each entry when the manifest is deployed, so it can serve it with an immutable cache header, compress it once, and answer conditional requests without thinking.

Static content is domain specific through the manifest's domains: a manifest for bobsplumbing.com carries Bob's pages, and a manifest for "*" carries what every domain shares. Static content uses exactly the same requirements as routes, which is what full privacy fidelity means here: an employee handbook is protected by the same grant roles as the jobs it describes, and a static entry with no requirements is denied unless it says "public": true.

Putting static content in the manifest does two things. It lets a box's UI be bundled with the box as one fixed unit, so everything about deploying, approving, shadowing, and splitting a box holds for its pages too, and a box and its pages can never drift apart. It also gives a single, unified deployment artifact, where a site with no box at all is simply a config, as described in the configs design. Large files, like videos or big PDFs, don't belong in a manifest; they belong in objects, below.

## Objects and attachments

Objects are the files that people add while using a product: a photo of a job site, a signed quote, a receipt. They are not part of the box's deploy, so they live in object storage, and they are declared in the manifest the way data is, as a provider and a strategy whose key resolves from the secure context.

```json
{
	"objects": {
		"store": {
			"job_photos": {
				"key": "{tenant}/jobs/{job_id}/",
				"types": ["image/jpeg", "image/png", "application/pdf"],
				"max-bytes": 10485760,
				"read": true,
				"write": true
			}
		}
	}
}
```

The box never sees a bucket, a URL, or a credential. An upload arrives at a route, the host checks its size and that its bytes really are what its name and type claim, stores it under the resolved key, and hands the box a handle. A download goes through the host as a static proxy, which checks the route's requirements before streaming a single byte, so a link to a private photo is worthless to anyone without the role. Objects that browsers could execute, like HTML or SVG, are always served as downloads rather than inline, so an upload can never become a page.

We start with a directory on disk, since that is enough for one machine. However, we plan around S3's limits and semantics from day one: keys are flat strings, objects are written whole, large objects are uploaded in parts, and nothing depends on listing being fast. That way, moving from disk to S3, or to anything else that speaks its API, changes the host's configuration and not a single manifest.

## One backing tree

Objects, and the deployed manifests whose static content and templates the host has unpacked for serving, all live in one common backing directory structure that the host manages. Every product, version, and tenant has a predictable place in it, so the host can back it up, move a tenant, or delete a tenant by working on a directory, the same way a tenant's database is a file.

```
/var/goober/assets/
	products/
		jobs/
			<version hash>/
				manifest.json
				static/
	objects/
		jobs/
			bobs_plumbing/
				jobs/
					8812/
						front-door.jpg
						quote-signed.pdf
```

However, the tree is the host's business, not the world's. The only ways to query it are to fetch a single object by its full key, or to list the files directly inside one directory. There is no walking the tree, no recursive listing, and no searching across directories, so the cost of any query is known up front, and it maps directly onto how S3 lists a single prefix with a delimiter.

Even those listings are off by default. The hierarchy is never exposed outside the host, to a box or to a browser, until the manifest opts in for a specific objects strategy.

```json
{
	"objects": {
		"store": {
			"job_photos": {
				"key": "{tenant}/jobs/{job_id}/",
				"listing": true,
				"read": true
			}
		}
	}
}
```

With "listing": true, a box can ask for the objects in one directory of that strategy, and nothing above or beside it, and an asset data route can offer the same to callers who pass its requirements. Without it, a caller can only fetch objects whose keys they already know. This matters because a hierarchy leaks information all by itself: which tenants exist, how many jobs they have, and what people named their files. A key that the box handed out is a fine way to reach an object, but a directory listing that nobody asked for is a map nobody should have.

## Styling the sign-in

Templates are also how a product styles the OAuth sign-in from the identity design. The identity service renders its screens through the product's layout template, so the sign-in page looks like Bob's Plumbing rather than like a platform. However, the identity design's sign-in requirements can't be reskinned away: the client's origin, the plain-words consent, the device code warnings, and the rest are rendered by the host in fixed slots that the template can place but not remove or rewrite.

## Keeping browsers safe

Serving HTML means taking on the browser's threat model, so the host takes on its defenses:

- **A strict content security policy.** Scripts run only from the box's own static files, never inline, so injected text has nowhere to execute.
- **Cookies belong to identity.** Only the identity service sets cookies, they are HttpOnly and SameSite, and boxes can't set or read them, which matches the HTTP design putting cookies outside of routes.
- **Forms can't be forged.** State-changing routes reached from a browser are checked for cross-site requests by the host, so a box never has to remember to.
- **Framing is refused.** Pages can't be embedded in other sites unless the manifest says so.

## Helpers

Since the manifest describes every route, type, and subscription, the host can serve helpers that make building a UI on top of a box pleasant:

- **A small client script**, served by the host, that calls routes with the signed-in user's session, follows SSE subscriptions from the bus design, and reconnects with the last sequence it saw.
- **A typed client**, generated from the box's OpenAPI document, so a web, mobile, or desktop app gets the same types the box uses.
- **A default layout and stylesheet**, so a box with no design at all still produces pages that look reasonable, on a phone and on a desktop.

The markdown renderer, the template engine, the default layout, and the client script are all host code, so each one is pinned by version in the manifest, as described in the stability design. A host upgrade can never change how a deployed box's pages look.

Mobile and desktop apps don't need anything special. They call the same routes with application/json, sign in through the same OAuth flow, and subscribe to the same signals.

## The invariants

- **One route can serve every audience.** The box fills in one structure, and the host renders it for whoever asked.
- **Templates and markdown can't execute.** Templates are logic-less, values are escaped, and raw HTML in markdown is off by default.
- **Static content and objects obey the same requirements as routes.** Nothing is served without requirements or an explicit "public": true.
- **The box never touches a bucket.** Objects are reached by handles, and the host proxies every byte.
- **The backing tree stays private.** It can only be queried one object or one directory at a time, and listing is off unless the manifest opts in.
- **Uploads can't become pages.** Executable types are always served as downloads.
- **Reskinning can't remove a security element.** The identity screens keep their fixed slots under any template.
