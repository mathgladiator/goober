# The Bus

Come on loser, we're going to publish and subscribe. Similar to data, we will embed an event bus using topical pub/sub. This is a well-trodden space, and the key design pattern is that we are going to focus on simplifying publish/subscribe to respect the last write. Pub/sub has fundamental problems since it can create quadratic problems, and to solve this, we need some kind of amortization and rate limiting to flatten the curve. This means publishing data to a topic should be a sequencer-like thing or a timestamp, so we refine how we expose publishing to restrict how the topics get updated. This restriction is sane, since we should not trust pub/sub for the delivery of data that belongs in a database, and it also addresses reliability issues when pub/sub throttles too hard or during a reconnect, which forces a data refresh.

This impacts the manifest in a few ways. First, we get an SSE route for subscriptions, and we introduce a model that mirrors a subscription that polls a function. This is expensive in many ways, but it is better than fixed-period polling if we have a wake-up signal. The wake-up signal needs to be part of the route. This allows us to leverage SSE as a protocol, which is how we will express pub/sub.

We may explore different models, but we start with the simplest approach that provides fault tolerance and real-time capability.

## Why the last write is all that matters

Most pub/sub systems pretend to be a database with a delivery problem. They carry the data itself, promise to deliver every message, and then spend the rest of their lives failing at that promise in creative ways: slow consumers, dropped connections, replays, backpressure, and a queue on a broker somewhere quietly eating memory. We are not going to play that game, because we already have a place where data lives, and it is the database.

So the bus carries signals, not data. A message on a topic is just "this topic is now at sequence N." That is the whole payload. A subscriber that hears N and has already seen N, or anything later, does nothing. A subscriber that hears N, N+1, and N+2 in quick succession only cares about N+2. The intermediate messages can be skipped, dropped, merged, or lost, and nothing breaks, because the truth is in the database and the signal only says when to go look at it.

This is what we mean by respecting the last write. Once the bus only has to deliver "the latest number," every hard problem in pub/sub gets easier:

- **Throttling is free.** When the host is under pressure, it holds signals and sends only the newest one, and subscribers lose latency rather than correctness.
- **Reconnects are boring.** A client that reconnects says the last sequence it saw, and if the topic has moved on, the host evaluates the function once and sends the current answer. There is no replay, no backlog, and no gap to fill.
- **Lost messages heal.** A periodic refresh catches anything the bus dropped, so a lost signal costs a little time instead of a wrong screen.

## The quadratic problem

Picture a room with N people in it, where every person's action is published to everyone else. Each action fans out to N subscribers, and with N people acting, that is N² messages. Double the room and you quadruple the work, and that is how a chat feature takes down a fleet on a busy afternoon.

Coalescing breaks the curve. Each subscriber evaluates its function at most once per coalescing window, no matter how many signals arrived in that window. The work becomes proportional to the number of subscribers per window rather than the number of publishes times the number of subscribers. A room that gets louder does not get more expensive; it gets slightly less real-time, which is a trade we can actually choose.

We can go one step further. The signature from the manifest design tells us exactly which context and scopes a subscription can see, so two subscribers with the same signature asking the same route will get the same answer. The host evaluates once per signature and fans out the result, which turns a thousand people watching the same dashboard into one evaluation and a thousand writes to sockets. For this to be safe, the host refuses writes and effectful calls during a subscription evaluation, since an evaluation that might run once for many people must not change anything.

## The manifest

Publishing is not something the box does by hand. A strategy declares the topic its writes publish to, and when a write set commits, the host bumps the topic to the new sequence number. That means a signal is published if and only if the data it describes is committed, which is the same promise the outbox makes for side effects, and for the same reason.

```json
{
	"context": {
		"tenant_id": {
			"type": "int64",
			"source": "lookup/tenant_by_domain"
		}
	},
	"routes": {
		"sse": {
			"/orders/live": {
				"subscribe": {
					"name": "live_orders",
					"response": "json",
					"wake": [ "orders/{tenant_id}" ],
					"coalesce-ms": 250,
					"refresh-ms": 30000
				}
			}
		}
	},
	"data": {
		"sqlite3": {
			"orders_by_customer": {
				"schema": "orders7.schema",
				"database": "tenant_{tenant_id}",
				"table": "orders",
				"pattern": "by_index",
				"index": "customer_id",
				"limit": 50,
				"read": true,
				"write": true,
				"publish": "orders/{tenant_id}"
			}
		}
	}
}
```

Topics are hierarchical paths, and like database names, they are templates filled from the context. A subscription can only wake on topics that resolve from its own context, so a box serving tenant 9 can't listen to tenant 7, for the same reason it can't read tenant 7's rows: it has no words for it.

The subscribe route is where the wake-up signal lives. When any topic in wake moves forward, the host waits out the coalescing window, evaluates the route like a GET, and sends the result down the SSE stream as an event whose id is the sequence number. If the result is identical to the last one sent, the host sends nothing at all. If refresh-ms passes without a signal, the host evaluates anyway, which is the safety net for the signals we lost. From the box's side, a subscription route is just a route that answers a question, and it may be asked that question many times.

## Options

On a single machine, the bus is in-process: a table of topics to sequence numbers and a list of who is waiting on each, which is a few hundred lines of code and the fastest thing possible. In the cluster scenario, we need something to carry signals between machines, and since we only carry tiny signals that are allowed to be lost, almost anything works. That is the point. Tactically, there are many options:

| option | delivery | why we would use it | why we might not |
| --- | --- | --- | --- |
| In-process | Exact, one machine | The single-machine default. No network, no broker, and no failure modes beyond the process itself. | It stops at the edge of the machine. |
| NATS (core) | At-most-once | The natural fit. Subjects are hierarchical with wildcards, it is small and fast, and fire-and-forget is exactly what a signal needs. | Messages to a disconnected subscriber are gone, which is fine for us and only for us. |
| NATS JetStream KV | Last value per key | Literally last-write-wins: each topic keeps its latest value, and a watcher gets the current value on connect. | More moving parts than core NATS for durability we mostly don't need. |
| Redis Pub/Sub | At-most-once | Already deployed nearly everywhere, and trivial to operate. | Single-threaded fan-out and no history; clustering it for pub/sub is awkward. |
| PostgreSQL LISTEN/NOTIFY | At-most-once | No extra infrastructure when Postgres is already the database, and notifications fire on commit. | Bound to one primary, with small payload limits and a ceiling on throughput. |
| etcd watch | Ordered, with revisions | Revisions are a sequencer for free, and a watch can resume from a revision. | Built for small amounts of coordination data, not for a high rate of signals. |
| MQTT (Mosquitto, EMQX) | Configurable, retained messages | Retained messages are last-value-per-topic, and it is the language devices already speak. | The ecosystem leans towards devices rather than servers. |
| Kafka or Redpanda | At-least-once, durable log | Log compaction keeps the last value per key, and it is the standard when a durable history matters. | Heavy machinery for signals that are allowed to be lost. |
| ZeroMQ | At-most-once, brokerless | A library rather than a service, with no broker to run. | We would be building the routing, discovery, and reconnects ourselves. |
| Managed (Google Pub/Sub, SNS) | At-least-once | Nothing to operate, and it scales without asking. | Latency is higher, and a cloud dependency sits in the middle of the real-time path. |

The recommendation is in-process for a single machine and core NATS for a cluster. The design deliberately asks so little of the bus that the cheapest, fastest, least durable option is the right one, and if we ever regret that, JetStream KV is the same vocabulary with a memory.

## The invariants

- **The bus carries signals, never data.** A signal is a topic and a sequence number, and the data lives in the database.
- **Signals are monotonic per topic.** A signal at or behind what a subscriber has seen is discarded.
- **Signals coalesce.** A subscriber evaluates at most once per coalescing window, so cost scales with subscribers, not with publishes times subscribers.
- **A lost signal costs latency, not correctness.** Refreshes and reconnects always converge on the current state.
- **A signal is published if and only if its write set commits.** Publishing comes from the data, not from the box's good intentions.
- **Topics are scoped like data.** A box can only subscribe to topics that resolve from its own context.
- **A subscription evaluation changes nothing.** The host refuses writes and effectful calls during an evaluation, which is what lets one evaluation serve many subscribers.

## What the box never thinks about

Connections, reconnects, backlogs, fan-out, throttling, deduplication, and the broker all live in the host. The box writes data, and the data publishes itself. The box answers a question, and the host decides when to ask it again. There is an open question as to whether some features truly need every message rather than the last one, like a chat log, but those are better modeled as data with an append-only pattern and a subscription that reads the newest page, which keeps the bus honest and the database in charge.
