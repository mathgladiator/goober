# Operating the Thing

We reserve /goober-operations/* as an open admin for the host, and the host can either open it on a different port or merge it into the mainline port. This is a security and blast radius protection system. It leverages the same OAuth system, and it also enables agentic operations via /goober-operations-mcp.

Tactically, every box starts as a complete black box, and we provide analytics per route, with basic classifiers for the common user agents that capture 95% of people and the major search bots. This goes into access logs, so we can do full audits of who did what, and we also capture latency and result codes, along with request and response hashes, and the box and version that responded. No user data goes into access logs.

We will use the logs to accumulate a basic hourly dashboard for the last 12 hours of uptime, and reduce the logs to performance per box and per version, so we can get a sense of the cost.

Each box will be instrumented in terms of time running on CPU, throughput and data usage into and out of the box, and failure rates, along with capacity concerns like the memory used by the box, as p50, p99, and p100 of the box's size.

We also get the multiplicity and instance count, along with the queue sizing required for the box, and the time to spin up and the time to shut down a box. Each box will have an operable configuration for how many instances can run at once, with a queue backing up behind them, and we have a queue policy for each public route and for each internal route.

We want to treat the box just like a black box to the operating system, but we also want to give the agent important ways to register simple counters to capture frequency. We start with counters, since they provide capture-the-flag style introspection for quality assurance: were these branches reached or not?

At core, the dashboard is about the health of the host as a whole, and from there, a sidebar shows a heat map of boxes, hot versus cold. There is also a graphical view where a single box can be selected, and then we see its manifest visualized. We can see the heat per route, the heat per data flow in and data flow out, and the heat per service call. This is presented visually, so that we can completely feel how the box performs operationally, and the agent has the same information.

In this model, heat is CPU cost, weight is the size of data, and bandwidth pressure is the data rate of the box per source.

From here, we also get a manifest explorer, with tools that provide token traces to inspect each user flow.

This operational panel sets the stage for everything to come, like deployments, approval workflows, and agentic operators.

## The reserved surface

| path | what it is |
| --- | --- |
| /goober-operations/* | The panel itself: dashboards, the heat map, box views, the manifest explorer, and traces. |
| /goober-operations-mcp | The same information and actions as MCP tools, for agentic operators. |

No manifest can register a route under these paths, on any protocol. The host decides where they are served:

```json
{
	"operations": {
		"listen": "127.0.0.1:9443",
		"merge-into-mainline": false,
		"retention": {
			"access-log-days": 14,
			"rollup-days": 400
		}
	}
}
```

Serving operations on their own port, bound to a private interface, is the blast radius protection: a mistake in the panel, or a stolen operator session, can't be reached from the public internet at all. Merging into the mainline port is available for a single machine where a separate port is a nuisance, and then the panel is only ever served on the platform's own domain, never on a tenant's.

The panel signs people in with the same OAuth system, in the platform's own realm from the identity design. Access uses grant roles like everything else:

| role | can |
| --- | --- |
| owner | Everything, including changing operable configuration. |
| operator | See everything, and change operable configuration within the bounds the manifests allow. |
| observer | See everything, and change nothing. |

Agents connect to /goober-operations-mcp through the same OAuth flow, with exactly the roles of the person who connected them, so an agentic operator working for an observer can look but never touch. Every action taken in the panel, by a person or an agent, is written to the identity audit.

## Access logs

Every request to every box produces one line in the access log. The access log describes what happened, never who it happened to.

| field | meaning |
| --- | --- |
| at | When the request arrived, in int64 milliseconds. |
| request_id | A random id for the request, shared with every internal call, outbox element, and audit row it causes. |
| domain | The domain it arrived on. |
| box, version | Which box, and which deployed version of it, answered. |
| protocol, route, verb | Which route was called. |
| status | The result code. |
| latency_ms | How long it took, from hand-off to response. |
| bytes_in, bytes_out | The size of the request and response bodies. |
| request_hash, response_hash | Keyed hashes of the bodies. |
| client_class | The user agent class, like a browser, a mobile app, a search bot, an MCP agent, or other. |
| principal_kind | Whether the caller was anonymous, a user, an agent, a box, or a timer, but never which one. |

There are no user ids, no IP addresses, no bodies, and no headers in the access log. The audit of who did what comes from joining a request_id to the identity design's audit table and the MCP audit, which hold the who, and which only an owner or operator can read. Keeping the two apart means the access log can be kept longer, shared with agents more freely, and lost without leaking anyone's data.

The request and response hashes are keyed with a secret that rotates, rather than plain hashes, since a plain hash of a short body, like a four-digit code, can be reversed by guessing. Keyed hashes still let us see that two requests had the same body, which is enough to spot caching opportunities, compare a shadow deployment with the live one, and notice when a box starts answering the same question differently.

The client classifier is deliberately small: the handful of browsers and mobile platforms that cover nearly everyone, the major search engine bots, MCP agents, and "other." It is updated by the host, never by a box.

## Rollups and cost

The host reduces the access log into hourly rollups per box and per version: requests, error rate, latency at p50, p99, and p100, CPU time, and bytes in and out. The dashboard shows the last 12 hours by default, and rollups are kept far longer than raw logs, so the history of how a box has performed outlives the details of any request.

Cost comes straight from the rollups. CPU time, bytes, storage from the upload ledger, and calls to external services from the egress audit are each multiplied by a price the operator sets, so every box, every version, and every tenant has a cost per hour that someone can actually read.

## Box instrumentation

| measure | what it tells us |
| --- | --- |
| CPU time | How much work the box does, which is its heat. |
| Throughput | Requests per second, per route. |
| Data in and out | Bytes read and written through each strategy, external service, and internal call, which is its weight and bandwidth pressure. |
| Failure rate | Errors, timeouts, traps, and blown budgets, per route. |
| Memory | The isolate's memory at p50, p99, and p100. |
| Instances | How many isolates of the box are running, and how many requests share them. |
| Queue depth | How many requests are waiting for an instance, per route. |
| Spin-up and shutdown | How long an isolate takes to start, including goober_on_start, and to drain and stop. |

## Instances and queues

Each box has an operable configuration for how many instances may run at once, and each public route and each internal route has a queue policy for what happens when they are all busy. The manifest declares the defaults and the bounds, and an operator can tune within those bounds from the panel without a deployment, since tuning capacity doesn't change what a box can do.

```json
{
	"behavior": {
		"instances": {
			"default": 4,
			"max": 32
		}
	},
	"routes": {
		"http": {
			"/jobs": {
				"get": {
					"name": "list_jobs",
					"response": "json",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]],
					"queue": {
						"max-depth": 100,
						"max-wait-ms": 250,
						"overflow": "reject"
					}
				}
			}
		}
	}
}
```

A request that would make the queue deeper than max-depth, or that waits longer than max-wait-ms, is refused with a 503 for public routes, or a failed call for internal routes, rather than piling up until everything times out. Changing a bound itself, as opposed to tuning within it, is a change to the box's shape and goes through the approval queue.

## Counters

The box is a black box to the host, but an agent building a box can register simple counters to see inside it. Counters are declared in the manifest, so their names are fixed, reviewed, and can never carry user data.

```json
{
	"counters": [
		"invoice_paid_in_full",
		"invoice_paid_partially",
		"invoice_overdue_reminder_sent"
	]
}
```

```C
// Generated from the manifest's counters.
void goober_counter_invoice_paid_in_full();
void goober_counter_invoice_paid_partially();
void goober_counter_invoice_overdue_reminder_sent();
```

Each call adds one, per box and per version. That is the capture-the-flag style of quality assurance: after a test run or a shadow deployment, any counter still at zero names a branch that was never reached, and a counter that suddenly jumps in a new version names a branch whose behavior changed. Counters ride the write set, so a request that fails doesn't count.

## The dashboard

The home of the panel is the health of the host as a whole: requests, errors, latency, CPU, memory, disk, the outbox and dead letters, the bus, the vault, and the sweeper. A sidebar shows the heat map of boxes, from hot to cold, so the boxes that deserve attention are the ones that glow.

Selecting a box opens its graphical view: the manifest drawn as a picture. Routes come in on one side, data strategies, external services, internal calls, outbox destinations, and bus topics go out on the other, and the box sits in the middle. Every edge is drawn with its numbers.

| measure | defined as | shown as |
| --- | --- | --- |
| Heat | CPU cost | The color of a route or a box. |
| Weight | The size of the data | The thickness of an edge. |
| Bandwidth pressure | The data rate of the box, per source | The motion along an edge. |

The point is that a person can look at a box and feel how it behaves, the same way they feel the shape of its manifest, without reading a line of its code. The agent gets the same picture as data through /goober-operations-mcp, so a person and an agent can talk about the same box while looking at the same numbers.

## The manifest explorer and traces

The manifest explorer walks a box's manifest as a graph, and adds the live numbers to every node. From any route, it can follow a trace token, which is the request_id from the access log, through everything that request caused: internal calls, data reads and writes, outbox elements, bus signals, and the timers that later fired because of it. Each step shows its route, its latency, its status, its counters, and its heat, but never its bodies.

Following one person's flow through a product, from the page they loaded to the email that arrived the next morning, is how a person or an agent finds out where time and money actually go, and it is exactly the view a future approval workflow will want when deciding whether a change made things better or worse.

## For agentic operators

/goober-operations-mcp offers the panel as tools, filtered by the connecting person's roles like every other MCP surface:

| tool | does |
| --- | --- |
| host_health | Returns the host's health summary. |
| hot_boxes | Lists boxes by heat over a window. |
| box_graph | Returns a box's manifest graph with its live numbers. |
| access_rollups | Returns hourly rollups for a box, version, route, or tenant. |
| counters | Returns a box's counters by version. |
| trace | Follows a trace token through everything it caused. |
| tune_instances, tune_queue | Change operable configuration within the manifest's bounds; operator role only. |

## The invariants

- **Operations are never served on a tenant's domain.** They live on their own port or on the platform's domain, and no manifest can claim their paths.
- **The access log holds no user data.** Who did what lives in the audits, joined by request_id, and only owners and operators can read them.
- **Hashes are keyed.** No body can be recovered from the access log by guessing.
- **Counters are declared, not invented.** Their names are fixed in the manifest, so they can't carry user data.
- **Tuning stays within bounds.** Operators adjust capacity inside what the manifest allows, and changing the bounds is a deployment.
- **People and agents see the same thing.** The panel and its MCP tools offer the same information, filtered by the same roles.
