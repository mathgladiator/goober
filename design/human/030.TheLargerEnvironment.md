# The Network

We are going to be opinionated about the services brought to the box, such that we generate code for a RESTful API. Basically, we will enable OpenAPI/Swagger to bring network resources into the system much like a schema, and these can be brought to the box via an external field that enumerates the methods allowed along with the restrictions on the request object that must be true to invoke.

A box that can open a socket to anywhere is a box that can mail your customer list to a stranger, so the box gets no sockets. All networking leaves through the host, and the host only speaks to what the manifest declares. This is the same move we made with data: the box does not get a connection, it gets a strongly typed function that the host fulfills, and the host is the only party that knows where the wire actually goes.

## Bringing in a service

Let's start with something useful and a little dangerous: sending an email. The box should be able to send a message to the user making the request, and it should be impossible for the box to send a message to anyone else.

```json
{
	"external": {
		"mail_user": {
			"openapi": "mailer.v3.openapi.json",
			"operation": "mailer",
			"base": "https://mail.example.com",
			"credentials": "keys/system/mailer",
			"methods": {
				"sendMessage": {
					"require": {
						"body.to": "{!email}"
					},
					"budget": {
						"calls": 3
					}
				}
			}
		}
	}
}
```

The pattern here is external.$service.$method, where $service is a unique label for the service and the $method is what is exposed to the box. The operation field is the operationId from the OpenAPI document. Similar to a strategy for data, the label namespaces the generated code, and the OpenAPI document is tightly coupled to the manifest the same way a .schema file is. If the service changes its document, then the box's shape changes, and that goes through the same human approval queue as everything else.

The require block is where the paranoia lives. Each entry pins a field of the request object to a value, and that value can come from the context. In the above, the "to" field must be the email of the principal, and the interesting consequence is that the generator does not even put "to" in the structure handed to the box. The host fills it in. The box can't send mail to the wrong person because the box has no way to say who the mail goes to. This is the theme of the whole project in one field: we don't frown upon the wrong action, we remove the words for it.

```C
#include <stddef.h>
#include <stdint.h>

struct mailer_send_message_request {
	const char* subject;
	size_t subject_len;
	const char* text;
	size_t text_len;
	// no "to": the host fills it from {!email}
};

int32_t mailer_send_message(const struct mailer_send_message_request* request);
```

The credentials are a name, not a secret. The host resolves keys/system/mailer at the time of the call and attaches it on the way out, so the API key never enters the box, never lands in the box's memory, and can't be logged, leaked, or shared between isolates. Rotating a key is an operational concern of the host, and the box doesn't care.

A few services are so common and so critical, like sending email, that the host offers them as long-term capabilities with swappable providers instead, and any OpenAPI service can later be redirected to an adapter box without changing the box that calls it, as described in the stability design.

## Consequences for the box

The boundary from the manifest decides how the call feels. In sync, mailer_send_message blocks the box until the host has a response, which is easy mode and mirrors how most HTTP clients work anyway. In async, the call returns immediately, and the response shows up later as a completion event tied to the request's context_id. Same manifest, same restrictions, different shape of networking.

The budget is per request and speaks operationally. Three calls means the fourth call fails without ever leaving the host, which caps the blast radius of a box stuck in a loop and makes the cost of a request something we can count before the bill arrives. The host also owns the timeouts, retries, and rate limits towards the service, since the host is the one that can see every box talking to the same service and the box only sees itself. Every call gets written down, what went out and what came back, because an audit of egress is the thing that legal will ask for first.

Sharing follows the same rule as data. If a restriction resolves from the context, then the resolved value becomes part of the signature, and two requests with different values will never share an isolate. A box that can only email its caller is a box that holds one caller at a time.

## Boxes talking to boxes

Every box already has a manifest that describes its routes, response shapes, and errors, so the tools can stamp out an OpenAPI document for any box. That means a box calling another box is not a new idea, it is just another entry under external where the base is an internal address the host resolves. The same restrictions apply, the same budgets apply, and the same audit applies, which gives us how boxes flow data between them explicitly. How data flows implicitly, through shared databases and the like, is a different and scarier conversation that we will have later.

The first-class version of this is the internal route, described in the internal messaging design: a box registers internal routes in its manifest, naming the boxes allowed to call them, and a caller declares the call with "box" in place of a base URL and an OpenAPI document. The host routes the call in-process on a single machine, or over an internal RPC in a cluster, so the caller never learns where the other box runs.

## Starting small

Tactically, we start with REST and OpenAPI because that is where the documents already exist, and agents have read more Swagger than any human ever should. The require block starts with simple equality on a field, and we will grow it towards ranges, sets, and patterns as we find out what boxes actually need. gRPC, GraphQL, websockets, and other protocols can earn their way in later. There is an open question as to how far restrictions can go before they turn into a programming language of their own, and the moment that happens, we have lost the plot.

This closes an implicit question from how routes defined stricted inputs and outputs such that every route will describe its inputs and outputs using a Swagger style schema.
