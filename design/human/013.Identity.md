# Identity and Access

A foundational concern of the platform is identity, for which we will provide a default API and the ability to reskin it on demand. The tactical solution at hand is a single server that handles the OAuth flow with passwordless login, and the built-in identity service will use a dedicated SQLite database, in an isolated thread and an isolated directory, so that no box can pick up the database by accident. The design for identity will be pluggable, so we consider the abstraction to be the key design.

At core, we ultimately want two things: a user id, and an easy-to-cache map of user ids to grant roles. As part of the routing, we add requirements to a route, so that the host is responsible for gating access at the route level. This means access control is a prime concern, and we model it in the manifest as a requirements field on each route.

```json
{
	"routes": {
		"http": {
			"/hello": {
				"get": {
					"name": "hello_world",
					"signal": 42,
					"response": "text",
					"requirements": ["user_id"]
				}
			}
		}
	}
}
```

The user_id is part of the secure context. A user is anyone who has a secure context through an OAuth flow on the domain they are using, whether they signed in with a password, without one, or through an agent acting on their behalf. The identity service puts the user_id there, and only the identity service can put it there. A requirement of "user_id" is satisfied when the secure context holds one, which is to say the caller is a user. It is not a role that anybody grants; it is the identity itself, and so "user_id" can't be used as the name of a grant role.

## A warning about the built-in identity service

The built-in identity service will work, but it is high risk. It uses decent practices throughout, as this document describes, but its implementation is a one-person vibe affair, and identity is exactly the kind of system where small mistakes become large breaches. Nobody is probing it daily, there is no security team behind it, and it hasn't survived the years of attack that mature identity products have.

What is meant to be sound is the contract, not the implementation. Boxes never talk to the identity service directly; they only ever see the secure context, the user_id, the grant roles, and the requirements the host checks for them. That contract is designed to outlive the built-in service, so future versions can plug in a more adult offering that does everything a larger business needs, like single sign-on with the identity provider a company already runs, without changing a single box.

So the built-in service is the primary gate for small to medium scale offerings, and it should be used according to the business risk of whatever sits behind it. Playing, prototyping, a personal server, or a small business with modest stakes are fine. Anything where a breach would be serious should plug in a dedicated identity product instead, until this project is funded well enough to have an entire team probing the built-in service every day. For now, it's vibed, and it will "work."

## Identity is per domain

Identity follows the domain, as described in the domains design. Every primary domain in the registry is its own identity realm, with its own users, its own sessions, its own OAuth clients, and its own grant roles. A tenant's other domains are always redirects to its primary domain, so they never sign anyone in, and every realm has exactly one name. The identity service is one host feature, but it keeps one database per realm, so a realm moves, backs up, and is deleted along with its domain.

This means the same email address on two domains is two different people as far as the system is concerned. Alice's account at bobsplumbing.com and her account at anneslandscaping.com share nothing: not a user_id, not a password, not a passkey, and not a role. A user_id only means something together with the domain it belongs to, so the secure context always carries both, and a token issued in one realm is never accepted in another.

The browser already wants it this way. Passkeys are bound to the domain they were created on, cookies are set for the exact domain, and an OAuth issuer is a URL, so making each domain its own realm lines the design up with the web rather than fighting it. It also means a breach of one realm's sessions, or a person phished on one domain, never reaches another tenant.

## Grant roles

A grant role is just a string, like "admin", "owner", or "admin/bobs_plumbing". There is no hierarchy between grant roles: "owner" does not imply "admin", and "admin/bobs_plumbing" does not imply anything about "admin". A user either holds a string or does not, and a requirement either matches the strings a user holds or does not. This is deliberately dumb, because dumb is auditable. Everything about access in this system comes down to which grant strings a route requires and which grant strings a route can hand out or take away.

The "/" character is reserved to separate namespaces within a grant role, so "admin/bobs_plumbing" is the role admin in the namespace bobs_plumbing, and there is exactly one way to read it. No substituted value may contain "/", which means a value can never smuggle in an extra namespace. A tenant slug of "bobs/plumbing" is rejected by the host before any matching happens, rather than quietly becoming a different role.

We stick to this simple string-matching scheme, but recognize that we can enable allow and deny lists as a pluggable feature. At this point, we have a clear way to audit what users can do or execute.

The requirements field is in disjunctive normal form (an OR of AND clauses), or just a flat list, which is a single AND clause. A route with no requirements is denied to everyone, and the checker refuses it. The two exceptions are internal routes, which are gated by their callers list instead, and timer routes, which only the host can ever call, as the deep manifest design's reachability table spells out. To opt out of this behavior, a route must say so explicitly with "public": true, and a route that has both requirements and "public" is also refused, since it can't mean both.

```json
{
	"routes": {
		"http": {
			"/": {
				"get": {
					"name": "landing_page",
					"response": "text",
					"public": true
				}
			}
		}
	}
}
```

## Granting and revoking roles

This begs the question of how boxes can grant roles to other users, and here we give a route the ability to grant roles to a specific user id. The mirror image is revoking, and it sits right next to granting in the manifest, so a reader sees both directions of a role change in one place. In the scenario below, a user can make another user an admin, or stop them being one, if the user doing the mutating is either an admin or the owner.

```json
{
	"routes": {
		"http": {
			"/grants/mutate-admin/{to : int64}": {
				"post": {
					"name": "mutate_admin",
					"response": "text",
					"requirements": [["admin"], ["owner"]],
					"grantable": {
						"options": ["admin"],
						"to": "{to}"
					},
					"revocable": {
						"options": ["admin"],
						"to": "{to}"
					}
				}
			}
		}
	}
}
```

The revocable block has exactly the same shape and rules as grantable: the options are the only strings the route can take away, and "to" names whose roles they are. A route can have either block, both, or neither, and the checker treats each as its own power, so "who can remove an admin?" is answered the same way as "who can make one?" by reading the options.

By default, the host rejects a revocation where "to" is the caller, so nobody can remove their own roles by accident. A route that truly needs it, like "leave this team," must opt in with a specific flag.

```json
{
	"revocable": {
		"options": ["member/{tenant}"],
		"to": "{to}",
		"allow-self-revoke": true
	}
}
```

The checker warns on every route with this flag and spells out the implications for the human approving it: the caller may lose access to the very route they are using, and if the option is an owner role, a namespace can be left with no owner at all, so that only the absolute owner can repair it.

Since there is no hierarchy, a route can grant or revoke a role that the caller does not hold. That is not a loophole; it is the point. The manifest is the only place that says which strings a route can hand out or take away, so the question "who can make someone an admin?" is answered by searching every manifest for routes whose grantable options include "admin" and reading their requirements. Nothing is implied, and nothing is inherited.

This will then generate C code that the box calls and the runtime checks. The generator uses the route name and hides the target user, since "to" is already resolved by the host. The role stays a string, because a route may offer a range of options, and the host validates the string against those options at runtime.

```C
#include <stdbool.h>
#include <stddef.h>

// Grants the role to the user named by the route; returns true if accepted.
// The role must match one of the route's grantable options.
bool mutate_admin_grant(const char* role, size_t role_len);

// Revokes the role from the user named by the route; returns true if accepted.
// The role must match one of the route's revocable options.
bool mutate_admin_revoke(const char* role, size_t role_len);
```

Grants and revocations ride the outbox, just like any other side effect. Each is captured in the request's write set, and it only commits when the request responds. If the box traps, times out, or blows its budget, the change never happened. Accepted is not committed, the same as data.

This protects agentic boxes from abusing intent, and it does it in the runtime such that we maintain flexibility of how roles are checked, granted, revoked, and ultimately stored.

## Scoping roles by substitution

A single product will often serve many tenants, so a role needs to say which tenant it belongs to. We do this with plain strings again: admin of Bob's Plumbing is "admin/bobs_plumbing", and admin of Anne's Landscaping is "admin/annes_landscaping". They are different strings, so holding one says nothing about the other.

Writing a route per tenant would be silly, so requirements and options can contain variables that the host substitutes before matching, using the same {name} syntax as everywhere else in the manifest. However, the two places have different rules about where a variable may come from:

| where | variables may come from | why |
| --- | --- | --- |
| requirements | the secure context, the route path, or the query parameters | The caller still has to hold the substituted string, so a caller-chosen value can only ever check the caller against a role they claim to have. |
| grantable and revocable options | the secure context, or the user id in question ({to}) | These hand out or take away power, so nothing the caller types may decide which role changes hands. |

```json
{
	"requirements": [["admin/{tenant}"], ["owner/{tenant}"]],
	"grantable": {
		"options": ["admin/{tenant}", "member/{tenant}"],
		"to": "{to}"
	},
	"revocable": {
		"options": ["admin/{tenant}", "member/{tenant}"],
		"to": "{to}"
	}
}
```

When the secure context resolves tenant to "bobs_plumbing", the requirement becomes admin/bobs_plumbing or owner/bobs_plumbing, and the options become admin/bobs_plumbing and member/bobs_plumbing. The box then asks to grant "admin/bobs_plumbing", and the host checks that string against the substituted options. The box never gets to substitute anything itself.

The rule on options closes the obvious hole. If options could use a variable from the route path, a route that grants owner/{slug} for whatever slug the caller typed could hand someone a tenant that already belongs to somebody else. Because options only substitute from the secure context or the target user, the tenant a route can grant into is always the tenant the host resolved, never the tenant the caller asked for, and the checker refuses any options that use another source.

## Bootstrapping the first owner

Someone has to hold the first role in each realm, and no route can grant it, since every route requires something. So first owners are minted outside of routes, in two places. The absolute owner is minted by server-side configuration, on the platform's own domain, which only an operator can change.

```json
{
	"identity": {
		"directory": "/var/goober/identity",
		"bootstrap": {
			"owner": "founder@example.com"
		}
	}
}
```

On first start, the identity service grants "owner" to the user who signs in with that address on the platform's domain. Tenant owners are minted by the domain registry instead: registering a primary domain names the email address of its first owner, and the first time that address signs in on that domain, the identity service grants "owner/$tenant" to them in that domain's realm.

In a multi-tenant system, there are then two kinds of owner to contend with: the absolute owner, "owner", which belongs to whoever runs the system and lives in the platform's realm, and the tenant owner, "owner/$tenant", which belongs to whoever runs a business and lives in that business's realm. These are different strings in different realms, so the absolute owner is not automatically the owner of every tenant, and in fact has no account on a tenant's domain at all unless the tenant creates one. A tenant owner can never become the absolute owner through substitution, since "/" can't be substituted away.

## A multi-tenant example

Here is how it all fits together for a product that hosts many trade businesses. The tenant comes from the domain, as in the data design, and the domain registry assigns each domain to exactly one tenant, so the tenant is always part of the secure context.

```json
{
	"context": {
		"tenant": {
			"type": "string",
			"source": "domain/tenant"
		}
	},
	"routes": {
		"http": {
			"/": {
				"get": {
					"name": "landing_page",
					"response": "text",
					"public": true
				}
			},
			"/team/{to : int64}": {
				"post": {
					"name": "mutate_team",
					"response": "text",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"]],
					"grantable": {
						"options": ["admin/{tenant}", "member/{tenant}"],
						"to": "{to}"
					},
					"revocable": {
						"options": ["admin/{tenant}", "member/{tenant}"],
						"to": "{to}"
					}
				}
			},
			"/jobs": {
				"get": {
					"name": "list_jobs",
					"response": "json",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]]
				}
			}
		}
	}
}
```

The story, step by step:

1. **The operator configures the founder.** On first start, the founder signs in on the platform's domain and holds "owner" in the platform's realm.
2. **The founder registers Bob's domain.** bobs-plumbing.example.com is registered for the tenant bobs_plumbing, and verified if the host requires it, naming bob@bobsplumbing.com as its first owner, as described in the domains design. Any request on that domain now carries tenant = bobs_plumbing in its secure context, and the domain has a fresh, empty realm.
3. **Bob claims his business.** Bob signs in on bobs-plumbing.example.com with that address, and the identity service grants him "owner/bobs_plumbing" in Bob's realm. The tenant came from the registry, not from anything anyone typed.
4. **Bob builds his team.** Alice signs up on Bob's domain, which creates her account in Bob's realm, and Bob calls mutate_team for her. He holds owner/bobs_plumbing, so he passes, and the box grants "member/bobs_plumbing" to Alice. Later, if Alice leaves, the same route revokes it.
5. **Alice works.** Alice calls list_jobs on Bob's domain and passes as a member. On annes-landscaping.example.com, Alice's account from Bob's realm doesn't exist at all. If she signs up there, she is a brand new user in Anne's realm, with no roles, so she is denied.
6. **The founder is not everywhere.** The founder holds "owner" in the platform's realm and has no account in Bob's realm, so the founder can't list Bob's jobs unless Bob invites them, which is exactly how it should be for somebody else's business.

Every one of these facts can be read straight out of the manifest, the domain registry, and each realm's role table, and that is the audit.

**Warning: the absolute owner can reassign any tenant.** Because the absolute owner controls the domain registry, whoever runs the system can re-register a tenant's domain, name a different first owner, or reset a realm at any time. This is true of every service business, since the operator always controls the servers, so we don't pretend otherwise. However, it is a power that tenants deserve to see used, and that requires an audit rule in the larger ecosystem, such as recording every grant and revocation made by the absolute owner and showing it to the affected tenant's owners. We are not there yet, and until we are, the domain registry should be treated as one of the most sensitive tools in the system.

## Sessions, schema, and the login API

The identity service is a host feature, not a box, and it keeps one SQLite database per realm, in its own directory. It speaks standard OAuth 2.1 with PKCE, since that is what every client already knows, and it supports both passwordless and password-based sign-in behind the same flow. Whatever way a person proves who they are, the result is the same: an access token, whose secure context carries a user_id.

### The schema

Every secret is stored as a hash, never as itself, so a stolen database file yields no usable codes, passwords, or tokens. Times are int64 milliseconds since the epoch.

```sql
-- People.
CREATE TABLE users (
	id INTEGER PRIMARY KEY,               -- the user_id in the secure context
	email TEXT NOT NULL UNIQUE,
	created_at INTEGER NOT NULL,
	disabled_at INTEGER                   -- set to stop every session at the next request
);

-- Password-based sign-in.
CREATE TABLE passwords (
	user_id INTEGER PRIMARY KEY REFERENCES users(id),
	hash TEXT NOT NULL,                   -- argon2id, with its parameters encoded in the hash
	updated_at INTEGER NOT NULL
);

-- Passwordless sign-in by a one-time code or link sent by email.
CREATE TABLE email_codes (
	id INTEGER PRIMARY KEY,
	email TEXT NOT NULL,
	code_hash TEXT NOT NULL,
	expires_at INTEGER NOT NULL,          -- minutes, not hours
	attempts INTEGER NOT NULL DEFAULT 0,  -- locked after a handful of failures
	consumed_at INTEGER                   -- single use
);

-- Passwordless sign-in by passkey (WebAuthn).
CREATE TABLE passkeys (
	credential_id BLOB PRIMARY KEY,
	user_id INTEGER NOT NULL REFERENCES users(id),
	public_key BLOB NOT NULL,
	sign_count INTEGER NOT NULL,
	created_at INTEGER NOT NULL
);

-- Applications and agents that may ask for tokens.
CREATE TABLE clients (
	client_id TEXT PRIMARY KEY,
	name TEXT NOT NULL,                   -- shown to the person on the consent screen
	redirect_uris TEXT NOT NULL,          -- JSON array; exact match only
	kind TEXT NOT NULL,                   -- 'public' (PKCE, no secret) or 'confidential'
	secret_hash TEXT,
	created_at INTEGER NOT NULL
);

-- Short-lived codes in the authorization code flow.
CREATE TABLE authorization_codes (
	code_hash TEXT PRIMARY KEY,
	client_id TEXT NOT NULL REFERENCES clients(client_id),
	user_id INTEGER NOT NULL REFERENCES users(id),
	redirect_uri TEXT NOT NULL,
	code_challenge TEXT NOT NULL,         -- PKCE, S256 only
	expires_at INTEGER NOT NULL,
	consumed_at INTEGER
);

-- Pending sign-ins for clients without a browser, like a command-line agent.
CREATE TABLE device_codes (
	device_code_hash TEXT PRIMARY KEY,
	user_code TEXT NOT NULL UNIQUE,       -- short, typed by the person
	client_id TEXT NOT NULL REFERENCES clients(client_id),
	user_id INTEGER REFERENCES users(id), -- set when the person approves
	expires_at INTEGER NOT NULL,
	approved_at INTEGER,
	denied_at INTEGER
);

-- Sessions: every access token and refresh token issued.
CREATE TABLE tokens (
	token_hash TEXT PRIMARY KEY,
	kind TEXT NOT NULL,                   -- 'access' or 'refresh'
	user_id INTEGER NOT NULL REFERENCES users(id),
	client_id TEXT NOT NULL REFERENCES clients(client_id),
	is_agent INTEGER NOT NULL,            -- 1 when the client acts on the person's behalf
	expires_at INTEGER NOT NULL,
	rotated_to TEXT,                      -- refresh tokens rotate on every use
	revoked_at INTEGER
);

-- Grant roles, keyed by the full role string, namespace included.
CREATE TABLE roles (
	user_id INTEGER NOT NULL REFERENCES users(id),
	role TEXT NOT NULL,                   -- like 'owner' or 'admin/bobs_plumbing'
	granted_by INTEGER REFERENCES users(id),
	granted_at INTEGER NOT NULL,
	PRIMARY KEY (user_id, role)
);

-- Every change of identity or role, for the audit.
CREATE TABLE audit (
	id INTEGER PRIMARY KEY,
	at INTEGER NOT NULL,
	actor INTEGER,                        -- the user_id that did it, if any
	action TEXT NOT NULL,                 -- like 'sign_in', 'grant', 'revoke', 'token_revoked'
	subject INTEGER,                      -- the user_id it was done to
	detail TEXT NOT NULL                  -- JSON
);
```

Tokens are opaque random strings rather than self-describing ones, so revoking a token or disabling a user takes effect at the next request, and the easy-to-cache map from user ids to roles is the only thing the host needs to keep hot.

### The implicit API

These endpoints exist on every registered domain without any manifest declaring them, since they belong to the host. Each primary domain is its own OAuth issuer, so its metadata, clients, and tokens describe that realm alone. Boxes never see them, and no box can shadow them.

| endpoint | purpose |
| --- | --- |
| GET /.well-known/oauth-authorization-server | Metadata describing every endpoint below, so clients discover the rest. |
| POST /oauth/register | Dynamic client registration, so an agent can introduce itself without an operator. |
| GET /oauth/authorize | The browser sign-in and consent screen, for the authorization code flow with PKCE. |
| POST /oauth/device | Starts a device sign-in, returning a device code, a short user code, and a link to visit. |
| POST /oauth/token | Exchanges an authorization code, a device code, or a refresh token for tokens. |
| POST /oauth/revoke | Revokes a token. |
| POST /identity/email/start | Sends a one-time code to an email address, through the outbox. |
| POST /identity/email/verify | Checks the code, completing the passwordless sign-in. |
| POST /identity/password | Checks an email and password, completing the password sign-in. |
| POST /identity/passkey/begin and /finish | The two halves of a passkey sign-in or registration. |
| GET /identity/me | Returns the caller's user_id and grant roles. |

The sign-in endpoints under /identity are only ever used by the sign-in screen itself, inside the authorization or device flow. They never hand a token straight to whoever called them, which means no client, and especially no agent, ever touches a person's password or one-time code.

### How an agent logs in

An agent gets a token the same way any other application does, and the person stays in control of the only step that matters: proving who they are. An agent running somewhere without a browser uses the device flow.

1. **Discover.** The agent fetches /.well-known/oauth-authorization-server on the domain it wants to work with, and learns where everything is for that realm.
2. **Register.** The agent calls /oauth/register with its name and gets a client_id. The name is what the person will see when asked to approve it.
3. **Start a device sign-in.** The agent calls /oauth/device and gets back a device code, a short user code like WDJB-MJHT, and a link.
4. **The person signs in.** The agent shows the link and the user code to the person. The person opens the link, signs in with an emailed code, a passkey, or a password, checks that the user code matches, and approves the agent by name.
5. **Collect the token.** Meanwhile, the agent polls /oauth/token with its device code, and once the person approves, it receives an access token and a refresh token, marked as acting for an agent.
6. **Work.** The agent calls routes with the access token as a bearer token. The secure context carries the person's user_id, so the agent can do exactly what the person can do, and nothing more.
7. **Refresh and revoke.** When the access token expires, the agent trades its refresh token for a new pair, and the old refresh token stops working. When the person disables the agent or their account, the next request fails.

An agent with a browser, or a web application, uses the authorization code flow with PKCE instead, which differs only in steps 3 to 5: the person signs in at /oauth/authorize, and the agent exchanges the resulting code at /oauth/token. In both flows, the password, the emailed code, and the passkey stay between the person and the identity service, and every step lands in the audit table.

## Sign-in screen requirements

The sign-in and consent screens are where phishing happens, because they are the one place a person is asked to trust something. Since agents and applications can register themselves, the screens must never let a name do the work of an identity. These are requirements on the identity service, and reskinning may change colors, fonts, and logos, but never remove any of them.

- **The screens live on the identity service's own origin.** They are never embedded in a frame, and no box can serve anything under /oauth or /identity, so a box can't host a convincing copy of the sign-in page.
- **A client is shown by where it comes from, not just what it calls itself.** The consent screen names the domain being signed in to, and shows the client's name next to its redirect host, or "a device without a browser" for the device flow, along with when it registered. A dynamically registered client is marked as unverified, so "Bob's Plumbing Official App" from an unknown host looks exactly as suspicious as it is.
- **Consent says what is being handed over, in plain words.** The person sees that the client will act as them, along with their grant roles, so approving an agent while holding owner/bobs_plumbing reads as handing over the keys to Bob's Plumbing, because it is.
- **The device code is typed, not trusted.** The person types the user code on a page they reached themselves, rather than following a link with the code already filled in, and the page warns them to continue only if they started this sign-in themselves. A device code sent by somebody else is the classic way this flow gets phished.
- **Passkeys come first.** A passkey is bound to the identity service's origin, so it can't be replayed on a look-alike site, which makes it the most phishing-resistant way in. Emailed codes and passwords stay available, but the screen offers the passkey first and invites people to add one.
- **Emailed codes say what they are for.** The email names the client asking for the sign-in and warns never to share the code. It carries a code to type into the page the person already has open, never a link that signs them in on its own.
- **The screens reveal nothing about who has an account.** Starting an emailed code, failing a password, and asking for a sign-in with an unknown address all look and respond the same way, so the sign-in page can't be used to find out who is a customer.
- **Every new session is visible.** The person gets an email when a new client or agent is approved, and their account page lists every active session with a way to revoke it. The email tells them to review sessions on the account page rather than linking to a button, since a link in an email is exactly what a phisher would send.
- **Repeated failures slow down.** Codes, passwords, and device code polling are rate limited per address and per client, and a code locks after a handful of wrong attempts.
