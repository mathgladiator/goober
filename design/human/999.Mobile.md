# The Mobile Terminal

The terminal is a native app, called dumb, that runs on Android, Linux, and Windows, with iOS stubbed. It is a dumb personal terminal into one goober domain: it holds no logic of its own, and the backend decides everything it shows. It does three things for one person, the executive:

* **Alarms.** It schedules alarms and notifications locally on the phone from rules the backend sends, like "15 minutes before sunset today", and keeps the phone's schedule in step with the backend through an hourly pull, plus a push nudge when there is one.
* **Dashboards.** It renders multi-page JSON dashboards, with settings the person can change.
* **The approval queue.** It shows what agents are waiting on, with a rich-text description, and sends back the person's decision: approve, deny, or approve with feedback.

This document is the contract goober has to keep for that app. Most of it is ordinary goober: an OAuth client, a box with HTTP routes, a types document, and some data. A few parts touch the host, and a few places where the app and the rest of this design disagree today are listed at the end, each with options and a recommendation.

The app's own description of the protocol lives in its repository at `docs/PROTOCOL.md`. Where the two differ, this document is what goober commits to, and the app changes to match.

## The shape

The terminal talks to exactly one primary domain, so it lives in exactly one identity realm, as described in the identity design. Everything it does goes through three surfaces:

| surface | owned by | what the terminal uses it for |
| --- | --- | --- |
| /.well-known/ and /oauth/ | The host | Discovering the realm, and signing the person in with OAuth 2.1 and PKCE. |
| /identity/ | The host | The sign-in screens, inside the system browser, never inside the app. |
| /terminal/v1/ | A box, called terminal here | The snapshot, dashboards, decisions, device registration, and alarm events. |

The terminal is not a host feature. It is a product, built on a box like any other, and the host only has to keep the identity contract that every native app relies on. The /terminal/ prefix keeps its routes out of the way of the product's own routes on the same domain, since the domain is the primary key of every conflict, as described in the conflicts design.

## Who the terminal is

The terminal is the person's own hands, not an agent. This is the most important requirement in the document, because the approval queue only means something if an agent can't use it.

* **Its tokens are person tokens.** A token issued to the terminal must have is_agent = 0 in the tokens table, and must not carry an agent's !client_id, so the host treats every call as the person in a browser would be treated.
* **Its routes refuse agents.** No route under /terminal/v1/ sets "agents": true. The MCP design already refuses agent tokens on HTTP routes by default, so an agent acting for the executive, holding exactly the executive's roles, still can't call the decision route. No agent can approve anything, which matches the operator API's rule for agents.
* **Agents get their own box.** The agents that create approval requests do it through their own MCP tools, in their own box, whose data strategies can insert a request but have no write path to its status. The checker can then prove that no agent can approve its own request, as described in the MCP design's section on isolating agents.

How the host decides that a client acts as a person rather than as an agent isn't settled in the identity design, and it has to be before the terminal can work. It is the first open decision below.

## Signing in

The terminal is a public OAuth client in the sense of RFC 8252, using the authorization code flow with PKCE from the identity design. It never shows a sign-in form of its own. It opens the system browser (a Custom Tab on Android), and the person signs in on the identity service's own origin.

| requirement | detail |
| --- | --- |
| Metadata | GET /.well-known/oauth-authorization-server returns authorization_endpoint, token_endpoint, and revocation_endpoint for the realm, as RFC 8414 describes. |
| PKCE | S256 only. The terminal always sends code_challenge and code_challenge_method=S256. |
| State | The host returns the state parameter unchanged. The terminal refuses a response whose state doesn't match. |
| Scope | The terminal sends no scope, since grant roles do that job here. The host must accept an authorization request without one. |
| Client | The terminal is a public client with no secret. Its client_id is known before sign-in (see the open decisions). |
| Redirect, mobile | `com.mathgladiator.dumb:/oauth/callback`, a private-use URI scheme, as RFC 8252 §7.1 describes. |
| Redirect, desktop | `http://127.0.0.1:{port}/callback`, a loopback listener on an ephemeral port chosen per sign-in, as RFC 8252 §7.3 describes. |
| Token response | JSON with access_token, token_type "Bearer", expires_in, and refresh_token. The terminal refuses any other token type. |
| Refresh | grant_type=refresh_token. Refresh tokens rotate on every use, as the identity design says, so every refresh response carries the new refresh token. |
| Revocation | On sign-out, the terminal posts its refresh token to revocation_endpoint. |
| Failure | Any 4xx from the token endpoint during a refresh means the session is over. The terminal throws its tokens away and asks the person to sign in again. |

The sign-in screen requirements apply to the terminal like any other client, with one detail the identity design doesn't cover yet: a private-use scheme has no host. The consent screen shows the client's name next to its redirect host, so for a scheme like `com.mathgladiator.dumb:` it must show the scheme itself, and for a loopback redirect it must say "an app on this computer", so the person can see what they are handing over.

The terminal enforces TLS on its side: every URL in the metadata must be https, except loopback (localhost, 127.0.0.1, [::1], and 10.0.2.2 for the Android emulator), which is for local development. On Android, only system certificate authorities are trusted, so a goober domain needs a publicly trusted certificate, which Caddy already provides. Redirects are not followed, so the person must enter the tenant's primary domain, not one of its redirect domains.

## Calling the API

Every call after sign-in carries `Authorization: Bearer <access token>`, and the host checks it before any box wakes up. The terminal sends `Accept: application/json` and never asks for text/html, so the host answers a missing or expired session with a 401 rather than a redirect to the sign-in page, as the local identity design does for non-browser callers.

| status | what the terminal does |
| --- | --- |
| 2xx | Success. |
| 401 | Refreshes once and retries. A second 401, or a failed refresh, ends the session. |
| 403, 404 | Shown as an error. For a queued decision or event, the item is dropped. |
| 409 | For a decision: the approval was already resolved. The item is dropped, and the person is told. |
| 408, 429, 5xx, network failures | Retried later. Queued POSTs stay in the terminal's outbox. |

The terminal identifies itself as `User-Agent: dumb-terminal/<version> (<platform>)`, where platform is android, linux, windows, or ios, so the operating panel's client classifier can file it under mobile app.

## The routes

The terminal box declares these routes, all under /terminal/v1/, and all with the same requirements, which name whoever holds the executive's seat. In a personal realm that is "owner", but the role is the product's choice.

| route | verb | body | response | purpose |
| --- | --- | --- | --- | --- |
| /terminal/v1/me | get | | json:Me | Who is signed in, for the settings screen. |
| /terminal/v1/config | get | | json:TerminalConfig | The backend's display name and push configuration. |
| /terminal/v1/sync | get | | json:Snapshot | The full snapshot: alarms, pending approvals, dashboards, and the default location. |
| /terminal/v1/dashboards/{dashboard_id : string} | get | | json:Dashboard | One dashboard, with its settings as query parameters. |
| /terminal/v1/approvals/{approval_id : int64}/decision | post | json:DecisionRequest | empty | The person's decision on one approval. |
| /terminal/v1/devices | post | json:DeviceRegistration | empty | Registers this install, its timezone, and its push token. |
| /terminal/v1/events | post | json:ClientEvent | empty | Reports that an alarm fired, was snoozed, or was dismissed. |

```json
{
	"box": "terminal",
	"mission": "Let the executive's own devices read alarms, dashboards, and pending approvals, and record the executive's decisions.",
	"domains": ["example.com"],
	"types": "terminal.openapi.json",
	"routes": {
		"http": {
			"/terminal/v1/sync": {
				"get": {
					"name": "terminal_sync",
					"response": "json:Snapshot",
					"requirements": [["owner"]]
				}
			},
			"/terminal/v1/approvals/{approval_id : int64}/decision": {
				"post": {
					"name": "terminal_decide",
					"body": "json:DecisionRequest",
					"max-body-bytes": 8192,
					"request-headers": ["Idempotency-Key"],
					"response": "empty",
					"requirements": [["owner"]]
				}
			}
		}
	}
}
```

The manifest above is an illustration, not the product. It shows the two properties that matter: nothing says "agents": true, and the decision route declares the one request header it reads.

## Types on the wire

Every body and response is a named type in the box's types document, as described in the JSON design, and the terminal is built to live inside that strict subset.

* **Objects are closed.** Request bodies must carry exactly the fields of their type. The terminal never sends a field its type doesn't name. On responses, the terminal is a tolerant reader and ignores fields it doesn't know, so adding a field to a response is safe in both directions.
* **Variants are flat.** The subset refuses oneOf, so the terminal doesn't need it: an alarm trigger and a dashboard widget are each one flat object with a `type` field saying which of its optional fields matter. Unknown widget types render as a placeholder, and an unknown trigger type rejects only that alarm.
* **Arrays are bounded.** Every array carries a maxItems in the types document. The terminal accepts anything up to those bounds.
* **Ids are strings.** int64 ids cross JSON as strings, as the primary keys design says, and the terminal treats every id as an opaque string.
* **Times are strings.** Every instant is an RFC 3339 string in UTC, like `2026-10-27T13:00:00Z`. Local wall-clock times are `HH:mm`, dates are `YYYY-MM-DD`, and time zones are IANA names, like America/Chicago.
* **Enums are lowercase strings.** An unknown value of an enum with a default falls back to that default, like risk falling back to unknown, rather than failing the item.
* **Names are snake_case.** Every field the terminal reads or writes is lowercase with underscores.

The snapshot is decoded one item at a time: a malformed alarm, approval, or dashboard reference is dropped and listed on the terminal's settings screen, and everything else still works. A box should never rely on that. It is a safety net for a mistake, not a way to send partial data.

### Snapshot

The snapshot is the whole truth as of now. It isn't a delta: an alarm missing from the snapshot is cancelled on the phone, and an approval missing from it leaves the queue.

| field | type | notes |
| --- | --- | --- |
| server_time | instant | Optional. |
| alarms | array of Alarm | At most 64, which is iOS's limit on pending local notifications. |
| approvals | array of Approval | Pending only, newest first. |
| dashboards | array of {id, title, subtitle} | The menu of dashboards; each one is fetched on its own. |
| default_location | {lat, lon, label} | Optional; used by solar alarms that carry no location of their own. |

A GET whose data comes from strategies gets an ETag from the host for free, as described in the HTTP design. The terminal doesn't send If-None-Match yet, but the snapshot route should keep its answer cacheable this way, so it can later.

### Alarms

An alarm is a rule, not a time. The phone computes each concrete occurrence itself, from the rule, the device's clock, and its time zone, and computes them again after every sync, every firing, every reboot, and every change of clock or time zone. The backend never has to know when a phone will ring.

| field | type | notes |
| --- | --- | --- |
| id | string | Stable across snapshots; the phone keys its bookkeeping by it. |
| kind | "alarm" or "notification" | "alarm" is alarm-clock style: full screen over the lock screen, the alarm audio stream, and it rings until dismissed. "notification" is an ordinary notification. |
| title, body | string | Plain text, not markdown. Hidden characters are made visible. |
| priority | "low", "default", or "high" | For notifications only; selects the notification channel. |
| snooze_minutes | int32 | Default 9, clamped to 1 through 120. |
| enabled | boolean | Default true. |
| until | instant | Optional; no occurrence after it. |
| trigger | Trigger | When it fires; see below. |

| trigger type | fields that matter | fires |
| --- | --- | --- |
| at | at | Once, at that instant. |
| daily | time, days, date, tz | At a local wall-clock time on the listed days (MON through SUN, empty for every day), or only on date. |
| solar | event, offset_minutes, location, days, date, tz | At a solar event plus an offset, like sunset minus 15 minutes. |

The solar events are sunrise, sunset, civil_dawn, civil_dusk, nautical_dawn, nautical_dusk, astronomical_dawn, astronomical_dusk, golden_hour_start, golden_hour_end, and solar_noon. A solar alarm's location falls back in this order: its own location, then the snapshot's default_location, then a location the person set in the terminal, then the device's last known location. Daylight saving follows the time design: a local time that doesn't exist fires at the next time that does.

"Fire 15 minutes before sunset today", set in the morning, is a solar trigger with offset_minutes -15 and date set to today. The time design already has the natural way to produce that: a data-driven cron timer at 6am in each person's timezone, read from the timezone their device registered, writes the day's alarm row, and the next sync carries it to the phone. The timer acts about the person, through data, never as them.

Alarms that fire while the phone is off are not replayed. One-shot alarms in the past are never scheduled.

### Approvals

| field | type | notes |
| --- | --- | --- |
| id | int64, as a string | |
| task | string | Plain text title. |
| description | string | Markdown, in the restricted dialect below. |
| requester | string | Which agent asked, for display. |
| risk | "unknown", "low", "medium", or "high" | High asks the person to confirm before approving. |
| created_at, expires_at | instant | Optional. |
| actions | array of decision | Which decisions to offer; all three by default. |

A decision is one of:

| decision | feedback |
| --- | --- |
| approve | Not sent. |
| deny | Optional. |
| approve_with_feedback | Required; at most 4000 characters. |

The decision body is `{ decision, feedback, decided_at, idempotency_key }`, and the same key travels in the Idempotency-Key header. The terminal keeps every decision in a persistent outbox and retries it until the backend answers with a 2xx, or a 4xx other than 401, 408, or 429.

That makes retries normal, so the decision route has to be idempotent on its own:

* **A repeated key is a success.** When the approval was already decided with the same idempotency_key, the route answers 2xx and changes nothing. Only a different key on an already-decided approval gets a 409. Otherwise a decision that landed, but whose answer was lost, comes back as "rejected", and the person is told something false.
* **The decision is the write.** The route patches the approval's status, feedback, and key in one write set, conditional on the approval still being pending.
* **The effect rides the outbox.** Telling the agent is an outbox element to an internal route on the agent's box, like /approvals/{approval_id}/decided, marked "idempotent": true and listing terminal in its callers. The agent hears the decision if and only if it committed, at least once, and in practice once.

### The markdown dialect

Approval descriptions are written by agents, and agents read untrusted text, so a description is untrusted by construction. It can carry a prompt injection aimed at the person, a Trojan Source reordering, or a link that lies about where it goes. The terminal therefore doesn't trust any rendering the host could do: it takes the markdown as a plain string inside the JSON, lints it, and renders it natively, with no HTML engine, no web view, and no network access.

The box must send descriptions as a string field of a json response, never as a "response": "markdown" route, since content negotiation would hand a browser the host's HTML rendering and hand the terminal something it never asked for.

| supported | not supported, shown as literal text |
| --- | --- |
| Headings, paragraphs, **strong**, *emphasis*, ~~strike~~, `code`, fenced code, bullet, numbered, and task lists, block quotes, rules, pipe tables, and [links](https://...) to https | Raw HTML, images (never fetched), autolinks, reference links, and HTML entities |

| quarantines the description | flagged, but still rendered |
| --- | --- |
| Control characters, bidi overrides, zero-width and other invisible characters, Unicode tag characters, more than 64,000 characters or 2,000 lines; links to javascript:, data:, file:, or intent:, links with user@host, internationalized or punycode hosts, link text naming a different domain than the link's target, and percent-encoded control characters | Raw HTML, images, http: or IP or relative links (not tappable), words mixing Latin with Cyrillic or Greek, private-use characters, very long lines, and unclosed code fences |

A quarantined description is shown as raw monospace text, with every hidden character made visible, like ⟦U+202E⟧, and approving it takes an extra confirmation. Every tappable link shows its real host beside it, and tapping it asks first.

A box may run the same checks when an agent writes a description and refuse the bad ones early, which is cheaper for everybody, but the terminal checks regardless.

### Dashboards

| field | type | notes |
| --- | --- | --- |
| id, title, subtitle | string | |
| generated_at | instant | Shown as "as of". |
| refresh_seconds | int32 | Optional; the terminal re-fetches the dashboard on this period while it is on screen, and never more often than every 15 seconds. |
| settings | array of Setting | Knobs the person can turn: `select` with options, or `toggle` with "true" and "false". |
| pages | array of Page | Each page has an id, a title, a column count (a maximum; narrow screens use fewer), and its widgets. |

The terminal sends the selected value of every setting as a query parameter of the same name, as a string, and remembers the selection per dashboard. A box only sees the query parameters its route declares, as described in the HTTP design, so every setting a dashboard offers must also be declared in that route's query block. That is the reason for one literal route per dashboard, like /terminal/v1/dashboards/exec, owned by whichever box owns the data, rather than one catch-all route whose query block has to know every dashboard.

| widget type | fields |
| --- | --- |
| metric | label, value, unit, delta, delta_good, status, sparkline, detail |
| line_chart, bar_chart | series of {name, points}, labels |
| table | columns, rows |
| list | items of {title, subtitle, trailing, status} |
| progress | label, progress from 0 to 1, status, detail |
| status | label, status of ok, warn, crit, or info, detail |
| markdown | text, in the restricted dialect |

Every widget also has a type, an optional title, and a span in columns, defaulting to 1.

### Devices and events

DeviceRegistration is `{ platform, app_version, device_name, timezone, push_token }`, with push_token optional. The terminal sends it after its first successful sync and again whenever its push token changes. The box keeps one row per install, scoped by {!user_id}, and the timezone in that row is what data-driven timers read for "6am for this person."

ClientEvent is `{ type, at, idempotency_key, alarm_id, minutes }`. type is alarm_fired, alarm_snoozed, or alarm_dismissed, and minutes is present only for a snooze. Events ride the terminal's outbox like decisions do, so the route stores them with a unique key and answers 2xx for a repeat. Events are for the backend's own curiosity. Nothing about the phone's schedule depends on them.

## Push

Push is only a nudge. A push message means "sync now", and nothing else: the terminal ignores the payload, never displays it, and responds by pulling the snapshot. That is the bus design's rule, a signal instead of data, carried one hop further, to a phone. A lost push costs latency, never correctness, since the hourly pull catches everything.

* **What the terminal needs.** TerminalConfig carries the Firebase client configuration the app initializes at runtime: project_id, application_id, api_key, and sender_id. None of these are secrets. With no push configuration, the terminal relies on the hourly pull alone.
* **What the backend sends.** A data-only FCM message, `{ "type": "sync" }`, with a collapse key of `sync`, so a burst of changes becomes one wake-up. It is sent to every registered push token of the person whose snapshot changed.
* **When.** Whenever a write set commits that changes what a person's snapshot would say: a new approval, an approval resolved somewhere else, or a changed alarm.
* **How.** As an outbox element to FCM's HTTP v1 API, so a push is sent if and only if the change committed. FCM's sending credential is a Google service account, which is the host's to hold, as described in the network and keys designs.
* **Dead tokens.** When FCM answers that a token is unregistered, the result route deletes that device's push_token.

## Timing and load

| | |
| --- | --- |
| Hourly pull | Android WorkManager, with a network constraint, so it can drift within Doze windows. |
| On open | A sync whenever the app comes to the foreground and the last one is more than 5 minutes old. |
| After a decision | An immediate sync, so the queue reflects the decision. |
| On push | An immediate sync. |
| Desktop | Every hour while running. Desktop alarms only fire while the app runs, from the tray. |

One person with a few devices produces a few dozen snapshot reads an hour. The snapshot route still deserves a queue policy and a bounded snapshot, since it is a public route with a person behind it.

## Local development

The goober host's local mode listens on 127.0.0.1 over plain HTTP. The terminal accepts plain HTTP only for localhost, 127.0.0.1, [::1], and 10.0.2.2, so a phone reaches a local host over USB with `adb reverse tcp:8080 tcp:8080` and the URL `http://localhost:8080`, which local mode routes to the platform domain. The terminal does not accept `$domain.localhost` names today.

The app's repository carries a dev server at `tools/dev-server/server.py`, which implements this contract strictly, answering violations the way goober would and listing them on its console, and an end-to-end test that drives the real client against two of them at once.

## Prerequisites in the host

The terminal needs the OAuth half of the identity design. The first host only has emailed codes and cookie sessions, so before the terminal can sign in, the host needs:

* /.well-known/oauth-authorization-server, /oauth/authorize, /oauth/token with authorization_code and refresh_token grants, and /oauth/revoke, from the identity design's implicit API.
* Bearer tokens accepted on box routes, resolved into the same secure context a cookie session gets.
* The clients table, with a way to register the terminal as a person's client, from the first open decision.
* Loopback redirects with any port, for the desktop app, from the second open decision.

## Where the app and this design disagree today

The app was first written against its own mock backend. These are the places where it and the rest of this design didn't line up. Each one is a decision for the human, and the recommendation is listed first. The app has since adopted the recommended app-side changes for decisions 3, 4, and 5: RFC 8414 discovery, /terminal/v1/me and /terminal/v1/config, and a closed ClientEvent. Decisions 1, 2, 6, and 7 still need goober.

### 1. Person or agent

The identity design marks a token is_agent when "the client acts on the person's behalf", which describes every OAuth client, including the terminal. If the terminal's tokens are agent tokens, every terminal route needs "agents": true, and then every agent of the person can call the decision route too, which empties the approval queue of its meaning.

* **Recommended: clients say what they are.** The clients table gains whether a client acts as the person or as an agent. Dynamically registered clients are always agents. A person client can only be registered by the realm's owner or by host configuration, and is shown on the consent screen as the realm's own app.
* **Alternative: by flow.** The device flow issues agent tokens, and the authorization code flow issues person tokens. This needs no new column, but any web app an agent controls could use the code flow and pass as the person.

### 2. Loopback redirects

The identity design matches redirect_uris exactly. The desktop app listens on an ephemeral loopback port, as RFC 8252 §7.3 and OAuth 2.1 both expect, so its redirect URI is different on every sign-in.

* **Recommended: any port, for loopback only.** A registered redirect of `http://127.0.0.1/callback` matches any port on 127.0.0.1, and nothing else is relaxed: not localhost, not other hosts, not other paths.
* **Alternative: a fixed port.** The desktop app binds a fixed port, which fails whenever something else holds it.

### 3. Discovery

The app bootstraps today from `GET /.well-known/dumb-terminal`, a document of its own that carries name, api_base, the OAuth endpoints, client_id, and push. /.well-known/ belongs to the host, as described in the reserved routes design, so no box can serve it.

* **Recommended: the app uses what the host already serves.** The app reads /.well-known/oauth-authorization-server for the endpoints, uses the fixed client_id `dumb-terminal`, registered as a person client in the realm, takes api_base as `https://{domain}/terminal`, and reads the display name and push configuration from /terminal/v1/config after signing in. The host adds nothing.
* **Alternative: the host serves /.well-known/dumb-terminal.** It is generated from host configuration, and added to the reserved routes list. This makes one product a host feature, which the design otherwise avoids.

### 4. Who am I

The app calls GET {api_base}/v1/me and reads id, name, and email. The host already offers GET /identity/me, with user_id, email, and roles.

* **Recommended: the terminal box serves /terminal/v1/me**, from {!user_id} and {!email}, so the app depends on one API surface.
* **Alternative: the app reads /identity/me**, and maps user_id onto id.

### 5. Event detail

The app sends ClientEvent with `detail`, a map of strings to strings. The JSON design refuses open objects, so that body would be rejected with a 400 before the box wakes up.

* **Recommended: the app sends minutes**, an optional int32, in place of detail, as this document specifies. Snoozing is the only event with a detail today.

### 6. Host approvals

The approval queue in this document is for product approvals: what a product's agents want to do. The approvals design's queue, of box versions, policies, schemas, and migrations, is a different queue, and the operator API says that approving a version policies don't cover has no API, and happens only in the panel's UI, by a person. The panel also lives on a private port by default, which a phone can't reach.

* **Recommended: product approvals only.** The terminal never approves host approvals. It may later show a count of host approvals waiting, as a reminder to open the panel.
* **Alternative: the terminal as a panel surface.** It would sign in as a host identity on the platform domain and be granted the panel's approval power. That contradicts both the operator API's rule and the panel's blast radius protection, and would need both changed on purpose.

### 7. Push credentials

FCM's HTTP v1 API authenticates with a short-lived Google OAuth token minted from a service account key. The network design's host-held credentials don't yet say how a credential that has to be exchanged for a token works.

* **Recommended: a push capability**, like push-notify@1 from the stability design, with an FCM provider whose credential handling lives in the host. APNs for iOS becomes a second provider behind the same capability.
* **Alternative: an adapter box** that holds the exchange logic and is called through the outbox.

### 8. Many backends

The terminal holds any number of servers, each one domain, one realm, and one session, the way a chat client holds servers. Approvals from all of them are shown together. This needs nothing from goober, since it is exactly identity being per domain, seen from the client. Alarms from different servers are namespaced on the device, so their ids never collide.

The one cost is push. A device has one FCM token per Firebase project, so only servers that share a project can push to it, and every other server relies on the hourly pull. A shared push relay for all of a host's domains, so that one host means one project, is a question for the push capability in decision 7.

## The invariants

* **The terminal is the person.** Its tokens are person tokens, and no terminal route accepts an agent.
* **No agent can decide an approval.** Agents create requests through their own box, which has no write path to a request's status.
* **The snapshot is the whole truth.** It replaces what the phone holds, and anything missing is cancelled.
* **Alarms are rules, and phones compute the times.** The backend never schedules a phone's ring; it states when, and the phone works it out.
* **Decisions are idempotent by key.** A repeated key answers 2xx and changes nothing, and only a different key on a decided approval gets a 409.
* **Descriptions are untrusted.** They cross as markdown strings inside JSON, and the terminal lints them and renders them natively, without HTML.
* **Push is a nudge, never a message.** It carries no data, and losing one costs only time.
* **Wire types stay inside the strict subset.** Closed objects, bounded arrays, flat variants, and string ids.
