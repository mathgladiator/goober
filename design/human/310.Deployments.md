# Box Deployments

A traditional developer would have a GitHub repo with a build script of sorts that pops out a WASM module, and they would be maintaining a manifest. We like this model for humans, and deployment is simply the developer running another script that uploads the new version of both the WASM module and the manifest as an atomic pairing, such that a new version id is minted. A version is minted because each new version is a new artifact to validate, approve, and audit.

Responsible developers will have a staging environment to test in, but we want to be modern, such that we only test in production.

Not only do we test in production, we will enable scientific measurement to compare boxes, for an operator or an AI. We offer two primary modes. The first is shadowing traffic, such that the shadow box gets the same requests, but all of its side effects are only logged, while the real box's side effects are executed, and then the two are compared. This works well for data writes, but it is complicated for service calls, so whether service calls are enabled or disabled in a shadow will be a manifest property, both on the service and in a per-route allow list. By default, service calls fail in a shadow box, which complicates any automated testing.

This will give us system safety and permission measures, but it will not catch failures of product correctness and quality. It can produce logs about what changes between versions, and we internalize the comparison structure and try to pair the data flowing in with the data flowing out, such that we produce a report of what happened and what was different. The key requirement is that this report never leaks user data, so it is a noisy process, and agents get the reports. As part of operations, certain operations can be whitelisted in the configuration to see the raw data changes for debugging, so that the agent can be informed.

Bold people may just let the agent see data, which would be a reason to operate a staging environment. We want to encourage proper engineering, but accept that people may just happen to fuck around with production because FUN. The nice thing about a staging environment is that agents can be given full control to change everything, and then the human has a simpler deployment surface to audit in batch.

The other mode is A/B testing, which lets requests be split based on a hash of the user id (or, for public services, a hash of the IP), such that we can send 1%, 5%, and so on to the new version and see how the metrics move. This introduces a new view of the two boxes, where the changes between the two versions are visualized, for both their operational load and their interior metrics.

The goal is to maximize the science we can leverage, and to provide a foundation for agentic optimization using modern mesh tooling.

## The artifact

A version is everything that defines what a box can do, bundled together and named by the hash of its contents:

- the manifest,
- the WASM module,
- the types document,
- the .schema files,
- the templates and static content embedded in the manifest,
- the pinned OpenAPI documents and provider specs for every external service,
- and the pins for everything else outside the box that can change it, as described in the stability design.

Because the version id is the hash, the same bundle always gets the same id, and two versions are different if and only if something that defines the box changed. Nothing in a version can be edited after it is minted; a change is always a new version.

## The life of a version

```
uploaded → checked → approved → shadowing → splitting → live → retired
                │          │           │            │
                └ refused  └ declined  └ abandoned  └ rolled back
```

| state | what happens | who moves it on |
| --- | --- | --- |
| uploaded | The script, or an agent through the operations MCP, sends the bundle to the host, and the version id is minted. A version that never receives any traffic can be deleted as a bad push, since it has no liability. | The host, immediately. |
| checked | The checker runs: types, requirements, substitution rules, worst cases, bundle reports, type compatibility with the live version, and which other boxes are affected. | The checker; a failure ends the version as refused. |
| approved | A human reads the diff and the checker's reports in the operating panel and approves or declines the version, unless the manifest's policies cover every change, in which case it is approved by policy. | A person with the right role, or the box's policies. |
| shadowing | The version receives a copy of live traffic, and its effects are logged and compared, never executed. | An operator or an agent, within its permissions. |
| splitting | The version serves a share of real traffic, with real effects, next to the live version. | An operator or an agent, within guardrails. |
| live | The version serves all traffic. | Reaching 100%. |
| retired | The version stops receiving traffic, drains, and is kept so it can be brought back. | The next version going live, or an operator. |

Upload, check, and approval are the gate, and the approvals design describes how that gate works: a readable diff of the manifest, policies that let some kinds of change through without a human, and deployment modes (go, slow, and shadow) that watch a version's health and roll it back on their own. Shadowing and splitting are the science, and both are optional: a version can go straight from approved to live, for a person who just wants to ship.

Uploading is a host feature on the operations surface, so the script a developer runs and the agent that ships through /goober-operations-mcp use the same door, with the same audit.

## Staging

A staging environment is just another goober host, configured with its own domains and its own data. It is where agents can be given full control: they can upload, approve, shadow, and split freely, because nothing there belongs to a real person. When a set of versions is ready, the human promotes them to production as a batch, and production's approval queue sees the same checker reports, now for versions that have already been exercised.

Staging data should be synthetic, or a copy with personal data removed. A copy of production with real personal data in it is just production with weaker guards.

## Shadowing

A shadow version receives a copy of every request that the live version serves for the routes being shadowed. It runs completely, with its own isolates, but the host never commits what it does: its write set, its outbox elements, its grants, and its uploads are all recorded and then thrown away. The live version's response is the one the person receives; the shadow's response is only compared.

Service calls need a decision, since a shadow can't be allowed to send an email, but it may need to read the weather. The manifest decides, both on the service and per route:

```json
{
	"external": {
		"forecasts": {
			"openapi": "weather.v2.openapi.json",
			"base": "https://api.weather.example",
			"credentials": "keys/system/weather",
			"shadow": "allow",
			"methods": {
				"getForecast": {}
			}
		},
		"mail_out": {
			"capability": "send-email@1",
			"provider": "amazon-ses",
			"credentials": "keys/tenant/{!tenant}/ses",
			"shadow": "fail",
			"methods": {
				"send": {
					"effect": "outbox"
				}
			}
		}
	},
	"routes": {
		"http": {
			"/jobs/{job_id : int64}/forecast": {
				"get": {
					"name": "job_forecast",
					"response": "json:Forecast",
					"requirements": [["owner/{!tenant}"], ["admin/{!tenant}"], ["member/{!tenant}"]],
					"shadow-calls": ["forecasts"]
				}
			}
		}
	}
}
```

| shadow setting | in a shadow |
| --- | --- |
| fail | The call fails, as if the service were down. This is the default. |
| allow | The call really happens, which is only permitted for methods whose effect is "none." |

A call is only made in a shadow when the service says "allow" and the route lists the service in shadow-calls. Effectful calls can never be allowed, so whatever a shadow does, the world can't tell it ran. Since service calls fail by default, a shadow of a box that depends on them will see errors that the live version didn't, which is why the comparison report separates "different because of a failed call" from "different on its own."

## The comparison report

For every shadowed request, the host pairs what flowed into both versions with what flowed out of both, and reports the differences without ever showing the data itself:

- **Responses:** whether the keyed response hashes from the operating panel matched, and how status codes and latency differ, per route.
- **Writes:** which tables and columns each version would have written, and how many rows, but not the values.
- **Effects:** which outbox elements, grants, and uploads each version would have produced, by destination and method, but not their contents.
- **Counters:** how every counter moved in each version, which shows which branches the new version reaches that the old one didn't, and the reverse.
- **Cost:** CPU, memory, and bytes per request for each version.

The report is noisy by design. Any difference seen in fewer than a minimum number of requests is folded into "other," so a report can't single out one person's request, and agents can read reports freely because there is nothing personal in them.

When a difference needs to be understood, an operator can whitelist specific routes, for a limited time, so that their raw differences are visible to a named person or agent. Every raw view is recorded in the audit, and the whitelist expires on its own, so debugging access never quietly becomes a standing permission.

## Splitting traffic

Splitting sends a share of real requests to the new version, which really commits and really sends, so it comes after shadowing has said the version behaves. Requests are assigned by a stable hash, so a person stays on the same version for the whole experiment:

| caller | split by |
| --- | --- |
| A signed-in user | A hash of the domain and user_id, so the same person always lands on the same version within a realm. |
| An anonymous caller on a public route | A hash of the IP address. |
| A timer | A hash of the timer's key. |
| Another box | The same version as the request that caused the call, carried through the trace. |

The split moves up a ladder, like 1%, then 5%, 25%, 50%, and 100%, and each step can carry guardrails: if the new version's error rate, p99 latency, or cost per request moves past a threshold relative to the live version, the host stops the ramp and moves the traffic back on its own. Rolling back is instant, because the old version is still running.

Two versions serving the same data at once must agree on its shape. The checker refuses to split between versions whose schemas or types are incompatible, using the same compatibility rules as the JSON design, so a split never has one version writing rows the other can't read.

The operating panel shows both versions side by side: the same box graph, with heat, weight, and bandwidth pressure for each, and the counters and rollups of both, so the difference between them can be felt rather than inferred.

## The traffic controller

Every split is run by the traffic controller, a host feature the operator drives from the operating panel. It holds the traffic plan for every URL that more than one thing could answer: two versions of the same box, or, after an approved conflict, two different boxes. A plan says which versions or boxes answer, at what share, and on what schedule, and the controller moves traffic along it, applying the guardrails above.

Manifests never say anything about traffic. A version that contests another box's URLs is rejected unless it arrives through approval with a traffic decision, as described in the conflicts design: hold, A/B test, slow roll out, or cut over. That is how a large box gets peeled apart into small ones, one URL at a time, without any URL ever answering nothing, and it keeps every decision about who answers what in the operator's hands.

## Agentic optimization

With versions, shadows, reports, and splits, an agent has everything it needs to improve a box scientifically: it can propose a version, shadow it, read the report, ramp a split within the guardrails an operator set, and roll back when the numbers say so. A human still approves every version, since that is where the box's shape is decided, but the human no longer has to babysit the experiment. Traffic splitting, shadowing, and comparison all live in the host, so no separate service mesh is needed, though the same ideas map directly onto one if a deployment ever grows into it.

## The invariants

- **A version is immutable, and its id is its hash.** Any change is a new version.
- **Nothing serves traffic without approval.** Shadowing and splitting both come after a human approves the version.
- **A shadow never changes the world.** Its writes, effects, grants, and uploads are recorded and discarded, and only calls with no effect can be allowed.
- **Reports never carry user data.** Differences are counted, hashed, and thresholded, and raw views need a time-limited, audited whitelist.
- **A person stays on one version during a split.** Assignment is by a stable hash.
- **Splits only run between compatible versions.** The checker refuses splits across incompatible schemas or types.
- **Rolling back is instant.** The previous version keeps running until the new one is fully live.
