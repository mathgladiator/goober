# Emulating Life with Time

Life is ultimately some change over time. Much like how HTTP is a protocol, we think about time as a new kind of event.

We think about this in two regards. First, there is time driven at the system level, like every second until forever, or every day at 6am in the host's timezone. Second, there is time driven by data within the databases (or within a number of databases). This split is important because a time event has no request context. For the host level, we introduce a timer-like route, since it can either be a cron job in the host's timezone or a periodic wake-up to do something. For data-driven time, we make it a property of a data provider, such that we can query a database for a timezone and use that to build cron jobs, along with a specific key to provide context.

## Host-level timers

A host-level timer is a route under the timer protocol, with the timer's name in place of the path and fire as the verb. It either runs on a cron schedule in the host's timezone, or wakes up periodically.

### Example: a periodic wake-up

A booking product holds a time slot for a few minutes while a customer fills in their details. Every second, it releases holds that have expired.

```json
{
	"routes": {
		"timer": {
			"release-expired-holds": {
				"fire": {
					"name": "release_expired_holds",
					"every-ms": 1000,
					"timeout-ms": 500
				}
			}
		}
	}
}
```

### Example: a cron job in the host's timezone

Every night at 3am, a product clears out abandoned upload sessions.

```json
{
	"routes": {
		"timer": {
			"nightly-cleanup": {
				"fire": {
					"name": "nightly_cleanup",
					"cron": "0 3 * * *"
				}
			}
		}
	}
}
```

Neither timer has a user, so neither has a user_id in its context, and so neither can satisfy a requirement. Timer routes aren't reachable from outside the host at all, so they don't carry requirements or "public"; the host is the only caller. What a timer can touch is limited by its context instead: with no user and no tenant, a host-level timer can only use strategies that resolve from what the timer itself provides.

## Data-driven timers

A data-driven timer comes from a data provider. A strategy declares a schedule, and the host queries the database for each key that should fire, along with whatever that key needs, like a timezone. Each key becomes its own fire, with its own context.

A schedule never templates or computes anything. Every value it pulls from a row is named by a field ending in -field, like zone-field, at-field, and key-field, and provides-fields maps context names to plain field names. The host reads those fields as they are, so any math, like "a day before the appointment," belongs to the box that writes the row, where it is ordinary code rather than a little language hiding in the manifest.

### Example: a daily digest at 6am in each business's own timezone

Every business on the platform gets a summary of today's jobs at 6am in its own timezone, which is different for a plumber in Seattle and a landscaper in Miami.

```json
{
	"data": {
		"sqlite3": {
			"tenants_by_schedule": {
				"schema": "platform3.schema",
				"database": "platform",
				"table": "tenants",
				"pattern": "by_index",
				"index": "active",
				"read": true,
				"schedule": {
					"cron": "0 6 * * *",
					"zone-field": "timezone",
					"key-field": "slug",
					"provides-fields": { "tenant": "slug" },
					"fire": "daily_digest"
				}
			}
		}
	},
	"routes": {
		"timer": {
			"daily-digest": {
				"fire": {
					"name": "daily_digest"
				}
			}
		}
	}
}
```

For each active row in tenants, the host computes the next 6am in the zone held by that row's timezone field, and when it arrives, fires daily_digest with tenant set to that row's slug field. From there, everything works as if a request had arrived on that tenant's domain: tenant-scoped strategies resolve, and the digest is sent through the outbox.

### Example: a reminder the day before an appointment

A one-shot timer can come from a timestamp column rather than a cron schedule. Each appointment gets a reminder 24 hours before it starts. The box computes remind_at when it saves the appointment, so moving the appointment moves the reminder, since the schedule is just the data.

```json
{
	"data": {
		"sqlite3": {
			"appointments_upcoming": {
				"schema": "jobs4.schema",
				"database": "tenant_{tenant}",
				"table": "appointments",
				"pattern": "by_index",
				"index": "remind_at",
				"read": true,
				"write": true,
				"schedule": {
					"at-field": "remind_at",
					"key-field": "id",
					"provides-fields": { "appointment_id": "id" },
					"fire": "send_reminder"
				}
			}
		}
	}
}
```

### Example: the same job across many databases

Every tenant has their own database, and every night, each tenant's overdue invoices should be marked overdue. The schedule lives on a platform-wide list of tenants, and each fire resolves into that tenant's own database.

```json
{
	"data": {
		"sqlite3": {
			"tenants_by_schedule": {
				"schema": "platform3.schema",
				"database": "platform",
				"table": "tenants",
				"pattern": "by_index",
				"index": "active",
				"read": true,
				"schedule": {
					"cron": "30 0 * * *",
					"zone-field": "timezone",
					"key-field": "slug",
					"provides-fields": { "tenant": "slug" },
					"fire": "mark_overdue_invoices"
				}
			},
			"invoices_due": {
				"schema": "billing2.schema",
				"database": "tenant_{tenant}",
				"table": "invoices",
				"pattern": "by_index",
				"index": "due_at",
				"limit": 500,
				"read": true,
				"write": true
			}
		}
	}
}
```

Each fire touches exactly one tenant's database, so each fire is atomic on its own, and a failure in one tenant never stops the others.

### Example: a habit check-in in each person's timezone

A habit tracker emails each person at 8pm in their own timezone, but only if they haven't marked today's habits yet. The schedule comes from the people, the context carries the user_id, and the box decides whether there is anything worth sending.

```json
{
	"data": {
		"sqlite3": {
			"people_by_schedule": {
				"schema": "habits2.schema",
				"database": "habits",
				"table": "people",
				"pattern": "by_index",
				"index": "reminders_on",
				"read": true,
				"schedule": {
					"cron": "0 20 * * *",
					"zone-field": "timezone",
					"key-field": "user_id",
					"provides-fields": { "user_id": "user_id" },
					"fire": "habit_check_in"
				}
			}
		}
	}
}
```

Providing a user_id from a schedule is a powerful thing, since it lets a timer act within a person's scope, so the checker flags every schedule that provides one, and it may only come from a table whose rows the identity service vouches for.

## What a fire is

Every fire, whether from the host or from data, is a request in every way that matters: it has a timeout, a write set that commits atomically when it responds, an outbox, and a budget. The only difference is that its context comes from the schedule rather than from a person. The fire's own details are in the context as well, so a box can tell when it was supposed to run.

| context value | meaning |
| --- | --- |
| timer/name | The name of the timer that fired. |
| timer/key | The key of the row that produced the fire, for data-driven timers. |
| timer/scheduled_at | When the fire was supposed to happen, as int64 milliseconds. |

## The rules of time

| question | answer |
| --- | --- |
| What if the host was down when a fire was due? | Each timer says "missed": "once" to run a single catch-up fire, or "missed": "skip" to wait for the next one. Cron timers default to once, and periodic timers default to skip. |
| What if a fire is still running when the next one is due? | The next one is skipped, so a slow timer never piles up on itself. |
| Can a fire happen twice? | Fires are at-least-once, and each one carries a key made from the timer, the row key, and timer/scheduled_at, so a box can make a repeat harmless, and the outbox uses the same key for its idempotency. |
| What about daylight saving time? | A local time that doesn't exist, like 2:30am on the night clocks spring forward, fires at the next time that does. A local time that happens twice, when clocks fall back, fires only the first time. |
| How many fires can one schedule produce? | As many as there are matching rows, so the checker multiplies the strategy's limit by the fire route's worst case, and a schedule over an unbounded table is refused. |
| What clock does the host use? | The host's own injected clock, so tests can run a year of schedules in a second. |
| Do thousands of 6am fires all start at once? | No, the host spreads fires within a short window, so a timezone's morning is a gentle slope rather than a cliff. |

## The invariants

- **Timer routes are only ever called by the host.** They are unreachable from outside, so they carry no requirements.
- **A fire's context comes from its schedule.** Host-level timers provide only timer values, and data-driven timers provide what their row declares.
- **Every fire is a full request.** It has a timeout, an atomic write set, an outbox, and a budget.
- **Fires are idempotent by key.** Timer, row key, and scheduled time identify a fire, everywhere it goes.
- **Schedules are bounded.** The checker knows the worst case of a schedule before it ever runs.
