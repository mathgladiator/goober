# Emulating Life with Time

Life is ultimately some change over time. Much like how HTTP is a protocol, we think about time as a new kind of event.

We think about this in two regards. First, there is time driven at the system level, like every second until forever, or every day at 6am in the host's timezone. Second, there is time driven by data within the databases (or within a number of databases). This split is important because a time event has no request context. For the host level, we introduce a timer-like route, since it can either be a cron job in the host's timezone or a periodic wake-up to do something. For data-driven time, we make it a property of a data provider, such that we can query a database for a timezone and use that to build cron jobs, along with a specific key to provide context.

## Host-level timers

A host-level timer is a route under the timer protocol, keyed by the timer's name. Timers have no verb, since there is only one thing a timer can do: fire. It either runs on a cron schedule in the host's timezone, or wakes up periodically.

### Example: a periodic wake-up

A booking product holds a time slot for a few minutes while a customer fills in their details. Every second, it releases holds that have expired.

```json
{
	"routes": {
		"timer": {
			"release-expired-holds": {
				"name": "release_expired_holds",
				"every-ms": 1000,
				"timeout-ms": 500
			}
		}
	}
}
```

### Example: a cron job in the host's timezone

Every night at 3am, a product clears out abandoned upload sessions.

```json
{
	"routes": {
		"timer": {
			"nightly-cleanup": {
				"name": "nightly_cleanup",
				"cron": "0 3 * * *"
			}
		}
	}
}
```

Neither timer has a user, so neither has a user_id in its context, and so neither can satisfy a requirement. Timer routes aren't reachable from outside the host at all, so they don't carry requirements or "public"; the host is the only caller. What a timer can touch is limited by its context instead: with no user and no tenant, a host-level timer can only use strategies that resolve from what the timer itself provides.

## Data-driven timers

A data-driven timer has two halves. The data source says what is available to schedule: a strategy whose pattern is by_timer, which the box can't call from its code at all, since it exists only for the timer. The timer route says how to execute it: which source to read, when to fire, and where each fire goes. Keeping them apart means the data source illustrates what the timer can see, and the route informs how it runs and how the work is broken down.

This is also a scheduling problem for the host. It has to wake up, read the source, partition it into one scheduled event per row, compute when each one is due, and keep that plan current as rows change. Each active row becomes its own fire, with its own context, and the host spreads, retries, and records them, so the box only ever sees one item at a time.

A by_timer source names two columns instead of an index: timezone-field, the column holding each row's timezone, so a cron schedule like 6am means 6am for that row, and active-field, the column saying whether the row takes part at all, so turning a reminder off is just updating a row. Every row that is active becomes its own fire, and the entire row is part of the data provided to the fire: the box receives it as a typed structure stamped out from the source's .schema, so there is nothing to map and nothing to forget. The row's primary key is the fire's key.

A timer never templates or computes anything. Every value it pulls from a row is named by a field ending in -field, like timezone-field, active-field, and at-field, and the host reads those columns as they are, so any math, like "a day before the appointment," belongs to the box that writes the row, where it is ordinary code rather than a little language hiding in the manifest. The tenant is a special case, since !tenant is reserved, and the examples below stay within projects rather than leaning on it. When a timer truly needs to set the tenant, tenant-field names the column that holds one, and the host looks that value up in the domain registry before setting !tenant, as described in the reserved identifiers design.

### Example: a daily digest at 6am in each project's own timezone

Every project gets a summary of today's jobs at 6am in its own timezone, which is different for a crew working in Seattle and one working in Miami.

```json
{
	"data": {
		"sqlite3": {
			"projects_for_timers": {
				"schema": "jobs4.schema",
				"database": "jobs",
				"table": "projects",
				"pattern": "by_timer",
				"timezone-field": "timezone",
				"active-field": "active"
			}
		}
	},
	"routes": {
		"timer": {
			"daily-digest": {
				"name": "daily_digest",
				"source": "projects_for_timers",
				"cron": "0 6 * * *"
			}
		}
	}
}
```

For each row in projects whose active column is true, the host computes the next 6am in that row's timezone, and when it arrives, fires daily_digest with the project's row. The box reads the project's jobs, builds the digest, and sends it through the outbox.

### Example: a reminder the day before an appointment

A one-shot timer can come from a timestamp column rather than a cron schedule. Each appointment gets a reminder 24 hours before it starts. The box computes remind_at when it saves the appointment, so moving the appointment moves the reminder, since the schedule is just the data.

```json
{
	"data": {
		"sqlite3": {
			"appointments_for_timers": {
				"schema": "jobs4.schema",
				"database": "jobs",
				"table": "appointments",
				"pattern": "by_timer",
				"active-field": "reminder_on"
			}
		}
	},
	"routes": {
		"timer": {
			"appointment-reminder": {
				"name": "send_reminder",
				"source": "appointments_for_timers",
				"at-field": "remind_at"
			}
		}
	}
}
```

Each active appointment becomes its own fire at its remind_at, carrying the appointment's row. A one-shot timer is a promise the host keeps on its own: it makes sure the fire runs at least once, and when the fire completes, the host itself turns the row's active-field from true to false, in the same bundle as whatever the fire wrote. That is the job of an at-field timer: fire, then disable. The box never has to remember to switch the reminder off, a reminder can't fire twice because the box forgot, and moving the appointment is just setting remind_at again and turning reminder_on back to true. If a source's database is scoped by {!tenant}, the host partitions the work the same way across every tenant in the domain registry, which is the special case where the tenant comes into play.

### Calling into an internal service

A timer can also hand each fire to another box, by naming one of that box's internal routes as its target, instead of running the fire in its own box. The fire becomes an internal call carrying the row, and the receiving route must list the timer's box in its callers, like any internal route, as described in the internal messaging design. When the work belongs to a tenant, the internal route binds to the tenant through a path argument, like /sweeps/{tenant_slug}/overdue, filled from a column of the row.

```json
{
	"routes": {
		"timer": {
			"overdue-sweep": {
				"name": "overdue_sweep",
				"source": "projects_for_timers",
				"cron": "30 0 * * *",
				"target": {
					"box": "billing",
					"path": "/sweeps/{tenant_slug}/overdue",
					"verb": "post"
				}
			}
		}
	}
}
```

If the receiving route is marked idempotent, the host deduplicates repeated deliveries by the fire's key, which is what gives timers global at-least-once delivery across a cluster with the work still happening once.

## Where timer state lives

Timers aren't something a domain turns on. When a by_timer source's database is scoped by {!tenant}, every tenant gets the timer automatically, the moment its domain is in the registry, and no tenant has to opt in or be configured. A timer is a property of the manifest, and the tenants it runs for are a property of the registry.

That means the host's plan for timers is ephemeral state, derived from three things it already has: the deployed manifests, the domain registry, and the rows in each source. Which rows are due, and when, is never stored as configuration; the host rebuilds the plan by reading the sources whenever it starts, takes over a partition of the work, or sees a source change. What has to survive a restart is only the progress: the active-field flips of one-shot timers, the last time each cron timer fired for each row, and the idempotency keys of completed fires. Those live in the same databases as the data they describe, so they move, back up, and fail over with it.

How that work is spread across a cluster is described in the cluster design.

## What a fire is

A fire is fired reactor style into the box, the same way the host calls goober_on_request for a request, as described in the manifest design. The host calls an export generated from the timer's name, and the only thing it hands the box is the database row, for a data-driven timer, or nothing at all, for a host-level one. There are no context values to read about the fire itself: no timer name, no key, and no scheduled time. The box does its work with the row in front of it.

```C
#include <stdint.h>

struct projects_row;

// A data-driven timer: the host passes the row that is due.
__attribute__((export_name("daily_digest")))
void daily_digest(const struct projects_row* row);

// A host-level timer: the host passes nothing.
__attribute__((export_name("release_expired_holds")))
void release_expired_holds(void);
```

Otherwise, a fire is a request in every way that matters: it has a timeout, a write set that commits as a bundle when it returns, an outbox, and a budget. The host keeps its own key for each fire, made from the timer, the row's primary key, and when the fire was due, and uses it for retries, for idempotency, and for the outbox, but that key stays in the host; the box never needs it.

## The rules of time

| question | answer |
| --- | --- |
| What if the host was down when a fire was due? | Each timer says "missed": "once" to run a single catch-up fire, or "missed": "skip" to wait for the next one. Cron timers default to once, and periodic timers default to skip. |
| What happens to a one-shot timer after it fires? | The host runs it at least once, and then turns its row's active-field to false in the same bundle, so it doesn't fire again until something sets it back to true. |
| What if a fire is still running when the next one is due? | The next one is skipped, so a slow timer never piles up on itself. |
| Can a fire happen twice? | Fires are at-least-once across the whole cluster, and the host keeps a key for each one, made from the timer, the row's primary key, and when it was due. A fire delivered to an internal route marked idempotent is deduplicated by the host using that key, so the work happens once; otherwise the box should make a repeat of the same row harmless, and the outbox uses the host's key for its idempotency. |
| What about daylight saving time? | A local time that doesn't exist, like 2:30am on the night clocks spring forward, fires at the next time that does. A local time that happens twice, when clocks fall back, fires only the first time. |
| How many fires can one schedule produce? | As many as there are active rows in its source, multiplied across every tenant in the special case where the source is scoped by {!tenant}, so the checker multiplies that bound by the fire route's worst case, and a source over an unbounded table is refused. |
| What clock does the host use? | The host's own injected clock, so tests can run a year of schedules in a second. |
| Do thousands of 6am fires all start at once? | No, the host spreads fires within a short window, so a timezone's morning is a gentle slope rather than a cliff. |

## The invariants

- **Timer routes are only ever called by the host.** They are unreachable from outside, so they carry no requirements.
- **A fire is given a row, or nothing.** Data-driven timers hand the box the row that is due, host-level timers hand it nothing, and there are no context values about the fire itself.
- **by_timer sources belong to timers.** The box can't read them as code; only the scheduler does.
- **One-shot timers disable themselves.** After an at-field fire completes, the host turns its active-field to false.
- **Every fire is a full request.** It has a timeout, a write set, an outbox, and a budget.
- **Fires are idempotent by key.** Timer, row key, and scheduled time identify a fire, everywhere it goes, and idempotent internal routes turn at-least-once into once.
- **Schedules are bounded.** The checker knows the worst case of a schedule before it ever runs.
