# Conflicts

Many manifests land on the same domains. Boxes declare routes, manifests and configs embed static content and rewrites that act as routes of their own, and sooner or later, two of them will claim the same address. We need a rule for what happens, and the rule has to be one a person can read in a manifest and predict.

## The domain comes first

The domain is the primary key of every conflict. Each domain is its own space of URLs, so /about on bobsplumbing.com and /about on anneslandscaping.com never conflict, however many manifests declare them. This is how we isolate content and different apps to different domains, while still allowing some common domains to be shared: a manifest says which domains it serves, either a list of specific domains or "*" for every domain, and conflicts only exist where those lists overlap.

| manifest A serves | manifest B serves | can they conflict? |
| --- | --- | --- |
| bobsplumbing.com | anneslandscaping.com | No; different spaces. |
| bobsplumbing.com | bobsplumbing.com | Yes, wherever their routes overlap. |
| "*" | bobsplumbing.com | Yes, on bobsplumbing.com, wherever their routes overlap. |
| "*" | "*" | Yes, on every domain, wherever their routes overlap. |

A "*" manifest and a specific one get no automatic ordering; when they overlap, priority decides, exactly as it does between two specific manifests, so which one answers is always written down rather than implied.

## What counts as a conflict

Two routes conflict when a single request could match both: an overlapping domain, the same protocol, the same verb, and paths that could match the same URL. Types count, so /jobs/{job_id : int64} and /jobs/new don't conflict, since "new" can never be an int64, while /pages/{slug : string} and /pages/about do.

| protocol | what has to overlap |
| --- | --- |
| http and sse | The path and verb. |
| mail | The address. |
| mcp | The tool or resource name. |
| internal | Nothing; internal routes are addressed by box, so two boxes can never claim the same one. |
| timer | Nothing; timers are never addressed from outside. |

Conflicts are checked across every manifest and config that serves an overlapping domain, including their static content and rewrites, so a page, a redirect, and a route in a box are all held to the same rule.

## The default: reject

By default, a conflict is rejected. The checker refuses the version that arrives second, and names the route and box it collides with. Nothing ever silently replaces something else, and an old route has to be decommissioned, by retiring the version that holds it, before its URL can be repurposed.

That rule is safe, but it is operationally difficult. Retiring a box to free one URL leaves a hole: for the time between the old box going away and the new one arriving, the URL answers nothing. And a box that does twenty things can't give up one of them without being redeployed itself.

## Priority

So every route can carry a priority, which is just a number. When routes overlap, the one with the higher priority wins, and the request resolves to that box. Routes without a priority have a priority of 0.

```json
{
	"routes": {
		"http": {
			"/jobs/{job_id : int64}": {
				"get": {
					"name": "get_job_v2",
					"response": "json:Job",
					"priority": 10,
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]]
				}
			}
		}
	}
}
```

The rules are simple enough to hold in your head:

- **A higher priority wins.** A request goes to the overlapping route with the highest priority that it matches.
- **Equal priorities conflict.** Two overlapping routes with the same priority are still rejected, so priority is always a deliberate choice, never a tie broken by accident.
- **Shadowing is always reported.** When a new route takes a URL away from an existing one, the checker warns, naming the box and route that lost it, and the approver sees the warning before the version goes live. The operating panel keeps listing shadowed routes, so nobody forgets that a box is still deployed but no longer answering some of its URLs.
- **Fully shadowed boxes are flagged.** A box whose every route has been taken by higher priorities is flagged for decommissioning, since it is costing a deployment while doing nothing.

## Peeling traffic away

Priority gives us a new way to split a box, one URL at a time. A new box can claim a single route from an old box at a higher priority, take over that one URL, and leave everything else where it was. Over time, a large box can be peeled apart into small ones without a single moment where a URL answers nothing, and without the old box ever being redeployed.

Combined with the splitting from the deployments design, this gets even finer. A higher-priority route can declare a share, so that only that share of requests resolves to it, and the rest falls through to the next route down:

```json
{
	"routes": {
		"http": {
			"/quote": {
				"post": {
					"name": "quote_v2",
					"response": "json:Quote",
					"priority": 10,
					"share": 5,
					"requirements": ["user_id"]
				}
			}
		}
	}
}
```

Here, 5% of quote requests go to quote_v2 in the new box, and the other 95% fall through to the existing quote route in the old box, assigned by the same stable hash that version splits use. That is A/B testing between two different boxes, on a single URL, with nothing redeployed but the new one. Raising the share to 100 completes the move, and the old route is reported as shadowed.

## Static content, rewrites, and priority

Static content is embedded directly in manifests and configs, and every static entry is a route at its own path, with its own priority, as described in the UI design. Rewrites are routes too, as described in the configs design. Since they all compete under the same rules, a single page in a config can override a box's route at a higher priority, a box can take a URL from a config the same way, and a whole site and a handful of dynamic routes can share one domain, interleaved URL by URL.

## The invariants

- **The domain is the primary key.** Routes on different domains never conflict, and "*" overlaps every domain.
- **Every request resolves to exactly one route.** Overlaps are either separated by priority or rejected.
- **Equal priorities never overlap.** A tie is always a refusal, never a coin toss.
- **Nothing is replaced silently.** Every route taken away by a higher priority is reported when it happens and listed in the operating panel afterwards.
- **No URL ever has a hole.** A route can be taken over by priority before the old one is retired, so moving a URL never means a moment where it answers nothing.
- **Shares fall through.** A route with a share only takes that share of requests, and the rest go to the next route down.
