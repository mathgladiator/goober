# Conflicts

Many manifests land on the same domains. Boxes declare routes, manifests and configs embed static content and rewrites that act as routes of their own, and sooner or later, two of them will claim the same address. We need a rule for what happens, and the rule has to be one a person can read in a manifest and predict.

## The domain comes first

The domain is the primary key of every conflict. Each domain is its own space of URLs, so /about on bobsplumbing.com and /about on anneslandscaping.com never conflict, however many manifests declare them. This is how we isolate content and different apps to different domains, while still allowing some common domains to be shared: a manifest says which domains it serves, either a list of specific domains or "*" for every domain, and conflicts only exist where those lists overlap.

| manifest A serves | manifest B serves | can they conflict? |
| --- | --- | --- |
| bobsplumbing.com | anneslandscaping.com | No; different spaces. |
| bobsplumbing.com | bobsplumbing.com | Yes, wherever their routes overlap. |
| "*" | bobsplumbing.com | Yes, on bobsplumbing.com, wherever their routes overlap. |
| "*" | "*" | Yes, on every domain, wherever their routes overlap. |

A "*" manifest and a specific one get no automatic ordering; when they overlap, it is a conflict like any other, and an operator decides how traffic flows between them, as described below, so which one answers is always written down rather than implied.

## What counts as a conflict

Two routes conflict when a single request could match both: an overlapping domain, the same protocol, the same verb, and paths that could match the same URL. Types count, so /jobs/{job_id : int64} and /jobs/new don't conflict, since "new" can never be an int64, while /pages/{slug : string} and /pages/about do.

| protocol | what has to overlap |
| --- | --- |
| http and sse | The path and verb. |
| mail | The address. A catch-all, "*@", never conflicts with a specific address, since it only receives what no other route claims. |
| mcp | The tool or resource name. |
| internal | Nothing; internal routes are addressed by box, so two boxes can never claim the same one. |
| timer | Nothing; timers are never addressed from outside. |

Reserved routes, listed in the reserved routes design, are never part of a conflict, since no manifest can declare them at all. Conflicts are checked across every manifest and config that serves an overlapping domain, including their static content and rewrites, so a page, a redirect, and a route in a box are all held to the same rule.

## The default: reject

A conflicting version is rejected. The checker refuses any version whose routes overlap another box's live routes on the same domain, names the route and box it collides with, and the version never gets into the system on its own. Nothing ever silently replaces something else, and nothing a manifest says can make it win: there is no priority in a manifest, because deciding who answers a URL is not the author's call. It is the operator's.

This shapes how we think about what we accept into the system. A manifest only ever describes what a box can do. Which box actually answers a contested URL, and how much of its traffic, is a decision about the running system, so it belongs to deployment and approval, where a person can see the whole picture.

## Shipping a conflict

To ship a conflict, you up-rev: you submit it as a new version, and the conflict becomes part of its approval. The approval shows every route the new version would contest, on which domains, and which boxes currently answer them, and it can't be completed without a traffic decision about how to integrate it.

That decision belongs to the operator, who has full control of the traffic plan through the deployments design's traffic controller:

| traffic decision | what happens to the contested URLs |
| --- | --- |
| Hold | The new version is approved, but the contested URLs stay with the boxes that answer them today, so the new version only answers what nobody else claims. |
| A/B test | The contested URLs are split between the old box and the new version by the same stable hash that version splits use, at a share the operator chooses, so the two can be compared on real traffic. |
| Slow roll out | The contested URLs move to the new version on a schedule, like 1%, 5%, 25%, 50%, and 100%, with the guardrails from the deployments design rolling them back on bad health. |
| Cut over | The contested URLs move to the new version all at once. |

Until a plan reaches 100%, every contested URL is answered by exactly one box per request, chosen by the plan, and the old box keeps answering the rest. When a plan completes, the old box's routes for those URLs are recorded as given up, and the operating panel lists them, so nobody forgets that a box is still deployed but no longer answering some of its URLs. A box whose every route has been given up is flagged for decommissioning, since it is costing a deployment while doing nothing.

## Peeling traffic away

The traffic plan gives us a new way to split a box, one URL at a time. A new box can contest a single route from an old box, and the operator can move just that URL, slowly or as an experiment, while everything else stays where it was. Over time, a large box can be peeled apart into small ones without a single moment where a URL answers nothing, and without the old box ever being redeployed.

## Static content and rewrites

Static content is embedded directly in manifests and configs, and every static entry is a route at its own path, as described in the UI design. Rewrites are routes too, as described in the configs design. They are held to exactly the same rule: a page, a redirect, or a box's route that contests a URL already answered on the same domain is rejected, unless it arrives as a version whose approval comes with a traffic decision. So a whole site and a handful of dynamic routes can still share one domain, interleaved URL by URL, with every overlap decided by an operator rather than by whichever manifest arrived last.

## The invariants

- **The domain is the primary key.** Routes on different domains never conflict, and "*" overlaps every domain.
- **Conflicting versions are rejected.** A manifest can't win a URL by anything it says; there is no priority in a manifest.
- **Conflicts ship through approval.** Up-rev the version, and the operator makes a traffic decision for every contested URL.
- **Every request resolves to exactly one route.** The traffic plan decides which, for every contested URL.
- **Nothing is replaced silently.** Every route given up is recorded when the plan completes and listed in the operating panel afterwards.
- **No URL ever has a hole.** The old box keeps answering until the plan moves its traffic, so moving a URL never means a moment where it answers nothing.
