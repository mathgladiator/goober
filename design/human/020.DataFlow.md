# Data Flow (DRAFT)

A box without data is just a computer having happy thoughts about numbers, so we need a way for the manifest to outline the data flow: what the box can read and write. Similar to routes, the manifest will have a data section that dives into access patterns along with access claims from a security token perspective.

```json
{
	"routes": {
		"http": {
			"/profile": {
				"get": {
					"name": "get_user",
					"response": "json",
					"requirements": []
				},
				"put": {
					"name": "put_user",
					"response": "json",
					"requirements": []
				}
			}
		}
	},
	"data": {
		"sqlite3": {
			"user_by_id": {
				"schema": "core13.schema",
				"database": "some_database",
				"table": "users",
				"pattern": "by_id",
				"id-is": "{!user_id}",
				"read": true,
				"writes": {
					"save_profile": { "kind": "upsert" },
					"rename": { "kind": "patch", "columns": ["name"] }
				}
			}
		}
	}
}
```

The user_id is a reserved identifier, set by the host after identity resolution, so a manifest never declares it and can use {!user_id} directly. The context is essentially hidden request context, like the authorization token or a look-aside table that maps a user id into a common field. This is data held uniquely by the server in a secure context.

The data section is structured as data.$provider.$strategy, where $strategy is a unique label for an access pattern strategy that scopes the permissions on the data by a well-known access pattern. The access pattern then determines the generated code, using $strategy as the namespace prefix for functions. However, a key point is that a .schema file is associated with the strategy as well, where a schema is a partial set of the database's tables, so different products can own different tables in the same database, since the platform must now handle all database migrations and strategies. We are going to place an operational burden on every database so that each can be live migrated in a sane way and they can all coexist at once. We will talk about this more in the migration design, but the important thing for right now is that a manifest is tightly coupled to a version of a schema. The manifest tools can load this schema and then stamp out structures for the box to leverage.

What we have to describe is the litany of access patterns and their implications. For example, by_id is a single row, and we can introduce by_index, which is a single-table lookup on a common column value, paginated with limits dictated by the schema and manifest. These can be locked down, and they can be code generated so that they even minimize data sharing on connections, since they are isolated queries controlled by the host. We can also leverage dynamic database names to choose an entirely different database, so that each tenant gets its own database (the SQLite + Litestream pattern), where the context converts a domain into a tenant id through the host's domain registry. As a consequence, each pattern can dictate the worker's shared memory model, since by_id and by_index can fully share a worker if and only if all the scopes used are the same. We can compute a signature of the data by combining the resolved access patterns, and then find an existing worker with that signature to reuse.

Joins, reports, and dynamic queries are described in the queries design, which adds manifest query iterators and direct SQL above these access patterns. However, once the access patterns cross the boundary where SQL bleeds into the box, we have to force the box into solo mode and also inspect the queries to ensure isolation properties. Tactically, we start with by_id and by_index, since that is how every ORM starts historically, and they provide good guarantees. It is an uphill battle to safely expose every edge case that SQL can offer, so we will start simply to build momentum. The primary escape hatch is a SQL query in the table schema, exposed as a stored procedure that requires human approval, so we have options that can be robust. There is an open question as to whether or not agents can play this game.

## Generated code

Like routes, the access pattern stamps out a header, and the interesting part is what is missing. The id for user_by_id resolves from the context, so the generator does not give the box a way to pass one in. The box asks for "the user," and the host decides which user that is.

```C
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

// Stamped out from users in core13.schema.
struct users_row {
	int64_t id;
	const char* name;
	size_t name_len;
	const char* email;
	size_t email_len;
};

// Generated for data.sqlite3.user_by_id because "read" is true.
bool user_by_id_read(struct users_row* out);

// Generated from the write named save_profile, an upsert of the whole row.
// The host stamps the id from {!user_id}.
bool user_by_id_save_profile(const struct users_row* row);

// Generated from the write named rename, a patch of exactly the listed columns.
struct user_by_id_rename_values {
	const char* name;
	size_t name_len;
};
bool user_by_id_rename(const struct user_by_id_rename_values* values);
```

The box can't read another user's row because there is no argument for another user. This is the same trick as everywhere else: we don't check the id the box hands us, we never let the box hand us an id. The memory behind any const char* belongs to the host-provided buffer for the duration of the call, and the box copies what it wants to keep.

### Every write has a name and a kind

There is no "write": true. A strategy lists its writes explicitly, each with a name and a kind, and each one becomes exactly one generated function, named after the strategy and the write. A reader of the manifest sees every way a box can change a table, and nothing else is possible.

| kind | what it does | what the box passes |
| --- | --- | --- |
| insert | Inserts a whole row, and fails if the row already exists. | The whole row. |
| update | Replaces a whole row, and fails if the row doesn't exist. | The whole row. |
| upsert | Inserts a whole row, or replaces it if it already exists. | The whole row. |
| patch | Changes exactly the columns it lists, and leaves every other column alone. | Only the listed columns. |
| patch-except | Changes every column except the ones it lists. | Every column except the listed ones. |

Every write says exactly what it is changing, because the table it writes to may change shape while the box is running, as described in the migration design. A whole row is a structure stamped out from the schema version the manifest pins, so it is implicitly locked to that version, and the host knows the meaning of every field. A patch names its columns by inclusion or by exclusion, so the host knows exactly which columns a write touches, and an old box can never blank out a column it has never heard of. Since a patch always writes all of its columns, there are no flags for "this one, but not that one"; a different set of columns is simply a different write, with its own name.

### Writes by pattern

The pattern decides which row a write lands on, and it does so in the host, so a box can never aim a write at a row outside its scope.

- **by_id** has exactly one row, the one id-is resolves to. Every kind of write targets that row, and the host stamps its id, so the generated functions take no id at all.
- **by_index** has a group of rows, the ones whose index column equals the value index-is resolves to. An insert or upsert adds a row to the group, and the host stamps the index column, so a box can't put a row into somebody else's group. An update, patch, or patch-except takes the primary key of one row, and the host checks that the row belongs to the group before it changes anything, so a box can only ever change rows it was allowed to read.

```json
{
	"data": {
		"sqlite3": {
			"orders_by_customer": {
				"schema": "orders7.schema",
				"database": "tenant_{!tenant}",
				"table": "orders",
				"pattern": "by_index",
				"index": "customer_id",
				"index-is": "{customer_id}",
				"limit": 50,
				"read": true,
				"writes": {
					"place_order": { "kind": "insert" },
					"set_status": { "kind": "patch", "columns": ["status"] },
					"edit_order": { "kind": "patch-except", "columns": ["id", "customer_id", "created_at"] }
				}
			}
		}
	}
}
```

```C
// The host stamps customer_id; the box passes the rest of the row.
bool orders_by_customer_place_order(const struct orders_row* row);

// The host checks that order_id belongs to this customer before changing status.
struct orders_by_customer_set_status_values {
	const char* status;
	size_t status_len;
};
bool orders_by_customer_set_status(int64_t order_id, const struct orders_by_customer_set_status_values* values);
```

## Where scope comes from

Scope is the root of every permission, so where it comes from has to be a small, closed set that the checker understands rather than a free-for-all. There are exactly two sources, told apart by a single character, as described in the reserved identifiers design:

| written as | example | meaning |
| --- | --- | --- |
| {!name} | {!user_id}, {!tenant}, {!email} | A reserved identifier, set only by the host after it has resolved who and where the request is. |
| {name} | {postal_code} | A route or query parameter. The caller controls it, so it is only allowed for strategies that are read-only and public, or read-only strategies on routes whose every requirement names a host role, as described in the identity design. |

There is no context field to declare: the reserved identifiers are always available, and a box that needs anything else to decide its scope reads it as ordinary data, through a strategy. As a rule, every reserved identifier that is visible to the box is part of the signature, whether or not an access pattern uses it, since a value the box can see is a value the box can leak into the next request.

## Patterns, tenants, and limits

A by_index strategy names an index that must exist in the .schema file, and the manifest sets the page size, so every query the host runs is an index seek with a known ceiling. If the index isn't in the schema, the checker refuses the manifest and explains why to the agent.

```json
{
	"data": {
		"sqlite3": {
			"orders_by_customer": {
				"schema": "orders7.schema",
				"database": "tenant_{!tenant}",
				"table": "orders",
				"pattern": "by_index",
				"index": "customer_id",
				"limit": 50,
				"read": true
			}
		}
	}
}
```

The database field is a template filled from the context, just like id-is, so a tenant id resolves into a database name, and the database name lands in the signature for free. Each tenant gets their own file, and the version comes from the .schema file itself, so the full address resolves to storage/sqlite3/$database/$version/$table and a human can read exactly where the data lives.

Because the database name decides which tenant's data a strategy can reach, there is a firm rule about what may fill it. A strategy reachable from an HTTP route, or any other route the outside world can call, may only name its database with reserved identifiers, like tenant_{!tenant}, so the tenant always comes from the domain and never from anything a caller typed. Internal routes are free to build database names from their own path arguments, like tenant_{tenant_slug}, since only the boxes in their callers list can reach them, and that is how an internal service binds to a tenant when a timer or another box hands it one. That freedom puts the burden on the human approving the box to make sure every caller passes the right tenant, so the checker refuses a database built from a path argument on any route except an internal one, and flags every internal route that does it for a person to review.

## SQL and solo

When SQL bleeds into the box, the box becomes solo, and the checker will refuse a manifest that asks for "shared" alongside it rather than quietly overriding it. The manifest is the artifact humans trust, and a manifest that says "shared" while the box runs solo is a manifest that lies. Solo by itself is not the guardrail, though; it only stops one request from leaking into the next. The real guardrail is that the connection can't see past the scope, which is exactly what a database per tenant gives us, and query inspection and human-approved stored procedures sit on top of that.
