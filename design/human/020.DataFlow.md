# Data Flow (DRAFT)

A box without data is just a computer having happy thoughts about numbers, so we need a way for the manifest to outline the data flow: what the box can read and write. Similar to routes, the manifest will have a data section that dives into access patterns along with access claims from a security token perspective.

```json
{
	"context": {
		"user_id": {
			"type": "int64",
			"source": "principal/agent"
		}
	},
	"routes": {
		"http": {
			"/profile": {
				"get": {
					"name": "get_user",
					"response": "json"
				},
				"put": {
					"name": "put_user",
					"response": "json"
				}
			}
		}
	},
	"data": {
		"sqlite3": {
			"user_by_id": {
				"schema": "core13.schema",
				"database": "some_database",
				"table": "users",
				"pattern": "by_id",
				"id_is": "{user_id}",
				"read": true,
				"write": true
			}
		}
	}
}
```

The context is essentially hidden request context, like the authorization token or a look-aside table that maps a user id into a common field. This is data held uniquely by the server in a secure context.

The data section is structured as data.$provider.$strategy, where $strategy is a unique label for an access pattern strategy that scopes the permissions on the data by a well-known access pattern. The access pattern then determines the generated code, using $strategy as the namespace prefix for functions. However, a key point is that a .schema file is associated with the strategy as well, since the platform must now handle all database migrations and strategies. We are going to place an operational burden on every database so that each can be live migrated in a sane way and they can all coexist at once. We will talk about this more in the database migration design, but the important thing for right now is that a manifest is tightly coupled to a version of a schema. The manifest tools can load this schema and then stamp out structures for the box to leverage.

What we have to describe is the litany of access patterns and their implications. For example, by_id is a single row, and we can introduce by_index, which is a single-table lookup on a common column value, paginated with limits dictated by the schema and manifest. These can be locked down, and they can be code generated so that they even minimize data sharing on connections, since they are isolated queries controlled by the host. We can also leverage dynamic database names to choose an entirely different database, so that each tenant gets its own database (the SQLite + Litestream pattern), where the context converts a domain into a tenant id via a cacheable lookup table. As a consequence, each pattern can dictate the worker's shared memory model, since by_id and by_index can fully share a worker if and only if all the scopes used are the same. We can compute a signature of the data by combining the resolved access patterns, and then find an existing worker with that signature to reuse.

However, once the access patterns cross the boundary where SQL bleeds into the box, we have to force the box into solo mode and also inspect the queries to ensure isolation properties. Tactically, we start with by_id and by_index, since that is how every ORM starts historically, and they provide good guarantees. It is an uphill battle to safely expose every edge case that SQL can offer, so we will start simply to build momentum. The primary escape hatch is a SQL query in the table schema, exposed as a stored procedure that requires human approval, so we have options that can be robust. There is an open question as to whether or not agents can play this game.

## Generated code

Like routes, the access pattern stamps out a header, and the interesting part is what is missing. The id for user_by_id resolves from the context, so the generator does not give the box a way to pass one in. The box asks for "the user," and the host decides which user that is.

```C
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

// Stamped out from users in core13.schema.
struct users_row {
	int64_t id;
	const char* name;
	size_t name_len;
	const char* email;
	size_t email_len;
};

// Generated for data.sqlite3.user_by_id because "read" is true.
bool user_by_id_read(struct users_row* out);

// Generated because "write" is true; the host stamps the id from {user_id}.
bool user_by_id_write(const struct users_row* row);
```

The box can't read another user's row because there is no argument for another user. This is the same trick as everywhere else: we don't check the id the box hands us, we never let the box hand us an id. The memory behind any const char* belongs to the host-provided buffer for the duration of the call, and the box copies what it wants to keep.

## Where context comes from

The context is the root of every scope, so where it comes from has to be a small, closed set that the checker understands rather than a free-for-all.

| source | example | meaning |
| --- | --- | --- |
| principal/* | principal/agent, principal/email | A claim from the verified security token of the request. |
| route/* | route/postal_code | A parameter from the route. The caller controls it, so it is only allowed for strategies that are read-only and public. |
| lookup/* | lookup/tenant_by_domain | A cacheable lookup table run by the host before the box wakes up, like converting a domain into a tenant id. |

A lookup is the host's code, not the box's code, so the box never gets to influence how its own scope resolves. As a rule, every context value that is visible to the box is part of the signature, whether or not an access pattern uses it, since a value the box can see is a value the box can leak into the next request.

## Patterns, tenants, and limits

A by_index strategy names an index that must exist in the .schema file, and the manifest sets the page size, so every query the host runs is an index seek with a known ceiling. If the index isn't in the schema, the checker refuses the manifest and explains why to the agent.

```json
{
	"context": {
		"tenant_id": {
			"type": "int64",
			"source": "lookup/tenant_by_domain"
		}
	},
	"data": {
		"sqlite3": {
			"orders_by_customer": {
				"schema": "orders7.schema",
				"database": "tenant_{tenant_id}",
				"table": "orders",
				"pattern": "by_index",
				"index": "customer_id",
				"limit": 50,
				"read": true
			}
		}
	}
}
```

The database field is a template filled from the context, just like id_is, so a tenant id resolves into a database name, and the database name lands in the signature for free. Each tenant gets their own file, and the version comes from the .schema file itself, so the full address resolves to storage/sqlite3/$database/$version/$table and a human can read exactly where the data lives.

## SQL and solo

When SQL bleeds into the box, the box becomes solo, and the checker will refuse a manifest that asks for "shared" alongside it rather than quietly overriding it. The manifest is the artifact humans trust, and a manifest that says "shared" while the box runs solo is a manifest that lies. Solo by itself is not the guardrail, though; it only stops one request from leaking into the next. The real guardrail is that the connection can't see past the scope, which is exactly what a database per tenant gives us, and query inspection and human-approved stored procedures sit on top of that.
