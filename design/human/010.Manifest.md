# The Manifest

This document is about the shape of the manifest, since the manifest will be the primary artifact that humans read, and we are going to make it JSON so we can move fast now. The primary concerns to contend with are: implicit context or session data, routes to the box, data the box depends on flowing inward, data flowing out of the box, services the box depends on, the lifetime or multiplicity of the box, and how boxes flow data between them, explicitly or implicitly.

The implicit assumption is that the host service is written in C++ and uses WASM as the guest provider for a box. We will associate a manifest with the WASM module and have tooling for another language (like C) so the agent can generate the right headers and body to link against. In this document, we start with C because it will help establish a reasonable estimate of the overhead of copying data in and out of the guest box.

## Start with Hello World

Let's start with the most basic example, Hello World, in the HTTP sense: a server that you can go to and say hello to.

```json
{
	"routes": {
		"http": {
			"/hello": {
				"get": {
					"name": "hello_world",
					"signal": 42,
					"response": "text"
				}
			}
		}
	}
}
```

The host acts as a router for various protocols, like HTTP as shown, and each route is defined first by the protocol spoken, then by the path, then by the verb, and so on depending on the protocol. This gives token locality to each conceptual unit of work. The verb can then define a signal, which is the linkage between the host and the guest, so that we minimize the ceremony for the guest to start executing the route. The key rule is that each signal is a box-level unique identifier, managed by tooling per box and enforced by a checker that explains the rule to an agent. Similarly, the name must also be unique, and it is used to namespace the generated code. The manifest checker will enforce both, and it will also provide guidance if a signal changes between box shape deployments. We also treat the manifest and the WASM module as an atomic deployment, since the manifest defines the binary. As such, the system will version the manifests and take control of deployments via a human approval queue. This calls for a future design of how deployments reach a running system. For now, we develop the core relationship between the manifest, host, and guest box. The above manifest will generate a C header with functions like:

```C
#include <stddef.h>
#include <stdint.h>

// Imported from the host.
void hello_world_respond_full(const char*, size_t);
void hello_world_respond_error_simple_4xx(int32_t status);
void goober_unknown_signal();

// Exported by the guest. The host calls goober_on_start once when the isolate
// is created and goober_on_request once per request.
__attribute__((export_name("goober_on_start")))
void goober_on_start();
__attribute__((export_name("goober_on_request")))
void goober_on_request(int32_t signal);
```

This gives whatever agent is building the box enough information to handle the route. For example:

```C
#include <string.h>

// There is no main: the box is a WASM reactor. Under "solo", every request gets
// a fresh isolate; under "shared", globals persist between calls.
void goober_on_start() {
	// one-time setup for the isolate
}

void goober_on_request(int32_t signal) {
	if (signal == 42) {
		const char* message = "Oh, Hello there Mr. World!";
		hello_world_respond_full(message, strlen(message));
	} else {
		goober_unknown_signal();
	}
}
```

At its core, we want to enforce the calling contract. Each request has a timeout that we measure like any responsible service, and failures to respond will be caught. Poor invocations of the API, like multiple hello_world_respond_full calls or a hello_world_respond_error_simple_4xx call with a 302 or 200 status code, are monitored like a timeout. Since we want to bias towards returning, we clamp the input of hello_world_respond_error_simple_4xx to a floor of 400 and a ceiling of 499 and also raise a flag in monitoring. Care will be taken so that agents understand the behavior, with sensible defaults and fallbacks, under the premise that a box seeks to return quickly. Having a box gives us new ways to isolate it easily, both during development and in production (shadow traffic, A/B testing, etc.), to provide runtime feedback that helps agents reason about what is in the box. Publicly, system failures will return a 500 (or another appropriate error code), while we keep detailed accounting for the reasons failures happened, and an agent can tap the telemetry system of the box in real time to take measurements during a deployment. We will talk about instrumentation and visibility in a development flow design.

Since we don't want to trust the box, we are presented with a performance concern: is the box isolated to a single request, or can it handle multiple requests, which requires some concept of a multiplexing request id? The output above is, ultimately, for an isolate that handles one request at a time. The burden of multiplexing multiple requests also implicitly converts the box into an asynchronous box, which requires the host to deliver events into the box, so the multiplexed version of the header would look like:

```C
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

struct EVENT {
	int32_t type;
	int32_t context_id;
	union {
		int32_t signal;
		// other event-related payloads
	};
};

// Imported from the host.
bool goober_is_event_request_signal(struct EVENT* event);
void hello_world_respond_full(struct EVENT* event, const char*, size_t);
void hello_world_respond_error_simple_4xx(struct EVENT* event, int32_t status);
void goober_unknown_signal(struct EVENT* event);

// Exported by the guest. The host calls goober_on_start once when the isolate
// is created and goober_on_event once per event.
__attribute__((export_name("goober_on_start")))
void goober_on_start();
__attribute__((export_name("goober_on_event")))
void goober_on_event(struct EVENT* event);
```

```C
#include <string.h>

void goober_on_start() {
	// one-time setup for the isolate
}

// The event is only valid for the duration of this call; keep its context_id
// to tie later events back to the same request.
void goober_on_event(struct EVENT* event) {
	if (goober_is_event_request_signal(event)) {
		if (event->signal == 42) {
			const char* message = "Oh, Hello there Mr. World!";
			hello_world_respond_full(event, message, strlen(message));
		} else {
			goober_unknown_signal(event);
		}
	}
}
```

This complicates the code, but that's what the throughput gods demand. Both boundaries share the reactor pattern: the box exports functions and the host calls them, so the event loop always lives in the host and never in the box. The host calls goober_on_start once when the isolate is created, which gives the box a clean place to set up state worth keeping, and then a sync box receives each request via goober_on_request while an async box receives every event, requests and completions alike, via goober_on_event.

The generator controls the entire API surface between the host and the guest, and that surface is strongly typed. The "respond_full" suffix above has a signature appropriate for a textual response with a 200 status. When we get to HTTP details, we will discuss the full range of possibilities, but the goal is to have a strongly typed route signature that outlines everything while also having a balanced vocabulary. We seek a precise shape for how a request comes in and leaves, so the box focuses on the task at hand instead of the accidental ceremony of protocols. We let the host provide a rich vocabulary, from super restricted to open and free, as this reflects a scoping taste.

We make the boundary something the manifest generator controls, since there is a tradeoff between simplicity, data sharing, and performance: the box is either sync (and simple) or async (and complex). We encode this in a behavior field within the manifest, so that a "worker" mode with a synchronous boundary gives us a nice, simple world that is easy to reason about and has minimal risk. We also place operational controls in the manifest, like a timeout in milliseconds, which defaults to 1 second; the clock starts when the request is handed off to the box. For the total timeout experience, we will have a system-wide timeout for when the system struggles to keep up, so that we abort requests if the box is too full, but that belongs in an operational design document for a later date.

```json
{
	...,
	"behavior": {
		"mode": "worker",
		"boundary": "sync",
		"timeout-ms": 2500
	}
}
```

The boundary does not decide how long the box lives; it changes the shape of how networking works between easy mode (sync) and hard mode (async). In sync, an outbound call blocks the box until it returns, while in async, the call returns later as a completion event. That choice has consequences. For example, a sync box can only work on one request at a time, so we will also have multiple parallel isolates to load balance in the future. An example is a box that converts a postal code into a city name. It will use a blocking database thread, so we are going to have the API mirror the operating model of the database client. The data provider does not choose the boundary. We bias towards sharing connections with isolated transactions, and the host will pick the right solution to maintain assurances and tolerances while balancing performance. The full discussion of data belongs in the data design.

A worker can have an extended lifetime when we explicitly hold the box open for a future request, so there is no clean "stop time," and we introduce two things. First, a lifecycle of either "solo" or "shared." Solo is a single request in a single isolate. Shared is multiple requests within the same data boundary. Second, a budget, which limits the blast radius of a rogue worker. The budget speaks operationally, while the data boundary is the scope of data allowed in and out. The budget sets the maximum number of requests that may share a worker's state, along with how long a shared box can last in total (in milliseconds, like timeout-ms). The budget applies per isolate, so parallel isolates each have their own. Whichever of the budget's "time-ms" or "requests" runs out first stops the isolate from taking requests, and then "timeout-ms" bounds the drain until final reaping. This means capacity churns in spikes, which lowers p50 latency with a nominal effect on p100, and that is better than churning on every request.

Data sharing is a prime concern, and we handle this by considering the scope and claims for the box. For example, if two requests differ in the data they require, as defined by the box's data providers and the policy that limits the box's access to data, then those requests will not share an isolate. The important detail is that the manifest resolves one scope per data strategy, along with authorization claims. Read and write do not split the scope; they only enable which operations resolve against it, which reduces redundant declarations and generated code. Routes never guarantee read-only; they only determine whether the box has access. Since a strategy's name is independent of its pattern, reads and writes can be isolated by declaring separate strategies. As a platform constraint, requests with different resolved scopes or claims will never share an isolate. This is the path from extreme isolation at elevated cost to isolation at the data boundary between requests. Beyond enabling better performance (and therefore cost control), this will mirror how humans handle and isolate risk. As an example, if a box is tied strictly to one user's data, then that box will only contain that user's data, while a box that can read all users' data can be shared. The design of data providers is coming up, so here we only contend with the ramifications of sharing, to help set the stage.

```json
{
	...,
	"behavior": {
		"mode": "worker",
		"boundary": "async",
		"lifecycle": "shared",
		"timeout-ms": 2500,
		"budget": {
			"requests": 100,
			"time-ms": 60000
		}
	}
}
```

| boundary | lifecycle | box | requests in flight | outbound calls | state | goober_on_start |
| --- | --- | --- | --- | --- | --- | --- |
| sync | solo | clean | one | block the box until they return | blows away after the request | runs for every request |
| sync | shared | clean | one at a time, with head-of-line blocking | block the box until they return | remains between requests | amortized across the budget |
| async | solo | messy | one | return later as completion events | blows away after the request | runs for every request |
| async | shared | messy | many, interleaved by context_id | return later as completion events | remains between requests | amortized across the budget |

The worker model is essentially an on-demand service with no stateful needs, such that there is no assumed state within the box beyond what is required to convert requests into responses. Workers are ephemeral, just optimized, and the point is to optimize the runtime of the box within a discipline. We will talk about additional modes, like a "service," which is a long-lived box that always runs, but that belongs in a future design document. As a design philosophy, we bias towards convention, with a sane way to override it with full configuration.

The complete reference for every field in a manifest, and for the difference between a box's manifest and a config, is the deep manifest design. Routes are registered in the manifest by protocol, and every protocol shares the same shape of protocol, then path or name, then verb. The protocols are http for the outside world, internal for other boxes, sse for subscriptions, mail for email, mcp for agents, and timer for time, each described in its own design.

Manifest keys follow one naming rule everywhere. Keys that the platform defines, like timeout-ms, max-body-bytes, or allow-self-revoke, are lowercase words joined by hyphens. Names that people choose, like route names, strategy labels, context variables, and type fields, use underscores instead, since they become identifiers in generated code, like hello_world_respond_full. A hyphen means the platform said it, and an underscore means somebody named it. Keys that come from a borrowed format, like OpenAPI's operationId or additionalProperties, keep that format's spelling.

The schema described in this section, with reasonable defaults for what the prose does not mention. Types are written the way OpenAPI writes them, as described in the JSON design:

| field | type | default | description |
| --- | --- | --- | --- |
| `domains` | array of string | required | The domains this manifest applies to, or `"*"` for every domain, as described in the domains and conflicts designs. |
| `static.<path>` | object | none | Static content embedded as `content` (a string) or `content-base64`, with a `content-type`, served by the host at exactly that path, as described in the UI design. |
| `templates.<name>` | string | none | A Mustache template, embedded by name. |
| `headers.<name>` | object | none | A header property with a `value` and a `priority`, as described in the configs design. |
| `rewrites` | array of object | none | Rewrite and redirect rules, as described in the configs design. |
| `routes.http.<path>.<verb>` | object | none | An http route, keyed path, then verb; written as `<route>` below. |
| `routes.internal.<path>.<verb>` | object | none | An internal route, shaped like an http route but only reachable by other boxes, as described in the internal messaging design. |
| `<route>.name` | string | required | Unique within the box; namespaces the generated code. |
| `<route>.signal` | integer (int32) | assigned by tooling | Unique within the box; links the route between host and guest. |
| `<route>.response` | `"text"` | `"text"` | The response shape; `"text"` is a textual response with a 200 status. |
| `<route>.priority` | integer (int32) | `0` | When routes overlap, the higher priority answers; equal priorities are refused, as described in the conflicts design. |
| `<route>.share` | integer (int32) | `100` | The percentage of matching requests this route takes; the rest fall through to the next route down. |
| `<route>.callers` | array of string | required for internal routes | The boxes allowed to call an internal route; an internal route without callers is refused. |
| `behavior.mode` | `"worker"` | `"worker"` | The only mode for now; `"service"` is a future design. |
| `behavior.boundary` | `"sync"` \| `"async"` | `"sync"` | Whether the box handles one request at a time or multiplexes events. |
| `behavior.lifecycle` | `"solo"` \| `"shared"` | `"solo"` | Whether each request gets a fresh isolate or requests within the same data boundary share one. |
| `behavior.timeout-ms` | integer (int32) | `1000` | Per-request timeout, starting when the request is handed off to the box; also bounds the drain. |
| `behavior.budget.requests` | integer (int32) | `100` | Only for `"shared"`: the maximum number of requests each isolate accepts. |
| `behavior.budget.time-ms` | integer (int32) | `60000` | Only for `"shared"`: how long each isolate accepts requests before it drains. |
