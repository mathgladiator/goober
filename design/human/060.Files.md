# Uploading and File IO

We think about uploading attachments as a new flow within the host, and we leverage a database to keep track of uploads as they happen. The reason we do this is to provide garbage collection to a degree. When a user attaches a file, the host treats it as a preprocessing step for the request, using a table in SQLite that is private to the host, and then it will:

* create an upload row, to get an id and mark that a resource is starting to be written (to disk or S3),
* put the content on disk fully, using the id, in the directory indicated by the upload route, and
* update the row to record that the upload is done.

The generated code then has a file-like API for reading the asset in a meaningful way, and a long-term endeavor is to mirror the file IO of existing POSIX, such that existing algorithms or image tools can work. This is a research endeavor, but it would be nice to have a safe file system for the box to read from. In a similar way, we can leverage this same model to invert the flow, such that boxes can generate files. This provides a file system to the box that is more classical, but also under the complete control of the host at the boundary.

A classical problem with uploading is taking ownership of an upload in a meaningful way, so the generated code will have the ability to attach a file to a row in a database, and the host will detect this, such that the upload row is associated with a database, table, and column. This allows the system to do a mark and sweep to keep orphans from piling up.

## Reasoning as a preprocessing step

The reason we think about uploading files as a different step is that uploads are a thorny point for browsers, and we want to support the fullness of devices, beyond a traditional multipart MIME upload. As such, we make it possible to break up the HTTP transaction, and to leverage resumable uploads as a future feature, or the newfangled browser APIs for streaming. This is why upload is its own verb in the manifest. It is not an HTTP method; it is a promise that the host handles the transfer however the device needs it, whether that is one multipart POST today or a resumable series of requests later, and the box only wakes up once the bytes are complete.

Furthermore, we do this because the host has configuration for additional preprocessing steps, since the host bears the cost burden of uploads. All these rules are enforced by content type, as detected from the bytes rather than as claimed by the device.

| content type | preprocessing |
| --- | --- |
| Images | Resized to a sane size from what cameras generate, and stripped of private information and metadata, like the GPS location that phones embed in every photo, so that we hold as little private data as possible. |
| Archives | Checked for dangerous uploads, like zip bombs, by limiting the expanded size, the number of entries, and the nesting depth before anything is accepted. |
| Everything else | Checked that the bytes match the declared type, and refused if the type isn't one the store allows. |

## The upload ledger

The host keeps one ledger per tenant, in the tenant's own directory, so the ledger moves, backs up, and gets deleted along with everything else the tenant owns.

```sql
CREATE TABLE uploads (
	id INTEGER PRIMARY KEY,
	store TEXT NOT NULL,                  -- the objects strategy, like 'job_photos'
	folder TEXT NOT NULL,                 -- the route's folder, resolved, like 'attachments/bobs_plumbing/8812'
	state TEXT NOT NULL,                  -- 'writing', 'stored', 'attached', 'asset', or 'orphaned'
	content_type TEXT,                    -- as detected from the bytes, not as claimed
	size INTEGER,
	sha256 TEXT,
	created_at INTEGER NOT NULL,
	stored_at INTEGER,
	committed_at INTEGER,                 -- when the request that received it committed
	attached_database TEXT,               -- where the reference lives, once attached
	attached_table TEXT,
	attached_column TEXT,
	attached_row INTEGER,
	attached_at INTEGER,
	orphaned_at INTEGER
);
```

The file itself lives in the route's resolved folder, named by the upload's id, so the ledger row is all it takes to find the bytes, and nothing about the location is ever handed to the box.

Every upload walks through the same states:

| state | meaning | what moves it on |
| --- | --- | --- |
| writing | The row exists, and bytes are arriving, possibly across several requests. | The last byte lands and passes preprocessing, or the transfer is abandoned. |
| stored | The bytes are complete, checked, and durable, and the box has a handle. | The request commits, and the upload is either attached, kept as an asset, or orphaned. |
| attached | A row in a database refers to it, so it belongs to that row. | That row stops referring to it. |
| asset | The route marked it as an asset, like a static file for serving, so it is kept without a row. | It is explicitly deleted. |
| orphaned | It was committed without an owner, or its owner let go. | The sweeper removes it. |

The order of the three steps is what makes this safe. The ledger row is written before the first byte, so if the host crashes halfway through, there is a "writing" row pointing at a partial file, and the sweeper knows to clean it up. There is never a file on disk that the ledger doesn't know about.

## Uploading through a route

A route opts into uploads with the upload verb, naming the objects store from the UI design that holds the files and the folder within it where they land. The host does the preprocessing before the box wakes up: it receives the bytes into the backing tree, runs the steps for the content type, and only then runs the request.

```json
{
	"routes": {
		"http": {
			"/jobs/{job_id : int64}/photos": {
				"upload": {
					"name": "add_job_photo",
					"store": "job_photos",
					"folder": "attachments/{tenant}/{job_id}",
					"response": "json:Job",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"], ["member/{tenant}"]]
				}
			},
			"/site/images": {
				"upload": {
					"name": "add_site_image",
					"store": "site_images",
					"folder": "site/{tenant}",
					"asset": true,
					"response": "json:Image",
					"requirements": [["owner/{tenant}"], ["admin/{tenant}"]]
				}
			}
		}
	}
}
```

The folder is a location in the host's backing tree, not something the box or the browser ever sees. It is filled in from the secure context and the route's parameters, under the identity design's rule that no substituted value may contain "/", so a job_id of "../../other" is rejected before anything is written, and an upload can never land outside its own directory. Since the tenant comes from the secure context, an upload can never land in another tenant's tree.

The box gets a handle for each uploaded file. A handle is just a number that means something to the host for the duration of the request; it isn't a path, and it can't be turned into one.

## The file-like API

Reading an upload looks like reading a file, because that is what every library already knows how to do.

```C
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

// Handles for the files uploaded with this request.
int32_t add_job_photo_upload_count();
int64_t add_job_photo_upload_handle(int32_t index);

// Reading.
int64_t goober_file_size(int64_t handle);
const char* goober_file_content_type(int64_t handle);
int64_t goober_file_read(int64_t handle, int64_t offset, void* buffer, size_t len);

// Writing a new file that the box generates, like an invoice PDF or a thumbnail.
int64_t job_photos_create(const char* content_type, size_t content_type_len);
bool goober_file_write(int64_t handle, const void* buffer, size_t len);
bool goober_file_close(int64_t handle);
```

Reads take an offset rather than keeping a hidden position, so there is no cursor to get wrong. A box writing a file creates it in a store, writes it, and closes it, and when it closes, it goes through the same preprocessing as an upload and lands in the ledger as "stored." Generated files and uploaded files are the same thing from then on, including the rule that they must be owned by the time the request commits.

## Taking ownership

Ownership comes from the data, not from the box's good intentions. A column in a .schema file can be declared as a reference to an objects store, and when the box writes a row whose column holds a handle, the host records the attachment in the ledger.

```sql
CREATE TABLE job_photos (
	id INTEGER PRIMARY KEY,
	job_id INTEGER NOT NULL,
	photo INTEGER NOT NULL                -- goober: object(job_photos)
);
```

The attachment rides the write set, just like the write that carries it. When the request commits, every upload it received is settled in that same moment: an upload referenced by a committed row becomes "attached," an upload received by a route marked as an asset becomes an "asset," and anything else becomes "orphaned." When a later request overwrites the column or deletes the row, the upload becomes "orphaned" in that commit.

As a forcing function, unless a route marks the upload as an asset, like a static file for serving, a file that isn't associated with a row by the time its request commits is orphaned right away. A box that forgets to save the reference finds out on the very first try, in development, rather than months later, and nobody wakes up to discover that the photos they thought they had saved were never owned by anything.

This doesn't stop a product from letting someone upload a photo now and press save later; it just makes that a product decision rather than a platform one. A product that wants it gives the upload an isolated commit of its own, into the product's own uploads table, with an object column that owns the file. The save then makes it live, either by flipping a flag on that row or by copying the reference into the row where it belongs, and the product has access to everything a person uploaded before. The goal is system-level garbage collection, not product-level garbage collection: the platform guarantees that no byte is ever stranded, and the product decides what "draft" means.

## Asset data routes

An asset has no row to own it, so it needs its own way to be read and deleted. An asset data route is a route the host fulfills by itself, with no box involved: it names a store and a folder, and it declares which operations it allows, each with its own requirements.

```json
{
	"routes": {
		"http": {
			"/site/images/{asset_id : int64}": {
				"asset": {
					"name": "site_image",
					"store": "site_images",
					"folder": "site/{tenant}",
					"read": {
						"public": true
					},
					"delete": {
						"requirements": [["owner/{tenant}"], ["admin/{tenant}"]]
					}
				}
			},
			"/site/images/": {
				"asset": {
					"name": "site_images",
					"store": "site_images",
					"folder": "site/{tenant}",
					"list": {
						"requirements": [["owner/{tenant}"], ["admin/{tenant}"]]
					}
				}
			}
		}
	}
}
```

| operation | HTTP | what the host does |
| --- | --- | --- |
| read | GET | Streams the asset's bytes, with its detected content type, content-addressed caching, and range requests, the same as static content. Executable types are still served as downloads. |
| delete | DELETE | Orphans the asset in the ledger, so the sweeper removes it like anything else. |
| list | GET on the folder | Lists the assets directly in that one folder, and nothing above or beside it, under the listing rules from the UI design. |

An operation that isn't declared doesn't exist, so a route with only read can't be used to delete, and a route without list never reveals what is in its folder. Each operation follows the identity design's deny-by-default rule on its own: it needs requirements, or an explicit "public": true. A public read beside an admin-only delete is the common case, as in the site images above.

Boxes can work with assets too, through generated functions scoped to the store and its folder, so a box can only ever reach assets in the folder its context resolves to.

```C
#include <stdbool.h>
#include <stdint.h>

// Opens an existing asset for reading with the file-like API; returns a handle, or -1 if not found.
int64_t site_images_open(int64_t asset_id);

// Deletes an asset by orphaning it; rides the write set, so it only happens if the request commits.
bool site_images_delete(int64_t asset_id);
```

Deleting an asset, from a route or from a box, never removes bytes on the spot. It orphans the asset in the ledger, the sweeper does the rest, and the bytes still outlive the backup retention, so an accidental delete is recoverable by restoring, exactly like a row.

## Mark and sweep

The sweeper runs as a host-level timer, and for each tenant, it operates on exactly two kinds of upload:

1. **Super old uncommitted work.** An upload that is still "writing" or "stored," but whose request never committed, because a transfer was abandoned partway or the host crashed, is swept once it has gone 7 days without an association. Seven days is long enough to resume a large upload from a phone that lost its signal, and short enough that abandoned bytes don't pile up.
2. **Committed but not associated.** An upload that is "orphaned," because its request committed without attaching it, or because its owner let go of it later, is swept on the next run.

Because every reference lives in a column the schema declared, the host also knows exactly where to look to double-check its own ledger. Before it sweeps, it marks every handle referenced by the tenant's declared object columns, and it never sweeps an upload that was marked, or one that changed state after the mark began. The ledger is the plan, and the mark is the proof.

Sweeping an upload ends its life as far as boxes and browsers are concerned, but the bytes are kept until the backup retention has passed, so restoring a database to yesterday never brings back a row that points at a file that is already gone.

## Toward a real file system

The long-term research endeavor is to let a box use files as POSIX knows them, so that existing tools, like image libraries compiled to WASM, work without being rewritten. WASI already has the right shape for this: a box can be handed a pre-opened directory, and it can only see what is inside. For each request, the host can build a small virtual directory holding just that request's uploads, read-only, plus a scratch directory for output, so an existing tool can open a file by name while the box still can't reach anything else. When the request ends, whatever the box wrote to its output directory goes through the same preprocessing and into the ledger, and everything else disappears with the request.

## The invariants

- **The ledger knows about every byte.** A row is written before any bytes, so there are no files the host can't account for.
- **Bytes are preprocessed before the box sees them.** Size, type, metadata stripping, and dangerous-content checks all happen first.
- **Handles are not paths.** A box reads and writes through handles and never learns where anything lives.
- **Folders can't escape.** Substituted values can't contain "/", and the tenant comes from the secure context.
- **Every upload is settled when its request commits.** It is attached, an asset, or orphaned, with nothing in between.
- **Assets are only reached through declared operations.** Reading, deleting, and listing each exist only when a route or a store declares them, each with its own requirements.
- **Deleting is orphaning.** Every delete goes through the ledger and the sweeper, so there is one way bytes ever leave.
- **Orphans are swept, never stranded.** Uncommitted work goes after 7 days, and committed but unassociated work goes on the next run.
- **Sweeping never outruns backups.** Bytes outlive the backup retention, even after the upload is gone.
