# The Working Set

Static bundles are great for deploying an entire site, but they are annoying for small, frequent changes. An agent like Grok that wants to fix one paragraph shouldn't have to assemble a whole bundle, and a content writer shouldn't have to wait for a release to see their words on the real page. A CMS could be a hyper-specific box, but publishing content is common enough that the platform should give everyone a simpler path. That path is the working set.

## What the working set is

A working set is a live, editable copy of a manifest's static content and templates that sits on top of what is deployed. It can hold any static entry, including markdown, raw HTML, Mustache templates, and base64-encoded assets, so templates can arrive as a bundle or as a single updated entry. Changes to the working set take effect immediately, but only for the people allowed to see it: the content writers and admins who are working on the content, and the agents acting for them. Everyone else keeps seeing the live, approved content until the working set is approved and goes live.

This gives us production development without production risk. Writers and agents edit on the real domain, at the real URLs, with the real templates and real data around them, and the public never sees anything that hasn't been approved.

## Who sees it

A working set is enabled on a manifest, usually a config that carries a site's static content, along with the requirements for editing it and for approving it.

```json
{
	"config": "bobs-site",
	"domains": ["bobsplumbing.com"],
	"working-set": {
		"edit": [["editor/{tenant}"], ["admin/{tenant}"], ["owner/{tenant}"]],
		"approve": [["admin/{tenant}"], ["owner/{tenant}"]]
	},
	"static": {
		"/": {
			"content-type": "text/markdown",
			"content": "# Bob's Plumbing",
			"public": true
		}
	}
}
```

| caller | sees |
| --- | --- |
| Anyone who passes edit, or an agent acting for them | The working set laid over the live content, so their edits show up at the real URLs right away. |
| Everyone else | The live content only, exactly as if the working set didn't exist. |

Because the working set changes what a person sees, it is part of the signature: a request that sees the working set never shares an isolate, a cache entry, or an ETag with one that doesn't, so a draft can't leak into the public cache.

## How an agent publishes

Editing is a host feature, offered as plain HTTP for people and as MCP tools for agents, with the same requirements.

| tool | does |
| --- | --- |
| working_set_put | Writes one static entry or template into the working set, like the page at /about or the template named page. |
| working_set_delete | Marks one static entry or template as deleted in the working set. |
| working_set_diff | Shows everything the working set changes compared with what is live. |
| working_set_check | Runs the checker on the working set as it stands, without submitting it. |
| working_set_submit | Freezes the working set into a bundle version and submits it for approval. |
| working_set_discard | Throws the working set away. |

So when Grok wants to fix one paragraph, it puts one entry, looks at the real page as its person would see it, and either keeps going or submits. There is nothing to assemble and nothing to upload in bulk.

## From working set to live

1. **Edit.** Writers and agents put and delete entries. Each change is recorded with who made it, so the working set has its own history.
2. **Check.** The rogue content checks from the static bundles design run on every change, so a working set that grows a password field or a script from an unknown origin is flagged right away, not just at the end.
3. **Submit.** Submitting freezes the working set into a new, immutable version of the manifest, named by its hash, exactly like a version that was uploaded whole.
4. **Approve.** Someone who passes approve reads the diff and the checker's report, and approves or declines it.
5. **Go live.** The approved version unbundles into routes and replaces the live content, and the working set starts empty again on top of the new live content.

Nothing in the working set ever bypasses approval. It is only a faster way to build the bundle that gets approved.

## When the live content changes underneath

If a bundle goes live while someone has a working set open, the working set stays on top of the new live content. An entry the working set never touched simply shows the new live version. An entry that both the working set and the new release changed is marked as conflicting in working_set_diff, and the working set can't be submitted until each conflict is resolved by keeping one side or writing a new version. This is the same idea as the conflicts design, applied to entries: nothing is ever silently overwritten.

## The invariants

- **The public only ever sees approved content.** The working set is visible only to those who pass edit and their agents.
- **A draft never leaks through a cache.** Seeing the working set is part of the signature, for isolates, caches, and ETags alike.
- **Every change is checked as it is made.** Rogue content is flagged during editing, not just at approval.
- **Submitting makes an ordinary version.** A working set becomes an immutable, hash-named manifest version and goes through the same approval as any other.
- **Concurrent changes are never silently overwritten.** Entries changed both in the working set and in a new release must be resolved before submitting.
