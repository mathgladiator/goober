# Primary Keys

The host (and the cluster) generates ids, since this gives us better properties across the board: each id belongs to exactly one row in any database. This means the host is responsible for managing id range leases, which can be scoped per thread. An id range lease is simply an id_start and a length, and ids are handed out by incrementing within it. All ids are 64-bit, so this will last a while.

In the cluster environment, this requires the registration service to maintain a counter for vending lease ranges.

All ids come from this id service, without exception: rows in every box's databases, user ids in every identity realm, uploads in the ledger, and anything else the host keys by an id. So an id never needs a table, a tenant, or a realm next to it to mean exactly one thing.

## Why the host owns ids

A box never chooses a primary key. The id service only applies to the creation of new rows: when a box inserts a row whose primary key isn't bound by the strategy, the host stamps a fresh id on it, and the generated insert hands the new id back to the box, so it can use it in the same request, like putting a new job's id into the email that announces it. Upserts are fine as they are, since a by_id upsert targets the row id-is resolves to, like {!user_id}, and that id was already minted by the id service when the user was created.

Because every id comes from one counter, an id is unique across every table, every database, and every tenant on the host or the cluster, not just within its table. That one property pays off all over the design:

| where | why a globally unique id helps |
| --- | --- |
| Moving and merging tenants | A tenant's database can be moved to another host, or merged with another database, without any two rows ever colliding. |
| References between databases | A row in one database can point at a row in another by id alone, with no question of which table or tenant it meant. |
| Files | An object column holds an upload's id, and that id means exactly one file anywhere, as described in the files design. |
| Idempotency and traces | Outbox elements, timers, and traces can use ids as keys without worrying that two databases minted the same one. |
| Audits | An id in an audit row, a log, or a support ticket names exactly one thing, with no table or tenant needed to make sense of it. |
| Boxes can't forge rows | A box can't pick an id, so it can't aim an insert at a row it wasn't meant to create or guess its way into an existing one. |

## Range leases

Handing out ids one at a time from a central counter would be far too slow, so the counter hands out ranges, and each range is used up locally.

| level | holds | gets more from |
| --- | --- | --- |
| The counter | The next unused id, for the whole host or cluster | Nothing; it only ever moves forward. |
| A host | A range, like a million ids at a time | The counter, through the registration service in a cluster, or the platform's own database on a single machine. |
| A thread | A small slice of its host's range, like a thousand ids | Its host, in memory, with no lock on the hot path. |

```sql
-- On a single machine, in the platform's own database; in a cluster, held by the registration service.
CREATE TABLE id_counter (
	next_id INTEGER NOT NULL              -- the first id that has never been vended
);

-- Every range ever vended, for audit and debugging.
CREATE TABLE id_ranges (
	id_start INTEGER PRIMARY KEY,
	length INTEGER NOT NULL,
	vended_to TEXT NOT NULL,              -- the host that received it
	vended_at INTEGER NOT NULL
);
```

The counter moves forward durably before a range is handed out, so a range can never be vended twice, even if the host or the registration service crashes the moment after.

The counter is the one thing that can break uniqueness, since a restore that rewinds it would vend ids a second time. So on a single machine, the counter is backed up along with the data, and shares the same failure domain as the backups: whatever restores the data also restores the counter. On restore, the host moves the counter past the highest id in any restored database, and then jumps it ahead by a safety margin, so no id that ever left the host, even one written after the last backup, can be minted again. A range is never returned or reused: when a host dies, the rest of its range is simply lost. That leaves gaps, and gaps are fine, since an id only promises to be unique, never to be dense.

Unlike the leases in the cluster design, a range lease needs no epoch and no expiry. Ownership of a service or a database can move from host to host, so it needs fencing, but a range is only ever vended once, so there is nothing for a stale host to collide with. A host that wakes up after a long pause and keeps using its old range is still minting ids that nobody else can ever mint.

## Ids in JSON are strings

Every id crosses JSON as a string, like "8812", never as a number. JavaScript holds numbers as doubles, which lose precision above 2^53, so an id that travels as a number can silently become a different id in a browser. Inside the box and in the database, an id is still an int64; the host converts it to a string on the way out and back on the way in, so the box never thinks about it, and every client, typed or not, gets ids it can't corrupt.

## Volume doesn't leak

Since every database shares one counter, and hosts take ranges of 10,000 ids or more at a time, the ids a single tenant sees jump around in ways that say nothing about its own volume. Invoice 1,204,331 followed a week later by invoice 1,290,002 means the cluster was busy, or a host restarted and lost the rest of its range, not that a business sent 85,000 invoices. That is the point of a shared counter: an id is unique everywhere, and a business's growth can't be read off its ids.

## The numbers

- **Ids are positive.** They start at 1, and 0 and negative values are never minted, so 0 can mean "no row" in generated code.
- **The space is 2^63.** Even at a million ids per second, the counter would take nearly 300,000 years to run out.
- **Ids are increasing, but not ordered by time.** Within one thread's slice, ids go up, but two hosts working from different ranges mint ids out of order relative to each other. Anything that needs time order uses a timestamp column, never the id.

## The invariants

- **Only the host mints ids.** A box never chooses a primary key; the insert returns the one the host stamped.
- **An id names exactly one row, anywhere.** Ids are unique across every table, database, and tenant.
- **All ids come from the id service.** Rows, users, uploads, and everything else the host keys by id.
- **Ids are strings in JSON.** They are int64 inside, and never lose precision in a browser.
- **A range is vended once.** The counter moves forward durably before a range leaves it, ranges are never reused, and the counter is backed up with the data so a restore never rewinds it.
- **Gaps are allowed, and order isn't promised.** An id is unique, not dense and not a clock.
