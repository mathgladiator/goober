# Static Bundles

Similar to deployments, static content is bundled up and deployed like a box, and this enables the same A/B testing, while shadow testing doesn't make sense. This also provides a way to protect against rogue content when the system is used as a content management system. The same deployment system works with content as bundles, and bundles include raw markdown, raw HTML, and Mustache templates.

## What a bundle is

A bundle is a config, which is to say a manifest with no box, as described in the configs design, whose job is to carry static content. Its pages, styles, templates, and small assets are embedded directly in it, as plain strings or base64-encoded strings, exactly as the UI design describes. Like a box version, it is named by the hash of its contents, it can't be edited once it is minted, and a change is always a new bundle version.

```json
{
	"config": "bobs-site",
	"domains": ["bobsplumbing.com"],
	"templates": {
		"page": "<!doctype html><html><head><title>{{title}}</title></head><body>{{{body}}}</body></html>"
	},
	"static": {
		"/": {
			"content-type": "text/markdown",
			"content": "---\ntitle: Bob's Plumbing\ntemplate: page\n---\n\n# We fix things",
			"public": true
		},
		"/handbook": {
			"content-type": "text/markdown",
			"content": "# Employee handbook",
			"requirements": [["owner/{!tenant}"], ["admin/{!tenant}"], ["member/{!tenant}"]]
		}
	},
	"content-security": {
		"allow-origins": ["https://maps.example.com"],
		"scripts": false,
		"forms": false
	}
}
```

| part | what it holds |
| --- | --- |
| Markdown | Pages, rendered through the bundle's templates with front matter, as in the UI design. |
| Raw HTML | Hand-built pages, served as written, within the bundle's content security rules. |
| Mustache templates | Layouts for the bundle's own markdown pages. |
| Assets | Styles, fonts, icons, and small images, base64-encoded, content-addressed for caching. |

The static and requirements rules are exactly the ones from the UI design: nothing is served without requirements or "public": true, and the manifest's domains decide where it applies. A bundle is not a tenant-level concern: like any manifest, it applies to the domains it lists, so a bundle for bobsplumbing.com is Bob's site, and a bundle for "*" is something every domain shares.

## Unbundling at deployment

A bundle is a convenient way to ship many pages at once, but it doesn't stay a bundle once it is deployed. When a bundle goes live, the host unbundles it: every static entry becomes its own route, with its own generated manifest entry, carrying its requirements and headers. From then on, a page from a bundle is just a route on its domain, so URLs from different bundles and boxes can be mixed freely, and the conflicts design decides which one answers when two of them claim the same URL.

## Bundles and boxes

A box embeds its own UI in its own manifest, so its pages are part of the box's version and deploy, shadow, and split with it as one fixed unit. A bundle is content that lives on its own schedule: a business's website, a handbook, a set of help pages. Keeping them apart means Bob can fix a typo on his about page without anyone deploying a box, and a box can be upgraded without anyone touching Bob's words.

When a bundle and a box both claim the same path on the same domain, the conflicts design decides: the second one is rejected, unless it arrives as a version whose approval comes with a traffic decision from the operator. Since bundles unbundle into routes, a single page can even take over a box's route that way, or the reverse.

## The life of a bundle

Bundles move through the same lifecycle as box versions, minus shadowing:

```
uploaded → checked → approved → splitting → live → retired
```

Shadowing doesn't make sense for content, since content has no side effects to compare: there are no writes to discard and no calls to fail, only pages that are either shown or not. Splitting, on the other hand, makes perfect sense, since "which version of the home page gets more people to call" is exactly the question A/B testing answers.

Uploading and approving bundles are host features, gated by grant roles like everything else. For content that changes often, the working set design gives writers and agents a faster way to build the bundle that gets approved, with the requirements for editing and approving declared in the manifest, so a product can let an editor upload and an owner approve without involving the platform's operators at all:

| action | typical requirement |
| --- | --- |
| Upload a bundle | editor/{!tenant}, admin/{!tenant}, or owner/{!tenant} |
| Approve a bundle | admin/{!tenant} or owner/{!tenant} |
| Split or roll back | admin/{!tenant} or owner/{!tenant} |

An agent working for an editor can upload bundles through MCP like any other action, and still can't approve one unless its person can.

## Protecting against rogue content

When the system is used as a content management system, the danger isn't a crashing box; it is content that looks like a page but does something else. An editor's account is phished, an agent is talked into "improving" a page, or a pasted snippet carries a tracker. The checker reviews every bundle before it can be approved, and its report is what the approver reads.

| check | what it catches |
| --- | --- |
| Scripts | Any script in raw HTML is refused unless the bundle allows scripts, and even then, scripts can only come from the bundle's own files, never inline. |
| Forms | Any form is refused unless the bundle allows forms, and even then, a form can only submit to the tenant's own routes. A password or card field outside the identity screens is always refused, since that is what a phishing page looks like. |
| External origins | Images, frames, styles, and links to other sites can only come from origins the bundle lists, so a tracker or a look-alike login page can't sneak in through a pasted snippet. |
| Markdown | Raw HTML inside markdown stays off, as in the UI design. |
| Templates | Every template must parse and must only use values the page provides. |
| Executable files | HTML and SVG uploaded as assets are always served as downloads. |
| Links | Links to pages that don't exist in the bundle are reported, so a release doesn't ship broken navigation. |
| Secrets | Anything that looks like a key or a password is reported, since content is published to the world. |
| Size | Bundles and individual files have limits, and big jumps in size are reported. |

The report also shows what changed, in plain words: pages added, removed, and changed, with a text diff of each change, plus every new external origin, script, and form. Unlike the comparison report for boxes, a bundle's diff can show its content freely, since a bundle is something the tenant is publishing, not somebody's personal data. The approver sees exactly what will be published, and a page that suddenly grows a login form in a release about fixing a typo is impossible to miss.

## Splitting content

Splitting a bundle works exactly like splitting a box version. Visitors are assigned by a stable hash of the user_id for signed-in visitors, or of the IP address for anonymous ones, so a person sees the same version of the site throughout an experiment. The share moves up a ladder, like 1%, 5%, 25%, 50%, and 100%, and the operating panel compares the two versions from the access log: which pages people visit next, how long pages take to load, and which routes they lead to, such as a booking form or a call link.

Rolling back is instant, since the previous bundle stays deployed until the new one is fully live, so a broken release costs a click.

## Where bundles live

Bundles live in the host's one backing tree from the UI design, each version in its own folder named by its hash, with its static content unpacked for serving. An old version is only removed after it has been retired for longer than the backup retention, so restoring yesterday's data never points at content that is gone.

## The invariants

- **A bundle is immutable, and its id is its hash.** Any change is a new bundle.
- **No bundle is served without approval.** Uploading and approving are separate, and both are gated by grant roles.
- **Content can't become a weapon.** Scripts, forms, and outside origins only appear when the bundle declares them, and never inline.
- **Approvers see exactly what will be published.** Every change comes with a plain diff and a list of new scripts, forms, and origins.
- **Bundles unbundle into routes.** Once deployed, every static entry is its own route, and conflicts are resolved through approval and traffic plans like any other route.
- **Rolling back is instant.** The previous bundle keeps serving until the new one is fully live.
