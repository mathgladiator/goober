# Managing Keys

The keys design describes how keys are stored and used. This document is about the people who look after them: the host's operators, holding host roles, who need to manage keys without ever seeing them, and who need to know, quickly and specifically, when a request is failing because a key isn't there.

## Who manages which keys

| scope | managed by | where |
| --- | --- | --- |
| system | Host operators with host:owner, or a host role the owner grants for keys | The keys section of the operating panel |
| tenant | The tenant's owner, and host operators acting for them | The tenant's account pages, and the operating panel |
| user | The person the key belongs to | Their own account page, as described in the keys design |

Host operators can see every key's metadata in every scope, but never a value. Only the owners of tenant and user keys enter or replace them, with the one exception that a host operator can act inside a tenant, as described in the identity design, and that action is recorded like any other.

## What the panel shows

The keys section of the operating panel lists every key by its name, its scope, and its owner, the same way the secrets table stores it. For each one, it shows what an operator needs to look after it, and nothing that could leak it:

| field | meaning |
| --- | --- |
| Name, scope, owner | Like keys/tenant/bobs_plumbing/ses. |
| Fingerprint | A short keyed hash, enough to tell two values apart, never enough to recover one. |
| Created, last rotated | When the value was entered, and when it last changed. |
| Last used, uses this week | From the key access log, by name and purpose. |
| Referenced by | Every deployed manifest and external service that names this key. |
| Recent failures | Calls that failed because this key was missing or rejected, with counts. |

Values are write-only. Once a key is entered, nobody can read it back, through the panel, through an agent, or through any API; replacing it is the only way to change it.

## Missing keys are the platform's failure

A request that needs a key the host can't find is not the box's fault and not the caller's fault: the manifest named a key, and nobody has provided it yet. So it is really a 500. The host stops the request before the call goes out, throws away its bundle, and answers with a 500, while recording exactly what was missing:

| recorded | meaning |
| --- | --- |
| The key name | Like keys/tenant/{!tenant}/ses, resolved to the tenant or user it was for. |
| The box, version, and route | What was trying to use it. |
| The request_id | To join with the access log and the audits, as described in the operating panel. |
| The kind of failure | Missing, meaning no value exists, or rejected, meaning the service turned the value down, as when an API key has expired or been revoked. |

A rejected key gets the same treatment as a missing one. A service that answers 401 or 403 to a call made with a key is telling us the key is wrong, which is the platform's problem to surface, not the box's to handle.

## Urgent key requests

Every missing or rejected key becomes an urgent key request, a queue in the keys section of the panel sorted by how many requests are failing and how recently. Each entry says which key is needed, for whom, by which boxes, and how many requests it has cost so far, so an operator can see at a glance that, say, Bob's Plumbing has failed 40 receipt emails in the last hour because its SES key was never entered.

The request also goes to whoever can actually fix it:

| scope | who is asked |
| --- | --- |
| system | The host operators, through the panel, and through the notifications the host sends for anything urgent. |
| tenant | The tenant's owner, on their account pages and by email from the system mailer, since a tenant's own mailer may be the very key that is missing. |
| user | The person, the next time they sign in, with a prompt naming the product that needs the key and what it is for, using the label from the manifest. |

When the key is entered or replaced, the request closes itself as soon as a call with the new value succeeds, so the queue only ever shows what is still broken.

## Catching it before it happens

Some missing keys can be caught before any request fails. When a version is checked for deployment, the checker looks up every system key its manifest names, and warns the approver about any that don't exist yet. Tenant and user keys can't be known ahead, since every tenant and person provides their own, so the panel offers a coverage view instead: for each key a deployed manifest declares, how many tenants or people have provided it, and which ones haven't.

## Rotating and revoking

The keys section is also where rotation happens, using the mechanics from the keys design:

- **Rotating the root key** asks the vault to rewrap every data key, and is a handful of vault calls.
- **Rotating a data key** starts a new version and re-encrypts secrets in the background, with progress shown in the panel.
- **Revoking a key** deletes its value immediately, after which any request that needs it fails as missing and shows up as an urgent key request, which is exactly what an operator wants to see after pulling a compromised key.

Every one of these actions, along with every entry, replacement, and deletion of a value, lands in the audit with who did it and when, but never with the value itself.

## For agentic operators

The operations MCP surface offers keys as read-only tools: listing keys and their metadata, the coverage view, and the urgent key requests, so an agent can find out why requests are failing and tell a person exactly which key to enter. Agents can't enter, replace, rotate, or revoke keys; a value only ever comes from a person, typed into a host screen.

## The invariants

- **Nobody can read a key back.** Values are write-only; the panel shows fingerprints, never values.
- **A missing or rejected key is a 500.** The host stops the request, discards its bundle, and records exactly what was missing.
- **Every missing key becomes an urgent key request.** It is queued for operators and sent to whoever can fix it, and it closes itself once a call succeeds.
- **System keys are checked before deployment.** Tenant and user keys are covered by the coverage view.
- **Agents can see keys' metadata, never change them.** Values only come from people.
- **Every key action is audited.** Who did what and when, never what the value was.
