# What's new on a goober host

Served by the `whats_new` tool, built into the binary: each entry is something agents and
engineers can do now, newest first, with the tools to use. A host has every entry up to its
build (`host_health`'s `build`). Add an entry with every change agents should know about.

## 2026-10-31

- log_search, access_log, and the panel's Logs view read each log back from its end, so the newest lines come back in milliseconds however big today's file is; answers are the same. host_health's ready (and /goober/ready) has a disk check: free_bytes, total_bytes, low (under 10% or 2 GiB, a warning), failing under 256 MiB. Tell the human when disk is low.
- db_export {tenant, database, sql, params?}: for private rows (emails, names) that shouldn't pass through an agent. Runs one read-only statement like db_query (up to 100000 rows) and answers {export, rows, columns, bytes, sha256, expires, fetch}, never a row: the CSV is sealed on the server, kept 7 days, and a person fetches it with `goober-host export get <export>`. Audited; never waits for approval.
- Roles a box grants and revokes (013; 006 § 3.1): a post, put, patch, or delete route with requirements declares "grantable" and "revocable": {"options": [roles], "to": "{!user_id}" or "{param}", "allow-self-revoke"?}. The box calls goober_role_grant / goober_role_revoke (Rust: goober::role_grant, role_revoke) with one of the options; the change lands when the call commits, never in a try or a 5xx. Pages and routes gate on these roles like any other (page_put fields.requirements). Agents' calls can't change roles; options are tenant roles only; a caller-chosen scope must be checked by the requirements. version_upload lists new options as widenings; the realm's audit (realm_get) and the host's audit log (role.grant, role.revoke) name the box.
- "client-ip": true on a post, put, patch, or delete HTTP route hands the box client_ip, the address the request came from (a consent record that must say where it was given). Refused on a GET; other route kinds have no such field. version_upload's review lists it as a widening; every call that receives it is an audit-log line (client_ip, with the address as a keyed hash); route_try hands 192.0.2.1.
- Schema columns take "description" (what the column holds, for people, 1 to 500 characters) and "references": "<table>" (a table of the same schema whose key the column holds; the column is that key's type, id or int64; schema_check verifies it, it silences the reference warning, and nothing enforces it as a foreign key). Changing either is an annotation step that applies at once. schema_get returns them as stored; db_describe shows each column's from the newest schema applied; the panel's database view too.
- Box SQL takes named savepoints: SAVEPOINT x, ROLLBACK TO x, RELEASE x, inside the host's transaction, so a job step that fails can undo its writes and still commit a FAILED marker in the same call. Names starting goober_ are refused; RELEASE and ROLLBACK TO must name a savepoint the call opened in that database; BEGIN, COMMIT, END, and ROLLBACK stay refused; one left open commits with the call.
- schema_apply {tenant, database, schema, dry_run?}: applies a stored schema to one database now. A schema otherwise applies lazily, on the first call that opens the database for a box naming it, never at promote, so a database nothing calls stays where it was. From what is applied it walks the line (v1 applied, naming v4: v2, v3, v4 in one transaction), snapshot first when a step drops or rewrites data; answers each step's changes, the snapshot, applied_before and applied_after, and named_by. dry_run changes nothing. Refused when a step waits for a person or an upgrade box.
- version_promote, a live version_upload, and box_enable answer schemas: each schema the version names, per database, "applied" or "pending" (with the schema_apply call that applies it now).
- A step lists annotation-only changes ("not-a-reference" added or removed) as kind annotation; nothing stored changes.
- A forced step (say, a required column with no default) needs no person when its tables are empty in every database on an older version and no active box on an older version writes them: schema_check answers held: false and immediate. Checked again as it applies.
- A walk of several versions (v1 to v4) snapshots before a rewrite in a later step too.
- Inside a box, count(*), count(1), SELECT 1, and EXISTS (SELECT 1 ...) work under any read grant on the table, even "read": ["id"].
- operator_scope answers operator, the name every log records your calls under (token:$name, oauth:$email:$client, or config for host.json's shared operations.token, with a note to ask for a token of your own). Every agent should hold its own token: goober-host token create --name <who>.
- A deep link's #fragment survives every return= flow, not just the gate's redirect: <!--#include keep-fragment--> (in the built-in base template; add it to your own layout) loads /goober/keep-fragment.js, which appends the page's #fragment to each <input name="return" data-fragment> and to the return= of each link to /identity/sign-in or marked data-keep-fragment. A box's own consent or gate page does the same and redirects to the return it gets back. site_guide's "Deep links" section.
- route_try {internal: "<route>", caller: "<box>", arguments?: {path, query, body}, as?} calls an internal route of any stored version as that caller would through goober_call (caller must be in its callers; the same path, type, and requirement checks), on copies. Internal routes are in no HTTP route table: one at /x never answers or shadows the site's /x. A box with no http, mcp, or mail routes claims no path; its "domains" only say which tenants' data it serves.
- job_dry_run {box, job, tenant, version?} runs a stored version that isn't live (dark or older) on copies, without promoting it; its pass counts as a try (version_promote's tried), and job_start runs once that version is promoted. job_start's version is a check: a real run is always of the live version.
- box_failures lists failed tries and dry runs apart, under tries (each with trial: route_try or job_dry_run), so a failed dry run says why; they count in no rate. A job batch the host couldn't take (an answer without a cursor, a cursor that didn't move) is class job_failed.
- version_get answers module_sha256 (hex SHA-256 of the stored binary module; a wat upload is stored compiled) and module_bytes; version_upload answers module_sha256 too, so a reviewer can match the bytes to their build.
- Change sets: one change made of schema adds, box versions, content, and flag values. changeset_create {title, why}, changeset_add {id, schemas?, versions? ({box, version, tries?} or {manifest, wat | wasm_base64}), content? ({tenant, pages?, files?} or {tenant, from_stage: true}), flags?}, changeset_preview {id} (every member's dry run, one widens list; stores nothing), changeset_apply {id} (snapshots, then schemas, versions, content, flags; a failure undoes what applied), changeset_rollback {id, force?} (all of it, in reverse; refused over later changes unless forced; schemas stay), changeset_show, changeset_list, changeset_discard. Drafts never wait for approval; apply and rollback do.
- route_try {timer, at_ms?, row?} fires a stored version's timer route once, dark versions too, as the scheduler would, on copies: at_ms is the fire's now (the box's now_ms); a by_timer source fires the named row or the row due first, and a fired at-field row is turned off in the copies. Answers due, row, ok, and the changes and would-be deliveries, like any try on copies.
- version_promote answers tried (each route_try kind by tenant, a job_dry_run, or "live" for a version that ran live before) and, for a version nothing tried, a warning. It never refuses: try, promote, then version_health.
- Schemas evolve (design/machine/041.SchemaEvolution.md): a schema's next version names the one it replaces, "follows": "orders1", and its tables replace that one's. schema_check and schema_put answer the step (each change: expansion, contraction, indexing, emulated, forced, refused, with a sentence and its consequences), held, and what it would do to each database holding the old version. Expansions, indexing, and int32 to int64, float to double, allowing null, or a longer max-length apply when a box names the version. Dropped columns and tables wait for a person to approve the schema in the panel (db_unbound's held_schemas); then older boxes read the default and their writes are dropped, and a dropped name is never used again. A primary key never changes. The box guide's "Changing a schema" has it all.
- Upgrade boxes: routes.upgrade.$table {from, to, rows: {name}} in a box with nothing else; the handler gets one row in the old shape as its body and answers it in the new shape. upgrade_dry_run {box} runs it on copies of every database and names failing rows; upgrade_start {box} runs it for real after a passed dry run and a person's approval, each database snapshotted first. Both wait until no box pinned to the old version uses the table.
- Error pages: content_put {tenant, path: "error-message/404.html", text} (or 403, 500, ...) is the page a browser gets when the host answers that status. It is a template ({{status}}, {{reason}}, {{request_id}}, the site's data), "layout: base" front matter wraps it in the site's layout, and partials work; it renders for a visitor with no session. /error-message/... itself answers 404 and no sitemap lists it; page_put refuses that path. site_guide's "Error pages" lists the statuses.
- A box route's 4xx with an empty body gets the site's error page for it (an API caller gets the host's JSON); a 4xx with a body keeps the box's body.
- error_report {window, tenant?}: every 4xx and 5xx visitors and clients got, against all requests, by status and by place (a box route, a page, a host area, or "(not found)" for every path nothing answers), split by error_by (host, box, box_failed) and by whether a link on this site, another site, or none led there. The panel's Errors view.
- box_failures {window, tenant?, box?, latest?}: every box call (requests, tools, timers, mail, jobs, internal calls) and how it failed, by class (trap, timeout, out_of_fuel, failed, bad_response, bad_status, render_failed, commit_failed, ...; sql_error, no_clock, refused_write per statement; delivery_retry, delivery_dead; internal_failed; mail_rejected, mail_deferred), per box and route, with the latest messages and request ids. The panel's Box failures view.
- The sitemap's icicle (uri_tree) holds the site's own traffic: requests the host refused before any box ran ("(refused)") and paths nothing answers ("(not found)") stay out; a box route's own errors stay on it. Access lines say error_by and ref (same or other site).

- route_try reaches MCP tools ({tool, arguments, as: {email}}) and mail routes ({mail: {to, from, subject, text, headers?}}, answered with the SMTP reply), always on copies; a try's mail sender is never verified. Observers and the panel may try HTTP GETs and HEADs only.
- version_health reads every access-log file still on the machine (7 days) for its window, not only the newest two, and leaves out route_try's calls.
- partial_put, partial_delete, and content_put take if_etag (the file_etag you read, or "none" for a new one): no write lands over a teammate's change made since you read it. Every content write now can.
- Every version_upload (live, activate: false, dry_run) answers review and widens: each change that adds reach (a grant, a write, a route made public, a new mail address, service, From address, domain, browser caching, flag value), in sentences; a person approving a held upload sees them. version_diff {box, from?, to?} compares stored versions; version_list shows stored_at.
- version_health {box, minutes?}: after a version goes live, compares each route's failures and latency with the version it replaced, and names the version_promote that rolls back. Nothing rolls back by itself.
- content_deploy {dry_run: true} runs every check, renders each URL signed out from the would-be files, lints it, and answers status, body_etag, and problems; nothing is stored, and it never waits for approval.
- content_stage builds one content deploy over several calls (kept an hour); content_deploy {tenant, stage: true} deploys the whole draft at once, with every check first.
- page_lint {body, path, format} lints an unsaved page; page_render {as: "signed_out"} shows what a visitor gets (a gated page's 303 or 401); content_deploy items take expect_status and expect_location, verified signed out.
- Title and description lengths count characters, not bytes (title_chars).
- route_try: call any stored version's HTTP route (dark ones too) as signed_out or as an account ({email}), before version_promote. GETs read live data read-only; writes run on copies and report the rows they changed and what they would have queued. Nothing reaches people or real data.
- whats_new: this list, by day; call it after a deploy or a reconnect to learn what arrived.
- A real job_start snapshots every database the box may write before its first batch (the run's snapshots name them); db_restore_to_new brings the data back as it was.
- A deep link's #fragment survives signing in (/docs/guide#install lands on #install after the code).
- Box SQL has no clock: 'now', CURRENT_TIMESTAMP and its kin, and date functions with no value are refused, and the statement is undone; pass the call's now_ms (datetime(:now_ms / 1000, 'unixepoch')). Operators' db_query keeps the clock.
- The id service's first id is 4294967297 (2^32 + 1): every new id is past the 32-bit range; treat ids as 64-bit strings everywhere.
- Mail routes get from_user_id (a string) when the host verifies the sender (a DKIM signature aligned with the From domain) and the address belongs to an active account; otherwise null, with sender_why.
- Route caching, opt-in per GET route: "cache": {"by": "data" | "wake", "fresh-ms", "browser-ms", "check-percent"}; 304s without the box; sampled checks; cache_status, cache_clear.
- Performance reports: perf_report (per-route time split and findings: cacheable, missing_index, lock_wait, get_writes, subscription_churn, cache_mismatch, browser_cache) and perf_statements; the panel's Performance view.
- Every operator tool says whether it is a read tool or a changing tool (waits for approval when an agent's approvals are on), what it returns, and whether it goes live, is stored dark, or stores nothing. The operator server's instructions define the shared terms.
- Box flags: a manifest's "flags" declares switches; boxes read goober_flag(name) (Rust: goober::flag); operators set flag_set {tenant, box, flag, value, reason} and read flag_list. A freeze needs no new version.
- Databases: db_create (from stored schemas, empty), db_snapshot, db_snapshots, db_restore_to_new, db_unbound. Drops happen only in the panel, by a person, with a snapshot first.
- Schemas: "not-a-reference": true on a column silences the reference warning; types accept const; pattern is refused (no safe regex engine yet).
- Moving a route between boxes: a disabled box holds no names. version_upload {activate: false} warns on a clash; box_disable the old box, version_promote the new; roll back the same way in reverse.
- version_upload {dry_run: true, schemas: [...]} checks a manifest against schemas not stored yet.
- Templates take if_etag (template_put, template_delete); template_get and template_list return file_etag; list_etags covers templates and partials.
- Every answer from a templated box route carries Vary: Accept.
- Write tools answer change_id / change_ids (numbers) for the change log rows they made.
- Etags are named everywhere: file_etag (the stored file's, what if_etag compares) and body_etag (the served body's).
- version_upload {dry_run: true} never waits for approval; source_checkout is a read tool; mail_unsubscribed with "set" waits for approval.

## 2026-10-30

- Ids: one id service mints users, invites, uploads, and rows keyed {"type": "id", "primary-key": true}; a box never names a key; ids are strings in JSON; ids_status.
- Jobs: routes.job, one-time boxes an operator starts; job_dry_run on copies first, then job_start; batches with a kept cursor; job_list, job_status, job_stop.
- Account deletion: from /identity/account or user_delete; boxes get routes.identity "deleted" and erase within 30 days; deletions.
- Mail: mail_domain_check (MX, SPF, DMARC, SES DKIM), mail_route_check, the SMTP listener in host_health, test sends in mail_activity.
- Source: source_stage builds one commit over several calls; schema_check; version_upload {activate: false} stores a version dark; box_disable / box_enable.
- Box pages render inside the site's layout (layout: base front matter); box_render previews them; version_upload {dry_run: true}.
- Redirect domains (www. to the site); deploys offer them.
- The panel: source projects, revisions, diffs, build logs; grants down to the table (grant_usage).
- GETs change nothing: a GET or HEAD that tries to write is refused.
